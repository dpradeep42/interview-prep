@p17-132 | What is thread pool starvation, and how do you detect it?
Thread pool starvation happens when all thread pool threads are busy, usually blocked waiting, so new work, like incoming requests or async continuations, has to wait for a free thread. The thread pool adds new threads slowly, roughly one or two per second once it's above the minimum, so under load, response times explode while CPU stays low.

The most common cause is sync over async: calling .Result or .Wait or GetAwaiter().GetResult on async code. The thread blocks waiting for an operation whose continuation also needs a thread pool thread, so under load, threads are all blocked waiting for each other. Other causes are long synchronous I/O, like a synchronous database or file call, Thread.Sleep, or long locks in hot paths.

The symptoms: requests get very slow or time out, the thread count keeps climbing, and CPU isn't high. Health checks may time out too, causing restarts.

To detect it, I use dotnet-counters and watch the thread pool queue length and thread count; a growing queue is the signal. A memory dump or dotnet-stack shows many threads blocked in the same place, like waiting on a Task.

The fix is to make the call chain async all the way, remove blocking calls, and use async APIs for I/O. Raising the minimum threads is only a temporary relief.

@p17-133 | How do you call async code from synchronous code safely?
The best answer is to avoid it, by making the calling code async as well, all the way up. In ASP.NET Core, controllers, middleware, hosted services and even Main can be async, so there's almost always a way.

When I truly can't, for example in a legacy interface that I can't change, or a constructor, there are some options and risks.

Blocking with .Result, .Wait or GetAwaiter().GetResult works, but it blocks a thread. In apps with a synchronisation context, like classic ASP.NET on .NET Framework, WinForms or WPF, it can deadlock: the async method tries to resume on the context that's blocked waiting for it. ASP.NET Core has no synchronisation context, so it doesn't deadlock there, but blocking still wastes threads and can cause thread pool starvation under load. If I must block, GetAwaiter().GetResult is preferable to .Result, because it throws the original exception instead of an AggregateException, and in libraries, ConfigureAwait of false reduces deadlock risk.

For constructors, I avoid async work entirely. Instead I use an async factory method, like CreateAsync, or lazy async initialisation, or do the work in a hosted service at startup.

For event handlers in desktop apps, async void with try-catch is acceptable.

Our legacy .NET Framework code had a few of these deadlocks, so this is a real concern in our migration.

@p17-134 | What is a race condition? Give an example.
A race condition is a bug where the result depends on the timing of two or more operations that run concurrently, so it works most of the time and fails occasionally, which makes it hard to reproduce.

A classic example is check-then-act. Two requests try to reserve the last kit at a site. Both read the stock and see one available. Both pass the check. Both reserve it. Now we've allocated two kits when only one existed. Each request was correct on its own; the problem is the interleaving.

Another example is a shared counter incremented by many threads without synchronisation, where updates are lost, or a lazy cache initialised twice.

Race conditions happen both in memory and in databases, and with multiple server instances, an in-memory lock doesn't help at all.

Fixes depend on where the shared state lives. In memory: locks, Interlocked, or concurrent collections. In the database: make the check and update one atomic operation, like UPDATE with a WHERE condition on the available quantity and checking the rows affected, use optimistic concurrency with a row version, or a unique constraint so the second insert fails. Across instances: a distributed lock, or a single queue consumer per key.

In our IRT, kit allocation uses database transactions and concurrency checks for exactly this reason.

@p17-135 | What is Lazy<T>, and how does it work?
Lazy of T defers creating an object until it's first needed, and then caches it. I give it a factory function, and the first time I read its Value property, it runs the factory and stores the result. Later reads return the same instance without running the factory again.

It's useful when an object is expensive to create, like loading a large lookup table or building a complex client, and it may not be needed in every code path, so I don't pay the cost at startup or at all if unused.

It's also thread-safe by default. With the default mode, ExecutionAndPublication, if many threads read Value at the same time, only one runs the factory, and the others wait and get the same result. That makes it a simple way to implement a thread-safe singleton or a one-time initialisation, and it's the standard trick to make ConcurrentDictionary's GetOrAdd run the factory only once.

One gotcha: if the factory throws, Lazy caches the exception by default, and every later access rethrows it. That's bad for transient failures, like a network error at startup. In that case, I use the PublicationOnly mode, or a custom approach that retries.

For async initialisation, Lazy of Task of T works, though libraries like AsyncLazy handle retry and cancellation better.

@p17-136 | throw vs throw ex: what is the difference?
Both rethrow an exception from a catch block, but they treat the stack trace differently.

throw, on its own, rethrows the current exception and preserves its original stack trace, so I can still see where the error really happened, deep in the call chain.

throw ex resets the stack trace to the current location, the catch block. All information about where the exception actually originated is lost, which makes debugging production issues much harder. Code analysis tools flag it as a warning.

So inside a catch block, if I want to log something and let the exception continue, I use plain throw.

If I want to add context, I wrap it: throw new ShipmentProcessingException with a useful message and the original exception as the inner exception. Then both the new context and the original stack trace are preserved.

If I need to rethrow an exception later, outside the catch block, for example after capturing it in one thread and rethrowing on another, ExceptionDispatchInfo.Capture and Throw preserve the original stack trace. That's what await does internally.

And often the best choice is not to catch at all. I only catch when I can handle the exception, add useful context, or translate it, and let global exception handling deal with the rest.

@p17-137 | What are exception filters in C#?
Exception filters let me add a condition to a catch block using the when keyword, like catch HttpRequestException when ex.StatusCode equals NotFound. The catch block only runs if the condition is true; otherwise the exception keeps propagating as if that catch block didn't exist.

There are a few advantages over catching and then rethrowing inside an if statement.

The stack isn't unwound when the filter is evaluated. If the filter returns false, the exception continues with its original state intact, which makes debugging and crash dumps more useful.

The code is cleaner, especially with several catch blocks for the same exception type but different conditions, like handling a SqlException differently for a deadlock, error number 1205, versus a unique constraint violation, 2627 or 2601.

A neat trick is logging in a filter: catch Exception when LogAndReturnFalse of ex. The filter logs the exception at the point where it happened, with the full stack, and returns false, so the exception isn't actually caught and continues upwards.

Polly-style transient error checks also benefit, for example catching only specific HTTP status codes for a retry.

Filters should be quick and must not throw, because an exception inside a filter is swallowed and treated as false.

@p17-138 | Exceptions vs the Result pattern: which do you prefer for business errors?
Exceptions are for exceptional, unexpected situations, like a database being down, a bug, or a broken invariant. They're expensive to throw, they're invisible in method signatures, and using them for normal business outcomes, like "validation failed" or "stock not available", turns control flow into hidden jumps.

The Result pattern makes the expected outcome explicit. A method returns a Result object that is either success with a value or failure with an error, like a code and message. The caller must handle both cases, and the signature tells you the operation can fail. It's also faster, because no exception is thrown.

In practice, I use both. Expected business failures, like a validation error, a not-found entity, a rule violation such as "site not active", or a conflict, return a Result. The API layer maps it to the right HTTP response: 400, 404, 409 or 422 with ProblemDetails. Unexpected technical failures throw exceptions, which go to the global exception handler, are logged, and become a 500.

Libraries like FluentResults, ErrorOr or OneOf help, or a small custom Result type.

The main downside is more verbose code, and teams must apply it consistently.

In our newer IRT APIs, MediatR handlers return results for business rules, and FluentValidation errors become 400 responses automatically.

@p17-139 | System.Text.Json vs Newtonsoft.Json: what are the differences?
System.Text.Json is the built-in serialiser in modern .NET, and ASP.NET Core's default. Newtonsoft.Json, or Json.NET, is the older, very popular third-party library.

System.Text.Json is faster and allocates less, because it works on UTF-8 bytes and spans, and it supports source generation for even better performance and Native AOT. It's secure by default and strict: case-sensitive property matching by default outside ASP.NET Core, no comments or trailing commas unless enabled, and no automatic loosely typed conversions, like a number in a string.

Newtonsoft is more feature-rich and flexible: very lenient parsing, JObject and LINQ to JSON for dynamic JSON, rich converters, reference loop handling, and many settings. A lot of older code and libraries depend on it.

System.Text.Json has caught up a lot: polymorphic serialisation with JsonDerivedType, JsonNode for dynamic documents, required properties, ReferenceHandler for cycles, and naming policies including snake case.

When migrating, the differences that bite are case sensitivity, how enums, dates and nulls are handled, private setters, and custom converters, which must be rewritten.

My approach: System.Text.Json for new code, with web defaults; Newtonsoft only where a legacy behaviour or library needs it. In our legacy .NET Framework code, Newtonsoft is still used.

@p17-140 | Ordinal vs culture-sensitive string comparison: why does it matter?
String comparisons can be ordinal, comparing the raw character codes, or culture-sensitive, following the linguistic rules of a culture, like how accented letters sort.

The problem is that some methods are culture-sensitive by default, like string.Compare, StartsWith with a string argument, and ToUpper and ToLower, so the result can change depending on the server's culture settings. The famous example is the Turkish I problem: in Turkish culture, the uppercase of "i" isn't "I", so a case-insensitive check like "file".ToUpper() equals "FILE" fails on a Turkish machine. Bugs like this appear only for certain users or servers.

Culture-sensitive comparison is also slower than ordinal.

So my rule is: for identifiers, codes, keys, file paths, URLs, HTTP headers, configuration keys and anything machine-readable, use ordinal comparison, StringComparison.Ordinal or OrdinalIgnoreCase. For dictionary keys that should be case-insensitive, pass StringComparer.OrdinalIgnoreCase. Only use culture-sensitive comparison for text shown to and sorted for users, with the user's culture explicitly.

I always pass the StringComparison argument explicitly, and the code analysers, CA1307 and CA1309, help enforce it.

For normalising case, I use ToUpperInvariant, not ToUpper.

In a global product with sites in many countries, like ours, this matters.

@p17-141 | Explain the Strategy pattern with a real example.
The Strategy pattern defines a family of interchangeable algorithms behind one interface, so the calling code can pick one at runtime without knowing the details. It replaces big if-else or switch blocks that choose behaviour based on a type or setting.

For example, imagine calculating resupply quantities for sites, where studies use different methods: a simple min and max level, or a predictive method based on upcoming visits. Instead of one method with a growing switch statement, I define an interface, IResupplyStrategy, with a method like CalculateQuantity. Then I write MinMaxResupplyStrategy and PredictiveResupplyStrategy, each with its own logic and its own unit tests. The calling service gets the right strategy, based on the study's configuration, and just calls CalculateQuantity.

With dependency injection, I register all strategies, inject an IEnumerable of them, and pick by a key property, or use .NET 8 keyed services, resolving by the strategy name.

The benefits: each algorithm is isolated and testable, adding a new one doesn't touch existing code, which is the open-closed principle, and the choice can come from configuration.

The pluggable SFTP providers I built are also a Strategy: one interface, three provider implementations, selected by configuration.

I don't use it for two simple cases; an if statement is fine there.

@p17-142 | Explain the Decorator pattern and how you use it with dependency injection.
The Decorator pattern wraps an object with another object that implements the same interface, adding behaviour before or after delegating to the wrapped one. The caller doesn't know it's talking to a decorator. Decorators can be stacked.

It's perfect for cross-cutting concerns that I don't want inside the business class: caching, logging, retries, timing metrics or authorization checks.

For example, I have an IStudyConfigProvider that reads study configuration from the database. I write a CachedStudyConfigProvider that also implements IStudyConfigProvider, takes the real provider in its constructor, and checks the cache first, only calling the inner provider on a miss. The database class stays simple, and caching can be added, removed or tested separately.

In ASP.NET Core's built-in DI, registering decorators is a bit manual: I register the inner class, then register the interface with a factory that creates the decorator around it. The Scrutor library makes it one line with services.Decorate.

The framework uses the pattern a lot too: DelegatingHandler for HttpClient is a decorator chain, where each handler adds behaviour like logging or auth headers. MediatR pipeline behaviours work the same way around handlers. And Stream wrappers, like BufferedStream or GZipStream, are decorators.

@p17-143 | Explain the Factory pattern, and when you need a factory with DI.
A factory is an object or method whose job is creating other objects, so the calling code doesn't need to know which concrete class to create or how to build it.

The Factory Method lets a method decide which class to instantiate, often based on input, like a NotificationSenderFactory that returns an EmailSender or SmsSender based on the channel. The Abstract Factory creates families of related objects that belong together.

With dependency injection, most object creation is handled by the container, so I need fewer factories. But I still use them when: the concrete type depends on runtime data, like the study's configuration or a user's choice, which the container can't know at startup; the object needs both injected services and runtime parameters, like a file processor that needs a logger and a file path; or creation is complex and needs validation.

In .NET, the factory itself is registered in DI and gets its dependencies injected. It can use IServiceProvider internally, carefully, or ActivatorUtilities.CreateInstance, which builds an object using DI for services plus the runtime parameters I pass. Keyed services in .NET 8 often replace simple factories that choose by name. IHttpClientFactory and IDbContextFactory are framework examples.

I avoid factories that just wrap new for no reason.
