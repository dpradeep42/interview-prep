@p17-2 | How do you define microservice boundaries?
I define microservice boundaries around business capabilities, not around technical layers or database tables. The main tool is domain-driven design: I find the bounded contexts, the places where a word like "shipment" or "subject" has one clear meaning and one team owns the rules.

Then I check a few signals. First, data ownership: each service should own its data, and no other service should write to its tables. Second, change together, live together: if two things always change in the same release, they probably belong in one service. Third, communication: if two services need many chatty synchronous calls to finish one request, the boundary is probably wrong. Fourth, team ownership: one team should be able to own and deploy a service on its own.

I also avoid going too small. Nano-services that each hold one table create network calls, distributed transactions and operational cost with no real benefit.

In our IRT, for example, randomisation, supply and shipments, drug accountability and notifications are natural boundaries, because each has its own rules, data and users. When in doubt, I start with a well-structured modular monolith and split a module out only when there's a clear reason, like independent scaling or a separate team.

@p17-3 | Service A calls Service B, and B calls Service C. Service C becomes very slow. How do you troubleshoot it?
When a chain like A to B to C gets slow, my first job is to prove where the time is going, and my second job is to stop the slowness from spreading.

To find it, I use distributed tracing with a correlation id. A trace shows each hop with its duration, so I can see that A waits on B, and B waits on C. Then I look at C's own metrics: latency percentiles, error rate, CPU, memory, thread pool, database time and any of its own downstream calls. Usually the cause is in C's dependency, like a slow query, a lock, a missing index, or an external API, or it's resource saturation after a traffic jump or a recent release.

While fixing C, I protect A and B. Every call has a timeout, so B doesn't wait forever. Retries are limited, with backoff and jitter, so we don't hammer C even harder. A circuit breaker on B's calls to C fails fast when C is unhealthy, and B returns a fallback or a clear error. Bulkheads keep C's slowness from using up all of B's threads or connections.

Long term, I ask whether the chain needs to be synchronous at all. If B only needs to inform C, a message on a queue removes the dependency completely.

@p17-4 | How do you implement a circuit breaker?
A circuit breaker stops calling a dependency that is clearly failing, so we fail fast instead of piling up slow requests. It has three states. Closed is normal: calls go through, and failures are counted. When failures cross a threshold, for example more than half of calls failing within 30 seconds with at least 20 calls, the breaker opens. While open, calls fail immediately without touching the dependency. After a break duration, it goes half-open and lets a few trial calls through. If they succeed, it closes again; if not, it opens again.

In .NET I implement it with Polly, which is now built into Microsoft.Extensions.Http.Resilience. On a typed HttpClient, I add a resilience pipeline with a timeout, a retry with exponential backoff and jitter, and a circuit breaker, in that order, so retries happen inside the breaker's view. I configure the failure ratio, sampling duration, minimum throughput and break duration.

When the circuit is open, the caller gets a BrokenCircuitException, and I handle it with a fallback: cached data, a default, or a clear 503 to the client. I also log state changes and add metrics, so we get an alert when a breaker opens.

The key is to only count real failures, like timeouts and 5xx, not 404s or validation errors.

@p17-5 | How should you secure microservices, and what type of authentication should you implement?
I secure microservices in layers, and for authentication I use OAuth 2.0 and OpenID Connect with JWT access tokens from a central identity provider, never home-grown logins in each service.

For users, the front end signs in through the identity provider with the authorization code flow with PKCE. The provider issues a short-lived access token, a JWT, and each API validates it: the signature against the provider's public keys, the issuer, the audience and the expiry. Then authorization is done with roles, scopes or policies in each service, because only the service knows its own rules.

For service-to-service calls, I use the client credentials flow, so each service has its own identity and only the scopes it needs. On top of that, mutual TLS or a service mesh can encrypt and authenticate traffic inside the network.

Around authentication, there's the rest: an API gateway for rate limiting and a single entry point, HTTPS everywhere, secrets in a vault, least privilege on databases, input validation, and audit logging.

In our IRT, Keycloak is the identity provider. The React app uses OIDC, our newer .NET APIs validate Keycloak JWTs with the bearer handler, and permissions come from role, module and action rules.

@p17-6 | In which layer do you implement authentication: frontend, middleware or backend?
Authentication must be enforced on the backend, normally in the API's middleware, and the frontend only helps the user sign in and carry the token. The rule is simple: never trust the client, because anyone can change JavaScript in the browser or call the API directly with a tool like Postman.

So the layers work like this. The frontend redirects the user to the identity provider, receives the tokens, stores them safely, and attaches the access token to every API call, for example with an axios interceptor or an Angular HTTP interceptor. It can also hide menus the user can't use, but that's only for user experience, not security.

In the backend, ASP.NET Core's authentication middleware validates the JWT on every request, before any controller runs, and builds the user's identity. Then authorization checks roles and policies, with attributes or policies on endpoints, and sometimes resource-level checks in the business logic, like "can this user see this site's data".

An API gateway can also validate tokens early and reject bad traffic, but each service still validates the token itself, because of defence in depth.

In our IRT, the React app uses Keycloak OIDC, and every new .NET API validates the JWT in middleware, with role and module checks in policies.

@p17-7 | How do you implement idempotency in REST APIs?
An operation is idempotent if doing it many times has the same effect as doing it once. GET, PUT and DELETE are idempotent by definition, but POST is not, and POST is where retries and double clicks cause duplicate orders or payments.

The standard way is an idempotency key. The client generates a unique key, like a GUID, and sends it in a header, for example Idempotency-Key. On the server, before doing the work, I check a store for that key. If it's new, I record it as in progress, do the work, and save the response with the key. If the same key comes again, I return the saved response instead of doing the work again. If it's still in progress, I return 409. Keys expire after a sensible period, like 24 hours.

The store must be atomic: a unique constraint in the database, or a Redis SET with NX, so two parallel requests can't both pass the check. Ideally the key is saved in the same transaction as the business change.

I add database constraints too, as a last safety net. In our IRT, I used exactly this for re-randomisation: an idempotency key from the UI, plus a unique constraint of one assignment per subject per stage, so a retry can never randomise twice.

@p17-8 | In dependency injection, what happens if a Singleton depends on a Scoped service, and what is the drawback?
That's called a captive dependency. A singleton lives for the whole application, so if it takes a scoped service in its constructor, that scoped instance gets captured and lives forever too, instead of living for one request.

The drawbacks are serious. A DbContext is scoped, so a captured DbContext is shared across all requests and threads. DbContext is not thread-safe, so you get random concurrency exceptions, stale cached entities, growing memory from change tracking, and data from one user's request leaking into another. Anything request-specific, like the current user, would also be wrong for everyone after the first request.

ASP.NET Core protects you in development: scope validation is on, and you get an error like "Cannot consume scoped service from singleton". In production that check is off by default, so the bug can slip through if you don't test properly.

The fixes: make the consumer scoped too, if it doesn't need to be a singleton. Or, if it must be a singleton, like a background service, inject IServiceScopeFactory and create a scope for each unit of work, resolve the scoped service inside it, and dispose the scope afterwards. For DbContext specifically, IDbContextFactory is a clean option.

I always enable ValidateScopes and ValidateOnBuild, so these mistakes fail at startup.

@p17-10 | What is the difference between useState and useMemo?
They solve different problems. useState stores state: a value that belongs to the component and, when you change it with the setter, makes React re-render. useMemo doesn't store state at all; it caches the result of a calculation between renders and only recalculates when its dependencies change.

So with useState, I destructure count and setCount from useState(0), and calling setCount triggers a re-render with the new value. With useMemo, I write const total = useMemo(() => items.reduce(...)) with items in the dependency array, and React reuses the previous total until items changes.

The typical uses of useMemo are two. First, expensive calculations, like filtering or sorting thousands of rows. Second, keeping the same object or array reference between renders, so a child wrapped in React.memo, or a useEffect dependency, doesn't see a "new" value every time.

A common mistake is using useMemo everywhere. It has its own cost and makes code harder to read, so I use it only when the profiler shows a slow calculation or unnecessary re-renders. Another mistake is storing derived values in useState and syncing them with useEffect; it's simpler and safer to calculate them during render, with useMemo if needed.

@p17-11 | How do you prevent unnecessary re-renders in a React application?
First I measure, with the React DevTools Profiler and the "highlight updates" option, to see which components re-render and why. Optimising without measuring usually adds complexity with no benefit.

Then I apply the right fix. Keep state as close as possible to where it's used, so a change in one input doesn't re-render the whole page. Wrap pure, expensive child components in React.memo, so they skip rendering when their props haven't changed. Make props stable: use useCallback for functions and useMemo for objects and arrays passed to memoised children, because a new function or object on every render breaks memo. Split big Contexts, or put fast-changing values in a store with selectors, like Redux Toolkit or Zustand, so components subscribe only to the slice they need. Use stable keys in lists, never array indexes when items can move. For very long lists, use virtualisation, so only visible rows render.

Avoid creating components inside other components, because that remounts them every time.

In our React shell, a drug accountability grid was slow because every keystroke in a filter re-rendered all rows. [Moving the filter state down, memoising the row component and virtualising the grid made typing smooth again.]

@p17-12 | How do you implement lazy loading and code splitting?
Code splitting means breaking one big JavaScript bundle into smaller chunks, and lazy loading means downloading a chunk only when it's needed. Together they make the first page load much faster.

In React, I use React.lazy with a dynamic import, like const Reports = lazy(() => import('./Reports')), and wrap it in Suspense with a fallback spinner. The most useful place is route-level splitting: each page is its own chunk, so the login page doesn't download the reporting module. I also lazy load heavy components that aren't visible at first, like charts, rich editors or big dialogs. Vite and webpack create the chunks automatically from dynamic imports. I add an error boundary around lazy parts, because a chunk download can fail after a deployment, and I can prefetch likely next pages on hover.

In Angular, it's built into the router: loadChildren for a feature module, or loadComponent for a standalone component, and the new @defer blocks in templates.

Then I check the result with the bundle analyser and Lighthouse.

In our React shell, each feature module is a separate npm package, and the shell lazy loads each one by route, so a site user who never opens drug accountability never downloads that code.

@p17-13 | How do you troubleshoot a React application in production, and what tools do you use?
In production, I can't attach a debugger to the user's browser, so I rely on good telemetry and a clear process.

First, collect evidence. Error monitoring, like Sentry or Datadog RUM, captures JavaScript errors with stack traces mapped back to the TypeScript source through uploaded source maps, plus the browser, the release version and the user's steps. An error boundary in React catches render errors, shows a friendly message, and reports the error. For API problems, correlation ids in the response headers let me find the backend logs for the same request.

Second, reproduce. I check the browser's DevTools, the network tab for failing or slow calls, the console for errors, and the performance tab for long tasks. I try the same browser, role and data as the user.

Third, check performance. Lighthouse, Web Vitals data from real users, like LCP, INP and CLS, and tools like GTmetrix or WebPageTest show slow loading, big bundles or layout shifts.

Common causes are a new release with a chunk loading error, a browser-specific API, an unhandled null from the API, or a slow endpoint.

Finally, I fix forward or roll back, and add a test so it doesn't come back.

@p17-14 | What is GTmetrix?
GTmetrix is an online tool that tests how fast a web page loads and explains why it's slow. You give it a URL, and it loads the page in a real browser from a chosen test location and device, then gives a performance grade and a detailed report.

The report is built on Google Lighthouse. It shows Web Vitals, like Largest Contentful Paint, which is when the main content appears, Total Blocking Time, and Cumulative Layout Shift, which measures things jumping around. It also has a waterfall chart, showing every request the page makes, in order, with its size and timing, so you can spot a huge image, a slow API call, render-blocking scripts or too many requests. And it gives specific recommendations, like compressing images, enabling caching, or reducing unused JavaScript. You can also track a page over time and get alerts if it gets slower.

It's similar to Google PageSpeed Insights and WebPageTest. The limitation is that it tests public URLs from its own servers, so for an internal app behind login, I'd use Lighthouse in Chrome DevTools or in the CI pipeline instead, plus real-user monitoring.

I use these tools after a release to check that bundle sizes and load times haven't got worse.

@p17-16 | If a Python application is very slow, how do you optimise it?
I always start by measuring, because the slow part is rarely where you guess.

First, find the bottleneck. For a quick view, I use cProfile or py-spy, which can attach to a running process without changing code and shows a flame graph. For a web service, I check traces and logs to see whether time goes into the database, external calls or Python code itself.

Then I fix based on what I find. If it's I/O, like database or HTTP calls, I reduce the number of calls, batch them, add indexes, cache results, or use async with asyncio and httpx so calls run concurrently. If it's CPU in pure Python loops, I use better algorithms and data structures, like sets and dicts for lookups instead of lists, vectorise with NumPy or pandas, use built-in functions, or move the hot path to a compiled library. Because of the GIL, threads don't speed up CPU work, so for that I use multiprocessing or ProcessPoolExecutor. For memory, I use generators to stream large data instead of loading everything.

For web services, I also check the server setup: enough uvicorn or gunicorn workers, connection pooling, and no blocking calls inside async code, which freezes the event loop.

Then I measure again, to prove the improvement.

@p17-17 | What is the difference between AWS ECS, EKS and Lambda?
All three run your code on AWS, but they differ in how much you manage.

ECS, Elastic Container Service, is AWS's own container orchestrator. You define a task definition with your Docker image, CPU, memory and environment, and an ECS service keeps the desired number of tasks running behind a load balancer. With Fargate, there are no servers to manage. It's simple and deeply integrated with IAM, CloudWatch and load balancers.

EKS, Elastic Kubernetes Service, is managed Kubernetes. AWS runs the control plane, and you use standard Kubernetes objects like Deployments, Services and Ingress. It's more powerful and portable across clouds, with a huge ecosystem like Helm and service meshes, but it needs more Kubernetes skill and operational effort.

Lambda is serverless functions. You upload code, it runs in response to events, like an API Gateway request, an S3 upload or an SQS message, it scales automatically, even to zero, and you pay per invocation. The limits are a 15-minute maximum, cold starts and less control.

So my rule is: Lambda for event-driven glue and spiky, short tasks; ECS for most containerised APIs and workers when you're on AWS; and EKS when you already have Kubernetes skills or need its ecosystem or portability.

@p17-18 | An ECS service's CPU reaches 95% and API latency suddenly increases. How do you troubleshoot it?
First I check whether it's load or a problem. In CloudWatch, I compare CPU with request count on the load balancer. If traffic doubled, it may just be a scaling issue. If traffic is normal but CPU jumped, something changed, so I check for a recent deployment, a configuration change, or a new type of request.

To protect users quickly, I scale out by increasing the desired task count, and check that auto scaling is working and that its CPU target isn't too high. If a release caused it, I roll back to the previous task definition revision.

Then I find the root cause. Container Insights shows CPU per task: if one task is hot, it may be stuck in a loop or retry storm. Traces and logs show which endpoints got slower. For .NET, I use dotnet-counters for CPU, garbage collection and thread pool queue length, and dotnet-trace for a CPU profile, which points to the hot method. Common causes are a new inefficient code path, heavy JSON serialisation, too much logging, regex backtracking, garbage collection pressure from big allocations, or thread pool starvation from sync-over-async code.

Finally, I fix the cause, load test the fix, and tune auto scaling and alarms, so we scale before latency suffers.

@p17-19 | An ECS task keeps starting and stopping. How do you investigate it?
A task that keeps starting and stopping is ECS replacing tasks that exit or fail health checks, so I need the reason it stops.

First, the stopped task's details. In the ECS console or with describe-tasks, every stopped task has a stopped reason and an exit code. "Essential container exited" with exit code 1 usually means the app crashed at startup. Exit code 137 means it was killed, often out of memory, which shows as OutOfMemoryError. "Task failed ELB health checks" means it started but the load balancer marked it unhealthy. "CannotPullContainerError" means an image or permission problem.

Second, the logs, in CloudWatch Logs for that task, just before it stopped. Startup crashes are often a missing environment variable, a secret the task role can't read, a wrong connection string, or a port mismatch.

Third, health checks. If the app is slow to start, the health check grace period may be too short, so ECS kills it before it's ready. I check the health check path, the expected status code, timeouts, and that the container listens on the right port.

Fourth, resources: memory limits too low, or CPU too small for startup.

The deployment circuit breaker can also roll back automatically. Once fixed, I add a startup configuration check, so failures are clear in logs.

@p17-20 | Have you used RDS and DynamoDB, and what is a partition key in DynamoDB?
Yes. In IQVIA's newer services on AWS I've worked with RDS for SQL Server, for relational data with transactions and joins, and DynamoDB for simpler, high-volume lookups like status and event data. Our main CIRT platform itself uses on-premise SQL Server.

In DynamoDB, the partition key is the attribute DynamoDB uses to decide where an item is stored. It hashes the partition key value and places the item in one of many physical partitions. Every item must have it, and if the table has only a partition key, it must be unique, like an order id.

A table can also have a sort key. Then the primary key is the combination of both, and many items can share the same partition key, stored together and sorted by the sort key. For example, partition key is shipmentId and sort key is the event timestamp, so I can query all events for one shipment in time order.

The partition key matters for performance. Each partition has throughput limits, so the key should have many distinct values with evenly spread traffic. A key like "status" with only a few values creates hot partitions and throttling. And queries need the partition key; without it you're doing a slow, expensive scan.

@p17-21 | How do you design keys in DynamoDB for large-scale applications?
In DynamoDB, you design keys from your access patterns, not from entities, because you can only query efficiently by key.

So first I list every access pattern: get shipment by id, list events for a shipment in time order, list shipments for a site by status, and so on. Then I design the partition key and sort key to answer them.

The partition key needs high cardinality and even traffic, like a shipment id or customer id, so load spreads across partitions. I avoid low-cardinality keys like status or date, which create hot partitions. If one key is naturally very busy, I use write sharding: add a suffix, like a random number from 1 to 10, and query all shards in parallel.

The sort key gives ordering and range queries, and I often use composite values, like "EVENT#2026-11-24T10:00", so begins_with and between work.

For other access patterns, I add global secondary indexes, with their own partition and sort keys, keeping in mind they're eventually consistent. Many teams use single-table design, storing related entities in one table with generic keys like PK and SK, so one query fetches a whole aggregate.

I also use TTL to expire old items, and on-demand capacity for unpredictable traffic.

@p17-22 | How do you implement caching in AWS, and which service would you use?
It depends on what I'm caching, and there are usually several layers.

For application data, like reference data, configuration, sessions or expensive query results, I use ElastiCache, normally the Redis or Valkey engine, because it supports rich data types, expiry, persistence and replication. The common pattern is cache-aside: the service checks Redis first, and on a miss it reads the database, stores the value with a TTL, and returns it. On writes, I update the database and then delete the cache key, so the next read refreshes it. I add random jitter to TTLs, so many keys don't expire at once, and use a lock or single-flight to prevent a stampede on hot keys.

For static content and cacheable API responses at the edge, I use CloudFront, which caches close to users. API Gateway also has its own response cache. For DynamoDB, DAX is a microsecond read cache. And inside each service, a small in-memory cache, like IMemoryCache in .NET, is the fastest layer, for data that rarely changes.

I'm careful with what not to cache: anything that must be strongly consistent, or user-specific data without a proper key. In our CIRT platform, which runs on-premise, Redis caches study configuration, refreshed by RabbitMQ events.

@p17-23 | Do you know AWS Parameter Store?
Yes. AWS Systems Manager Parameter Store is a managed, central place to store configuration values for applications, like URLs, feature flags, timeouts and connection settings, outside the code and outside the container image.

Parameters are organised in a hierarchy, like /myapp/prod/Database/Timeout, so I can load all settings for one service and environment with one call, by path. There are three types: String, StringList, and SecureString, which is encrypted with a KMS key, so it can hold sensitive values too. Access is controlled with IAM, so each service's role can read only its own path. Every change is versioned, so you can see history and roll back, and changes can trigger events through EventBridge.

There's a standard tier, which is free, with values up to 4 KB, and an advanced tier with larger values and parameter policies, like expiry.

In .NET, I use the Amazon.Extensions.Configuration.SystemsManager package, so Parameter Store becomes a normal configuration source, bound to the options pattern, with optional reload. In ECS, I can also inject parameters as environment variables in the task definition.

In IQVIA's newer services on AWS that I've worked on, settings live in Parameter Store, much like Azure DevOps variable groups hold settings for our on-premise CIRT releases.

@p17-24 | What is the difference between AWS Parameter Store and Secrets Manager?
Both store values outside your code, and both can encrypt with KMS, but they're designed for different jobs.

Parameter Store is mainly for configuration. It stores plain strings and SecureStrings in a hierarchy, with versioning and IAM access. The standard tier is free, which makes it great for lots of settings, like URLs, timeouts and feature flags. It can store secrets as SecureString, but it has no built-in rotation.

Secrets Manager is purpose-built for secrets, like database passwords, API keys and SFTP credentials. Its main advantage is automatic rotation: for RDS and other databases, it can rotate the password on a schedule with a Lambda function, updating both the database and the secret, so nobody needs to touch the password. It also supports cross-region replication, resource policies for cross-account access, and generating random passwords. It costs per secret per month, plus API calls.

So my rule is: configuration in Parameter Store, real secrets in Secrets Manager, especially anything that should rotate. Applications read both at runtime with their IAM role, and cache the values, to avoid throttling and cost.

In our AWS services, database credentials live in Secrets Manager with rotation, and normal settings live in Parameter Store.

@p17-25 | A Docker image is 2 GB. How do you reduce its size?
A 2 GB image is slow to push, pull and start, and has a bigger attack surface, so I'd shrink it step by step.

First, I look at what's inside, with docker history and a tool like dive, which shows the size of each layer. Usually the culprits are a full SDK base image, build tools, caches and unneeded files.

Then the main fixes. Use a multi-stage build: compile in a stage based on the SDK image, then copy only the published output into a small runtime image. For .NET, that means building with the sdk image and running on the aspnet runtime image, or an Alpine or chiselled Ubuntu variant, which can be around 100 MB or less. Add a .dockerignore, so bin, obj, node_modules, .git and test data never enter the build context. Combine package installs into one RUN, with --no-install-recommends, and clean the package cache in the same layer, because deleting files in a later layer doesn't reduce size. Don't copy large data files or models into the image; mount or download them at runtime.

For .NET, trimming or a self-contained single file, or even Native AOT for suitable apps, can go further.

I then scan the smaller image and check that startup and tests still pass.

@p17-26 | What is blue-green deployment?
Blue-green deployment means running two identical production environments. Blue is the current live version, and green is the new version. You deploy and test the new version on green while blue keeps serving users. When green is verified, you switch traffic from blue to green in one step, usually at the load balancer or DNS. If something goes wrong, you switch back to blue immediately, because it's still running.

The benefits are near-zero downtime, instant rollback, and the ability to test the real production setup before users see it.

The costs: you need double capacity during the switch, and the database is the hard part. Both versions usually share one database, so schema changes must be backward compatible, using the expand-and-contract approach: add new columns first, deploy code that works with both, and remove old columns only later.

On AWS, ECS supports blue-green through CodeDeploy, with two target groups behind the load balancer, a test listener, and automatic rollback on CloudWatch alarms. Kubernetes can do it by switching a Service's selector between two deployments.

It's different from canary, where you shift traffic gradually, like 10 percent first, and from rolling deployment, where instances are replaced one by one.

@p17-27 | When you deploy to production through CI/CD, how do you implement automatic rollback if something goes wrong?
Automatic rollback needs two things: a reliable signal that the deployment is bad, and a fast, safe way to go back to the last good version.

For the way back, I build once and keep every versioned artifact or image, so rollback is redeploying the previous version, never rebuilding. Database changes are backward compatible, so the old code still works with the new schema.

For the signal, I use several checks. Readiness and health checks fail the deployment if new instances don't start. Smoke tests run right after deployment against key endpoints. And during a bake period, monitoring alarms watch error rate and latency compared with the baseline.

Then the tools act. In ECS, the deployment circuit breaker with rollback enabled returns to the last stable task definition if tasks fail to become healthy, and CodeDeploy blue-green can roll back on CloudWatch alarms. In Kubernetes, a failed rollout can be undone with rollout undo, and tools like Argo Rollouts automate canary analysis. In Azure DevOps, a post-deployment gate can query monitoring, and a failure stage redeploys the previous release.

I also use feature flags, so a risky feature can be turned off without a deployment. In our releases, we keep the previous tagged release ready, and [rolled back a UAT release within 15 minutes] once when a setting was missing.

@p17-28 | What testing strategy do you follow in microservices, including unit tests?
I follow the test pyramid, adjusted for microservices: many fast unit tests, a good layer of integration and contract tests, and a few end-to-end tests.

Unit tests cover business logic in isolation, like validators, domain rules and handlers, with xUnit or NUnit, and Moq or fakes for dependencies. They run in seconds on every build. I focus on behaviour and edge cases, not on mocking every line.

Integration tests check a service with its real dependencies. In .NET, WebApplicationFactory hosts the API in memory, and Testcontainers starts a real SQL Server, PostgreSQL or RabbitMQ in Docker, so I test real queries, migrations and message handling, not mocks.

Contract tests protect the boundaries between services. With Pact, the consumer defines what it expects from an API, and the provider's pipeline verifies it, so a breaking change is caught before deployment, without running all services together.

End-to-end tests, with Playwright, cover a few critical user journeys in a deployed environment, because they're slow and fragile.

Around that: performance tests for key endpoints, security scans, and quality gates in SonarQube on coverage of new code.

In our regulated IRT, we add formal verification on top, and every rule in a feature like the CSV import has a unit test matching it.

@p17-29 | A production API that took 200 ms now takes 5 seconds. How do you troubleshoot it?
I follow a fixed order: scope, find the slow step, restore service, then fix the root cause.

Scope first. Is it every endpoint or one? All users or some? Since when exactly? And what changed at that time: a deployment, a configuration change, a data growth, a traffic spike, or a change in a dependency?

Then find where the 5 seconds go. Distributed traces break the request into spans, so I can see if it's the database, a downstream API, a queue or the code itself. If it's the database, I check Query Store or the slow query log for the query whose duration jumped, and its execution plan. Common causes are a plan change from parameter sniffing, a missing index after a new filter, lock blocking, or a table that grew. If it's the application, I check thread pool starvation from sync-over-async, connection pool exhaustion, garbage collection pauses, or a new N+1 query. If it's a downstream call, I check its latency and whether timeouts and retries are making it worse.

To restore service, I roll back a bad release, scale out, or force the last good query plan.

Then I fix it properly. [In March 2025, our shipments API went from about 200 milliseconds to 3 seconds because of parameter sniffing; I forced the good plan, then fixed the index.]

@p17-30 | Customers report HTTP 500 errors, but nothing appears in the application logs. How do you investigate?
If there are 500s but nothing in the application logs, the error is probably happening before or outside our code, or our logging is losing it. So I work from the outside in.

First, confirm where the 500 comes from. I check the response headers and body, and the load balancer or gateway logs and metrics. An ALB returning 502 or 503, or an API Gateway integration error, is different from a 500 generated by our app. On IIS, a 500.30 or 502.5 means the ASP.NET Core app failed to start, which is in the Windows event log, not our app logs.

Second, check the hops between: the reverse proxy, the ingress, a WAF, or the gateway timing out. Their access logs show which upstream answered.

Third, check whether our logging works at all. A crash at startup happens before logging is configured. An unhandled exception middleware might return 500 without logging. Logs might be dropped because the logging sink is down, buffered and lost when the container dies, or filtered by a wrong log level. A process killed for memory leaves no log.

Fourth, check the container or host: restarts, exit codes and out-of-memory kills.

Then I fix the cause and the visibility: global exception logging, startup logging to console, and correlation ids returned to users.

@p17-31 | A production issue can't be reproduced locally. What is your approach?
When it only happens in production, I stop trying to guess and focus on what's different between production and my machine.

First, gather evidence from production itself: logs and traces filtered by correlation id for the failing requests, the exact time, the user, the data involved, the version deployed and the environment. Patterns matter: does it happen for one site, one study, one browser, or only under load?

Then compare the differences. Data: production has volumes and edge cases, like special characters, nulls or old records, that test data doesn't. Configuration: a setting, feature flag or secret differs. Infrastructure: several instances instead of one, a load balancer, time zones, culture settings, Linux instead of Windows. Concurrency: race conditions only appear under real parallel load. And dependencies: real third-party systems behave differently from mocks.

To reproduce, I copy the exact request, use masked production data in a lower environment, match the configuration, and use load tests for concurrency issues. If it still won't reproduce, I add targeted logging or metrics around the suspected code, release them, and wait for the next occurrence. For memory or CPU issues, I take a dump from production.

[Once, a date filter bug appeared only for US sites, because I'd tested only in Indian time; I fixed it by storing everything in UTC.]

@p17-32 | How do you implement centralised logging across multiple microservices?
Centralised logging means every service sends its logs to one searchable place, so I can follow a request across all of them.

There are four parts. First, structured logs. Each service writes JSON with consistent fields: timestamp, level, service name, environment, version, message, exception, and, most importantly, a correlation or trace id. In .NET I use Serilog or the built-in logger with message templates.

Second, correlation. The first service generates a trace id, or reads it from the incoming request, and every outgoing HTTP call and every message carries it in a header. With OpenTelemetry and W3C trace context, this is automatic, and the same id links logs and traces.

Third, collection and shipping. Services either write to stdout and an agent collects them, like Fluent Bit, the CloudWatch agent or the Datadog agent, or they ship directly through a sink. Agents are better, because the app doesn't block on the log platform.

Fourth, the central store and tools: Elasticsearch with Kibana, Splunk, Datadog, CloudWatch Logs or Azure Log Analytics, with search, dashboards, alerts and retention rules.

I also mask personal data and secrets before logging. In our CIRT platform, Serilog sends logs to Splunk, and the correlation id in each message lets support trace one request across services.

@p17-33 | Five teams build microservices in different stacks like .NET and Java. How do you implement centralised logging across all of them?
With different stacks, I don't standardise the logging library; I standardise the format, the correlation and the pipeline.

First, a shared logging standard that every team follows: JSON output, a common set of field names, like timestamp, level, service.name, environment, version, trace_id, span_id and message, and agreed log levels. Using a known schema, like OpenTelemetry's semantic conventions or the Elastic Common Schema, avoids arguing about names.

Second, OpenTelemetry as the common layer. It has SDKs for .NET, Java, Node, Python and Go, and uses W3C trace context headers, so a trace started in a .NET service continues in a Java service, and every log line carries the same trace id. Each team keeps its own library: Serilog or ILogger in .NET, Logback or Log4j2 with a JSON encoder in Java, pino in Node.

Third, collection outside the apps. Services write to stdout, and the OpenTelemetry Collector or Fluent Bit collects, enriches, masks and forwards everything to one backend, like Elastic, Splunk, Datadog or CloudWatch. Changing backends later doesn't touch any service.

Fourth, governance: a shared starter package or template per stack, and a check in the pipeline or dashboards that flag services missing trace ids. That keeps five teams consistent without forcing one language.

@p17-34 | In AWS or Azure, which managed services are available for centralised logging?
Both clouds have managed services for this, and they map quite closely.

On AWS, the core is CloudWatch Logs. Services in ECS, Lambda and EKS send logs there through the awslogs driver, the Lambda runtime, or Fluent Bit. Logs are grouped into log groups, searched with CloudWatch Logs Insights, and turned into metrics and alarms. X-Ray, or the AWS Distro for OpenTelemetry, adds distributed tracing. For heavy search and dashboards, Amazon OpenSearch Service gives a managed Elasticsearch-style stack, often fed by subscription filters or Kinesis Data Firehose. S3 is used for cheap long-term archive, queried with Athena. CloudTrail is the audit log of AWS API calls.

On Azure, the core is Azure Monitor with a Log Analytics workspace. Application Insights collects application logs, requests, dependencies and traces, and can use OpenTelemetry. Everything is queried with KQL, the Kusto query language, with workbooks for dashboards and alert rules. Diagnostic settings send platform logs from resources like App Service and AKS to the workspace, and Container Insights covers AKS.

Many teams also use third-party platforms that work across clouds, like Datadog, Splunk, Elastic Cloud or Grafana Loki.

In our on-premise CIRT platform, we use Splunk, and our newest services also use OpenTelemetry with Datadog.

@p17-35 | When should you use Azure Web App versus Kubernetes (AKS)?
I choose based on how many services there are, how much control we need, and the team's operational skills.

Azure App Service, often called Web App, is a fully managed platform for web apps and APIs. You deploy code or a container, and Azure handles the servers, patching, scaling, TLS certificates and deployment slots for zero-downtime swaps. It integrates easily with Azure AD, Key Vault and Application Insights. It's ideal for a handful of web apps or APIs, a small team, or when you want to go live quickly with little operations work.

AKS, Azure Kubernetes Service, is managed Kubernetes. It gives much more control and flexibility: many microservices with complex networking, sidecars and service meshes, custom scaling with KEDA based on queue length, background workers, stateful workloads, GPU nodes, and portability across clouds. But you need Kubernetes skills to manage cluster upgrades, node pools, ingress, security policies and monitoring.

There's also a middle option, Azure Container Apps, which runs containers with Kubernetes-style features like KEDA scaling and Dapr, without managing a cluster.

So my rule: a few web apps or APIs, use App Service; many containerised services with a platform team, use AKS; containers without cluster management, consider Container Apps.
