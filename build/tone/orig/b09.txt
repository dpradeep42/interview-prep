@p17-96 | How do you keep an Angular or React app's API keys safe?
The honest answer is that you can't hide a secret in a browser app. Everything in the JavaScript bundle, including environment variables injected at build time, like Vite's VITE_ variables or Angular's environment files, is visible to anyone who opens the developer tools.

So the rule is: never put real secrets in front-end code. Only public values belong there, like the API base URL, the identity provider's URL, a public client id, or a publishable key that's designed to be public and restricted, like a maps key locked to our domain.

When the front end needs to call a service that requires a secret key, the call goes through our own backend. The browser calls our API with the user's token; our API adds the secret, which it reads from a vault, and calls the third-party service. That's also where rate limits and authorization are applied.

For our own APIs, the front end doesn't use API keys at all. Users log in with OpenID Connect, and the app sends a short-lived access token.

I also check build output and the repo with secret scanning, because developers sometimes put a key in a .env file that ends up in the bundle.

Our React shell's Vite variables contain only URLs and the public Keycloak client id.

@p17-97 | What is the difference between a WAF and a firewall?
A traditional network firewall works at the network and transport layers. It allows or blocks traffic based on IP addresses, ports and protocols, like "allow HTTPS on port 443 from anywhere, block everything else", or "only the app servers can reach the database on port 1433". In the cloud, security groups, network ACLs and Azure network security groups play this role.

A web application firewall works at the application layer, layer 7. It understands HTTP and inspects the content of requests: URLs, headers, query strings and bodies. It can block common attack patterns, like SQL injection strings, cross-site scripting payloads, known bad bots, requests from certain countries, or too many requests from one IP. Examples are AWS WAF on CloudFront, an ALB or API Gateway, Azure Web Application Firewall on Front Door or Application Gateway, and Cloudflare.

They complement each other: the network firewall limits who can talk to what, and the WAF filters malicious content in allowed traffic.

But a WAF is a safety net, not a replacement for secure code. It can be bypassed with clever encoding and can produce false positives, so I start rules in count mode, review what would be blocked, then enable blocking. The application must still validate input and use parameterised queries.

@p17-98 | How do you rotate secrets and certificates without downtime?
The trick is to have two valid credentials for an overlap period, so nothing breaks during the switch.

For database passwords or API keys, the common approach is dual credentials. Create a new secret while the old one still works. Update the secret store. Applications pick up the new value, either by reloading configuration periodically, or by fetching a fresh secret when authentication fails, then retrying. After all instances use the new one, revoke the old one. AWS Secrets Manager automates this with rotation Lambdas, using alternating users, so one is always valid.

For signing keys, like JWT keys, the identity provider publishes both the old and new public keys in its JWKS. It starts signing with the new key, and once old tokens have expired, removes the old key.

For TLS certificates, I automate renewal well before expiry, using AWS Certificate Manager, Key Vault auto-renewal, or Let's Encrypt with cert-manager, and alert at 30 days before expiry for anything manual. Expired certificates are a surprisingly common cause of outages.

Better still, remove secrets entirely where possible: IAM roles and managed identities rotate credentials automatically.

The application side matters: don't cache secrets forever, and don't require a restart to pick up a new one.

@p17-99 | How do you implement field-level security so some roles never see certain fields?
Sometimes the question isn't whether a user can see a record, but which fields of it they can see. In clinical trials, this is critical: blinded users must never see which treatment a subject received, while unblinded roles, like pharmacists or the safety team, can.

I enforce it on the server, never just by hiding fields in the UI, because anyone can call the API directly or look at the network response.

The approach: the user's permissions, from their role, determine a data access level. The API builds different DTOs, or projections, for different access levels, so sensitive fields are simply not selected from the database for blinded users. A blinded user's response doesn't contain the treatment arm at all, not even as null with a hint. Reports and exports follow the same rules, and so do logs and error messages.

For extra protection, the database can enforce it too, with views or column permissions, so a reporting tool can't bypass the application.

Testing is essential: automated tests call each endpoint as a blinded user and assert that unblinded fields never appear.

In our IRT, role and field-level blinding is a core feature, and things like kit numbers that could reveal the treatment are handled carefully.

@p17-100 | Which identity provider would you choose for a new system: Keycloak, Entra ID or Amazon Cognito?
All three are identity providers that support OAuth 2.0 and OpenID Connect, so applications integrate with them in a similar way. The differences are about hosting, features and ecosystem.

Keycloak is open source and self-hosted. You run it yourself, on-premise or in the cloud, which gives full control, deep customisation of login flows and themes, user federation with LDAP and Active Directory, and no per-user licence cost. The trade-off is that you operate it: upgrades, high availability, database backups and security patching.

Microsoft Entra ID, formerly Azure AD, is a managed service, ideal when the organisation already uses Microsoft 365, with corporate single sign-on, conditional access, MFA and B2B guest users built in. Entra External ID handles customer-facing identity.

Amazon Cognito is AWS's managed service, with user pools for app users, integration with API Gateway and ALB, and identity pools for temporary AWS credentials. It's cost-effective for customer apps on AWS, though less flexible for complex enterprise scenarios.

For the .NET API, it barely matters: AddJwtBearer with the authority and audience works with all of them.

We use Keycloak for our on-premise IRT, because it runs inside our network and supports our compliance needs, like password policies and lockout.

@p17-101 | What is the difference between TLS termination at the load balancer and end-to-end TLS?
With TLS termination, or SSL offloading, the load balancer or gateway handles the HTTPS connection with the client, decrypts the traffic, and forwards it to the backend, often as plain HTTP inside the private network. It's simple and efficient: certificates are managed in one place, like AWS Certificate Manager on an ALB, backends don't spend CPU on encryption, and the load balancer can inspect and route by HTTP content, and apply a WAF.

The risk is that traffic between the load balancer and the backend is unencrypted. Inside a well-isolated private network, many teams accept that. But for sensitive data, compliance requirements, or a zero-trust approach, it's not enough.

End-to-end TLS means traffic is encrypted all the way. There are two styles. Re-encryption: the load balancer terminates TLS, inspects the request, then opens a new TLS connection to the backend. TLS passthrough: the load balancer just forwards the encrypted bytes, using a layer 4 balancer, and the backend terminates TLS, but then the load balancer can't route by path.

In ASP.NET Core behind a terminating proxy, I configure the forwarded headers middleware, so the app knows the original request was HTTPS and uses the right client IP and scheme.

For healthcare data, I prefer re-encryption to the backend.

@p17-102 | What is the difference between == and Equals() in C#?
For reference types, the == operator by default compares references, meaning whether two variables point to the same object in memory. Equals is a virtual method, and by default it also compares references, but classes can override it to compare values.

The difference shows up when a type overrides them. String is the classic example: both == and Equals are overridden to compare the characters, so two different string objects with the same text are equal either way.

But == is resolved at compile time, based on the variable's declared type, while Equals is resolved at runtime, based on the actual object. So if two strings are stored in variables of type object, == compares references and can return false, while Equals still compares the text and returns true. That's a classic interview trick.

For value types, like int or a struct, Equals compares the values. A struct's default Equals uses reflection, which is slow, so for performance-sensitive structs, I implement IEquatable of T.

Records generate value-based Equals and == for you.

If I override Equals, I must also override GetHashCode, and usually the == and != operators, so they behave consistently. And for a guaranteed reference check, I use ReferenceEquals.

@p17-103 | What is the contract between Equals and GetHashCode?
The rule is: if two objects are equal according to Equals, they must return the same hash code. The reverse isn't required; different objects can share a hash code, which is a collision.

This matters because hash-based collections, like Dictionary and HashSet, first use the hash code to find the bucket, and only then call Equals within that bucket. If I override Equals to compare by value but leave the default GetHashCode, which is based on the object reference, two "equal" objects will usually land in different buckets. Then a dictionary lookup with an equal key fails to find the entry, and a HashSet happily stores duplicates. Those bugs are very confusing.

So whenever I override Equals, I override GetHashCode using the same fields. In modern .NET, HashCode.Combine of the fields does it neatly.

Another important rule: the hash code shouldn't change while the object is used as a key. If I mutate a field that's part of the hash after adding the object to a dictionary, it's effectively lost in the wrong bucket. That's why keys should be immutable.

Records and value tuples generate correct Equals and GetHashCode automatically, so for value-like keys, like a composite key of study id and site id, I use a record struct.

@p17-104 | Why are strings immutable in C#, and when do you use StringBuilder?
In C#, a string can't be changed after it's created. Any operation that looks like it modifies a string, like concatenation, Replace or ToUpper, actually creates a new string and leaves the original as it was.

There are good reasons. It's thread-safe, because nobody can change a string another thread is reading. It's safe to use as a dictionary key, since its hash never changes. It allows string interning, where identical literals share one instance. And it's secure, because a validated value, like a file path, can't be changed afterwards.

The cost is that repeated concatenation in a loop creates many temporary strings. Building a string from 10,000 pieces with plus-equals copies the growing string every time, which is roughly quadratic, and creates a lot of garbage for the GC.

StringBuilder fixes this. It keeps a growable internal buffer and appends into it, and only creates the final string when you call ToString.

My rule: for a few concatenations, or one expression, plain concatenation or interpolation is fine and more readable; the compiler optimises it. In loops or when building large text, like a CSV export or an email body, I use StringBuilder, or string.Join for joining collections.

For very hot paths, there's also Span-based formatting and string.Create.

@p17-105 | What are required members and init-only setters in C#?
Both are about creating objects safely with object initialiser syntax.

An init-only setter, written with init instead of set, lets a property be assigned during object initialisation, but not afterwards. So I can write new Shipment with Id equals 5 and Status equals Pending, and after that the object is effectively read-only. It gives immutability without needing a long constructor. Records use init properties by default.

The required modifier, from C# 11, goes further: the compiler forces the caller to set that property in the object initialiser. If someone writes new Shipment without setting a required property, it's a compile error, not a runtime null reference later. It works well with nullable reference types, because a required non-nullable string won't produce a "might be null" warning.

If a constructor sets all the required members itself, I mark it with SetsRequiredMembers, so callers using that constructor aren't forced to set them again.

I use these a lot for DTOs, options classes and commands: required plus init gives objects that are always complete and can't be changed by accident.

One caution: System.Text.Json respects required since .NET 7, so a missing JSON property causes a deserialisation error, which is usually what I want for incoming requests.

@p17-106 | What are primary constructors in C# 12?
Primary constructors let me declare constructor parameters directly on the class or struct declaration, like public class ShipmentService(IShipmentRepository repo, ILogger of ShipmentService logger). Those parameters are in scope throughout the class body, so I can use them in methods without declaring private fields and writing a constructor to assign them.

Records already had this, but in C# 12 it came to normal classes and structs. It removes a lot of boilerplate, especially for dependency injection in services and controllers.

There are some differences from records that are worth knowing. In a class, primary constructor parameters don't become public properties; they're just captured parameters. They're not readonly, so the class could accidentally reassign one; if I care about that, I assign it to a readonly field explicitly. And if the class has other constructors, they must call the primary constructor using this.

One subtle trap: if I both capture a parameter and also use it to initialise a property, the class ends up with two copies of the state, and the compiler warns about it.

I find them great for small services and handlers with a few injected dependencies. For classes with complex validation in the constructor, I still use a regular constructor, because it's clearer.

@p17-107 | What does yield return do, and how do iterators work in C#?
yield return lets me write a method that produces a sequence one item at a time, lazily, without building the whole collection in memory.

When a method returns IEnumerable of T and uses yield return, the compiler turns it into a state machine class. Nothing runs when the method is called. Code runs only when someone enumerates the result, for example with foreach. Each time the consumer asks for the next item, the method runs until the next yield return, hands back that value, and pauses, remembering where it was. yield break ends the sequence early.

This is useful for reading large files line by line, paging through an API, or generating sequences on demand, because only one item is in memory at a time, and if the consumer stops early, for example with Take of 10, the rest is never produced.

There are some gotchas. Because execution is deferred, argument validation inside an iterator doesn't run until enumeration starts, so I put validation in a non-iterator wrapper method, or a local function. Enumerating twice runs the whole method twice. And a using block inside an iterator stays open until enumeration finishes or the enumerator is disposed.

For asynchronous sources, like paging through an API, I use async iterators: IAsyncEnumerable with yield return and await foreach.
