@p17-180 | How do you support multiple authentication schemes, like JWT and API keys, in one API?
ASP.NET Core supports several authentication schemes side by side. A scheme is a named handler, like the JWT bearer handler, a cookie handler, or a custom one.

For API keys, which partners or older systems might use, I write a custom authentication handler by inheriting AuthenticationHandler. It reads the key from a header, like X-API-Key, looks it up, comparing a hash of the key, not plain text, and with a constant-time comparison, and if it's valid, creates a ClaimsPrincipal with claims like the client id and its permissions. If the header is missing, it returns NoResult, so other schemes can try.

Then I register both: AddAuthentication with JWT as the default, AddJwtBearer, and AddScheme for the API key handler.

To choose per request, there are two approaches. On endpoints, Authorize with AuthenticationSchemes listing which schemes are accepted, or a policy that specifies them. Or a policy scheme, with AddPolicyScheme and ForwardDefaultSelector, which looks at the request, like whether it has an Authorization bearer header or an API key header, and forwards to the right handler.

Authorization policies then work on claims, regardless of how the user was authenticated.

API keys are long random values, stored hashed, scoped, rotatable, rate-limited, and only sent over HTTPS.

@p17-181 | What is IClaimsTransformation, and when would you use it?
IClaimsTransformation lets me modify or add claims to the user's ClaimsPrincipal after authentication, before authorization runs. I implement its TransformAsync method and register it in DI, and ASP.NET Core calls it during authentication.

The typical use is enriching the identity with application-specific data that isn't in the token. Identity providers usually issue tokens with generic claims, like the user id, email and maybe some roles. But my application's permissions, like which studies and sites a user can access and which actions they can perform, live in the application database. So the transformation looks up the user's permissions and adds them as claims, and authorization policies can then simply check for those claims.

Other uses: mapping claim names from different identity providers to one standard set, or flattening nested role claims, like Keycloak's realm_access roles in a JSON structure, into standard role claims that the Authorize attribute understands.

There are some gotchas. It can be called more than once per request, so it must be idempotent: check whether the claims were already added. It runs on every request, so database lookups must be cached, like in memory or Redis with a short expiry, otherwise every request pays for extra queries. And I don't put too many claims in, especially if they end up in a cookie.

@p17-182 | What changed with OpenAPI in .NET 9, and do you still use Swashbuckle?
For years, ASP.NET Core templates used Swashbuckle to generate the OpenAPI document and show the Swagger UI. In .NET 9, Microsoft removed Swashbuckle from the templates and added built-in OpenAPI document generation in the Microsoft.AspNetCore.OpenApi package. In .NET 10, it supports OpenAPI 3.1.

With the built-in support, I call AddOpenApi and MapOpenApi, and the document is served at openapi/v1.json. It works with both controllers and minimal APIs, and supports document and operation transformers, which are hooks to customise the output, like adding a security scheme for JWT bearer tokens, or adding descriptions and examples. It also works with Native AOT, and the document can be generated at build time, which is useful for checking breaking changes in the pipeline.

The built-in package doesn't include a UI. For interactive documentation, I add one separately: Swagger UI from Swashbuckle's UI package pointed at the new document, or Scalar, which many teams now use.

Swashbuckle still works and has been actively maintained again, so existing projects don't need to migrate urgently, especially if they use its filters heavily.

For new .NET 9 or 10 services, I use the built-in generator, add a bearer security scheme with a transformer, and expose the UI only in non-production environments.

@p17-183 | How do you stream a large file download efficiently from an API?
The key is never loading the whole file into memory. If I read a 2 GB file into a byte array and return it, the server needs 2 GB of memory per concurrent download, it lands on the Large Object Heap, and the server can run out of memory quickly.

Instead, I stream it. In ASP.NET Core, I return a file result with a Stream, like Results.File or File in a controller with a FileStream opened with async and sequential-scan options, or a stream from blob storage. The framework copies the stream to the response in small chunks, so memory use stays small, regardless of file size.

Setting enableRangeProcessing to true supports HTTP range requests, so clients can resume interrupted downloads, and video players can seek. I set the content type and a Content-Disposition header with a safe file name, and ETag and Last-Modified headers for caching.

For generated content, like a large CSV export, I write directly to the response body as I go, or return an IAsyncEnumerable for JSON, so rows stream from the database to the client without being collected first.

When files are in cloud storage, the best option is often not to stream through the API at all: the API checks permissions and returns a short-lived pre-signed URL, and the client downloads directly from S3 or Blob Storage.

@p17-184 | How do you log HTTP request and response details safely?
ASP.NET Core has built-in HTTP logging middleware. I enable it with AddHttpLogging and UseHttpLogging, and choose which fields to log: request method, path, query, headers, status code, duration, and optionally request and response bodies, with a size limit. Since .NET 8, it supports combining everything into one log entry per request, and an IHttpLoggingInterceptor to customise or redact per request.

But I'm careful with what gets logged, because logs are widely accessible and kept for a long time. By default, headers are redacted unless explicitly allowed, and I keep it that way for Authorization, cookies and API keys. Request and response bodies can contain personal data or credentials, so I don't log them in production, except for specific, non-sensitive endpoints, during a limited investigation, with masking.

What I always want per request is: method, route template rather than the full URL, status code, duration, user or client id, and the trace id, in one structured log entry. Serilog's request logging middleware, UseSerilogRequestLogging, does this neatly, with enrichment from the HttpContext.

Health check and metrics endpoints are excluded, otherwise they flood the logs.

For debugging production issues, distributed traces with OpenTelemetry often give better insight than logging bodies, without the privacy risk.

@p17-185 | What is IHttpContextAccessor, and what are its pitfalls?
IHttpContextAccessor gives access to the current HttpContext from places that don't receive it directly, like a service class. I register it with AddHttpContextAccessor, inject it, and read HttpContext from it. A common use is a CurrentUser service that reads the user's claims, or getting the correlation id for logging.

It works using AsyncLocal, so the context flows with the async execution of the request.

There are several pitfalls. Outside a request, like in a background service, a hosted service or a message consumer, HttpContext is null, so code that depends on it fails there. If code captures the HttpContext and uses it after the request ends, for example in fire-and-forget work, it may be reading a recycled or disposed context, which causes strange bugs. HttpContext isn't thread-safe, so it mustn't be used from parallel tasks. And it couples business logic to the web layer, making it harder to test and reuse.

So my approach: in the business layer, I depend on a small abstraction, like ICurrentUser with UserId and Permissions. The web implementation reads from IHttpContextAccessor; a background job or message consumer provides its own implementation, using the user from the message. Tests just use a fake.

And I copy the values I need while the request is active, never the HttpContext itself.

@p17-186 | How would you migrate an ASP.NET MVC 4.8 application to ASP.NET Core?
For a large MVC application, I'd avoid a big-bang rewrite and migrate incrementally.

Microsoft's recommended approach is the strangler fig with YARP. I create a new ASP.NET Core app that sits in front of the old one as a reverse proxy. Requests for migrated routes are handled by the new app, and everything else is forwarded to the legacy app. I then move controllers and views one area at a time. The System.Web adapters help share code, and can share session and authentication between the two apps, so users don't notice which app served the page.

Before moving code, I prepare it: move business logic into class libraries targeting .NET Standard 2.0, so both old and new apps can use them; remove System.Web dependencies like HttpContext.Current from business code; and update packages to versions that support modern .NET. The .NET Upgrade Assistant helps analyse and convert projects.

The main differences to handle: Global.asax and web.config become Program.cs, middleware and appsettings.json; HTTP modules and handlers become middleware; built-in DI replaces third-party containers; authentication changes; and bundling, Razor and some HTML helpers differ.

Our approach is similar in spirit: rather than converting the legacy MVC portal, we're moving modules to the React shell with new .NET APIs, while shared Keycloak SSO keeps the experience seamless.

@p17-187 | What is SignalR, and how does it scale across multiple servers?
SignalR is ASP.NET Core's library for real-time communication between server and clients. It lets the server push messages to browsers instantly, like notifications, live dashboards or progress updates, without the client polling.

It uses WebSockets when available, and falls back automatically to Server-Sent Events or long polling. I define a Hub class on the server with methods clients can call, and the server can call methods on clients: all clients, a specific user, or a group, like everyone viewing a particular study. The JavaScript and .NET clients handle connection and automatic reconnection.

Authentication works with the same JWT or cookie, though for WebSockets in browsers, the token is passed as a query string parameter, so I make sure it's not logged.

Scaling out is the tricky part. Each connection lives on one server. If server A wants to send a message to a user connected to server B, it can't, by itself. Solutions: a Redis backplane, where every server publishes messages through Redis pub-sub so all servers receive them; or a managed service, like Azure SignalR Service, which holds all the connections itself, so app servers don't. Sticky sessions are also needed for the fallback transports, unless WebSockets-only mode is used.

For AWS, API Gateway WebSocket APIs are an alternative, especially for serverless.

@p17-188 | What are Server-Sent Events, and when would you use them instead of WebSockets?
Server-Sent Events is a simple standard for the server to push a stream of text events to the browser over a normal HTTP connection. The browser uses the EventSource API, which reconnects automatically and can resume from the last event id. The response has the text/event-stream content type, and the server writes events as they happen.

Compared with WebSockets: SSE is one-way, server to client only, while WebSockets are two-way. SSE runs over plain HTTP, so it works through most proxies, load balancers and firewalls without special configuration, and benefits from HTTP/2 multiplexing. It's text-only, and reconnection is built in.

So SSE fits well when the client mostly listens: live notifications, progress of a long-running job, a dashboard feed, or streaming an AI model's response token by token, which is exactly how many LLM APIs stream output. WebSockets are better for genuinely interactive two-way communication, like chat or collaborative editing, or binary data.

In ASP.NET Core, I can write SSE manually by setting the content type and flushing writes to the response, and .NET 10 adds TypedResults.ServerSentEvents, which takes an IAsyncEnumerable and streams it as events. SignalR can also use SSE as one of its transports.

One caution: the browser's EventSource can't set an Authorization header, so I use cookies or a fetch-based client.

@p17-189 | What do HTTP/2 and HTTP/3 bring, and does Kestrel support them?
HTTP/1.1 sends one request at a time per connection, so browsers open several connections and requests queue behind each other.

HTTP/2 multiplexes many requests and responses over a single TCP connection at the same time, as independent streams. It also compresses headers with HPACK, which saves a lot for APIs with large headers like tokens, and supports stream prioritisation. Fewer connections means less TLS handshaking. gRPC requires HTTP/2.

But HTTP/2 still runs over TCP, so if one packet is lost, all streams on that connection wait for the retransmission. That's TCP head-of-line blocking, and it hurts on unreliable networks, like mobile.

HTTP/3 runs over QUIC, which is built on UDP. Each stream is independent, so a lost packet only delays its own stream. QUIC also has faster connection setup, combining the transport and TLS 1.3 handshakes, and connection migration, so a phone switching from Wi-Fi to mobile data keeps its connection.

Kestrel supports both. HTTP/2 is enabled by default with TLS. HTTP/3 is supported since .NET 7, requiring TLS and the platform's QUIC library, and I configure the endpoint with HttpProtocols.Http1AndHttp2AndHttp3, and clients discover it through the Alt-Svc header.

In practice, the load balancer or CDN in front often handles HTTP/2 and HTTP/3 with clients, and talks to the app over HTTP/1.1 or HTTP/2.

@p17-190 | How does session state work in ASP.NET Core, and should you use it?
ASP.NET Core supports session state as an opt-in feature. I call AddSession with a distributed cache, and UseSession. The browser gets a cookie with a session id, and on the server, ISession stores small values, like strings or byte arrays, keyed by that id. Unlike classic ASP.NET, it doesn't store objects directly; I serialise them, often as JSON.

The storage is an IDistributedCache. The in-memory one only works on a single server. With multiple instances, I use Redis or SQL Server, so any instance can read the session.

Some important behaviours. The session is loaded on first access, and since session access in ASP.NET Core can be synchronous, I call LoadAsync first to avoid blocking. Session data isn't locked, so concurrent requests from the same user can overwrite each other's changes, which differs from the old ASP.NET behaviour. Sessions expire after an idle timeout. And the session cookie is marked essential, or it won't be set when the user hasn't consented to non-essential cookies under privacy settings.

Should I use it? For APIs, no; APIs should be stateless, with state in the client or the database. For server-rendered web apps, it's fine for small, temporary data, like a multi-step wizard, but not for authentication or anything important.

Our legacy MVC portal uses session state, which is one reason Redis was introduced for the load-balanced IIS servers.

@p17-191 | Razor Pages vs MVC vs Blazor: when would you use each?
All three are ways to build web UIs with .NET.

MVC uses controllers and views. Controllers handle requests and choose views, with models in between. It's well suited to large applications with many related actions, and to teams familiar with the pattern. It's also the basis of Web API controllers.

Razor Pages is page-focused: each page has a .cshtml file and a PageModel class with handlers like OnGet and OnPost. For page-based apps, like forms and admin screens, it's simpler and more cohesive than MVC, because everything for a page is in one place. Microsoft recommends it for new server-rendered page apps.

Blazor lets you build interactive UIs with C# components instead of JavaScript. Since .NET 8, Blazor Web Apps support several render modes per component: static server rendering, interactive server, where the UI runs on the server and updates the browser over a SignalR connection, interactive WebAssembly, where .NET runs in the browser, and auto, which starts on the server and switches to WebAssembly once it's downloaded.

My choice: for APIs consumed by React or Angular, which is our main setup, controllers or minimal APIs. For a simple internal tool built by .NET developers, Razor Pages or Blazor, which avoids a separate JavaScript stack. For rich public-facing apps with a large front-end team, React or Angular.
