@p17-48 | What is gRPC, and when would you use it instead of REST?
gRPC is a high-performance remote procedure call framework from Google. You define services and messages in a .proto file with Protocol Buffers, and tools generate strongly typed client and server code for many languages, including C#.

Compared with REST and JSON, it's faster and smaller, because Protocol Buffers is a compact binary format and it runs over HTTP/2, with multiplexing on one connection. It has a strict contract, so breaking changes are obvious. And it supports streaming in both directions, which is great for real-time feeds.

The downsides: browsers can't call gRPC directly without gRPC-Web, the binary messages aren't human-readable, so debugging with curl or Postman is harder, and HTTP/2 can be tricky through some proxies and load balancers. Public APIs and partners usually expect REST.

So I use gRPC for internal, service-to-service calls where performance and strong contracts matter, like high-volume internal lookups or streaming, and REST for public APIs, browser clients and partner integrations.

In ASP.NET Core, gRPC is built in: AddGrpc, map the service, and use the generated client with the HttpClient factory, so it gets the same resilience policies. You can even expose both from one service with JSON transcoding.

@p17-49 | What is a distributed monolith, and how do you avoid it?
A distributed monolith is a system that's split into many services, but they're still so tightly coupled that you have all the problems of a monolith plus all the problems of distributed systems. You can't deploy one service without deploying several others, a change touches many repos, services share a database, and one user request needs a long chain of synchronous calls.

The signs are: releases that must be coordinated across teams, shared libraries with business logic that every service depends on, services that break whenever another changes its API, and an outage in one service taking everything down.

To avoid it, I start with good boundaries around business capabilities, so most changes stay inside one service. Each service owns its data, with no shared database. Communication is mostly asynchronous for side effects, so services don't depend on each other being up. APIs are versioned and backward compatible, with contract tests, so services deploy independently. Shared libraries contain only technical concerns, like logging or messaging helpers, never business rules. And each service has its own pipeline.

Sometimes the honest answer is that a modular monolith is the better design, until there's a real reason, like independent scaling or separate teams, to split.

@p17-50 | What is a modular monolith, and when is it better than microservices?
A modular monolith is one deployable application that's internally split into well-defined modules, each with its own domain logic, its own data tables or schema, and a clear public interface. Modules don't reach into each other's internals; they talk through interfaces or in-process events.

It gives many of the design benefits of microservices, like clear boundaries and ownership, without the operational cost: one deployment, one process, in-process calls instead of network calls, real ACID transactions, simple debugging and much simpler infrastructure.

It's better than microservices when the team is small, the domain is still being understood and boundaries are likely to change, the load doesn't need independent scaling, or the organisation doesn't have strong DevOps and observability yet. Splitting too early often produces a distributed monolith.

The trick is to enforce the boundaries, otherwise it becomes a big ball of mud. I use separate projects per module, internal classes, architecture tests with a library like NetArchTest to block forbidden references, and separate database schemas.

Later, when a module needs independent scaling, a different technology or its own team, it can be extracted into a microservice with much less pain, because its boundary is already clean.

@p17-51 | How do you monitor and replay messages from a dead-letter queue?
A dead-letter queue is where messages go when they can't be processed successfully, so one bad message doesn't block the queue or get retried forever.

First I separate failure types. Transient failures, like a database timeout, get a few retries with backoff, ideally using delayed redelivery so the consumer isn't hammering a struggling dependency. Permanent failures, like a message with invalid data, called a poison message, go straight to the dead-letter queue, because retrying won't help.

In RabbitMQ, I configure a dead-letter exchange on the queue, so rejected or expired messages are routed there. In SQS, a redrive policy moves a message to the DLQ after a maximum receive count, like five.

The DLQ is useless if nobody looks at it, so I add an alarm when its depth is above zero, and I keep the original headers, the error reason and the number of attempts with each message. Then there's a clear process: inspect, fix the bug or the data, and replay the messages back to the main queue with a tool or a script. Since consumers are idempotent, replaying is safe.

In our CIRT platform, failed vendor messages land in a dead-letter queue with an alert, and the support team can replay them after the fix.

@p17-52 | How do you handle out-of-order events in a consumer?
Ordering is hard to guarantee globally, so I first ask: ordering of what? Usually we only need ordering per entity, like all events for one shipment in order, not every event in the whole system.

The standard approach is partitioning by key. In Kafka, messages with the same key, like the shipment id, go to the same partition, and a partition is read in order by one consumer in the group. In SQS FIFO queues, the message group id does the same thing. In RabbitMQ, ordering holds within one queue with one consumer, but multiple consumers or redeliveries can reorder messages.

But ordering can still break, through retries, redeliveries or producers sending from different instances. So I also make consumers tolerant. Each event carries a version number or sequence number for its entity, and the consumer ignores anything older than what it has already applied. Or the consumer re-reads the current state from the source instead of trusting the event payload.

I also avoid designs that need ordering across different entities, because they limit parallelism a lot.

In IQVIA's newer AWS services, shipment events on Kafka are keyed by shipment id, and consumers store the last version applied, so a late, older event can't overwrite newer data.

@p17-53 | How do you handle a downstream service that is completely down for an hour?
For a long outage, retries and circuit breakers alone aren't enough, so I plan how the system behaves while the dependency is down.

First, fail fast. The circuit breaker opens, so requests aren't waiting on timeouts and threads aren't piling up. Health and alerts tell the team quickly which dependency is down.

Then graceful degradation, depending on how important the dependency is. If it's only for enrichment, like showing recommendations or a non-critical widget, I hide that part or return cached or default data, and the main feature keeps working. If the work can wait, I make it asynchronous: accept the request, put it on a queue, show the user "accepted, processing", and process it when the dependency returns. The queue buffers the backlog.

If the dependency is truly critical, like a payment or a safety check, I fail clearly with a helpful message, rather than doing something unsafe or inconsistent.

When it comes back, I control the recovery: the backlog drains at a limited rate, so we don't overwhelm the recovering service, and I check the DLQ and replay anything that failed.

In our IRT, if a depot's system is down, shipment requests queue up, and site users see "pending", which we clear when the depot recovers.

@p17-54 | What is a sidecar and a service mesh?
A sidecar is a helper container that runs next to the main application container, in the same pod, sharing its network and lifecycle. It adds capabilities without changing the application code, like a logging agent, a proxy or a secrets fetcher.

A service mesh uses sidecar proxies, usually Envoy, next to every service, plus a control plane, to manage all service-to-service traffic. Tools are Istio, Linkerd, or AWS App Mesh historically. All calls go through the proxies, so the mesh can provide, in one consistent way: mutual TLS between services, retries, timeouts and circuit breaking, traffic splitting for canary releases, and detailed metrics and tracing for every call, all configured centrally, without code in each service.

The benefits are consistency across languages and teams, and strong security with zero-trust mTLS. The costs are complexity, extra latency and memory for each proxy, and a steep learning curve. Newer approaches, like Istio's ambient mode, reduce the per-pod sidecar overhead.

I'd consider a mesh when there are many services in different languages, and strict security or traffic-control needs. For a smaller number of .NET services, libraries like Polly, OpenTelemetry and a gateway usually give enough, with much less to operate.

@p17-55 | How do you choose the size of a microservice?
I don't measure size in lines of code. A service is the right size when it maps to one business capability, can be owned by one team, and can be changed and deployed independently most of the time.

Signs that services are too big: several teams keep changing the same service, deployments are risky because unrelated features ship together, or parts of it have very different scaling needs.

Signs they're too small, sometimes called nano-services: almost every feature needs changes in several services, services call each other constantly in long chains, transactions need sagas for things that should be simple, and the operational overhead, like pipelines, monitoring and on-call, outweighs the benefits.

So I start from the domain, using domain-driven design and bounded contexts, and group things that change together and need strong consistency together. Data that must be updated in one transaction is a strong hint that it belongs in one service.

It's also fine to start a bit bigger and split later when there's a real reason, like independent scaling, a different release cadence, or a separate team, because merging services back is harder than splitting a clean module.

In our IRT, inventory and shipments stay together, because kit allocation and the shipment request must be consistent.

@p17-56 | What is an anti-corruption layer?
An anti-corruption layer is a translation layer between your domain and an external or legacy system whose model you don't want leaking into your code.

Legacy systems and third-party APIs often have confusing names, odd data formats, magic codes and different concepts. If your new service uses those directly, its model gets "corrupted" by them, and every change in the external system ripples through your code.

So I put an adapter in between. My domain code talks only to an interface in my own language, like IShipmentGateway with CreateShipment taking my own Shipment type. The implementation of that interface calls the external system, maps my types to theirs and back, converts codes, handles their error formats and retries. If the external system changes, or is replaced, only the adapter changes.

It's especially useful during a strangler migration, where new services must work with an old system for a long time.

In our IRT modernisation, the new .NET APIs talk to the legacy transaction engine through a translation layer, so the new code uses clean names and DTOs, while the old procedures and formats stay hidden behind it. When parts of the legacy side are replaced, the new code doesn't change.

@p17-57 | How do you share code between microservices?
I share code carefully, because shared libraries can couple services as badly as a shared database.

What I'm happy to share is technical, cross-cutting code: logging and OpenTelemetry setup, a messaging wrapper, standard health checks, authentication setup, error-handling middleware, and maybe a result type. I publish these as versioned NuGet packages in a private feed, like Azure Artifacts or GitHub Packages, with semantic versioning, so each service upgrades when it's ready, not forced all at once.

What I avoid sharing is business logic and domain models. If two services share a domain library, a change for one forces a change and redeployment of the other, which brings back the monolith's coupling. A little duplication is better than the wrong coupling.

For contracts, like message and event schemas or API clients, I prefer generating them from a single source, such as an OpenAPI spec, a protobuf file or a schema registry, rather than hand-sharing DTO classes. That keeps each side independent and catches breaking changes.

I also keep shared libraries small, well tested, backward compatible, with few dependencies of their own.

In our CIRT platform, common logging and messaging helpers ship as internal NuGet packages from Azure DevOps Artifacts, while domain models stay inside each service.

@p17-58 | What is the difference between a command and an event in messaging?
They're both messages, but they mean different things, and that affects how I design them.

A command is a request to do something, addressed to one specific receiver that owns the action. It's named in the imperative, like CreateShipment or SendEmail. The sender expects it to be handled, and the receiver can accept or reject it. It's usually sent to a queue with one consumer.

An event is a statement that something has already happened. It's named in the past tense, like ShipmentCreated or SubjectRandomised. The publisher doesn't know or care who listens; zero, one or many subscribers can react. It can't be rejected, because it's a fact. Events are published to a topic or exchange.

This distinction matters for coupling. With commands, the sender depends on the receiver. With events, the publisher is independent of its subscribers, so you can add new consumers without changing the publisher.

There's also domain events versus integration events. Domain events are raised inside a service, between parts of its own domain. Integration events are published outside, to other services, and are part of the public contract, so they're versioned and kept stable.

In our IRT, SubjectRandomised is an integration event that the notification and reporting consumers both listen to.

@p17-59 | What should an event contain: full data or just an id?
There are two main styles, and both are valid.

A thin event, or notification event, contains just the id and type, like "Shipment 123 changed". Consumers then call the owning service to get the current data. It's small and always gives fresh data. But every consumer makes a call back, which adds load and coupling, and if the owner is down, consumers can't proceed.

A fat event, or event-carried state transfer, contains the relevant data, like the shipment's status, site, kit count and timestamps. Consumers have everything they need without calling back, so they're more independent and resilient, and the owner gets less load. The downsides are bigger messages, more care about schema changes, and the risk of including sensitive data that not every consumer should see.

I usually go in the middle: include the data consumers commonly need, plus the id and a version number, so they can ignore stale events. I don't include sensitive personal data unless every subscriber genuinely needs it, especially in clinical systems where patient data must be minimised.

And I version event schemas, adding fields in a backward-compatible way.

In IQVIA's newer AWS services, shipment events carry status, location and a version, so most consumers never call back.
