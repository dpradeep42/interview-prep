@p17-156 | What is .NET Aspire?
.NET Aspire is a set of tools and libraries for building and running distributed, cloud-ready applications, especially for the local development experience.

The App Host is a small C# project where I describe the application's parts in code: the API projects, a front end, and resources like SQL Server, Redis, RabbitMQ or PostgreSQL. When I run it, Aspire starts everything, runs the infrastructure in containers, and wires up connection strings and service discovery automatically. So a new developer can clone the repo and press F5, instead of following a long setup document.

The Aspire dashboard shows all services, their logs, traces and metrics in one place, using OpenTelemetry, so I can follow a request across services locally.

Service defaults is a shared project that adds OpenTelemetry, health checks, service discovery and HTTP resilience to every service with one call, so they're consistent.

Integrations are NuGet packages for common services, like Redis or Azure Service Bus, which register clients with health checks and telemetry built in.

For deployment, Aspire can generate manifests and deploy to Azure Container Apps or Kubernetes, though teams often keep their own pipelines.

I see it as very useful for local development and consistency, even if production deployment uses Terraform or existing pipelines.

@p17-157 | What is the Big-O complexity of common .NET collections?
Knowing this helps me pick the right collection.

List of T is a dynamic array. Index access is O(1). Add at the end is O(1) on average, with occasional resizing. Insert or remove in the middle is O(n), because elements shift. Contains or IndexOf is O(n), because it scans. Sort is O(n log n).

Dictionary and HashSet are hash tables, with O(1) average for add, remove and lookup by key, and no ordering.

SortedDictionary is a balanced tree, with O(log n) for add, remove and lookup, keeping keys sorted. SortedList is an array-backed sorted collection with O(log n) lookup by binary search, but O(n) inserts; it uses less memory.

LinkedList has O(1) insert and remove when you already have the node, but O(n) to find anything, and poor cache locality, so it's rarely the best choice in practice.

Queue and Stack are O(1) for enqueue, dequeue, push and pop.

PriorityQueue, added in .NET 6, is a heap: O(log n) to enqueue and dequeue the item with the smallest priority, and O(1) to peek.

In practice, the biggest real-world win is usually replacing repeated List.Contains or First lookups inside loops with a Dictionary or HashSet built once, turning O(n squared) into O(n).

@p17-158 | What is the difference between Task.Run and an async method?
An async method that awaits I/O, like a database query or an HTTP call, doesn't use a thread while waiting. The thread goes back to the pool, and when the I/O completes, a thread picks up the continuation. That's what makes servers scalable.

Task.Run queues a delegate to run on a thread pool thread. It's for CPU-bound work: it moves the work off the current thread. In a desktop app, that's useful to keep the UI thread responsive while doing a heavy calculation.

In ASP.NET Core, the request is already running on a thread pool thread. So wrapping work in Task.Run and immediately awaiting it just swaps one pool thread for another, adding overhead and no benefit. And wrapping a synchronous I/O call in Task.Run, called fake async, still blocks a thread; it just hides it. The right fix there is a truly async API.

Task.Run in ASP.NET Core is useful only in specific cases: running several CPU-bound pieces of work in parallel, or starting fire-and-forget background work, though for that I prefer a hosted service with a queue, because it handles errors, scopes and shutdown properly.

So: async and await for I/O; Task.Run only for CPU-bound work that genuinely benefits from running elsewhere.

@p17-159 | What are tuples and deconstruction in C#?
Tuples group a few values together without defining a class. Modern C# uses ValueTuple, which is a struct, with nice syntax: a method can return (int Count, decimal Total), and the caller reads result.Count and result.Total. The element names are a compile-time feature, so they make the code readable without creating a type.

Deconstruction splits a tuple, or any type with a Deconstruct method, into separate variables: var (count, total) equals GetSummary(). Records support it automatically through their positional parameters, and I can use underscore as a discard for values I don't need. Deconstruction also enables neat tricks, like swapping two variables with (a, b) equals (b, a).

Tuples also work well in pattern matching, like switching on a tuple of two values, for example (status, isUrgent) switch, which is much clearer than nested if statements.

I use tuples for private and internal helper methods that return two or three related values, and for local grouping in LINQ. I avoid them in public APIs, DTOs and anything serialised, because element names don't survive serialisation and they don't carry meaning or validation. If a tuple is passed around a lot, it's a sign it should become a record.

The older System.Tuple class, with Item1 and Item2, is a reference type, and I don't use it in new code.

@p17-160 | What are local functions, and how are they different from lambdas?
A local function is a method declared inside another method. It's only visible inside that method, so it keeps helper logic close to where it's used without cluttering the class.

They differ from lambdas in a few useful ways. Local functions can be declared after they're used, are named, and can be recursive easily. They support generics, ref and out parameters, params and iterators with yield return. And performance: a lambda that captures variables allocates a closure object and a delegate on the heap. A local function that's only called directly can capture variables into a struct on the stack, so no allocation, which matters in hot paths.

Marking a local function as static prevents it from capturing any variables of the enclosing method, which makes dependencies explicit and avoids accidental captures.

Two common uses. First, argument validation for iterators and async methods. Because an iterator's body runs lazily, I validate arguments in the outer method, which runs immediately, and put the yield return logic in a local function. Same for async methods, when I want validation exceptions thrown immediately rather than inside the task. Second, splitting a long method into readable steps that don't make sense as class-level methods.

I use lambdas when I need a delegate to pass somewhere, like to LINQ or an event.

@p17-161 | How do you design pagination in an API response?
I always paginate list endpoints, because returning everything works in testing and fails in production when a table grows.

The request takes either a page number and page size, or a cursor. Page size has a sensible default, like 25, and a hard maximum, like 100, enforced on the server, so nobody can request a million rows.

The response wraps the items with metadata: for page-based paging, the page number, page size and total count; for cursor-based paging, a next cursor or continuation token, and whether there are more items. Some APIs also return links to the next and previous pages, or use the Link header, so clients don't build URLs themselves.

Which style I choose depends on the data. Offset paging, with skip and take, is simple and lets users jump to page 10, which suits admin screens. But it gets slow on deep pages, because the database still reads all the skipped rows, and results shift if rows are added while paging. Cursor or keyset paging uses the last item's sort key, like "created after this date and id", which is fast at any depth and stable, so it's better for large tables, infinite scrolling and API consumers syncing data.

Ordering must be deterministic, so I always add a unique tie-breaker, like the id, to the sort.

Total counts can be expensive on big tables, so I make them optional.

@p17-162 | What are ETags, and how do you use them for caching and concurrency?
An ETag is a version identifier for a resource, returned in a response header. It can be a hash of the content, or a version number like SQL Server's rowversion. Clients use it in conditional requests, for two purposes.

Caching: the client sends If-None-Match with the ETag it has. If the resource hasn't changed, the server returns 304 Not Modified with no body. That saves bandwidth and processing, which helps for large resources that are fetched often, like study configuration.

Concurrency control: when updating, the client sends If-Match with the ETag it got when it read the resource. The server checks it against the current version. If someone else changed the resource in the meantime, the versions don't match, and the server returns 412 Precondition Failed instead of silently overwriting the other person's change, which is the lost update problem. The client then reloads and lets the user merge or retry. Some APIs also return 428 Precondition Required if If-Match is missing on updates, to force clients to use it.

In ASP.NET Core, I implement this myself: map the entity's row version to the ETag header, read If-Match in the update endpoint, and pass the version into EF Core's concurrency token check, so the database enforces it.

It's the HTTP version of optimistic concurrency.

@p17-163 | How do you use HTTP caching headers for APIs?
HTTP caching headers tell browsers, CDNs and proxies whether and how long they can reuse a response, which can massively reduce load.

Cache-Control is the main header. max-age equals 300 means the response can be reused for 300 seconds. public allows shared caches, like a CDN, to store it, while private means only the user's own browser may cache it, which is right for user-specific data. no-cache means the client may store it but must revalidate with the server before using it, often with an ETag. no-store means don't store it anywhere, which I use for sensitive data, like patient information or tokens.

Vary tells caches which request headers change the response, like Accept-Language or Authorization, so different versions are cached separately.

For APIs, my defaults are: sensitive or user-specific data gets no-store or private, no-cache; truly public, rarely changing data, like a list of countries or static reference data, gets public with a max-age, maybe through a CDN; and responses with ETags support cheap revalidation.

In ASP.NET Core, I set headers directly, use the ResponseCache attribute, or use output caching middleware for server-side caching of whole responses, which is different: it's the server reusing its own response, regardless of what clients do.

Getting caching wrong with user data can leak information between users, so I'm conservative.

@p17-164 | What is content negotiation in ASP.NET Core?
Content negotiation is how the server picks the response format based on what the client asks for. The client sends an Accept header, like application/json or application/xml, and the server chooses a matching output formatter. If several are acceptable, it uses the client's preference order.

In ASP.NET Core controllers, JSON is the default formatter, using System.Text.Json. I can add others, like XML with AddXmlSerializerFormatters, or a custom formatter for CSV. By default, if the client asks for a format the server doesn't support, ASP.NET Core falls back to JSON; setting ReturnHttpNotAcceptable to true makes it return 406 Not Acceptable instead, which is stricter.

The Produces attribute restricts or documents which content types an action returns, and Consumes does the same for request bodies, checked against the Content-Type header, which returns 415 Unsupported Media Type if it doesn't match.

Minimal APIs are simpler: they return JSON by default and don't do full content negotiation, so for other formats, I return a specific result, like Results.Text or a file.

In practice, most modern APIs are JSON only, and that's fine. I've used negotiation mainly for exports, where the same report endpoint returns JSON for the UI and CSV for download, based on the Accept header or a format parameter.

Accept-Language for localisation is a related kind of negotiation.

@p17-165 | What is HATEOAS, and do you use it?
HATEOAS stands for Hypermedia as the Engine of Application State. It's the highest level of the Richardson maturity model for REST. The idea is that responses include links telling the client what it can do next, like a shipment response containing links to "cancel" or "track", only when those actions are allowed. So the client discovers actions from the response, instead of hard-coding URLs and business rules.

The benefits in theory: clients are less coupled to URL structures, and the server controls which actions are available based on the current state and the user's permissions.

In practice, I rarely see full HATEOAS in real projects, including ours. Most front ends are built together with the API, so they know the URLs. Client developers find it more work to parse links than to call documented endpoints, and the tooling, like OpenAPI clients, is built around fixed endpoints.

What I do use are the practical parts. Pagination links in list responses, like next and previous. A Location header on 201 Created pointing to the new resource. And flags in responses indicating allowed actions, like canCancel or canReturn, computed on the server from the state and the user's permissions, so the UI shows the right buttons without duplicating business rules. That gives most of the benefit with less complexity.

@p17-166 | FluentValidation vs data annotations: which do you use and why?
Data annotations are attributes on model properties, like Required, StringLength, Range or EmailAddress. They're built in, simple, and ASP.NET Core with ApiController checks them automatically before the action runs, returning a 400 with validation problem details. They're fine for simple rules on simple DTOs.

FluentValidation is a library where rules live in a separate validator class, like CreateShipmentValidator inheriting AbstractValidator, written as fluent code: RuleFor Quantity GreaterThan zero, RuleFor SiteId NotEmpty, and so on.

I prefer FluentValidation for real applications, for a few reasons. Complex rules are much easier: conditional rules with When, rules that compare properties, collection rules with RuleForEach, and async rules that check the database, like "site must exist and be active". Validators are classes, so they can use dependency injection. Messages are easy to customise and localise. Rules are kept out of the DTO, which stays clean. And validators are very easy to unit test.

The FluentValidation team no longer recommends the automatic ASP.NET Core integration, so I run validators explicitly, typically in a MediatR pipeline behaviour, or in an endpoint filter for minimal APIs.

That's how our newer IRT APIs work: FluentValidation in a MediatR behaviour, so every command is validated before its handler runs.

@p17-167 | What is a custom model binder, and when would you write one?
Model binding maps data from the HTTP request, like route values, query strings, headers, form fields and the body, to the action's parameters. The built-in binders handle common types and JSON bodies well. A custom model binder lets me control how a specific type is created from the request when the defaults don't fit.

Typical reasons: binding a strongly typed id, like StudyId, from a route string; parsing a comma-separated list in the query string, like ids equals 1,2,3, into a list; or combining values from several sources, like a header and a route value, into one object.

To write one, I implement IModelBinder, read the value with the ValueProvider, convert it, and either set the result as success or add a model state error. Then I register it with a ModelBinder attribute on the type or parameter, or globally through an IModelBinderProvider.

But often there's a simpler option. For simple types, if the type has a static TryParse method, both controllers and minimal APIs can bind it from route and query values automatically. Minimal APIs also support a static BindAsync method for custom binding from the whole HttpContext.

So I first try TryParse or BindAsync, and only write a full model binder for complex cases in controllers.
