XSS and CSRF are both browser-based attacks, but they kind of work in opposite directions.

XSS, cross-site scripting, is when an attacker manages to run their own JavaScript inside your site, usually by injecting it through user input that's displayed without proper encoding, like a comment or a name field. That script runs with your site's privileges, so it can read data on the page, steal tokens from localStorage, or act as the user. To prevent it, encode output, which React does by default, sanitise any HTML you have to render, with DOMPurify, use a Content Security Policy to block inline and unknown scripts, and keep session cookies HttpOnly, so scripts can't read them.

CSRF, cross-site request forgery, is when an attacker's website makes the user's browser send a request to your site, and the browser automatically includes the user's cookies, so the request looks legitimate. Like a hidden form that submits a change. To prevent it, SameSite cookies, which stop cookies being sent on cross-site requests, anti-forgery tokens in forms, which ASP.NET Core supports built in, and checking the Origin header.

APIs using bearer tokens in headers, not cookies, aren't vulnerable to CSRF, but they are to XSS if tokens sit in localStorage. People miss that. I can explain how we store tokens.

My rule for secrets is simple. They never show up in source code, configuration files in git, container images or logs.

Secrets live in a managed store. On AWS, that's Secrets Manager for credentials that should rotate, and Parameter Store SecureString for others, encrypted with KMS. In Azure, Key Vault, and in pipelines, secret variables. Services read them at runtime using their IAM role, so there are no keys to bootstrap the keys. Access follows least privilege, each service can read only its own secrets, per environment, and access is audited through CloudTrail. Secrets get rotated regularly. For RDS, Secrets Manager does it automatically, and apps re-read the secret if a connection fails. For local development, developers use .NET user secrets or a local file that's excluded from git.

Detection matters too. Secret scanning in CI and pre-commit hooks, like gitleaks, so if someone accidentally commits a key, it's caught and rotated straight away. And logs mask sensitive values.

@p2-54
The Model Context Protocol, MCP, is an open protocol that standardises how AI applications connect to external tools and data. I like to think of it as USB-C for AI, one standard connector instead of a custom integration for every pair of tools.

There are three roles. The host is the AI application, like Claude, Cursor or GitHub Copilot. Inside it, an MCP client connects to MCP servers. An MCP server exposes capabilities, tools, which are actions the model can call, like "queue a build", resources, which are data the model can read, and prompts, which are reusable templates. The client discovers what the server offers, including each tool's name, description and input schema, and the model decides when to call a tool based on the user's request. Communication uses JSON-RPC, over stdio for local servers, or HTTP for remote ones.

The big win is that you build an integration once, and it works with any MCP-compatible host. Before MCP, every AI tool needed its own plugin format.

An MCP server lets an AI model take real actions, so safety has to be designed in, not bolted on later. I think about it in layers.

Identity and least privilege come before anything. The server acts with the calling user's own credentials and permissions, never a shared admin token. So the AI can never do more than that user could do manually. Then separating risk. Read-only tools, like getting status or logs, are separate from write tools, like queuing a build or deploying. Destructive or production-affecting actions need explicit confirmation, and our existing human approval gates in Azure DevOps stay in place. The AI doesn't bypass the GxP process. Then input validation. Every input is checked against a schema, with allow-lists for things like environment names, so a model can't pass something unexpected. Auditability too, every tool call is logged with who, what, parameters and result. And protection against prompt injection. Content returned from tools, like logs, is treated as data, not instructions, and tools never execute arbitrary commands.

And clear errors, so the model reports a failure instead of guessing.

A good tool definition makes it easy for the model to pick the right tool and call it correctly the first time. It's really API design, but the consumer is an AI model.

The name should be specific and verb-first, like queue build or get release status, not something vague like "build" or "helper". The description is the most important part, honestly. It should say what the tool does, when to use it, and when not to, what it returns, and maybe a short example. The model reads it to decide. The input schema should be small and typed, with enums for fixed choices, like environment names, sensible defaults, and only truly required fields marked as required. Fewer, clearer parameters mean fewer mistakes. The output should be compact and structured, like a status, the key fields and a link, instead of huge raw responses that waste the model's context. And errors should be clear and actionable, like "environment UAT2 doesn't exist, valid values are FV, TechOps, UAT, Prod", so the model can correct itself.

Also, avoid overlapping tools that do almost the same thing, because the model will pick the wrong one.

Good prompting is mostly about giving the model the same context and clarity you'd give a new colleague, I think.

Context and goal come before anything, the role, the relevant code or files, the exact outcome I want, and constraints, like ".NET 10, use our existing logging pattern, don't add new packages". RAG, retrieval-augmented generation, is a way to make a language model answer questions using your own, up-to-date documents, instead of relying only on what it learned during training.

It has two phases. Ingestion, where you take your documents, like wikis, runbooks or specifications, split them into chunks, create an embedding for each chunk, which is a vector that represents its meaning, and store them in a vector index. And querying. When a user asks a question, you embed the question, search the index for the most similar chunks, often combined with keyword search, and put those chunks into the prompt with instructions like "answer using only this context and cite sources". The model then answers grounded in that content.

What you get is answers that use current and private information, without retraining the model, and they can cite sources, so users can verify them, which cuts hallucinations. The quality depends heavily on retrieval, chunk size, good metadata, hybrid search, and re-ranking. And access control matters, users should only retrieve documents they're allowed to see.

In my work, I built a RAG service in Python that gives GitHub Copilot and Cursor the context of our codebase and coding standards, through MCP tools like search codebase, so their code fits our project and hallucinations drop. I can explain how to evaluate retrieval quality.

An AI agent is basically a language model running in a loop. It plans what to do, calls a tool, looks at the result, and decides the next step, repeating until the goal is reached. Agentic orchestration is how you coordinate that loop, or several agents, safely and reliably.

Orchestration covers a few things. Which agents exist and their roles, say a planner that breaks down the task, an executor that calls tools, and a reviewer that checks the result. Which tools each agent can use. And the limits, a maximum number of steps, cost or time budgets, permissions, and points where a human has to approve. AutoGen, from Microsoft, is a framework for building multi-agent conversations, where agents with different roles talk to each other to solve a task. Claude Code is an agentic coding tool that works in your repository and terminal. It reads files, runs commands, edits code and runs tests, in that same plan-act-observe loop.

The engineering concerns that matter are reliability and safety, clear tool definitions, good error messages so agents can recover, logging every step, and human approval for risky actions.
