The Interface Segregation Principle says clients shouldn't be forced to depend on methods they don't use. So it's better to have several small, focused interfaces than one big "fat" interface.

When an interface is too large, every implementer has to implement methods it doesn't need, often by throwing, and every consumer gets access to more than it should. Changes to unrelated methods also force recompiles and test changes everywhere. Microsoft follows this principle with IReadOnlyList being separate from IList.

A practical example from our code. Instead of one big IShipmentRepository with read, update and delete, we can split it into an IShipmentReader for queries and an IShipmentWriter for commands. A reporting service only takes the reader, so it physically can't modify shipments, which is nice in a GxP system, and its unit tests only need to mock two or three methods. Same idea in the MCP server, tools are grouped by capability, so read-only tools don't get access to deployment operations.

The balance, I think, is not going too far, with one-method interfaces everywhere. I can talk about how I find the right size.

So the Dependency Inversion Principle says high-level business code should depend on abstractions, not on concrete low-level classes. Both sides depend on the interface, so the dependency direction is inverted.

Without it, a business service creates its infrastructure directly, like new-ing up a specific SFTP library. Then the business logic is tied to that library, changing it means editing business code, and you can't unit test the service without a real server.

In our vendor file exchange, the VendorExchangeService depends only on ISftpClient, which is defined alongside the business logic. The infrastructure layer has the Rebex, SSH.NET and ComponentPro implementations, and Program.cs registers them in the ASP.NET Core DI container. So the business code never references Rebex at all. When a vendor needed a different library, it was a configuration change, and in unit tests I just inject a mock ISftpClient with Moq.

Dependency injection is the mechanism, and dependency inversion is the design principle behind it. People mix those two up quite a bit. I can explain how this shapes our project structure, if useful.

I chose an interface for our SFTP integration for some very concrete reasons.

I needed several interchangeable implementations behind one contract. We had three libraries, Rebex, SSH.NET and ComponentPro, and different vendors needed different ones. An interface let business code depend on ISftpClient and stay completely unaware of which library ran. Then testability. With an interface I can inject a mock with Moq in unit tests, so testing the file-exchange logic doesn't need a real SFTP server. And extensibility. Interfaces let me add decorators, like retry and logging wrappers, around any provider without touching the providers, and adding a new library is just a new class.

I also used an abstract base class, because the providers shared real code like retry policies, timeouts and logging. So the interface is the contract, and the base class is shared implementation. Callers only see the interface.

Honestly, I avoid inheritance in a few situations.

When the relationship isn't truly "is-a", for one. If I just want to reuse a few methods, inheritance is the wrong tool, and composition, having a collaborator, is better. When behaviour varies in several independent ways, too. Like, transfer method and retry policy are separate concerns, and subclasses for every combination explode, so strategies or decorators work better. When hierarchies get deep. A change in a base class ripples to every child, which is called the fragile base class problem. And across module or team boundaries, where others would inherit from my class and depend on its internals.

A real example. We needed retry and logging around SFTP clients. Instead of creating a RetryingRebexClient, a RetryingSshNetClient and so on, I wrote one retry decorator that wraps any ISftpClient. That's one class instead of three.

I still use inheritance where it's natural and shallow, like one abstract base class for shared provider code. I can explain composition over inheritance further if useful.

@p4-48
Garbage collection affects performance because, while the GC runs, it has to pause or slow down application threads to find and free unused objects.

Gen 0 collections are very quick, but if the app allocates lots of objects, they happen very often. The expensive ones are gen 2 and Large Object Heap collections, which can cause noticeable pauses and push up tail latency, like p99. So the main lever is allocation rate. The less garbage you create, the less the GC has to do. ASP.NET Core uses server GC by default, tuned for throughput, with background collection to reduce pauses.

In hot paths I reduce allocations with a handful of techniques, Span of T and Memory of T to slice data without copying, ArrayPool to reuse buffers, avoiding boxing, avoiding big temporary strings and LINQ chains in tight loops, and streaming large data instead of loading it whole. I measure with dotnet-counters and a profiler before and after.

Like, for our CSV import I streamed the file row by row instead of loading it all, which kept memory flat even for large files. I can explain how I'd investigate a GC problem in production.

@p4-49
When an exception happens inside an async method, it doesn't crash straight away. It's captured and stored inside the Task that the method returns.

When you await that task, the exception is rethrown at the await, with its original stack trace, so a normal try-catch around the await works exactly as you'd expect. But if nobody awaits the task, like a fire-and-forget call, the exception is unobserved and basically lost, which hides bugs. With async void methods it's worse. There's no task to hold the exception, so it's raised on the synchronization context or thread pool and can crash the whole process. That's why I only use async void for event handlers.

With Task.WhenAll, await throws the first exception, but the task's Exception property holds all of them, so I check that when I need every failure.

In our services, every async call is awaited, background work runs in a BackgroundService with its own try-catch and logging, and unhandled request exceptions go to our global exception handler. I can show how I test async exceptions with xUnit.

Dependency injection means a class receives the objects it needs, its dependencies, from outside, usually through its constructor, instead of creating them itself with new.

In ASP.NET Core there's a built-in DI container. In Program.cs I register services with a lifetime, singleton, scoped or transient, and when a controller or service is created, the container builds it and passes in everything it needs, then disposes things at the right time.

Why we use it, basically. Loose coupling, because classes depend on interfaces, not concrete types. Testability, because in unit tests I can pass mocks instead of real databases or servers. Flexibility, because I can swap implementations through configuration. And central lifetime management, so things like DbContext are created per request and disposed automatically.

A real example, our VendorExchangeService gets an SFTP client factory, a logger and its options injected. In production the factory returns the right library for each vendor, and in unit tests I inject a mock, so I can test the retry and error logic without a real SFTP server.

@p4-51
A dependency is anything a class needs in order to do its job.

Typical dependencies are a repository or DbContext for data, an HttpClient for calling another service, a logger, configuration options, a message publisher, or an SFTP client. Less obvious ones are the current time and random numbers, because code that calls DateTime.Now directly is hard to test. If a class creates its dependencies itself, with new or static calls, it's tightly coupled to them. You can't swap them, and you can't test the class in isolation.

With dependency injection, those dependencies are passed in through the constructor, so the class just declares what it needs and the container provides it.

Like, our study-transfer safety guard depends on a repository to read study state, a logger, and TimeProvider for the current time. Because time is injected, in unit tests I use a fake time provider to test rules like "block transfers after the cut-off date" without waiting for real time to pass.

A good sign of too many dependencies is a long constructor, which usually means the class does too much, in my experience. I can say more about that.

@p4-52
Inversion of Control is a design idea where the framework controls the flow of the program and calls your code, rather than your code controlling everything. It's often summed up as "don't call us, we'll call you".

In ASP.NET Core, I don't write a main loop that reads requests. The framework receives the request, runs the middleware pipeline, creates my controller and calls the action. Object creation is also inverted. Instead of my classes creating their dependencies, something else creates and supplies them. Dependency injection is the most common form of IoC.

An IoC container is the component that does that work. You register types and their lifetimes, and it builds the whole object graph, injects constructor parameters, manages singleton, scoped and transient lifetimes, and disposes objects at the right time. In .NET the built-in one is IServiceCollection for registration and IServiceProvider for resolution. Third-party ones like Autofac add features like property injection or modules.

In our services, honestly, the built-in container is enough. I can explain lifetimes or how scopes work next.

@p4-53
Both are ways of giving a class its dependencies, but constructor injection is the one I use almost always.

With constructor injection, dependencies are parameters of the constructor. That makes required dependencies explicit. You can't create the object without them, so it's always fully ready. The fields can be readonly, so they can't be swapped later, and it's easy to see in tests what to mock. With property injection, dependencies are set through public properties after the object is created. That hides what's required, allows half-initialised objects, and makes the dependency mutable. It's only reasonable for truly optional dependencies.

The built-in .NET container supports only constructor injection, property injection needs something like Autofac. With C# 12 primary constructors, constructor injection is also very concise.

One useful side effect, I'd say. If a constructor grows to seven or eight parameters, it's a clear signal the class has too many responsibilities. I've split services for exactly that reason, like separating CSV parsing from validation. I can talk about that refactoring if useful.

@p4-54
IServiceProvider is the interface of the built-in .NET DI container. It's the object that actually resolves services, through GetService or GetRequiredService.

You register services on an IServiceCollection in Program.cs, and when the host is built, that becomes the root IServiceProvider, which holds the singletons. For each HTTP request, ASP.NET Core creates a scope, a child provider, which holds that request's scoped services like DbContext, and HttpContext.RequestServices points to it. When the request ends, the scope is disposed, along with its scoped and transient disposables.

In normal code I don't use IServiceProvider directly. I use constructor injection, because calling the provider all over the code is the service locator anti-pattern and hides dependencies. I use it in a few specific places, inside factories that pick an implementation at runtime, and in singletons or background services where I create a scope with IServiceScopeFactory to get scoped services. Like, our background message consumer creates a scope per message to get a fresh DbContext.

@p4-55
My rule is that a service should only depend on services that live at least as long as it does.

A singleton lives for the whole application, so it should depend only on other singletons. A scoped service lives for one request, so it can depend on scoped and singleton services. A transient is created every time, so it can depend on anything, as long as it's resolved inside a scope when it needs scoped services. A singleton can technically take a transient, but that transient then effectively becomes a singleton, which can surprise you.

The dangerous case is a singleton depending on a scoped service, like DbContext. That's called a captive dependency. The singleton holds the first request's DbContext forever, which isn't thread-safe and serves stale data. ASP.NET Core catches this in development with scope validation, which throws at startup.

When a singleton genuinely needs scoped work, like our background consumer, it injects IServiceScopeFactory and creates a scope per unit of work. I can show that pattern in code.
