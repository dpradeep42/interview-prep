@p5-18
Primary and foreign keys are basically the tools for identity and integrity in a relational database.

A primary key uniquely identifies each row in a table. It can't be null, and there's only one per table, though it can span multiple columns. In SQL Server, the primary key creates a clustered index by default, so it often also defines the physical order of the data. A good primary key is small, stable and never changes, like an integer identity or a GUID. A foreign key is a column, or columns, in one table that refers to the primary key of another table. It enforces referential integrity. You can't create a shipment for a site that doesn't exist, and you can't delete a site that still has shipments, unless you've defined cascade rules, like cascade delete or set null.

In practice, I always index foreign key columns, because SQL Server doesn't do it automatically, and joins and deletes depend on them. People miss that.

In a clinical system, foreign keys are a cheap but very strong guarantee of data integrity, so we never skip them for convenience. I can explain how to choose between integer and GUID keys.

@p5-19
A unique constraint guarantees that no two rows have the same value in a column, or a combination of columns. SQL Server enforces it with a unique index behind the scenes.

A primary key is also unique, but there are differences. A table has only one primary key, but can have many unique constraints. A primary key can't contain nulls, while a unique constraint in SQL Server allows one null, or with a filtered unique index you can allow many. The primary key is the row's main identity, used by foreign keys, while unique constraints protect alternate keys, which are natural business identifiers. And by default, the primary key is clustered, while unique constraints are non-clustered.

A typical design, I'd say, is a surrogate primary key, like an integer Id, plus unique constraints on natural keys that must never duplicate.

In our IRT database, kits have an integer Id as the primary key, but KitNumber has a unique constraint, because two physical kits with the same number would be a serious problem in a trial. The database enforces it even if two requests race each other. I can explain how we surface that as a 409 in the API.

@p5-20
A composite index is an index on more than one column, like StudyId, Status and ShipmentDate together.

The order of columns matters a lot. The index is sorted by the first column, then by the second within that, and so on, like a phone book sorted by surname then first name. So it can support seeks on the leading columns, StudyId alone, or StudyId and Status, or all three. But it can't efficiently seek on Status alone, because Status isn't the leading column. That's called the leftmost prefix rule.

My rule for column order is equality columns up front, the ones compared with equals, and range columns last, like dates with greater than or less than, because once you hit a range, the following columns can't be used for seeking. Then add INCLUDE columns for anything the query selects, to avoid key lookups.

Our shipment list index followed exactly that. StudyId and Status for equality, then ShipmentDate for the range, with the displayed columns included. That's what let the query seek directly to a study's pending shipments in a date range. I can show the execution plan difference.

@p5-21
So a filtered index is a non-clustered index with a WHERE clause, so it only contains a subset of the table's rows.

Like, an index on ShipmentDate, WHERE Status equals Pending. If only a small percentage of shipments are pending at any time, this index is much smaller than a full one. That means less storage, faster seeks, cheaper maintenance on writes, and more accurate statistics for that subset. It's ideal for queries that always target a "hot" subset of the data. Another classic use is a filtered unique index, like enforcing that a kit number is unique only where it's not null, or only among active records.

The catch is that the query's predicate has to match the filter, so SQL Server knows the index covers it. Parameterised queries can make that tricky, because the optimizer can't always prove a parameter matches the filter. It works best with literal values, like Status equals Pending in the query text.

In our IRT system, dashboards repeatedly query pending and in-transit shipments, which are a small fraction of all shipments. A filtered index on those statuses made those dashboard queries much faster. I can explain how to check whether the index is used.

@p5-22
Indexes improve performance by letting SQL Server find rows without reading the whole table.

An index is a B-tree, sorted by its key. Instead of scanning millions of rows, SQL Server navigates the tree in a few page reads, which is logarithmic, and seeks straight to the matching rows. A covering index, with included columns, can answer the whole query without touching the table. Indexes also help with sorting and joins, because data is already ordered.

But they have costs. Every insert, update and delete has to also update every relevant index, so write-heavy tables slow down with too many indexes. They use disk and memory. Random keys can cause page splits and fragmentation. And indexes on low-selectivity columns, like a true or false flag, or indexes no query uses, are pure cost with no benefit.

So I add indexes based on real queries and execution plans, and every so often check the index usage DMVs to find unused or duplicate indexes to remove. When we added the covering index for our shipment list, we also tested the write impact in validation, because shipments are updated frequently, honestly. I can explain how to find missing index suggestions.

@p5-23
An execution plan is the optimizer's recipe for running a query, which indexes to use, in what order to access tables, which join algorithms to use, and where to sort or aggregate.

SQL Server's optimizer creates the plan based on statistics about the data, and then caches it for reuse. The plan is a tree of operators, like index seeks and scans, key lookups, nested loops, hash and merge joins, and sorts. Each shows estimated rows and cost, and in the actual plan, the actual rows too. You get the estimated plan, which doesn't run the query, and the actual plan, which runs it and shows what really happened.

When I read a plan, I look for a few red flags. Scans on large tables where I expected a seek, expensive key lookups, sorts or hash operations spilling to tempdb, and big differences between estimated and actual rows, which point to stale statistics or parameter sniffing. I use SSMS for single queries, and Query Store to see plans over time and spot regressions.

In our shipment list fix, the plan showed a clustered index scan and key lookups, and honestly that directly told me what to fix. I can walk through that plan.

@p5-24
These are three ways SQL Server can read data, and they differ hugely in cost.

A table scan reads every row of a heap, which is a table without a clustered index. An index scan reads all, or a large range, of an index, either the clustered index, which is effectively the whole table, or a non-clustered one. Both scale with the size of the table, so they get slower as data grows. An index seek uses the B-tree structure to navigate directly to the matching rows, reading only a few pages to find them. That scales with the number of matching rows, not the table size.

Seeks aren't always better, though. If a query needs a large percentage of the table, a scan can genuinely be cheaper than thousands of seeks plus lookups, and the optimizer picks that on purpose. The problem is an unexpected scan for a selective query, usually caused by a missing index, a non-SARGable predicate, or a data type mismatch.

In our slow shipment list, the plan showed a clustered index scan for a query that needed a few hundred rows. Fixing the predicate and adding the right index turned it into a seek, and reads dropped from [about 400,000 to 2,000]. I can explain how to spot that in a plan, you know.

@p5-25
Cardinality is the number of rows the optimizer expects at each step of a query plan. Statistics are what it uses to make those estimates.

Statistics are objects that describe how values are distributed in a column or index, mainly through a histogram of up to 200 steps, plus density information. When the optimizer sees a filter like StudyId equals 42, it uses the histogram to estimate how many rows will match. That estimate drives every decision, which index to use, which join type, and how much memory to grant. If the estimate is badly wrong, the plan can be terrible, like a nested loop over a million rows, or a sort that spills to tempdb.

Statistics go stale when data changes a lot, say after a big data load. SQL Server updates them automatically after enough changes, but on large tables that threshold can be reached late. Then I update them manually, or schedule maintenance.

The symptom I look for is a big gap between estimated and actual rows in the actual plan. In our IRT system, after a large data import, [one query became slow until we updated statistics], which is why we now update stats after big imports. I can explain how this relates to parameter sniffing.

@p5-26
Both combine the results of two or more queries into one result set, with the same columns. The difference is how they treat duplicates.

UNION removes duplicate rows from the combined result. To do that, SQL Server has to compare all rows, which means an extra sort or hash operation, and that costs CPU and memory, and can spill to tempdb on large results. UNION ALL just appends the results and keeps every row, including duplicates. It's faster, because there's no deduplication step, and it can stream results without waiting for all of them.

So my default is UNION ALL. I only use UNION when I actually need distinct rows, and the inputs can genuinely overlap. Very often the two queries can't produce the same row anyway, like combining "shipments from depot A" with "shipments from depot B", and then UNION is just wasted work.

It's one of those small things I look for in code reviews of SQL, because people write UNION out of habit a lot. On a large reporting query, switching to UNION ALL removed an expensive sort from the plan. I can explain how to read that in the execution plan.

@p5-27
EXISTS and IN both check whether a value has a match in another set, and modern SQL Server often produces the same plan for both. But there are differences worth knowing.

EXISTS checks whether a subquery returns any row, and stops at the first match, so it's naturally efficient for existence checks. It's also correlated, meaning it can compare several columns. IN compares a value against a list of values, or the result of a subquery. For a short fixed list, like status IN Pending and Shipped, IN is the clearest. For subqueries, the optimizer usually converts both into the same semi-join.

The important difference is with negation and NULLs. NOT IN returns no rows at all if the subquery returns even one NULL, because comparing with NULL is unknown. That's a classic, silent bug, and it can catch people out. NOT EXISTS doesn't have that problem. So I always prefer NOT EXISTS for "find rows with no match".

Like, "sites with no shipments" in our system is written with NOT EXISTS against the shipments table, which is correct and uses the foreign key index efficiently. In EF Core, a negated Any translates to exactly that. I can show an example of the NOT IN bug.

@p5-28
Both hold an intermediate result inside a larger query, but they behave very differently.

A CTE, defined with WITH, is a named query that exists only for the single statement that follows it. It's not stored anywhere, the optimizer just expands it into the main query, like a view. So it's mainly about readability, breaking a complex query into named steps. It's also the only way to write recursive queries, like walking a depot hierarchy. But if you reference a CTE twice, it may be computed twice. A temporary table, with a hash prefix, is actually materialised in tempdb. It can have indexes, it gets its own statistics, and it can be reused across several statements in the same session or procedure.

So my rule is CTE for readability and recursion in a single query. Temp table when the intermediate result is large, reused multiple times, or when the optimizer is making bad estimates on a complex query, because materialising it with real statistics often gives a much better plan.

In our IRT reporting, a heavy monthly report got much faster when I moved a large intermediate step from a CTE into an indexed temp table. Table variables are another option, for small sets. I can explain the difference.

@p5-29
All three are window functions that number rows within a partition, based on an ORDER BY. The difference is how they handle ties, rows with the same ordering value.

ROW_NUMBER gives every row a unique sequential number, 1, 2, 3, 4, even if values tie. The order among tied rows is arbitrary, unless you add a tie-breaker column. RANK gives tied rows the same rank, and then leaves a gap. So if two rows tie for second place, you get 1, 2, 2, 4. DENSE_RANK also gives ties the same rank, but without gaps, 1, 2, 2, 3.

The use cases follow from that. ROW_NUMBER is for picking exactly one row per group, like the latest status per shipment, or for deduplication, or paging. RANK is for competition-style rankings, where gaps make sense. DENSE_RANK is for questions like "the top 3 distinct values", say the sites with the three highest dispensing counts, including ties.

In our IRT database, I use ROW_NUMBER partitioned by shipment, ordered by status date descending, to get each shipment's current status from the history table. I'd say it's the one I use most. I can write that query out.
