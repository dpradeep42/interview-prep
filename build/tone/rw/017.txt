So by default the request body is a forward-only stream. Once something reads it, like model binding or some middleware, it's consumed, and anything after that just sees an empty body. You hit this when a middleware wants to log the body, or verify a webhook signature, and the controller also needs to bind it.

The fix is Request.EnableBuffering. It makes the body seekable by buffering it, in memory for small bodies and in a temp file for bigger ones. After reading, you reset the position to zero, Request.Body.Position equals 0, so the next reader starts from the beginning.

The typical middleware goes like this. Call EnableBuffering, read the body asynchronously with a StreamReader, with leaveOpen set to true, do whatever you need, like computing the HMAC signature, then reset the position and call the next middleware.

A few cautions though. Buffering big bodies costs memory or disk, so I only do it where it's needed, like specific webhook routes, and with a size limit. I always read async, because synchronous I/O is disabled by default in Kestrel anyway. And for really high throughput, the newer Pipelines-based Request.BodyReader is more efficient.

For webhook signature checks, another option is to bind the body as a raw string or byte array right in the endpoint, verify it, and then deserialise it yourself. Honestly, that's often simpler than the middleware route.

@p17-193
Open generic registration means you register a generic interface with a generic implementation once, without the type argument. Like AddScoped with typeof IRepository of open T, and typeof EfRepository of open T. Then when something asks for IRepository of Shipment, the container creates EfRepository of Shipment automatically. One registration covers every entity type.

The framework actually uses this itself. ILogger of T is registered as an open generic, which is why any class can ask for ILogger of its own type. IOptions of T works the same way.

Other places I see it, generic handlers or validators, like IValidator of T. MediatR pipeline behaviours, which are open generics applied to every request type. And generic caching decorators.

Constraints work too. If the implementation has generic constraints, like where T is an entity, the container only uses it for types that satisfy them. That's been there since around .NET 5.

The built-in container has some limits though. It can't do convention-based scanning, like register every class ending in Service. So I use the Scrutor library for assembly scanning and for decorating open generics. And when there are several registrations for the same closed type, the last one wins when you resolve one, while IEnumerable gives you all of them.

I use this for cross-cutting behaviours. But I don't create generic repositories over EF Core by default, that's mostly an extra layer for nothing.

@p17-194
Named options let you have several configured instances of the same options class, each with a name. Let me take an example. I have a VendorApiOptions class with BaseUrl, timeout and credentials, and there are three vendors, each needing its own settings. Instead of three almost identical classes, I register one class three times with names. Configure of VendorApiOptions named DepotA bound to one config section, DepotB bound to another, and so on.

To read them, you use IOptionsMonitor or IOptionsSnapshot and call Get with the name, like Get DepotA. IOptions of T doesn't support names, it only gives you the default unnamed instance. People get stuck on that one.

The framework uses named options a lot. Each authentication scheme has its own named options, which is how you can configure two JWT bearer schemes differently. HttpClient factory's named clients use named options under the hood too.

Validation works per name as well, with ValidateDataAnnotations or a custom IValidateOptions, which receives the name. So I can validate each vendor's settings at startup with ValidateOnStart.

PostConfigure and ConfigureAll let you apply common defaults to every named instance, like a default timeout, and then override per name.

I used this pattern for integration settings, where each partner has its own endpoint and credentials. Adding a new partner is then just a new configuration section, no code change.

@p17-195
Okay, so the Generic Host is the .NET foundation for running any long-lived app. It gives you dependency injection, configuration, logging, and lifetime management for hosted services, with graceful startup and shutdown. It's used for console apps, worker services, and as the base of web apps. Earlier you created it with Host.CreateDefaultBuilder and a chain of callbacks, like ConfigureServices and ConfigureWebHostDefaults.

WebApplication came in .NET 6 with minimal hosting. It's a simpler, more direct API built on top of the Generic Host, specifically for web apps. WebApplication.CreateBuilder gives you a builder with Services, Configuration, Logging and Environment as properties. You register services, call Build, then configure middleware and endpoints on the app, and Run. No Startup class, no nested callbacks. It still uses the Generic Host underneath, so hosted services and everything else just work.

For non-web apps, .NET 7 added Host.CreateApplicationBuilder, which gives the same simple linear style as WebApplication, just without the web server. The Worker Service template uses it.

So these days, WebApplication.CreateBuilder for APIs and web apps, Host.CreateApplicationBuilder for workers and consumers, and the older callback style only in existing code. The concepts, DI, configuration, hosted services, are identical across all of them, so moving between them isn't a big deal.

@p17-196
A Worker Service is a .NET app on the Generic Host with one or more BackgroundService classes. To run it as an OS service, you basically add one line and the matching package.

For Windows, it's the Microsoft.Extensions.Hosting.WindowsServices package and AddWindowsService with a service name. That makes the host respond to the Windows Service Control Manager. Start, stop and shutdown signals map to the host's lifetime, so StopAsync runs when the service stops. Then you install it with sc.exe create, or PowerShell New-Service, pointing at the published exe, and set the recovery options, like restart on failure, and the account it runs under. Ideally a managed service account with least privilege.

For Linux, it's the Microsoft.Extensions.Hosting.Systemd package and AddSystemd. It hooks into systemd's notifications and logging format. Then you create a unit file under etc systemd system with the ExecStart path, the user, Restart equals always, and environment variables, and enable it with systemctl.

A few things to watch. The working directory is different for services, like System32 on Windows, so I use AppContext.BaseDirectory for file paths. I learned that the hard way with a config file not being found. Logging should go to a central sink or the event log, not just the console. And configuration and secrets per environment.

In our CIRT environment, some RabbitMQ consumers run as Windows services on the application servers, so this is pretty familiar for me.

@p17-197
Honestly, I follow a few simple conventions so the API is predictable for whoever calls it.

Use nouns for resources, not verbs, because the HTTP method is already the verb. So GET shipments, POST shipments, GET shipments slash id. Not getShipments or createShipment.

Plural nouns for collections, and consistently. Sites, kits, subjects.

Nesting for clear parent-child relationships, but only one level deep, like sites slash site id slash subjects. Deep nesting, like studies, sites, subjects, visits all chained together, gets fragile. Once a resource has its own id, you can just address it directly, like visits slash 4.

Lowercase with hyphens for multi-word names, like return-shipments, and camelCase for JSON property names.

Query parameters for filtering, sorting and paging. Like status equals pending, sort by createdAt descending, page 2.

Then there are actions that don't fit CRUD neatly, like cancel or dispatch. Two reasonable choices there. Model it as a state change and PATCH the status, or a sub-resource action, like POST shipments slash id slash cancel. I prefer the second when the action has its own rules and side effects, because it's clearer and easier to authorise.

If you use URL versioning, put the version at the start of the path, like api slash v1.

And above everything, be consistent across the whole API, and write it down in the team's API guidelines. That matters more than any single rule.

@p17-198
PATCH is for partial updates, changing just some fields of a resource. And there are two common formats.

JSON Merge Patch, RFC 7396, sends a JSON object with only the fields to change, like status Cancelled. Fields you don't include stay the same, and a field set to null gets removed or cleared. Simple and intuitive for clients. The limitation is you can't really tell "set to null" apart from other intentions, and you can't update individual array elements. Arrays get replaced entirely.

JSON Patch, RFC 6902, sends a list of operations, add, remove, replace, move, copy and test, each with a path. Like op replace, path slash status, value Cancelled. It's more powerful. It can change array items and include test operations that act like preconditions. But it's more complex for clients.

In ASP.NET Core, JsonPatchDocument of T supports JSON Patch. It used to need Newtonsoft.Json, and .NET 10 added a System.Text.Json-based version. What I do is apply the patch to a DTO, not directly to the EF entity, then validate the DTO, and map only the allowed fields onto the entity. That prevents over-posting through patch paths.

For merge patch, I deserialise into a DTO with nullable or optional wrapper properties, so I know which fields were actually sent.

Honestly though, for simple partial updates I often prefer specific endpoints, like PUT status, which are easier to validate and authorise.

@p17-199
For data annotations, you can create your own attribute by inheriting ValidationAttribute and overriding IsValid. The method gets the value and a ValidationContext, and returns ValidationResult.Success, or a ValidationResult with an error message and the member name. Like a FutureDate attribute that checks a date is after today, or a ValidCountryCode attribute that checks against a list.

The ValidationContext gives you the whole object being validated, so you can compare with other properties, and the service provider too. But I avoid pulling heavy dependencies inside attributes.

For rules involving multiple properties, like end date must be after start date, you can go two ways. A class-level attribute, or implement IValidatableObject on the model, where Validate returns any number of results. ASP.NET Core runs that after the property-level attributes pass.

Once you've built it, the attribute works anywhere data annotations work. ApiController's automatic 400 responses, Validator.TryValidateObject, options validation with ValidateDataAnnotations, and Blazor forms.

That said, for complex rules, especially ones that need the database or services, I go with FluentValidation. Attributes can't easily do async work or use injected services cleanly, and they get hard to test once they need dependencies. So for me, custom attributes are for small, reusable, self-contained rules, and that's about it.

@p17-200
Both let you share data between different parts of the pipeline during a single request. Like a tenant id resolved in middleware and then used in a controller and a repository.

HttpContext.Items is a dictionary on the HttpContext, object keys and object values, and it lives only for the current request. It's built in and quick to use. But it's untyped, so you're casting values, keys can clash between components unless you use private object keys, and it ties consumers to HttpContext, which isn't there in background work and is annoying to set up in unit tests.

A scoped service is a class registered with AddScoped, so DI creates one instance per request. A middleware gets it injected through InvokeAsync parameters and sets properties, like TenantContext.TenantId. Then controllers, handlers and repositories inject the same instance and read it. It's strongly typed, easy to discover, easy to fake in tests, and it doesn't depend on HTTP. So the same TenantContext can be filled by a message consumer for background processing.

So my rule is, a scoped service for anything important that business code depends on, current user, tenant, study context, correlation data. HttpContext.Items is fine for small, web-layer-only details, like passing something between two middlewares.

One reminder, scoped services must never be captured by singletons, or they'll leak across requests. That's a nasty bug to track down.

See, there are basically two ways to do it.

One is serving the SPA from the ASP.NET Core app itself. The front-end build output, the index.html and the bundled JavaScript and CSS, gets copied into wwwroot. The app uses UseStaticFiles to serve the files, and MapFallbackToFile with index.html, so deep links, like shipments slash 123, return index.html and the client-side router handles them, while api routes go to the controllers. It's one deployment, one origin, so no CORS, and cookies just work. For caching, the hashed bundle files get a long max-age, while index.html isn't cached, so users pick up new versions after a deployment.

The other is serving the SPA separately. The front end goes to static hosting, like S3 with CloudFront, Azure Static Web Apps or a CDN, and calls the API on its own domain. It's cheaper and faster to serve globally, front end and back end deploy independently, and the API stays focused on data. The cost is CORS configuration, or putting both behind one domain with path routing on the CDN.

During development, Vite or the Angular CLI dev server runs the front end with hot reload and proxies API calls to the ASP.NET Core app, so you avoid CORS locally.

In our IRT, the React shell is built with Vite and deployed separately, and the MVC portal links into it, sharing the Keycloak SSO session. So we went with the second approach.

@p17-202
The environment name comes from the ASPNETCORE_ENVIRONMENT or DOTNET_ENVIRONMENT variable. Standard values are Development, Staging and Production, and it defaults to Production if not set. IWebHostEnvironment, or IHostEnvironment for workers, exposes it, along with paths like the content root and web root.

Configuration uses it automatically. appsettings.json loads first, then the environment-specific appsettings file overrides it, then environment variables and other sources override those.

In code, IsDevelopment is typically used to turn on the developer exception page, Swagger UI or detailed errors only in development.

To use it safely, a few rules I stick to. Defaulting to Production is actually a good thing. If someone forgets the variable, the app runs with the safest settings. I keep environment checks few and at the edges, mostly in Program.cs, and drive differences through configuration values, like a feature flag for Swagger, instead of scattering IsDevelopment checks through business code. Business logic should behave the same in every environment, otherwise testing in UAT doesn't prove anything about production. And no secrets in a committed appsettings.Development.json. Local secrets go in user secrets.

You can also add custom environments, like UAT, checked with IsEnvironment UAT, and a matching appsettings.UAT.json. That fits validated release flows like ours, with separate UAT and production settings.

This one's really common, and I check things in a fixed order.

The first thing I check is the Content-Type header. If the client doesn't send application/json, ASP.NET Core can't use the JSON input formatter. With ApiController, that usually gives a 415 Unsupported Media Type, but in some setups the parameter is just null.

Then the JSON shape versus the DTO. If the JSON doesn't match, like a wrapping object the DTO doesn't expect, a string where a number should be, or a bad date format, deserialisation fails. With ApiController, that returns a 400 with details in the problem details response, so I read that response body carefully. Without ApiController, the parameter comes in null and ModelState has the error.

After that, property naming and casing. ASP.NET Core uses camelCase and case-insensitive matching by default, but custom JsonSerializerOptions might have changed that. Properties also need public setters or a matching constructor, and fields aren't bound by default.

Then the binding source. A complex type in an ApiController is inferred as FromBody, but without ApiController, or for simple types, you may need FromBody explicitly. And only one parameter can come from the body.

And one more, maybe something read the body earlier, like a logging middleware without EnableBuffering.

To actually see what's going on, I log ModelState errors, test with a known-good request from an HTTP file or Postman, and turn on debug logging for model binding. Usually one of those shows it pretty quickly.
