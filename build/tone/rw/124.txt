An artifact is the output of a build that gets deployed, like a zip of published .NET files, a NuGet package, or a Docker image. The key principle is "build once, deploy many". The pipeline builds the artifact once, and that exact same artifact is promoted through every environment, dev, test, UAT and production. We never rebuild for production, because a rebuild could produce something different from what was tested.

Versioning makes each artifact uniquely identifiable and traceable. I use semantic versioning for releases, major, minor and patch, plus the build number, say 4.2.1 plus build 345. Lots of teams calculate this automatically from Git tags, with a tool like GitVersion. For Docker images, the tag is the version, or the commit hash, never just "latest", because latest is ambiguous and makes rollback hard. The artifact also records the Git commit it came from.

Artifacts are stored in a repository, Azure Artifacts or the pipeline's own artifacts for packages and build output, and Amazon ECR for images, with retention rules so old ones are cleaned up, but released versions are kept.

In our GxP environment, honestly, this traceability is essential. For any version in production, we can show exactly which commit, build, tests and approvals produced it. It also makes rollback simple, you just redeploy the previous artifact.

@p6-29
To build Docker images in a pipeline, I want the build to be repeatable, fast, secure and traceable.

In Azure DevOps, the steps are build the image using the multi-stage Dockerfile from the repository, tag it with a unique version, like the build number or commit hash, never just latest, run the tests, scan the image, and only then push it to the registry, which is Amazon ECR for us.

The Dockerfile itself does the restore, build and publish in a build stage using the .NET SDK image, and the final stage uses the small runtime image. Tests can run in their own stage, so a failing test fails the image build.

Speed comes from layer caching, copying project files and restoring before copying the rest of the source, and using BuildKit with a cache from the registry, because pipeline agents are often fresh machines with no local cache. People forget that one.

On security, the pipeline authenticates to the registry using a service connection, with short-lived credentials where possible. No secrets are passed as build arguments, because they can end up in the image history. And the image scan, with a tool like [Trivy], fails the pipeline on high or critical vulnerabilities.

The image digest and tag are saved with the build, so the release stages deploy exactly that image to every environment. That's the build-once, deploy-many idea applied to containers.

Okay, so our Azure DevOps Server is on-premise, a legacy from Cenduit's CIRT, and [IQVIA's newer services, which I've worked on,] run on AWS, IQVIA's standard cloud. So we deploy to AWS from Azure DevOps by connecting the pipeline to AWS securely, pushing the image, and then telling ECS to run the new version.

The connection is the bit to get right. Azure DevOps uses an AWS service connection. The best option is OpenID Connect, where the pipeline gets short-lived credentials by assuming an IAM role, so no long-lived access keys are stored anywhere. The role only has the permissions the deployment needs, like pushing to ECR and updating specific ECS services.

Then the build stage builds the Docker image, tests and scans it, and pushes it to Amazon ECR with a unique version tag.

Then the release stage, per environment. It registers a new revision of the ECS task definition with the new image tag, then updates the ECS service to use it. ECS does a rolling deployment. It starts new tasks, waits for them to pass the load balancer health checks, then stops the old ones. The deployment circuit breaker can roll back automatically if the new tasks keep failing. Infrastructure changes, like new queues or alarms, go through Terraform steps in the same pipeline, with plan and apply.

Each environment is a stage with its own variables, and controlled environments have approvals by named people before the stage runs.

Rollback is just redeploying the previous task definition revision, which is quick because the old image is still in ECR.

@p6-31
In CI/CD, my rule is that non-secret settings live with the pipeline or the application configuration, and secrets live in a secrets manager, never in code, YAML or logs.

For normal settings, like environment names, URLs or feature flags, I use variable groups or stage variables in Azure DevOps, per environment, or the application's appsettings files per environment.

Secrets come in two kinds, really. Secrets the pipeline itself needs, like credentials to reach AWS or a registry, are stored as secret variables or service connections in Azure DevOps. Secret variables are encrypted, masked in logs, and not passed to forked pull request builds. Even better is OIDC to AWS, so there's no long-lived key at all. Secrets the application needs at runtime, like database passwords, shouldn't go through the pipeline. They live in AWS Secrets Manager, and the ECS task reads them at startup through its IAM role. The pipeline only deploys a reference to the secret, not the value. Azure Key Vault can also be linked to a variable group when it's needed during the pipeline.

On top of that, least privilege for service connections, approvals on who can use production connections, rotation of secrets, and never echoing secrets in scripts. And we scan the repository for accidentally committed secrets.

Deployment approvals mean a human, with the right authority, checks a release before it goes into a controlled environment.

In Azure DevOps, you can do it two ways. In classic release pipelines, which we use, each stage, like UAT or production, can have pre-deployment approvals, named people or groups who must approve before the stage runs, and post-deployment approvals to confirm it went well. @p6-33
Okay, so Kafka is a distributed event streaming platform. It stores streams of events in an ordered, durable log, and lets lots of applications publish and read those events at high volume. Unlike a traditional queue, reading a message doesn't delete it. Events are kept for a retention period, so several consumers can read the same data independently, and even replay it.

The main terms, quickly. A broker is a Kafka server, and several brokers form a cluster. A topic is a named stream of events, like shipment-status. Each topic is split into partitions, which are the unit of parallelism and scaling, and each partition is an ordered, append-only log stored on brokers. An offset is the position of a message inside a partition, a number that only goes up, and consumers track their offset to know where they've got to. A producer is an application that writes events to a topic. It chooses the partition, usually by hashing the message key, so all events with the same key, like the same shipment id, go to the same partition and stay in order. A consumer reads events, and consumers with the same group id form a consumer group, where each partition is read by only one consumer in the group, so the group shares the work.

In [the AWS-side services I've worked on], we use Kafka for events like shipment status updates, which several services consume, each in its own consumer group, and which we sometimes need to replay.

@p6-34
Kafka gets scalability mainly through partitioning, and fault tolerance mainly through replication.

For scalability, each topic is split into partitions, and the partitions are spread across the brokers in the cluster. Producers write to different partitions in parallel, and in a consumer group, each partition is read by one consumer, so adding consumers, up to the number of partitions, increases processing in parallel. Adding brokers spreads the load further. Kafka is also very efficient by design. It writes sequentially to an append-only log, batches and compresses messages, and relies on the operating system's page cache, so it handles very high throughput.

For fault tolerance, each partition is replicated to several brokers, usually three, set by the replication factor. One replica is the leader, which handles reads and writes, and the others are followers, which copy from the leader. The replicas that are fully caught up are the in-sync replicas. If the leader's broker fails, one of the in-sync followers automatically becomes the new leader, and clients carry on. With producer acks set to all, and a minimum of two in-sync replicas, a write is only confirmed once it's safely on more than one broker, so a single failure doesn't lose data. Consumers also store their offsets in Kafka, so after a consumer crashes, another one continues from the last committed position. That's basically the whole story.

@p6-35
The replication factor is how many copies of each partition Kafka keeps, on different brokers. A replication factor of three, which is the usual choice for production, means every partition exists on three brokers, so the cluster can lose a broker without losing data.

Among those copies, one is the leader and the others are followers. The leader handles all the writes for that partition, and usually the reads too. The followers keep copying new messages from the leader. Followers that are fully caught up are called in-sync replicas, the ISR. If a follower falls too far behind, it's removed from the ISR until it catches up.

If the leader's broker fails, the cluster controller picks one of the in-sync followers as the new leader, and producers and consumers automatically switch to it. Because it was in sync, nothing confirmed is lost. Leaders are spread across brokers, so the load is balanced.

Two settings work together for durability, and honestly this is where people get confused. On the producer, acks set to all means a write is only acknowledged when all in-sync replicas have it. On the topic, min.insync.replicas set to two means a write is rejected if fewer than two replicas are in sync. So with a replication factor of three and a minimum of two in-sync replicas, the cluster tolerates one broker failure with no data loss and no downtime.

@p6-36
Kafka guarantees ordering within a partition, but not across a whole topic.

Each partition is an append-only log. Messages are written in order and each gets an increasing offset, and a consumer reads them in that same order. But a topic has several partitions, processed in parallel by different consumers, so there's no global order between messages in different partitions.

In practice, you usually don't need global ordering, you need ordering per entity, like all the events for one shipment or one order. You get that with a message key. The producer hashes the key to choose the partition, so every event with the same key, like the shipment id, always goes to the same partition, and stays in order. So "shipment created", "shipped" and "delivered" for one shipment are always processed in sequence.

A few things can break ordering, though. Retries on the producer can reorder messages, which the idempotent producer, now the default, prevents. Increasing the number of partitions changes which partition a key maps to, so existing keys can move. And on the consumer side, if you process messages from one partition in parallel threads, you lose the order, unless you parallelise per key.

If you really need a total order across everything, you'd use a single partition, but that limits throughput to one consumer. In our shipment events, we key by shipment id, which gives the ordering that matters.

@p6-37
Retention and log compaction are basically the two ways Kafka decides when to remove old messages from a topic.

Retention removes messages based on time or size. By default, messages are kept for seven days, set by retention.ms, or until the partition reaches a size limit. After that, old segments of the log are deleted, whether or not anyone has read them. Consumers just need to read within the retention window. Because consumption doesn't delete data, lots of consumers can read independently, and you can replay events within that window, say after fixing a bug in a consumer.

Log compaction works differently. Instead of deleting by age, Kafka keeps at least the latest message for each key, and removes older messages with the same key. So the topic becomes a snapshot of the current state of every key. Like, a topic of customer addresses keyed by customer id would keep the latest address for each customer forever. To delete a key completely, you send a message with that key and a null value, called a tombstone. Compacted topics are great for rebuilding a cache or state store, and Kafka uses one internally to store consumer offsets.

The choice depends on the use. For event history, like shipment status events, time-based retention, and for "latest value per key" data, compaction. A topic can also combine both.

@p6-38
When a Kafka consumer crashes, the consumer group recovers automatically, and the real question is just whether messages get processed twice.

Each consumer in a group sends heartbeats. When one crashes, it stops sending them, and after the session timeout, the group coordinator considers it dead. Then a rebalance happens, and its partitions are reassigned to the remaining consumers in the group. The new owner of each partition starts reading from the last committed offset for that partition.

Honestly, here's the important part. If the crashed consumer had processed some messages but hadn't committed their offsets yet, those messages will be processed again by the new consumer. That's at-least-once delivery. So consumers have to be idempotent, meaning processing the same message twice has the same effect as once, like by recording processed message ids, or using upserts with a unique key. The opposite mistake is committing the offset before processing, then a crash would skip messages, so I commit after processing.

To make crashes less disruptive, tune the session timeout, use the cooperative rebalancing strategy, so only the affected partitions move, and handle shutdown gracefully, committing offsets before leaving the group.

And while a consumer is down and before the rebalance, lag grows on its partitions, which is why we alert on consumer lag.

@p6-39
So basically, consumer lag is the difference between the latest offset written to a partition and the offset the consumer group has committed. In simple words, it's how many messages are waiting to be processed. Some lag is normal, but lag that keeps growing means consumers can't keep up, and data is getting more and more delayed. And if lag grows beyond the retention period, messages are deleted before they're processed.

I monitor it per partition, with tools like Burrow, Kafka exporters for Grafana, or the cloud provider's metrics, and alert when it keeps growing.

To troubleshoot, I ask a few questions. Is the lag on all partitions or just one? If one, it might be a hot key, where one key gets most of the traffic, or a poison message that keeps failing. Did the incoming volume go up? Then I may need more consumers, up to the number of partitions. Did processing get slower? Then I check what each message does, often a slow database call, an external API, or processing one message at a time where batching would help. Are consumers rebalancing a lot? Frequent rebalances, often because processing takes longer than max.poll.interval.ms, stop consumption again and again. And are the consumers healthy, with enough CPU and memory?

The fix follows the cause, so scale out, add partitions, optimise processing, batch, tune poll settings, or move poison messages to a dead-letter topic.
