A cold start is when Lambda has to create a new execution environment to handle a request. That means downloading the code, starting the runtime, and running your initialisation code, before the function itself even runs. Later requests reuse the warm environment and they're fast.

Cold starts happen on the first request, after a period of inactivity, and when scaling up, because each new concurrent execution needs its own environment. For .NET, cold starts have traditionally been longer than for Node or Python, because of runtime startup and JIT compilation, sometimes over a second.

To reduce them, keep the deployment package small and trim dependencies. Use native AOT compilation, which removes JIT and makes .NET start much faster, or ReadyToRun as a lighter option. Use SnapStart where it's supported, which restores a snapshot of an initialised environment. Keep initialisation code light, and create heavy clients lazily. More memory also gives you more CPU, which speeds up startup. And for latency-critical functions, provisioned concurrency keeps environments warm, at extra cost.

Honestly, often the simplest answer is architecture. If a path is latency-critical and constant, a container on ECS might suit it better. Our Lambdas are event-driven background tasks, where a cold start doesn't hurt users. I can explain native AOT trade-offs.

@p2-5
DynamoDB modelling is kind of the opposite of relational modelling. Instead of starting from entities and normalising, you start from the access patterns.

I list every query the application needs before anything else, like "get a shipment by id", "list shipments for a site by date", or "get all events for a shipment". Then I design keys to serve them. The partition key has to have high cardinality, like a shipment id rather than a status, so data and traffic spread evenly and we avoid hot partitions. The sort key allows range queries within a partition, with conditions like begins with or between, say a sort key of "EVENT#" plus a timestamp. Extra access patterns are served with global secondary indexes. Single-table design goes further, storing related item types in one table with generic key names, so one query can fetch a shipment and its events together.

Other tools I use, conditional writes for optimistic concurrency and uniqueness, TTL to expire old items automatically, and Streams to react to changes.

The catch is that unplanned queries are expensive, so this works best when access patterns are stable. In the newer IQVIA services on AWS, DynamoDB holds simpler, high-volume status and event data, designed exactly this way. I can sketch a key design.

@p2-6
Caching strategies differ mainly in when the cache and the database get written, and which one you read first.

Cache-aside, or lazy loading, is the most common. The application reads from the cache, and on a miss, it reads from the database and stores the result in the cache with an expiry. It only caches data that's actually requested, and the cache can fail without breaking anything, but the first read is slower and data can be stale until it expires. Write-through writes to the cache and the database together, so the cache is always up to date for reads, at the cost of slower writes and caching data that might never be read. Write-behind writes to the cache first and flushes to the database later. It's really fast, but risky, because data can be lost if the cache fails.

Whatever the strategy, a few rules apply. Set TTLs, invalidate or update the cache when data changes, add jitter to expiries, and protect against cache stampedes, where lots of requests miss at once, with locking or HybridCache. And never treat the cache as the source of truth, trust me.

In the newer IQVIA services on AWS, ElastiCache Redis uses cache-aside for reference data, like depots and country rules, with short TTLs and eviction on change. I can explain how we handle invalidation.

@p2-7
Both spread traffic across targets, but they work at different network layers.

The Application Load Balancer works at layer 7, the HTTP level. It understands HTTP and HTTPS, so it can route based on the URL path, the host name, headers or query strings. Like, slash api slash shipments goes to one service and slash api slash sites to another. It terminates TLS, integrates with AWS WAF for web protection, supports WebSockets and HTTP/2, can authenticate users with OIDC, and works directly with ECS target groups. The Network Load Balancer works at layer 4, TCP and UDP. It doesn't look inside the request, so it's extremely fast, with very low latency, handles millions of requests per second, and gives you static IP addresses, which some partners need for firewall allow-lists. It also supports non-HTTP protocols.

Both do health checks and spread traffic across availability zones.

So for web APIs and microservices, I'd say the ALB is the default. I use an NLB when I need static IPs, extreme performance, or non-HTTP traffic, like an SFTP endpoint or a TCP service. In the newer IQVIA services on AWS, the ALB fronts all our ECS services, with path-based routing to each service. I can explain how target group health checks work.

@p2-8
S3 is AWS's object storage. It stores files, called objects, in buckets, with extremely high durability, eleven nines, and practically unlimited capacity.

It's used for all sorts of things, uploaded files and exports, backups, static websites, build artifacts, data lakes and logs. Storage classes trade cost against access speed, from S3 Standard for frequently accessed data, to Infrequent Access, to Glacier for archives. Lifecycle rules automatically move objects to cheaper classes or delete them after a period.

A presigned URL gives temporary access to one specific object, for upload or download, without giving the client any AWS credentials. Our backend, which has permission, generates a URL signed with its credentials, valid for a short time, like five minutes. The client uses that URL directly with S3. That's really useful for large files, because the upload goes straight to S3 instead of through our API, which saves bandwidth and memory, and avoids API Gateway size limits.

Security basics always apply, Block Public Access, encryption, least-privilege policies. In the newer IQVIA services on AWS, file imports and exports use presigned URLs, and our API only receives the object key after the upload completes. I can walk through that flow.

@p2-9
Least privilege means every identity gets only the permissions it needs to do its job, nothing more. In AWS, I apply it in a few concrete ways.

Every service gets its own IAM role, an ECS task role or a Lambda execution role. No shared "app" role with everything. Policies are specific, specific actions, like s3 GetObject rather than s3 star, and specific resource ARNs, like one bucket and prefix, or one secret, never a wildcard on everything. Conditions can narrow it further, like requiring requests to come through our VPC endpoint, or requiring encryption. No long-lived access keys in code or configuration. Services use roles with temporary credentials, and people use SSO. Separate AWS accounts for environments, so a mistake in development can't touch production. And regular reviews, where IAM Access Analyzer finds unused permissions and resources shared externally, so we can tighten policies over time.

Honestly, starting broad and planning to tighten later rarely happens, so I start tight and add permissions when needed.

In the newer IQVIA services on AWS, the vendor exchange service's role can only read its own Secrets Manager entries and write to one S3 prefix. If it were compromised, the blast radius is small. I can show a sample policy.

@p2-10
A typical layout uses one VPC spread across at least two availability zones, so losing one data centre doesn't take the system down.

In each availability zone, there are public and private subnets. Public subnets hold only what has to face the internet, the Application Load Balancer, and NAT Gateways for outbound traffic. Private subnets hold everything else, ECS tasks, Lambdas that need VPC access, RDS databases and ElastiCache. Often the databases sit in a separate, more restricted data subnet tier. Nothing in a private subnet has a public IP.

Security groups control traffic between layers, by reference. The ALB accepts 443 from the internet, the services accept traffic only from the ALB's security group, and the database accepts connections only from the services' security groups. VPC endpoints for S3, DynamoDB, ECR and Secrets Manager keep AWS traffic private and avoid NAT costs. In front, Route 53 for DNS and WAF on the ALB. Flow logs record traffic for troubleshooting and audits.

That's basically how the newer IQVIA services on AWS are set up, with each environment in its own account and VPC. It gives defence in depth, even a compromised container can't reach the database unless its security group allows it. I can draw it out.

Infrastructure as code means defining cloud resources, like networks, databases, load balancers and permissions, in versioned files, instead of creating them by clicking around in a console.

Tools like CloudFormation and Terraform read those files and create or update the real infrastructure to match. That brings the same benefits we get with application code. Repeatability, every environment, development, validation and production, is built from the same definitions, so they don't drift apart. Code review, infrastructure changes go through pull requests, and a plan shows exactly what'll change before it happens. Audit trail, git history shows who changed what, when and why. Drift detection, we can find manual changes. And recovery, a whole environment can be rebuilt quickly, which you really need for disaster recovery.

In regulated work like ours, that traceability matters a lot. Auditors want to see that every production change was reviewed, approved and reproducible, and IaC gives that evidence naturally.

Changes flow through the same pipeline as code, pull request, plan, review, approval, apply. Nobody changes production infrastructure by hand. I can compare CloudFormation and Terraform if that's useful.

@p2-12
Both are infrastructure-as-code tools, with different strengths, I'd say.

CloudFormation is AWS's native service. You write templates in JSON or YAML, and AWS manages them as stacks, including the state, so there's no state file for you to look after. It supports change sets to preview changes, and automatically rolls back if a deployment fails. New AWS features are usually supported quickly, and it's free. Its limit is that it's AWS only. AWS CDK lets you write CloudFormation in real programming languages, like C# or TypeScript. Terraform, from HashiCorp, uses its own language, HCL, and works across many providers, AWS, Azure, GCP, and also things like GitHub, Datadog or Kubernetes. It has an explicit plan and apply workflow, and a large ecosystem of reusable modules. But you manage the state file yourself, securely and with locking. OpenTofu is the open-source fork.

So I'd pick CloudFormation or CDK for an AWS-only organisation that wants the native, managed experience. Terraform for multi-cloud, or when managing non-AWS resources with the same tool.

The principles matter more than the tool, everything in code, reviewed, deployed by pipelines. I can explain how Terraform state works.

@p2-13
Terraform state is a file that maps the resources defined in your code to the real resources in the cloud, along with their attributes, like IDs and ARNs.

Terraform needs it to know what it's managing. When you run plan, it compares your code, the state, and the real infrastructure, and works out what to create, change or destroy. Without state, it wouldn't know that a bucket in your code is the bucket that already exists.

Managing it properly is critical. It should be stored remotely, never on a laptop and never in git, because it can contain sensitive values. On AWS, the common setup is an S3 backend with encryption and versioning, plus locking, traditionally through a DynamoDB table, or S3 native locking in newer versions. Terraform Cloud is another option. Locking stops two people or pipelines from applying at the same time and corrupting it. I keep separate state per environment, and often per component, like network and application, so a mistake has a small blast radius. And I use terraform import to bring existing resources under management, and moved blocks or state commands carefully when refactoring.

My golden rule is never edit the state by hand, and only change infrastructure through Terraform. I can explain what happens when state and reality drift.

@p2-14
The Terraform workflow is write, plan, review and apply, ideally all through a pipeline.

I write or change the configuration in HCL, usually with modules for reusable pieces. Then terraform init downloads the provider plugins and modules and configures the backend where state is stored. terraform fmt and validate check formatting and syntax. Then terraform plan compares the code with the state and the real infrastructure, and shows exactly what'll be created, changed or destroyed. That plan is the key review artifact. In a pull request, the pipeline posts the plan, and reviewers check it carefully, especially anything marked "destroy" or "replace", which can mean data loss. People miss that more than you'd think. After approval, terraform apply makes the changes, ideally applying the exact saved plan that was reviewed.

Important practices, run it from the pipeline, not from laptops, so there's one controlled identity with the right permissions and a full log. Use state locking. And detect drift by running a scheduled plan, which alerts if real infrastructure no longer matches the code.

For regulated environments, the saved plan and the approval become part of the change evidence. I can explain how we handle a resource that must not be replaced.

@p2-15
Drift is when the real infrastructure no longer matches what's defined in the code. It usually happens because someone made a manual change in the console, often during an incident, like opening a security group port or resizing a database, and never put it back into code.

Drift's dangerous for a few reasons. Environments stop being identical, so something works in UAT but not in production. The next deployment might silently undo the manual fix, or fail. And in a regulated environment, an untracked change is an audit finding.

To detect it, CloudFormation has built-in drift detection, and with Terraform, I run a scheduled terraform plan in the pipeline, which alerts if it shows any changes when the code hasn't changed. AWS Config rules can also flag non-compliant resources.

To prevent it, restrict console write access in production, so people have read-only access by default and changes go through pipelines. Allow emergency break-glass access, but with logging and a rule that any emergency change goes into code right after. Tag resources managed by IaC so everyone knows not to touch them manually.

The culture part matters most, for me. The fix isn't done until it's in code. I can explain how we handle emergency changes.
