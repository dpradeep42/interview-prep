So Angular scopes component styles, so one component's CSS doesn't leak out and mess up other components. The ViewEncapsulation setting controls how.

Emulated is the default. Angular adds unique attributes to the component's elements and rewrites its CSS selectors to include those attributes, so styles only apply inside that component's template. ShadowDom uses the browser's real Shadow DOM, which gives true isolation, but then global styles, like a design system's base styles, don't reach inside. None makes the component's styles global, which people occasionally use for theme files, but it risks conflicts.

There are special selectors too. Colon host styles the component's own host element, like making it display block, and host with a class lets the component react to a class on itself. Host-context applies styles based on an ancestor, like a dark theme class higher up the tree.

To style inside a child component, especially third-party ones like Angular Material, people use ng-deep, which turns off encapsulation for that rule. It's deprecated, but honestly still everywhere, because there's no full replacement. Better options are the child component's inputs, CSS custom properties, which pass through encapsulation, or the library's theming APIs.

In a big app, I keep component styles small, use a shared design system for consistency, and rely on CSS variables for theming. We keep the Angular sub-apps visually consistent with the React shell through shared design tokens.

Server-side rendering means the Angular app runs on the server, in Node.js, and returns fully rendered HTML for the requested page. The browser can show content immediately, before the JavaScript has even downloaded. That improves first paint and Largest Contentful Paint, helps SEO, and gives good link previews on social media, because crawlers see real content.

It used to be called Angular Universal. Since Angular 17, SSR is built into the CLI, ng new with the ssr option, or ng add the angular ssr package. Prerendering, or static site generation, renders pages at build time for content that doesn't change per request.

Hydration is what happens next in the browser. Instead of throwing away the server HTML and re-rendering everything, which used to cause flicker, Angular reuses the existing DOM and attaches event listeners and state to it. Full hydration has been stable since Angular 16. Event replay captures clicks that happen before hydration finishes and replays them. And incremental hydration, Angular 19 onwards, hydrates defer blocks only when they're triggered, which cuts JavaScript work further.

The tricky bits, code must not touch browser-only objects like window or localStorage during server rendering, so you guard with isPlatformBrowser or afterNextRender. And HTTP data fetched on the server gets transferred to the client, so it isn't fetched twice.

Honestly, for internal, login-only business apps like ours, SSR adds very little, so we don't use it. It really matters for public, content-heavy sites.

Okay, so Angular's environment files get compiled into the bundle at build time. That means a separate build for every environment, which goes against build once, deploy many, where the same tested artifact moves from test to UAT to production. In a validated environment that really matters, because a rebuilt artifact isn't the artifact that was tested.

So I load configuration at runtime instead. The app ships with a config.json file, or the server serves one at a known URL, with environment-specific values like the API base URL, the identity provider URL, the client id and feature flags. The deployment pipeline writes the right file for each environment, or the server generates it.

At startup, the app fetches this file before anything else runs, using an app initialiser. provideAppInitializer in recent versions, or the APP_INITIALIZER token in older ones, which can return a Promise or Observable that Angular waits for. A config service holds the values, and other services read from it, or I provide individual values through InjectionTokens. Another way is fetching the config in main.ts before calling bootstrapApplication and passing it into the providers.

Only non-secret values go in this file though, since the browser can read everything.

For our React shell, we use Vite environment variables, but the same principle applies, [and the older Angular sub-apps read their settings from the hosting MVC page].

Angular officially supports upgrading one major version at a time. So going from 8 to 17 is nine steps, not one jump, and I'd plan it as a proper project.

The first thing is preparation. Make sure there's a decent test suite and an end-to-end smoke test, because every step needs verifying. Check the third-party libraries, because honestly they're usually the real blocker. Each library needs a version compatible with each Angular version, and some are abandoned, so you have to replace them. Also check the Node.js and TypeScript versions each Angular version needs.

Then go step by step with the Angular Update Guide on angular.dev, which lists the changes for each version pair. For each version, run ng update for core and cli, which applies automatic migrations to the code, then update the other Angular packages like Material, fix compile errors, run tests, and commit. Keeping each step in its own commit or branch makes problems easy to isolate.

The big milestones on the way, Ivy becoming the only engine around 12 and 13, which removed View Engine and broke old libraries. Dropping IE11 support. Strict typed forms in 14. Standalone components in 14 and 15. And the esbuild builder plus the new control flow in 17. Those later features are optional migrations, which I'd do after the upgrade itself.

Our older sub-apps are on Angular 8 and 12, and the plan has been to move modules to React rather than upgrade them all.

This is a really common modernisation pattern. The legacy MVC application keeps its layout, menu and authentication, while specific pages host a modern Angular sub-application.

The Angular app is built separately with the Angular CLI, producing JavaScript and CSS bundles. The MVC view for that page includes the bundles with script and link tags, and has the root element, like a custom app-root tag, where Angular bootstraps. Settings the Angular app needs, like the API URL, the current study, the user's culture, or an anti-forgery token, can be passed from the server into the page, like a JSON block or data attributes that the app reads at startup.

Routing needs care. Either the Angular app uses hash-based routing, so it doesn't clash with MVC routes, or MVC routes all sub-paths of that page to the same view and Angular's base href is set to that page's path.

Authentication is shared. If the MVC site uses cookies, the Angular app calls the same site's APIs and the cookie goes along automatically, with anti-forgery protection. Or both use SSO and tokens.

Styles must not clash with the MVC site's global CSS, so encapsulation and prefixed classes help. And deploying means copying the Angular build output into the MVC site, ideally with hashed file names for cache busting.

In my project, our legacy portal hosts Angular 8 and 12 sub-apps exactly this way, for screens like the advanced subject view and the material forecasting dashboard.

NgRx is a Redux-style state management library for Angular, built on RxJS.

The store holds the application state as one immutable object tree. Components never change it directly. Instead they dispatch actions, which are plain objects describing events, like "Shipments Page Opened" or "Shipment Cancelled", created with createAction or grouped with createActionGroup.

Reducers are pure functions. They take the current state and an action and return a new state, built with createReducer and on handlers. No side effects in there, so state changes are predictable and easy to test.

Selectors read and derive data from the store, created with createSelector. They're memoised, so derived values, like pending shipments for the selected site, only get recalculated when their inputs change. Components use store.select, or selectSignal to get a signal.

Effects handle side effects, like API calls. An effect listens for specific actions, calls a service, and dispatches a success or failure action with the result, usually with switchMap or exhaustMap and catchError. Then the reducers update state from those actions.

Redux DevTools shows every action and state change, with time-travel debugging, which honestly helps a lot when debugging.

The downside is boilerplate and indirection. For simple apps or local component state, it's overkill, and services with signals are enough. It pays off in big apps with lots of shared state and complex async flows, with several developers who need consistent patterns.

@p17-282
NgRx SignalStore is a newer, lighter state management approach from the NgRx team, built on Angular signals instead of RxJS and the Redux pattern.

You create a store with signalStore and compose it from features. withState defines the initial state, which becomes signals for each property. withComputed adds derived signals. withMethods adds methods that update state with patchState, or do async work, using rxMethod for RxJS-based flows or plain async functions. And withHooks runs logic on init and destroy. There are reusable features too, like withEntities for collections with ids, and community features for devtools and request status.

The store is an injectable service, so you can provide it at root for global state, or at component level for local, feature-specific state. I like that flexibility.

Compared with the classic NgRx store, there are no separate actions, reducers and effects files, so way less boilerplate. Components just call methods directly. It's signal-based, so it works naturally with OnPush, zoneless change detection and signal inputs. And it's more modular, stores per feature rather than one big global tree. What you lose is some of the strict event-driven traceability that actions give you, though NgRx has added an events plugin for people who want that back.

For new Angular apps, I'd start with SignalStore or simple signal-based services, and only use the classic store where the Redux pattern clearly adds value.

@p17-283
In RxJS, when an Observable errors, the stream terminates. No more values come through. So in a long-lived stream, like a search box or a polling feed, one single error stops it working until the page is reloaded. That's honestly the most common RxJS bug I see.

catchError intercepts the error and returns a replacement Observable. A fallback value, like an empty array, with of. Or EMPTY to complete quietly. Or rethrow a friendlier error with throwError. The key trick for long-lived streams is putting catchError inside the inner Observable, inside switchMap, not at the end of the outer stream. Then only that one request fails, and the outer stream keeps listening for the next search term.

retry resubscribes to the source after an error, a number of times. Since RxJS 7, retry takes a config with count and a delay function, which allows exponential backoff, like retry with count 3 and a delay based on a timer and the retry count. I only retry for transient errors, network failures or 503, not 400 or 404.

finalize runs when the stream completes, errors or gets unsubscribed, which is useful for turning off a loading spinner.

In Angular, HTTP errors can also be handled centrally in an interceptor, for logging, notifications or redirects on 401, while components handle the errors specific to their screens. That split works well for us.

These all combine multiple Observables, but they emit at different times, and that's the whole difference.

forkJoin waits until all the sources complete, then emits once with the last value from each. It's like Promise.all. The right choice for running several HTTP calls in parallel and using all the results together, like loading a site, its inventory and its users before showing a page. If any source errors, the whole thing errors. And if any source never completes, forkJoin never emits, so it's not for long-lived streams.

combineLatest emits whenever any source emits, once each source has emitted at least once, giving the latest value from each. It's for combining ongoing streams, like filters. When the status filter, the date range or the search term changes, recalculate with the latest of all three. A common surprise is nothing emits until every source has emitted once, so startWith helps there.

withLatestFrom is driven by one primary stream. When the primary emits, it combines that value with the latest of the others, but the others emitting doesn't trigger anything. Perfect for "when the user clicks save, take the current form value and the selected site".

zip pairs values by index, first with first, second with second, and so on. I rarely need it, mostly when values correspond one to one.

And with signals, computed covers a lot of combineLatest's use cases more simply.

@p17-285
A typeahead calls an API as the user types, so it has to avoid flooding the server and deal with responses arriving out of order.

I start with a stream of the input's values, from a reactive form control's valueChanges, or a signal converted with toObservable. Then a pipeline of operators.

debounceTime of about 300 milliseconds waits till the user pauses typing, so we're not calling the API on every keystroke.

map to trim the text, and filter out terms that are too short, like under two characters, maybe returning an empty result for those.

distinctUntilChanged skips the call if the term is the same as last time, like when the user types a letter and deletes it.

switchMap calls the search API, and this is the key one. When a new term arrives, it unsubscribes from the previous request, and Angular's HttpClient cancels it. So a slow response for an old term can never overwrite the results for a newer term. That's the race condition people hit with mergeMap or plain promises.

Inside switchMap, catchError returns an empty result on failure, so one failed request doesn't kill the stream. And I can track loading state with a signal or startWith.

The template shows the results with the async pipe, or a signal from toSignal.

On the server side, the search endpoint should be fast, limited and indexed, because even with debouncing it gets hit a lot. So that's the full picture.

@p17-286
A cold Observable starts producing values separately for each subscriber. Angular's HttpClient calls are cold, so each subscription sends a new HTTP request. If a template has two async pipes on the same HTTP Observable, or two components subscribe to the same service method's result, the request goes out twice.

A hot Observable produces values regardless of subscribers, and all subscribers share the same source. Like DOM events, a WebSocket stream, or a Subject. Late subscribers miss earlier values, unless the stream replays them.

share and shareReplay turn a cold Observable into a shared hot one. share multicasts to all current subscribers through one subscription to the source. shareReplay also replays the last N values to new subscribers. So shareReplay with bufferSize 1 is the common way to cache an HTTP result. The first subscriber triggers the request, and everyone after gets the cached value with no new call.

There are pitfalls though. With the old shareReplay of 1 signature, the source subscription stays alive even when all subscribers leave, which can leak for long-lived sources. Using the config with refCount true unsubscribes when nobody's left. A cached error or stale value stays cached, so you need a way to refresh, like a Subject that triggers reloading. And caching in a root service means the data sticks around for the whole session.

For simple shared state, honestly, a signal or BehaviorSubject in a service is often clearer.

Rendering thousands of rows with a simple loop creates thousands of DOM elements and component instances. Initial render gets slow, scrolling gets janky, and change detection gets expensive.

The main thing I'd reach for is virtual scrolling. The Angular CDK's virtual scroll viewport, with the cdkVirtualFor directive, only renders the rows visible in the viewport plus a small buffer, and recycles them as the user scrolls. The list can have 50,000 items, but only about 30 are in the DOM. It works best with a fixed row height, set with itemSize. Variable heights are harder. Data grids like AG Grid have virtualisation built in, even for columns.

Then server-side paging or infinite scrolling. Often the user doesn't need all items at once, so loading pages on demand, with filters and search on the server, beats sending everything to the browser.

After that, reduce the work per row. OnPush on row components, a proper track expression in the for block so rows get reused when data refreshes, pure pipes instead of method calls in templates, and no heavy components inside each row. Like rendering a dropdown only when a row is being edited.

You can also use defer for parts of each row that aren't needed immediately.

And I'd measure with Angular DevTools' profiler and the browser's performance panel, to see whether time goes to change detection or DOM rendering.

[Our material forecasting dashboard was the kind of screen where server-side paging and OnPush made the difference.]
