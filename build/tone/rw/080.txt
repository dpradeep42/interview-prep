@p17-948 | A container runs fine locally but crashes in Kubernetes. What is different?
Kubernetes runs containers with settings that differ from a plain docker run, so I compare the environments one by one, starting with kubectl describe pod and kubectl logs with the previous flag.

Common differences. Security context, that's usually the first suspect for me. Production pods often run as non-root with a read-only root file system and dropped capabilities. An app that writes temp files, logs or caches to its own folder, or binds to port 80, just fails. The fix is to write to mounted emptyDir volumes, like slash tmp, and listen on a high port, like 8080.

Configuration. Environment variables, ConfigMaps and Secrets differ from the local env file. A missing or misnamed variable, or a secret mounted as a file instead of an environment variable, makes the app fail at startup.

Resource limits. A low memory limit causes OOMKilled, and low CPU limits make startup so slow that probes fail.

Probes. Liveness probes kill the app before it finishes starting, and a startup probe or a longer initial delay fixes it.

Networking. Services are reached by Kubernetes DNS names, not localhost. Network policies might block traffic to databases or other services, and egress to external services might need proxies or firewall rules.

Architecture. An ARM image pulled on x86 nodes, or the other way round, fails with exec format error.

User and file permissions. Files copied into the image owned by root aren't readable by the non-root user.

Time zone and locale. The container uses UTC, which can change date-dependent behaviour.

Running the container locally with the same constraints, read-only, non-root, memory limits and the same environment, usually reproduces it pretty quickly.

@p17-949 | Someone changed production by hand in the cloud console, and Terraform now shows drift. What do you do?
Drift means the real infrastructure doesn't match the code anymore. The danger is the next terraform apply quietly undoes the manual change, which might've been an emergency fix. Or the manual change might itself be a mistake, or even a security incident.

So, don't apply blindly. Run terraform plan, read exactly what differs, and identify the change. CloudTrail or the Azure activity log shows who changed what and when.

Talk to whoever made the change. Was it an emergency fix during an incident, an experiment, or a mistake? If nobody can explain it, I'd treat it as a possible security issue and pull in the security team.

Then decide the source of truth. If the change should stay, update the Terraform code to match it, through a normal pull request with review, and confirm plan shows no changes. If the change was wrong, apply the code to revert it, at a safe time and knowing the impact. If it touched resources Terraform doesn't manage, think about importing them with import blocks.

Preventing repeats. Restrict console write access in production, read-only roles for day-to-day, with break-glass access for emergencies that's logged and alerts the team.

Make the emergency path codified, a fast-track pipeline for urgent infrastructure changes, so people don't need the console at all.

Detect drift automatically, a scheduled plan in CI, or tools like AWS Config and Azure Policy, alerting when drift shows up.

And afterwards I add a "back-port manual changes into code" step to the incident checklist, so emergency fixes don't stay undocumented.

@p17-950 | A secret value appeared in pipeline logs. What do you do?
Look, a secret in logs is a leaked secret. Logs are often readable by lots of people, kept for a long time, and sometimes copied to other systems. So I respond the same way as for a committed secret.

Immediately, rotate it. Revoke and replace the credential at its source, the database password, API key or token, and update it in the secret store. Rotation's the only real fix, because I can't be sure who saw the log.

Limit exposure. Delete or restrict access to the affected pipeline run logs if the platform allows, and check whether logs were forwarded somewhere else, like a log platform, and clean them there too.

Check for misuse. Review access logs for that credential during the exposure window, looking for anything unusual.

Then find out why masking failed. Pipeline platforms mask secret variables in logs, but masking fails when the secret's transformed, base64 or URL encoded, split across lines, or embedded in JSON. Or when a tool prints it in debug or verbose mode, or a script echoes environment variables or runs with set minus x. Or when the value was never marked secret at all, like a plain variable or something read from a file at runtime.

Preventing it again. Mark all sensitive values as secrets, avoid printing commands with credentials and use files or environment variables tools read directly, keep verbose debug logging off by default, prefer short-lived credentials through OIDC federation and managed identities so leaked values expire quickly, and add secret scanning for pipeline logs and artifacts.

And then a blameless review to share what happened, because honestly this is a common, easy mistake.

@p17-951 | A dependency you use is reported as compromised in a supply chain attack. What do you do?
This one's different from a normal vulnerability. A compromised package might have run malicious code on developer machines, build agents or production, for example stealing tokens or environment variables at install time.

So the starting point is, are we affected? Which versions are compromised, and do any of our lock files, builds or images contain them? I search lock files across repos, our package feed's cache, and the SBOMs of built images. Lock files and pinned versions make this answerable quickly.

If we did pull a compromised version, assume any credentials on machines that installed it are exposed. Rotate the tokens and secrets available in those environments, CI variables, cloud credentials, npm or NuGet publishing tokens, developer tokens.

Remove the version. Pin to a known-good one, rebuild and redeploy affected services, and purge it from our internal feed cache so it can't be pulled again.

Investigate. Check build and runtime logs and network activity for the malicious behaviour described in the advisory, like outbound connections to unknown hosts, and bring in the security team for incident handling.

If we didn't pull it, block the bad versions in the feed and keep monitoring.

For the future, lock files with exact versions and integrity hashes, npm ci instead of npm install in builds, install scripts disabled where possible, an internal proxy feed with a delay or approval before new versions get used, minimal permissions and short-lived credentials on build agents, and SBOMs for every build. That way "are we affected?" gets answered in minutes, which I think is the real goal.

@p17-952 | A front-end bundle size suddenly doubled after a pull request. How do you find the cause?
Bundle size jumps usually come from a single change, so I just compare before and after.

Find what changed. Build the previous commit and the new one with a bundle analyser, like the rollup visualizer plugin for Vite or the webpack bundle analyser, and compare the treemaps. The new big block is usually obvious.

Typical causes. A new heavy dependency, a charting, date, PDF or editor library, imported into the main bundle.

Importing a whole library instead of a part. Pulling in an entire icon set or utility library rather than named or per-file imports, or a CommonJS package that can't be tree-shaken. That one catches people a lot with icon libraries.

Duplicated dependencies. Two versions of the same library, like React, MUI or lodash, because an internal package declared it as a dependency instead of a peer dependency.

Lost code splitting. A lazy-loaded route or component that's now imported statically somewhere, which pulls it into the main chunk.

Assets inlined, large images, fonts or JSON files imported into JavaScript.

Development code in production, a debug tool or mock data included by accident.

The fix follows the cause. Lazy-load heavy features, switch to lighter libraries, fix imports, align versions with peer dependencies and deduplication, and move large data to separate fetched files.

And for prevention, a size budget check in CI with something like size-limit or bundle budgets, which comments on pull requests with the size difference and fails past a threshold. Then the reviewer sees the impact before merging, instead of users finding out through a slower app.

@p17-953 | Duplicate records appear in the database under concurrent requests. How do you fix it?
This is usually a check-then-insert race, you know. The code checks whether a record exists, finds nothing, and inserts. Two requests arriving at the same moment both pass the check before either inserts, so both insert. It happens with double-clicks, retries from clients or gateways, and parallel message consumers.

To confirm it, look at the timestamps of the duplicate rows, often milliseconds apart, and at logs showing two requests or two message deliveries.

Fixes, usually combined. A unique constraint in the database, that's the real guarantee. Add a unique index on the business key, like kit number per study, or on an idempotency key. The second insert fails with a duplicate key error, which the code catches and handles, returning the existing record or a 409. Before adding it to an existing table, clean up existing duplicates carefully, with business input on which record to keep.

Upsert or atomic operations. An insert with a not-exists condition in a single statement, or a merge with proper locking hints, rather than separate select and insert round trips.

Idempotency keys for APIs. Clients send a unique key per operation, and the server stores it with the result and returns the same result for repeats.

Idempotent message handling. Record processed message ids in the same transaction as the business change.

Locking, for complex cases, an application lock, like sp_getapplock in SQL Server or a distributed lock, around the critical section, though constraints are simpler and more reliable.

UI help. Disable the submit button while a request's in progress, which reduces duplicates but doesn't eliminate them.

Then I add a concurrency test that fires parallel requests to prove the fix.

@p17-954 | One big Redis key is causing latency spikes. How do you find and fix it?
Redis is single-threaded for command execution, so one slow command blocks everything else. A really large key, like a hash with millions of fields, a list with hundreds of thousands of items, or a multi-megabyte string, makes commands on it slow, and every client waits.

Finding it. redis-cli with the bigkeys or memkeys option scans the keyspace and reports the largest keys per type, and MEMORY USAGE on a key shows its size.

SLOWLOG GET shows recent slow commands and their arguments, which often points straight at things like HGETALL, SMEMBERS or LRANGE on huge keys, or a DEL of a big key.

LATENCY DOCTOR and monitoring tools show the spikes and their timing.

Cloud services, ElastiCache or Azure Cache for Redis, expose metrics for CPU, latency and network that highlight it.

Hot keys are a related issue. A normal-sized key that's read extremely often, concentrating load on one shard in a cluster. The hotkeys option, with an LFU eviction policy, helps find them.

Fixing. Split big keys. Shard a large hash or set into multiple keys by a bucket, like site id modulo 100, or store items as separate keys.

Avoid full reads. Use HSCAN, SSCAN or ranged reads instead of fetching everything at once, and fetch only the fields you need.

Delete safely. UNLINK instead of DEL, which frees memory in the background. I've seen a single DEL on a huge key freeze things for a noticeable moment.

Reduce value size, compress, or store only what's needed.

For hot keys, an in-process cache in front of Redis, or replicating the key across several keys and picking one at random.

Then monitoring on key sizes and slow log entries, so it doesn't creep back.

@p17-955 | A partner says they never received your webhook callbacks. How do you investigate?
My approach is evidence from our side first, then work with the partner on theirs.

Our side. Did we send it? Check that the business event happened and a webhook was created for it, in the outbox or delivery table, with the partner's endpoint and payload.

What happened on delivery? Our delivery log should have each attempt, time, URL, response status, response time and error. If there's no such log, that's the first improvement to make.

Common findings. The partner's endpoint returned errors, 401, 404 or 500, maybe after they changed URLs, credentials or certificates. Timeouts because their endpoint's slow. TLS errors, like they renewed a certificate with an incomplete chain or dropped an older TLS version. DNS changes on their side. Our outbound IP changed and their firewall allow-list blocks the new one. Or our retry policy gave up and the delivery went to a dead-letter state nobody was watching.

Configuration. The subscription might point to an old endpoint, or got disabled after repeated failures.

Their side. Share exact timestamps, request ids and signature details, so they can search their gateway and application logs. Sometimes requests actually arrived but their signature validation failed, or their system dropped them silently.

Recovery. Once it's fixed, replay the missed events from our delivery store, in order, idempotently, with their agreement.

Improvements, a delivery dashboard per partner, alerts on consecutive failures, a self-service endpoint for partners to view and replay deliveries, documented static outbound IPs, and a reconciliation API they can call to fetch events they might've missed.

@p17-956 | A canary release shows a higher error rate only for some users. How do you investigate?
When a canary shows more errors, I'd say the safest move is to pause or roll back the canary straight away, since only a small slice of traffic is affected and the stable version's still there. Then I can investigate without pressure.

Narrow down who's affected. Break errors down by dimensions in logs and metrics, endpoint, client version, browser or app version, tenant, study, region, user role, request characteristics. A canary often shows problems that only certain data or clients trigger.

Typical causes. Data-dependent bugs, where the new code fails on edge cases in some records, like null fields, old data formats or special characters that test data didn't have.

Client compatibility. Older mobile app or front-end versions send requests the new API doesn't accept anymore, or expect fields that changed.

Session or affinity issues. Users bouncing between canary and stable mid-session, where the two versions disagree on cookies, cache formats or token handling.

Configuration differences. The canary has different settings, feature flags or secrets.

Dependency limits. The new version calls a downstream service differently, hitting rate limits or timeouts for heavy users.

Schema mismatch. The canary expects a database change, or writes data the stable version can't read.

Then I reproduce it with the specific failing inputs, using trace ids from the errors to find the exact requests, fix it, add a test with that data, and release a new canary.

Process improvements, automated canary analysis comparing error rates and latency between canary and stable per segment, sticky routing so users stay on one version, and canaries that start with internal users.

@p17-957 | A load test shows throughput stops increasing while CPU is only at 40 percent. What is the bottleneck?
If throughput flattens but CPU isn't busy, the system's waiting on something, so I look for whatever's queuing.

Connection pools. Database connection pools at their max, with requests waiting for a connection. Metrics like pool wait time, or active connections sitting at the limit, show it. Same for HTTP client connection limits per server to a downstream service.

The database or a downstream service. The bottleneck might simply be somewhere else. I check database CPU, waits, blocking and slow queries, and downstream latency in traces.

Locks and contention. A lock in the code, a single-threaded section, or database row and table locks serialising work. Traces with long waits but little actual work point here.

Thread pool starvation in .NET, honestly I'd check this early. Blocking calls, like dot Result or synchronous I/O, keep threads busy waiting. The thread pool grows slowly, so requests queue while CPU stays low, and dotnet-counters shows the thread pool queue length growing.

Rate limits and throttling, API gateways, cloud services, or our own rate limiter capping throughput.

Network and load balancer limits, bandwidth, connection limits, or too few load generator machines. I always check the load test tool itself isn't the bottleneck.

Single partition or queue, messaging with one partition or one consumer, or a hot key in a cache or database.

The method is increase load step by step, watching latency and every resource. The first resource to saturate, or the first queue to grow, is the bottleneck. Fix it, then repeat, because the next one shows up once the first is gone.

Results go into capacity planning, known limits per instance and which component to scale.

@p17-958 | A .NET service's memory grows steadily until it restarts. How do you find the leak?
Let me start with confirming it's a real leak and where the memory actually is. Using metrics or dotnet-counters, I look at GC heap size after collections, generation 2 size, and the large object heap. If the managed heap keeps growing after full collections, it's a managed leak. If process memory grows but the GC heap doesn't, it's native memory, like unmanaged buffers, native libraries or too many threads.

For a managed leak, I take memory snapshots at two points, say after 30 minutes and after 3 hours, with dotnet-gcdump, which is lightweight, or a full dump with dotnet-dump. Comparing them in Visual Studio, PerfView or dotnet-dump analyze shows which types grew in count and size. Then the GC root path for a sample object shows what's keeping it alive.

Common culprits I find this way. Event handlers on long-lived objects, static events or singleton services, that short-lived objects subscribe to and never unsubscribe from.

Unbounded caches, a static dictionary or MemoryCache without size limits or expiry, often keyed by something unbounded like a user or request id.

Captive dependencies, singletons holding scoped services, like a DbContext that keeps tracking entities forever.

Timers and background tasks capturing objects.

HttpClient or other disposable objects created again and again without disposal.

Large strings or byte arrays held on to by logging or buffering.

The fix depends on the cause, and then I verify with a soak test, running the service under steady load for hours and watching memory level off. Meanwhile, a memory alert and controlled restarts limit the impact.

@p17-959 | A query is fast in SSMS but slow when called from the application. Why?
Ah, this is a classic SQL Server puzzle, and the usual answer is that the two are getting different execution plans.

Why the plans differ. SET options. SSMS sets ARITHABORT on by default, while ADO.NET connections use ARITHABORT off. Plans are cached per combination of SET options, so the application and SSMS use separate plans, even for the same query.

Parameter sniffing. The application's cached plan was compiled for unusual parameter values, like a site with very few rows, and that plan performs badly for typical values. In SSMS you might test with literal values or a fresh compile and get a good plan.

Parameter data types. The application sends nvarchar parameters for varchar columns, causing implicit conversions that prevent index seeks, while the SSMS test uses literals of the right type. That one catches people a lot with ORMs.

Local variables versus parameters. Testing in SSMS with local variables gives estimates based on averages, which differs from how parameters are optimised.

How I diagnose it. Find the application's actual plan, from Query Store or the plan cache, by query hash, and compare it with the SSMS plan. To reproduce in SSMS, I match the SET options, turn ARITHABORT off, and use the same parameterised form, with sp_executesql and the same parameter types.

Fixes, correct parameter types in the application, like specifying varchar with a length in Dapper or EF Core mappings. Better indexes so one plan works for all values. OPTION RECOMPILE for queries with very different parameter distributions. Or forcing a known good plan in Query Store as a short-term fix.

Just never fix it by clearing the whole plan cache in production. That only hides the problem for a while.
