So an image is an immutable, read-only template that has everything needed to run an application, the base operating system layer, the runtime, dependencies, and the application itself. A container is a running instance of an image, with its own process, a thin writable layer, and its own isolated view of the network and file system. One image can run as many containers as you want.

A Dockerfile is the recipe that builds an image. It's a list of steps. Start FROM a base image, set the working directory, COPY files in, RUN commands like restoring packages and building, set environment variables, EXPOSE a port, and define the ENTRYPOINT that starts the app.

Each instruction creates a layer, and layers are cached. If a layer hasn't changed, Docker reuses it. So the order really matters. Put things that change rarely at the top, like the base image and dependency restore, and things that change often at the bottom, like copying source code. That makes rebuilds much faster.

Containers also share the host's kernel, which makes them much lighter and quicker to start than virtual machines. In our platform, every .NET service is built into an image in the pipeline, and the same image goes from validation to production. I can show a production Dockerfile.

A pod is the smallest deployable unit in Kubernetes. It's one or more containers that run together on the same node, share the same network address and can share storage volumes. Usually it's one application container, sometimes with a sidecar, like a log shipper or a proxy. Pods are disposable, you replace them, you don't repair them.

Around pods, there are a handful of main objects. A Deployment declares how many replicas of a pod you want and manages rolling updates and rollbacks, through ReplicaSets. A Service gives a stable virtual IP and DNS name that load-balances across the pods, because pod IPs keep changing. An Ingress, or the newer Gateway API, routes external HTTP traffic to services by host and path. ConfigMaps and Secrets hold configuration and sensitive values. A Namespace separates teams or environments within a cluster. And for special cases, a StatefulSet for stateful apps that need stable identities and storage, a DaemonSet to run one pod per node, and Jobs and CronJobs for batch and scheduled work. The Horizontal Pod Autoscaler scales replicas.

The core idea is declarative. You describe the desired state, and Kubernetes keeps working to make reality match it.

A Kubernetes Deployment YAML describes the desired state of an application, what to run, how many copies, and how to update it.

At the top, you've got apiVersion apps slash v1, kind Deployment, and metadata with a name and labels. In the spec, replicas sets how many pods, say three. The selector says which pods this Deployment manages, by matching labels. Then the template describes the pod itself, its labels, which have to match the selector, and the containers. For each container, the image with a specific version tag, never latest, the container port, environment variables, often from ConfigMaps and Secrets, and resources, with requests, which the scheduler uses to place the pod, and limits, which cap usage. @p2-20
Kubernetes has three probes to understand the health of a container, and each one triggers a different action.

The readiness probe asks, is this pod ready to take traffic right now? If it fails, Kubernetes removes the pod from the Service's endpoints, so no requests go to it, but it doesn't restart it. That's useful during startup, or when a dependency is temporarily down. The liveness probe asks, is this container stuck or broken beyond recovery? If it fails repeatedly, Kubernetes kills and restarts the container. That's for deadlocks or hung processes. The startup probe gives slow-starting applications time to start. While it's running, liveness and readiness checks are paused, so a slow startup isn't mistaken for a hang.

The common mistake, and I've seen it, is making the liveness probe check dependencies, like the database. If the database has a brief problem, every pod fails liveness, and Kubernetes restarts all of them at once, which makes the outage worse. So liveness should be cheap, checking only the process itself, while readiness can check critical dependencies.

In ASP.NET Core, I expose slash health slash live and slash health slash ready with health checks tagged accordingly. Our ECS services use the same split with ALB health checks. I can show the configuration.

Both hold configuration for containers in Kubernetes, separated by how sensitive it is.

A ConfigMap holds non-sensitive configuration, like URLs, feature settings, timeouts or a whole appsettings file. A Secret holds sensitive values, like passwords, API keys and certificates. Now, one detail people miss, Secrets are only base64-encoded by default, not encrypted, so anyone with read access can decode them. In production, you enable encryption at rest in etcd, restrict access with RBAC, or better, use an external store like AWS Secrets Manager with the External Secrets Operator or the Secrets Store CSI driver, so secrets get synced or mounted from the vault.

Both can be injected into containers as environment variables or as mounted files. Mounted files can be updated without restarting the pod, while environment variables only change on restart.

The principle I follow is build once, configure per environment. The same image runs everywhere, and only ConfigMaps and Secrets differ between environments, managed through infrastructure as code. In ASP.NET Core, environment variables and mounted files plug straight into the configuration system, and the Options pattern with ValidateOnStart catches missing values. Autoscaling in both platforms adds capacity when load goes up and removes it when load drops, but the mechanisms are a bit different.

In Kubernetes, it works at two levels. The Horizontal Pod Autoscaler scales the number of pod replicas based on metrics, like average CPU or memory, or custom metrics such as requests per second or queue length, using tools like KEDA. Then, if there's no room on existing nodes for the new pods, the Cluster Autoscaler or Karpenter adds nodes to the cluster, and removes underused ones. For HPA to work well, pods need accurate resource requests, because CPU utilisation is calculated against the request.

In ECS, Service Auto Scaling adjusts the desired task count. The most common policy is target tracking, like keeping average CPU at 60 percent, or a target number of requests per task from the ALB. Step scaling reacts to CloudWatch alarms, and scheduled scaling handles predictable patterns. With Fargate, there are no nodes to scale, which basically removes the second level.

Either way, scale out quickly, scale in slowly, and make sure apps start fast and shut down gracefully. Our ECS services use target tracking on CPU and request count, with a minimum of two tasks. I can explain scaling consumers on queue depth.

These three get mentioned together a lot, but they solve different problems.

Docker is the tool for building and running containers on a single machine. You write a Dockerfile, build an image, and run containers from it. It's perfect for development and for packaging, but by itself it doesn't manage containers across many machines, or restart them when a machine fails. Kubernetes is a container orchestrator. These three describe how far automation goes on the path from a code change to production.

Continuous integration means every change merged into the main branch is automatically built and tested, many times a day. Problems show up within minutes, while the change is still fresh in the developer's mind, instead of in a painful integration phase later. Continuous delivery goes further. Every change that passes the pipeline is in a releasable state, and deploying it to production is a simple, automated action, but a human decides when, usually with an approval. Continuous deployment removes that last manual step. Every change that passes all automated checks goes to production automatically, with no human approval.

Continuous deployment needs really strong automated testing, monitoring, and feature flags, because there's no human gate.

In a regulated GxP environment like ours, we do continuous integration and continuous delivery, but not continuous deployment. But each release to validated environments needs formal approvals and test evidence.
