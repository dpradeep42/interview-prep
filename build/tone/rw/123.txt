@p6-16
Configuration and secrets should be passed into a container at runtime, never baked into the image. That way, the same image runs in every environment, and secrets aren't exposed to anyone who can pull the image.

For normal configuration, environment variables are the standard way. In Docker, you pass them with the e flag or an env file, in Docker Compose, in the environment section, and on Amazon ECS, in the task definition. In .NET, environment variables override appsettings.json automatically, and nested settings use a double underscore, like ConnectionStrings double underscore Default.

For secrets, honestly, plain environment variables in a task definition or Compose file are visible to anyone who can read that definition. So secrets should come from a secrets manager. On ECS, the task definition references a secret in AWS Secrets Manager or SSM Parameter Store, and ECS injects the value when the task starts, using the task's IAM role. Kubernetes has Secrets, ideally synced from a vault, and Docker Swarm has secrets as files. Another option is for the application to read secrets directly at startup through a configuration provider.

Also, secrets must never be logged, and they shouldn't be passed as build arguments, because those can stay in the image history.

In our AWS services, connection strings and API keys come from AWS Secrets Manager into the ECS tasks at startup.

@p6-17
Kubernetes is an open-source platform for running containers across a cluster of machines. People usually call it a container orchestrator.

The core idea is desired state. I describe what I want in YAML, like "run three copies of this image, with this much memory, reachable on this port", and Kubernetes keeps working to make reality match that description. If a container crashes, it restarts it. If a whole node fails, it reschedules the pods onto healthy nodes. If I change the image version, it does a rolling update, replacing pods gradually with no downtime, and it can roll back.

It also handles the other stuff you need to run services at scale. Scheduling containers onto nodes based on the resources they need, service discovery and load balancing, so services find each other by name, scaling, manually or automatically based on CPU or custom metrics, configuration and secrets through ConfigMaps and Secrets, and health checks with readiness and liveness probes.

The main building blocks are pods, the smallest unit, wrapping one or more containers, Deployments, which manage replicas and updates, Services, which give pods a stable address, and Ingress, for HTTP routing from outside.

The IQVIA production services I work on in AWS run on Amazon ECS, which follows the same ideas, and we use Kubernetes in our [dev] cluster for internal tooling services. Understanding Kubernetes helped me there, like when I fixed a crash loop caused by a liveness probe that checked too early.

@p6-18
Okay, so these are three types of Kubernetes Service, and the difference is where the service can be reached from.

A Service gives a set of pods one stable address, because pods come and go and their IP addresses change. The Service finds its pods by labels and load-balances traffic across them.

ClusterIP is the default type. It gives the service an internal IP address that's only reachable from inside the cluster. It's used for internal communication, like an API calling another service, or connecting to a database inside the cluster. Most services are ClusterIP.

NodePort exposes the service on a fixed port, from a range like 30000 to 32767, on every node in the cluster. So anyone who can reach a node's IP can reach the service on that port. It's simple, but you have to manage node addresses and the odd port numbers yourself, so it's mainly used for testing, or behind your own load balancer.

LoadBalancer asks the cloud provider to create an external load balancer, like an AWS load balancer, which sends traffic to the service. It's the standard way to expose one service publicly, but each one creates a separate load balancer, which costs money.

Each type builds on the previous one. And for HTTP services, it's usually better to use an Ingress, or the Gateway API, so one load balancer that routes many hostnames and paths to internal ClusterIP services.

@p6-19
A ReplicaSet is a Kubernetes object whose job is to keep a specified number of identical pods running at all times. You say "I want three replicas of this pod", and the ReplicaSet watches the cluster. If a pod crashes or a node fails, and there are only two, it creates a new one. If somehow there are four, it removes one. It finds the pods it owns using a label selector.

In practice, you almost never create ReplicaSets directly. You create a Deployment, and the Deployment creates and manages ReplicaSets for you. The reason is updates. A ReplicaSet can keep pods running, but it doesn't know how to update them from one version to another. A Deployment does. When you change the image version in a Deployment, it creates a new ReplicaSet for the new version, and gradually scales the new one up and the old one down. That's a rolling update. The old ReplicaSet is kept, scaled to zero, which is what makes a quick rollback possible. The Deployment just scales the old ReplicaSet back up.

So basically, a Deployment manages ReplicaSets, and a ReplicaSet manages pods.

When I'm troubleshooting a deployment, kubectl get replicasets is useful, because it shows the old and new versions and how many pods each one has, which tells me whether a rollout is stuck.

@p6-20
So a rolling deployment updates an application gradually, replacing old instances with new ones a few at a time, so the service stays available throughout, with no downtime.

In Kubernetes, when you change a Deployment's image, it creates new pods with the new version, waits for each one to pass its readiness probe, and only then removes old pods. Two settings control the pace. maxSurge says how many extra pods can be created above the desired count, and maxUnavailable says how many can be missing during the update. Readiness probes really matter here, without them, traffic could go to pods that aren't ready yet. Amazon ECS works the same way, using minimum and maximum healthy percentages, and the load balancer's health checks.

A rollback means going back to the previous version when the new one has problems. In Kubernetes, kubectl rollout undo switches back to the previous ReplicaSet, which is kept for exactly this reason. On ECS, you redeploy the previous task definition, and ECS also has a deployment circuit breaker that can roll back automatically if new tasks keep failing.

Two things people miss here. During a rolling update, old and new versions run at the same time, so they have to be compatible, including with the database schema. That's why we make database changes backward compatible. And rollback doesn't undo data changes, so those need their own plan.

@p6-21
When a pod's container crashes, Kubernetes handles it automatically, based on the pod's restart policy, which is Always for Deployments.

The kubelet on that node sees that the container's process has exited, and restarts the container inside the same pod. If it keeps crashing, Kubernetes waits longer between each restart, 10 seconds, 20, 40, up to five minutes. That's the CrashLoopBackOff status you see in kubectl get pods. While the container isn't ready, its readiness check fails, so the Service stops sending it traffic, and the other replicas keep serving users. If a whole pod is lost, say because its node fails, the ReplicaSet notices there are fewer pods than desired, and creates a new pod on another healthy node.

Anything stored in the container's own filesystem is lost on restart, which is why apps should be stateless or use persistent volumes.

To find the cause, I use kubectl describe pod to see the events and the last state, including the exit code and reason, like OOMKilled for out of memory, and kubectl logs with the previous flag, to see the logs from the crashed container.

A real example from our [dev] cluster, honestly a fun one. A service kept crash-looping with no errors in its logs. The events showed it was being killed by its liveness probe, because it needed [about 40 seconds] to warm up. A startup probe fixed it.

@p6-22
Service discovery is how one service finds another, when pods are created and destroyed all the time, and their IP addresses keep changing.

Kubernetes solves this with Services and DNS. A Service selects a group of pods by their labels, and gets a stable virtual IP address and a stable DNS name. Kubernetes keeps track of the IPs of the healthy pods behind it, the endpoints, and updates them automatically as pods come and go. Only pods that pass their readiness probe are included.

The cluster runs a DNS server, CoreDNS. Every Service gets a DNS name like orders-api dot shop dot svc dot cluster dot local. Within the same namespace, a pod can just call http colon slash slash orders-api, and from another namespace, orders-api dot shop. When a request is sent to the Service's IP, kube-proxy on each node routes it to one of the healthy pods, which also gives basic load balancing.

There's also a headless Service, with no virtual IP, where DNS returns the individual pod addresses. That's used for things like databases, where clients need to talk to specific pods.

The nice part is that application code doesn't need any discovery logic. In a .NET app, the other service's base URL is just its service name in configuration. Amazon ECS offers kind of the same idea with Service Connect or Cloud Map.

@p6-23
I'd secure Kubernetes in layers. Who can access the cluster, what workloads can do, how they talk to each other, and what goes into them.

Access control comes first for me. Use RBAC with least privilege, so people and service accounts only get the permissions they need, preferably limited to a namespace. Users sign in through the company's identity provider, and the API server isn't exposed publicly. Then workload security. Pods run as non-root, with a read-only root filesystem, no privilege escalation, and dropped Linux capabilities. Pod Security Admission can enforce the restricted standard for a namespace. Pods should only mount a service account token if they need one. Then network policies. By default, every pod can talk to every other pod, so I'd add network policies that only allow the traffic each service needs. Secrets too. Kubernetes Secrets are only base64 encoded, so enable encryption at rest, restrict who can read them, and preferably sync them from an external vault, like AWS Secrets Manager. Images, use trusted, minimal base images, scan them in the pipeline with a tool like [Trivy], and only allow images from our own registry. And keep Kubernetes and nodes updated, and turn on audit logging and monitoring.

Resource limits on every container also matter, so one workload can't starve the others.

@p6-24
To deploy a .NET application to Kubernetes, I'd go through four steps. Containerise it, publish the image, describe how it runs, and deploy it through a pipeline.

Containerising means a multi-stage Dockerfile. The SDK image builds and publishes the app, and the final image uses the smaller ASP.NET runtime image, runs as a non-root user, and listens on port 8080. Then the pipeline builds the image, runs tests, scans it, tags it with the build version, and pushes it to a registry, like Amazon ECR.

Then the Kubernetes manifests, often as a Helm chart. A Deployment sets the image tag, the number of replicas, CPU and memory requests and limits, and environment variables, with normal settings from a ConfigMap and secrets from Kubernetes Secrets, ideally synced from a secrets manager. It also sets readiness and liveness probes, pointed at the app's health check endpoints, which I add in ASP.NET Core with AddHealthChecks and MapHealthChecks. For slow-starting apps, a startup probe too. A Service gives it a stable internal address, and an Ingress exposes it over HTTP. A horizontal pod autoscaler can scale it on CPU.

And the pipeline deploys with helm upgrade, or a GitOps tool like Argo CD, as a rolling update.

One thing people forget, the app itself has to handle SIGTERM, so it finishes in-flight requests before shutting down. ASP.NET Core does this by default, within the shutdown timeout.

@p6-25
In CI, unit tests run automatically on every pull request and every merge, and if any test fails, the build fails, so broken code can't be merged.

In our Azure DevOps pipelines for .NET, the steps are restore the NuGet packages, build the solution in Release mode, then run dotnet test, which finds and runs all the test projects. I use a logger that produces results in the TRX format, which the pipeline publishes, so the test results show up in the build summary, with each failing test, its error and its history. I also collect code coverage, using the XPlat Code Coverage collector with Coverlet, and publish a coverage report, which also goes to SonarQube, where the quality gate checks the coverage of new code.

Branch policies in Azure DevOps require this build to pass before a pull request can be completed. So nothing reaches the main branch without passing tests.

A couple of practical things. Unit tests have to be fast and independent of databases or networks, so they run quickly on every change. Slower integration tests can run in a separate stage. Flaky tests are fixed or quarantined quickly, because if people stop trusting the tests, they start ignoring failures.

I once had a quality gate fail at [68 percent] coverage against an [80 percent] requirement, and we fixed it in [half a day] by adding meaningful tests.

@p6-26
SonarQube is basically a static code analysis platform. It looks at source code without running it, and reports problems in a few categories, bugs, which are code likely to behave wrongly, vulnerabilities and security hotspots, like possible SQL injection or hard-coded passwords, code smells, which are maintainability issues, like overly complex methods or duplication, plus code coverage from our test results, and duplicated code.

The big feature is the quality gate. It's a set of conditions that new code has to meet, like coverage on new code at least [80 percent], no new bugs or vulnerabilities, all security hotspots reviewed, and duplication below a threshold. If the code fails the gate, the pipeline fails, so problems are caught before merging. Focusing on new code is important, because it lets a team improve gradually without having to fix all the old issues first.

In Azure DevOps, we run the SonarQube prepare step before the build, the analysis after build and tests, and then check the quality gate, with the result shown on the pull request. Developers can also use SonarLint in the IDE to see issues while coding.

One time our gate failed with [68 percent] coverage against [80 percent]. Instead of lowering the bar, we added meaningful tests for the missing paths and passed it in [half a day].

Before merging, every change goes through a pull request with at least one reviewer, and branch policies stop anyone pushing directly to main.
