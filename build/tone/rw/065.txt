@p17-768 | How do you customize the automatic 400 response for invalid models?
So with the ApiController attribute, ASP.NET Core automatically sends back a 400 Bad Request when model binding or validation fails, before your action even runs. The default body is a ValidationProblemDetails object, with a title, a status, a trace id and an errors dictionary mapping each field name to its messages.

Most of the time that default's fine. But teams sometimes need to customise it, to add an application error code, include a correlation id, match an error format the front ends already handle, or log validation failures.

How you customise it. The main hook is InvalidModelStateResponseFactory. You configure ApiBehaviorOptions and set a factory that gets the ActionContext with the ModelState, and returns your own result, like a BadRequestObjectResult wrapping a custom ProblemDetails.

AddProblemDetails with CustomizeProblemDetails lets you add extensions, like the trace id or an error code, to every ProblemDetails response, validation ones included, in one place.

Or you switch the automatic behaviour off with SuppressModelStateInvalidFilter and validate manually or through a filter. That's useful if you run FluentValidation in a MediatR pipeline and want one consistent validation path.

For minimal APIs, .NET 10 adds built-in validation with AddValidation, and before that you'd use endpoint filters that return a validation problem result.

What I aim for is one error format for all errors, validation, business rule or server error, using ProblemDetails, with field-level details the front end can show next to inputs, and stable error codes instead of relying on message text. Front-end folks really appreciate that, in my experience, because they can map codes to messages and stop parsing English sentences.

@p17-769 | What is YARP, and when would you use a reverse proxy built in .NET?
YARP, Yet Another Reverse Proxy, is a Microsoft library for building reverse proxies on ASP.NET Core. You configure routes and clusters, usually in appsettings. Routes match incoming requests by path, host, headers or method, and clusters define the destination servers, with load balancing, health checks and session affinity. And because it's just an ASP.NET Core app, you can add any middleware you like, authentication, rate limiting, logging, request and response transforms.

Where I'd use it. Strangler fig migrations, honestly that's the big one. You put YARP in front of a legacy application and route specific paths, like slash api slash shipments, to a new .NET 8 service, while everything else still goes to the old system. As features move over, you change routes, and clients never notice. That fits moving from ASP.NET MVC 4.8 to ASP.NET Core gradually.

A lightweight API gateway or BFF, central authentication, token handling for SPAs, header transforms and routing to internal services, when a full gateway product is too heavy or just not available on-premise.

Internal routing in containers, or as an edge component, with custom logic off-the-shelf proxies can't easily do.

Compared to Nginx, Envoy or cloud gateways, those are excellent for standard proxying and might be faster or better tied into platform features. YARP shines when a .NET team needs custom C# logic in the proxy and wants familiar tools.

One thing to watch is it becomes critical infrastructure. So it needs high availability, monitoring, timeouts, and careful forwarding of headers like X-Forwarded-For and correlation ids.

@p17-770 | What is OData, and would you use it for your APIs?
Okay, OData is a standard protocol for queryable REST APIs. Clients add query options to the URL. Dollar filter to filter, like status equals Shipped, dollar select to choose fields, dollar expand to pull in related entities, dollar orderby, dollar top and dollar skip for paging, and dollar count. In ASP.NET Core, the OData package turns those into LINQ on an IQueryable, so with EF Core they become SQL queries.

The good side, very flexible querying with little code, standard conventions with metadata describing the model, and good support in tools like Excel and Power BI, which can read OData feeds directly. So it's attractive for reporting and data-exploration endpoints.

The risks. Clients can build expensive queries, filtering on non-indexed columns or deep expands, and that hurts the database. Exposing the data model that directly couples clients to it, so changes get harder. Security needs care, so users can't expand or filter into data they shouldn't see. And honestly, the URL syntax is unfamiliar to a lot of front-end developers.

If I use it, I lock it down. Allow only specific properties for filtering and sorting, cap page size with MaxTop and page size settings, limit expand depth, apply authorisation filters before OData's query, and expose DTO projections instead of raw entities.

My view is for internal reporting or admin grids with lots of filter combinations, OData can save a lot of work. For public or core business APIs, I prefer purpose-built endpoints with explicit filters, which are easier to optimise, secure and evolve.

@p17-771 | FromBody, FromQuery, FromRoute, FromHeader, FromForm and FromServices: how does binding source work?
Model binding decides where each action parameter comes from, and these attributes basically make that explicit.

FromRoute is from the URL path template, like the id in shipments slash id.

FromQuery is from the query string, like status equals Shipped and page equals 2. Complex types can bind from several query parameters, which is handy for filter objects.

FromBody is from the request body, deserialised by the input formatter, usually JSON. Only one parameter can bind from the body, because the body stream's read once.

FromForm is form fields and multipart data, IFormFile for uploads included.

FromHeader reads a request header, like X-Correlation-Id, using its Name property.

FromServices injects a service from DI into just that action, useful when only one action needs a dependency.

With ApiController, inference rules kick in. Complex types are assumed to be from the body, simple types matching route parameters come from the route, other simple types from the query, and registered services get inferred as FromServices in newer versions. Minimal APIs have similar inference, plus AsParameters to group parameters into one object.

Common problems I've hit. A complex filter type on a GET wrongly inferred as body, so it needs FromQuery. Content type mismatches, like sending form data to a FromBody parameter, which gives a 415 Unsupported Media Type. And JSON property names that don't match.

So I'm explicit with attributes whenever there's any ambiguity. It documents the API and avoids surprises.

@p17-772 | How do you configure Swagger UI to send JWT tokens, and should it be enabled in production?
To test secured endpoints from Swagger UI, the OpenAPI document needs a security scheme, and the UI needs a way to get or enter a token.

The simple way is a bearer token. In Swashbuckle you add a security definition called Bearer, with type Http, scheme bearer and format JWT, and a security requirement so operations use it. The UI then shows an Authorize button where you paste a token, and it sends the Authorization Bearer header on each call. With the built-in OpenAPI support in .NET 9, a document transformer adds the security scheme.

The nicer way, for teams using an identity provider like Keycloak or Entra ID, is an OAuth flow. Define an OAuth2 scheme with the authorisation code flow and PKCE, configure Swagger UI with a client id, and users log in through the identity provider straight from the Authorize button. No copying tokens around, and real user roles get used.

An operation filter can mark only endpoints with the Authorize attribute as needing security, and show which scopes or policies they need.

Production? For internal APIs, a lot of teams enable the UI only in lower environments, Development and Test, with an environment check, and keep the OpenAPI JSON available in production behind authentication for client generation. For public partner APIs, a proper developer portal is better than Swagger UI on the live service. If it really has to be in production, protect it with authentication and keep internal or admin endpoints out of the document.

And never put real secrets, like client secrets, into the Swagger config in front-end code. I've seen that happen, and it's an easy leak.

@p17-773 | How do you generate typed API clients from OpenAPI for .NET and TypeScript?
Writing HTTP client code by hand for every endpoint is repetitive, and it drifts from the real API. Generating clients from the OpenAPI document keeps them in sync with the contract.

Tools I'd look at. For .NET, NSwag generates C# client classes with a method per operation plus DTO classes. Kiota, from Microsoft, generates clients for lots of languages with a fluent, path-based style. Refit's different, you write an interface with attributes and it generates the implementation.

For TypeScript, openapi-typescript generates types only, which pair nicely with a small fetch wrapper like openapi-fetch. orval and openapi-generator can generate full clients, even React Query or Angular service code.

How I set it up. The API produces its OpenAPI document at build time, for example with the build-time document generation in .NET 9. The client gets generated in CI or as a build step, never edited by hand. And the generated code is versioned, either committed or published as a package, like an internal npm package on our Azure DevOps feed, so front ends depend on a specific API version.

What you get is compile-time errors when the contract changes, no typos in URLs or property names, and way less boilerplate.

Watch-outs. The OpenAPI document has to be accurate, correct nullability, enums and response types, otherwise the generated code is just wrong. Generated clients can be big. And breaking API changes show up as compile errors, which is good, but they still need coordinating.

Put that together with contract tests and you catch integration mistakes really early.

@p17-774 | How do you host an ASP.NET Core app under a sub-path or IIS virtual directory?
Right, sometimes an app isn't at the root of a domain, it's under a path like company dot com slash portal, either as an IIS sub-application or behind a reverse proxy that routes slash portal to the app.

The challenge is the app has to generate correct links, redirects, cookie paths and static file URLs with slash portal in them, while routing ignores that prefix.

On IIS with the ASP.NET Core Module, sub-applications are handled for you. IIS passes the path base, Request PathBase gets set, and the URL helpers and redirects include it.

Behind a reverse proxy that forwards the full path, you call UsePathBase with slash portal early in the pipeline. It moves slash portal from Path into PathBase, so routes like slash api slash shipments still match. If the proxy strips the prefix, it should send it in an X-Forwarded-Prefix header, and the forwarded headers middleware can apply it to PathBase.

One thing I always check is cookie paths, so auth cookies are scoped correctly, especially when several apps share a domain. Then OpenID Connect redirect URIs, registered with the full path. Swagger and OpenAPI server URLs. SPA front ends, where the base href in Angular or the base option in Vite for React has to match, otherwise scripts and assets load from the wrong place. And any absolute URLs hardcoded in code or config.

This is a really common setup with on-premise IIS, where several applications share one site, like our MVC host with Angular sub-apps and APIs under different paths. Getting path base right avoids broken links and those annoying login loops.

@p17-775 | AddControllers vs AddControllersWithViews vs AddMvc: what is the difference?
These register different sets of MVC services, and picking the right one keeps the app lean.

AddControllers registers what API controllers need, controller discovery, model binding, validation, formatters, filters, authorisation and CORS integration. No views, no Razor, no tag helpers. That's the right one for Web APIs.

AddControllersWithViews adds view support on top. The Razor view engine, tag helpers, view components, antiforgery for forms, and temp data. You use it for traditional MVC apps that return HTML views.

AddRazorPages registers Razor Pages, the page-based model, and you can combine it with the others.

AddMvc registers everything, controllers, views and Razor Pages. It's mainly there for compatibility with older apps migrated from ASP.NET Core 2, where it was the standard call.

You also need the matching endpoint mapping. MapControllers for attribute-routed API controllers, MapDefaultControllerRoute or MapControllerRoute for conventional MVC routes, and MapRazorPages for pages.

Why does it matter? Registering services you don't need adds a bit of startup time and memory, and switches on features you don't want, like view-related behaviour in a pure API. Also AddControllers doesn't include antiforgery validation for views, so if a migrated app uses forms, you need the views version. That one can catch people out during migrations.

In a migration from ASP.NET MVC 4.8, a hybrid app with both views and APIs would use AddControllersWithViews and map both route styles, while new pure API services use AddControllers or minimal APIs.

@p17-776 | How do you support field selection or sparse fieldsets in a REST API?
Sometimes clients only need a few fields of a big resource, like a mobile app that wants the shipment id, status and date, not the whole object with items and addresses. Sending everything wastes bandwidth and database work.

You've got a few choices. A fields query parameter, like get shipments with fields equals id, status, shipped-at. The API returns only those. To implement it, validate the requested fields against an allowlist, then either build a dynamic projection, a Select expression built from the field list, so the database only fetches those columns, or fetch a normal DTO and shape the output by serialising just the selected properties into a dictionary or JsonObject. JSON:API standardises this with a fields parameter per resource type.

Predefined views. Instead of arbitrary fields, offer a few named shapes, view equals summary or view equals detail, or separate endpoints like shipments slash summary. Easier to optimise, cache and document, and usually enough.

Expansion the other way round, return a lean resource by default and let clients ask for related data with expand equals items and site.

And GraphQL, if lots of clients need lots of different shapes. It's built for exactly this.

What you pay for arbitrary field selection is harder caching, since every combination's a different response, messier OpenAPI docs, and careful security so clients can't select fields they shouldn't see.

My usual approach is predefined summary and detail shapes, because they cover most needs and performance stays predictable. I'd add field selection only with a clear, measured need, like big payloads hurting a mobile or partner client.

@p17-777 | How do you write a custom output formatter, for example to return CSV?
ASP.NET Core uses output formatters to serialise action results based on content negotiation. JSON's the default, but you can add formatters for other media types, like CSV, so a client sending an Accept header of text slash csv gets CSV from the same endpoint.

To write one, you create a class inheriting TextOutputFormatter. In the constructor, add the supported media types, text slash csv, and encodings, UTF-8. Override CanWriteType to say which types it handles, say an IEnumerable of some DTO. Override WriteResponseBodyAsync to write the data, a header row and then each item's values, escaping commas, quotes and newlines properly, writing to the response body asynchronously. Then register it in AddControllers by adding a new CSV output formatter to the output formatters list. Optionally add a format mapping so a format equals csv query, or a dot csv extension, works through the FormatFilter.

Things to watch. Use a proper CSV library like CsvHelper for escaping and culture-safe numbers and dates, not string concatenation. I learned that the hard way with decimal commas.

Large data, stream rows instead of building everything in memory, ideally from an IAsyncEnumerable, so big exports don't eat memory.

Security, CSV injection, where values starting with equals, plus, minus or at are treated as formulas when someone opens the file in Excel. Prefix or escape them for user-provided data.

Set Content-Disposition with a file name so browsers download it.

And for really large or slow exports, I'd generate the file in a background job and return a download link, instead of formatting it inside the request.

@p17-778 | What is host filtering, and why does AllowedHosts matter in ASP.NET Core?
Every HTTP request has a Host header saying which host name the client wants. Apps often use it to build absolute URLs, links in password reset emails, redirect URLs, callback URLs. If the app trusts any Host header, an attacker can send a request with the host set to evil dot com, and the app might generate links pointing to the attacker's site. Think of a password reset email whose link sends the token to the attacker, or caches poisoned with wrong URLs.

ASP.NET Core's host filtering middleware checks the Host header against the AllowedHosts setting. The default template sets AllowedHosts to star, which allows anything. Convenient for development, not great in production. Set it to specific names, like app dot example dot com and api dot example dot com separated by a semicolon, and the app rejects other hosts with a 400 Bad Request.

When the app's behind a reverse proxy or load balancer, the forwarded headers middleware might replace the host with X-Forwarded-Host. So configure KnownProxies, KnownNetworks and AllowedHosts on the forwarded headers options too, so spoofed forwarded headers aren't trusted.

Even better, don't build security-sensitive URLs from the incoming request at all. Use a configured public base URL for emails and callbacks. That's my preferred fix, honestly.

Kestrel doesn't validate host headers by itself, and IIS bindings only partly protect you if a site binding accepts all hosts.

It's a small config change that closes a real class of attacks, so I include it in production readiness checks.

@p17-779 | How do you avoid slow first requests after deployment, and warm up an ASP.NET Core app?
So the first requests after a deployment or an app pool recycle are often slow. The JIT compiles code on first use, DI builds services, EF Core builds its model and compiles queries, connection pools are empty, caches are cold, and HttpClient connections and TLS handshakes are all new. Whoever hits the app first sees seconds of delay.

How I reduce it. Warm up before taking traffic. In rolling or slot deployments, call key endpoints or run a warm-up routine before the instance is marked ready. An IHostedService can do warm-up work at startup, touching the DbContext, loading reference data into cache, opening connections, and a readiness health check only passes once warm-up's done.

IIS specifics, enable the Application Initialization module with preload enabled and start mode AlwaysRunning, and configure initialisation pages, so IIS starts the app and calls warm-up URLs after a recycle, before users arrive. Also avoid unnecessary recycles, like the default idle timeout that shuts down quiet apps. That idle timeout catches people out a lot on internal apps that only get used in the morning.

Reduce the startup cost itself. ReadyToRun compilation to pre-compile code, EF Core compiled models for big models, which matters when you've got hundreds of tables, avoiding heavy reflection scanning at startup, and lazy initialisation only for rarely used parts.

Measure it. Track the latency of the first requests after deployments and the startup duration, so regressions are visible.

For serverless, like Lambda or Azure Functions, it's the same idea as cold starts, with provisioned concurrency or premium plans as extra options.
