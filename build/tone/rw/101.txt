High availability means the system keeps working when individual components fail. The core idea, basically, is removing single points of failure at every layer.

For compute, run multiple instances of every service, spread across at least two availability zones, behind a load balancer that health-checks them and stops sending traffic to unhealthy ones. The orchestrator, like ECS, automatically replaces failed tasks. Services are stateless, so any instance can handle any request. For data, managed databases with Multi-AZ, where a synchronous standby takes over automatically if the primary fails, plus automated backups and point-in-time recovery. Caches and brokers are clustered too. For the application, timeouts, retries and circuit breakers between services, queues to absorb failures, and graceful degradation, so non-critical features can fail without taking down core ones. For deployments, rolling or blue-green, with health checks and automatic rollback, because a lot of outages come from changes.

And then you test it. Failover drills, chaos experiments like killing instances, and monitoring with alerts, so you know availability is real, not assumed.

In [the newer IQVIA services on AWS], every service runs at least two tasks across two availability zones, and RDS SQL Server is Multi-AZ, because sites in many countries need the system round the clock. I can explain how failover affects connections.

@p3-10
Honestly, the hardest part wasn't the code. It was designing the tools so the AI reliably picked the right one out of about 77.

Early on, the model sometimes chose the wrong tool, or passed slightly wrong parameters, because some tools overlapped or had vague descriptions. I fixed that with a strict verb-noun naming convention, like queue build and get release status, descriptions that say "use this when", enums for environment names instead of free text, and by removing overlapping tools. Outputs mattered too. Returning raw JSON logs filled up the model's context, so I switched to short structured summaries with a link to the full details.

Then there were long-running deployments. A deployment can take an hour, and a tool call can't block that long. So start tools return an id, and status tools poll. And the on-premise Azure DevOps Server API was its own headache. It differs from the cloud documentation in versions and authentication details, so I tested every call against our actual server. Throughout, I had to keep humans in control, read-only tools at the start, write tools with confirmation, and production only through existing approvals.

What I learned is that for AI tools, interface design matters more than implementation. I can show a before and after tool description.
