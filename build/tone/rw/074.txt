@p17-876 | pandas vs Polars: how do you process data efficiently in Python?
So both are DataFrame libraries for tabular data, used for analysis, ETL, reports and preparing data for things like RAG ingestion or exports.

pandas is the long-established standard. Huge ecosystem, integrations everywhere, and most data people know it. But it's mostly single-threaded and eager, it can eat a lot of memory, and some of its APIs are a bit inconsistent.

Polars is newer, written in Rust, and built for performance. It uses all the CPU cores, has a lazy API that builds a query plan and optimises it, pushing filters down and reading only the columns it needs, and it uses Apache Arrow memory, which is efficient. It's often much faster than pandas with lower memory, and the expression API is consistent.

How I choose, for new pipelines, especially with big files, Polars is a strong choice. For existing code, or when a library expects pandas, stay with pandas. Converting between them through Arrow is easy anyway.

Some performance tips apply to both. Vectorise, use column operations instead of Python loops or apply with a lambda row by row, which is really slow. I've seen jobs go from minutes to seconds just by fixing that.

Read only what you need. Select columns and filter early, use efficient formats like Parquet instead of CSV for intermediate data, and specify data types, like categories for repeated strings.

Process in chunks, or with lazy streaming, when the data's bigger than memory.

Push heavy filtering and aggregation down to the database with SQL when the data lives there, instead of loading everything into a DataFrame.

And for very large or distributed workloads, tools like DuckDB, which runs SQL directly on files, or Spark come into the picture.

@p17-877 | How do you consume RabbitMQ or Kafka messages in a Python service?
For RabbitMQ in Python the main libraries are pika, which is synchronous, and aio-pika, which is asyncio-based and fits FastAPI or other async services. For Kafka, confluent-kafka, which wraps the fast librdkafka C library, or aiokafka for asyncio.

Honestly the reliability rules are the same as in .NET and Node.

Manual acknowledgement after processing. With aio-pika you use the message process context manager, which acks on success and rejects on an exception, or you ack explicitly. In Kafka, turn off auto-commit and commit offsets after processing.

Prefetch, set_qos with a prefetch count to limit in-flight messages per consumer.

Retries and dead-lettering. Reject without requeue to send failures to a dead-letter exchange, use retry queues with TTLs for delayed retries, and track a max attempt count in the headers.

Idempotency, store processed message ids, because redelivery does happen.

Validation, parse message bodies with Pydantic models and dead-letter invalid ones straight away.

Connection resilience, aio-pika's connect_robust reconnects and restores channels automatically after network blips.

Concurrency, in asyncio you process messages concurrently up to the prefetch limit. For CPU-heavy processing, use separate processes, since the GIL limits threads.

Graceful shutdown, handle SIGTERM, stop consuming, finish in-flight messages, then close the connection.

Observability, structured logs with message and correlation ids, OpenTelemetry context propagated through message headers, and metrics for processing time and failures.

Celery's another option for task-style work over RabbitMQ or Redis, but for consuming domain events from other services, I'd go with a plain consumer because it gives more control.

@p17-878 | Which Python standard library modules do you use most: itertools, collections, functools?
Python's standard library saves you a lot of code if you know it well. The ones I reach for most.

collections. defaultdict for grouping without checking keys, like grouping shipments by site. Counter for counting and most_common. deque for queues and sliding windows. And namedtuple for lightweight records, though I mostly use dataclasses now.

itertools. chain to loop over several sequences as one, islice to take part of an iterator, groupby for consecutive grouping, after sorting, product and combinations, and batched, from 3.12, to split an iterable into chunks. That one's really handy for batching database inserts or API calls.

functools. lru_cache and cache to memoise pure functions, partial to pre-fill arguments, wraps for decorators that keep the wrapped function's name and docstring, reduce now and then, and cached_property.

pathlib, object-oriented paths, like Path of data slash file dot csv, reading and writing text, globbing. Cleaner and safer than string paths with os path.

datetime and zoneinfo for timezone-aware dates, with zoneinfo giving IANA time zones since 3.9.

json, csv and logging for everyday I/O and logs. dataclasses and enum for clear data and constants.

contextlib, contextmanager to write context managers with a generator, and suppress to ignore specific exceptions.

concurrent futures for thread and process pools, and subprocess for running commands safely with argument lists.

secrets for secure random tokens, and hashlib for hashing.

Knowing these, I mean, avoids extra dependencies, which also cuts supply chain risk.

@p17-879 | How do you cache results in Python with lru_cache and Redis?
Python has caching at a few different levels.

In-process with functools. Put lru_cache with a max size of, say, 1024 on a function and it memoises results based on the arguments, evicting the least recently used entries. cache is the unbounded version. Good for pure functions with hashable arguments, parsing config, expensive calculations, loading reference data that never changes. The limits, no expiry, arguments have to be hashable, it's per process so each worker has its own copy, and on methods it can keep instances alive. It also doesn't work on async functions directly, because it'd cache the coroutine object. That one catches people out. Libraries like async-lru handle it.

With expiry, cachetools gives you TTLCache and LRUCache classes with time-based expiry, for data that changes now and then.

Shared cache with Redis. When several processes or instances need the same cache, or the data should survive restarts, use Redis with redis-py, which has an asyncio interface too. The usual cache-aside pattern, try Redis, on a miss load from the source, then set it with an expiry. Serialise with JSON or orjson. Pydantic models can be dumped to JSON and validated on the way back.

Good practices, versions and identifiers in keys, jitter on expiries, stampede protection with a short lock or request coalescing, Redis timeouts with a fallback to the source if Redis is down, and measuring hit ratios.

In our RAG service, caching embeddings for repeated queries and caching document metadata are typical places where this saves time and model cost.

@p17-880 | How do you publish an internal Python package to a private feed?
Okay, when several Python services share code, like logging setup, auth helpers or API clients, an internal package stops you copying code between repos.

Packaging. Define the package in pyproject dot toml with a name, version, dependencies and a build backend like hatchling or setuptools. Use a src layout, so tests run against the installed package and not local files by accident. Build with python dash m build or uv build, which gives you a wheel and a source distribution.

Versioning, semantic versioning, with the version coming from Git tags in CI through something like hatch-vcs or setuptools-scm, so nobody edits versions by hand.

Publishing to a private feed. Azure Artifacts supports Python feeds, so do AWS CodeArtifact, GitHub Packages and JFrog. In the pipeline, authenticate with the platform's mechanism, like the Twine authenticate task in Azure Pipelines or a short-lived CodeArtifact token, and upload with twine or uv publish. No personal credentials in scripts.

Consuming, configure pip or uv with the feed as an index URL, using a keyring or environment-based credentials in CI and on developer machines. Be careful mixing public and private indexes, because of dependency confusion attacks. Use a feed that proxies PyPI as an upstream source, and give internal packages a unique name prefix, so a public package with the same name can't get installed by mistake.

Quality, the package has its own tests, type hints with a py typed marker so consumers get type checking, a changelog, and dependency ranges that aren't too strict.

It's the same discipline we use for npm feature packages and NuGet packages on our Azure DevOps feed.

@p17-881 | What is new in recent Python versions, like free-threading and the JIT?
Recent Python releases have been really focused on performance and developer experience.

Faster CPython. Since 3.11 the interpreter's become a lot faster, often 10 to 60 percent over 3.10, through specialising adaptive interpretation. Just upgrading gives you a noticeable speed-up.

Free-threaded Python. 3.13 brought an experimental build without the GIL, and 3.14 made it officially supported, though still optional. Threads can run Python code truly in parallel across cores, which helps CPU-bound multi-threaded work. The catch is single-threaded code can be a bit slower, and C extensions have to be updated to be thread-safe, so ecosystem support is still maturing.

An experimental JIT compiler, a copy-and-patch JIT added in 3.13, off by default, laying groundwork for future speed-ups.

Better error messages, clearer suggestions like "did you mean", and precise locations in tracebacks. Honestly that one makes day-to-day debugging nicer.

Language features, exception groups and except-star in 3.11, the type statement and new generic syntax in 3.12, where a function can declare its type parameter T right after its name, f-string improvements in 3.12, template strings in 3.14, and deferred evaluation of annotations.

Standard library, tomllib for reading TOML in 3.11, asyncio TaskGroup and timeout, itertools batched in 3.12, and a much better interactive shell in 3.13.

My practical approach is run services on a recent supported version, upgrade yearly once dependencies support it, and test performance-sensitive services on the new version, since the speed gains often come for free.

@p17-882 | How do you write and package Python Lambda functions?
Python's a natural fit for Lambda, quick cold starts and a simple handler model. You write a handler function that takes the event and the context and returns a response.

Structure, initialise clients like boto3 clients and config at module level, so they're reused across warm invocations. Keep the handler thin. Parse the event, call business logic in separate functions or modules, return the result. That way the logic's testable without Lambda.

Packaging dependencies. For pure-Python packages, a zip file with the dependencies installed into the package folder is enough. For packages with compiled parts, like pydantic-core, cryptography or numpy, they have to be built for Amazon Linux and the right architecture, x86 or arm64. So build in a matching container, or use the right platform flags with pip. This one bites people constantly, it works locally and fails in Lambda. Big dependencies can go in layers shared across functions, or use a container image, up to 10 GB, for heavy data or ML libraries.

Tools, AWS SAM or CDK to define and deploy functions, with sam build handling dependency packaging. And Powertools for AWS Lambda for structured logging, metrics, tracing, event parsing with Pydantic, idempotency, and batch helpers for partial SQS failures.

Performance, more memory gets you more CPU, arm64 Graviton gives better price-performance, avoid importing heavy libraries you don't need, and use SnapStart for Python if cold starts matter.

Testing, unit-test business logic directly, test handlers with sample events, and use moto to mock AWS services, or LocalStack for integration-style tests.

Security, least-privilege execution roles, and secrets from Secrets Manager or Parameter Store, not plain-text environment variables.

@p17-883 | How do you handle dates, time zones and naive vs aware datetimes in Python?
Right, Python's datetime objects are either naive, with no time zone info, or aware, with a tzinfo attached. Mixing them causes errors, like not being able to compare naive and aware values, and naive values cause silent bugs when code assumes a time zone that just isn't there.

My rules. Use aware datetimes in UTC internally. datetime now with timezone utc, not utcnow, which returns a naive value and is deprecated, and not plain now, which gives local server time.

Store UTC in databases, in timestamp with time zone columns in Postgres, or as UTC with a clear naming convention in SQL Server.

Convert to the user's or site's local time only for display, or for business rules that depend on local time, using zoneinfo with IANA names, like Asia slash Kolkata, which handles daylight saving properly. Never use fixed offsets for regions that switch for daylight saving.

Use date, not datetime, for business dates without a time, like a visit date or date of birth. That avoids off-by-one-day bugs when converting between zones.

Parse and format with ISO 8601. fromisoformat handles most ISO strings since 3.11, and APIs should exchange ISO strings with offsets or a trailing Z. Pydantic parses those automatically.

Arithmetic across daylight saving changes, adding 24 hours isn't always "the same time tomorrow" in local time, so for schedules compute in local time and then convert.

Testing, use freezegun or time-machine to control the current time, and test around midnight and daylight saving changes. That's where the bugs hide.

These are the same principles I follow in .NET with DateTimeOffset and DateOnly.

@p17-884 | What is SQS long polling, and how do you handle large messages?
When a consumer calls ReceiveMessage, SQS can respond two ways.

Short polling returns immediately and only checks a subset of SQS servers, so it can return nothing even when messages exist. And an idle consumer makes constant empty calls, which costs money, because SQS bills per request.

Long polling waits up to 20 seconds for messages to arrive before responding, and checks all the servers. You set the wait time seconds on the receive call, or the receive message wait time on the queue, to 20. It cuts empty responses, cost, and pickup latency. I use it by default for every consumer, and Lambda's SQS integration already uses it.

Batching, receive up to 10 messages per call with the max number of messages setting, and delete them in batches too, which cuts the request count further.

Message size. SQS messages are limited to 256 KB, recently raised to 1 MB. For bigger payloads, it's the claim-check pattern. Store the payload in S3 and send a message with a reference to it. The SQS Extended Client Library does that automatically for Java and Python, and there are equivalents for .NET. Consumers fetch the object from S3, and a lifecycle rule cleans up old payloads.

Even under the limit, I keep messages small, ids and essential data, because smaller messages are cheaper and faster, and you don't put sensitive data into queues for no reason.

Other settings that go with it, a visibility timeout longer than your processing time, a dead-letter queue with a sensible max receive count, and monitoring the age of the oldest message to catch consumers falling behind. That metric's saved us a few times, I think.

@p17-885 | How do multipart uploads work in S3, and how do you get good S3 performance?
Multipart upload splits a big object into parts that get uploaded independently and in parallel, and then S3 combines them. You get faster uploads through parallelism, you only retry failed parts instead of the whole file, and you can upload objects up to 5 TB. AWS recommends it over 100 MB, and it's required above 5 GB for a single PUT. The SDKs do it automatically, the TransferUtility in .NET or the Upload helper in JavaScript.

The hidden cost is incomplete multipart uploads keep their parts stored, and billed, forever, unless you clean them up. So I always add a lifecycle rule to abort incomplete multipart uploads after a few days. People miss that one and then wonder about the bill.

Browser uploads, the backend can start a multipart upload and return pre-signed URLs per part, so big files go straight from the browser to S3 in parallel.

Performance tips. Request rates, S3 handles at least 3,500 writes and 5,500 reads per second per prefix and scales automatically, so spreading keys across prefixes allows more throughput for really heavy workloads.

Parallel downloads too, byte-range fetches pull parts of a large object in parallel.

Transfer Acceleration uses CloudFront edge locations for faster long-distance uploads, say from users on other continents, at extra cost.

Same region, keep compute and buckets in the same region to avoid latency and transfer charges, and use a VPC gateway endpoint for S3 so traffic doesn't go through NAT gateways, which saves money.

And CloudFront in front of S3 for content that's read a lot.

@p17-886 | How do S3 bucket policies, IAM policies and Block Public Access work together?
Access to S3 is decided by several layers, and basically an action's allowed only if something allows it and nothing denies it.

IAM policies are attached to users and roles and say what that identity can do, like get-object on a bucket's objects. That's the normal way to give your own applications access.

Bucket policies are resource-based policies on the bucket itself, saying who can do what to it. You need them for cross-account access, for granting AWS services access, like CloudFront through origin access control, and for enforcing rules on everyone, like denying requests that don't use TLS, requiring encryption, or allowing access only from a specific VPC endpoint.

ACLs are the old mechanism. AWS now recommends disabling them by setting object ownership to bucket owner enforced, which is the default for new buckets.

Block Public Access is a safety net at the account and bucket level. When it's on, it overrides any policy or ACL that would make data public. I keep it on at the account level and only turn it off for buckets that genuinely have to be public, which is rare, because CloudFront with origin access control serves public content without a public bucket.

Encryption, if objects use SSE-KMS, the caller also needs permission on the KMS key. That's a really common cause of AccessDenied surprises.

Good practices, least privilege with specific actions and prefixes, deny insecure transport, enable server access logging or CloudTrail data events for sensitive buckets, and use IAM Access Analyzer to spot buckets shared outside the account.

@p17-887 | How do CloudFront cache policies and invalidations work?
CloudFront caches responses at edge locations, and cache behaviours and policies control what's cached, for how long and under which key.

Cache behaviours match path patterns, like slash assets slash star or slash api slash star, each with its own origin and policies, so static files and API calls get treated differently.

The cache policy defines the cache key, which headers, cookies and query strings make a response unique, plus minimum, default and maximum TTLs. A smaller cache key means more cache hits. Include only what actually changes the response, so for static assets don't include all the cookies.

The origin request policy defines what gets forwarded to the origin without being part of the cache key, like a header the origin needs that doesn't change the response.

TTLs, the origin's Cache-Control headers set the time, bounded by the policy's min and max.

Invalidation removes objects from edge caches before they expire, using paths like slash index dot html or slash star. The first 1,000 paths a month are free, then they cost, and they take a little while to finish.

My approach for SPAs avoids frequent invalidation. Hashed file names for JavaScript and CSS, like main dot some-hash dot js, cached for a year, because every new build produces new names. And index dot html with no-cache or a very short TTL, so users get the new version right after a deployment. Then one small invalidation of index dot html, or none at all, is enough.

For APIs, I'd say caching's usually disabled with the managed caching-disabled policy, or there's short caching only for public, non-personalised GET responses.
