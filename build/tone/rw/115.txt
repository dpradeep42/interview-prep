These are two approaches to deciding what's the source of truth, the C# model or the database.

In Code First, the C# entity classes and their configuration are the source of truth. You design the model in code, and migrations create and evolve the database schema. It works well when the development team owns the database, because the schema is versioned with the code, reviewed in pull requests, and reproducible in every environment. In Database First, the database already exists, often designed and owned by DBAs, or it's a legacy schema. You use dotnet ef dbcontext scaffold to generate the entity classes and DbContext from the existing tables, and you re-scaffold when the schema changes. It's the practical choice when you can't control the schema.

EF Core removed the old EDMX designer, so both approaches now produce plain code. You can also mix them, scaffold once from an existing database, then carry on with migrations.

In our IRT services, newer services are Code First with migrations, while some older shared databases were scaffolded Database First, because other systems depend on that schema. Honestly, that's the pragmatic split. I can explain how we handle schema changes there.

@p5-7
LINQ-to-Entities basically means writing LINQ queries against EF Core's DbSet, which is an IQueryable, and having EF Core translate them into SQL that runs in the database.

When I write something like Shipments where status is Pending, order by date, take 20, nothing runs yet. EF Core builds an expression tree describing the query. When I enumerate it, like with ToListAsync, the provider translates the whole expression tree into one SQL statement, sends it to SQL Server, and maps the rows back into objects. So filtering, sorting, paging and aggregates all happen in the database, which is efficient.

The key restriction is that only translatable operations can be used. Standard operators, comparisons, many string and date functions, work fine. But a custom C# method inside a Where can't be translated, and EF Core will throw an exception rather than silently loading everything.

That's different from LINQ-to-Objects, which runs on in-memory collections using delegates. Knowing which one you're in, IQueryable or IEnumerable, is one of the most important things in EF Core performance. I can explain how to check the generated SQL.

@p5-8
Client-side evaluation is when part of a query runs in .NET memory instead of in the database, which can mean loading way more data than needed.

It happens when the query uses something EF Core can't translate into SQL, like calling a custom C# method inside a Where clause, or certain complex string operations. In old EF Core 2, it silently switched to client evaluation. It pulled every row into memory and then filtered, which was a hidden performance disaster. Since EF Core 3, it throws an exception instead, except in the final Select projection, where running C# on the results is harmless.

The other cause is our own code, calling AsEnumerable, ToList or ToArray too early in the chain. Everything after that point runs in memory. So filtering after ToList loads the whole table first.

To avoid it, I keep the query on IQueryable until the end, rewrite custom logic into translatable expressions, and check the generated SQL with ToQueryString or logging. In a code review on our team, I actually caught a ToList before a Where on a large shipment table. Moving it to the end cut the data loaded from the whole table to a few rows. I can show the difference.

@p5-9
For EF Core performance, I start by looking at the generated SQL and the execution plan, because most problems are in the query, not in EF itself.

Then I apply a set of habits. For read-only queries, AsNoTracking, so no change-tracking overhead. Project with Select into DTOs, so SQL fetches only the needed columns. Filter and page in the database, keeping everything on IQueryable. Avoid N+1 queries by using projections or Include, and use AsSplitQuery when several collections are included. Make sure the right indexes exist for the filters and sort order. For bulk changes, use ExecuteUpdate and ExecuteDelete, which run one SQL statement without loading entities. For very hot paths, compiled queries and DbContext pooling cut overhead. And always pass cancellation tokens, so abandoned requests stop querying.

I log the generated SQL in development, and in production, Query Store and our Grafana latency dashboards show which queries need attention.

Let me give a concrete example. Our shipment list screen went from [about 9 seconds to under 300 ms] mainly through a SARGable rewrite, a covering index, and server-side paging. I can walk through that.

@p5-10
SaveChanges is the method that writes all pending changes tracked by the DbContext to the database.

When I call it, EF Core runs change detection, comparing tracked entities with their original snapshots to find what's added, modified and deleted. Then it generates the INSERT, UPDATE and DELETE statements, batching them where possible, and runs them all inside one transaction. So either all of the changes are saved, or none are. After success, it updates the entities, like with generated identity values and new concurrency tokens, and marks them as unchanged. It returns the number of rows affected.

SaveChangesAsync does exactly the same, but asynchronously. While the database is doing the work, the thread is released back to the thread pool, instead of sitting idle. In ASP.NET Core, that's what you want, because it lets the server handle more requests under load. So in web APIs and services, I always use SaveChangesAsync, passing the cancellation token.

One more thing, honestly. I call it once per unit of work, at the end of the operation, not after every small change. That keeps the operation atomic and reduces round trips. I can explain how concurrency tokens work with it.

@p5-11
Bulk operations are where the default EF Core approach, loading entities, changing them, and saving, gets too slow.

For updates and deletes, EF Core 7 added ExecuteUpdate and ExecuteDelete. They translate directly into a single set-based UPDATE or DELETE statement, without loading any rows into memory or using the change tracker. Like, marking all expired kits at a depot as unusable becomes one SQL statement instead of thousands of tracked updates. For inserts, AddRange plus SaveChanges already batches statements, which is fine for hundreds or a few thousand rows. For very large loads, like tens or hundreds of thousands of rows, I use SqlBulkCopy, or a bulk extensions library, which uses SQL Server's bulk insert path and is much faster. I usually process in chunks, so transactions and memory stay manageable.

One caution, and it can catch people out. ExecuteUpdate bypasses the change tracker, so audit logic in SaveChanges interceptors doesn't run. In a GxP system, we make sure auditing still happens for those operations.

Our CSV import of [about 10,000] rows uses batched inserts in chunks inside a transaction, after validation. I can explain why we chose that over SqlBulkCopy.

@p5-12
Compiled queries are a way to skip the cost of translating a LINQ query into SQL every time it runs.

Normally, when EF Core executes a LINQ query, it has to process the expression tree and produce SQL. It caches that work internally, keyed by the shape of the query, so repeated queries are already fairly cheap. But there's still some overhead in computing the cache key from the expression tree on every call. With EF.CompileAsyncQuery, or EF.CompileQuery, I define the query once, as a static delegate with parameters. EF Core translates it once, and every call reuses it directly, so the overhead goes away.

The gain is real but small, usually noticeable only on very hot paths with simple queries, executed thousands of times per second. Compiled queries are also less flexible, because the query shape is fixed.

So my rule is to use them only after measuring shows translation overhead matters. In our services, I've used a compiled query for a frequently called lookup, getting a kit by its number, which sits on a hot path during dispensing. For most queries, indexes and projections matter far more. I can explain other EF hot-path optimisations.

@p5-13
Seeing the SQL that EF Core generates is essential, because that's where most performance problems show up.

You've got a few options. The simplest in development is LogTo on the DbContext options, like LogTo Console.WriteLine, filtered to Information level. In an ASP.NET Core app, I can enable the log category Microsoft.EntityFrameworkCore.Database.Command at Information level in configuration, and the SQL appears in the normal logs, with execution times. For a single query, ToQueryString returns the SQL without executing it, which is handy in tests and debugging. And for parameter values, EnableSensitiveDataLogging shows them, but only in development, because in production it could log personal or clinical data.

Outside the application, SQL Server tools help too. Query Store shows the heaviest queries over time, and Extended Events can capture specific ones.

In our team, during code reviews of data-heavy changes, we look at the generated SQL for new queries. That's how we've caught N+1 queries and accidental client-side evaluation before they reached production, honestly more than once. I can explain how to read the execution plan next.

@p5-14
EF Core supports all three relationship types, configured by convention or with the Fluent API.

One-to-many is the most common. A principal has a collection navigation, and the dependent has a reference navigation and a foreign key. Like, a Site has many Shipments, and each Shipment has a SiteId. In Fluent API, that's HasMany Shipments WithOne Site HasForeignKey SiteId, and I choose the delete behaviour explicitly. One-to-one uses reference navigations on both sides, and the dependent holds the foreign key, say a Subject and their ConsentRecord, configured with HasOne WithOne. Many-to-many, since EF Core 5, can be configured with collections on both sides, and EF creates the join table automatically.

But when the link itself has data, like a role or an assigned date, I model an explicit join entity instead.

That's our case for users and studies. A user can be on many studies, and a study has many users, but each assignment has a role and an assigned date, which our authorization checks use. So we have an explicit StudyAssignment entity. I can explain how we configure cascade deletes safely, which I think is the tricky part.

@p5-15
Shadow properties are properties that exist in the EF Core model and in the database table, but not in the C# entity class.

You configure them in OnModelCreating with Property of type and a name, and EF Core tracks them like normal properties. To read or filter by them in queries, you use EF.Property with the entity and the property name. To set them, you go through the change tracker, like entry dot Property of "LastModifiedBy" CurrentValue. EF Core also creates shadow properties automatically, like a foreign key column when the class only has a navigation property.

They're useful when a column matters to the database but shouldn't clutter the domain model. The classic use is audit columns, like CreatedBy, CreatedAt, LastModifiedBy and LastModifiedAt. Instead of adding these to every entity class, I define them as shadow properties on all entities, and set them centrally in a SaveChanges interceptor, using the current user and TimeProvider.

In our services, that's basically how audit columns are populated consistently, so no developer can forget to set them, which matters for GxP audit trails. I can show the interceptor code.

@p5-16
Owned entities are how EF Core maps value objects, types that don't have their own identity and only exist as part of another entity.

You configure them with OwnsOne for a single value object, or OwnsMany for a collection. Like, a Site has an Address, with street, city, postcode and country. Address isn't an entity on its own, it has no id, and it only makes sense as part of a site. With OwnsOne, EF Core stores the address fields as columns in the Site table, like Address underscore City, and loads them automatically whenever the site is loaded. OwnsMany stores the collection in a separate table, but it's still owned and loaded with its owner. Since EF Core 8, complex types offer a similar option for value objects.

What you get is a richer domain model. Instead of loose string properties on Site, I have a proper Address type, with its own validation, which can be reused in other entities like Depot, while the database stays simple.

In our IRT model, addresses and some quantity-with-unit values are owned types. I'd say that made validation consistent across sites and depots. I can explain how this relates to domain-driven design.

In EF Core, indexes are part of the model, so they're defined in code and created through migrations, which keeps them versioned and reviewed.

With the Fluent API, in the entity configuration, I call HasIndex with the columns. Like, HasIndex of StudyId and Status creates a composite index, and column order matters. I can add IsUnique for a unique index, like a kit number. HasFilter creates a filtered index, say only active rows. And with SQL Server, IncludeProperties adds included columns, to make a covering index. HasDatabaseName gives it a clear name. Or the Index attribute on the entity class works for simple cases. Then I add a migration, and the index is created through our normal release scripts.

The important part is choosing indexes from real query patterns, using the execution plan, rather than adding them everywhere, because every index slows down writes. People forget that.

The covering index from our shipment list fix, on StudyId, Status and ShipmentDate including the displayed columns, was added exactly this way, through a reviewed migration script. I can show the configuration code.
