All three define types, but they behave quite differently.

A class is a reference type with identity. Two objects with exactly the same values are still different objects, because equality compares references by default. A record is designed for data. It's still a reference type by default, but it compares by value, so two records with the same values are equal. You also get concise immutable syntax, a readable ToString, and with-expressions to make a modified copy. A struct is a value type, so it's copied on assignment, and it's best for small values. And there's record struct, which is a value type with value equality.

In my services I use records for DTOs, API contracts and messages we publish to Kafka or RabbitMQ, because those are pure data and should be immutable. I use classes for services and EF Core entities, because entities have identity and change over time. Structs, honestly, I use rarely, only for small values.

I can explain why EF entities shouldn't be records, if that's useful.

My main rule is, catch an exception only where I can actually do something about it, and let everything else bubble up to one global handler.

In practice that means a few things. I never swallow exceptions with an empty catch. When I rethrow, I use throw on its own, not throw ex, so the stack trace is kept. People mix that up a lot. I log an exception once, with context like the correlation id and the study id, instead of logging it at every layer. I create specific domain exceptions for business rules, like a StudyTransferNotAllowedException, but I don't use exceptions for normal flow like validation, because they're slow and hide intent. And I use using or finally to clean up resources.

In our ASP.NET Core APIs, one global exception handler catches anything unhandled, logs it, and returns a consistent ProblemDetails response with the right status code, without leaking stack traces to the client.

That gives us consistent errors and clean logs during an incident. I can show how we set up IExceptionHandler in .NET 8.

So generics let me write code once and use it with many types, while keeping full type safety.

Without generics, you'd use object and cast everywhere, which is error-prone, and value types would get boxed. With List of T or Dictionary of K and V, the compiler knows the exact type, so there's no casting and no boxing. Constraints tell the compiler what a type parameter can do. Like, where T is a class, where T implements an IEntity interface, or where T has a parameterless constructor. Then I can safely call those members inside the generic code. There's also variance, where an IEnumerable of a derived type can be used as an IEnumerable of the base type.

In my work, I wrote a generic paged result type, so every list API returns items, total count and page info in the same shape. I've also used a generic Result of T wrapper for success or error responses, and generic repository methods constrained to our entity base class.

So generics cut duplication and catch mistakes at compile time. I can explain covariance in more detail if you want.

The middleware pipeline is basically the chain of components every HTTP request passes through in ASP.NET Core, from the moment Kestrel receives it until the response goes back.

Each middleware gets the HttpContext and a next delegate. It can do some work, call next to pass the request along, and then do more work as the response comes back through it, in reverse order. Or it can short-circuit, like the static files middleware returning a file, or authorization returning 403. The pipeline's built in Program.cs with app dot Use calls, and order matters a lot. A typical order is the exception handler first, so it catches everything, then HSTS and HTTPS redirection, static files, routing, CORS, authentication, authorization, rate limiting, custom middleware like logging and correlation ids, and the endpoints at the end.

A good mental picture is Russian dolls, each layer wraps the next one.

In our services, the first custom piece is our correlation-id middleware, placed near the top so even errors from later middleware get logged with the id. That lets us trace one request across [4] services. I can explain what goes wrong when the order's wrong.

@p1-18
Service lifetimes decide how long an object created by the DI container lives, and who shares it.

Singleton means one instance for the whole application. Everyone gets the same object, so it has to be thread-safe. It's good for configuration, caches, IHttpClientFactory or a RabbitMQ connection. Scoped means one instance per scope, which in a web app is one per HTTP request. Everything in that request shares it, and it's disposed at the end. DbContext is the classic example, because it's a unit of work. Transient means a new instance every time it's requested, which suits lightweight, stateless helpers like validators or mappers.

The rule that really matters is about dependencies. A service shouldn't depend on something with a shorter lifetime. If a singleton takes a scoped DbContext, that DbContext gets captured forever, shared across threads and requests. That's called a captive dependency, and ASP.NET Core's scope validation catches it in development.

In our services, DbContext is scoped, the RabbitMQ connection is a singleton, and validators are transient. Our background services create a scope per message. I can explain that pattern if it's useful.

@p1-19
Both build HTTP APIs on the same foundation, same routing, DI, middleware and authentication. The difference is really style and structure.

Controllers are classes that inherit ControllerBase, with actions marked by attributes like HttpGet. They give you a mature, conventional structure, the full filter pipeline, ApiController behaviours like automatic validation, and every .NET developer knows them. That suits large APIs with many endpoints and teams. Minimal APIs map routes directly to lambdas or methods with MapGet and MapPost. There's less ceremony, startup's faster, performance is slightly better, and they work well with native AOT. Route groups, endpoint filters, TypedResults and, since .NET 10, built-in validation have closed most of the gaps.

So my choice is practical, not religious. For a large existing service with lots of controllers, I stay with controllers, for consistency. For a new small service, or just a few endpoints, minimal APIs are cleaner.

In our team, the main IRT APIs use controllers, and newer small internal services use minimal APIs organised into feature-based extension methods. I can show how a minimal API is structured for a bigger service.

@p1-21
Middleware and filters can both run code before and after a request, but they work at different levels.

Middleware sits in the ASP.NET Core pipeline and runs for every request, including static files, health checks and requests that never reach a controller. It only knows about the HttpContext, the request, the response and the user. Filters run inside MVC, around a specific controller action. They know the action context, which controller and action is running, the bound arguments, model state and the result. And they run in a defined order, authorization, resource, then model binding, action, exception and result filters.

So my rule's simple. If the concern is about HTTP in general and applies everywhere, I use middleware, like correlation ids, request logging, security headers or global exception handling. If it needs to know about the action, its arguments or its result, I use a filter, like validating a model, auditing which study an action changed, or caching an action's result.

In our project, the correlation-id is middleware because it has to cover every request across [4] services, while study-level audit logging is an action filter because it reads the action's arguments. I can show both in code.

@p1-22
Model binding is how ASP.NET Core turns the raw HTTP request into typed parameters for my action, and then validation checks those values before my code runs.

Binding reads values from different sources, the route, the query string, headers, form fields and the JSON body. I can be explicit with attributes like FromRoute, FromQuery and FromBody, and with ApiController, complex types come from the body by default. If a value can't be converted, like text for an integer, it's recorded as a model state error. Then validation runs, using data annotations like Required and Range, or FluentValidation for richer rules. With ApiController, an invalid model automatically returns a 400 with ValidationProblemDetails, listing each field and its error.

That checks the shape of the data. Business rules, like "this site must belong to an active depot", still belong in the service layer, because they need data and context.

For our CSV bulk import, a single request can contain [around 10,000] rows. So what we did was validate every row and return a per-row error report with line numbers, instead of failing on the first error. Users fixed everything in one go. I can explain that design.

@p1-23
Global exception handling means one central place catches every unhandled exception and turns it into a consistent, safe error response, instead of try-catch blocks in every controller.

In ASP.NET Core, I put UseExceptionHandler at the top of the pipeline, so it wraps everything after it. Since .NET 8, I write IExceptionHandler classes that map known exceptions to the right status code. So a validation exception becomes 400, not found becomes 404, a concurrency conflict becomes 409, and anything unknown becomes 500. With AddProblemDetails, every error follows the standard ProblemDetails format, with a type, title, status and trace id.

Two rules matter, for me. Log the full exception server-side, with the stack trace and correlation id. But never return internal details to the client in production, just a clear message and the id. And I don't use exceptions for normal flow, expected outcomes like "not found" can just return a result.

This kept our controllers clean and our errors consistent across services. When a user reports an error, they give support the correlation id from the response, and we find the exact exception in Splunk in seconds. I can show a sample handler.

@p1-24
REST is an architectural style for APIs built on HTTP. Everything's a resource, identified by a URL, like slash studies slash 12 slash shipments. Clients use standard HTTP verbs to act on them, exchange representations, usually JSON, and every request is stateless, meaning it carries everything the server needs, like the token. Responses can also be cacheable.

The verbs have clear meanings. GET reads data, and it's safe, it changes nothing. POST creates, and it's not idempotent, sending it twice creates two things. PUT replaces a resource, and it's idempotent, sending it twice gives the same result. PATCH partially updates. DELETE removes, and it's idempotent too. Idempotent just means repeating the request has the same effect as doing it once, which is what makes retries safe.

Status codes complete the picture, 200, 201 with a Location header, 204, 400, 401, 403, 404, 409 and so on.

The idempotency part actually matters in real systems, because networks fail and clients retry. For POST operations that create important things, like a shipment, we accept an idempotency key, so a retry returns the original result instead of creating a duplicate. I can explain that pattern.
