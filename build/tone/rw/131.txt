In .NET Framework, there was no built-in dependency injection container, unlike modern .NET, where it's part of the platform. So teams basically added it themselves.

The common approach was a third-party container, like Unity, Autofac, Ninject, Castle Windsor or Simple Injector. You registered your interfaces and their implementations with the container at application startup, usually in Global.asax, with their lifetimes, like transient, per request or singleton. Then you hooked the container into the framework. For ASP.NET MVC, you set a custom dependency resolver, for ASP.NET Web API, you set the configuration's DependencyResolver, and the framework would ask the container to create controllers with their dependencies through constructor injection.

WCF was harder, because WCF creates the service instances itself. To use constructor injection, you needed a custom instance provider and a service behaviour, or a custom service host factory, and the containers often provided integration packages for that, like Autofac's WCF integration.

Without a container, some older code used the service locator pattern, or created dependencies with new directly, which made it hard to test.

In modern .NET, dependency injection is built in, through IServiceCollection, and used consistently by ASP.NET Core, background services and libraries. That's one of the nice things when we migrate older WCF and Framework code. It gets easier to test, because dependencies can be replaced.

@p7-47
We migrate away from WCF because WCF server isn't supported in modern .NET. Staying on it means staying on the .NET Framework, which is Windows-only, gets only security fixes, and can't use modern features, performance improvements, or container hosting on Linux, like the ECS setup IQVIA's newer AWS services use. REST APIs, or gRPC, are also much easier to build, test, monitor and integrate with modern clients and tools.

The challenges are real, honestly. Existing clients, for one. Some external or internal clients still expect SOAP, and we can't always change them at the same time, so we may need to keep a SOAP endpoint, say using CoreWCF, or a facade that translates, during a transition period. Then WCF-specific features, like WS-Security message signing, duplex callbacks, or transactions, which have no direct REST equivalent and need a redesign. Behaviour has to stay exactly the same, including data formats, edge cases and errors, which matters a lot in a validated GxP system. And configuration and hosting, moving from XML configuration and IIS to code-based configuration and containers.

So the approach is to migrate one service at a time, not big bang, using the strangler fig pattern. We write characterisation tests against the existing service first, to capture its current behaviour, run old and new side by side, compare results, and switch clients over gradually, with a rollback path, through FV and UAT validation.

@p7-49
GxP is a general term for good practice quality guidelines and regulations in life sciences. The x stands for the specific area, like GMP for good manufacturing practice, GCP for good clinical practice, and GLP for good laboratory practice. They're enforced by regulators, like the FDA in the US and the EMA in Europe.

The purpose is to make sure that products like medicines are safe and effective, and that the data used to make decisions about them is reliable and trustworthy.

For software, the key regulations are FDA 21 CFR Part 11 and EU Annex 11, which cover computerised systems and electronic records. The core idea is data integrity, often summarised as ALCOA plus. Data has to be attributable, meaning we know who did it, legible, contemporaneous, meaning recorded at the time, original, and accurate, plus complete, consistent, enduring and available.

Why does it matter? Because in clinical trials, software mistakes can affect real patients. If our IRT system gave a patient the wrong kit, or lost a record of what they received, it could harm the patient, or make the trial's results unreliable, which could invalidate years of research. Regulators can reject trial data, or take action against a company, if its systems aren't compliant.

So in our work, honestly, GxP means validated systems, complete audit trails, strict change control and documented evidence for everything. It shapes how we develop, test and release software every day.

These three ideas are really at the heart of working in a regulated environment.

Validation means proving, with documented evidence, that a system consistently does what it's meant to do, and meets its requirements. It's not just testing, it's planned and documented. There's a validation plan, requirements, risk assessment, test scripts with expected results, executed tests with recorded evidence, and a summary report signed off before the system is used. It's often described as installation, operational and performance qualification. In our process, the FV team does the formal validation testing.

Traceability means being able to follow the links between things. Each requirement is linked to its design, to the code changes, to the tests that verify it, and to their results, usually in a traceability matrix. So we can answer questions like, was this requirement tested? Which requirement does this change affect? In Azure DevOps, we link work items, commits, builds and test results to make this possible.

Auditability means anyone reviewing the system, like an auditor or regulator, can reconstruct what happened. Every change to data is recorded in an audit trail, who did it, when, what the old and new values were, and why. Audit trails can't be changed or deleted. The same applies to changes to the system itself, through change records and approvals.

Put together, they let us prove that the system is correct and that its data can be trusted.

Change control is a formal process for managing any change to a validated system, so every change is justified, assessed, approved, tested and documented before it reaches production, and the system stays in a validated state.

Approval to release, then deployment to production, following the documented plan, including a rollback plan. And closure, with verification that it worked and all documentation complete.

Shipment tracking connects our IRT system with external depots and couriers, so we always know where trial medication is.

When IRT decides a site needs medication, it creates a shipment order. That order goes to the depot vendor, either as a file over SFTP, using our SFTP integration component, or through an API, depending on the vendor. The depot picks and packs the kits, and the courier transports them. As the shipment moves, the vendor sends status updates back, like dispatched, in transit, delivered, or a temperature excursion, again as files or API calls.

On our side, integration services collect those updates and handle them carefully. They validate the format and content, check for duplicates, using the file name and content hash, and the shipment id and status, so a resent update isn't applied twice, and then update the shipment. They publish events, through RabbitMQ and Kafka, so other parts of the system can react, like updating site inventory, and notifying site staff that medication is on its way or has arrived.

Failures are expected, so there are retries with backoff, dead-letter queues, alerts to support, and a reconciliation report that compares what we sent with what the vendor has acknowledged, to catch anything missed.

I learned the importance of this the hard way in [mid-2024], when [about 1,200] updates were lost silently. We recovered them by replaying the vendor files, and added publisher confirms.
