The four main OOP principles are encapsulation, abstraction, inheritance and polymorphism.

Encapsulation means an object keeps its data private and changes it only through its own methods, so it protects its rules. Abstraction means exposing what something does and hiding how it does it, usually through an interface. Inheritance lets a class reuse and extend the behaviour of a base class. And polymorphism means one interface, many implementations, where the right method is picked at runtime.

They work best together, honestly. In my SFTP integration component, business code depends on an ISftpClient interface, which is abstraction. Three providers, ComponentPro, SSH.NET and Rebex, implement it, which is polymorphism, since the caller just calls UploadAsync and configuration decides which one runs. They inherit shared retry and logging logic from a base class, which is inheritance. And each provider keeps its connection details private, which is encapsulation.

In practice I prefer composition over deep inheritance trees. I can go deeper into any of the four.

@p4-18
Encapsulation basically means bundling an object's data with the methods that change it, and hiding the internal state, so the object can protect its own rules.

In C# that means private fields, properties with private setters where needed, and public methods that enforce business rules. The outside world can only ask the object to do something, it can't put it into an invalid state directly. What you get is the rules living in one place, so the data stays valid and the code is safer to change later, because callers don't depend on the internals.

A real example is a shipment in our system. Instead of a public Status property anyone can set, the Shipment class has methods like MarkDispatched and MarkDelivered. MarkDelivered checks that the shipment was actually dispatched, and records the time. If someone tries to deliver a cancelled shipment, it throws a clear domain exception. In a GxP system that matters a lot, because every state change has to be valid and auditable.

I can explain how this relates to rich versus anaemic domain models if that helps.

Inheritance lets a class reuse and extend the behaviour of another class, called the base class. It models an "is-a" relationship, like a Rebex SFTP client is an SFTP client.

In C#, a class can inherit from only one base class, but it can implement many interfaces. The derived class gets the base members, can add its own, and can override virtual methods to change behaviour. It's powerful for sharing real code, but it creates tight coupling, because changes in the base class ripple into every child. Deep hierarchies also get hard to understand.

So I use it carefully. In our SFTP component, an abstract SftpClientBase class holds the common retry, timeout and logging logic, and each provider class inherits it and only implements the library-specific connect, upload and download. That removed a lot of duplication.

But when the relationship is really "has-a", or behaviour varies a lot, I'd go with composition, injecting a collaborator instead of inheriting. I can talk about when I'd avoid inheritance if you like.
