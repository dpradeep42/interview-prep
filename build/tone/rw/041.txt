So SignalR is ASP.NET Core's library for real-time communication, pushing messages from server to clients over WebSockets, with fallbacks. Self-hosted SignalR has a scaling problem though. Each client is connected to one server instance, so to send a message to all users, or to a user connected to a different instance, the servers need a backplane, like Redis, and load balancers need sticky sessions. Each server also holds lots of open connections, which eats resources.

Azure SignalR Service fixes that. It's a managed service that holds all the client connections. The app servers connect to the service and send messages through it, so the service handles fan-out to the right clients, no matter which app instance sends the message. No backplane, no sticky sessions, and app servers don't hold thousands of connections anymore. It scales to very large numbers of concurrent connections through units. Integration is mostly configuration, you call AddSignalR and then chain AddAzureSignalR onto it.

It also has a serverless mode, used with Azure Functions bindings, where functions send messages through the service without any hub server. That suits event-driven notifications, like pushing a status update to a user when a background process finishes.

Azure Web PubSub is a related service for plain WebSocket clients, without the SignalR protocol, useful for non-.NET clients and other frameworks.

Where I'd use it, live dashboards, notifications, collaborative editing, chat and progress updates. Authentication uses access tokens, and user ids let you target specific users and groups.

Actually every container in a pod can declare requests and limits for CPU and memory, and they do quite different jobs.

Requests are what the container is guaranteed. The scheduler uses them to place pods. A node only accepts a pod if the sum of requests on it fits the node's allocatable capacity. So requests decide where pods go and how many fit on a node. Too low, and nodes get overpacked and pods fight for resources. Too high, and you're paying for idle capacity.

Limits are the ceiling. For memory, if a container goes over its limit, the kernel kills it, and you see OOMKilled. For CPU, a container over its limit isn't killed, it's throttled, which shows up as latency. That difference trips people up a lot.

Together they decide the pod's quality of service class. Guaranteed, when requests equal limits for every container, and those pods are the last to be evicted under node pressure. Burstable, when requests are lower than limits. BestEffort, when nothing is set, and those go first.

My defaults for a .NET API, memory request and limit set to the same value, based on observed usage plus headroom, because memory isn't compressible. A CPU request based on typical usage, and often no CPU limit, or a generous one, to avoid throttling. Then I check actual usage in metrics and adjust, because the first guesses are usually wrong.

Okay, OOMKilled means the container used more memory than its limit and the kernel killed it. kubectl describe pod shows the last state as OOMKilled with exit code 137, and the restart count keeps climbing.

The first thing I check is whether it's a real leak or just a limit that's too low. I look at the container's memory graph over time, in Prometheus or Container Insights. A sawtooth that climbs steadily until the kill, after every restart, points to a leak. A sudden spike points to one big operation, like loading a large file or a huge query result into memory. A flat line just under the limit means the limit is simply too tight for normal work.

For .NET specifically, the runtime reads the container's memory limit and sizes the GC heap from it, but if the limit is really small, server GC with many heaps can still push close to it. Options are setting GCHeapHardLimitPercent, using workstation GC for small containers, or just giving a realistic limit.

If it's a leak, I reproduce it, take a memory dump with dotnet-dump or dotnet-gcdump before the kill, and look for what's growing. Caches without expiry, static collections, event handlers not removed, or undisposed objects.

For spikes, I stream instead of buffering, page large queries, and limit concurrency of heavy jobs.

Only after I understand the cause do I raise the limit. And I set an alert on memory near the limit, so we hear about it before the kills start, not after.
