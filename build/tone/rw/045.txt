So Kubernetes talks to container runtimes through the Container Runtime Interface, CRI. Docker Engine never implemented CRI, so Kubernetes had an adapter called dockershim to talk to it. That adapter was removed in Kubernetes 1.24.

What that meant in practice. Clusters switched to CRI-compatible runtimes, mainly containerd, which was actually the component Docker itself used under the hood, or CRI-O. Managed services like EKS, AKS and GKE moved to containerd.

What didn't change, images built with Docker still work everywhere, because they follow the OCI image standard, and containerd runs OCI images. Developers keep using Docker Desktop or Docker Engine to build and run containers locally. Only the runtime on the cluster nodes changed.

What did break was anything relying on the Docker socket on nodes. Like CI jobs building images inside pods by mounting the Docker socket file, or monitoring agents reading Docker's API. Those moved to alternatives, like BuildKit, Kaniko or buildah for in-cluster builds, and runtime-agnostic agents. Debugging on nodes uses crictl instead of the docker command.

So in an interview, I'd say the key points are, Docker is a developer tool and image format ecosystem. containerd is the runtime. OCI standards make images portable between them. And Kubernetes only needs a CRI runtime on the nodes. A lot of people panicked about that change for nothing, honestly.

See, running migrations from the app at startup, like calling Database.Migrate in Program.cs, is risky in Kubernetes. With several replicas starting at once, they race to apply the same migration, startup gets slow, and the app needs DDL permissions it really shouldn't have at runtime.

Better options.

A Kubernetes Job before the rollout. The pipeline runs a migration Job, using the same image or a dedicated migrator image, waits for it to finish successfully, and only then updates the Deployment. In Helm, this is often a pre-upgrade hook, so the release fails if the migration fails. The Job uses a separate database identity with schema-change rights.

A migration step in the pipeline itself, outside the cluster, applying an idempotent script or an EF Core migration bundle generated at build time. That makes the migration a visible, auditable release step, which I like.

Init containers can work for simple cases, but every pod would try to run them, so they need locking, and I don't usually go that way.

Whatever the mechanism, the schema changes themselves have to be backward compatible, because during a rolling update old and new versions run side by side. I use expand and contract. Add new columns or tables first, deploy code that writes both, backfill, switch reads, and only drop old columns in a later release. That also keeps rolling back the app safe without rolling back the database.

Actually a plain Deployment does a rolling update. It replaces pods gradually, but it only checks readiness, not whether the new version is actually healthy for users. Progressive delivery tools add real canary and blue-green releases with automated analysis.

Argo Rollouts replaces the Deployment with a Rollout resource. A canary strategy lists steps, like send 10 percent of traffic, pause five minutes, run analysis, go to 30 percent, analyse again, then 100 percent. Traffic splitting can be by replica count, or precise using an ingress controller, the Gateway API, or a service mesh. Analysis templates query a metrics provider, like Prometheus, Datadog or CloudWatch, with success conditions, like error rate below one percent and p95 latency below 400 milliseconds. If analysis fails, the rollout aborts and traffic goes back to the stable version automatically. Blue-green is supported too, with preview services and promotion.

Flagger does the same with a different model. You keep your Deployment, and Flagger creates the canary and primary objects and drives traffic shifting with a mesh or ingress, using metric checks and webhooks for load tests or approvals.

What makes it work in practice, good metrics per version, labelled so you can compare canary with stable. Enough traffic for the statistics to mean something. And backward-compatible database changes, since both versions run together.

It's basically the automatic rollback answer for Kubernetes. Health gets judged by real user signals, not by humans staring at dashboards.

Okay, so trunk-based development means everyone integrates into one main branch at least daily, through short-lived branches that live a day or two, instead of long-running feature or develop branches that merge weeks later with painful conflicts.

Making it work needs a few supporting habits.

Small changes. A big feature gets split into small, safe pull requests that each keep main working, like adding the database column first, then the API, then the UI.

Feature flags. Unfinished work merges behind a flag that's off in production, so code gets integrated before the feature is ready. Release becomes a flag switch, not a merge.

Fast, reliable CI. Every pull request runs build, unit tests and static checks in about ten minutes. Branch policies require a passing build and a review before merging.

Keep main releasable. If main breaks, fixing it is the team's top priority, and reverting is a normal, blame-free thing to do.

Release branches only when needed, cut from main for a release that needs stabilisation or hotfixes, and fixes go to main first, then get cherry-picked.

What you get is fewer merge conflicts, earlier feedback, and a codebase that's always close to shippable. In a regulated environment, the validated release is still a specific, tagged build from main, so traceability is kept. That was the main worry people had when I've seen teams move to it.

@p17-533
So feature flags let you change behaviour at runtime without deploying, but they turn into technical debt if nobody manages them. I think about them by type.

Release flags hide unfinished or new features until they're ready. They should be short-lived, removed within a few weeks of full rollout. Ops flags or kill switches let you turn off an expensive or risky path during an incident, like disabling a heavy export, and these can live longer. Experiment flags drive A/B tests. Permission flags turn on features for specific customers or plans, which is really configuration and belongs in the product's settings model.

In .NET, Microsoft.FeatureManagement gives you IFeatureManager and attributes for controllers, with filters for percentage rollout, user or group targeting, and time windows. Flags can come from configuration, Azure App Configuration, or a dedicated service like LaunchDarkly or Unleash, and OpenFeature gives a vendor-neutral API.

My rules for keeping it clean. Every flag has an owner and an expiry date, recorded when it's created. Check the flag in one place, near the edge, instead of scattering checks across the code. Test both states. Default to the safe value if the flag service is unreachable. And add a ticket to remove the flag and the dead code once rollout's done.

In a regulated product, a flag that changes validated behaviour is itself a configuration change, so its state per environment has to be controlled and recorded.

See, semantic versioning is MAJOR dot MINOR dot PATCH. Bump MAJOR for breaking changes, MINOR for new backward-compatible features, PATCH for backward-compatible fixes. Pre-release labels, like 2.1.0-beta.3, mark builds that aren't final. For libraries and packages it's essential, because consumers rely on it to know if an upgrade is safe.

Editing version numbers by hand doesn't scale, so I automate it.

GitVersion calculates the version from Git history, tags, branch names and commit messages. A tag v1.4.0 on main marks the release, builds after it become 1.4.1-something or 1.5.0 depending on configuration, and feature branches get pre-release labels.

Conventional commits put intent in commit messages, like feat colon for a feature, fix colon for a fix, and feat with an exclamation mark or BREAKING CHANGE for breaking changes. Tools like semantic-release or release-please read them, bump the version, create the tag and generate a changelog. That works really well for npm packages.

The build then stamps the version everywhere. Assembly versions in .NET through the Version property, package versions, container image tags, and the build name in the pipeline, so the running app can show its version on a health or about endpoint. That's saved us a lot of "which version is in prod" conversations.

For deployable services, I also add the commit SHA in the build metadata, like 1.4.2 plus abc1234, so any running instance traces back to its exact source.

@p17-535
Honestly when lots of services have similar pipelines, copying YAML into each repo leads to drift and painful updates. Azure Pipelines templates fix that.

You can template at a few levels. Step templates hold a sequence of steps, like restore, build, test and publish coverage for a .NET project. Job and stage templates hold whole jobs or stages, like a standard deploy stage with approvals and smoke tests. Variable templates hold shared variables. Templates take typed parameters, like the project path, .NET version or environment name, with defaults and allowed values, and can use template expressions with each loops and conditions, evaluated at compile time.

Templates usually live in a central repository, referenced with a resources repositories block and pinned to a tag or branch, so a change to the shared template is versioned and teams can adopt it deliberately.

Extends templates go further. The pipeline in each repo just extends a central template and passes parameters, and the template controls the overall structure. Combine that with a required template check on protected resources, like production environments or service connections, and you enforce that every pipeline deploying to production runs the mandatory security scans and approvals. That's a strong governance tool.

What I do is keep templates simple and well documented, avoid deep nesting, and test template changes on a sample pipeline before releasing a new version. Otherwise one bad change breaks every team at once.

@p17-536
Okay, an Azure Pipelines YAML pipeline has a pretty clear hierarchy.

Stages are the big phases, like Build, Deploy to Dev, Deploy to QA and Deploy to Production. They run sequentially by default, can depend on each other with dependsOn, and can have conditions, like only deploying from main. Approvals and checks are attached at the environment level, so a stage waits until they pass.

Jobs run inside stages. Each job runs on one agent, from a pool, and jobs in a stage can run in parallel. A job can be a normal job or a deployment job.

Steps are the individual tasks or scripts inside a job, like checking out code, running dotnet build, publishing artifacts, or running a PowerShell script.

Deployment jobs are special jobs for releases. They target an environment, which records deployment history, which build went to which environment and when. They support strategies, runOnce, rolling across virtual machines in the environment, and canary with increments. Each strategy has lifecycle hooks, like preDeploy, deploy, routeTraffic, postRouteTraffic, and on failure or success, so you can run smoke tests after routing traffic and roll back on failure.

Artifacts are published in the build stage and downloaded automatically in deployment jobs, so the exact same build output moves through every stage.

On our on-premise Azure DevOps Server, the older classic release pipelines are still used for some apps, but YAML pipelines with environments give us code review and history for pipeline changes.

@p17-537
So build once, deploy many means the pipeline compiles and packages the app one time, and that exact artifact, the same zip, package or container image, gets deployed to dev, test, UAT and production. Only configuration differs per environment.

Why it matters. If you rebuild for each environment, you're not deploying what you tested. A different build agent, an updated base image, a newer dependency pulled in by a floating version, or a different commit can sneak in. Then a bug shows up in production that never existed in test, and you can't easily tell why.

With a single artifact, testing in each environment adds confidence to the same binary. It's faster, because the build happens once. And it's traceable, the artifact has a version and a hash, linked to a commit and a build, and each deployment records which artifact went where.

To make it work, configuration has to live outside the artifact. Environment variables, appsettings per environment loaded at runtime, a configuration service, or secrets managers, not build-time constants or per-environment build flags. Front ends need the same idea, loading a runtime config file instead of baking API URLs into the bundle.

In a validated GxP environment, this is close to mandatory, because the validated package has to be provably identical to what goes into production. In our team we keep the build artifact, its version and its approvals linked in Azure DevOps for exactly that reason.

Okay, storing an AWS access key and secret as a pipeline secret is common but risky. The keys are long-lived, often over-privileged, hard to rotate, and if leaked, they work from anywhere. The better way is OpenID Connect federation.

How it works with GitHub Actions. In the AWS account, I create an IAM OIDC identity provider for GitHub's token issuer, and an IAM role whose trust policy allows the STS AssumeRoleWithWebIdentity action from that provider, with conditions on the token's claims. The audience has to be sts.amazonaws.com, and the subject has to match a specific repository and branch or environment, like the shipments-api repo in our org with the production environment. In the workflow, I grant the id-token write permission and use the configure-aws-credentials action with the role ARN. Each run gets temporary credentials, valid for about an hour, and nothing's stored.

Azure Pipelines and GitLab support the same pattern, and so does Azure with federated credentials.

My rules here, separate roles per environment and per purpose, like a deploy role that can update ECS services and push to ECR, and a read-only plan role for Terraform pull requests. Least-privilege policies. Tight subject conditions, never a wildcard on the whole organisation. And CloudTrail monitoring of role usage.

For our on-premise Azure DevOps Server, federation depends on network and version support, so the same least-privilege idea applies with whatever mechanism is available, with credentials kept only in a protected library and rotated.
