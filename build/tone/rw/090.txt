API versioning is basically how an API evolves without breaking existing clients.

You can put the version in a few places. In the URL, like slash api slash v2 slash shipments, in a query string like api-version equals 2, in a header, or in the media type. I prefer the URL segment, because it's explicit, easy to see in logs, and easy to route at the load balancer. In .NET, the Asp.Versioning library handles this, including reporting supported and deprecated versions in response headers, and it works with OpenAPI, so each version gets its own document.

But honestly the best strategy is not needing new versions. Additive changes, like adding an optional field or a new endpoint, aren't breaking. Renaming or removing fields, or changing types or meanings, are breaking, and only those need a new version. When we do release one, the old version gets deprecated with a clear timeline, and we watch the logs until nobody calls it.

Because external vendors integrate with our APIs, we're strict about this. We also compare OpenAPI documents in the pipeline to catch accidental breaking changes. I can explain that check.

Configuration in ASP.NET Core comes from layered providers, and the Options pattern turns it into strongly-typed, validated classes.

The providers are layered, and later ones override earlier ones. appsettings, then appsettings for the environment, like Production, then user secrets in development, environment variables, and command-line arguments. For our services on AWS, we add Systems Manager Parameter Store and Secrets Manager. With the Options pattern, I bind a section to a class, say Configure of SftpOptions, and then inject IOptions of SftpOptions instead of reading raw strings.

For values that change, IOptionsSnapshot re-reads per request, and IOptionsMonitor gives live updates to singletons.

In our services, vendor SFTP settings are named options, secrets like passwords and keys come from Secrets Manager, never from appsettings, and the same container image runs in every environment with different configuration. And I always validate options at startup, with ValidateDataAnnotations and ValidateOnStart. So a missing or wrong setting stops the service immediately with a clear message, instead of failing later on the first real request. Trust me, that's way less painful at two in the morning.

My approach to performance is always measure first, fix the biggest bottleneck, then measure again.

I start with data. Splunk logs and Grafana metrics for latency percentiles and error rates, traces to see where the time goes, and profiling or slow query logs. Most of the time, the database is the problem. So I fix queries before anything else, proper indexes, AsNoTracking for reads, projecting into DTOs so we only fetch needed columns, paging, and removing N+1 queries. Then the code, async I/O all the way, IHttpClientFactory for outgoing calls, avoiding unnecessary allocations in hot paths. Then caching, in-memory or Redis for reference data, and output caching for expensive responses. Response compression helps for large payloads. Only once the code is efficient do I scale horizontally behind the load balancer.

CORS stands for Cross-Origin Resource Sharing. Browsers enforce the same-origin policy, which blocks a page from one origin, like our front-end domain, from reading responses from a different origin, like our API domain. CORS is how the server tells the browser which other origins are allowed.

For simple requests, the browser sends the request with an Origin header and checks the Access-Control-Allow-Origin header in the response. For other requests, like ones with a JSON content type or an Authorization header, the browser sends a preflight OPTIONS request first, asking which origins, methods and headers are allowed, and only sends the real request if the answer allows it.

In ASP.NET Core, I call AddCors with a named policy listing the exact allowed origins, methods and headers, and add UseCors in the pipeline after routing and before authentication, so preflight requests aren't rejected for having no token. I never combine AllowAnyOrigin with credentials, and I avoid wildcards in production.

And one thing people mix up, CORS isn't API security, it only affects browsers. In our services, origins come from configuration per environment. I can explain how to debug a CORS error.

@p1-30
In microservices, calls to other services will fail sometimes, so resilience is about making sure a temporary problem in one service doesn't turn into an outage for everyone.

I use several patterns together. Timeouts on every call, because a hanging call is worse than a failed one. Retries with exponential backoff and jitter, but only for transient errors, like timeouts, 503s and 429s, and only for idempotent operations. A circuit breaker, which after repeated failures opens and stops calling the failing service for a while, then tests it with a single call in the half-open state before closing again. Bulkheads to limit how many concurrent calls one dependency can use, and fallbacks, like cached data, where that makes sense. In .NET, I configure this on IHttpClientFactory with Polly, usually with AddStandardResilienceHandler.

And often the best resilience is not calling synchronously at all. For work that doesn't need an immediate answer, we publish a message to RabbitMQ, so if the other service is down, the work just waits in the queue.

Our vendor API calls use the standard resilience handler, and most short vendor outages now recover without anyone even noticing. I can explain how the circuit breaker states work.

@p1-31
So these are four styles of API communication, each good at different things.

REST is resource-based HTTP with JSON. It's simple, universal, cacheable, and every client and tool understands it, so it's my default for public and front-end APIs. SOAP, which in .NET usually meant WCF, uses XML envelopes with strict contracts defined in WSDL, plus standards like WS-Security and transactions. It's heavy, but still common in older enterprise systems. gRPC uses binary Protocol Buffers over HTTP/2. It's really fast, strongly typed from a shared contract, and supports streaming both ways. That makes it great for internal service-to-service calls, but browser support is limited. GraphQL exposes one endpoint where the client asks for exactly the fields it needs. Great when many different front ends need different shapes of data, but caching and per-field authorization get harder.

So the choice depends on the consumer. Public or browser APIs get REST. High-performance internal calls can use gRPC. Varied front-end needs suggest GraphQL.

In our IRT platform, the APIs are REST, and some older integrations still expose WCF SOAP endpoints, which we're gradually modernising. I can explain how I'd migrate those.

@p1-32
Background work in ASP.NET Core means work that runs outside the request, either long-running, like consuming a queue, or scheduled, like a nightly cleanup.

The built-in way is a BackgroundService, which implements IHostedService. I override ExecuteAsync with a loop that runs until the stopping token is cancelled, and register it with AddHostedService. It's a singleton, so for scoped services like DbContext, I inject IServiceScopeFactory and create a scope for each unit of work. It has to honour the stopping token for graceful shutdown, and catch and log exceptions inside the loop, so one bad message doesn't stop the whole service.

I'm careful not to do heavy work inside a web request, or fire-and-forget with Task dot Run, because that work's lost if the instance restarts, and it ends up using disposed services. I've seen that bite people. For heavy or important work, I put a message on a durable queue and let a separate worker process it, or use a Lambda or a scheduler.

In our platform, RabbitMQ consumers and our SFTP poller are BackgroundServices running in dedicated worker containers. That way, scaling and deployments of the API and the workers are independent. I can explain how we handle poison messages.

@p1-33
Change tracking is how EF Core knows what to save. When I load entities through a DbContext, it keeps a snapshot of their original values and tracks each one's state, Added, Unchanged, Modified, Deleted or Detached.

When I call SaveChanges, EF Core detects changes by comparing the current values with the snapshot, and generates only the needed INSERT, UPDATE and DELETE statements, all in one transaction. That's really convenient for writes, because I just change properties and save. But tracking has a cost, memory for snapshots and time for change detection, especially with thousands of entities.

So for read-only queries, like GET endpoints, lists and reports, I use AsNoTracking. It skips the snapshots, so queries are faster and use less memory. Even better for reads is projecting with Select into DTOs, which fetches only the needed columns and isn't tracked at all. For bulk changes, EF Core 7 added ExecuteUpdate and ExecuteDelete, which run a single SQL statement without loading entities.

In our services, reads default to no tracking, and we used ExecuteUpdate for a status update that used to load thousands of rows. I can explain how tracking interacts with concurrency.

@p1-34
These are the three ways EF Core loads related data, and the N+1 problem is what you get when you pick the wrong one.

Eager loading uses Include, so related data comes back in the same query, like shipments with their kits. Lazy loading loads related data automatically the first time you touch a navigation property, using proxies. It's convenient but it hides database calls. Explicit loading is when I deliberately load a navigation later, with Entry, Collection and Load.

The N+1 problem is one query to get a list of N parents, plus one more query for each parent's children. So listing 100 shipments and touching each one's site becomes 101 queries. It usually comes from lazy loading inside a loop, and it's slow because of all the round trips. To fix it, I use Include, or better, a Select projection into a DTO that gets exactly the needed fields in one query. For several large collections, AsSplitQuery avoids a huge cartesian join.

To catch it, I watch the SQL logs in development. I once found a shipment report making hundreds of queries because of lazy loading, and a projection brought it down to one. We keep lazy loading turned off for us. I can explain split queries.

In a regulated GxP environment, database changes have to be reviewed, repeatable and traceable, so we don't let the app change the schema by itself.

Developers create migrations in code with EF Core, as usual. But for deployment, we generate an idempotent SQL script with dotnet ef migrations script and the idempotent option. That script checks the migrations history table, so it's safe to run in any environment, whatever state it's in. The script's reviewed in the pull request, stored with the release, and applied by the release pipeline through each environment, FV, TechOps, UAT and then production, never automatically at app startup with Migrate. That gives us an audit trail of exactly what ran where.

The other key practice is backward-compatible changes, called expand and contract. During a rolling deployment, old and new versions of the app run at the same time. So we add new columns or tables to begin with, deploy the code that uses them, and only remove old columns in a later release.

Honestly, this made our database releases boring, which is exactly what you want. I can explain how we handle a rollback.

Concurrency conflicts happen when two users edit the same record at the same time, and without protection, the last save quietly overwrites the first. That's called a lost update.

EF Core's main approach is optimistic concurrency. I add a rowversion column, marked as a concurrency token. When EF updates the row, it includes the original rowversion in the WHERE clause. If someone else changed the row in the meantime, the rowversion doesn't match, zero rows get updated, and EF throws a DbUpdateConcurrencyException. Then I decide how to resolve it. Reload and retry automatically if the change is safe to reapply, merge the values, or return 409 Conflict and let the user see the latest data and decide.

Pessimistic locking, actually locking the row with something like UPDLOCK, is only for short, critical sections where conflicts are frequent and costly.

In our IRT system, we use both. Editing shipments and sites uses optimistic concurrency, returning 409 to the UI. But allocating limited drug supply to a site uses a short pessimistic lock, because two sites must never be promised the same last kits. I can explain that allocation design.
