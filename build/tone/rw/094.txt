On the front end, I watch for a few main kinds of security issues.

Cross-site scripting, XSS, is the big one. React escapes values by default, which protects us, but dangerouslySetInnerHTML, or putting user input into URLs like javascript links, bypasses that, so I avoid it or sanitise with DOMPurify. A Content Security Policy adds another layer. Then token storage. Tokens in localStorage can be stolen by any XSS, so I prefer HttpOnly, Secure, SameSite cookies, or keeping tokens in memory. Then reverse tabnabbing. Links with target blank used to give the new page access to window dot opener, so it could redirect our original tab to a phishing page. The fix is rel noopener noreferrer. Then never trusting the front end for security. Hiding a button isn't authorization, the API has to check everything. And dependency vulnerabilities, checked with npm audit in the pipeline.

The tabnabbing one is actually a real fix I did in IRT. A security scan flagged it, and I updated [about 40] external links, added a shared link component that sets rel by default, and a lint rule so it can't come back. I can explain how CSP helps.

@p1-74
Node.js runs JavaScript on a single main thread with an event loop, and uses non-blocking I/O through a library called libuv.

When a request needs a database query or an HTTP call, Node doesn't wait. It starts the operation, moves on to other requests, and runs the callback when the result comes back. So one process can handle thousands of concurrent connections with very little memory, because there's no thread per request. Things like file system operations and DNS run on a small libuv thread pool behind the scenes.

That makes Node a great fit for I/O-heavy work, APIs that mostly call databases and other services, backend-for-frontend layers, real-time apps with WebSockets, and developer tooling. Sharing TypeScript with the front end is a productivity win too. It's a weak fit for CPU-heavy work, like big calculations or image processing, because that blocks the event loop and every request waits. For those, worker threads or a different service are better. And in production, you run several processes or containers to use all the CPU cores.

In my work, I've used Node and TypeScript for internal tooling and integration services, while the core domain logic stays in .NET. I can explain the event loop phases.

FastAPI and Flask are both popular Python web frameworks, but they're kind of built for different eras of Python.

Flask is a minimal micro-framework, built on WSGI, and synchronous by default. It's simple, really flexible, and has a huge ecosystem, but you add things like request validation and API docs yourself with extensions. FastAPI is newer and async-first, built on ASGI. It uses Python type hints with Pydantic models, so request bodies are validated and converted automatically, and invalid input returns a clear 422 error. It generates OpenAPI documentation and Swagger UI from the code, it has built-in dependency injection with Depends, and it's one of the fastest Python frameworks.

So for a new typed REST service, I'd go with FastAPI. It feels quite close to ASP.NET Core minimal APIs, with typed models and automatic docs. Flask still makes sense for very simple apps, or existing Flask codebases where there's no reason to rewrite.

I've built REST services with both. In practice, the type-driven validation in FastAPI removed a lot of hand-written checking code, and the automatic docs made integration with other teams easier. I can explain how async works in FastAPI.

@p1-77
FastAPI is built on ASGI, so it supports async natively, and it uses Pydantic for validation.

For async, if I declare an endpoint with async def, it runs on the event loop. That's efficient for I/O, but only if everything inside is also async, using libraries like httpx for HTTP calls and asyncpg or async SQLAlchemy for databases. If I call blocking code inside an async def, it blocks the whole event loop and every request waits. If I have to use blocking libraries, I declare the endpoint with plain def, and FastAPI runs it in a thread pool instead. That's a common mistake, and it catches people out.

For validation, I define Pydantic models with type hints and constraints. FastAPI automatically parses and validates the request body, query and path parameters against them, and returns a 422 with detailed errors if they're invalid. Response models filter and serialise the output, so internal fields don't leak. Depends gives you dependency injection for database sessions, authentication and configuration.

In production, I run it with uvicorn workers, behind a load balancer, in a container. It's conceptually very similar to ASP.NET Core model binding plus DI. I can show a short example.

Spring Boot and ASP.NET Core are really similar in concept, so moving between them is mostly learning new names.

Both have a built-in dependency injection container with constructor injection, use annotations or attributes to declare routes, run on an embedded web server, support configuration profiles per environment, and have a mature ORM. The mapping is pretty direct. RestController in Spring is like a controller with ApiController. Constructor injection works the same way. JPA with Hibernate is like EF Core. application dot yml is like appsettings, Spring profiles are like ASP.NET Core environments, and Maven or Gradle play the role of NuGet and the dotnet CLI. Spring filters and interceptors are similar to middleware and filters.

The differences are more about ecosystem and style. Spring has a very large ecosystem, like Spring Security, Spring Cloud and Spring Data, and leans heavily on annotations and auto-configuration, which can feel a bit magical. ASP.NET Core is a bit more explicit, with configuration in Program.cs, and it's very fast in benchmarks.

Because the concepts transfer, I'm comfortable reading and contributing to Spring Boot services, and the design principles I use in .NET apply directly. I can compare their security models too.

@p1-80
In both ecosystems, the goal's the same, reproducible builds, controlled updates, and catching vulnerable packages early.

In Node, package dot json declares dependencies with version ranges, and the lock file, package-lock, records the exact versions of everything, including transitive dependencies. The lock file always gets committed. In CI, I use npm ci instead of npm install, which installs exactly what's in the lock file and fails if it's out of sync. npm audit, or a tool like Dependabot, checks for known vulnerabilities. In Python, I use a virtual environment per project, so dependencies don't clash, and pin exact versions, either in a requirements file or with a lock file from Poetry or uv. pip-audit checks for vulnerabilities.

For both, Docker images pin versions too, including the base image, and updates happen regularly through small pull requests, so we never face one huge risky upgrade.

It's basically the same idea as NuGet with central package management in .NET, which I introduced during our .NET 10 upgrade after a version conflict. I can explain how we handle a vulnerable transitive dependency.

@p2-1
EC2, ECS and Lambda are basically three levels of compute on AWS, from most control to least management.

EC2 gives you virtual machines. You choose the instance type and operating system and manage everything on it, patching, scaling, software. It's the right choice for legacy applications, special software that needs OS-level access, or workloads that don't fit containers. ECS runs Docker containers as long-running services, either on EC2 instances or on Fargate, where you don't manage servers at all. It's a great fit for web APIs and background workers with steady traffic, because containers are always running, start consistently, and you control the runtime. Lambda runs functions in response to events, like an HTTP request, a file in S3, or a message in a queue. You pay only per invocation and duration, and it scales automatically, even to zero. But each run's limited to 15 minutes, and cold starts add latency.

So my rule is Lambda for event-driven glue, scheduled jobs and spiky or low traffic. ECS for core APIs and workers with steady load. EC2 only when I need that level of control.

[The newer IQVIA services I've worked on] follow exactly that, the .NET services and consumers run on ECS, and Lambda handles event-driven pieces like reacting to files in S3. I can explain the cost trade-offs.

@p2-2
ECS has a small set of building blocks, and once you know them, the rest is pretty straightforward.

A cluster is a logical group of capacity where tasks run, either EC2 instances you manage, or Fargate, where AWS manages it. A task definition is the blueprint, a bit like a docker-compose file. It specifies the container image, CPU and memory, environment variables and secrets, port mappings, the IAM task role the app uses to call AWS services, the execution role ECS uses to pull images and secrets, and the logging configuration. A task is a running instance of that definition, one or more containers running together. A service keeps a desired number of tasks running, say three. It replaces unhealthy or stopped tasks, registers them with a load balancer target group, handles rolling deployments when you update the task definition, and integrates with autoscaling.

There are also capacity providers, which decide where tasks run, like Fargate or Fargate Spot.

In the newer IQVIA services on AWS, each .NET service has its own task definition and ECS service, behind an ALB target group, with a task role scoped to just what it needs. Deployments just register a new task definition revision. I can explain how a rolling deployment works step by step.

@p2-3
API Gateway is a managed front door for APIs. Clients call it, and it routes requests to the backend, like Lambda functions, HTTP services on ECS, or straight to other AWS services.

Its value is everything it handles before the request reaches your code. Authentication, with JWT and Cognito authorisers, custom Lambda authorisers, or IAM. Throttling and quotas, including usage plans with API keys per client, so one partner can't overload the system. Request validation against a schema, CORS, and request and response transformation. It also supports stages, like dev and prod, custom domains, caching, and logging and metrics in CloudWatch. It comes in three flavours, REST APIs, the most feature-rich, HTTP APIs, which are simpler, faster and cheaper, and WebSocket APIs for real-time two-way communication.

Limits to remember, a default 29-second integration timeout, and payload size limits, so it's not for long-running or large requests. That timeout one catches people out.

In the newer IQVIA services on AWS, partner-facing APIs go through API Gateway, which gives us per-partner throttling and keys, while internal UI traffic goes through the ALB directly to ECS. I can compare it with an ALB in more detail.
