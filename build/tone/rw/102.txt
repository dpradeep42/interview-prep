When an API suddenly gets slow in production, I work in a fixed order. Understand the scope, find the slow step, restore service, and then fix the root cause properly.

Scope and timing come before anything. On the dashboards I check whether it's one endpoint or all of them, since when, and whether anything changed, like a release, a configuration change or a jump in traffic. Then I look at latency by dependency, database, downstream APIs and queues, and use traces and logs filtered by correlation id to find exactly which step got slow. I also rule out the usual .NET suspects, thread pool starvation from sync-over-async code, connection pool exhaustion, and garbage collection pressure.

A real example. In [March 2025], our shipments API p95 jumped from [about 200 milliseconds to about 3 seconds], with no release at all. The traces pointed to one SQL query. Query Store showed its execution plan had changed after a statistics update. It was parameter sniffing, the new plan was built for a small study and was terrible for big ones. To restore service quickly, I forced the previous good plan in Query Store. Then I fixed it properly by improving the index and the query shape, so it no longer depended on a lucky plan.

Afterwards, I added a p95 latency alert per endpoint and a Query Store regression review to our routine, so next time we'd know within minutes, not from users.
