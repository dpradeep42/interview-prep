DbContext is basically a unit of work with the database. It tracks entities, holds a connection when it needs one, and saves changes in one transaction. That's why it's meant to be short-lived.

In ASP.NET Core, it's registered as scoped, so each HTTP request gets its own DbContext, shared by all services in that request and disposed at the end. And here's the key thing, DbContext isn't thread-safe. If two tasks use the same instance in parallel, like Task dot WhenAll over two queries, EF Core throws an exception about a second operation starting on this context. So for parallel work, each task needs its own context, which you get from IDbContextFactory.

In background services, which are singletons, I create a scope per unit of work, like per message, so each one gets a fresh DbContext with clean change tracking. Keeping one context around for a long time makes the change tracker grow and the data go stale. For really high-throughput APIs, AddDbContextPool reuses context instances to cut allocation cost.

In our RabbitMQ consumers, each message gets its own scope and DbContext. I can explain IDbContextFactory in more detail.

EF Core lets me run raw SQL when LINQ isn't enough, but I have to do it safely, with parameters.

For queries that return entities, I use FromSql, or FromSqlInterpolated. For commands, ExecuteSql or ExecuteSqlInterpolated. By default, each SaveChanges call in EF Core is atomic. All the inserts, updates and deletes it generates run in one database transaction, so either all succeed or none do.

When I need several SaveChanges calls, or a mix of EF operations and raw SQL, to succeed or fail together, I start an explicit transaction with BeginTransactionAsync, do the work, and call CommitAsync. If anything fails, it rolls back. With retrying execution strategies, I wrap the transaction in the strategy's ExecuteAsync, so the whole unit gets retried. I keep transactions short, and never call external services inside them, because long transactions hold locks and cause blocking and deadlocks.

Across microservices, there's no shared database transaction, you know. Distributed transactions are fragile, so we use the outbox pattern. The business change and an outbox message are saved in the same local transaction, and a separate process publishes the message afterwards. For multi-step workflows, a saga coordinates the steps with compensating actions.

In our shipment flow, the shipment update and its outbox event are saved together, so we never update the database without publishing the event, or the other way round. I can explain the outbox in detail.

WCF, Windows Communication Foundation, is the .NET Framework technology for building service-oriented applications. Mostly SOAP web services, but also TCP and named-pipe communication.

Every WCF endpoint is defined by its ABCs. A is the Address, where the service lives, the URL. B is the Binding, how you talk to it, the transport and encoding, like basicHttpBinding for simple SOAP, wsHttpBinding for WS-Security and reliable messaging, or netTcpBinding for fast binary communication between .NET systems. C is the Contract, what the service offers, ServiceContract on the interface, OperationContract on each method, and DataContract on the data types. WCF also supports message-level security, transactions and reliable messaging, which is why it got so popular in enterprises.

Modern .NET doesn't include the WCF server, only a client. For the server side, there's CoreWCF, a community project Microsoft supports, or you move to REST or gRPC.

In our IRT platform, some older integrations still expose WCF SOAP endpoints for external partners, so I've maintained those contracts, and I've been involved in planning how to modernise them. I can explain the migration options.

Migrating WCF services is mainly about not breaking existing clients, while getting onto modern, supported .NET.

You've got two main paths. One is CoreWCF, a port of the WCF server to modern .NET. It keeps the same SOAP contracts and most bindings, so existing clients don't change at all. It's the lowest-risk path when external partners depend on the SOAP interface. The other is re-exposing the functionality as REST with ASP.NET Core, or gRPC for internal calls. That's more modern, but clients have to change, so during the transition I'd keep a thin adapter that still serves the old SOAP contract.

Whichever path, I'd go step by step. Move business logic out of the service classes into shared libraries to begin with, so the WCF layer becomes thin. Then migrate endpoint by endpoint, using the strangler fig pattern, routing traffic gradually to the new implementation. Contract tests compare old and new responses for the same inputs, to prove behaviour's identical, which also gives validation evidence in a GxP system.

For our partner-facing SOAP integrations, I'd say CoreWCF is the pragmatic first step, and REST can come later. I can go into the testing approach.

Both are B-tree structures that help SQL Server find rows quickly, but they store data differently.

A clustered index defines the physical order of the table's rows. The leaf level of the clustered index is the actual data, so there can only be one per table, and it's usually on the primary key. A non-clustered index is a separate structure, with its own sorted key columns and a pointer back to the row, which is the clustered key. You can have lots of them. When a query uses a non-clustered index but needs columns that aren't in it, SQL Server does a key lookup back into the clustered index for every row, which gets expensive for large results. A covering index solves that by adding the extra columns with INCLUDE, so the query's answered from the index alone.

The catch is that every index speeds up reads but slows down inserts, updates and deletes, and uses storage. So I index based on real query patterns, not guesses.

My best example is our shipment list fix. A covering index on StudyId, Status and ShipmentDate, with the displayed columns included, took the query from [about 9 seconds to under 300 ms]. I can walk through that story.

SARGable means Search ARGument-able. A predicate is SARGable when SQL Server can use an index seek for it, jumping straight to the matching rows instead of scanning everything.

The most common way people break it is wrapping the indexed column in a function or calculation. Like WHERE YEAR of CreatedOn equals 2024, or CONVERT to date on a datetime column, or LEFT of Code, or Column plus 1 equals 5. SQL Server has to compute that for every row before comparing, so it scans. A sneaky one is a data type mismatch, like comparing an NVARCHAR parameter to a VARCHAR column, which causes an implicit conversion on the column. Leading wildcards, like LIKE percent ABC, also prevent seeks.

The fix is to keep the column bare and move the logic to the other side. Instead of YEAR equals 2024, write CreatedOn greater than or equal to January 1st 2024 and less than January 1st 2025. Instead of LEFT, use LIKE 'ABC%'.

This exact issue was one of the causes of our slow shipment list, a CONVERT on the ShipmentDate column. Rewriting it as a date range was the first step in taking that query [from about 9 seconds to under 300 ms]. I can explain how to spot it in an execution plan.

@p1-47
Joins combine rows from two or more tables based on a related column, and the type of join decides what happens to rows that don't match.

An INNER JOIN returns only rows that match in both tables, like shipments with their site. A LEFT JOIN returns every row from the left table, plus matching rows from the right, with NULLs where there's no match. So "all sites, and their shipments if any". A RIGHT JOIN is the mirror image, and in practice we just rewrite it as a LEFT JOIN. A FULL OUTER JOIN returns all rows from both sides, matched where possible, which is useful for reconciliation. A CROSS JOIN returns every combination of rows, like every site with every kit type, handy for generating grids but dangerous on large tables. And a SELF JOIN joins a table to itself, like an employee table to find each person's manager.

A classic use of LEFT JOIN is finding missing data, you LEFT JOIN and then filter WHERE the right side IS NULL.

In our IRT work, I used exactly that to find sites with no shipments in the last 30 days, for a study team's resupply review. I can explain how joins relate to performance.

@p1-48
Normalisation organises a relational database to remove duplicate data, so each fact is stored in exactly one place. Denormalisation deliberately duplicates some data to make reads faster.

The normal forms build on each other. In first normal form, each column holds a single, atomic value, with no repeating groups. In second normal form, every non-key column depends on the whole primary key, not part of a composite key. In third normal form, non-key columns depend only on the key, not on other non-key columns. Like, a site's country name belongs in a countries table, not repeated on every shipment row. Normalisation prevents update anomalies, where you change data in one place and forget another.

Denormalisation trades that safety for read speed, fewer joins, precomputed values. It's common in reporting databases, read models in CQRS, and NoSQL stores like DynamoDB, where you design tables around access patterns.

So for me the balance is normalised for writes, denormalised for reads. In our IRT system, the transactional database is normalised, because data integrity is critical in clinical trials. But reporting views, and some read models fed by events, are denormalised for speed. I can explain how we keep them in sync.
