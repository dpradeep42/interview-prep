Polymorphism basically means "one interface, many forms". The same method call behaves differently depending on the actual object behind it.

In C# you get it in two flavours. Runtime polymorphism happens through virtual and override methods, or through interfaces, where the method that runs is decided at runtime based on the real type of the object. Compile-time polymorphism is method overloading, where the compiler picks a method by its parameters. Runtime polymorphism is the important one for design, because it lets code depend on an abstraction and lets new behaviour plug in without changing the caller.

My real example is the SFTP integration. The business code calls UploadAsync on an ISftpClient. Depending on the vendor's configuration, the Rebex, SSH.NET or ComponentPro implementation runs, and the calling code has no idea which one. When we added Rebex, nothing in the callers changed.

It also makes testing easy, because in unit tests I just pass a mock that implements the same interface. I can explain how dependency injection uses this too.

@p4-21
Abstraction means showing only what the user of a class needs to know, and hiding the complex details of how it works.

In C#, we usually express abstraction with interfaces and abstract classes. They describe the essential contract, the operations and their meaning, while the implementation details stay inside. It's slightly different from encapsulation, and people mix them up. Encapsulation is about protecting an object's data, while abstraction is about modelling a simple concept that hides complexity. Good abstractions make code easier to use, easier to test and easier to change.

Like, our ISftpClient interface only exposes a few things, connect, upload, download and list files. Behind it, each library deals with its own complexity, like different authentication APIs, key formats, timeouts and error types. Business code just thinks "send this file to the vendor", and doesn't care about any of that.

The trap is creating abstractions too early, or leaking details, like exposing library-specific exceptions through the interface. I mapped all provider errors to our own exception types to avoid that. I can show the interface design if useful.

@p4-22
A class is the blueprint, and an object is an actual instance created from that blueprint.

The class defines the type, what data it holds through fields and properties, and what it can do through methods. It's written once in code. An object is created at runtime with new, it has its own copy of the data in memory, and you can create as many objects from one class as you need. Changing one object's data doesn't affect the others, unless they share static members, which belong to the class itself rather than to any one object.

Like, Shipment is a class in our code. It defines properties like ShipmentId, Status and Destination, and methods like MarkDispatched. When EF Core loads ten shipments from the database, it creates ten Shipment objects, each with its own id and status.

I think the simplest analogy is the plan of a house versus actual houses built from that plan. I can also explain how classes differ from records and structs.

@p4-23
Both let one method name have multiple versions, but they work at different times.

Overloading means having several methods with the same name but different parameters in the same class, like a Log method that takes a string, and another that takes a string and an exception. The compiler picks the right one at compile time based on the arguments, so it's compile-time polymorphism. The return type alone isn't enough to overload.

Overriding means a derived class provides its own version of a virtual or abstract method from the base class, with the same signature. The decision is made at runtime, based on the actual object, even if you call it through a base-class reference. That's runtime polymorphism.

Let me give a real example. In our SFTP providers, the base class has a virtual method for building connection settings, and the Rebex provider overrides it to add its own key handling. Separately, we have overloaded upload methods, one taking a file path and one taking a stream.

I can also explain new versus override, which is a related trap.

@p4-24
So the virtual keyword goes on a base-class method to say derived classes are allowed to replace it. The override keyword goes in the derived class to actually replace it.

When you call a virtual method, the runtime looks at the actual type of the object, not the type of the variable. So even if I hold the object through a base-class reference, the derived override runs. Without virtual, a method can't be overridden at all. C# methods are non-virtual by default, which is a deliberate design choice for performance and safety. An override can call the base version with base dot method name, and it can be marked sealed to stop further overriding.

In our SFTP component, the base class has a virtual method that builds connection options with sensible defaults. The Rebex provider overrides it, calls the base version at the start, and then adds its specific settings. That way the shared defaults live in one place.

Abstract methods are similar but have no body, so derived classes have to override them. I can explain the difference between override and new as well.

@p4-25
Override and new both put a method with the same name in a derived class, but they behave very differently.

Override replaces a virtual method. Whichever reference you use, base type or derived type, the derived version runs, because it's decided at runtime by the actual object. That's normal polymorphism. The new keyword hides the base method instead, which is called method hiding. Then the version that runs depends on the declared type of the variable. Through a base-class reference the base version runs, and through a derived reference the new version runs. So the same object can behave differently depending on how you hold it.

That's confusing and honestly a common source of bugs, so I avoid it. If you forget both keywords, the compiler warns you that you're hiding a member, and in our projects we treat warnings as errors in CI.

The only legitimate use I've seen is when a base class you don't control adds a member with the same name as yours. I can show a small code example if you like.

@p4-26
A sealed class is a class that can't be inherited from. A sealed method is an override that can't be overridden again by classes further down the hierarchy.

Sealing communicates design intent. This class wasn't designed for extension, so nobody should depend on its internals by subclassing it. It also prevents subtle bugs where a subclass breaks the class's assumptions. There's a small performance gain too, because the JIT can devirtualise calls on sealed types. The string class is a well-known example of a sealed class. A sealed method is useful when you've overridden something carefully and want to lock that behaviour down.

In our code, we seal classes by default when they aren't meant to be inherited, which is most service classes, handlers and DTOs, and some analyzers even suggest it. If later we really need extension, we usually add an interface rather than unsealing.

Like, our concrete SFTP providers are sealed, while the shared base class is abstract, so the hierarchy is exactly one level deep. I can explain how that keeps the design simple.

@p4-27
The stack and the heap are two areas of memory that .NET uses in different ways.

The stack is per thread. It stores method call frames, parameters, local variables and return addresses. It works last-in, first-out, so it's extremely fast, and the memory is freed automatically when a method returns. The heap is shared memory where objects created with new live, mostly reference types. Objects on the heap stay until the garbage collector finds nothing references them.

A common misconception, and I've seen people get this wrong in interviews, is that value types always live on the stack. Actually, a value type lives where it's declared. A local int is on the stack, but an int field inside a class object is on the heap, as part of that object. And boxing moves a value type onto the heap.

In practice this matters for performance. Fewer heap allocations means less GC work. Like, when tuning CSV parsing, using Span of T to slice strings without allocating new ones reduced GC pressure noticeably. I can explain how the GC cleans up the heap if useful.

@p4-28
Boxing is when a value type, like an int or a struct, gets wrapped inside an object on the heap. Unboxing is pulling the value back out with an explicit cast.

Boxing happens implicitly, like when you assign an int to an object variable, put it in an old non-generic collection like ArrayList, or call an interface method on a struct through the interface. Each box is a new heap allocation, and it creates extra work for the garbage collector. Unboxing needs a cast to the exact type, or you get an InvalidCastException.

In normal business code it rarely matters, but in hot paths, like processing thousands of CSV rows or logging in a tight loop, it adds up. The fix is generics. List of int instead of ArrayList, generic methods instead of object parameters, and structured logging templates, which avoid boxing in newer .NET versions.

So my rule is simple, use generic collections and APIs, and watch allocations in a profiler when performance matters. I can talk about how I measure allocations if helpful.

@p4-29
IDisposable is the interface for objects that hold resources the garbage collector doesn't manage, like file handles, database connections, network streams or SFTP sessions. Its Dispose method releases them deterministically, right away, instead of waiting for the GC.

The using statement is the safe way to call Dispose. You write using, create the object, and put the code in a block, and Dispose is called automatically at the end of the block, even if an exception is thrown, because it compiles into try-finally. The newer using declaration, from C# 8, is just using var x equals something, without braces, and it disposes at the end of the current scope, which means less nesting. For async cleanup there's IAsyncDisposable with await using.

In our SFTP component, every connection is wrapped in a using, so sessions are always closed, even when a transfer fails halfway. With dependency injection, the container disposes scoped and transient services at the end of the request, so I don't dispose injected services myself. People get that wrong sometimes.

@p4-30
All three make a value unchangeable, but at different times and in different ways.

A const is a compile-time constant. It's implicitly static, and its value is copied into every assembly that uses it. So it has to be a simple literal, like a number or string, and if you change it, every calling assembly needs recompiling, otherwise they keep the old value. That one can catch people out. A readonly field can be set only in its declaration or in the constructor, so each object can have a different value, decided at runtime. A static readonly field is set once for the whole type at runtime, and it can hold any object, like a TimeSpan, a Regex or a list.

My rule is const only for values that are truly fixed forever, like a header name. Static readonly for shared defaults and objects, like a compiled Regex for validating study codes. Readonly for injected dependencies in constructors, which is the most common use in our services.

And for configuration that can change between environments, I use the Options pattern, not constants at all. Happy to explain that further.

@p4-31
ref, out and in are all ways to pass an argument by reference, instead of passing a copy.

With ref, the variable has to be initialised before the call, and the method can read and change it, and the caller sees the change. With out, the method has to assign a value before it returns, and the caller doesn't need to initialise it. The classic example is int.TryParse, which returns a bool for success and gives the parsed number through an out parameter. With in, you pass a read-only reference. The method can't change it, and the point is to avoid copying a large struct.

In everyday code I use out mostly for Try-pattern methods. Like, our CSV validator has a TryParseRow method that returns true or false and gives the parsed row as an out parameter, so we avoid exceptions for normal validation failures.

I use ref and in rarely, mostly in performance-sensitive code. Usually returning a result object or a tuple is clearer, I'd say. I can show an example if useful.
