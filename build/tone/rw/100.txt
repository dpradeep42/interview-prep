@p2-66
The main difference is how the application is built and deployed, as one unit, or as many independent services.

A monolith is a single deployable application. All features share one codebase, one process and usually one database. It's simple to develop, test and debug, calls between parts are fast in-process calls, transactions are easy, and there's one thing to deploy and monitor. The downsides show up at scale. The codebase can get tangled, one team's change means redeploying everything, you can only scale the whole application, and one bug can take everything down. Microservices split the application into independent services, each owning one business capability and its own data. Teams can deploy and scale their services independently, failures can be isolated, and each service can use the best technology. But you pay for that with network calls and their failures, distributed data and eventual consistency, and a lot more DevOps and observability work.

My view is that a well-structured modular monolith is often the right start, and microservices make sense when teams and parts of the system really need independence.

Our IRT platform is microservices, because many teams, [about 5] per release, work on clearly separate areas like randomisation, supply and shipments. I can explain how we keep it manageable.

@p2-70
The API gateway pattern puts a single entry point in front of a set of microservices, so clients don't need to know about each individual service.

The gateway handles cross-cutting concerns in one place, routing requests to the right service, authentication and token validation, rate limiting and throttling, TLS termination, CORS, logging, and sometimes caching and request aggregation, where it combines several service calls into one response for the client. Backend-for-frontend, or BFF, takes that further. Instead of one general gateway, each type of client gets its own thin backend. Like, the web app's BFF returns exactly what the web screens need, and the mobile BFF returns smaller payloads tuned for mobile. The front-end team often owns its BFF, so they can change it without affecting other clients. A BFF is also a good place to keep tokens server-side, instead of in the browser.

My rule is keep business logic out of the gateway. It should route and protect, not make business decisions, or it turns into a new monolith.

On AWS, that's API Gateway or an ALB. In the newer IQVIA services on AWS, the ALB routes to our services by path, and API Gateway gives per-partner throttling for external APIs. I can explain when a BFF is worth it.

@p2-71
The CAP theorem says that in a distributed system, when there's a network partition, meaning parts of the system can't talk to each other, you have to choose between consistency and availability. You can't fully have both.

Consistency means every read gets the most recent write, or an error. Availability means every request gets a response, even if it might be stale. Partition tolerance isn't really optional, because networks do fail. So the real choice is how the system behaves during a partition. A CP system refuses or delays some requests to stay correct. An AP system keeps answering, possibly with stale data, and reconciles later. When there's no partition, you can have both, and then it's latency versus consistency, which is the PACELC extension.

The useful bit, I think, is that you choose per feature, not for the whole system. In clinical trials, allocating limited drug kits or a randomisation slot has to be consistent, so it's CP. Better to fail and retry than to promise the same kit to two sites. But dashboards, notifications and reports can be AP. Slightly stale data is fine there, and availability matters more.

That's exactly how our IRT platform is designed, transactional SQL for allocation, eventually consistent events for everything around it. I can explain how we handle the stale data in the UI.

@p2-72
The saga pattern handles business transactions that span several microservices, where a single database transaction isn't possible.

The long transaction gets split into a sequence of local transactions. Each service does its part in its own database, and then publishes an event or triggers the next step. If a step fails, the saga runs compensating actions to undo the earlier steps. Say, reserve kits, create a shipment, notify the vendor. If the vendor rejects the shipment, compensations cancel the shipment and release the reserved kits. Compensations are business actions, not database rollbacks, and they have to be idempotent too.

You've got two styles. Choreography, where there's no central coordinator, each service listens for events and reacts, publishing its own events. It's simple for short flows, but the overall process gets hard to see and change. And orchestration, where a central orchestrator tells each service what to do next and tracks the state of the saga. It's easier to understand, monitor and change for complex flows, but the orchestrator is an extra component. AWS Step Functions or a durable workflow engine can play that role.

Sagas need the outbox for reliable events, idempotent consumers, and clear statuses so users see "pending" rather than inconsistent data. That's where people get bitten. I can sketch the shipment saga.

@p2-73
In a GxP system, the audit trail is a regulatory requirement, under rules like FDA 21 CFR Part 11, so it has to be complete, trustworthy and easy to review.

For every create, update and delete of regulated data, I'd record who did it, their user id and name, what changed, with the entity, old values and new values, when, with a synchronised UTC timestamp, where, like the source system or IP, and why, a reason for change where the process needs it. The audit store is append-only and tamper-evident. No user, not even admins through the application, can edit or delete audit records, and techniques like hash chaining or write-once storage can prove nothing was altered.

To capture changes consistently, I'd use an EF Core SaveChanges interceptor that looks at the change tracker and writes audit entries in the same transaction, so a change can't be saved without its audit. Business events, like "subject randomised", are audited explicitly too. Bulk operations that bypass the change tracker need their own auditing, which people forget. The audit data is stored separately, with retention matching regulatory requirements, and there's a search UI for auditors.

Our correlation id is also stored in audit records, which links an audit entry to the exact request and logs. I can explain the interceptor design.

@p2-74
I'd design rate limiting by deciding what to protect, who to limit, and where to enforce it.

The algorithm comes before anything. Fixed window is the simplest, like 100 requests per minute, but it allows bursts at window edges. Sliding window smooths that out. Token bucket allows short bursts, while enforcing an average rate, which suits most APIs. And concurrency limits cap how many requests run at the same time, which is good for expensive operations. Then the key, per user, per API key or client, per IP address for anonymous traffic, or per tenant. Then where. At the edge, API Gateway throttling and WAF rate rules stop abuse before it reaches services. In the application, ASP.NET Core's rate limiting middleware applies finer, per-endpoint policies. With multiple instances, in-app limits are per instance, so for a true global limit, I'd use a shared store, like Redis, with atomic counters.

And the response. Return 429 Too Many Requests with a Retry-After header, and well-behaved clients back off. Monitor rejections, so limits are tuned rather than guessed.

In the newer IQVIA services on AWS, partners get per-key limits at API Gateway, and in CIRT, our CSV import has a concurrency limit of [2] imports per user. I can explain the token bucket in detail.
