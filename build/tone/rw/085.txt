@p17-1008 | How do you capture and debug JavaScript errors in production with source maps?
Production JavaScript is minified, so a raw stack trace points to line one, column fifty thousand of a bundle full of random names, which is useless. Source maps map those positions back to the original TypeScript files and line numbers.

The setup has a few parts. Capturing errors is the starting point. An error tracking tool like Sentry, Datadog RUM or the Application Insights JavaScript SDK listens for unhandled errors and promise rejections, and frameworks have hooks too, like a React error boundary or Angular's ErrorHandler, to report errors the framework catches. Each report includes the browser, the route, the release version and recent user actions as breadcrumbs.

Then generate source maps in the production build, but don't serve them publicly if you don't want your source readable. Instead, upload them to the error tracking tool in the pipeline, tagged with the same release version as the deployed bundle. The tool then shows readable stack traces.

And link errors to releases, so you can see a new error started with version 2.4, and connect front-end errors to back-end traces by propagating trace headers on API calls.

Be careful with privacy, honestly this is the bit people skip. Scrub form values, tokens and personal data from error payloads and breadcrumbs before they leave the browser.

In our React shell with Vite, the pipeline uploads hidden source maps per release. When a sub-app started failing for one browser version, the readable stack trace pointed straight at an unsupported API call, which saved hours of guessing.

@p17-1009 | What is eBPF, and why is it used for observability?
eBPF lets small, verified programs run safely inside the Linux kernel, attached to events like system calls, network packets or function calls, without changing kernel code or restarting anything. For observability, that means you can see what processes are doing from the outside, without adding code to the application.

What it can show you. Network flows between pods, including latency and dropped connections. HTTP and gRPC requests parsed at the kernel level. DNS lookups. File and disk activity. CPU profiles across all processes. And security events like unexpected process launches.

Tools built on it include Cilium with Hubble for Kubernetes network visibility, Pixie and Grafana Beyla for automatic request metrics and traces, Parca and other continuous profilers, Falco for runtime security, and Datadog and other vendor agents, which use it for network monitoring.

The upside is no code changes, really low overhead, and visibility into things applications don't report, like a connection the network dropped or a slow DNS lookup.

The limits are real too, though. It's Linux only and needs a recent kernel and privileges. It sees bytes and calls, not business context, so it can't tell you which study or order a request belonged to. And encrypted traffic is harder to inspect, it needs hooks into TLS libraries.

So for me, eBPF is a complement to OpenTelemetry, not a replacement. It gives a baseline for every workload in a cluster, including ones nobody instrumented, while application instrumentation adds the business meaning.

@p17-1010 | What does 99.9 percent availability mean in downtime, and how do dependencies affect it?
Each extra nine cuts allowed downtime by ten. Ninety-nine percent allows about seven hours of downtime a month. 99.9 percent, three nines, allows about forty-three minutes a month, or under nine hours a year. 99.95 is about twenty-two minutes a month, and 99.99, four nines, only about four minutes a month, which is less than one manual deployment going wrong.

Dependencies multiply, and this is where people get caught. If a request needs three services in series, each 99.9 percent available, the combined availability is roughly 99.9 times 99.9 times 99.9, which is about 99.7 percent. So you can't promise a higher SLA than your critical dependencies allow, unless you take the dependency off the critical path.

Redundancy works the other way. Two independent instances, each 99 percent available, behind a load balancer give about 99.99 percent in theory, because both have to fail together. In practice, shared failure causes, the same bad deployment, the same database, the same region, reduce that benefit a lot.

So to improve availability, make fewer things critical. Cache data, use queues so a downstream outage delays work instead of failing requests, degrade gracefully when an optional service is down, and run across zones.

Also be precise about what availability measures. Is it uptime of a health endpoint, or successful user requests? Request-based SLIs are more honest. And scheduled maintenance windows often aren't counted in contractual SLAs, but users still feel them, which is one more reason I'd aim for zero-downtime releases.

@p17-1011 | How do you change log levels at runtime without redeploying?
During an incident you often want detailed debug logs from one component, but production runs at Information or Warning to control volume and cost. Redeploying just to change a log level is slow and risky, so the level should be changeable at runtime.

In ASP.NET Core, logging configuration reloads automatically when the configuration source changes. If levels come from appsettings with reload enabled, or from a central store like Azure App Configuration or a Kubernetes ConfigMap the app watches, changing a category's level takes effect within seconds. Serilog does the same through a logging level switch, which you can expose through a protected admin endpoint, and it can read level overrides from configuration.

In Node, pino lets you change the logger's level property at runtime, and in Python, you can call set level on a logger from a protected admin endpoint or a signal handler.

A few practices make this safe. Change the level for a specific category or namespace, not globally, so you don't flood the system. Add an automatic expiry, so debug logging turns off after, say, thirty minutes even if someone forgets. That expiry bit has saved us more than once, honestly. Protect the admin endpoint with strong authorization and audit who changed what. And make sure debug logs still don't contain secrets or personal data, since they'll be written in production.

Combining it with sampling helps too, debug logs for one tenant or one request header rather than all traffic. In our services, a temporary category-level override has helped diagnose integration issues without a release, which matters a lot when every release needs validation.

@p17-1012 | How do you monitor third-party APIs and external dependencies?
Look, many production incidents start outside your system. A partner API slows down, a payment provider has an outage, or a certificate on their side expires. You need to know quickly whether the problem's yours or theirs, and ideally before your users tell you.

Start with outbound telemetry. Every external call should produce metrics and spans, duration, status codes, timeouts and retries per dependency. HttpClient instrumentation in OpenTelemetry gives you this automatically, tagged by host. Dashboards per dependency show latency percentiles and error rates, and you can compare them with the vendor's own status page.

Add synthetic checks for critical dependencies, a scheduled call to a harmless endpoint, from where your services run, so you notice problems even when there's no traffic. Monitor certificate expiry dates and DNS resolution for external hosts as well.

Alert on your user impact first, then on the dependency. An alert saying the partner API error rate is above ten percent for five minutes, plus circuit breaker open events, helps on-call people go straight to the cause.

Know the contract. Rate limits, timeouts, maintenance windows and support contacts belong in the runbook. Log enough about failed calls, like the request id the partner returns, to raise a useful ticket, without logging sensitive payloads.

Design for failure too, timeouts, retries with backoff, circuit breakers and fallbacks. In our integrations with external partner systems, per-partner dashboards and request ids in logs turned arguments about whose fault something was into a quick, factual conversation.

@p17-1013 | How do you read a trace waterfall to find where the time is spent?
A trace waterfall shows every span of a request on a timeline. The root span at the top, child spans indented, and each bar's length showing its duration. Reading it well is a quick way to find the real cause of slowness.

I start with the root span's duration and compare it with what's typical, so I know I'm looking at a representative slow trace. Exemplars from a latency chart, or a filter for slow traces, help find one.

Then follow the critical path, the chain of spans that actually decided the end time. A long span running in parallel with others might not matter, while a short span repeated many times in sequence often does.

Common patterns kind of jump out visually. A staircase of many small database or HTTP spans one after another is an N plus one problem. A big gap with no child span means time spent in the service itself, CPU work, lock waits, garbage collection, thread pool starvation, or an uninstrumented call. Spans that could run in parallel but run one after another suggest missing concurrency. A span that waits a long time before starting, like a message sitting in a queue, shows backlog.

Then check span attributes and events, the SQL statement, retry counts, cache hit or miss, response size.

And compare it with a fast trace for the same endpoint. The difference between the two usually points straight at the cause. In our services, the gap pattern once led us to thread pool starvation from a synchronous call inside async code.

@p17-1014 | How do audit logs differ from application logs, and how long should you keep each?
Application logs are for engineers. Diagnosing errors, understanding behaviour and performance. They're high volume, can be sampled or dropped, and usually only need keeping for days or weeks, because nobody investigates a debug log from last year.

Audit logs are for accountability. Who did what, to which record, when, and sometimes why. They're a business and compliance record, so they have to be complete, accurate and tamper-evident, and kept as long as regulations or contracts require, which can be many years in regulated industries.

That difference drives the design. Audit records shouldn't depend on the logging pipeline, which might drop messages under load. They're usually written in the same database transaction as the change, or through an outbox, so a change can't happen without its audit record. They're append-only, with permissions that stop even administrators from editing them, and ideally protected with hashing or write-once storage. They hold old and new values and the user identity, and they're designed to be queried by business users and auditors.

Application logs go to tools like Splunk, Datadog or CloudWatch, with retention set by cost and need, often thirty to ninety days hot, with older data archived cheaply if required.

Both need data protection. Personal data in application logs should be minimised or masked, while audit logs, which might need personal data, need strict access control.

In a GxP system, I'd say the audit trail is a validated feature of the product, not a side effect of logging, and treating it that way avoids a lot of findings.

@p17-1015 | How do you add observability to AWS Lambda functions?
Lambda functions are short-lived and there's no server to put an agent on, so observability is built into the function and the platform.

Logs go to CloudWatch Logs automatically. Write structured JSON logs with the request id and a correlation id, and use the advanced logging controls to set JSON format and log levels without code changes. Set a log retention period, because the default is keeping logs forever. People miss that and the bill creeps up.

Metrics come from the platform for free, invocations, errors, duration, throttles, concurrent executions, and for queue triggers, iterator age or queue metrics. Custom business metrics are best written with the Embedded Metric Format, which turns log lines into metrics without extra API calls.

Tracing can use X-Ray, turned on with one setting, or OpenTelemetry through the AWS Distro for OpenTelemetry Lambda layer, which can send to X-Ray or to a vendor like Datadog. Trace context should flow from API Gateway or the message attributes, so a request is traceable end to end.

Powertools for AWS Lambda, available for Python, TypeScript, .NET and Java, packages all of this. Structured logging with context, metrics with EMF, tracing helpers, plus idempotency and batch failure handling.

Alerts I always set, error rate, throttles, duration close to the timeout, dead-letter queue depth, and iterator age for streams. Lambda Insights adds memory and CPU detail if needed.

Cold starts deserve a dashboard too, because a sudden jump in init duration after a dependency upgrade is a really common surprise.

@p17-1016 | What is the inbox pattern for processing each message only once?
Most brokers, RabbitMQ, SQS, Service Bus, deliver messages at least once. A consumer might get the same message twice after a timeout, a lost acknowledgement or a redelivery. And if processing has side effects, like reserving stock or sending an email, duplicates do real damage.

The inbox pattern makes the consumer idempotent. Every message carries a unique message id. The consumer has an inbox table, or processed messages table, keyed by that id. When a message arrives, in one database transaction the consumer inserts the message id into the inbox and does its business changes. If the insert fails because the id already exists, the message was already processed, so the consumer just acknowledges it and does nothing else. Because both happen in one transaction, you can't end up with the change done but not recorded, or recorded but not done.

It pairs naturally with the outbox pattern on the producer side. The outbox guarantees the message gets published, and the inbox guarantees it's processed once.

Details to handle, clean old inbox rows after a retention period longer than any possible redelivery. And for side effects outside the database, like calling an external API, pass an idempotency key so the other system can deduplicate too.

Libraries like MassTransit and NServiceBus include inbox and outbox support. In our RabbitMQ consumers, a processed message table per database made retries from the dead-letter flow safe, because replaying a message twice simply has no effect the second time. That's pretty much the whole point.

@p17-1017 | How do you implement a distributed lock, and when should you avoid one?
A distributed lock makes sure only one instance across many servers does something at a time, like running a scheduled job, refreshing a shared token or processing one customer's batch.

Common ways to do it. Redis with SET using NX and an expiry, where the value's a unique token so only the owner can release it. SQL Server's sp_getapplock, which is simple if you already have a database and is released automatically with the session or transaction. Blob leases in Azure Storage. DynamoDB conditional writes. Or ZooKeeper and etcd for stronger guarantees. Libraries like DistributedLock for .NET wrap several of these.

The hard part is that locks expire. If the holder pauses, say a long garbage collection or a network delay, its lock can expire while it still thinks it owns it, and a second instance starts the same work. The fix is a fencing token, an increasing number issued with each lock, which the protected resource checks, rejecting writes with an older token. Redis-based locks can't fully guarantee safety without that.

So honestly, I avoid distributed locks where I can. Often a better design exists. A database unique constraint, optimistic concurrency with a row version, partitioning work so each key always goes to one consumer, a single active consumer queue, or a scheduler with built-in clustering, like Quartz.NET with a clustered job store.

When I do use one, I treat it as an efficiency mechanism, preventing duplicate work, and make the work itself idempotent, so a rare double run is still safe.

@p17-1018 | Should microservices share common libraries, and what should go in them?
Sharing code across services saves duplication, but a shared library is also a kind of coupling. If every service has to upgrade together whenever it changes, you've basically built a distributed monolith through a NuGet or npm package.

What's good to share is technical, cross-cutting plumbing that rarely changes. Logging and OpenTelemetry setup, standard health checks, authentication configuration, a resilient HTTP client setup, error response formats, and messaging conventions. People often call this a service chassis, and it makes services consistent.

What shouldn't be shared is domain logic and domain models. If two services share a customer entity class, a change for one forces a change in the other, and the service boundaries stop meaning anything. Each service should own its models. For contracts between services, share schemas or generated clients, versioned carefully, not internal classes.

Practices that keep sharing healthy. Version libraries with semantic versioning and keep breaking changes rare. Don't force simultaneous upgrades, services should be able to lag behind for a while. Keep packages small and focused, rather than one giant common package. Avoid heavy transitive dependencies that dictate framework versions. And have a clear owner who reviews changes.

In our front-end work, shared npm packages on the Azure DevOps feed hold the design system, API client and auth helpers for the React shell and sub-apps. They're versioned independently, and a sub-app can stay on an older version until its team's ready, which avoids coordinated big-bang upgrades.

@p17-1019 | How does request-reply over a message broker work?
Sometimes you want the decoupling of a broker but you still need an answer, like asking a pricing service to calculate a quote. Request-reply over messaging does that.

The requester sends a message to the service's request queue with two extra properties. A reply-to address, which is a queue where it listens for answers, and a correlation id that's unique to the request. The responder processes the message and sends the result to the reply-to queue with the same correlation id. The requester matches the reply to the waiting request by that correlation id.

The reply queue can be one temporary exclusive queue per requester instance, or RabbitMQ's direct reply-to feature, which avoids creating queues. In Azure Service Bus, sessions are often used, with the session id matching the request.

Important points. Always set a timeout, because a reply might never arrive. Messages can be delivered twice, so the responder should be idempotent. If the requesting instance restarts, pending replies are lost, so this suits short, interactive requests, not long processes.

And I'd always ask whether you really need it. If the caller blocks waiting for the reply, you get the latency of the broker and most of the coupling of a direct call. For real-time answers, a direct HTTP or gRPC call is usually simpler. Request-reply over a broker makes sense when the responder has to sit behind the broker, for load levelling or network reasons, or when the reply can be processed asynchronously, like an event updating status later.
