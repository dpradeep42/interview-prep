Ansible is an automation tool for configuring servers and deploying software. It's agentless, so it connects over SSH to Linux machines, or WinRM to Windows, and runs tasks defined in YAML playbooks, organised into reusable roles.

In our environment, we used Ansible together with Python and Shell scripts to install releases across multiple nodes, copying artifacts, stopping and starting services, updating configuration, and running checks, the same way on every server. Idempotency is basically the core Ansible idea. An idempotent task can run many times and always leaves the system in the same final state. So these are three ways of releasing a new version with minimal risk and downtime.

A rolling deployment replaces instances gradually. Start a new instance, wait till it's healthy, then stop an old one, and repeat. It needs little extra capacity and it's the default on ECS and Kubernetes. The downside is that old and new versions run side by side for a while, so they have to be compatible, and rolling back means another rolling deployment. Blue-green runs two complete environments. Blue serves production, and you deploy the new version to green, test it there, then switch all traffic at once, usually at the load balancer. Rollback is instant, you just switch back. The cost is double the resources during the switch, and database changes have to work for both. Canary sends a small percentage of real traffic to the new version, like 5 percent, while you watch error rates and latency. If metrics stay healthy, you increase gradually to 100 percent. If not, you roll back, and only a small share of users were affected.

My choice depends on risk. Rolling for routine changes, blue-green when I want instant rollback, and canary for high-risk changes where we have good metrics.

Our ECS services use rolling deployments with health checks and automatic rollback. I can explain how we handle database changes with each.

@p2-30
Rollback with database changes is tricky, because you can redeploy old code in minutes, but you can't easily "undeploy" a schema change, especially if new data was written.

So my main strategy is to keep rollback of the code always possible, by keeping schema changes backward compatible. That's the expand and contract pattern. In the first release, we only expand, add new columns or tables, nullable or with defaults, and never remove or rename anything the old version uses. The new code uses the new structure. If we roll back, the old code still works, because everything it needs is still there. Only in a later release, once the new version is proven, do we contract, removing old columns.

Other safeguards too. Keep the previous artifact and release tag ready to redeploy. Use feature flags, so new behaviour can be switched off without a deployment. Take a backup or snapshot before risky migrations. Have tested down scripts for changes that really need reversing. And document the rollback plan in the release, with clear decision criteria and who decides.

In a GxP release, the rollback plan is part of the change record, reviewed before release. In practice, with expand and contract, we've never needed to reverse a schema change, rolling back code was enough. I can explain how this works with EF Core migrations.

Logs, metrics and traces are the three pillars of observability. Each one answers a different question about a running system.

Logs are detailed records of individual events, like "shipment 123 failed validation", with context like the user, the correlation id and the error. They answer "what exactly happened?" They're best as structured JSON, so they can be searched and filtered, and in our case they go to Splunk from the CIRT services, through Serilog, and to CloudWatch Logs from our AWS services. Metrics are numbers measured over time, request rate, latency percentiles, error rate, CPU, memory, queue depth. They're cheap to store and fast to query, so dashboards and alarms are built on them. They answer "is something wrong, and how bad is it?" Traces follow a single request across all the services it touches, with timing for each step. They answer "where in the chain is the problem?", like which service or database call made a request slow.

You really need them together. An alarm on a metric tells me error rates are up. A trace shows which service is failing. And the logs for that request, found by its correlation id, show the actual error.

@p2-34
The golden signals are four metrics, from Google's SRE practices, that tell you whether a service is healthy from the user's point of view.

Latency is how long requests take. I track percentiles, like p95 and p99, not just the average, because the average hides the slow requests that users actually complain about. It's also worth separating the latency of successful and failed requests, since fast errors can make latency look good. Traffic is how much demand the system is handling, like requests per second, or messages per second for a queue consumer. Errors is the rate of failing requests, 5xx responses, exceptions, and for messaging, dead-lettered messages. Saturation is how full the system is, CPU, memory, database connection pool usage, thread pool queues, or queue depth. Saturation often warns you before latency and errors get worse.

Put together, they give you a quick, reliable picture of any service, and they're a good basis for alerts and service level objectives.

In our Grafana dashboards, every service has these four right at the top. For RabbitMQ consumers, saturation means queue depth and consumer lag, which is honestly what warned us early in later broker issues. I can explain how we set alert thresholds on them.

Root-cause analysis has two phases for me. Stabilise the system, then understand why it happened, so it doesn't happen again.

Stabilise before anything else. Mitigate the user impact as quickly as possible, by rolling back a deployment, scaling out, failing over, or disabling a feature with a flag, and keep stakeholders informed. The full investigation can wait, users can't. Then gather evidence. Build a timeline of when it started, what changed just before, like a deployment, configuration or traffic pattern, and what the dashboards, logs and traces show. Logs filtered by correlation id from affected requests are really useful. Then form hypotheses and test them against the evidence, instead of jumping to conclusions. I use the 5 Whys technique to get past the symptom. Like, the API timed out, why? The database was slow, why? A query was scanning, why? A new filter was non-SARGable, why wasn't it caught? No performance check for that query. The last answer is usually the real fix.

After that, fix the root cause, add monitoring or tests so it can't recur silently, and write a blameless post-incident review with clear actions and owners.

A good alert, for me, is one that someone should act on right now, and knows how to act on.

It has to be actionable. When it fires, there's a clear action, ideally documented in a linked runbook, what it means, how to check, and how to mitigate. If the honest response is "ignore it", it shouldn't be an alert. It should be based on user impact, not internal noise. Alert on symptoms, like error rate or latency above a threshold, sustained for several minutes, rather than on a single CPU spike that resolves on its own. It goes to the right owner with the right severity. A critical production issue pages the on-call person, while a warning goes to a team channel or a ticket. And alerts get reviewed regularly. If an alert fires often and nobody acts, it's either tuned or deleted, because alert fatigue makes people ignore the important ones.

@p2-37
RabbitMQ and Kafka are both used for messaging, but they're built on pretty different models.

RabbitMQ is a traditional message broker. Producers publish to exchanges, which route messages to queues using bindings and routing keys. Consumers take messages from queues, acknowledge them, and then the message is removed. It has very flexible routing, per-message acknowledgements, priorities, and dead-letter queues, so it's excellent for task queues, commands, and work distribution, where each message should be processed once by one worker. Kafka is a distributed, partitioned, append-only log. Producers write events to topics, and the events are kept for a retention period, whether they've been read or not. Consumers track their own position, called the offset, so many independent consumer groups can read the same events, and you can replay history. It gives you ordering within a partition and very high throughput.

So I go with RabbitMQ for commands and work queues with complex routing, and Kafka for event streaming, when several services need the same events, or replay, retention and high volume matter.

In our platform, RabbitMQ handles service-to-service workflows like shipment processing. I can explain how we made publishing reliable after our [mid-2024] incident, which applies to both.

@p2-38
These are the three core concepts that give Kafka its scalability and ordering, basically.

A topic is a named stream of events, like "shipment-events". Each topic is split into partitions. A partition is an ordered, append-only log, where each event gets a sequential offset. Partitions are spread across brokers, which is how Kafka scales. When producing, the producer picks the partition, usually by hashing the message key. So all events with the same key, like the same study id or shipment id, always go to the same partition, and stay in order. Ordering is only guaranteed within a partition, not across the whole topic. People mix that up a lot.

A consumer group is a set of consumers that share the work of reading a topic. Each partition is read by exactly one consumer in the group at a time. So if a topic has six partitions, up to six consumers in a group can work in parallel, and a seventh would just sit idle. The partition count limits parallelism. Different consumer groups read the same topic independently, each with its own offsets. When consumers join or leave, Kafka rebalances partitions among them.

Consumers commit offsets after processing, so after a restart they carry on where they left off. I can explain how to choose a good partition key.

@p2-39
In RabbitMQ, producers never publish straight to a queue. They publish to an exchange, and the exchange type decides how messages get routed to the queues bound to it.

A direct exchange routes by exact match. A message with routing key "shipment.created" goes to queues bound with exactly that key. It's good for commands and simple point-to-point routing. A topic exchange routes by pattern. Routing keys are dot-separated words, and bindings can use wildcards, a star matches exactly one word, and a hash matches zero or more. So a queue bound with "shipment.*.created" gets created events from any region. It's the most flexible and honestly the one I use most. A fanout exchange ignores the routing key and copies every message to all bound queues, which is a simple broadcast, like telling several services that reference data changed. A headers exchange routes on message header values instead of the routing key, which you rarely need.

There's also the default exchange, which routes to a queue with the same name as the routing key.

In our platform, we use topic exchanges for domain events, like shipment status changes, so each consuming service binds only to the event patterns it cares about. I can explain how dead-letter exchanges fit in.
