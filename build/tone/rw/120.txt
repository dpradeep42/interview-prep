Fargate is basically AWS's serverless compute engine for containers. It works with both ECS and EKS, and it means you run containers without managing any servers.

Normally, to run containers on ECS, you need a cluster of EC2 instances. You choose instance types, patch the operating system, scale the instances, and pack containers onto them efficiently. AWS Lambda is serverless compute for running code in response to events, without managing any servers.

You upload a function, in .NET, Node, Python and others, and configure what triggers it, like an API Gateway request, a file uploaded to S3, messages in an SQS queue, changes in a DynamoDB stream, or a schedule. AWS runs the function when an event occurs, scales automatically from zero to thousands of concurrent executions, and you pay only for the number of requests and the execution time. Each invocation can run for up to 15 minutes, and you configure memory, which also scales the CPU.

The downsides are cold starts, the delay when a new execution environment starts, which matters for latency-sensitive APIs, although SnapStart and provisioned concurrency help. Then the 15-minute limit. And it's stateless, so state has to live elsewhere. For constant high traffic, containers can be cheaper.

So honestly, Lambda is great for event-driven glue, scheduled jobs and spiky workloads. In the newer IQVIA services on AWS, Lambda handles some event-driven pieces, like reacting to files landing in S3 and lightweight scheduled tasks, while the core services run on ECS. I can explain how we handle errors with dead-letter queues.

@p5-69
Lambda concurrency is just the number of executions of your functions running at the same time.

Each concurrent execution needs its own execution environment. If a function takes one second and receives 100 requests per second, it needs about 100 concurrent executions. By default, an AWS account has a regional limit, usually 1,000 concurrent executions shared by all functions. If that's reached, extra requests are throttled. For synchronous callers, they get a 429 error, and for async sources like SQS, the event is retried later.

You get two controls. Reserved concurrency sets aside a portion of the account limit for one function. It guarantees that function capacity, and also caps it, which is useful to protect a downstream database from being overwhelmed by thousands of parallel connections. Provisioned concurrency keeps a number of execution environments initialised and warm, which removes cold starts for latency-sensitive functions, at an extra cost.

Concurrency matters a lot when a Lambda talks to a relational database, honestly. Without a cap, a burst of events can open too many connections. So I set reserved concurrency, or use RDS Proxy for connection pooling. I can explain how SQS batch processing interacts with this.

@p5-70
The Lambda timeout is the maximum time a single invocation is allowed to run before AWS stops it. You can set it from 1 second up to 15 minutes, and the default is only 3 seconds, which people forget.

When the timeout is reached, the function is stopped, and the invocation fails. For synchronous callers, that's an error. For asynchronous events, Lambda retries, and with SQS the message becomes visible again and may be retried. So any work it did before the timeout has to be safe to repeat, which means idempotency.

How I set it is a little above the realistic maximum duration, not the maximum allowed, so a stuck call fails fast instead of burning money. It also has to fit with the surrounding timeouts. Like, API Gateway has a 29-second integration timeout by default, so a Lambda behind it doesn't benefit from a 10-minute timeout. And for SQS, the queue's visibility timeout should be longer than the Lambda timeout, or messages get processed twice.

For work that genuinely takes longer than 15 minutes, Lambda is the wrong tool. I'd use Step Functions to split it into steps, or a container task on ECS. I can explain how we handle a timeout mid-process.

@p5-71
DynamoDB is AWS's fully managed NoSQL database. It stores data as key-value items and documents, and gives you consistent single-digit millisecond latency at practically any scale.

Each table has a primary key, either just a partition key or a partition key plus a sort key. The partition key decides which partition stores the item, so data spreads across many servers automatically, and the sort key orders items within a partition, which allows efficient range queries, like all events for a shipment in time order. You can add secondary indexes for other access patterns. It's serverless, there are no servers to manage, and you choose on-demand capacity, paying per request, or provisioned capacity. It also has Streams for change events, TTL to expire items automatically, transactions, and global tables for multi-region replication.

The key difference from SQL is design, I'd say. You design the table around your access patterns, up front. It's very fast for known lookups, but poor at ad-hoc queries and joins.

In the newer IQVIA services on AWS, the core relational data stays in SQL Server, and DynamoDB is used for simpler, high-volume data like status and event lookups. I can explain partition key design and hot partitions.

@p5-72
Both are secondary indexes in DynamoDB that let you query data by something other than the table's primary key, but they work differently.

A Global Secondary Index, or GSI, can have a completely different partition key and sort key from the table. Say the table is keyed by ShipmentId, and a GSI is keyed by SiteId and ShipDate, so you can query all shipments for a site. It can be created or deleted at any time, it has its own capacity settings, and it's updated asynchronously, so reads from it are eventually consistent. A Local Secondary Index, or LSI, keeps the same partition key as the table, but uses a different sort key. Like, the same ShipmentId partition, but sorted by status instead of date. It has to be created when the table is created, it supports strongly consistent reads, and it shares the table's capacity. It also limits each partition key's data to 10 GB.

In practice, GSIs are much more common, because they're flexible and can be added later as new access patterns appear. LSIs are kind of niche, used when you need strong consistency on an alternative sort order.

When designing, I list the access patterns first, then decide which are served by the table and which need a GSI. I can explain GSI overloading.

RDS, Relational Database Service, is AWS's managed service for relational databases. It supports SQL Server, PostgreSQL, MySQL, MariaDB, Oracle, and Aurora.

With RDS, AWS takes care of the boring undifferentiated work, provisioning, operating system and database patching, automated backups with point-in-time recovery, monitoring, and high availability. @p5-74
Redis and a database do different jobs, and honestly they usually work together rather than replacing each other.

Redis is an in-memory data store. Because data lives in memory, reads and writes take well under a millisecond. It has rich data structures, like strings, hashes, lists, sets and sorted sets, and built-in expiry with TTL. That makes it ideal for caching, session data, rate limiting counters, distributed locks, leaderboards and short-lived tokens. But it's not designed to be the system of record. Persistence is optional, memory is expensive, and it doesn't support relational queries or rich transactions. A database, like SQL Server, is the durable source of truth. It stores data safely on disk, supports complex queries, joins, constraints and ACID transactions. It's slower per operation, but correct and complete.

The common pattern is cache-aside. Check Redis first, and on a miss, read from the database and store the result in Redis with an expiry. The hard part is invalidation when data changes.

In the newer IQVIA services on AWS, ElastiCache Redis caches reference data, and in CIRT, our on-premise Redis holds the token denylist, which our APIs check in about [1 ms] on every request. The real data stays in SQL Server. I can explain the token denylist design.

I secure S3 in layers, starting from "nothing is public unless it really needs to be".

Access comes before anything. Block Public Access is turned on at the account and bucket level. IAM, Identity and Access Management, controls who can do what on which AWS resources. It's made of identities, like users, groups and roles, and policies, which are JSON documents that allow or deny specific actions on specific resources.

An IAM user is a long-term identity, with permanent credentials like a password or access keys. Historically used for people, but today, for humans, we prefer single sign-on through IAM Identity Center, so there are no long-lived keys to leak. An IAM role is an identity without permanent credentials. It's assumed by someone or something, and AWS issues temporary credentials that expire automatically. Roles are used by services, like an ECS task role or a Lambda execution role, for cross-account access, and for federated users.

So roles are almost always preferred, for me. Temporary credentials rotate automatically and can't be accidentally committed to git. Long-term access keys are a common cause of security incidents.

In the newer IQVIA services on AWS, every ECS service has its own task role, with least-privilege policies, like read access to one S3 prefix and one secret. No service has access keys in its configuration. I can explain how the SDK finds those credentials.

CloudWatch Logs and CloudWatch Metrics are both part of AWS's monitoring service, you know, but they answer different questions.

Logs are detailed records of individual events, each request, error or business action, with all its context. They're great for investigating what happened, especially with structured JSON logs. CloudWatch Logs Insights lets you query them, like filtering by correlation id, or counting errors by type. Metrics are numeric time series, CPU usage, request count, latency, error rate, queue depth, measured over time. They're cheap to store, fast to graph, and they're what alarms and autoscaling work on. AWS services publish lots of metrics automatically, and you can publish custom ones, like shipments processed.

They connect through metric filters, which turn patterns in logs into metrics. Say, counting log lines with level Error, so you can alarm on them. The embedded metric format lets you write metrics inside log lines.

In practice, metrics and alarms tell me that something is wrong, and logs tell me why. In the AWS-side services, alarms on ALB 5xx rates and latency point us to a problem, and then a Logs Insights query by correlation id shows exactly which request failed and where. I can show a sample query.
