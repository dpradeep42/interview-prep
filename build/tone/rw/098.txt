These are the three delivery guarantees a messaging system can give you, and each one is a balance between losing messages and duplicating them.

At-most-once means a message is delivered once or not at all. There are no retries, so if something fails along the way, the message is gone. It's only okay for data where loss doesn't matter, like some metrics. At-least-once means the system keeps retrying until the message is acknowledged, so nothing is lost. But if a consumer processes a message and crashes before acknowledging, it'll get it again, so duplicates are possible. That's why consumers have to be idempotent. Exactly-once means no loss and no duplicates. It's only truly available within limits, like Kafka transactions for read-process-write inside Kafka. Across different systems, like a broker and a database, you get it "effectively" through at-least-once delivery plus idempotent processing.

In practice, I'd say at-least-once with idempotent consumers is the standard choice for business data.

That's how our platform works. Publishing uses confirms, so the broker definitely has the message, consumers acknowledge only after successful processing, and every message has an id, which consumers use to skip duplicates. I can explain how to make a consumer idempotent.

@p2-42
An idempotent consumer gives the same result whether it processes a message once or several times. With at-least-once delivery, duplicates will happen, so you really need this.

There are a handful of techniques, and I often combine them. Every message carries a unique message id. The consumer keeps an inbox table of processed ids, and skips any message it's already seen. The key detail is that the insert into the inbox table and the business update happen in the same database transaction, so either both get saved or neither does. Then there's natural idempotency, designing operations so repeating them is harmless. "Set shipment status to Delivered" is idempotent, while "increment delivered count" isn't. Upserts instead of inserts, and unique constraints, help too. And for ordering problems, a version or timestamp check, so an older event can't overwrite newer data.

Then the failure path. Retry transient errors with backoff, and after a few attempts move the message to a dead-letter queue, instead of retrying forever.

Honestly, this property saved us in our RabbitMQ incident in [mid-2024]. Because consumers upsert, I could safely replay a whole window of vendor files without creating duplicates. I can explain that recovery.

@p2-43
A dead-letter queue, or DLQ, is a separate queue where messages go when they can't be processed successfully, so they don't block the main queue or get lost.

Messages usually end up there because processing keeps failing after a set number of retries, say because of bad data or a bug, or the message is explicitly rejected, or it expires. Without a DLQ, a "poison message" that always fails can get retried forever, blocking other messages or burning resources. With a DLQ, it's moved aside, and normal processing carries on.

In RabbitMQ, you configure a dead-letter exchange on the queue, and rejected or expired messages get routed there. With quorum queues, you can also set a delivery limit. In Kafka, there's no built-in DLQ, so the consumer publishes failed messages to a retry topic or a dead-letter topic itself. In AWS SQS, you configure a redrive policy with a maximum receive count.

My rule is that a DLQ should never be silent. We alert on any message in a DLQ, someone inspects it, fixes the cause, and then replays the messages back to the main queue. Our consumers are idempotent, so replaying is safe. I can explain our replay process.

So the transactional outbox pattern solves a really common reliability problem in microservices, updating your database and publishing an event as one reliable step.

The problem is that the database and the message broker can't share one transaction. If you save the change and then publish, the publish might fail after the commit, and other services never hear about it. If you publish first and then the save fails, other services react to something that never happened. Either way, systems disagree.

The outbox pattern fixes this. In the same database transaction as the business change, you also insert a row into an outbox table, containing the event. Because it's one local transaction, either both get saved or neither does. Then a separate background relay reads unpublished rows from the outbox, publishes them to RabbitMQ or Kafka, and marks them as published. If publishing fails, it just retries later. That gives you at-least-once publishing, so consumers have to be idempotent. The relay can poll the table, or use change data capture with a tool like Debezium.

In our shipment flow, the shipment update and its outbox event are saved together, and a background service publishes them with publisher confirms. If the broker's down, events just wait. I can show the table design.

Authentication and authorization are two separate questions, and they always happen in that order.

Authentication answers "who are you?" It's proving identity, like logging in with single sign-on, or an API validating a token's signature, issuer, audience and expiry, and then knowing the user's identity and claims. Authorization answers "what are you allowed to do?" It's checking permissions, through roles, claims, policies, and resource-level checks, like "can this user see this specific study?"

In ASP.NET Core, they're two middleware. UseAuthentication runs first and sets HttpContext.User, then UseAuthorization evaluates the Authorize attributes and policies on the endpoint. The status codes show the difference too, and people mix these up. 401 Unauthorized actually means not authenticated, no valid token. 403 Forbidden means authenticated, but not allowed.

In our clinical system, authorization is the harder and more important part. A user with a valid login and the right role still mustn't see data from a study they're not assigned to. So beyond roles, we have resource-based checks on every request that touches study data. Missing that kind of check is the number one API risk in the OWASP list. A JWT, or JSON Web Token, is a compact, signed token that carries claims about a user. It's got three parts, separated by dots, each base64url-encoded.

The header says which algorithm was used to sign it, like RS256, and which key. The payload has the claims, sub for the user id, roles or scopes, iss for who issued it, aud for which API it's meant for, exp for when it expires, and so on. The signature is created by the identity provider with its private key, over the header and payload.

To validate it, the API checks the signature using the issuer's public key, usually downloaded from its JWKS endpoint, which proves the token wasn't tampered with and came from the trusted issuer. Then it checks the issuer and audience match what's expected, and that the token isn't expired or used before its not-before time, allowing a small clock skew. Only then are the claims trusted.

Two things people forget. A JWT is signed, not encrypted, so anyone can read the payload, never put secrets or personal data in it. And because it's validated without a server call, it can't be revoked easily. That's why we keep access tokens short, [15 minutes], and added a denylist for logout. I can explain that fix.

The authorization code flow with PKCE is the recommended way for apps to log users in with OpenID Connect and get tokens to call APIs.

The app starts by creating a random secret called the code verifier, and sends a hashed version of it, the code challenge, when it redirects the user to the identity provider's login page. The user logs in there, through single sign-on, and the app never sees their password. The identity provider then redirects back to the app with a short-lived, one-time authorization code. The app exchanges that code at the token endpoint, sending the original code verifier. The provider checks that the verifier matches the challenge, which proves the same app that started the login is finishing it, so a stolen code is useless. It then returns tokens, an access token, which is the OAuth part, for calling APIs, an ID token, which is the OpenID Connect part, saying who the user is, and often a refresh token.

PKCE was originally for mobile and single-page apps that can't keep a client secret, but honestly it's now recommended for all clients, and it replaces the old implicit flow.

Our web apps use this flow with Keycloak, our single sign-on identity provider, and our APIs validate the access tokens. I can explain how refresh tokens fit in.

Reverse tabnabbing is a phishing attack that abuses links opening in a new tab.

When a page opens a link with target equals blank, historically the new page got a reference back to the original page through window.opener. A malicious or compromised external site could then use window.opener.location to quietly redirect the original tab, say to a fake login page that looks exactly like ours. The user finishes reading the new tab, goes back to what they think is our app, sees "your session expired, please log in", and types their credentials into the attacker's page.

The fix is to add rel equals noopener noreferrer to links with target blank. noopener removes the window.opener reference, and noreferrer also stops the referrer header from leaking our URL. For links opened in JavaScript, use window.open with the noopener feature. Modern browsers now treat target blank as noopener by default, but I think being explicit is still best practice, and security scanners flag it anyway. A Cross-Origin-Opener-Policy header adds another layer.

I actually fixed this in IRT. A security scan flagged it, and I updated [about 40] external links, created a shared link component that sets rel by default, and added a lint rule so it can't come back. I can show the lint rule.
