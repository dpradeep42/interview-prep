Both resolve a service from the DI container, but they behave differently when the service isn't registered.

GetService returns null if the service isn't registered. So it's meant for optional services, where the caller handles the null case. GetRequiredService throws an InvalidOperationException with a clear message naming the missing type. So it's for services that have to exist. GetRequiredService is an extension method on IServiceProvider, and there's a generic version of each.

I prefer GetRequiredService, because failing fast with a clear message is much easier to diagnose than a NullReferenceException somewhere later. With GetService, a forgotten registration can turn into a confusing null error in a completely different place. ASP.NET Core also validates the whole container at startup in development, which catches missing registrations early.

But honestly, I rarely call either one. In normal code I use constructor injection. I only call GetRequiredService in factories or after creating a scope in a background service, like to get a fresh DbContext for each message in our consumer. In ASP.NET Core, a controller just declares what it needs as constructor parameters, and the framework supplies them for every request.

When a request comes in, ASP.NET Core creates a DI scope for it, available as HttpContext.RequestServices. The controller activator then creates the controller from that scope. The container looks at the constructor, picks the one with the most parameters it can satisfy, and resolves each dependency, and their dependencies, recursively, building the whole object graph. Scoped services, like DbContext, are shared by everything in that one request. When the request ends, the scope is disposed, along with the scoped and transient disposables.

Minimal APIs work the same way but inject straight into the handler's parameters, and in controllers I can use the FromServices attribute to inject into a single action.

Like, our shipments controller takes an IShipmentService and a logger. The service takes the DbContext and a publisher. One request, one DbContext, shared by both, and disposed at the end. That's basically it. I can explain the lifetime rules that make this safe.

@p4-60
So the service locator anti-pattern is when a class pulls its dependencies from the container itself, typically by injecting IServiceProvider and calling GetService inside its methods, instead of declaring them in the constructor.

It's called an anti-pattern because it hides the real dependencies. Looking at the constructor, you can't tell what the class needs, so the API kind of lies. Missing registrations only fail at runtime when that line runs, not at startup. And tests get harder, because you have to build or mock a whole service provider instead of just passing two mocks. It also makes it easy to resolve the wrong lifetime by accident.

There are legitimate places for it, the composition root in Program.cs, factories that pick an implementation at runtime, middleware, and background services creating scopes. Those are infrastructure code.

In business classes, I always use constructor injection. In code reviews, if I see IServiceProvider injected into a service, I ask what it needs and move that to the constructor. I can explain how this relates to testability.

@p4-63
Choosing lifetimes is a balancing act, and both extremes cause problems.

Not everything can be a singleton, because one instance is shared by every thread and every request. So it has to be thread-safe, and it should never hold per-request data, or one user could see another user's data. A singleton also can't safely hold scoped things like DbContext, which leads to captive dependency bugs, stale data and concurrency exceptions.

Not everything should be transient either. Creating new objects for every injection wastes allocations, expensive objects get rebuilt constantly, and you lose per-request sharing. Like, if two services in one request need the same unit of work, they need the same DbContext, which scoped gives you. Disposable transients resolved from the root also pile up until shutdown.

So my rule is singleton for stateless or thread-safe shared things, like configuration, caches, HttpClient factories and the RabbitMQ connection. Scoped for per-request state, like DbContext and the current user. Transient for light, stateless helpers, like validators. I can go through the lifetime dependency rules too.

@p4-64
When a request finishes, a few things happen in a clean order.

The endpoint returns, and the response flows back out through the middleware pipeline in reverse order, so middleware can add headers or log the result. Then the response is completed and flushed to the client. After that, ASP.NET Core disposes the request's DI scope. That disposes every scoped service and every transient disposable created in that scope. Like, the DbContext is disposed, which returns its database connection to the pool. And then the HttpContext is released, and its objects can be reused for the next request.

There's also the early-end case. If the client disconnects before we finish, HttpContext.RequestAborted, the request's cancellation token, is triggered. Code that passes that token down to EF Core and HttpClient stops working instead of finishing a response nobody will read.

That's why I never keep references to scoped services, like DbContext, beyond the request, say in a fire-and-forget task. That would use an already disposed object, and it bites people. I can explain how to do background work correctly instead.

@p4-65
The rule is simple, basically. The container disposes what it creates.

Scoped services, and transient services resolved inside a scope, are disposed when that scope ends. For web requests, that's at the end of the request. Singletons the container created are disposed when the root provider is disposed, which happens at application shutdown. The container calls Dispose, or DisposeAsync for IAsyncDisposable, in reverse order of creation.

Now, a couple of gotchas. If I create an instance myself and register it, like AddSingleton with new MyService, the container didn't create it, so it won't dispose it. I'm responsible for that. And if a disposable transient is resolved from the root provider, not a scope, the container keeps a reference so it can dispose it at shutdown. That means every resolution stays in memory, which is a slow memory leak.

In our background services, that's exactly why we create a scope per unit of work, so disposables like DbContext are cleaned up each time. I can explain how scope validation catches lifetime issues.

Kestrel is the web server built into ASP.NET Core. It's cross-platform, fully asynchronous, and really fast, and it supports HTTP/1.1, HTTP/2 and HTTP/3, as well as HTTPS and WebSockets.

When an ASP.NET Core app starts, Kestrel listens on the configured ports, accepts connections, parses the HTTP request, and hands it to the middleware pipeline.
