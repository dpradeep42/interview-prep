T: Why did your team move from Angular to React?
K: why move to react, angular to react reasons, migration reasons, why react
X: It wasn't because Angular is bad. Our product, which started as CIRT, Cenduit's IRT, before IQVIA acquired it, has a legacy site portal in ASP.NET MVC with Angular 8 and 12 sub-applications embedded in it, and those still work. The move was a practical decision.
X: First, the legacy portal mixes server-rendered MVC pages with several separately built Angular apps, on old versions. Upgrading them meant several major Angular upgrades plus the MVC parts, a similar effort to building fresh. Second, alignment with IQVIA: IQVIA has an in-house React design system on top of MUI, so building in React gives us IQVIA's consistent look and accessible components for free. Third, modularity: in React, each feature, like drug accountability or manual drug assignment, is its own repository and npm package, composed into a shell app, so teams can work and release more independently. Fourth, people: [most developers joining the team were stronger in React], and it's easier to hire for.
X: What we deliberately did not do was a big-bang rewrite. In a GxP-regulated product, every change must be validated, so rewriting working screens just to change the framework would add risk and validation effort with no benefit for users. Modules move one at a time, and drug accountability is the one being migrated now.
X: Interestingly, our newer internal study builder is still on Angular 17, which shows the choice is per application, not ideology. I'm comfortable in both.

T: How do you run Angular and React side by side in one product?
V: feSide
K: angular and react together, side by side, micro frontends, strangler fig front end, coexist, incremental migration, npm package modules, shell app
X: We run them side by side with an incremental, module-by-module approach, like the strangler fig pattern: new parts grow around the old ones until the old ones can retire. Our legacy site portal is ASP.NET MVC with embedded Angular 8 and 12 sub-applications, and the target is React 17 with TypeScript.
X: There are four pieces. First, a new React shell application, built with Vite, that owns layout, navigation and routing. Each feature, like drug accountability, manual drug assignment, material block or cohort management, lives in its own repository and is published as a versioned npm package to our Azure DevOps feed, then composed into the shell. Second, navigation between old and new: the MVC portal links or redirects into the React app for migrated features, using a configured base URL per environment. Third, one login: both use Keycloak single sign-on, the MVC side through an OWIN cookie and an SSO bridge, the React side with an OIDC client library, so users move between them without signing in again. An idle timer handles session timeout consistently, which matters for 21 CFR Part 11. Fourth, the backend: React modules call the new .NET 9 and 10 APIs through axios instances, with interceptors adding the Keycloak token, and base URLs from Vite environment variables.
X: The trade-off is two technology stacks to maintain, so we never mix frameworks inside one screen, and each feature belongs to exactly one side. The benefit is delivering features in React without rewriting working, validated screens.

T: How do you keep one design system across Angular and React?
K: design system, design tokens, shared styles, component library, consistent ui, angular react styling, mui, iqvia design system
X: The goal is that users feel they're in one product, even though our IRT has a legacy ASP.NET MVC portal with Angular 8 and 12 sub-applications, and a new React 17 and TypeScript application that we're migrating to module by module.
X: On the React side, it's straightforward: every module uses IQVIA's in-house React design system, which is built on MUI 5, along with its icon set. That gives us consistent buttons, form fields, data grids, dialogs and colours, with accessibility already handled. Because each feature is its own npm package composed into one shell, we keep the design system as a shared dependency at one version, so modules don't drift apart.
X: On the Angular side, components can't be reused directly from React, so we align on behaviour and appearance instead: the same colours, spacing and typography, the same layout of forms and tables, and the same patterns, like how validation errors appear, how confirmation dialogs work for risky actions, and how dates are formatted. When an Angular screen gets a significant change, we bring it closer to the design system's look.
X: We also share non-visual patterns that users notice: one Keycloak single sign-on session, consistent idle-timeout behaviour with a warning before logout, and the same error handling, where an axios interceptor shows a friendly message or redirects on an expired session.
X: My part has been building React screens with the design system components, and keeping the Angular screens I maintain visually consistent with them.
