X: Caching strategies differ mainly in when the cache and the database get written, and which one you read first.
X: Cache-aside, or lazy loading, is the most common. The application reads from the cache, and on a miss, it reads from the database and stores the result in the cache with an expiry. Write-through writes to the cache and the database together, so the cache is always up to date for reads, at the cost of slower writes and caching data that might never be read. X: Kubernetes has three probes to understand the health of a container, and each one triggers a different action.
X: The readiness probe asks, is this pod ready to take traffic right now? If it fails, Kubernetes removes the pod from the Service's endpoints, so no requests go to it, but it doesn't restart it. If it fails repeatedly, Kubernetes kills and restarts the container. That's for deadlocks or hung processes. The startup probe gives slow-starting applications time to start. X: RabbitMQ and Kafka are both used for messaging, but they're built on pretty different models.
X: RabbitMQ is a traditional message broker. Producers publish to exchanges, which route messages to queues using bindings and routing keys. Consumers take messages from queues, acknowledge them, and then the message is removed. It has very flexible routing, per-message acknowledgements, priorities, and dead-letter queues, so it's excellent for task queues, commands, and work distribution, where each message should be processed once by one worker. Kafka is a distributed, partitioned, append-only log. Producers write events to topics, and the events are kept for a retention period, whether they've been read or not. Consumers track their own position, called the offset, so many independent consumer groups can read the same events, and you can replay history. It gives you ordering within a partition and very high throughput.
X: So I go with RabbitMQ for commands and work queues with complex routing, and Kafka for event streaming, when several services need the same events, or replay, retention and high volume matter.
X: In our platform, RabbitMQ handles service-to-service workflows like shipment processing. I can explain how we made publishing reliable after our [mid-2024] incident, which applies to both.
+@p2-38
X: These are the three core concepts that give Kafka its scalability and ordering, basically.
X: A topic is a named stream of events, like "shipment-events". Each topic is split into partitions. A partition is an ordered, append-only log, where each event gets a sequential offset. Partitions are spread across brokers, which is how Kafka scales. When producing, the producer picks the partition, usually by hashing the message key. So all events with the same key, like the same study id or shipment id, always go to the same partition, and stay in order. Ordering is only guaranteed within a partition, not across the whole topic. People mix that up a lot.
X: A consumer group is a set of consumers that share the work of reading a topic. Each partition is read by exactly one consumer in the group at a time. So if a topic has six partitions, up to six consumers in a group can work in parallel, and a seventh would just sit idle. The partition count limits parallelism. Different consumer groups read the same topic independently, each with its own offsets. When consumers join or leave, Kafka rebalances partitions among them.
X: Consumers commit offsets after processing, so after a restart they carry on where they left off. I can explain how to choose a good partition key.
+@p2-39
X: In RabbitMQ, producers never publish straight to a queue. They publish to an exchange, and the exchange type decides how messages get routed to the queues bound to it.
X: A direct exchange routes by exact match. A message with routing key "shipment.created" goes to queues bound with exactly that key. It's good for commands and simple point-to-point routing. A topic exchange routes by pattern. Routing keys are dot-separated words, and bindings can use wildcards, a star matches exactly one word, and a hash matches zero or more. So a queue bound with "shipment.*.created" gets created events from any region. It's the most flexible and honestly the one I use most. A fanout exchange ignores the routing key and copies every message to all bound queues, which is a simple broadcast, like telling several services that reference data changed. A headers exchange routes on message header values instead of the routing key, which you rarely need.
X: There's also the default exchange, which routes to a queue with the same name as the routing key.
