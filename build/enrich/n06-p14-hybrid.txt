T: How do you keep validated releases safe across two platforms?
K: dual pipelines, two platforms release, validated release, hybrid release, release safety, aws and on-prem release
X: Our product started as CIRT, Cenduit's IRT, and after IQVIA acquired Cenduit, new services moved to AWS, while the validated core and our Azure DevOps Server stayed on-premise. So one release often touches both: the on-premise core and services on AWS. The risk is that the two sides drift apart.
X: I keep it safe with a few rules. One pipeline system: both sides are built and released from the same on-premise Azure DevOps Server, so there's one place for approvals, one release record and one audit trail. One release version: every component is tagged with the same release version, and we promote the exact same artifacts through FV, TechOps, UAT and production, never rebuilding in between. One order: the release plan says what goes first, usually database changes, then backend services on both platforms, then the UI, with backward-compatible changes so either side can go first safely. One configuration check: settings live in Azure DevOps variable groups for the on-premise side, and in Parameter Store and Secrets Manager for AWS, so before each deployment we compare the required keys on both sides. And one verification: after deployment, every on-premise node and every ECS service reports its version, and they must all match the release tag.
X: Approvals stay human, with named approvers in Azure DevOps for controlled environments. The CIRT MCP server I built runs these steps and checks, which is how one person can now do what took six, in 2 hours instead of 6.

A new required setting had been added, but it was missing in the UAT Parameter Store, because the checklist only covered variable groups.
X: Task: I rolled back within [15 minutes], and then took on the real problem: making sure configuration could never drift between the two platforms unnoticed.
X: Action: I did three things. First, the services validate their options at startup with ValidateOnStart, so a missing setting fails the deployment instead of the first user request. Second, [I added a configuration manifest to each service's repository, listing every required key per environment]. Third, I added a configuration parity check to the CIRT MCP server: before each deployment, it reads the manifest, checks the Azure DevOps variable groups and the AWS Parameter Store and Secrets Manager paths for that environment, and reports any missing keys, without ever showing secret values. It became a standard pre-deployment step.
X: Result: [Since then, we've had no configuration-related release failures], and the check caught missing settings several times before deployment. It also made the transition feel safer for the teams, because both platforms are checked the same way.

T: How does a release flow across on-premise Azure DevOps and AWS?
K: release day, hybrid release flow, release across azure and aws, deployment flow, end to end release
X: Our product started as CIRT, Cenduit's IRT, and after IQVIA acquired Cenduit, new services went to AWS, while our Azure DevOps Server and the validated core stayed on-premise. So a release day touches both, but it's driven from one place.
X: It starts in Azure DevOps. YAML build pipelines, on every merge, build and test the .NET code, run SonarQube, and publish versioned artifacts. For AWS services, they also build Docker images and push them to Amazon ECR. Everything is tagged with the release version.
X: Then the release pipeline promotes those exact artifacts through FV, TechOps, UAT and production. For the on-premise core, a release stage runs Ansible, Python and Shell install scripts across the [4 to 6] nodes of that environment, using the environment's variable group. For AWS services, a stage assumes an IAM role through a service connection, runs Terraform for any infrastructure changes, registers a new ECS task definition with the new image, and updates the service, which does a rolling deployment with health checks. Configuration comes from Parameter Store and Secrets Manager.
X: Controlled environments need approval by named people before the stage runs, and release evidence, like test results and the change record, is attached, because it's GxP.
X: Finally, verification: every node and every ECS service must report the release version and pass health and smoke checks. Today the CIRT MCP server I built drives these steps, which cut a deployment from 6 hours to 2, and from 6 people to 1.
