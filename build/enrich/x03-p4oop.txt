X: The four main OOP principles are encapsulation, abstraction, inheritance and polymorphism.
X: Encapsulation means an object keeps its data private and changes it only through its own methods, so it protects its rules. Abstraction means exposing what something does and hiding how it does it, usually through an interface. Inheritance lets a class reuse and extend the behaviour of a base class. And polymorphism means one interface, many implementations, where the right method is picked at runtime.
X: They work best together, honestly. In my SFTP integration component, business code depends on an ISftpClient interface, which is abstraction. Three providers, ComponentPro, SSH.NET and Rebex, implement it, which is polymorphism, since the caller just calls UploadAsync and configuration decides which one runs. They inherit shared retry and logging logic from a base class, which is inheritance. And each provider keeps its connection details private, which is encapsulation.

X: Encapsulation basically means bundling an object's data with the methods that change it, and hiding the internal state, so the object can protect its own rules.
X: In C# that means private fields, properties with private setters where needed, and public methods that enforce business rules. The outside world can only ask the object to do something, it can't put it into an invalid state directly. What you get is the rules living in one place, so the data stays valid and the code is safer to change later, because callers don't depend on the internals.
X: A real example is a shipment in our system. Instead of a public Status property anyone can set, the Shipment class has methods like MarkDispatched and MarkDelivered. MarkDelivered checks that the shipment was actually dispatched, and records the time. If someone tries to deliver a cancelled shipment, it throws a clear domain exception. In a GxP system that matters a lot, because every state change has to be valid and auditable.

+@p4-19
X: Inheritance lets a class reuse and extend the behaviour of another class, called the base class. It models an "is-a" relationship, like a Rebex SFTP client is an SFTP client.
X: In C#, a class can inherit from only one base class, but it can implement many interfaces. The derived class gets the base members, can add its own, and can override virtual methods to change behaviour. It's powerful for sharing real code, but it creates tight coupling, because changes in the base class ripple into every child. Deep hierarchies also get hard to understand.
X: So I use it carefully. In our SFTP component, an abstract SftpClientBase class holds the common retry, timeout and logging logic, and each provider class inherits it and only implements the library-specific connect, upload and download. That removed a lot of duplication.
X: But when the relationship is really "has-a", or behaviour varies a lot, I'd go with composition, injecting a collaborator instead of inheriting. I can talk about when I'd avoid inheritance if you like.
+@p4-20
X: Polymorphism means "one interface, many forms". The same method call behaves differently depending on the actual object behind it.
X: In C# there are two kinds. Runtime polymorphism happens through virtual and override methods, or through interfaces: the method that runs is decided at runtime based on the real type of the object. Compile-time polymorphism is method overloading, where the compiler picks a method by its parameters. Runtime polymorphism is the important one for design, because it lets code depend on an abstraction and lets new behaviour plug in without changing the caller.
X: My real example is the SFTP integration. The business code calls UploadAsync on an ISftpClient. Depending on the vendor's configuration, the Rebex, SSH.NET or ComponentPro implementation runs, and the calling code has no idea which one. When we added Rebex, nothing in the callers changed.
X: It also makes testing easy, because in unit tests I just pass a mock that implements the same interface. I can explain how dependency injection uses this too.
+@p4-21
X: Abstraction means showing only what the user of a class needs to know, and hiding the complex details of how it works.
X: In C#, we usually express abstraction with interfaces and abstract classes. They describe the essential contract, the operations and their meaning, while the implementation details stay inside. It's slightly different from encapsulation: encapsulation is about protecting an object's data, while abstraction is about modelling a simple concept that hides complexity. Good abstractions make code easier to use, easier to test and easier to change.
X: For example, our ISftpClient interface only exposes a few things: connect, upload, download and list files. Behind it, each library deals with its own complexity, like different authentication APIs, key formats, timeouts and error types. Business code just thinks "send this file to the vendor", and doesn't care about any of that.
X: The trap is creating abstractions too early, or leaking details, like exposing library-specific exceptions through the interface. I mapped all provider errors to our own exception types to avoid that. I can show the interface design if useful.

X: Overloading means having several methods with the same name but different parameters in the same class, for example a Log method that takes a string, and another that takes a string and an exception. The compiler picks the right one at compile time based on the arguments, so it's compile-time polymorphism. The return type alone isn't enough to overload.
X: Overriding means a derived class provides its own version of a virtual or abstract method from the base class, with the same signature. The decision is made at runtime, based on the actual object, even if you call it through a base-class reference. That's runtime polymorphism.
X: A real example: in our SFTP providers, the base class has a virtual method for building connection settings, and the Rebex provider overrides it to add its own key handling. Separately, we have overloaded upload methods, one taking a file path and one taking a stream.

+@p4-24
X: The virtual keyword is used on a base-class method to say derived classes are allowed to replace it. The override keyword is used in the derived class to actually replace it.
X: When you call a virtual method, the runtime looks at the actual type of the object, not the type of the variable. So even if I hold the object through a base-class reference, the derived override runs. Without virtual, a method can't be overridden at all; C# methods are non-virtual by default, which is a deliberate design choice for performance and safety. An override can call the base version with base dot method name, and it can be marked sealed to stop further overriding.
X: In our SFTP component, the base class has a virtual method that builds connection options with sensible defaults. The Rebex provider overrides it, calls the base version first, and then adds its specific settings. That way the shared defaults live in one place.
X: Abstract methods are similar but have no body, so derived classes must override them. I can explain the difference between override and new as well.
+@p4-25
X: Override and new both put a method with the same name in a derived class, but they behave very differently.
X: Override replaces a virtual method. Whichever reference you use, base type or derived type, the derived version runs, because it's decided at runtime by the actual object. That's normal polymorphism. The new keyword hides the base method instead, which is called method hiding. Then the version that runs depends on the declared type of the variable: through a base-class reference the base version runs, and through a derived reference the new version runs. So the same object can behave differently depending on how you hold it.
X: That's confusing and a common source of bugs, so I avoid it. If you forget both keywords, the compiler warns you that you're hiding a member, and in our projects we treat warnings as errors in CI.

X: A sealed class is a class that can't be inherited from. A sealed method is an override that can't be overridden again by classes further down the hierarchy.
X: Sealing communicates design intent: this class wasn't designed for extension, so nobody should depend on its internals by subclassing it. It also prevents subtle bugs where a subclass breaks the class's assumptions. There's a small performance benefit too, because the JIT can devirtualise calls on sealed types. The string class is a well-known example of a sealed class. A sealed method is useful when you've overridden something carefully and want to lock that behaviour down.
X: In our code, we seal classes by default when they aren't meant to be inherited, which is most service classes, handlers and DTOs, and some analyzers even suggest it. If later we really need extension, we usually add an interface rather than unsealing.

X: The stack and the heap are two areas of memory that .NET uses in different ways.
X: The stack is per thread. It stores method call frames: parameters, local variables and return addresses. It works last-in, first-out, so it's extremely fast, and the memory is freed automatically when a method returns. The heap is shared memory where objects created with new live, mostly reference types. Objects on the heap stay until the garbage collector finds nothing references them.
X: A common misconception is that value types always live on the stack. Actually, a value type lives where it's declared. A local int is on the stack, but an int field inside a class object is on the heap, as part of that object. And boxing moves a value type onto the heap.
X: In practice this matters for performance. Fewer heap allocations means less GC work. For example, when tuning CSV parsing, using Span of T to slice strings without allocating new ones reduced GC pressure noticeably. I can explain how the GC cleans up the heap if useful.
+@p4-28
X: Boxing is when a value type, like an int or a struct, is wrapped inside an object on the heap. Unboxing is extracting the value back out with an explicit cast.
X: Boxing happens implicitly, for example when you assign an int to an object variable, put it in an old non-generic collection like ArrayList, or call an interface method on a struct through the interface. Each box is a new heap allocation, and it creates extra work for the garbage collector. Unboxing needs a cast to the exact type, or you get an InvalidCastException.
X: In normal business code it rarely matters, but in hot paths, like processing thousands of CSV rows or logging in a tight loop, it adds up. The fix is generics: List of int instead of ArrayList, generic methods instead of object parameters, and structured logging templates, which avoid boxing in newer .NET versions.
X: So my rule is simply: use generic collections and APIs, and watch allocations in a profiler when performance matters. I can talk about how I measure allocations if helpful.

X: IDisposable is the interface for objects that hold resources the garbage collector doesn't manage, like file handles, database connections, network streams or SFTP sessions. Its Dispose method releases them deterministically, right away, instead of waiting for the GC.

X: All three make a value unchangeable, but at different times and in different ways.
X: A const is a compile-time constant. It's implicitly static, and its value is copied into every assembly that uses it. So it must be a simple literal, like a number or string, and if you change it, every calling assembly needs recompiling, otherwise they keep the old value. X: ref, out and in are all ways to pass an argument by reference, instead of passing a copy.
X: With ref, the variable must be initialised before the call, and the method can read and change it, and the caller sees the change. With out, the method must assign a value before it returns, and the caller doesn't need to initialise it. The classic example is int.TryParse, which returns a bool for success and gives the parsed number through an out parameter. With in, you pass a read-only reference: the method can't change it, and the point is to avoid copying a large struct.
X: In everyday code I use out mostly for Try-pattern methods. For example, our CSV validator has a TryParseRow method that returns true or false and gives the parsed row as an out parameter, so we avoid exceptions for normal validation failures.
X: I use ref and in rarely, mostly in performance-sensitive code. Usually returning a result object or a tuple is clearer. I can show an example if useful.

X: An async deadlock happens when code blocks on async work, for example by calling .Result or .Wait() on a task, in an environment that has a synchronization context.
X: In classic ASP.NET or desktop UI apps, the synchronization context means the continuation after an await must resume on the original thread. If that same thread is blocked waiting on .Result, the task can never finish, because it needs the thread that's waiting for it. So both wait forever. ASP.NET Core doesn't have that synchronization context, so you don't get this exact deadlock, but blocking still causes thread-pool starvation under load, where requests pile up and the API slows to a crawl.
X: The fix is async all the way: await instead of blocking, and make callers async too. In library code we use ConfigureAwait(false) so it's safe in any environment.
X: I've seen the starvation version in practice: an old helper that called .Result on an HTTP call caused timeouts under load, and making it async fixed it. I can explain how I spotted it.
