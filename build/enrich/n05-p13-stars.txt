T: Tell me about a time you prevented a double randomisation or re-randomisation.
K: double randomisation, duplicate randomization, idempotency story, re-randomisation story, concurrency bug, star irt
X: Situation: In our IRT, a study is one clinical trial set up in the system, and randomisation assigns each subject to a treatment arm. Every subject must get exactly one assignment per stage. [In 2024, while we were adding re-randomisation support for a study with a second treatment stage, we found in testing that if a site user double-clicked, or a slow request was retried, a subject could, in rare cases, be re-randomised twice.] In a live trial, that would be a serious data integrity issue.
X: Task: I owned the fix in our newer .NET API layer, and the goal was to make a duplicate assignment impossible, not just unlikely.
X: Action: Our new APIs don't randomise directly; they call the transaction engine in our legacy .NET Framework core, through a transaction engine API, and the engine writes to the study's own SQL Server database. I fixed it at three levels. First, idempotency: the UI sends an idempotency key with each request, and the API stores the key with the result, so a retry returns the original result instead of calling the engine again. Second, the database: [a unique constraint, so a subject can have only one assignment per randomisation stage], with slot allocation inside a transaction with row locking. Third, state checks before calling the engine, using a FluentValidation rule in the MediatR pipeline. The button is also disabled while the request runs, and I added concurrency tests firing parallel requests at the same subject.
X: Result: [The concurrency tests that previously produced a duplicate now always produce exactly one assignment], it passed validation, and we've had no duplicate assignments since. [The same pattern was then reused for the first randomisation and for kit dispensing.]

K: admin console story, study configuration validation, study build errors, pre go-live checks, star admin console, study transfer
X: Situation: In our IRT, a study is one clinical trial, and our internal Admin console tooling, the desktop study designer and the newer web-based study builder, is where the study build team configures it: sites, depots, arms, randomisation, visits, kits, supply settings and roles. Each study is then transferred from build to UAT to production with a diff review. [Configuration mistakes, like a visit that dispensed a kit type not assigned to any arm, or a site without a depot, were often only found late, in user acceptance testing, which meant rework and delayed go-lives.]
X: Task: [I was asked to help catch these problems earlier, before the study reached UAT.]
X: Action: [I designed a configuration check service in .NET that inspects a study's database as a whole before transfer.] I worked with the study build team to collect the most common mistakes and turned them into rules, like every dispensing visit having a valid kit type for each arm, every active site having a depot and resupply settings, strata matching the uploaded randomisation lists, and required roles being assigned. Each rule returns a clear message naming the exact item to fix. [The results appear alongside the transfer diff, and errors must be resolved before transfer], next to the study-transfer safety guard I built. Rules are unit tested, and adding one is simple, so the team kept adding them.
X: Result: [Configuration defects found in UAT dropped noticeably], the study build team fixes issues themselves in minutes, and go-lives became more predictable.

DARM was built in our legacy ASP.NET MVC portal, and it was chosen as the next module to migrate to our new React and TypeScript application.
X: Task: [I worked on the first migrated part: the accountability entry and return shipment screens, and the .NET APIs behind them.]

On the front end, I built the screens as part of the DARM npm package for our React shell, using IQVIA's MUI-based design system, Redux Toolkit, and axios with the Keycloak token. Because the old and new screens had to behave identically, [I wrote comparison test cases that ran the same scenarios against both].
X: Result: [The new screens passed validation with no behaviour differences, sites found them faster to use], and they became the template for migrating the rest of DARM.

T: Tell me about a time you worked on the eConsent integration and re-consent.
K: econsent story, re-consent, consent version, star econsent, protocol amendment consent, econsent integration story
X: Situation: In our IRT, a study is one clinical trial set up in the system. Our eConsent is integration-based: consent is captured in an external eConsent system, and IRT receives each subject's consent status through integration flows, then gates screening and randomisation on valid consent. Those flows were built in MuleSoft, as SFTP file drops, and were being migrated into our .NET data transfer API. [We had occasional issues where a status file arrived late or out of order, so a subject's re-consent after a new consent version could briefly show the wrong status.]
X: Task: [I worked on the .NET side of the consent integration, to make status processing reliable and re-consent clear for sites.]
X: Action: [I made processing idempotent, using each record's source id, so a re-sent file never created duplicates, and ordered updates by the event time in the file, not the arrival time, so an older status could never overwrite a newer one.] Every received status is stored as history, never overwritten, with full audit. When a status showed a new consent version was required, or a subject withdrew, the system triggered the notification emails to the site. And I added monitoring, so a missing expected file raises an alert instead of going unnoticed. Edge cases, like withdrawn subjects or subjects moving site, were covered by tests.
X: Result: [Out-of-order status problems stopped], sites get clear re-consent notifications, and the audit trail shows exactly which consent status applied at every transaction.
