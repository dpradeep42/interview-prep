T: How did you handle role-based access in the end-user RAG assistant?
K: rag access control, role based access rag, document permissions rag, sso groups, metadata filtering security
X: In the IRT Knowledge Assistant, our RAG tool for business analysts, QA, support and the study build team, access control was built into retrieval, not added after.
X: Every document chunk in the index carries metadata: its source, its owning team, and an audience label, like general, study build, support or internal engineering. When a user asks a question, the Teams bot or web page passes their identity from single sign-on, and the Python service reads their Azure AD group memberships. The search query then filters chunks by the audiences those groups allow, before ranking, inside the same PostgreSQL query. So content a user can't access is never retrieved, never sent to the model, and can never leak into an answer. Filtering after generation would be too late.
X: What goes into the index matters just as much. Only approved reference content is indexed: specs, user guides, release notes, Admin console configuration guides, and support resolutions sanitised to remove any patient, site or study data. No production systems are connected. That keeps it outside GxP scope, as an informational tool, which we stated clearly in the interface.
X: Every question, user and set of cited sources is logged, so we can audit who saw what. And when a document's permissions change, the next indexing run updates its labels.
X: The principle I followed: the assistant should never let someone see more than they could already open themselves.

T: What lessons did you learn from the end-user RAG assistant?
K: rag lessons learned, end user rag lessons, knowledge assistant lessons, rag mistakes, what would you do differently rag
X: Building the IRT Knowledge Assistant, a RAG tool on our Python retrieval service for business analysts, QA, support and the study build team, taught me lessons I now apply to every AI project.
X: First, content quality decides answer quality. Most bad answers came from outdated or contradictory documents, not the model. The assistant actually became a way to find and fix our documentation. Second, citations build trust. Users trusted answers they could check in one click, and stopped trusting quickly when they couldn't. Third, "I don't know" is a feature. Refusing to guess protected credibility. Fourth, start narrow. A pilot with one team and two topics, done well, beat launching everything half-ready. Fifth, the feedback loop is the product. Thumbs feedback reviewed weekly with content owners drove most of the improvement. Sixth, meet users where they work. Putting it in Microsoft Teams mattered more than any feature. Seventh, measure from the start: weekly users, questions answered without escalation, and thumbs-up rate, so we could prove value with numbers.
X: [If I did it again, I'd involve the content owners from day one, and set up document review dates], because stale content was our biggest ongoing issue.
X: The same lessons apply to our developer RAG, which gives GitHub Copilot and Cursor the context of our codebase and coding standards: good sources, clear citations and measurement matter more than clever models.
