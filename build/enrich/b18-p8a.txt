@p8-1
Q: Before MCP, every AI app had to build custom integrations for every tool or data source (N apps × M tools). The Model Context Protocol, an open standard introduced by Anthropic in late 2024, standardises how AI hosts discover and call tools and read data, so one server works with many hosts (N + M). It was donated to the Linux Foundation's Agentic AI Foundation in December 2025, with broad industry backing.
- Inspired by the Language Server Protocol, which did the same for editors and languages.
- Adopted by Cursor, Claude, VS Code/Copilot, ChatGPT and others.
- Primitives: tools, resources, prompts; client features: sampling, roots, elicitation.
- For us: one CIRT MCP server works from Cursor and Claude Code.
? What is LSP's connection? :: MCP borrows LSP's idea of one protocol connecting many clients and servers.
? What is elicitation? :: A way for a server to ask the user for extra input through the host during a tool call.

@p8-2
Q: The host app (Cursor, Claude Code) runs an MCP client per server. Client and server speak JSON-RPC 2.0 over stdio or Streamable HTTP: initialize (capability negotiation), then tools/list for discovery and tools/call to run a tool with JSON arguments, returning content blocks; the host shows tools to the model and executes the calls the model requests.
- Notifications (e.g. tools/list_changed) update tool lists dynamically.
- Progress notifications for long operations and cancellation support.
```json
{ "jsonrpc": "2.0", "id": 7, "method": "tools/call",
  "params": { "name": "get_release_status", "arguments": { "releaseId": 1234 } } }
```
? Who calls the tool: the model or the host? :: The model requests it; the host's client executes it.
? stdio vs Streamable HTTP? :: stdio for local processes per user; HTTP for shared remote servers.

@p8-3
Q: REST is for programs written by developers who read docs; MCP is for models: tools are self-describing (name, description, schema), discovered at runtime, with a standard calling convention every host understands. MCP servers often wrap REST APIs, adding model-friendly descriptions, validation, summarised outputs and safety controls.
- Raw REST exposes too much and returns verbose payloads that waste context.
- MCP adds a security boundary (allow-lists, confirmations).
? Does MCP replace REST? :: No, it usually sits on top of REST APIs for AI clients.
? Why not let the agent call REST via a generic HTTP tool? :: It's unsafe and error-prone; specific tools with validation are safer.

@p8-4
Q: On connect, the client calls tools/list and gets names, descriptions and input schemas, which the host gives the model. The model matches the user's goal against those descriptions and returns a tool call with arguments; the host runs it and feeds the result back, looping until done.
- Tool selection quality depends on names, descriptions and minimal overlap.
- Too many tools dilute accuracy; some hosts limit tool counts or let users enable subsets.
? How do you improve wrong selections? :: Clarify descriptions with "use when", remove overlap, add enums.
? Can tools change at runtime? :: Yes, with list_changed notifications.

@p8-5
Q: Parameters are a JSON Schema per tool (types, required fields, enums, descriptions); in the C# SDK they come from method parameters with [Description] attributes. Responses are content blocks (text, images, resource links) plus optional structuredContent matching an output schema, with isError for failures.
- Structured output (spec 2025-06-18) lets clients parse results reliably.
- Keep outputs concise: summary, ids, next steps.
```csharp
[McpServerTool(Name = "get_release_status"), Description("Get status of a release per environment. Use after create_release or deploy_release_stage.")]
public static async Task<ReleaseStatus> GetReleaseStatus(AdoClient ado, [Description("Release id")] int releaseId, CancellationToken ct)
    => await ado.GetReleaseStatusAsync(releaseId, ct);
```
? What does isError do? :: Tells the model the tool failed so it can adapt, without a protocol error.
? Why concise outputs? :: Context window space and model accuracy.

@p8-6
Q: I catch exceptions in the tool and return isError with a clear, actionable message (what failed, why, what to try) rather than a stack trace, distinguishing validation errors, permission errors and transient failures; transient Azure DevOps errors get limited retries inside the tool.
- Protocol errors (unknown tool, bad JSON) vs tool execution errors (isError).
- Never leak secrets or internal paths in messages.
- Log full details server-side with a correlation id.
? Example message? :: "Release 1234 is waiting for QA approval in UAT; approve it in Azure DevOps, then call get_release_status."
? Should the tool retry automatically? :: Only idempotent, transient operations.

@p8-7
Q: Each user's own Azure DevOps PAT, so the server can only do what that person can; production approvals stay in Azure DevOps; tools are read-only by default; write tools have explicit names and confirmation; environment allow-lists; no destructive tools (no delete); and every call is audited.
- Defence in depth: host confirmation, server validation, Azure DevOps permissions and approvals.

? Could someone use the server to bypass approvals? :: No, approvals are enforced by Azure DevOps itself.

@p8-8
Q: Schema validation first (types, enums, required), then server-side checks: environment names from an allow-list, release and build ids must exist and belong to the right project, versions must match approved artifacts, and dangerous combinations are rejected with clear messages. AI-generated arguments are treated as untrusted input.
- Same principle as validating any user input.
- Return what valid values are when rejecting.
? Why validate if the schema has enums? :: Clients may not enforce schemas strictly, and business rules go beyond types.
? Example rejection? :: Deploying a build from a feature branch to UAT.

@p8-9
Q: The stdio transport runs locally per engineer with their Azure DevOps PAT from an environment variable, so authentication is the person's own; for an HTTP deployment I'd use OAuth 2.1 as the MCP authorization spec defines (protected resource metadata, PKCE, audience-bound tokens) with SSO, and authorization still enforced by Azure DevOps permissions plus tool-level role checks.
- Never pass user tokens through to other services (token passthrough is forbidden in the spec).
- Short-lived tokens and scopes per tool group.
? Why not one service account? :: It would give everyone the account's permissions and break attribution.
? What is token passthrough? :: Forwarding the client's token to downstream APIs, which the MCP spec prohibits.

@p8-11
Q: The PAT and server URL come from environment variables in the MCP config, never from the repo; they're masked in logs and tool outputs; PATs use least-privilege scopes with expiry; and for a shared HTTP deployment, secrets would live in a vault with OAuth replacing PATs.
- Tools never return credentials, even if asked.
- Detect and redact secret-like strings in log summaries.

? What if a PAT leaks? :: Revoke it in Azure DevOps immediately; it expires anyway.

@p8-27
Q: Agentic AI is an LLM that plans and takes actions with tools in a loop toward a goal, checking results. A chatbot answers in conversation; an agent acts: it calls tools, observes outcomes and decides next steps, within limits.
- Components: model, tools, memory, planning, guardrails.
- Autonomy levels range from suggest-only to fully autonomous.
? When is an agent overkill? :: When a deterministic script or workflow does the job.
? What limits do agents need? :: Step caps, permissions, confirmations and budgets.
