T: What is the architecture of your MCP server in .NET 8?
V: mcpArch
K: mcp architecture, mcp server architecture, dotnet 8 mcp, net 8 mcp, generic host mcp, mcp design layers
X: The CIRT MCP server is a .NET 8 console application that lets AI assistants run builds, releases and multi-node deployments on our on-premise Azure DevOps Server. It's built in layers, using the normal .NET hosting model.
X: At the top is the generic host. Program.cs creates a host builder, registers the MCP server with the official ModelContextProtocol C# SDK, chooses the stdio transport, and discovers tools from the assembly. Configuration comes from appsettings and environment variables, bound to strongly typed options, with validation at startup, so a missing server URL fails immediately with a clear message.
X: Next is the tool layer: about 77 tools in classes grouped by domain, like builds, releases, deployments and diagnostics. Each tool is a normal C# method with attributes and a description, and the SDK generates its JSON schema. Tools get their dependencies through dependency injection.
X: Under that is a guard layer: argument validation, enums for environments, confirmation checks for risky actions, and the audit logger, which records the user, tool, arguments with secrets removed, duration and result.
X: At the bottom is a typed Azure DevOps client, built on IHttpClientFactory, with the engineer's personal access token, timeouts, and Polly retries with backoff only for safe, read-only calls. Our install scripts are wrapped the same way. Logging uses Serilog, writing to standard error and a rolling file, never to standard output, because stdout carries the protocol.
X: It's packaged as a .NET global tool. The result: deployments went from 6 hours to 2, and from 6 people to 1.

T: How do you register MCP tools in C# with the official SDK?
K: mcp c# sdk, modelcontextprotocol package, mcpservertool, mcpservertooltype, addmcpserver, withtoolsfromassembly, register tools c#
X: I built the CIRT MCP server in C# on .NET 8, with the official ModelContextProtocol SDK for C#, and its tool registration is one of the nicest parts, because tools are just normal C# methods.
X: In Program.cs, on the generic host builder, I call AddMcpServer, then WithStdioServerTransport, and WithToolsFromAssembly. The SDK scans the assembly for classes marked with the McpServerToolType attribute, and inside them, methods marked with McpServerTool, where I set the tool name, like get_release_status. The Description attribute on the method tells the model when to use the tool, and Description attributes on each parameter explain what to pass. From the method signature, the SDK generates the JSON schema automatically: types, required parameters, and enums from C# enum types, like our environment names.
X: Dependencies come in through dependency injection. A tool method can take services, like our Azure DevOps client, the audit logger or options, as parameters, and the SDK resolves them from the container, separately from the arguments the model provides. Methods can be async, receive a CancellationToken, so a cancelled request stops the work, and return a string or a structured object.
X: For errors, a tool returns a clear error result the model can understand, like "release 4.2 not found; latest is 4.1", instead of throwing raw exceptions.
X: Because it's plain C#, every tool is easy to unit test with a fake client. That made it practical to build and maintain about 77 tools on my own.

T: stdio vs Streamable HTTP transport in MCP: which did you use and why?
K: mcp transports, stdio, streamable http, sse, http transport mcp, local vs remote mcp server
X: MCP messages are JSON-RPC, and a transport is how they travel between the AI host's client and the server. There are two standard options.
X: With stdio, the host starts the server as a local child process and they exchange messages through standard input and output. It's simple and fast, there's no network port and nothing to host, and the server runs with the local user's identity and environment. The catch is that each user runs their own copy, and anything written to standard output must be protocol messages only.
X: Streamable HTTP is for remote servers. The client sends JSON-RPC messages as HTTP POST requests to one endpoint, and the server can reply with a single JSON response or stream several messages using server-sent events. It replaced the older HTTP plus SSE transport, which needed two separate endpoints. A remote server can serve many users, so you need proper authentication, which the MCP spec defines with OAuth, plus all the usual concerns: TLS, scaling and monitoring.
X: For the CIRT MCP server, built in C# on .NET 8, I chose stdio. Each engineer runs it locally inside the company network, with their own Azure DevOps personal access token, so every action happens with their permissions and shows their name, and there was no shared server to secure or operate. That fitted a team tool well.
X: If we rolled it out across the whole organisation, I'd move to Streamable HTTP with OAuth, for central updates, audit and monitoring.

T: How do you keep 77 MCP tools usable and avoid token bloat?
K: token bloat, too many tools, tool selection, 77 tools, context budget, tool descriptions, how llm picks tool
X: About 77 tools is a lot. Every tool's name, description and schema is sent to the model as context, so too many, or too wordy, tools cost tokens and make it more likely the model picks the wrong one. In the CIRT MCP server, which I built in C# on .NET 8, I handled it in five ways.
X: First, naming. A strict verb-noun convention, like queue_build, get_release_status and deploy_release_stage, so the name alone tells the model what the tool does. Second, short, precise descriptions that say when to use the tool and what it returns, plus "use this instead of" hints where two tools are close. Third, tight schemas: enums for environments and stages, required parameters marked, and no free text where a fixed value exists. Fourth, small outputs. Tools return short structured summaries, like status, the failing step and a link, never raw logs or full JSON, which protects the context window during long sessions. Fifth, composite tools for common sequences, like deploy and verify, so the model makes one call instead of six.
X: On the host side, engineers can switch off tool groups they don't need, and project rules give the model a recommended order for common jobs.
X: I check selection with realistic prompts, like "why did last night's UAT deployment fail?", and see whether the right tool is called with the right arguments. If I rebuilt it, I'd merge more tools into higher-level ones. But this design already made deployments go from 6 hours to 2.

T: How did you use HttpClient, Polly and Serilog in your MCP server?
K: polly mcp, serilog mcp, httpclient mcp, resilience mcp server, logging mcp, retries mcp
X: The CIRT MCP server, which I built in C# on .NET 8, spends most of its time calling our on-premise Azure DevOps Server, so resilience and logging were essential.
X: For HTTP, I built a typed Azure DevOps client registered with IHttpClientFactory, so connections are pooled properly and configuration is in one place. A delegating handler adds the engineer's personal access token and a correlation id to every request. Each call has a timeout, so a slow server can't hang a tool call, and cancellation flows through, so if the user stops the agent, the request stops too.
X: For resilience, I used Polly through the standard resilience handler: retries with exponential backoff and jitter, but only for safe, idempotent calls, like reading a build status, and only on transient errors, like timeouts and 503s. Write calls, like starting a deployment, are never retried automatically, because a retry could start a second deployment. Instead, the tool reports the problem and the model can check status first. A circuit breaker stops hammering the server if it's down, and the tool returns a clear message.
X: For logging, I used Serilog with structured logs: the tool, the user, duration, result and correlation id. Crucially, it writes to standard error and a rolling file, never standard output, because over stdio, standard output carries the JSON-RPC protocol. Separately, an audit log records every tool call, with secrets removed.
X: That combination is why the server stayed reliable enough to cut deployments from 6 hours to 2.

T: What was the hardest bug in your MCP server?
K: hardest bug mcp, mcp bug story, stdout logging bug, mcp disconnects, debugging mcp
X: Situation: Early on, when I was building the CIRT MCP server in C# on .NET 8, it worked perfectly in my unit tests, but in Cursor, the server would randomly disconnect, or tool calls would fail with parse errors. [It happened maybe one call in ten], with no pattern I could see.
X: Task: I had to find the cause before anyone else on the team used it, because an unreliable tool around deployments would destroy trust immediately.
X: Action: I started by capturing the raw traffic. Using the MCP Inspector, and by logging what the client received, I noticed that some messages on standard output weren't JSON-RPC at all. They were log lines. Over the stdio transport, standard output is the protocol channel, and any extra text corrupts the stream. The cause was that [a third-party library and one of my early console logging settings] wrote to the console, and only on certain code paths, like a retry, which is why it looked random. I fixed it properly: Serilog configured to write only to standard error and a rolling file, the default console logger removed, and a startup check, plus a test, that fails if anything writes to standard output outside the protocol.
X: Result: The disconnects disappeared completely, and the test makes sure they can't come back. [It took about a day to find], and it taught me a lesson I now share with anyone building MCP servers: with stdio, standard output belongs to the protocol, and nothing else.
X: After that, the server became the reliable tool that took deployments from 6 hours to 2.

K: mcp resources, mcp prompts, prompt templates, resources vs tools, mcp primitives
X: MCP servers can expose three kinds of capabilities. Tools are actions the model decides to call, like starting a deployment. Resources are read-only data identified by a URI, which the host or user can attach as context, like a document or a configuration file. And prompts are reusable templates the user chooses explicitly, often shown as slash commands in the host, which can take arguments and include resources.
X: In the CIRT MCP server, which I built in C# on .NET 8, tools are the core, about 77 of them, because the main job is to act on our on-premise Azure DevOps Server. But I also used the other two where they helped.

[For resources, I exposed things like the environment catalogue and the deployment runbook], so the model can read the rules without the engineer pasting them.
X: The difference matters: tools are model-controlled, resources are application-controlled, and prompts are user-controlled. Support for resources and prompts also varies between hosts, which is why the critical behaviour lives in tools and their guard checks.

T: How do you make sure secrets never reach the LLM through MCP?
K: secrets llm, no secrets to llm, pat security, redact secrets, mcp secret handling, variable group secrets
X: The rule is simple: anything a tool returns goes into the model's context, and may be logged by the host, so a secret must never appear in a tool's output, its arguments, or its errors.
X: In the CIRT MCP server, which I built in C# on .NET 8 for our on-premise Azure DevOps Server, I applied that at several points. Credentials: each engineer's personal access token comes from their own environment variable, is used only by the HTTP client, and never appears in a tool parameter or result, so the model never sees it. Tokens are scoped to the minimum permissions needed. Variable groups: the check tool only returns key names and whether each key is set per environment, never the values, and secret variables are masked by Azure DevOps anyway. Logs: before any build or deployment log summary is returned, a redaction step removes anything that looks like a password, connection string, key or token, using patterns, and the output is truncated. Errors: exceptions are turned into safe messages, without request headers or raw responses. And the audit log records arguments with sensitive fields removed.
X: There's also the reverse direction: the model shouldn't be able to ask for secrets. There's simply no tool that reads secret values.
X: Because it's a GxP product, I also kept patient and study data out of scope entirely: the server works with builds, releases and environments only. That design is why the team trusted it enough to use it for every deployment.
