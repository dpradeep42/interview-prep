X: These are the three delivery guarantees a messaging system can offer, and each is a trade-off between losing messages and duplicating them.
X: At-most-once means a message is delivered once or not at all. There are no retries, so if something fails along the way, the message is lost. It's only acceptable for data where loss doesn't matter, like some metrics. At-least-once means the system keeps retrying until the message is acknowledged, so nothing is lost. But if a consumer processes a message and crashes before acknowledging, it will receive it again, so duplicates are possible. That's why consumers must be idempotent. Exactly-once means no loss and no duplicates. It's only truly available within limits, like Kafka transactions for read-process-write inside Kafka. Across different systems, like a broker and a database, it's achieved "effectively" through at-least-once delivery plus idempotent processing.
X: In practice, at-least-once with idempotent consumers is the standard choice for business data.
X: That's how our platform works. Publishing uses confirms, so the broker definitely has the message, consumers acknowledge only after successful processing, and every message has an id, which consumers use to skip duplicates. I can explain how to make a consumer idempotent.

X: An idempotent consumer produces the same result whether it processes a message once or several times. With at-least-once delivery, duplicates will happen, so this is essential.
X: There are a few techniques, and I often combine them. First, every message carries a unique message id. The consumer keeps an inbox table of processed ids, and skips any message it has already seen. The key detail is that the insert into the inbox table and the business update happen in the same database transaction, so either both are saved or neither is. Second, natural idempotency: design operations so repeating them is harmless. "Set shipment status to Delivered" is idempotent, while "increment delivered count" isn't. Upserts instead of inserts, and unique constraints, help too. Third, for ordering problems, a version or timestamp check, so an older event can't overwrite newer data.
X: Then the failure path: retry transient errors with backoff, and after a few attempts move the message to a dead-letter queue, instead of retrying forever.
X: This property saved us in our RabbitMQ incident in [mid-2024]. Because consumers upsert, I could safely replay a whole window of vendor files without creating duplicates. I can explain that recovery.

X: A dead-letter queue, or DLQ, is a separate queue where messages go when they can't be processed successfully, so they don't block the main queue or get lost.

X: The transactional outbox pattern solves a very common reliability problem in microservices: updating your database and publishing an event as one reliable step.

X: The CAP theorem says that in a distributed system, when there's a network partition, meaning parts of the system can't talk to each other, you have to choose between consistency and availability. You can't fully have both.
X: Consistency means every read gets the most recent write, or an error. Availability means every request gets a response, even if it might be stale. Partition tolerance isn't really optional, because networks do fail. So the real choice is how the system behaves during a partition. A CP system refuses or delays some requests to stay correct. An AP system keeps answering, possibly with stale data, and reconciles later. When there's no partition, you can have both, and the trade-off becomes latency versus consistency, which is the PACELC extension.
X: The useful insight is that you choose per feature, not for the whole system. In clinical trials, allocating limited drug kits or a randomisation slot must be consistent, so it's CP: better to fail and retry than to promise the same kit to two sites. But dashboards, notifications and reports can be AP: slightly stale data is fine, and availability matters more.
X: That's exactly how our IRT platform is designed: transactional SQL for allocation, eventually consistent events for everything around it. I can explain how we handle the stale data in the UI.

X: The saga pattern handles business transactions that span several microservices, where a single database transaction isn't possible.
X: The long transaction is split into a sequence of local transactions. Each service does its part in its own database, and then publishes an event or triggers the next step. If a step fails, the saga runs compensating actions to undo the earlier steps. For example: reserve kits, create a shipment, notify the vendor. If the vendor rejects the shipment, compensations cancel the shipment and release the reserved kits. Compensations are business actions, not database rollbacks, and they must be idempotent too.
X: There are two styles. Choreography: there's no central coordinator; each service listens for events and reacts, publishing its own events. It's simple for short flows, but the overall process becomes hard to see and change. Orchestration: a central orchestrator tells each service what to do next and tracks the state of the saga. It's easier to understand, monitor and change for complex flows, but the orchestrator is an extra component. AWS Step Functions or a durable workflow engine can play that role.
X: Sagas need the outbox for reliable events, idempotent consumers, and clear statuses so users see "pending" rather than inconsistent data. I can sketch the shipment saga.
