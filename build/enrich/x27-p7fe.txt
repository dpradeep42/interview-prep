+@p7-2
X: Okay, so a component and an element are related, but they're different things.
X: A component is a function, or in older code a class, that describes a piece of UI. It accepts inputs, called props, and returns what should be displayed. Like a ShipmentRow component that takes a shipment and returns a table row. It's like a blueprint, or a template, that can be reused many times.
X: An element is the result of using a component. It's a plain, lightweight JavaScript object that describes what should appear on the screen, its type, like a div, or the ShipmentRow component, and its props. When I write JSX, like angle bracket ShipmentRow with a shipment, that creates an element. Elements are immutable, once created, you don't change them. When data changes, React creates new elements, compares them with the previous ones, and updates the real DOM only where something changed.
X: So a simple way to say it, a component is the recipe, and an element is a description of one dish made from that recipe, at one moment in time. Elements aren't the actual DOM nodes either, they're descriptions that React uses to create and update the DOM.
X: This also explains why we never call components directly as functions in JSX code. We create elements, and React decides when to call the component.

X: In React, components can be written as classes or as functions, and today functional components with hooks are pretty much the standard.

X: Props and state are the two kinds of data that control what a React component shows.
X: Props, short for properties, are inputs passed into a component from its parent, like arguments to a function. Say a ShipmentRow receives a shipment object as a prop. Props are read-only inside the component, the component must never change them. If the parent passes new props, the component re-renders with them.
X: State is data that a component owns and manages itself, and which can change over time, usually because of user actions or data loading. Like whether a dropdown is open, the text in a search box, or the list of shipments after an API call. In a functional component, I create state with useState, which gives me the current value and a setter function. Calling the setter tells React the state changed, and React re-renders the component.

+@p7-5
X: The dependency array is the second argument to hooks like useEffect, useMemo and useCallback. It tells React when to rerun the effect, or recalculate the value, so only when one of the listed values has changed since the last render.
X: For useEffect, you've got three cases. With no array at all, the effect runs after every render, which is rarely what you want. With an array of values, like userId, the effect runs after the first render and then again whenever userId changes. That's the normal case, like fetching a user's data whenever the selected user changes. With an empty array, the effect runs only once, after the component first mounts, because there's nothing that can change. That's used for one-time setup, like subscribing to an event. If the effect returns a cleanup function, React runs it before the effect runs again, and when the component unmounts. That's where you unsubscribe, or cancel a request.
X: The important rule is that the array has to include every value from the component that the effect uses, like props, state, and functions. If you leave one out, the effect keeps using an old value, which is called a stale closure, and causes subtle bugs. People miss this a lot. The ESLint rule for exhaustive dependencies catches it, and we keep it switched on.
X: Also, in development with Strict Mode, React runs effects twice on purpose, to help find missing cleanups.
+@p7-6
X: useMemo and useCallback are both React hooks for avoiding unnecessary work between renders, by remembering something until its dependencies change.
X: useMemo remembers the result of a calculation. You give it a function and a dependency array, and it only recalculates when a dependency changes. Like filtering and sorting a large list of shipments, useMemo means that work only happens when the list or the filter changes, not on every render.
X: useCallback remembers a function itself. Normally, every render creates a new function object, even if the code is the same. That matters when the function is passed as a prop to a child component wrapped in React.memo, or used in another hook's dependency array, because a new function each time would make the child re-render, or the effect rerun, every time. useCallback returns the same function instance until its dependencies change.
X: So the difference is, useMemo caches a value, useCallback caches a function. In fact, useCallback of a function is the same as useMemo returning that function.
X: Honestly, I don't use them everywhere, because they have their own cost and make code harder to read. I use them when there's a real reason, an expensive calculation, a memoised child component, or a value used as a dependency. And the new React Compiler can apply this memoisation automatically, which reduces the need to write them by hand.

X: useRef is a React hook that gives you a mutable object with a current property, which stays the same for the whole life of the component. The big difference from state is that changing ref.current doesn't cause a re-render.
X: It has two main uses. Accessing a DOM element directly is the common one. You create a ref, attach it to an element with the ref attribute, and then ref.current points to that DOM node. That's useful for things React doesn't handle declaratively, like focusing an input when a dialog opens, scrolling to an element, measuring its size, or plugging in a non-React library, like a chart.
X: The other is keeping a value between renders without displaying it. X: Controlled and uncontrolled components are basically two ways to handle form inputs in React.
X: In a controlled component, React state is the single source of truth for the input's value. The input's value attribute is set from state, and an onChange handler updates the state on every keystroke. So React always knows the current value. +@p7-11
X: Unnecessary re-rendering happens when components render again even though what they show hasn't changed. A little is normal and fine, but in large screens it can make the UI slow.
X: The usual causes, from what I've seen. A parent re-renders, and by default, all its children re-render too, even if their props are the same. New object, array or function props created on every render, like an inline style object, or an inline arrow function as onClick. Even with React.memo on the child, those are new references each time, so the child still re-renders. Context, when a provider's value changes, every consumer re-renders, and if the value is a new object on every render, they re-render every time. State kept too high in the tree, so a small change, like typing in a search box, re-renders a whole page. Derived data stored in state and synced with effects, causing extra render cycles. And unstable list keys, like using the array index, which can make React recreate items.
X: To fix them, measure with the React DevTools Profiler before touching anything. Then move state down to where it's used, memoise expensive children with React.memo, use useMemo and useCallback for stable props, split contexts, use stable ids as keys, and virtualise long lists, so only visible rows render.
X: The new React Compiler handles a lot of the memoisation automatically.

X: var, let and const are the three ways to declare variables in JavaScript, and they differ in scope, hoisting and reassignment.
X: var is the old way. It's function-scoped, meaning it's visible throughout the whole function, ignoring blocks like if statements and loops. It's hoisted and initialised as undefined, so you can use it before its declaration line without an error, which hides bugs. And it can be declared again in the same scope. A classic problem is var in a loop with callbacks, where all the callbacks share one variable and see the final value.
X: let and const came in with ES2015 and are block-scoped, they only exist inside the nearest curly braces. They're also hoisted, but not initialised, so using them before the declaration throws an error. That period is called the temporal dead zone. They can't be redeclared in the same scope.
X: The difference between let and const is reassignment. let can be reassigned. const can't be reassigned after it's created. But const doesn't make the value immutable, and people mix this up a lot. A const object or array can still have its contents changed, you just can't point the variable to a different object.
X: My rule is const by default, let only when the value has to change, like a counter, and never var. ESLint rules enforce this in our projects.
+@p7-17
X: Hoisting is JavaScript's behaviour of processing declarations before running the code in a scope. It feels as if declarations are moved to the top of their scope, though really the engine registers them during a setup phase.
X: How it behaves depends on what's declared. Function declarations are hoisted completely, both the name and the body, so you can call a function before the line where it's written. var declarations are hoisted and initialised to undefined. So if you use a var variable before its declaration, you don't get an error, you get undefined, which can hide bugs. let and const are hoisted too, but not initialised. Using them before the declaration throws a ReferenceError. The time between the start of the scope and the declaration is called the temporal dead zone. Classes behave like let. And function expressions or arrow functions assigned to a variable follow the variable's rules. So with var, the variable exists but is undefined, and calling it fails with "is not a function", and with const, you get a ReferenceError.
X: In practice, hoisting is mostly something to understand, not rely on, I'd say. I declare variables before using them, use const and let instead of var, and let ESLint flag anything used before it's defined. That avoids the confusing bugs hoisting can cause.
+@p7-18
X: A closure in JavaScript is a function that remembers the variables from the place where it was created, and can keep using them even after that outer function has finished running.
X: Every function in JavaScript keeps a reference to its surrounding scope. So if an outer function creates a local variable and returns an inner function that uses it, the inner function keeps access to that variable, and the variable stays alive as long as the inner function exists.
X: A simple example. A function makeCounter creates a variable count set to zero, and returns a function that adds one to count and returns it. Each time I call makeCounter, I get a new counter with its own private count. Nothing outside can change count directly, so closures are also a way to create private state.
X: Closures are everywhere in real code, honestly. Event handlers and callbacks that use variables from the component, functions like debounce and memoise, and React hooks, where every render's functions capture that render's props and state. That's also where a common bug comes from, a stale closure, when a callback or effect keeps using an old value of state. That's why the dependency array in useEffect matters.
X: The classic loop issue is a closure issue too. Callbacks created in a loop with var all share one variable, while let creates a new variable for each iteration.

X: Okay, so a Promise is an object that represents the future result of an asynchronous operation, like an API call. It's in one of three states, pending, while waiting, fulfilled, with a value, or rejected, with an error. Once it's settled, it doesn't change.
X: With Promises directly, you handle the result by chaining then for success, catch for errors, and finally for cleanup. Each then returns a new Promise, so steps can be chained one after another. There are also helpers for running several at once. Promise.all waits for all of them and fails if any fails, Promise.allSettled waits for all and reports each result, Promise.race takes the first to settle, and Promise.any takes the first success.
X: async and await is newer syntax built on top of Promises. It doesn't replace them, it makes them easier to read. An async function always returns a Promise, and inside it, await pauses that function until the Promise settles, without blocking the main thread. Errors are handled with a normal try, catch and finally. So the code reads top to bottom like synchronous code.
X: I use async and await almost everywhere for clarity. But I still use Promise.all to run independent calls in parallel, because awaiting them one after another would make them run in sequence and be slower.
+@p7-20
X: Callback hell is basically what happens when asynchronous code is written with nested callbacks, where each step is passed a function to call when it finishes, and the next step goes inside that function. With several steps in a row, the code keeps moving to the right, forming a pyramid shape, which is why it's also called the pyramid of doom.
X: Like, read a file, and in its callback, parse it, and in that callback, call an API, and in that callback, save the result. Each level also needs its own error check, usually the "if error, return" pattern in Node.js. The problems are that it's hard to read, hard to follow the flow, easy to forget error handling at one level, and difficult to do things like run steps in parallel or retry.
X: The solutions came in stages. Naming the functions and keeping them flat helps a little. Then Promises allowed chaining with then, and one catch for all errors. And today, async and await lets you write the same sequence as straight, top-to-bottom code, with normal try and catch. In Node.js, most built-in modules now have Promise versions, like fs slash promises, and util.promisify converts older callback functions.
X: So in modern code, callback hell is mostly avoided just by using async and await consistently.

X: Optional chaining and nullish coalescing are two JavaScript and TypeScript operators that make it much safer and cleaner to work with values that might be null or undefined.
X: Optional chaining, the question mark dot operator, lets you access a property deeply without checking each level. Like, user question-mark-dot address question-mark-dot city. If user or address is null or undefined, the whole expression just returns undefined, instead of throwing a "cannot read property of undefined" error. It also works for calling functions that might not exist, and for array access.
X: Nullish coalescing, the double question mark operator, gives a default value, but only when the left side is null or undefined. Say, settings dot pageSize double question mark 20.
X: The thing is how it differs from the older OR operator. OR returns the right side for any falsy value, zero, an empty string, false, and NaN, as well as null and undefined. X: any and unknown are both TypeScript types that can hold any value, but they're kind of opposites in terms of safety.
X: any switches off type checking. You can assign anything to it, and you can do anything with it, call methods, access properties, pass it anywhere, and TypeScript won't complain. X: unknown is the safe version. You can assign anything to it, but you can't use it until you prove what it is. X: Union types, intersection types and narrowing are how TypeScript models values that can take different shapes.
X: A union type, written with a vertical bar, means a value can be one of several types. Like string or number, or a status that's one of the literal strings Pending, Shipped or Delivered. That's a very common way to model fixed sets of values.
X: An intersection type, written with an ampersand, combines several types into one that has all their properties. Say a Shipment type and an Auditable type combined give an object with the shipment fields and the audit fields.
X: Type narrowing is how TypeScript works out the more specific type inside a union, based on checks in your code. If a value is string or number and I check typeof value equals string, inside that if block TypeScript knows it's a string. Other ways to narrow are instanceof, the in operator, equality checks, and custom type guard functions that return "value is Type".
X: The most useful pattern, I think, is a discriminated union. Each type in the union has a common literal property, like kind or status. Like an API result that's either success with data, or error with a message. A switch on that property narrows it fully. And with a never check in the default case, TypeScript gives an error if I add a new case and forget to handle it.

X: Strict mode can mean two things, honestly, and both are worth knowing.
X: In TypeScript, strict mode is the strict option in tsconfig. It turns on a group of stronger type checks. The big one is strictNullChecks, where null and undefined are no longer allowed everywhere, so TypeScript forces you to handle missing values, which prevents the most common runtime errors. Others include noImplicitAny, which reports values whose types TypeScript can't infer instead of quietly using any, strict function types, strictPropertyInitialization, which checks class properties are initialised, and treating catch errors as unknown. For new projects, I always turn strict mode on, and lots of teams add extra options too, like noUncheckedIndexedAccess. For older code, it can be enabled gradually.
X: In JavaScript, strict mode is enabled with the "use strict" directive at the top of a file or function. It makes JavaScript less forgiving. Like, assigning to an undeclared variable throws an error instead of creating a global variable by accident, this is undefined in plain function calls instead of the global object, and some unsafe features, like the with statement, aren't allowed. ES modules and classes are in strict mode automatically.
X: And in React, there's also StrictMode, a component that runs extra checks in development, like rendering components twice to find side effects.
X: All three exist to catch mistakes early, which is why I keep them on.
