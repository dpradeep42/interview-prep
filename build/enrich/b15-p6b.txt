@p6-33
Q: Kafka is a distributed, durable, append-only event log. A broker is a Kafka server; a topic is a named stream of events; a partition is an ordered shard of a topic; an offset is a record's position in a partition; producers append records (choosing partitions by key); consumers read and track offsets, usually in consumer groups.
- Since Kafka 4.0 (2025), KRaft replaces ZooKeeper entirely for metadata.
- Records have key, value, headers and timestamp.
- Consumers pull; brokers don't push.
? Why pull instead of push? :: Consumers control their pace and batching.
? What replaced ZooKeeper? :: KRaft, Kafka's built-in Raft-based metadata quorum.

@p6-34
Q: Scalability comes from partitions spread across brokers, consumer groups sharing partitions, sequential disk writes, zero-copy and batching with compression. Fault tolerance comes from replicating each partition to several brokers with leader election from in-sync replicas, plus consumers resuming from committed offsets.
- Producer batching (linger.ms, batch.size) and compression (lz4, zstd).
- Page cache use makes reads fast.
? What is zero-copy? :: Sending data from page cache to the network socket without copying into user space.
? What happens when a broker fails? :: Leadership of its partitions moves to in-sync followers.

@p6-35
Q: Replication factor is how many copies of each partition exist across brokers (typically 3); the leader handles reads and writes, followers copy it, and the in-sync replicas (ISR) are followers that are caught up. With acks=all and min.insync.replicas=2, a write is acknowledged only when at least two replicas have it.
- unclean.leader.election.enable=false prevents data loss by not electing out-of-sync replicas.
- Followers can serve reads (KIP-392, rack-aware fetching) to reduce cross-AZ traffic.
? What if ISR drops below min.insync.replicas? :: Producers with acks=all get errors instead of risking loss.
? Why RF 3? :: Survives one broker failure while still meeting min ISR 2.

@p6-36
Q: Ordering is guaranteed only within a partition, not across a topic. I use a key (such as ShipmentId) so all events for one entity go to the same partition in order, and enable the idempotent producer (default since Kafka 3.0) so retries don't reorder or duplicate.
- Changing partition count changes key mapping for new records.
- Consumer-side parallelism must preserve per-key order.
- max.in.flight.requests.per.connection up to 5 is safe with idempotence.
? Global ordering? :: Only with one partition, which limits throughput.
? How can a consumer break ordering? :: Processing messages of the same key in parallel threads.

@p6-37
Q: Retention keeps records for a time or size limit (e.g. 7 days) whether consumed or not, allowing replay. Log compaction keeps at least the latest record per key and removes older ones, so a topic acts like a changelog of current state; a null value (tombstone) deletes a key.
- cleanup.policy=delete, compact, or both.
- Compacted topics suit state like "current shipment status per id" or KTable sources.
- Tiered storage moves old segments to S3-like storage.
? What is a tombstone? :: A record with a key and null value that marks the key for deletion in compaction.
? Is compaction immediate? :: No, it runs in the background on closed segments.

@p6-38
Q: Its group rebalances and its partitions move to the remaining consumers, which resume from the last committed offset. Messages processed but not committed are processed again, so handlers must be idempotent; commit after processing for at-least-once.
- session.timeout.ms and heartbeat detect crashes; max.poll.interval.ms detects stuck processing.
- Cooperative sticky assignor and the new consumer group protocol (KIP-848, Kafka 4.0) reduce rebalance pauses.
- Static membership avoids rebalances on quick restarts.
? Commit before or after processing? :: After, for at-least-once; before risks loss.
? What's max.poll.interval.ms? :: Maximum time between polls before the consumer is considered failed.

@p6-39
Q: Lag is the latest offset minus the committed offset: how far a consumer group is behind. I troubleshoot by checking which partitions lag (hot keys), slow processing or downstream dependencies, errors and retries, rebalances, and too few consumers; then fix the bottleneck, scale consumers up to the partition count, or batch work.
- kafka-consumer-groups --describe shows lag per partition.
- Monitor lag in time (seconds behind), not just messages.
- Burrow, CloudWatch MSK metrics or Grafana.
```bash
kafka-consumer-groups --bootstrap-server $BROKERS --describe --group shipment-status-consumers
```
? Lag on one partition only? :: Likely a hot key or a poison message blocking it.
? Will adding consumers always help? :: Only up to the number of partitions.

@p6-40
Q: Add consumers to the group up to the partition count, increase partitions (key mapping changes for new data), or process in parallel inside a consumer while keeping per-key order. Consumers beyond the partition count sit idle as hot standbys.
- Size partitions for future peak throughput.
- Parallel processing libraries (Confluent parallel consumer pattern) key-ordered.
? Can you decrease partitions? :: No; create a new topic and migrate.
? Idle consumers useless? :: They take over quickly if another consumer fails.

@p6-41
Q: One topic per event type or business stream (e.g. irt.shipments.status-changed.v1) with a clear naming convention and a versioned schema (Avro, Protobuf or JSON Schema in a registry); partitions sized for throughput; keys chosen for ordering; retention and compaction set per use case; and ACLs per producer and consumer.
- Compatibility rules (backward/forward) in the schema registry.
- Events should be facts in past tense with ids and timestamps.
- Avoid too many tiny topics or one giant topic for everything.
? Fat vs thin events? :: Fat events carry full data (fewer callbacks); thin events carry ids (consumers fetch details).
? How do you evolve a schema? :: Add optional fields; never remove or change types without a new version.

@p6-42
Q: A poison message always fails and blocks the partition. I retry transient errors a few times with backoff (in-process or via retry topics), send permanently failing messages to a dead-letter topic with error headers, commit and move on, and alert and replay after a fix.
- Distinguish transient (timeout) from permanent (deserialization, validation) errors.
- Retry topics with delays preserve throughput but break strict ordering.
- Store original topic, partition, offset and exception in headers.
? Why not retry forever? :: It blocks all later messages in that partition.
? How do you replay a DLT? :: A tool consumes it and republishes to the original topic after the fix.

@p6-43
Q: Secure Kafka with TLS in transit, SASL authentication (SCRAM or IAM on Amazon MSK), ACLs per topic and group, encryption at rest and private networking. Monitor broker health, under-replicated partitions, request latency, disk usage, producer errors and consumer lag, with alerts.

@p6-44
Q: RabbitMQ is a message broker (AMQP 0-9-1, plus AMQP 1.0 native since 4.0) that routes messages from producers through exchanges to queues for consumers. A queue stores messages until consumers process them; a binding is a rule linking an exchange to a queue, with a routing key or pattern.
- Producers publish to exchanges, never directly to queues (the default exchange routes by queue name).
- Queue types: classic, quorum (replicated, Raft) and streams.
- Classic mirrored queues were removed in 4.0; use quorum queues for HA.
? What is a vhost? :: A logical namespace isolating exchanges, queues and permissions.
? Quorum vs classic queues? :: Quorum queues are replicated and safer; classic queues are single-node.

@p6-45
Q: A consumer ack tells RabbitMQ the consumer processed the message so it can be deleted; nack or no ack (on disconnect) requeues or dead-letters it. A publisher confirm is the broker telling the publisher it safely received the message. Consumer acks protect the consumer side; confirms protect the publisher side; both are needed.
- Manual acks after processing; autoAck=true loses messages on failure (Part 3 Q26).
- Consumer timeout (default 30 minutes) closes channels with long-unacked messages.
? What happens to unacked messages if a consumer dies? :: They're requeued and redelivered with the redelivered flag set.
? Ack multiple? :: multiple=true acks all up to a delivery tag, reducing overhead.

@p6-46
Q: A durable queue or exchange survives a broker restart (its definition); a persistent message (delivery mode 2) is written to disk. You need both for messages to survive a restart, and publisher confirms to know they were actually stored. Quorum queues are always durable and persist messages.
- Persistence costs throughput; transient messages suit non-critical data.
- Lazy behaviour (messages on disk) is default for quorum queues and classic v2.
? Durable queue with non-persistent messages? :: The queue survives, but messages are lost on restart.
? Does persistence alone prevent loss? :: No; without confirms, messages can be lost before reaching disk.

@p6-47
Q: Publishers can't send: they should retry with backoff or write to an outbox table and publish later; consumers reconnect automatically when it returns (automatic recovery in the .NET client). Durable queues with persistent messages keep data; quorum queues across nodes keep the service available if one node fails.
- Health checks and alerts on connection failures.
- Circuit breaker on publishing to avoid thread pile-ups.
? Does the .NET client reconnect? :: Yes, with AutomaticRecoveryEnabled (default true) and topology recovery.
? How do you avoid losing events while it's down? :: Outbox pattern.

@p6-48
Q: For transient errors I retry in-process a few times, then nack to a retry queue with a TTL that dead-letters back to the main queue (delayed retry); after a maximum number of attempts (tracked via the x-death header or a count header), the message goes to a DLQ with an alert.
- Quorum queues support delivery limits (x-delivery-limit, default 20 in 4.0) to stop poison loops.
- Exponential backoff with several retry queues of increasing TTL.
- Libraries like MassTransit provide retry and redelivery policies.
? Why not requeue immediately? :: It creates hot loops hammering a failing dependency.
? What is x-death? :: A header RabbitMQ adds with dead-lettering history, including counts.

@p6-49
Q: Publisher confirms (our outage fix), durable queues, persistent messages, quorum queues, manual consumer acks after processing, dead-letter queues, the outbox pattern for publish-after-commit, and monitoring of queue depth, unroutable messages and memory alarms.

- Idempotent consumers because redelivery happens.
? What's the most commonly missed piece? :: Publisher confirms.
? What are unroutable messages? :: Messages with no matching binding, dropped silently unless handled.

@p6-50
Q: Scale with more competing consumers per queue and tuned prefetch, clustering with quorum queues, splitting hot queues, and bigger nodes or Amazon MQ. Monitor queue depth, publish/deliver/ack rates, unacked counts, consumer counts, memory and disk alarms, connection churn and DLQ size via Prometheus and Grafana or CloudWatch.
- One queue is bound to one node's leader; spread queues across nodes.
- Avoid huge backlogs; queues work best near empty.
- Watch for connection and channel leaks.
? Why do huge queues hurt? :: Memory pressure, slow recovery and triggered alarms.
? How do you choose prefetch? :: Based on processing time and consumers; start small (10–50) and measure.
