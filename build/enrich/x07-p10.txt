X: Middleware is a component that sits in the ASP.NET Core request pipeline. Every HTTP request passes through a chain of middleware, and each one gets the HttpContext and a reference to the next one in the chain.
X: Each middleware can do three things. It can do some work before the request goes further, like reading headers. It can call next, to pass the request to the next middleware. And after next returns, it can do work on the way back, like adding a response header or logging the duration. It can also decide not to call next and end the request early, which is called short-circuiting. The pipeline is built in Program.cs with app.Use calls, and it runs in exactly the order you register them, which is why the order matters so much.
X: A lot of the framework is just middleware: exception handling, HTTPS redirection, static files, routing, CORS, authentication, authorization, rate limiting, and finally the endpoints.
X: In my project, I wrote a correlation-id middleware, so every request carries one id across our [4] services, and one log search shows the whole journey. I can walk you through how I wrote that one.

X: There are two fixes. For convention-based middleware, take scoped services as extra parameters of InvokeAsync, which are resolved per request. X: Rate limiting limits how many requests a client, or an endpoint, can make within a period. When the limit is exceeded, the API returns 429 Too Many Requests, ideally with a Retry-After header. It protects the service from abuse, accidental loops in a client, and one noisy consumer starving everyone else.
X: Since ASP.NET Core 7, there's built-in rate limiting middleware. In Program.cs I call AddRateLimiter and define policies. Policies can be partitioned, so each user, IP address or API key gets its own limit. Then I add UseRateLimiter to the pipeline, and apply policies per endpoint with RequireRateLimiting or the EnableRateLimiting attribute.
X: In a multi-instance setup, these limits are per instance, so for global limits we also use API Gateway or WAF limits.

X: IHttpClientFactory is the recommended way to create HttpClient instances in .NET, because using HttpClient naively causes two opposite problems.
X: If you create and dispose a new HttpClient for every request, each one opens new connections, and closed sockets stay in the TIME_WAIT state for a while. Under load, you can run out of sockets. X: Span of T is a type that gives you a view over a contiguous block of memory, like part of an array, a string, or stack memory, without copying it. Slicing a span is free, it just points to a different start and length.
X: That makes it perfect for high-performance parsing. For example, instead of calling Substring, which allocates a new string each time, I can slice a ReadOnlySpan of char and parse numbers directly from it. Span is a ref struct, so it can only live on the stack. That's what makes it safe and fast, but it also means it can't be a field in a class, can't be boxed, and can't be used across an await. Memory of T is the companion type that can live on the heap, so it works in async methods, and you get a span from it when you need to do the work.
X: Many .NET APIs now accept spans, like int.Parse, so you can avoid allocations entirely.
X: I used this when optimising our CSV parsing. Reading fields as spans instead of splitting strings reduced allocations a lot, which reduced garbage collection during large imports. I can explain ArrayPool, which works well with it.

X: IAsyncEnumerable of T is an asynchronous sequence. It lets you produce and consume items one at a time, where getting each item may involve async work, like reading from a database, a file or a network stream.
X: To produce one, you write an async iterator: an async method returning IAsyncEnumerable that uses await and yield return. To consume it, you use await foreach. X: These four are all caching, but at different levels.
X: Response caching is based on HTTP headers. The server sets Cache-Control headers, and browsers and proxies can reuse the response. X: JWT bearer authentication in ASP.NET Core is split between two middleware: authentication, which works out who you are, and authorization, which decides what you can do.
X: When a request comes in, UseAuthentication runs the default scheme handler, which is JwtBearerHandler. It reads the Authorization header, "Bearer" followed by the token, and validates it. X: I configure it with AddAuthentication and AddJwtBearer, with the authority and audience, and keep clock skew small.

X: System.Threading.Channels provides high-performance, thread-safe queues for the producer-consumer pattern inside one process.
X: You create a channel with Channel.CreateBounded or CreateUnbounded. Producers write items with WriteAsync, and consumers read them with ReadAllAsync in an await foreach loop. It's fully async, so no threads are blocked while waiting. A bounded channel has a maximum capacity, which gives you backpressure. When it's full, you choose whether the writer waits, or the channel drops the oldest or newest item. That stops a fast producer from exhausting memory. You can also have multiple readers to process items in parallel.
X: The typical pattern is pairing it with a BackgroundService. An HTTP request quickly writes a job into the channel and returns 202 Accepted, and the background service reads and processes jobs one by one. Of course, it's in-memory, so for work that must survive a restart, a durable queue like RabbitMQ or SQS is the right choice.
X: We used a bounded channel for sending non-critical notification emails, so slow email calls never delayed API responses. I can compare it with BlockingCollection.
