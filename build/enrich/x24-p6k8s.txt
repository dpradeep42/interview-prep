X: Kubernetes is an open-source platform for running containers across a cluster of machines. It's often called a container orchestrator.
X: The core idea is desired state. I describe what I want in YAML, like "run three copies of this image, with this much memory, reachable on this port", and Kubernetes continuously works to keep reality matching that description. If a container crashes, it restarts it. If a whole node fails, it reschedules the pods onto healthy nodes. If I change the image version, it does a rolling update, replacing pods gradually with no downtime, and it can roll back.
X: It also handles the other things you need to run services at scale: scheduling containers onto nodes based on the resources they need, service discovery and load balancing, so services find each other by name, scaling, manually or automatically based on CPU or custom metrics, configuration and secrets through ConfigMaps and Secrets, and health checks with readiness and liveness probes.
X: The main building blocks are pods, the smallest unit, wrapping one or more containers; Deployments, which manage replicas and updates; Services, which give pods a stable address; and Ingress, for HTTP routing from outside.
X: Our production services run on Amazon ECS, which follows the same ideas, and we use Kubernetes in our [dev] cluster for internal tooling services. Understanding Kubernetes helped me there, for example to fix a crash loop caused by a liveness probe that checked too early.
+@p6-18
X: These are three types of Kubernetes Service, and they differ in where the service can be reached from.
X: A Service gives a set of pods one stable address, because pods come and go and their IP addresses change. The Service finds its pods by labels and load-balances traffic across them.
X: ClusterIP is the default type. It gives the service an internal IP address that's only reachable from inside the cluster. It's used for internal communication, for example an API calling another service, or connecting to a database inside the cluster. Most services are ClusterIP.
X: NodePort exposes the service on a fixed port, from a range like 30000 to 32767, on every node in the cluster. So anyone who can reach a node's IP can reach the service on that port. It's simple, but you have to manage node addresses and the unusual port numbers yourself, so it's mainly used for testing, or behind your own load balancer.
X: LoadBalancer asks the cloud provider to create an external load balancer, like an AWS load balancer, which sends traffic to the service. It's the standard way to expose one service publicly, but each one creates a separate load balancer, which costs money.
X: Each type builds on the previous one. And for HTTP services, it's usually better to use an Ingress, or the Gateway API: one load balancer that routes many hostnames and paths to internal ClusterIP services.
+@p6-19
X: A ReplicaSet is a Kubernetes object whose job is to make sure a specified number of identical pods are running at all times. You say "I want three replicas of this pod", and the ReplicaSet watches the cluster. If a pod crashes or a node fails, and there are only two, it creates a new one. If somehow there are four, it removes one. It finds the pods it owns using a label selector.
X: In practice, you almost never create ReplicaSets directly. You create a Deployment, and the Deployment creates and manages ReplicaSets for you. The reason is updates. A ReplicaSet can keep pods running, but it doesn't know how to update them from one version to another. A Deployment does. When you change the image version in a Deployment, it creates a new ReplicaSet for the new version, and gradually scales the new one up and the old one down. That's a rolling update. The old ReplicaSet is kept, scaled to zero, which is what makes a quick rollback possible: the Deployment just scales the old ReplicaSet back up.
X: So the relationship is: a Deployment manages ReplicaSets, and a ReplicaSet manages pods.
X: When I'm troubleshooting a deployment, kubectl get replicasets is useful, because it shows the old and new versions and how many pods each one has, which tells me whether a rollout is stuck.
+@p6-20
X: A rolling deployment updates an application gradually, replacing old instances with new ones a few at a time, so the service stays available throughout, with no downtime.
X: In Kubernetes, when you change a Deployment's image, it creates new pods with the new version, waits for each one to pass its readiness probe, and only then removes old pods. Two settings control the pace. maxSurge says how many extra pods can be created above the desired count, and maxUnavailable says how many can be missing during the update. Readiness probes are critical here; without them, traffic could go to pods that aren't ready yet. Amazon ECS works the same way, using minimum and maximum healthy percentages, and the load balancer's health checks.
X: A rollback means returning to the previous version when the new one has problems. In Kubernetes, kubectl rollout undo switches back to the previous ReplicaSet, which is kept for exactly this reason. On ECS, you redeploy the previous task definition, and ECS also has a deployment circuit breaker that can roll back automatically if new tasks keep failing.
X: Two important points. During a rolling update, old and new versions run at the same time, so they must be compatible, including with the database schema. That's why we make database changes backward compatible. And rollback doesn't undo data changes, so those need their own plan.
+@p6-21
X: When a pod's container crashes, Kubernetes handles it automatically, based on the pod's restart policy, which is Always for Deployments.
X: The kubelet on that node sees that the container's process has exited, and restarts the container inside the same pod. If it keeps crashing, Kubernetes waits longer between each restart, 10 seconds, 20, 40, up to five minutes. That's the CrashLoopBackOff status you see in kubectl get pods. While the container isn't ready, its readiness check fails, so the Service stops sending it traffic, and the other replicas keep serving users. If a whole pod is lost, for example because its node fails, the ReplicaSet notices there are fewer pods than desired, and creates a new pod on another healthy node.
X: Anything stored in the container's own filesystem is lost on restart, which is why apps should be stateless or use persistent volumes.
X: To find the cause, I use kubectl describe pod to see the events and the last state, including the exit code and reason, like OOMKilled for out of memory, and kubectl logs with the previous flag, to see the logs from the crashed container.
X: A real example from our [dev] cluster: a service kept crash-looping with no errors in its logs. The events showed it was being killed by its liveness probe, because it needed [about 40 seconds] to warm up. A startup probe fixed it.

X: Service discovery is how one service finds another, when pods are created and destroyed all the time, and their IP addresses keep changing.
X: Kubernetes solves this with Services and DNS. A Service selects a group of pods by their labels, and gets a stable virtual IP address and a stable DNS name. Kubernetes keeps track of the IPs of the healthy pods behind it, the endpoints, and updates them automatically as pods come and go. Only pods that pass their readiness probe are included.
X: The cluster runs a DNS server, CoreDNS. Every Service gets a DNS name like orders-api dot shop dot svc dot cluster dot local. Within the same namespace, a pod can simply call http colon slash slash orders-api, and from another namespace, orders-api dot shop. When a request is sent to the Service's IP, kube-proxy on each node routes it to one of the healthy pods, which also gives basic load balancing.
X: There's also a headless Service, with no virtual IP, where DNS returns the individual pod addresses. That's used for things like databases, where clients need to talk to specific pods.
X: The benefit is that application code doesn't need any discovery logic. In a .NET app, the other service's base URL is just its service name in configuration. Amazon ECS offers the same idea with Service Connect or Cloud Map.

X: I'd secure Kubernetes in layers: who can access the cluster, what workloads can do, how they talk to each other, and what goes into them.
X: First, access control. Use RBAC with least privilege, so people and service accounts only get the permissions they need, preferably limited to a namespace. Users sign in through the company's identity provider, and the API server isn't exposed publicly. Second, workload security. Pods run as non-root, with a read-only root filesystem, no privilege escalation, and dropped Linux capabilities. Pod Security Admission can enforce the restricted standard for a namespace. Pods should only mount a service account token if they need one. Third, network policies. By default, every pod can talk to every other pod, so I'd add network policies that only allow the traffic each service needs. Fourth, secrets. Kubernetes Secrets are only base64 encoded, so enable encryption at rest, restrict who can read them, and preferably sync them from an external vault, like AWS Secrets Manager. Fifth, images. Use trusted, minimal base images, scan them in the pipeline with a tool like [Trivy], and only allow images from our own registry. And sixth, keep Kubernetes and nodes updated, and enable audit logging and monitoring.
X: Resource limits on every container also matter, so one workload can't starve the others.

X: To deploy a .NET application to Kubernetes, I'd go through four steps: containerise it, publish the image, describe how it runs, and deploy it through a pipeline.
X: First, a multi-stage Dockerfile. The SDK image builds and publishes the app, and the final image uses the smaller ASP.NET runtime image, runs as a non-root user, and listens on port 8080. Second, the pipeline builds the image, runs tests, scans it, tags it with the build version, and pushes it to a registry, like Amazon ECR.
X: Third, the Kubernetes manifests, often as a Helm chart. A Deployment sets the image tag, the number of replicas, CPU and memory requests and limits, and environment variables, with normal settings from a ConfigMap and secrets from Kubernetes Secrets, ideally synced from a secrets manager. It also sets readiness and liveness probes, pointed at the app's health check endpoints, which I add in ASP.NET Core with AddHealthChecks and MapHealthChecks. For slow-starting apps, a startup probe too. A Service gives it a stable internal address, and an Ingress exposes it over HTTP. A horizontal pod autoscaler can scale it on CPU.
X: Fourth, the pipeline deploys with helm upgrade, or a GitOps tool like Argo CD, as a rolling update.
X: And the app itself must handle SIGTERM, so it finishes in-flight requests before shutting down. ASP.NET Core does this by default, within the shutdown timeout.

X: In CI, unit tests run automatically on every pull request and every merge, and if any test fails, the build fails, so broken code can't be merged.
X: In our Azure DevOps pipelines for .NET, the steps are: restore the NuGet packages, build the solution in Release mode, then run dotnet test, which finds and runs all the test projects. I use a logger that produces results in the TRX format, which the pipeline publishes, so the test results appear in the build summary, with each failing test, its error and its history. I also collect code coverage, using the XPlat Code Coverage collector with Coverlet, and publish a coverage report, which is also sent to SonarQube, where the quality gate checks the coverage of new code.
X: Branch policies in Azure DevOps require this build to pass before a pull request can be completed. So nothing reaches the main branch without passing tests.
X: A few practical points. Unit tests must be fast and independent of databases or networks, so they run quickly on every change. Slower integration tests can run in a separate stage. Flaky tests are fixed or quarantined quickly, because if people stop trusting the tests, they start ignoring failures.
X: I once had a quality gate fail at [68 percent] coverage against an [80 percent] requirement, and we fixed it in [half a day] by adding meaningful tests.

X: SonarQube is a static code analysis platform. It examines source code without running it, and reports problems in a few categories: bugs, which are code likely to behave wrongly; vulnerabilities and security hotspots, like possible SQL injection or hard-coded passwords; code smells, which are maintainability issues, like overly complex methods or duplication; plus code coverage from our test results, and duplicated code.

X: An artifact is the output of a build that gets deployed, for example a zip of published .NET files, a NuGet package, or a Docker image. The key principle is "build once, deploy many": the pipeline builds the artifact once, and that exact same artifact is promoted through every environment, dev, test, UAT and production. We never rebuild for production, because a rebuild could produce something different from what was tested.
X: Versioning makes each artifact uniquely identifiable and traceable. I use semantic versioning for releases, major, minor and patch, plus the build number, for example 4.2.1 plus build 345. Many teams calculate this automatically from Git tags, with a tool like GitVersion. For Docker images, the tag is the version, or the commit hash, never just "latest", because latest is ambiguous and makes rollback hard. The artifact also records the Git commit it came from.
X: Artifacts are stored in a repository: Azure Artifacts or the pipeline's own artifacts for packages and build output, and Amazon ECR for images, with retention rules so old ones are cleaned up, but released versions are kept.
X: In our GxP environment, this traceability is essential. For any version in production, we can show exactly which commit, build, tests and approvals produced it. It also makes rollback simple: redeploy the previous artifact.

X: To build Docker images in a pipeline, I want the build to be repeatable, fast, secure and traceable.
X: In Azure DevOps, the steps are: build the image using the multi-stage Dockerfile from the repository, tag it with a unique version, like the build number or commit hash, never just latest, run the tests, scan the image, and only then push it to the registry, which is Amazon ECR for us.
X: The Dockerfile itself does the restore, build and publish in a build stage using the .NET SDK image, and the final stage uses the small runtime image. Tests can run in their own stage, so a failing test fails the image build.
X: Speed comes from layer caching: copying project files and restoring before copying the rest of the source, and using BuildKit with a cache from the registry, because pipeline agents are often fresh machines with no local cache.
X: Security: the pipeline authenticates to the registry using a service connection, with short-lived credentials where possible. No secrets are passed as build arguments, because they can end up in the image history. And the image scan, with a tool like [Trivy], fails the pipeline on high or critical vulnerabilities.
X: The image digest and tag are saved with the build, so the release stages deploy exactly that image to every environment. That's the build-once, deploy-many principle applied to containers.

X: We deploy to AWS from Azure DevOps by connecting the pipeline to AWS securely, pushing the image, and then telling ECS to run the new version.
X: First, the connection. Azure DevOps uses an AWS service connection. The best option is OpenID Connect, where the pipeline gets short-lived credentials by assuming an IAM role, so no long-lived access keys are stored anywhere. The role only has the permissions the deployment needs, like pushing to ECR and updating specific ECS services.
X: Second, the build stage builds the Docker image, tests and scans it, and pushes it to Amazon ECR with a unique version tag.
X: Third, the release stage, per environment. It registers a new revision of the ECS task definition with the new image tag, then updates the ECS service to use it. ECS performs a rolling deployment: it starts new tasks, waits for them to pass the load balancer health checks, then stops the old ones. The deployment circuit breaker can roll back automatically if the new tasks keep failing. Infrastructure changes, like new queues or alarms, go through Terraform steps in the same pipeline, with plan and apply.
X: Each environment is a stage with its own variables, and controlled environments have approvals by named people before the stage runs.
X: Rollback is simply redeploying the previous task definition revision, which is quick because the old image is still in ECR.

X: In CI/CD, my rule is that non-secret settings live with the pipeline or the application configuration, and secrets live in a secrets manager, never in code, YAML or logs.
X: For normal settings, like environment names, URLs or feature flags, I use variable groups or stage variables in Azure DevOps, per environment, or the application's appsettings files per environment.
X: For secrets, there are two kinds. Secrets the pipeline itself needs, like credentials to reach AWS or a registry, are stored as secret variables or service connections in Azure DevOps. Secret variables are encrypted, masked in logs, and not passed to forked pull request builds. Even better is OIDC to AWS, so there's no long-lived key at all. Secrets the application needs at runtime, like database passwords, shouldn't go through the pipeline. They live in AWS Secrets Manager, and the ECS task reads them at startup through its IAM role. The pipeline only deploys a reference to the secret, not the value. Azure Key Vault can also be linked to a variable group when it's needed during the pipeline.
X: On top of that: least privilege for service connections, approvals on who can use production connections, rotation of secrets, and never echoing secrets in scripts. And we scan the repository for accidentally committed secrets.

X: Deployment approvals make sure a human, with the right authority, checks a release before it goes into a controlled environment.
X: In Azure DevOps, there are two main ways.
