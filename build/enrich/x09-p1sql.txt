X: Joins combine rows from two or more tables based on a related column, and the type of join decides what happens to rows that don't match.

X: Normalisation organises a relational database to remove duplicate data, so each fact is stored in exactly one place. Denormalisation deliberately duplicates some data to make reads faster.
X: The normal forms build on each other. In first normal form, each column holds a single, atomic value, with no repeating groups. In second normal form, every non-key column depends on the whole primary key, not part of a composite key. In third normal form, non-key columns depend only on the key, not on other non-key columns. Like, a site's country name belongs in a countries table, not repeated on every shipment row. Normalisation prevents update anomalies, where you change data in one place and forget another.
X: Denormalisation trades that safety for read speed, fewer joins, precomputed values. It's common in reporting databases, read models in CQRS, and NoSQL stores like DynamoDB, where you design tables around access patterns.
X: So for me the balance is normalised for writes, denormalised for reads. In our IRT system, the transactional database is normalised, because data integrity is critical in clinical trials. X: Isolation levels control what one transaction can see of other transactions' uncommitted or changing data. Higher isolation gives you more consistency, but more locking and less concurrency.
X: Read Uncommitted allows dirty reads, so you can see data another transaction hasn't committed yet, which might get rolled back. Read Committed, SQL Server's default, prevents dirty reads, but if you read the same row twice, it might have changed in between. Repeatable Read prevents that by holding read locks until the end, but new rows can still appear, which are called phantoms. Serializable stops phantoms too, by locking ranges, so transactions behave as if they ran one after another. And then there are the row-versioning options. Snapshot isolation, and Read Committed Snapshot, or RCSI, let readers see a consistent version of the data without taking locks, so readers don't block writers.
X: I choose per use case. Most of our workload runs fine on read committed with RCSI turned on, which honestly removed a lot of reader-writer blocking. For allocating the last available drug kits, correctness matters more, so that short transaction uses stricter locking.

X: A deadlock is when two transactions each hold a lock the other one needs, so neither can continue. SQL Server detects the cycle, picks one transaction as the victim, rolls it back, and returns error 1205.
X: The usual causes are transactions touching the same tables in a different order, transactions that are too long and hold locks while doing other work, and missing indexes, because a scan locks way more rows than a seek. Higher isolation levels make it more likely too.

X: All three remove data, but at very different levels.

X: Both page through large result sets, but they work very differently and perform very differently on deep pages.
X: OFFSET FETCH, which is Skip and Take in EF Core, says "skip the first N rows, then return the next 20". It's simple and lets you jump to any page number. But the database still has to read and throw away all the skipped rows, so page 5,000 is much slower than page 1. And if rows get inserted while someone's paging, they can see duplicates or miss rows. Keyset pagination, also called seek pagination, remembers the last row's key from the previous page and asks for "the next 20 rows after this key", using a WHERE clause on an indexed column. It seeks straight to that position, so every page is equally fast, and it's stable when data changes. The downside is you can't jump to an arbitrary page, only next and previous.
X: So what I do is use OFFSET for admin screens with small data and page numbers, and keyset for large tables, infinite scrolling, exports and APIs, returning a continuation token.
