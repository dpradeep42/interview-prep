X: A clustered index defines the physical order of the table's rows. The leaf level of the clustered index is the actual data, so there can only be one per table, and it's usually on the primary key. X: Joins combine rows from two or more tables based on a related column, and the type of join decides what happens to rows that don't match.
X: An INNER JOIN returns only rows that have a match in both tables. For example, shipments with their site. A LEFT JOIN returns every row from the left table, plus matching rows from the right, with NULLs where there's no match. So "all sites, and their shipments if any". A RIGHT JOIN is the mirror image, and in practice we just rewrite it as a LEFT JOIN. A FULL OUTER JOIN returns all rows from both sides, matched where possible, which is useful for reconciliation. A CROSS JOIN returns every combination of rows, like every site with every kit type, which is useful for generating grids but dangerous on large tables. And a SELF JOIN joins a table to itself, for example an employee table to find each person's manager.
X: A classic use of LEFT JOIN is finding missing data: LEFT JOIN and then WHERE the right side IS NULL.

X: Normalisation organises a relational database to remove duplicate data, so each fact is stored in exactly one place. Denormalisation deliberately duplicates some data to make reads faster.
X: The normal forms build on each other. First normal form: each column holds a single, atomic value, with no repeating groups. Second normal form: every non-key column depends on the whole primary key, not part of a composite key. Third normal form: non-key columns depend only on the key, not on other non-key columns. For example, a site's country name belongs in a countries table, not repeated on every shipment row. Normalisation prevents update anomalies, where you change data in one place and forget another.
X: Denormalisation trades that safety for read speed: fewer joins, precomputed values. It's common in reporting databases, read models in CQRS, and NoSQL stores like DynamoDB, where you design tables around access patterns.
X: So the balance is: normalised for writes, denormalised for reads. In our IRT system, the transactional database is normalised, because data integrity is critical in clinical trials. But reporting views, and some read models fed by events, are denormalised for speed. I can explain how we keep them in sync.

X: Isolation levels control what one transaction can see of other transactions' uncommitted or changing data. Higher isolation means more consistency, but more locking and less concurrency.
X: Read Uncommitted allows dirty reads: you can see data another transaction hasn't committed yet, which might be rolled back. Read Committed, SQL Server's default, prevents dirty reads, but if you read the same row twice, it might have changed in between. Repeatable Read prevents that by holding read locks until the end, but new rows can still appear, called phantoms. Serializable prevents phantoms too, by locking ranges, so transactions behave as if they ran one after another. Then there are the row-versioning options. Snapshot isolation, and Read Committed Snapshot, or RCSI, let readers see a consistent version of the data without taking locks, so readers don't block writers.
X: I choose per use case. Most of our workload runs fine on read committed with RCSI enabled, which removed a lot of reader-writer blocking. For allocating the last available drug kits, correctness matters more, so that short transaction uses stricter locking.

X: A deadlock is when two transactions each hold a lock that the other one needs, so neither can continue. SQL Server detects the cycle, picks one transaction as the victim, rolls it back, and returns error 1205.
X: The common causes are: transactions accessing the same tables in a different order, transactions that are too long and hold locks while doing other work, and missing indexes, because a scan locks far more rows than a seek. Higher isolation levels make it more likely.
X: To fix and prevent them: access tables in a consistent order, keep transactions short with no external calls inside, add the right indexes so locks stay narrow, and consider RCSI so readers don't take shared locks. Because deadlocks can still happen occasionally, the application should retry the victim safely, which EF Core's retrying execution strategy can do for transient errors.
X: To investigate, I use the system_health Extended Events session, which captures the deadlock graph showing both queries and the locked resources. In our system, I traced a recurring deadlock between an inventory update and a reporting query to a missing index causing a scan. Adding the index stopped it. X: All three remove data, but at very different levels.
X: DELETE removes rows one at a time, and can use a WHERE clause to remove only some rows. Each deleted row is fully logged, triggers fire, and it can be rolled back inside a transaction. X: Both page through large result sets, but they work very differently and perform very differently on deep pages.
X: OFFSET FETCH, which is Skip and Take in EF Core, says "skip the first N rows, then return the next 20". It's simple and supports jumping to any page number. But the database still has to read and discard all the skipped rows, so page 5,000 is much slower than page 1. And if rows are inserted while someone is paging, they can see duplicates or miss rows. Keyset pagination, also called seek pagination, remembers the last row's key from the previous page and asks for "the next 20 rows after this key", using a WHERE clause on an indexed column. It seeks directly to that position, so every page is equally fast, and it's stable when data changes. The downside is you can't jump to an arbitrary page, only next and previous.
X: So I use OFFSET for admin screens with small data and page numbers, and keyset for large tables, infinite scrolling, exports and APIs, returning a continuation token.
X: For our shipment history API, we switched to keyset on ShipmentDate plus Id, and deep pages became as fast as the first. I can show the query.
