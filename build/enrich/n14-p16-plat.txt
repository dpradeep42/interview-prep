T: Why does your IRT use one database per study, and how do you manage schema changes?
K: database per study, multi-tenant database, tenant per database, schema changes many databases, ssdt, dacpac, model schema, global master database
X: In our IRT, a study is one clinical trial set up in the system, and each study gets its own SQL Server database, provisioned from a common model schema of [about 560] tables. Shared data, like users, security roles and global settings, lives in a global master database.
X: It's database-per-tenant, and it suits clinical trials well. Isolation: one sponsor's trial data can never mix with another's, which helps both security and audits. Changes are backward-compatible, like adding nullable columns first, so the application works during the rollout, and deployment verifies that every study database ends on the expected version. Data fixes go through reviewed scripts, never manual edits, because it's GxP.
X: Applications pick the right database per request: the study is resolved from the request, and the connection is built for that study's database, with EF Core in the new APIs.
X: If I designed it again, I'd keep database per study for regulated data, and invest early in automation and monitoring across all the databases.

T: How do you use Quartz.NET for scheduled jobs?
K: quartz, quartz.net, scheduled jobs, job scheduler, cron jobs dotnet, background jobs, failed jobs, scheduler database
X: Our IRT, which runs randomisation and drug supply for clinical trials, has many scheduled jobs: AlertWatchDog, our alert engine, report generation, imports and exports, and housekeeping. In the legacy core, they run on Quartz.NET.
X: Quartz.NET is a job scheduling library. A job is a class with an Execute method, and a trigger says when it runs, either simple intervals or CRON expressions. We use the persistent job store in a dedicated SQL Server scheduler database, which matters for three reasons: schedules survive restarts, several servers can run in a cluster without running the same job twice, because Quartz takes database locks, and missed runs can be handled with misfire rules after downtime.
X: Some practices we follow. Jobs are idempotent, so a re-run after a failure is safe. Long jobs work in batches and respect cancellation, so a deployment can stop them cleanly. Concurrent execution is disallowed for jobs that must not overlap. Failures are recorded in a custom failed-jobs table, with the error and the study, so support can see and re-run them. And every run logs a start, an end and counts, with a correlation id.
X: For newer services, we use .NET hosted services and RabbitMQ consumers, and some file processing runs as SSIS packages, like the material forecasting load. If I were building fresh on AWS, EventBridge Scheduler would replace Quartz; on Azure, a Functions timer trigger.
X: The key lesson: a scheduler must make failures visible, because a job that silently stops is worse than one that fails loudly.

T: How is RabbitMQ used in your IRT platform?
V: rmqRetry
K: rabbitmq in irt, rabbitmq retry, dead letter exchange, retry exchange, rabbitmq consumers, messaging library, cache refresh events, publisher confirms
X: In our IRT, which runs randomisation and drug supply for clinical trials, RabbitMQ carries the asynchronous work: notifications from AlertWatchDog, our alert engine, study configuration events that refresh caches, and integration events.
X: Every service uses a shared messaging library, built on .NET Standard, so publishing and consuming work the same way everywhere, with the same connection handling, serialisation and message metadata, including a correlation id for tracing across services.
X: Consumers run as .NET 9 worker services, with some older .NET Framework consumers still running. Reliability is built into the library. X: On the publishing side, I learned the importance of publisher confirms the hard way. [In mid-2024, about 1,200 updates were silently lost during a broker problem], because publishes weren't confirmed. I root-caused it and added publisher confirms, so the publisher knows the broker has safely stored each message, and retries if not.
X: Study configuration uses events too: when a study's configuration changes, an event tells the study consumer services to refresh their caches, so every server sees the new configuration quickly.

T: How do you cache study configuration, and keep the cache fresh?
K: caching study configuration, redis, memcached, cache invalidation, cache refresh, distributed cache, config cache
X: In our IRT, a study is one clinical trial set up in the system, and its configuration, like sites, arms, visits, kit types, forms and permissions, is read on almost every request. It lives in the study's own SQL Server database, so reading it from the database every time would be slow and wasteful.
X: So configuration is cached. Historically the platform used memcached, and it now uses Redis, which is faster to operate with and supports richer data types. Services use cache-aside: read from the cache, and on a miss, load from the study database and store it, keyed by study and configuration area.
X: The hard part is invalidation. Study configuration changes rarely, but when it changes, for example after a protocol amendment is transferred to production, every server must see it quickly. We do that with events: the change publishes a study event on RabbitMQ, and the study consumer and cache refresh services clear and reload the affected keys. There's also a time-to-live as a safety net, so even a missed event can't leave stale configuration forever.
X: Some rules matter in a regulated system. Blinded data is never cached in a way that could be returned to blinded users. Transactional data, like inventory or randomisation slots, is never served from cache, because it must be exact. And caches are warmed after deployments, so the first users don't pay the cost.
X: The principle: cache what's read often and changes rarely, and make invalidation explicit and event-driven.
