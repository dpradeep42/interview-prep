@p2-4
Q: A cold start is the extra latency when Lambda creates a new execution environment: download code, start the runtime, run initialisation, then the handler. It happens on the first request, after idle periods and when scaling out. Reduce it with smaller packages, less work at init, more memory (more CPU), Provisioned Concurrency, SnapStart and, for .NET, native AOT.
- .NET options: ReadyToRun or native AOT (`PublishAot`) cut startup a lot; avoid heavy reflection and DI scanning at init.
- SnapStart (Java, Python and .NET 8 managed runtime) snapshots the initialised environment and restores it.
- Provisioned Concurrency keeps environments warm (costs money); schedule it for business hours.
- VPC cold-start penalty was largely fixed by Hyperplane ENIs, but still keep dependencies light.
- Initialise SDK clients outside the handler so warm invocations reuse them.
? Does memory affect cold start? :: Yes; CPU scales with memory, so more memory often means faster init and can even reduce cost.
? How do you measure it? :: The Init Duration field in REPORT log lines, or X-Ray traces.

@p2-5
Q: DynamoDB modelling starts from access patterns, not entities: list every query, choose a partition key with high cardinality and even traffic, a sort key for ranges and ordering, and add GSIs for other patterns. Often several entity types share one table (single-table design) with generic keys like PK = STUDY#42, SK = SITE#7.
- Item collections: items sharing a partition key can be fetched together with one Query.
- Avoid scans; every request should be GetItem or Query by key.
- Hot partitions: spread writes with sharded keys if one key gets most traffic.
- Item limit 400 KB; large payloads go to S3 with a pointer.
- Use conditional writes for idempotency and optimistic locking (version attribute), TTL for expiry, Streams for change events.
```text
PK            SK                  Attributes
IDEMP#a1b2    REQ                 status=Done, response=..., ttl=1718000000
STUDY#42      SITE#007            name, country
STUDY#42      SHIPMENT#2024-06-01#881   status, kitCount
```
? Single-table design always? :: No; it optimises known patterns but is hard to evolve; separate tables are fine for simple cases.
? Query vs Scan? :: Query reads one partition by key; Scan reads the whole table and is slow and expensive.


@p2-19
Q: A Deployment YAML declares the replica count, the label selector, and the pod template: container image and tag, ports, environment from ConfigMaps and Secrets, resource requests and limits, liveness, readiness and startup probes, security context, and the update strategy (maxSurge, maxUnavailable).

```yaml

spec:
  replicas: 3
  selector: { matchLabels: { app: shipments-api } }
  strategy: { rollingUpdate: { maxSurge: 1, maxUnavailable: 0 } }
  template:
    metadata: { labels: { app: shipments-api } }
    spec:
      containers:
      - name: api
        image: 123456789.dkr.ecr.eu-west-1.amazonaws.com/shipments-api:1.8.3
```

@p2-20
Q: A liveness probe asks "is the process healthy, or should it be restarted?"; a readiness probe asks "can it receive traffic right now?", and failing removes the pod from load balancing without restarting it; a startup probe protects slow-starting apps by disabling the other probes until startup succeeds.
- Liveness must be cheap and only check the process itself; checking the database in liveness causes restart storms when the DB blips.
- Readiness can check critical dependencies and warm-up state.
- ASP.NET Core health checks: tag checks and map /health/live and /health/ready with predicates.
- ECS has container health checks and ALB target health checks with similar roles.
```csharp
builder.Services.AddHealthChecks()
    .AddCheck("self", () => HealthCheckResult.Healthy(), tags: ["live"])
    .AddSqlServer(cs, tags: ["ready"]);
app.MapHealthChecks("/health/live",  new() { Predicate = r => r.Tags.Contains("live") });
app.MapHealthChecks("/health/ready", new() { Predicate = r => r.Tags.Contains("ready") });
```
? What happens if readiness fails on all pods? :: The Service has no endpoints, so requests fail; that is why readiness checks must be well designed.
? Why a startup probe? :: So a slow start (migrations, cache warm-up) is not killed by the liveness probe.
