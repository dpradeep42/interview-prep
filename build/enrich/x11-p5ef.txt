X: Client-side evaluation is when part of a query runs in .NET memory instead of in the database, which can mean loading way more data than needed.

X: Compiled queries are a way to skip the cost of translating a LINQ query into SQL every time it runs.

X: Primary and foreign keys are basically the tools for identity and integrity in a relational database.
X: A primary key uniquely identifies each row in a table. It can't be null, and there's only one per table, though it can span multiple columns. In SQL Server, the primary key creates a clustered index by default, so it often also defines the physical order of the data. A good primary key is small, stable and never changes, like an integer identity or a GUID. A foreign key is a column, or columns, in one table that refers to the primary key of another table. It enforces referential integrity. You can't create a shipment for a site that doesn't exist, and you can't delete a site that still has shipments, unless you've defined cascade rules, like cascade delete or set null.
X: In practice, I always index foreign key columns, because SQL Server doesn't do it automatically, and joins and deletes depend on them. People miss that.
X: In a clinical system, foreign keys are a cheap but very strong guarantee of data integrity, so we never skip them for convenience. I can explain how to choose between integer and GUID keys.
+@p5-19
X: A unique constraint guarantees that no two rows have the same value in a column, or a combination of columns. SQL Server enforces it with a unique index behind the scenes.
X: A primary key is also unique, but there are differences. A table has only one primary key, but can have many unique constraints. A primary key can't contain nulls, while a unique constraint in SQL Server allows one null, or with a filtered unique index you can allow many. The primary key is the row's main identity, used by foreign keys, while unique constraints protect alternate keys, which are natural business identifiers. And by default, the primary key is clustered, while unique constraints are non-clustered.
X: A typical design, I'd say, is a surrogate primary key, like an integer Id, plus unique constraints on natural keys that must never duplicate.

X: SQL Server's optimizer creates the plan based on statistics about the data, and then caches it for reuse. +@p5-24
X: These are three ways SQL Server can read data, and they differ hugely in cost.
X: A table scan reads every row of a heap, which is a table without a clustered index. An index scan reads all, or a large range, of an index, either the clustered index, which is effectively the whole table, or a non-clustered one. X: EXISTS and IN both check whether a value has a match in another set, and modern SQL Server often produces the same plan for both. But there are differences worth knowing.
X: EXISTS checks whether a subquery returns any row, and stops at the first match, so it's naturally efficient for existence checks. It's also correlated, meaning it can compare several columns. X: The important difference is with negation and NULLs. NOT IN returns no rows at all if the subquery returns even one NULL, because comparing with NULL is unknown. X: Both hold an intermediate result inside a larger query, but they behave very differently.
X: A CTE, defined with WITH, is a named query that exists only for the single statement that follows it. It's not stored anywhere, the optimizer just expands it into the main query, like a view. X: So my rule is CTE for readability and recursion in a single query. Temp table when the intermediate result is large, reused multiple times, or when the optimizer is making bad estimates on a complex query, because materialising it with real statistics often gives a much better plan.
