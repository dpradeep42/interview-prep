Y: Middleware is a piece of code that sits in the ASP.NET Core request pipeline. Every request passes through the middleware in the order I register them, and each one can do some work, call the next one, and then do more work on the way back, or stop the request early. Authentication, routing, CORS and exception handling are all middleware. In my project, I wrote a correlation-id middleware so we could trace every request across [4] services.

Y: To write custom middleware, I create a class with a constructor that takes the next RequestDelegate and an InvokeAsync method that takes HttpContext. Inside, I do my work, await next, and then do any work after the response. Then I register it in Program.cs with app.UseMiddleware, at the right position. Our correlation-id middleware reads or creates an id, adds it to the response header and the logging scope, and then calls next.
K: custom middleware, invokeasync, requestdelegate, usemiddleware, httpcontext
+@p10-3
Y: Convention-based middleware is created once at startup, so it is effectively a singleton, and scoped services must be passed as parameters to InvokeAsync, not the constructor. Factory-based middleware implements IMiddleware and is created from DI for each request, so constructor injection of scoped services is fine, but I must register it in the container. The pitfall is injecting a scoped service like DbContext into a convention middleware's constructor, which captures it forever.
