X: To secure an AI deployment agent, I start from one principle: the agent should never be more powerful than the person using it, and it should never be able to deploy to production by accident.
X: First, identity. The agent acts with the user's own credentials, so it inherits their permissions; there's no shared admin account. Second, environment controls. X: Failed agent actions are normal, so I design for them from the start: the failure should be clear, the system should stay consistent, and a human should decide anything risky.
X: First, clear errors. A failed tool returns a structured error with what failed, why, and what to try, never a stack trace or secret. X: RBAC, role-based access control, means permissions are given to roles, and users get roles. For AI agents, the key rule is that the agent must never have more access than the human it's acting for. Privilege escalation happens when the agent runs with a powerful service account, so any user can do more through the agent than they could directly.
X: So first, I avoid shared high-privilege identities. The agent acts with the user's own delegated credentials, like a personal access token or an OAuth token for that user. The target system, like Azure DevOps, then enforces that user's permissions on every call. Second, I map roles to tools. For example, a viewer can only use read tools, a developer can deploy to lower environments, and production deployment needs a release manager role plus a separate approval. Fourth, no tools for things nobody should do through the agent, like deleting pipelines or changing permissions. And fifth, approval can't be done by the requester.
X: In my CIRT MCP server, using each engineer's own token meant Azure DevOps enforced RBAC for us. The agent made people faster, not more powerful, which was key to getting it approved.
+@p8-40
X: For an AI agent, the most important rule about secrets is that the model should never see them. The tools use secrets; the model only sees the results.
X: First, storage. Secrets never go in code, prompts, the repository or configuration files that get committed. For a local agent, like my CIRT MCP server, the user's personal access token comes from an environment variable in their own MCP configuration. For a hosted agent, secrets live in a secrets manager, like AWS Secrets Manager or Azure Key Vault, and are loaded at runtime using a managed identity or IAM role, so there's no secret needed to get the secret. Second, keep them out of the model's context. Tool outputs never include tokens or connection strings, and logs mask sensitive values, so nothing leaks into chat history or log files. Third, least privilege and short lifetimes. Each token has only the scopes it needs and an expiry date, and gets rotated. Where possible, I use delegated OAuth tokens for each user instead of long-lived keys. Fourth, monitoring: unusual usage of a credential triggers an alert, and any leak means immediate revocation.
X: In the CIRT MCP server, these rules meant that even if a conversation or log was shared, it contained no credentials, and each token only had that one engineer's limited permissions.

X: To evaluate whether an AI action is safe, I look at two things: how much damage it could do, and how sure we are that it's correct. Then the controls match the risk.
X: First, classify the action. Read-only actions, like getting status or logs, are low risk and can run automatically. Write actions in lower environments are medium risk and need user confirmation. X: OAuth 2.0 is an authorization framework. It lets an application get limited access to an API on behalf of a user, without ever seeing the user's password. The user signs in at an authorization server, approves access, and the application receives an access token, which it sends to the API. The token has scopes, like read only, and an expiry. For web and mobile apps, the recommended flow is the authorization code flow with PKCE. For service-to-service calls, there's the client credentials flow, with no user involved.
X: The important point is that OAuth is about access, not identity. It tells the API "this app may do these things", but it doesn't define who the user is.
X: OpenID Connect, OIDC, is an identity layer built on top of OAuth 2.0. It adds an ID token, which is a signed JWT containing information about the user, like their id, name and email, plus a userinfo endpoint and standard scopes like openid and profile. So the application can actually log the user in.
X: A simple way to say it: OAuth answers "what can this app access?", and OpenID Connect answers "who is the user?".
X: In my work, our applications use OIDC to sign users in through single sign-on, and then use the OAuth access token to call our ASP.NET Core APIs, which validate the token and check scopes and roles.
+@p8-44
X: SSO, single sign-on, lets a user sign in once with a central identity provider and then access many applications without signing in again.
X: Here's how it works with OpenID Connect, which is the common modern approach. The user opens an application, which sees there's no session and redirects them to the identity provider, like Microsoft Entra ID or Okta. The user signs in there, maybe with multi-factor authentication, and the identity provider creates its own session for them. It then redirects back to the application with an authorization code. The application exchanges that code for tokens, validates the ID token, and creates its own session, usually a secure cookie. When the user opens a second application, it also redirects to the identity provider, but because the user already has a session there, they're sent straight back, logged in, without typing anything. SAML is an older XML-based standard that works in a similar way.
X: The benefits are fewer passwords, central security policies like MFA, and one place to disable a user's access.
X: I've worked on SSO problems in our applications. In one case, users were randomly logged out because the session cookie had grown to [about 13 KB], close to the browser's limit, because we stored all the claims in it. We moved the claims to a server-side session, keeping the cookie [under 1 KB], and the issue stopped.

X: SQL injection is an attack where user input is treated as part of a SQL command, instead of as data. It happens when code builds a query by concatenating strings. For example, a login query built as "select from users where name equals" plus whatever the user typed. If the attacker types a quote followed by "or 1 equals 1", the query's meaning changes, and it can return every user. Worse inputs can read other tables, change data, or delete it.
X: The main fix is parameterised queries. The SQL text is fixed, with placeholders like @name, and the values are sent separately. The database always treats them as data, never as code, so injection isn't possible. In .NET, that means SqlParameter with ADO.NET, parameters in Dapper, or Entity Framework Core, which parameterises LINQ queries automatically. One trap: in EF Core, FromSqlRaw with string concatenation is still vulnerable, while FromSqlInterpolated or FromSql parameterise the values.
X: Extra layers help too: validate input, use a database account with least privilege, so the application can't drop tables, and use stored procedures carefully, without dynamic SQL inside them.
X: In my code reviews, any SQL built with string concatenation is a blocker, and our static analysis in SonarQube flags it automatically as well.

X: Cookies often hold session or authentication data, so how they're configured matters a lot for security. There are three key attributes.
X: HttpOnly means JavaScript in the page can't read the cookie. So if an attacker manages a cross-site scripting attack, they still can't steal the session cookie. Every authentication cookie should be HttpOnly.
X: Secure means the browser only sends the cookie over HTTPS, so it can't be intercepted on an unencrypted connection.
X: SameSite controls whether the cookie is sent with requests that come from other sites, which protects against cross-site request forgery. Strict means it's only sent when the request starts from your own site. Lax, the default in modern browsers, also sends it for top-level navigation, like clicking a link, but not for cross-site form posts or background requests. None sends it everywhere, but must be combined with Secure, and is needed for some cross-site scenarios, like certain single sign-on flows.
X: Beyond those, I keep cookies small, set a sensible expiry, and use the __Host- prefix where possible to lock a cookie to one domain.
X: In ASP.NET Core, I configure these in the cookie authentication options. In our applications, I've also fixed a sign-in problem where a SameSite setting blocked the cookie during an SSO redirect.

X: I secure APIs and microservices in layers, so no single mistake exposes everything.
