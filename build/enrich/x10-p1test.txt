X: The event loop is how JavaScript handles asynchronous work, even though it runs your code on a single thread.
X: There's one call stack, where your code runs. When you start async work, like a timer, a network request or file I/O, it's handed off to the browser or, in Node, to libuv, which does it in the background. When it's done, its callback goes into a queue. The event loop's job is simple, whenever the call stack is empty, take the next task and run it. You've got two kinds of queues. Microtasks, which are promise callbacks and awaits, and macrotasks, like setTimeout and I/O callbacks. After each task, the loop runs all pending microtasks first, then takes the next macrotask. That's why a resolved promise's then runs before a setTimeout with zero delay. That ordering can catch people out in interviews.
X: The practical lesson is that long synchronous code blocks everything, because nothing else can run while the stack's busy. In the browser the UI freezes, and in Node every request waits. So heavy CPU work goes to Web Workers or worker threads.
