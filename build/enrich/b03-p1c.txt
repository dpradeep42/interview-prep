Q: A clustered index defines the physical order of the table's rows: the leaf level is the data itself, so there is only one per table (usually the primary key). A non-clustered index is a separate B-tree of key columns with pointers (the clustered key) back to the rows; a table can have many, and INCLUDE columns can make them covering.
- Key lookup: when a non-clustered index lacks needed columns, SQL Server looks up each row in the clustered index; many lookups can make the optimizer choose a scan.
- Clustered key choice: narrow, unique, static and ever-increasing (INT/BIGINT identity, sequential GUIDs); random GUIDs cause page splits and fragmentation.
- Every non-clustered index stores the clustered key, so a wide clustered key bloats all indexes.
- Heaps (no clustered index) suit some staging tables, but forwarded records hurt reads.
- Columnstore indexes are for analytics over large tables.
- My shipment-list fix used a non-clustered index on (StudyId, Status, ShipmentDate) INCLUDE (display columns), removing scans and key lookups.
```sql
CREATE NONCLUSTERED INDEX IX_Shipments_Study_Status_Date
ON dbo.Shipments (StudyId, Status, ShipmentDate)
INCLUDE (SiteId, KitCount, TrackingNumber);
```
? Can the primary key be non-clustered? :: Yes; PK and clustered index are separate concepts, they just default together.
? What is a covering index? :: An index containing every column a query needs, so no lookups are required.

Q: Isolation levels trade consistency for concurrency: READ UNCOMMITTED (dirty reads allowed), READ COMMITTED (SQL Server default, no dirty reads), REPEATABLE READ (rows read cannot change), SERIALIZABLE (no phantoms, range locks), plus SNAPSHOT and READ COMMITTED SNAPSHOT (RCSI), which use row versions in tempdb so readers do not block writers.
