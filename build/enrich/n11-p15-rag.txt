T: How does your RAG pipeline work, from ingestion to retrieval?
V: ragPipe
K: rag pipeline, rag architecture, rag end to end, ingestion query, rag design, python rag pipeline
X: Our RAG service is written in Python, and its main job is to give AI coding tools, like GitHub Copilot and Cursor, the context of our codebase and our coding standards. It has two halves: ingestion and retrieval.
X: Ingestion. A pipeline collects content from [about 40] repositories, plus our coding standards, architecture decision records and API contracts. Code is chunked by structure using tree-sitter: one chunk per class or method, with its file path, namespace and signature, rather than cutting at a fixed number of characters. Documents are chunked by headings. Each chunk gets metadata, like the repository, path, language, module and last commit, and an embedding from Azure OpenAI. Everything is stored in PostgreSQL with pgvector, which also gives us full-text search and metadata filters in the same database.
X: Retrieval. When Copilot or Cursor calls the search tool through our MCP server, the query runs as a hybrid search: vector similarity for meaning, and full-text search for exact names, like a class or an error code, merged with reciprocal rank fusion. Filters narrow it by repository or language. Then a re-ranker reorders the top results, and we return the best few chunks, trimmed to a token budget, each with its file path and line numbers, so the tool can cite them and open the real file.
X: Freshness is handled by an incremental re-index on every merge to main. And it's evaluated with a golden question set, measuring whether the right chunks come back.

T: How do you chunk code for RAG?
K: code chunking, chunking strategy, tree-sitter, ast chunking, fixed size chunking, chunk size overlap
X: Chunking decides what the retriever can find, so for code it's one of the most important choices. In our Python RAG service, which gives GitHub Copilot and Cursor the context of our codebase and standards, I chunk code by its structure, not by character count.
X: Fixed-size chunking, say a thousand characters with some overlap, is simple and works for prose, but for code it cuts methods in half, separates a method from its class, and mixes unrelated code in one chunk. The retrieved pieces then make little sense to the model.
X: So I used tree-sitter, a parser that builds a syntax tree for many languages, including C#, TypeScript and SQL. From the tree, each chunk is a complete unit: a method, with its class name, namespace and signature added as a header, or a small class as a whole. Very long methods are split at statement boundaries, keeping the signature in each part. Every chunk carries metadata: repository, file path, line numbers, language, symbol name and the last commit, which helps filtering and lets the AI tool open the exact lines.
X: Some content needs its own rules. Markdown standards and decision records are split by headings, so each rule stays together with its title. Configuration and pipeline YAML is chunked by top-level sections. And generated code, build output and secrets files are excluded entirely.
X: [Switching from fixed-size to tree-sitter chunking raised our retrieval hit rate on the golden question set from about 62 percent to about 80 percent], before any other tuning.

T: Which embeddings and vector store did you use, and why?
K: embeddings, vector store, pgvector, vector database, azure openai embeddings, chroma, faiss, embedding model
X: Our RAG service, written in Python, gives AI coding tools like Copilot and Cursor the context of our codebase and coding standards. For it, I chose Azure OpenAI embeddings and PostgreSQL with the pgvector extension.
X: An embedding is a list of numbers that represents the meaning of a piece of text, so similar content ends up close together, and we can find relevant code even when the words differ. [I used Azure OpenAI's text-embedding-3-small model.] It's good on both code and English, inexpensive, and it runs in our enterprise Azure OpenAI tenant, where our data isn't used for training, which matters for an internal codebase. The query and the chunks must always use the same model, so changing models means re-embedding everything, which I planned for with a model version on every row.
X: For storage, I compared Chroma, FAISS and pgvector. FAISS is a fast library, but not a database: no metadata filtering or updates out of the box. Chroma is easy to start with. [I picked pgvector, on PostgreSQL in our AWS account], because one database gives vector search, full-text search for hybrid retrieval, metadata filters like repository and language, transactions for incremental updates, and standard backups and access control. At our scale, [a few hundred thousand chunks], an HNSW index keeps queries in milliseconds, so a specialised vector database wasn't needed.
X: The lesson I'd share: choose the simplest store that supports hybrid search and filtering, because retrieval quality matters far more than the database brand.

T: What are hybrid search and re-ranking, and why did you use them?
K: hybrid search, bm25, keyword search, vector search, reranking, re-ranker, reciprocal rank fusion, cross-encoder
X: In our Python RAG service, which gives GitHub Copilot and Cursor the context of our codebase and standards, retrieval quality improved most from two things: hybrid search and re-ranking.
X: Vector search finds content by meaning. That's great for questions like "how do we handle vendor file retries?", but weak for exact identifiers, like a class name, an error code or a configuration key, because embeddings blur precise tokens. Keyword search, like BM25, is the opposite: excellent for exact terms, poor at meaning. Code questions mix both, so hybrid search runs both and combines them. I used PostgreSQL full-text search alongside pgvector, and merged the two ranked lists with reciprocal rank fusion, which rewards items that rank well in either list, without having to tune scores against each other.
X: Re-ranking is a second, more careful pass. The first stage retrieves, say, the top 30 candidates quickly. Then a re-ranker, [a small cross-encoder model], reads the query and each candidate together and scores how well they actually match. It's slower, which is why it only runs on the shortlist. The top few results go to the AI tool.
X: Then I add metadata filters, like repository, language or module, and boost chunks from shared libraries and standards, because those are what we want reused.
X: On our golden question set, [hybrid search plus re-ranking lifted recall at five from about 80 percent to about 88 percent], and exact-name lookups, which vector search often missed, became reliable.

T: How do you keep the RAG index up to date?
K: rag freshness, reindex, incremental indexing, stale index, index on merge, rag pipeline trigger
X: A stale index is dangerous, because the AI tool will confidently suggest code that no longer exists. In our Python RAG service, which gives GitHub Copilot and Cursor the context of our codebase and standards, freshness is automatic.
X: Re-indexing happens on every merge to the main branch. A step in our Azure DevOps pipeline calls the indexing job with the repository and the list of changed files. For each changed file, the job re-parses it with tree-sitter, recalculates the chunks, and compares a content hash for each chunk with what's stored. Only chunks that actually changed are re-embedded, and chunks from deleted code or deleted files are removed. That keeps it fast and cheap, usually [under a minute per merge].
X: There's also a nightly full consistency check, comparing the index with the repositories, in case a pipeline run was missed. Every chunk records its commit, so a search result shows how recent it is. Standards and architecture decision records are indexed the same way when their documents change, so a new rule is available to the AI tools the same day.
X: If we change the embedding model, that's a full re-index into a new table, switched over only after the golden question set passes, so quality never drops during the change.
X: [Since moving to merge-triggered indexing, the index is normally within minutes of main], and reports of "the AI suggested a method that doesn't exist" became rare.

T: Why use RAG instead of just a long context window?
K: rag vs long context, long context window, why not paste whole repo, context window vs retrieval, rag vs fine-tuning
X: Modern models accept very large contexts, so it's a fair question: why not just give the model the whole codebase? For our project, RAG was clearly better, for five reasons.
X: First, size. Our IRT codebase spans [about 40] repositories, far more than any context window, plus standards and design documents. Second, quality. Models get worse at using information buried in the middle of a very long context, so a few highly relevant chunks often beat a huge dump. Third, cost and speed. Every token is paid for and slows the response, on every single request. Retrieval sends only what's needed. Fourth, freshness and control. The index updates on every merge, we can filter by repository or module, and every result has a source, so we know exactly what the model saw. Fifth, access control. Retrieval can respect which repositories a user is allowed to see, which a pasted dump can't.
X: Fine-tuning is the other alternative, but it changes how a model behaves, not what it knows today, and it goes stale with every merge. So my rule is: RAG for knowledge, fine-tuning for behaviour, and long context for working deeply on the few files you're actually changing.
X: That's how our setup works: our Python RAG service, through MCP tools in Copilot and Cursor, finds the relevant code and standards, and then the agent opens those few files fully in its context to make the change.

T: What are common RAG failure modes, and how do you fix them?
K: rag failure modes, rag problems, bad retrieval, rag debugging, rag pitfalls, irrelevant context
X: Most RAG failures are retrieval failures, not model failures, so I always debug retrieval first. From our Python RAG service, which gives Copilot and Cursor the context of our codebase and standards, these are the ones I've seen most.
X: Wrong chunks. Fixed-size chunks cut methods in half or mix unrelated content. The fix is structure-aware chunking, like tree-sitter for code and headings for documents. Missed exact names. Vector search struggles with identifiers and error codes. The fix is hybrid search, adding keyword search. Relevant but not best. The right chunk is in the top 30 but not the top 5. A re-ranker fixes that. Stale content. The model suggests code that was deleted. The fix is incremental re-indexing on every merge, plus a nightly consistency check. Too much context. Stuffing in many chunks confuses the model and costs tokens. The fix is a token budget and fewer, better results. Content gaps. The answer simply isn't written down anywhere. Logging queries with weak results shows those gaps, and the fix is better documentation, not more AI. And the model ignoring the context. Clear instructions, citations and "say if it's not in the sources" fix most of that.
X: The way to find which one you have is a golden question set with labelled answers, measured on every change. In our case, that took recall at five [from about 62 to about 88 percent]. Without measurement, RAG tuning is just guessing.
