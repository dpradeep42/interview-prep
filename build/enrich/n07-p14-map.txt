T: Azure DevOps variable groups vs AWS Parameter Store and Secrets Manager?
K: variable groups, parameter store, ssm, secrets manager, variable group vs parameter store, pipeline variables
X: Both answer the same question: where do environment-specific settings and secrets live, outside the code? We use both, because our product started as CIRT, Cenduit's IRT, on an on-premise Azure DevOps Server, and after IQVIA acquired Cenduit, AWS became the standard for IQVIA's newer services, while CIRT itself stayed on-premise.
X: A variable group in Azure DevOps is a named set of variables, like UAT-Shipments, that pipelines link to. Values are injected into the pipeline at run time, and secret variables are masked in logs. They can also be linked to Azure Key Vault. Access is controlled by Azure DevOps security, and changes are recorded in its history. The key point is that variable groups are a pipeline feature: the values exist at deploy time, and the pipeline has to push them into the application's configuration.
X: In AWS, Systems Manager Parameter Store holds configuration as a hierarchy of paths, like /irt/uat/shipments/timeout, with versions, and SecureString values encrypted with KMS. Secrets Manager is for real secrets, like database passwords, with automatic rotation. The big difference is that the application reads them at run time, using its IAM role, so the pipeline doesn't need to know secret values at all.
X: So the mapping is: plain variables to Parameter Store, secret variables and Key Vault to Secrets Manager, and Azure DevOps permissions to IAM policies. During our transition, a setting once existed in a variable group but was missing in UAT Parameter Store, so I added a parity check to the CIRT MCP server that compares both before each deployment.

T: Azure DevOps release pipelines vs AWS CodePipeline and CodeDeploy?
K: release pipelines vs codepipeline, codedeploy, codebuild, release gates, manual approval, azure releases aws
X: Our releases run in an on-premise Azure DevOps Server, inherited from CIRT, Cenduit's IRT, before IQVIA acquired Cenduit, and they deploy to both on-premise nodes and AWS. So I know the Azure DevOps side deeply, and how it maps to native AWS tools.
X: In Azure DevOps, a build pipeline produces an artifact, and a release pipeline deploys it through stages, one per environment, like FV, TechOps, UAT and production. The differences are mostly about tooling and identity: AWS uses IAM roles instead of service connections. [We haven't moved our releases to CodePipeline], because our release history and approvals in Azure DevOps are part of our validation evidence, so we deploy to AWS from Azure DevOps instead.

T: TFS and TFVC vs Git; Azure Repos vs GitHub or CodeCommit?
K: tfs, tfvc, git, tfs vs git, azure repos, codecommit, version control migration, centralized vs distributed
X: Our product started as CIRT, Cenduit's IRT, and its code lived in Team Foundation Server, using TFVC, Team Foundation Version Control. [It moved to Git, in Azure DevOps Server, after IQVIA acquired Cenduit,] as part of modernising the CIRT platform.
X: The core difference is centralised versus distributed. TFVC is centralised: there's one server copy, you check files out and in, branches are heavy server folders, and many operations need the server. Git is distributed: every developer has the full history locally, branches are cheap and fast, and work happens offline, with pull requests to review and merge. Git made pull requests with policies, like required reviewers, a passing build and a SonarQube quality gate, the normal way of working, which fits GxP well, because every change is reviewed and traceable.
X: A TFVC-to-Git migration needs some care: deciding how much history to bring, mapping branches, handling large binary files, and retraining people on branching and merging.
X: On the hosting side, Azure Repos is Git inside Azure DevOps. In AWS, the native option was CodeCommit, but AWS stopped offering it to new customers in 2024, so most AWS teams host Git on GitHub or GitLab and connect it to AWS pipelines. In our case, the Git repositories still live in our on-premise Azure DevOps Server, next to the pipelines, while the services they build run on AWS.

T: Azure DevOps agent pools vs AWS CodeBuild and self-hosted runners?
K: agent pools, build agents, self-hosted agents, codebuild, runners, build infrastructure
X: Agents are the machines that actually run pipeline jobs. Our pipelines run on an on-premise Azure DevOps Server, inherited from CIRT, Cenduit's IRT, before IQVIA acquired Cenduit, so we use self-hosted agents.

X: Whichever option, I treat agents as disposable and defined as code, with only the permissions their jobs need.

T: Azure DevOps service connections vs AWS IAM roles?
K: service connection, iam role, assume role, oidc, pipeline credentials, workload identity, access keys
X: Both are how a pipeline proves who it is to the target platform, so it can deploy. We deploy from an on-premise Azure DevOps Server, inherited from CIRT, Cenduit's IRT, into AWS, where IQVIA runs new services, so I work with both.
X: In Azure DevOps, a service connection stores how to connect to an external system, like Azure, a Docker registry, Kubernetes, or AWS. Pipelines reference it by name, and access to it is controlled, so only approved pipelines can use a production connection. The weak version stores long-lived secrets, like a client secret or an access key, inside it. The better version uses workload identity federation, with OpenID Connect, so no secret is stored.
X: In AWS, the equivalent identity is an IAM role. The pipeline, or the build agent, assumes a role and receives short-lived credentials, valid for maybe an hour. The role's trust policy says who may assume it, like a specific OIDC identity or a specific EC2 instance profile, and its permission policy says exactly what it can do, like pushing to one ECR repository and updating specific ECS services. Every call is recorded in CloudTrail.
X: So the mapping is: a service connection becomes a role that the pipeline assumes, plus a trust policy. The principles I follow are the same on both sides: no long-lived keys, one identity per environment, least privilege, and production identities usable only by approved pipelines.

T: Azure Key Vault vs AWS Secrets Manager and KMS?
K: key vault, secrets manager, kms, key management, certificates, secret rotation, azure vs aws secrets
X: Both keep secrets out of code and configuration files, with strict access control and auditing. We use both worlds, because our product began as CIRT, Cenduit's IRT, on Microsoft tooling, and after IQVIA acquired Cenduit, AWS became the standard for IQVIA's newer services, while CIRT itself stayed on-premise.
X: Azure Key Vault is one service for three things: secrets, like passwords and connection strings, cryptographic keys, and certificates. Access is controlled with Azure role-based access, apps use managed identities to read it, and Azure DevOps variable groups can link to it, so pipelines read secrets without copying them.
X: In AWS, those jobs are split across services. Secrets Manager stores secrets, with versioning and automatic rotation, which is built in for databases like RDS. KMS manages encryption keys: it encrypts data in other services, like S3, RDS and Parameter Store SecureString values, and keys never leave it. Certificates are handled by ACM, the AWS Certificate Manager, for load balancers and API Gateway. Access is through IAM policies, apps use their IAM roles, and every access is logged in CloudTrail.
X: So the mapping is: Key Vault secrets to Secrets Manager, or Parameter Store SecureString for simpler values, Key Vault keys to KMS, and Key Vault certificates to ACM.
X: In our AWS services, database credentials and vendor SFTP keys are in Secrets Manager, with rotation for RDS, and the application reads them at run time with its IAM role, so no secret ever sits in a pipeline variable or an image.

T: Azure Service Bus vs AWS SQS and SNS?
K: service bus, sqs, sns, queues topics, azure messaging aws, eventbridge
X: Both are managed messaging services for decoupling systems. Our product began as CIRT, Cenduit's IRT, on Microsoft technology, and after IQVIA acquired Cenduit, AWS became the standard for IQVIA's newer services, while CIRT itself stayed on-premise, so it helps to map the two.
X: Azure Service Bus offers queues, for one consumer processing each message, and topics with subscriptions, for publish and subscribe, all in one service. It has rich features: sessions for ordered processing per key, dead-letter queues, scheduled messages, duplicate detection, and transactions.
X: In AWS, those are split. SQS provides queues. Standard queues give nearly unlimited throughput with at-least-once delivery and best-effort ordering, and FIFO queues give strict ordering per message group and deduplication, which is like Service Bus sessions. Dead-letter queues are built in. SNS provides topics for publish and subscribe, and the common pattern is SNS fanning out to several SQS queues, one per consumer, which matches a Service Bus topic with subscriptions. EventBridge adds event routing with rules, and Amazon MQ runs RabbitMQ or ActiveMQ as a managed broker.
X: In our platform, we actually use RabbitMQ for work queues and Kafka for business events, with the outbox pattern, rather than SQS or Service Bus. But the same rules apply on any of them: idempotent consumers, because delivery is at least once, dead-letter queues with alerts, and confirmations on publish. I added publisher confirms to RabbitMQ after an outage in [mid-2024].

T: ARM templates and Bicep vs CloudFormation, CDK and Terraform?
K: arm templates, bicep, cloudformation, cdk, terraform, infrastructure as code azure aws
X: All of these are infrastructure as code: you describe cloud resources in files, review them in pull requests, and apply them through pipelines, instead of clicking in a console. We work across both worlds, because our product began as CIRT, Cenduit's IRT, on Microsoft tooling, and after IQVIA acquired Cenduit, AWS became the standard for IQVIA's newer services, while CIRT itself stayed on-premise.
X: In Azure, ARM templates are the native JSON format, and Bicep is a cleaner language that compiles to ARM. Deployments are declarative, and what-if shows changes before applying. In AWS, CloudFormation is the native equivalent, with templates in YAML or JSON, stacks, and change sets to preview changes. The CDK lets you write infrastructure in a programming language, like C# or TypeScript, and generates CloudFormation. So ARM maps to CloudFormation, Bicep is closest in spirit to cleaner CloudFormation or the CDK, and what-if maps to change sets.
X: Terraform is the cross-cloud option: one language, HCL, providers for Azure, AWS and many others, a readable plan before every change, and a state file that must be stored safely, like in S3 with locking.
X: In our platform, [the core AWS stacks, like networking, are in CloudFormation, owned by the platform team, and newer service infrastructure, like queues and alarms, is in Terraform.] Both run from our Azure DevOps pipelines, with plan or change set review before apply.

X: These are the compute options, from fully managed to full control. Our product began as CIRT, Cenduit's IRT, on Microsoft servers on-premise, and after IQVIA acquired Cenduit, AWS became the standard for IQVIA's newer services, which run mostly as containers on ECS, while CIRT itself stayed on-premise.
X: At the most managed level, Azure App Service runs web apps and APIs without managing servers: you deploy code or a container, and it handles scaling, patching and deployment slots. The AWS equivalents are Elastic Beanstalk, which deploys code onto managed EC2 instances, and App Runner, which runs a container from an image with almost no configuration. X: My rule is to choose the most managed option that meets the need. For our .NET microservices, that's ECS on Fargate: we build images in Azure DevOps, push them to ECR, and ECS runs them across two availability zones with rolling deployments. VMs, or EC2, make sense when you need full control of the operating system, which is why the validated core, with its multi-node installs, [still runs on servers rather than containers].
