+@p1-2
X: A value type holds its data directly. Examples are int, bool, DateTime, enums and structs. When you assign it to another variable or pass it to a method, the value is copied, so changing the copy doesn't affect the original.
X: A reference type, like a class, string, array or delegate, holds a reference to an object that lives on the managed heap. When you assign it, only the reference is copied, so two variables can point to the same object, and a change through one is visible through the other. Value types usually live inline, on the stack or inside their containing object, so they avoid heap allocations. But if you put a value type into an object variable, it gets boxed, which costs an allocation.
X: In practice, I use structs only for small, immutable values, and classes for business objects that have identity and behaviour. For example, in our services entities like Shipment are classes, while a small Money or date-range type can be a readonly struct.
X: One classic trap is a mutable struct inside a list, where you end up changing a copy. I can explain boxing in more detail if you like.
+@p1-3
X: Async and await let a method wait for slow work, like a database call or an HTTP request, without blocking the thread.
X: Under the hood, the compiler rewrites an async method into a state machine. When the code hits an await on a task that isn't finished yet, it registers the rest of the method as a continuation and returns the thread to the thread pool. Importantly, no new thread is created for I/O; the operating system just notifies us when the data arrives. Then the method resumes from where it stopped, on a pool thread. Because threads aren't sitting idle while we wait, one server can handle many more requests with fewer threads.
X: The rules I follow are: async all the way down, never block with .Result or .Wait(), because that can cause thread starvation or deadlocks, and avoid async void except for event handlers. In our IRT APIs, every database and HTTP call is async with cancellation tokens, so threads stay free while SQL Server is working.
X: I can also explain ConfigureAwait or what happens with exceptions in async methods.
+@p1-4
X: A Thread is an actual operating system thread. It's expensive to create, it has its own stack, and you manage its lifecycle yourself. I almost never create threads directly in modern code.
X: A Task represents an operation that will complete in the future. It might run on a thread-pool thread, or it might be pure I/O with no thread at all while it waits, like a database call. Tasks are what async and await are built on, they compose nicely with things like Task.WhenAll, and they carry results and exceptions.
X: ValueTask is a lighter alternative for methods that often complete synchronously, for example a cache lookup that usually hits. A Task is a heap object, so returning ValueTask in those cases avoids an allocation. But it has rules: you should await it only once and not store it.
X: In practice, in our web APIs I use Task everywhere by default, and I'd only use ValueTask in a measured hot path, like a cached configuration lookup. Threads I leave to the framework, or to a BackgroundService for long-running work. I can show where ValueTask is actually worth it.

X: All three are about collections, but they differ in where the work happens.
X: IEnumerable works on data in memory. When you use LINQ on it, the filters run as C# code on the application server. IQueryable is different: it builds an expression tree, and a provider like EF Core translates that into SQL, so the filtering, sorting and paging run inside the database. A List is a concrete collection that's already loaded in memory, with indexing and a Count.
X: The important practical point is when the query actually executes. If you call ToList too early, or pass an IQueryable as IEnumerable, EF Core pulls the whole table into memory and then filters it in C#. That's a classic performance bug.
X: So in our APIs I keep the query as IQueryable while I add filters, sorting and paging, then I call ToListAsync once at the end. For example, on our shipment search screen, building the filters on IQueryable meant SQL Server returned only one page of rows instead of thousands.

X: An interface is a contract. It says what a type can do, but not how, and a class can implement many interfaces. An abstract class is a partial base class. It can hold shared code, fields and constructors, but a class can inherit from only one.
X: So the way I decide is: if I need a capability or a dependency that I want to swap or mock, I use an interface. If several implementations share real code, I use an abstract base class. Since C# 8 interfaces can have default methods, but I still keep them mostly as pure contracts.
X: A real example is our SFTP integration. All three providers, ComponentPro, SSH.NET and Rebex, implement one ISftpClient interface, so the business code and the unit tests depend only on the interface, and the DI container or a factory picks the provider. Then they inherit from an abstract base class that holds the shared retry, timeout and logging logic, so I didn't repeat it three times.
X: So it's not either-or; they work well together. I can explain how that helped with testing.

X: SOLID is a set of five design principles that keep code easy to change and test. Let me explain each with an example from my work.
X: S is single responsibility: a class should have one reason to change. In our CSV import, the parser, the validator and the importer are separate classes. O is open-closed: open for extension, closed for modification. When we added Rebex as a new SFTP provider, I added a new class, I didn't edit the callers. L is Liskov substitution: any ISftpClient implementation can replace another without breaking the caller, so they all behave the same for errors and timeouts. I is interface segregation: small, focused interfaces, so a class that only reads files doesn't depend on write methods. And D is dependency inversion: high-level services depend on abstractions, which ASP.NET Core injects through DI, so I can mock them in unit tests.
X: I treat SOLID as guidance, not rules. Too many tiny interfaces can make code harder to follow. I can go deeper into any one of them.

+@p1-9
X: Garbage collection in .NET automatically frees memory for objects that nothing references any more, so we don't free memory by hand.
X: It's generational, based on the idea that most objects die young. New objects go into generation 0, which is collected often and cheaply. Objects that survive move to generation 1, and long-lived ones move to generation 2, which is collected less often because it's more expensive. Objects larger than about 85 KB go to the Large Object Heap, which is collected with gen 2. ASP.NET Core uses server GC by default, with a heap per core, for throughput.
X: One important point: the GC only handles managed memory. Things like files, sockets, database connections and SFTP sessions are unmanaged resources, so they need IDisposable and a using statement.
X: In practice I don't tune the GC much, but I watch for leaks. For example, I once investigated a .NET service whose memory kept growing, and the cause was event handlers that were never unsubscribed, keeping objects alive. I can walk through how I diagnosed that.

X: A delegate is a type-safe reference to a method. You can store it in a variable, pass it to another method and call it later.
X: Func and Action are built-in generic delegates, so we rarely declare our own. Func returns a value; for example Func of int, string takes an int and returns a string. Action returns nothing. There's also Predicate, which returns a bool. A lambda is a short inline way to write the method, like x goes to x.IsActive. An event is a delegate with restricted access: other classes can subscribe and unsubscribe, but only the owning class can raise it.
X: One thing to be careful about is that lambdas can capture variables, which creates a closure. That's very useful, but it can keep objects alive longer than expected, and event handlers that are never unsubscribed are a common memory leak.
X: I use these every day: lambdas in LINQ queries, Func in minimal API endpoints, and Action delegates for options configuration, like services.AddOptions with a configure lambda. I can explain closures in more depth if useful.
+@p1-11
X: Deferred execution means a LINQ query doesn't run when you write it. It only runs when you actually enumerate it, for example in a foreach loop, or when you call ToList, Count, First or Any.
X: That's useful, because you can build up a query step by step, adding filters and sorting based on conditions, and with EF Core it all becomes one SQL statement at the end. But there are two risks. First, every enumeration runs the query again, so if you loop over an IQueryable twice, you hit the database twice. Second, the data can change between definition and execution, because it reads the data at the time it runs.
X: So my rule is: if I need the results more than once, I materialise them once with ToList or ToArray and reuse that list. Operators like ToList, Count, Sum and First run immediately.
X: In our search APIs we build the query conditionally on IQueryable, and only call ToListAsync after paging, so SQL Server returns just one page. I can show the double-enumeration bug in code if you like.
+@p1-12
X: Code is thread-safe when it behaves correctly even if many threads run it at the same time.
X: My first approach is to avoid shared mutable state. I keep services stateless and use immutable objects, so there's nothing to protect. When I do need shared state, I pick the right tool. For simple counters I use Interlocked. For shared caches I use ConcurrentDictionary. For a short critical section I use the lock statement, and for async code I use SemaphoreSlim, because you can't await inside a lock. SemaphoreSlim is also handy to limit concurrency, for example to deploy to only a few nodes in parallel. For lazy initialisation I use Lazy of T instead of hand-written double-checked locking.
X: I'm also careful with singletons in DI, because a singleton that holds mutable state is shared by every request.
X: And thread safety can cross processes too. In our CSV import, we used a lock row in the database so two users couldn't import into the same study at the same time. I can go into that design if helpful.

X: All three define types, but they behave differently.
X: A class is a reference type with identity. Two objects with exactly the same values are still different objects, because equality compares references by default. A record is designed for data. It's still a reference type by default, but it compares by value, so two records with the same values are equal. It also gives you concise immutable syntax, a readable ToString, and with-expressions to create a modified copy. A struct is a value type, so it's copied on assignment, and it's best for small values. There's also record struct, which is a value type with value equality.
X: In my services I use records for DTOs, API contracts and messages we publish to Kafka or RabbitMQ, because those are pure data and should be immutable. I use classes for services and EF Core entities, because entities have identity and change over time. Structs I use rarely, only for small values.

+@p1-15
X: Generics let me write code once and use it with many types, while keeping full type safety.
X: Without generics, you'd use object and cast everywhere, which is error-prone, and value types would get boxed. With List of T or Dictionary of K and V, the compiler knows the exact type, so there's no casting and no boxing. Constraints tell the compiler what a type parameter can do. For example, where T is a class, where T implements an IEntity interface, or where T has a parameterless constructor. Then I can safely call those members inside the generic code. There's also variance: IEnumerable of a derived type can be used as IEnumerable of the base type.
X: In my work, I wrote a generic paged result type, so every list API returns items, total count and page info in the same shape. I've also used a generic Result of T wrapper for success or error responses, and generic repository methods constrained to our entity base class.
X: So generics reduce duplication and catch mistakes at compile time. I can explain covariance in more detail if you want.
