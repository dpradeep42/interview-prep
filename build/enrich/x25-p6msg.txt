X: Okay, so Kafka is a distributed event streaming platform. It stores streams of events in an ordered, durable log, and lets lots of applications publish and read those events at high volume. Unlike a traditional queue, reading a message doesn't delete it. Events are kept for a retention period, so several consumers can read the same data independently, and even replay it.
X: The main terms, quickly. A broker is a Kafka server, and several brokers form a cluster. A topic is a named stream of events, like shipment-status. Each topic is split into partitions, which are the unit of parallelism and scaling, and each partition is an ordered, append-only log stored on brokers. An offset is the position of a message inside a partition, a number that only goes up, and consumers track their offset to know where they've got to. A producer is an application that writes events to a topic. It chooses the partition, usually by hashing the message key, so all events with the same key, like the same shipment id, go to the same partition and stay in order. A consumer reads events, and consumers with the same group id form a consumer group, where each partition is read by only one consumer in the group, so the group shares the work.
X: In [the AWS-side services I've worked on], we use Kafka for events like shipment status updates, which several services consume, each in its own consumer group, and which we sometimes need to replay.
+@p6-34
X: Kafka gets scalability mainly through partitioning, and fault tolerance mainly through replication.
X: For scalability, each topic is split into partitions, and the partitions are spread across the brokers in the cluster. Producers write to different partitions in parallel, and in a consumer group, each partition is read by one consumer, so adding consumers, up to the number of partitions, increases processing in parallel. Adding brokers spreads the load further. Kafka is also very efficient by design. It writes sequentially to an append-only log, batches and compresses messages, and relies on the operating system's page cache, so it handles very high throughput.
X: For fault tolerance, each partition is replicated to several brokers, usually three, set by the replication factor. One replica is the leader, which handles reads and writes, and the others are followers, which copy from the leader. The replicas that are fully caught up are the in-sync replicas. If the leader's broker fails, one of the in-sync followers automatically becomes the new leader, and clients carry on. With producer acks set to all, and a minimum of two in-sync replicas, a write is only confirmed once it's safely on more than one broker, so a single failure doesn't lose data. Consumers also store their offsets in Kafka, so after a consumer crashes, another one continues from the last committed position. That's basically the whole story.
+@p6-35
X: The replication factor is how many copies of each partition Kafka keeps, on different brokers. A replication factor of three, which is the usual choice for production, means every partition exists on three brokers, so the cluster can lose a broker without losing data.
X: Among those copies, one is the leader and the others are followers. The leader handles all the writes for that partition, and usually the reads too. The followers keep copying new messages from the leader. Followers that are fully caught up are called in-sync replicas, the ISR. If a follower falls too far behind, it's removed from the ISR until it catches up.
X: If the leader's broker fails, the cluster controller picks one of the in-sync followers as the new leader, and producers and consumers automatically switch to it. Because it was in sync, nothing confirmed is lost. Leaders are spread across brokers, so the load is balanced.
X: Two settings work together for durability, and honestly this is where people get confused. On the producer, acks set to all means a write is only acknowledged when all in-sync replicas have it. On the topic, min.insync.replicas set to two means a write is rejected if fewer than two replicas are in sync. So with a replication factor of three and a minimum of two in-sync replicas, the cluster tolerates one broker failure with no data loss and no downtime.
+@p6-36
X: Kafka guarantees ordering within a partition, but not across a whole topic.
X: Each partition is an append-only log. Messages are written in order and each gets an increasing offset, and a consumer reads them in that same order. But a topic has several partitions, processed in parallel by different consumers, so there's no global order between messages in different partitions.
X: In practice, you usually don't need global ordering, you need ordering per entity, like all the events for one shipment or one order. You get that with a message key. The producer hashes the key to choose the partition, so every event with the same key, like the shipment id, always goes to the same partition, and stays in order. So "shipment created", "shipped" and "delivered" for one shipment are always processed in sequence.
X: A few things can break ordering, though. Retries on the producer can reorder messages, which the idempotent producer, now the default, prevents. Increasing the number of partitions changes which partition a key maps to, so existing keys can move. And on the consumer side, if you process messages from one partition in parallel threads, you lose the order, unless you parallelise per key.
X: If you really need a total order across everything, you'd use a single partition, but that limits throughput to one consumer. In our shipment events, we key by shipment id, which gives the ordering that matters.
+@p6-37
X: Retention and log compaction are basically the two ways Kafka decides when to remove old messages from a topic.
X: Retention removes messages based on time or size. By default, messages are kept for seven days, set by retention.ms, or until the partition reaches a size limit. After that, old segments of the log are deleted, whether or not anyone has read them. Consumers just need to read within the retention window. Because consumption doesn't delete data, lots of consumers can read independently, and you can replay events within that window, say after fixing a bug in a consumer.
X: Log compaction works differently. Instead of deleting by age, Kafka keeps at least the latest message for each key, and removes older messages with the same key. So the topic becomes a snapshot of the current state of every key. Like, a topic of customer addresses keyed by customer id would keep the latest address for each customer forever. To delete a key completely, you send a message with that key and a null value, called a tombstone. Compacted topics are great for rebuilding a cache or state store, and Kafka uses one internally to store consumer offsets.
X: The choice depends on the use. For event history, like shipment status events, time-based retention, and for "latest value per key" data, compaction. A topic can also combine both.
+@p6-38
X: When a Kafka consumer crashes, the consumer group recovers automatically, and the real question is just whether messages get processed twice.
X: Each consumer in a group sends heartbeats. When one crashes, it stops sending them, and after the session timeout, the group coordinator considers it dead. Then a rebalance happens, and its partitions are reassigned to the remaining consumers in the group. The new owner of each partition starts reading from the last committed offset for that partition.
X: Honestly, here's the important part. If the crashed consumer had processed some messages but hadn't committed their offsets yet, those messages will be processed again by the new consumer. That's at-least-once delivery. So consumers have to be idempotent, meaning processing the same message twice has the same effect as once, like by recording processed message ids, or using upserts with a unique key. The opposite mistake is committing the offset before processing, then a crash would skip messages, so I commit after processing.
X: To make crashes less disruptive, tune the session timeout, use the cooperative rebalancing strategy, so only the affected partitions move, and handle shutdown gracefully, committing offsets before leaving the group.
X: And while a consumer is down and before the rebalance, lag grows on its partitions, which is why we alert on consumer lag.
+@p6-39
X: So basically, consumer lag is the difference between the latest offset written to a partition and the offset the consumer group has committed. In simple words, it's how many messages are waiting to be processed. Some lag is normal, but lag that keeps growing means consumers can't keep up, and data is getting more and more delayed. And if lag grows beyond the retention period, messages are deleted before they're processed.
X: I monitor it per partition, with tools like Burrow, Kafka exporters for Grafana, or the cloud provider's metrics, and alert when it keeps growing.
X: To troubleshoot, I ask a few questions. Is the lag on all partitions or just one? If one, it might be a hot key, where one key gets most of the traffic, or a poison message that keeps failing. Did the incoming volume go up? Then I may need more consumers, up to the number of partitions. Did processing get slower? Then I check what each message does, often a slow database call, an external API, or processing one message at a time where batching would help. Are consumers rebalancing a lot? Frequent rebalances, often because processing takes longer than max.poll.interval.ms, stop consumption again and again. And are the consumers healthy, with enough CPU and memory?
X: The fix follows the cause, so scale out, add partitions, optimise processing, batch, tune poll settings, or move poison messages to a dead-letter topic.
+@p6-40
X: Kafka consumers scale through consumer groups. All consumers with the same group id share the work: each partition is assigned to exactly one consumer in the group, and one consumer can handle several partitions. So with six partitions and two consumers, each gets three. Adding consumers spreads the partitions out, and the group rebalances automatically.
X: That means the number of partitions is the maximum parallelism for a consumer group. If you have more consumers than partitions, the extra consumers sit idle, with no partitions assigned. They do act as hot standbys, taking over if another consumer fails, but they don't add throughput.
X: So to scale beyond the number of partitions, you have a few options. Add partitions to the topic, keeping in mind that this changes which partition each key maps to, which can affect ordering for existing keys, so it's best to plan enough partitions from the start. Or increase parallelism inside each consumer, processing messages concurrently with a worker pool, while keeping order per key if it matters. Or make processing itself faster, with batching and efficient database writes.
X: Separate applications that need the same events use different consumer groups; each group gets every message independently.
X: For autoscaling, I'd scale consumers on consumer lag rather than CPU, for example with KEDA in Kubernetes, up to the partition count.
+@p6-41
X: When I design Kafka topics, I think about what the events represent, who consumes them, how they need to be ordered, and how they'll change over time.
X: First, one topic per type of business event or entity, like shipment-status or order-events, named with a clear convention, for example domain, entity and version. Not one giant topic for everything, and not one topic per customer. Second, the key. I choose the message key based on ordering needs. If events for one shipment must be in order, the key is the shipment id. A good key also spreads load evenly, so one key doesn't overload a partition. Third, the number of partitions: enough for the consumer parallelism I need now and in the near future, because increasing it later changes key placement. Fourth, retention: time-based for event streams, or compaction for "latest value per key" topics. Fifth, the replication factor, three for production, with a minimum of two in-sync replicas.
X: Sixth, the schema. Events have a defined schema, with Avro, Protobuf or JSON Schema, preferably in a schema registry, with backward-compatible changes. Events include an event id, a timestamp, a type, a version and a correlation id. And seventh, a plan for failures: a retry topic and a dead-letter topic.
X: Our shipment status topic follows this: keyed by shipment id, with versioned events and correlation ids.
+@p6-42
X: A poison message is a message that a consumer can never process successfully, for example because it's malformed, has invalid data, or triggers a bug. Without handling, the consumer keeps retrying it forever. In Kafka, that's especially bad, because it blocks every message behind it in that partition.
X: My approach separates two kinds of failure. Transient failures, like a database timeout or an unavailable service, are worth retrying. Permanent failures, like a message that can't be deserialised or fails validation, will never succeed, so retrying is pointless.
X: For transient errors, I retry a few times in the consumer with exponential backoff. If it still fails, or for longer delays, I publish the message to a retry topic, sometimes several with increasing delays, like one minute, then ten, so the main partition isn't blocked while waiting. For permanent errors, or after the maximum attempts, the message goes to a dead-letter topic, with headers saying the original topic, partition, offset, the error, and the number of attempts. Then the consumer commits the offset and moves on.
X: The dead-letter topic is monitored, with an alert, and after investigating and fixing the cause, messages can be replayed to the main topic. Consumers are idempotent, so retries never cause duplicates.
X: We use exactly this pattern with RabbitMQ too: limited retries with backoff, then a dead-letter queue, with alerts.
+@p6-43
X: To secure Kafka, I cover four things: encryption, authentication, authorisation and network access.
X: Encryption in transit with TLS, between clients and brokers and between the brokers themselves, so messages can't be read on the network. Encryption at rest on the broker disks, which managed services like Amazon MSK provide. Authentication with SASL, for example SCRAM, or mutual TLS, or IAM authentication on MSK, so only known applications can connect. Authorisation with ACLs, applying least privilege: each service can only write to the topics it produces, and read from the topics it consumes, with its own consumer group. And network access: brokers in private subnets, reachable only from our services, never from the internet. Also, sensitive data in messages should be minimised or encrypted, and schemas validated.
X: For monitoring, the key metrics are: consumer lag per group and partition, which is usually the first sign of trouble; under-replicated partitions, which mean data is at risk; offline partitions and controller status; broker CPU, disk usage and network; and request latency, errors and throughput for producers and consumers. I'd collect these with Prometheus exporters or CloudWatch for MSK, show them in Grafana, and alert on growing lag, under-replicated partitions and disk space.
X: Consumers also log and trace with correlation ids from message headers, so one event can be followed across services.

X: RabbitMQ is a message broker. Applications send messages to it, and it routes them to queues, where consumers pick them up and process them. It decouples services: the sender doesn't wait for the receiver, and if the receiver is slow or down, messages wait safely in the queue.
X: The main concepts come from the AMQP protocol. Producers don't publish directly to queues. They publish to an exchange, with a routing key. A queue is where messages wait until a consumer receives and acknowledges them. A binding is the rule that connects an exchange to a queue, saying which messages should go there.
X: There are four main exchange types. Direct sends a message to queues whose binding key exactly matches the routing key, which is great for commands like "process this file". Fanout sends every message to all bound queues, like a broadcast. Topic matches routing keys with patterns, like shipment dot star, so different queues can subscribe to different groups of messages. And headers routes based on message headers.
X: Unlike Kafka, once a message is acknowledged, it's removed from the queue. So RabbitMQ is ideal for tasks and work queues, where each message should be processed once by one consumer, with retries and dead-lettering.
X: In our platform, we use RabbitMQ for work like processing vendor updates and sending notifications.
+@p6-45
X: Acknowledgements are how RabbitMQ makes sure messages aren't lost, and there are two separate kinds, one on each side.
X: Publisher confirms are about the producer. When a publisher sends a message, it can't assume the broker received and stored it. With confirms enabled on the channel, the broker sends back an acknowledgement once it has taken responsibility for the message, for a persistent message, that means written to disk. If something goes wrong, it sends a negative acknowledgement, and the publisher can retry. Without confirms, a message can be lost silently, for example if the connection drops at the wrong moment.
X: Consumer acknowledgements are about the consumer. When RabbitMQ delivers a message, it waits for the consumer to acknowledge it before deleting it. With manual acknowledgement, the consumer acks only after it has finished processing. If the consumer crashes before acking, RabbitMQ redelivers the message to another consumer. A consumer can also reject a message, and send it to a dead-letter queue. With automatic acknowledgement, the message is deleted as soon as it's delivered, so if processing fails, it's gone.
X: I learned this the hard way in [mid-2024]. Our publisher had no confirms, and during a [40-minute] problem, [about 1,200] updates were lost silently. We recovered them by replaying the vendor files that evening, then added publisher confirms, at about [5 percent] throughput cost. There's been no silent loss in the [12 months] since.
+@p6-46
X: Durability in RabbitMQ means messages survive a broker restart, and it needs several settings to work together.
X: First, the queue must be durable. A durable queue's definition survives a restart; a non-durable one disappears. Second, the message itself must be persistent, by setting the delivery mode to persistent when publishing. A persistent message in a durable queue is written to disk. If either part is missing, the message is lost on restart: a persistent message in a non-durable queue disappears with the queue. The exchange should also be durable, so the routing still exists after a restart.
X: But durability alone isn't enough. A message can still be lost before it's written, for example if the connection fails right after publishing. That's why publishers should use publisher confirms, which tell the publisher the broker has really stored the message. And consumers should use manual acknowledgements, so messages aren't removed until they're processed.
X: For surviving the loss of a whole node, not just a restart, you need replication. Modern RabbitMQ uses quorum queues, which replicate each queue across several nodes using the Raft consensus algorithm, and are the recommended choice for important data.
X: Persistence does cost some throughput, because of disk writes, but for business messages, it's worth it. After we lost [about 1,200] updates in [mid-2024] without confirms, we made sure all of these were in place.
+@p6-47
X: If RabbitMQ goes down, what happens depends on how it's set up, and on how well producers and consumers handle it.
X: On the broker side: with a single node, everything stops until it's back. Durable queues with persistent messages are recovered from disk after a restart, but non-durable queues and transient messages are lost. In a cluster with quorum queues, losing one node isn't a problem: the queue's leader moves to another node, and clients reconnect, with no data loss.
X: On the producer side: while the broker is unavailable, publishing fails. Without publisher confirms, a producer might think a message was sent when it wasn't. So producers should use confirms, retry with backoff, and, for critical messages, use the outbox pattern, saving the message in the database with the business change, and publishing it later, when the broker is back. That way nothing is lost during an outage.
X: On the consumer side: consumers lose their connection. Unacknowledged messages go back to the queue and are redelivered when consumers reconnect, so consumers must be idempotent. Client libraries support automatic connection recovery, and our services also have health checks and alerts on connection failures.
X: In [mid-2024], we had a [40-minute] problem where our publisher had no confirms, and [about 1,200] updates were lost silently. We recovered them by replaying vendor files, and adding confirms has prevented silent loss since.
+@p6-48
X: RabbitMQ doesn't have a single built-in retry feature, so I build retries from a few pieces, separating transient failures from permanent ones.
X: For quick transient failures, like a brief database timeout, the consumer retries in memory a few times with exponential backoff, for example using Polly, before giving up on the message.
X: For longer delays, I use a retry queue. When processing fails, the consumer rejects the message, or publishes it to a retry queue that has a message time-to-live, like 30 seconds, and a dead-letter exchange pointing back to the main queue. So the message waits in the retry queue, expires, and returns to the main queue to be processed again. Several retry queues with increasing delays give backoff. I track the number of attempts in a message header. Another option is the delayed message exchange plugin.
X: After the maximum attempts, or immediately for permanent errors like invalid data, the message goes to a final dead-letter queue, with the error details, and an alert, so someone can investigate and replay it after fixing the cause.
X: What I avoid is simply requeueing a failed message straight away, because it goes back to the front and can loop forever, blocking the queue.
X: A real case: some kit-assignment notifications vanished because the consumer used autoAck. I switched to manual acknowledgement, added [3] retries with exponential backoff, and then a dead-letter queue.
+@p6-49
X: To prevent message loss in RabbitMQ, I protect every step of the message's journey: publishing, storing, and consuming.
X: First, publishing. Use publisher confirms, so the publisher knows the broker actually stored each message, and retry when a confirm doesn't arrive. Use the mandatory flag, or an alternate exchange, so messages that can't be routed to any queue aren't silently dropped. For critical business messages, use the outbox pattern: save the message in the database in the same transaction as the business change, and a background process publishes it, so even a broker outage doesn't lose it.
X: Second, storing. Durable exchanges and queues, persistent messages, and quorum queues, which replicate across nodes, so a node failure doesn't lose data.
X: Third, consuming. Manual acknowledgements, only after processing has completed, for example after the database transaction commits. Never auto-ack for important messages. Failed messages are retried, and then go to a dead-letter queue, not discarded.
X: And finally, monitoring: alerts on dead-letter queues, unroutable messages and connection failures, plus idempotent consumers, because these measures can cause duplicates.
X: I learned this from a real incident in [mid-2024]: without publisher confirms, [about 1,200] updates were lost silently in [40 minutes]. We recovered them by replaying the vendor files, added confirms at about [5 percent] throughput cost, and there's been no silent loss since.

X: To scale RabbitMQ, I first scale the consumers, and only then think about the broker.
X: Scaling consumers: several consumers on the same queue share the work, with RabbitMQ distributing messages between them. The prefetch count controls how many unacknowledged messages each consumer gets at once; a sensible value, like 10 to 50, balances throughput and fairness. Consumers can be autoscaled on queue depth. Scaling the broker: run a cluster of three nodes, with quorum queues for important data, replicated for availability. A single queue is handled by one node, so for very high throughput, you can spread load across several queues, for example with the consistent hash exchange, or use RabbitMQ streams. Keep messages small and queues short, because RabbitMQ performs best when queues are near empty. Use long-lived connections with several channels, instead of opening a connection per message.
X: For monitoring, the key metrics are: queue depth and how it's changing, publish and acknowledge rates, unacknowledged messages, consumer count per queue, dead-letter queue size, connections and channels, memory and disk alarms, which block publishers, and node health. We use the management UI and Prometheus with Grafana dashboards, with alerts on growing queues, dead letters, zero consumers and resource alarms.
X: A queue with growing depth and no consumers is the classic warning sign I always alert on.
