X: MCP, the Model Context Protocol, was created to solve an integration problem in AI. Before it, every AI application had to build its own custom integration for every tool or data source it wanted to use. If you have N AI apps and M tools, that's N times M integrations, each one different, and each one maintained separately.
X: Anthropic introduced MCP as an open standard in late 2024 to fix that. It defines one common protocol for how an AI application discovers and calls tools and reads data. So you build an MCP server for a tool once, and any MCP-compatible host can use it: Claude, Cursor, GitHub Copilot, and others. That turns N times M into N plus M. People often compare it to USB-C for AI: one standard connector instead of a different cable for every device.
X: It also gives models a consistent way to see what a tool does, through its name, description and input schema, so they can decide when to use it.
X: That's exactly why I chose it for our deployment automation. I built the CIRT MCP server once, with about 77 tools for builds, releases and multi-node deployments on our on-premise Azure DevOps Server, and it works in Cursor, Claude Code and Copilot without any changes. It cut our deployments from 6 hours to 2, and from 6 people to 1.
+@p8-2
X: MCP has three roles: the host, the client and the server.
X: The host is the AI application the user works in, like Cursor or Claude Code. Inside the host, there's an MCP client for each server it connects to. The MCP server is a separate program that exposes capabilities: tools, which are actions the model can call, like queue a build; resources, which are data the model can read, like a file or a record; and prompts, which are reusable templates.
X: The client and server talk using JSON-RPC 2.0, either over stdio, where the host starts the server as a local process and they communicate through standard input and output, or over Streamable HTTP for remote servers. The flow is: first an initialize handshake, where they agree on the protocol version and capabilities. Then the client calls tools/list to discover the available tools, with their names, descriptions and input schemas. The host gives those to the model. When the model decides to use a tool, the host sends tools/call with the arguments, and the server runs it and returns the result, which goes back to the model.
X: My CIRT MCP server uses the stdio transport. Each engineer's Cursor or Claude Code starts it locally, and it calls our Azure DevOps Server with that engineer's own permissions.
+@p8-3
X: A REST API and MCP solve different problems, and they often work together.
X: A REST API is designed for programs written by developers. A developer reads the documentation, understands the endpoints, and writes code to call them in the right way. MCP is designed for AI models. Its tools are self-describing: each one has a name, a natural-language description of when to use it, and a JSON schema for its inputs. They're discovered at runtime, and there's one standard way to call them and return results, across every tool and every host.
X: So why not let the model call REST APIs directly? Because raw APIs are big, inconsistent, and full of details the model doesn't need, which leads to wrong calls and wasted context. An MCP server lets you design a small set of task-focused tools, like deploy_release_stage, with safe defaults, validation, permission checks and summarised outputs. It's a safety and usability layer for the model. And because MCP is a standard, the same server works in Cursor, Claude Code and Copilot.
X: In practice, MCP servers often wrap REST APIs. My CIRT MCP server is exactly that: it wraps the Azure DevOps Server REST APIs, plus our install scripts, as about 77 focused tools, so engineers can say what they want in plain language and the agent calls the right APIs safely.
+@p8-4
X: Discovery happens when the connection starts. The MCP client calls tools/list, and the server returns every tool with its name, a description, and a JSON schema for its input parameters. The host passes those definitions to the model, as part of its context, so the model knows which tools exist and what each one does.
X: The decision is made by the model. When the user asks something, like "deploy release 4.2 to UAT", the model compares that goal with the tool descriptions, picks the tool that fits best, and produces a tool call with arguments that match the schema. The host then sends that call to the server, gets the result, and gives it back to the model, which decides whether it's done or needs another tool. That's the agent loop.
X: This means the quality of the names and descriptions directly decides how well the agent behaves. If two tools sound similar, the model will mix them up.
X: I saw that in practice with my CIRT MCP server, which has about 77 tools. Early on, the model sometimes picked the wrong one. I fixed it by using verb-noun names like queue_build and get_release_status, adding "use this when" to descriptions, using enums for environment names, and removing overlapping tools. After that, tool selection became very reliable.
+@p8-5
X: Each MCP tool defines its parameters with a JSON Schema: the parameter names, their types, which ones are required, descriptions, and constraints like enums for fixed values. In the official C# SDK, which I used, you don't write the schema by hand. You write a normal C# method, mark it as a tool, and add Description attributes to the method and each parameter. The SDK generates the schema from the method signature. So a parameter like environment can be an enum of FV, TechOps, UAT and Prod, and the model can only choose from those.
X: Responses come back as a list of content items: usually text, but it can also include images or embedded resources. Newer versions of the protocol also support structured content, which is JSON with an output schema, so the result is machine-readable. And there's an isError flag for failures, so the model knows the call didn't succeed.
X: My design rule for responses is to keep them short and useful. In the CIRT MCP server, a status tool returns a compact summary, like the status, the failing step, a few key log lines and a link, instead of dumping raw JSON or full logs. That saves the model's context and helps it reason about the next step.
+@p8-6
X: I handle tool errors so that the model, and the user, can understand what went wrong and what to do next, instead of getting a stack trace.
X: Inside each tool, I catch exceptions and return a result with the isError flag set, and a clear, actionable message: what failed, why, and what to try. For example, "Environment UAT2 doesn't exist. Valid environments are FV, TechOps, UAT and Prod." The model can then correct itself and retry with the right value. I distinguish three kinds of errors. Validation errors, where the input is wrong, so the model should fix the arguments. Permission errors, where the user isn't allowed to do this, so the model should stop and tell the user. And transient failures from Azure DevOps, like timeouts, which the server retries itself with backoff, a limited number of times, only for safe operations.
X: I never return secrets or internal details in error messages, and every error is logged with a correlation id so I can investigate.
X: In the CIRT MCP server, this made a big difference to reliability. Clear errors meant the agent could recover from most mistakes on its own, and for real failures, like a failed deployment step, the user got a clear report with the failing node and step, instead of a confusing exception.
+@p8-7
X: Preventing unauthorised or dangerous operations was the core design concern for my CIRT MCP server, because an AI agent that can deploy is powerful.
X: First, identity. The server uses each user's own Azure DevOps personal access token. So the agent can only do what that person could already do by hand; there's no shared admin account. Second, the existing controls stay in place. Production releases still need pre-deployment approvals by named approvers in Azure DevOps, and the MCP tools can show pending approvals but can't approve them. Third, read and write are separated. Read-only tools, like status and logs, are the default. X: RAG and fine-tuning both adapt a model to your needs, but in different ways.
X: RAG, retrieval-augmented generation, adds knowledge at question time. When a user asks something, the system retrieves relevant pieces of your own documents and puts them into the prompt, so the model answers using current, private information, and can cite its sources. Nothing about the model changes. Fine-tuning actually retrains the model on your examples, changing its behaviour: its style, tone, format, or how it handles a specific task. It needs good training data, time and cost, and it doesn't keep knowledge up to date.
X: So my rule is: RAG for knowledge, fine-tuning for behaviour. If the problem is "the model doesn't know our documents", use RAG. If it's "the model doesn't answer in the format or style we need", consider fine-tuning, and often good prompting is enough.
X: To build a RAG workflow: ingest the documents, clean them, and split them into chunks of sensible size with some overlap. Create embeddings for each chunk and store them in a vector index, with metadata like source and access permissions. At query time, embed the question, retrieve the most relevant chunks, often with hybrid keyword and vector search plus re-ranking, filter by the user's permissions, and build a prompt that tells the model to answer only from those chunks and cite them. Then evaluate it with a test set.

X: I evaluate LLM output the same way I'd test any important feature: with real test cases, automatic checks, and human review, tracked over time.
X: First, a test set. I collect realistic questions or tasks, ideally from real usage, with the expected answers or the key facts an answer must contain. Second, automatic checks: is the output in the right format, does it follow the schema, are citations present, and is the answer grounded in the provided sources rather than invented. Third, LLM-as-judge: using a model with a clear rubric to score answers for correctness, completeness and tone. That scales well, but I check its scores against human judgement, because judges can be biased. Fourth, human review of a sample, especially for high-risk outputs. And fifth, tracking quality, latency and cost for each version of the prompt or model, so every change is compared with the previous one, like a regression test.
X: For tool-using agents, evaluation also means checking that the agent picks the right tool with the right arguments for each request.
X: For my CIRT MCP server, the most valuable evaluation would be exactly that: a set of deployment requests where we check the tool choice and arguments automatically on every change, so improvements are based on evidence.

X: Securing LLM applications with enterprise data has a few layers, and in a healthcare company like ours, the rules are strict.
X: First, the platform. Use enterprise endpoints, like Azure OpenAI or an enterprise agreement, where your data isn't used for training, with private networking, regional data residency and proper identity. Second, the data that goes in. Strip or mask personal health information and secrets before they reach a prompt, and only retrieve documents the user is allowed to see, enforcing access control in the retrieval step, not trusting the model to do it. Third, the tools. Give the model least-privilege tools that act with the user's own permissions, separate read and write actions, and require human approval for risky ones. Fourth, prompt injection. Treat retrieved content and tool outputs as data, never instructions, and validate everything the model produces before acting on it. Fifth, the output. Filter for sensitive data leaking out, and validate structured outputs against schemas. And finally, governance: log prompts and actions with sensitive data masked, audit usage, and follow the company's AI policy.
X: These are the same principles I used in the CIRT MCP server: the user's own credentials, no secrets in the model's context, confirmations for write actions, and every call logged.

X: AI-generated code has real risks. It can contain subtle logic bugs that look correct. It can use insecure patterns, like building SQL from strings or forgetting an authorization check. It can invent packages or APIs that don't exist, and an invented package name can even be registered by an attacker. It can bring in licensing issues. And maybe the biggest risk is code that gets merged but nobody on the team really understands.
X: To prevent those problems, I treat AI-generated code like a pull request from a new junior developer. I review every line, I don't accept large changes I can't explain, and I check APIs and packages against official documentation. Tests are required, and for important logic, I write or review tests for the edge cases myself. Then the normal pipeline protects us: compilation with warnings as errors, unit and integration tests, the SonarQube quality gate, dependency vulnerability scanning, and code review by a colleague. For security-sensitive code, like authentication or data access, I'm extra careful.
X: A real example: Copilot once suggested a retry policy that retried every HTTP call, including the POST that creates a release. A retry after a timeout could have created duplicate releases. I limited retries to safe, idempotent calls and added a test to prove POSTs aren't retried. That's why review matters.
