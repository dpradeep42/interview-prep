@p4-36
Q: An async deadlock happens when code blocks on a Task (.Result, .Wait()) while a SynchronizationContext (WinForms, WPF, classic ASP.NET) needs that same blocked thread to run the continuation: each waits for the other forever. ASP.NET Core has no SynchronizationContext, so it doesn't deadlock that way, but blocking still causes thread pool starvation.
- Fix: async all the way; never block on async in request code.
- Libraries use ConfigureAwait(false) to avoid capturing contexts.
- If you must call async from sync (Main, legacy), GetAwaiter().GetResult() at the very top, knowing the risks.
- Thread pool starvation symptoms: latency climbs, thread count grows slowly (about one thread per second injection beyond min).
? Why does ASP.NET Core avoid the classic deadlock? :: It has no request SynchronizationContext, so continuations run on any pool thread.
? Is .Result ever fine? :: After the task has completed (e.g. after WhenAll), it doesn't block.

@p4-37
Q: ConfigureAwait(false) tells await not to resume on the captured SynchronizationContext or TaskScheduler, so the continuation runs on a thread pool thread. It matters in libraries and UI apps to avoid deadlocks and context-switch overhead; in ASP.NET Core app code it makes little difference because there's no context.
- Library authors should still use it because their code may run under UI contexts.
- .NET 8 added ConfigureAwaitOptions (e.g. SuppressThrowing, ForceYielding) for Task.
- After ConfigureAwait(false), don't touch UI elements or context-bound state.
? Does ConfigureAwait(false) make code faster in ASP.NET Core? :: Negligibly; it's mainly about correctness in libraries.
? What does ForceYielding do? :: Forces the continuation to be queued asynchronously even if the task already completed.

@p4-39
Q: IEnumerable<T> gives forward-only iteration; ICollection<T> adds Count, Add, Remove and Contains; IList<T> adds index access and Insert. I accept the smallest interface a method needs and return read-only interfaces (IReadOnlyList, IReadOnlyCollection) to communicate intent.

@p4-40
Q: First returns the first match and throws if none; FirstOrDefault returns default (null) instead. Single requires exactly one match and throws if none or more than one; SingleOrDefault returns default if none but still throws if more than one.
- Use Single when duplicates indicate a data bug; First when order matters (with OrderBy).

- .NET 6 added FirstOrDefault(defaultValue) overloads.
- FindAsync by key checks the change tracker first.
? Which is faster in EF Core? :: First (TOP 1) reads less than Single (TOP 2), but pick by meaning.
? FirstOrDefault on value types? :: Returns default (0 for int), which may be ambiguous.

@p4-41
Q: Any() stops at the first match and translates to EXISTS in SQL; Count() counts every matching row. Use Any() to check existence; on in-memory collections the Count property is already O(1), and LINQ Count() uses it when available.

- Count() > 0 is a common code smell (CA1827 analyzer).
? What does EF Core generate for Any()? :: SELECT CASE WHEN EXISTS (...) THEN 1 ELSE 0 END.

@p4-42
Q: A closure is a lambda that captures variables from its outer scope; the compiler moves them into a hidden class so they live as long as the lambda. Pitfalls include capturing a loop variable in older for loops, accidentally keeping large objects alive, and hidden allocations on hot paths.
- foreach variables are per-iteration since C# 5; for loop variables are shared.
- static lambdas (C# 9) prevent capture and allocations.
- Captured variables are shared: changing them later changes what the lambda sees.
```csharp
var actions = new List<Action>();
for (int i = 0; i < 3; i++) actions.Add(() => Console.Write(i));   // prints 333
for (int i = 0; i < 3; i++) { var copy = i; actions.Add(() => Console.Write(copy)); } // 012
```
? Do closures allocate? :: Yes, a display class instance and a delegate, unless the lambda is static or captures nothing.
? Why can closures cause memory leaks? :: Long-lived delegates (event handlers) keep captured objects alive.

@p4-43

@p4-48
Q: Garbage collections pause threads (briefly for Gen 0/1, longer for Gen 2 and LOH compaction) and high allocation rates trigger more collections, raising p99 latency and CPU. I reduce allocations on hot paths (pooling, Span, avoiding LINQ in tight loops, streaming), and measure with dotnet-counters and profilers.
- Generational GC: Gen 0 (short-lived), Gen 1, Gen 2 (long-lived), LOH and POH.
- Server GC for throughput (one heap per core); DATAS (default for Server GC since .NET 9) adapts heap count to reduce memory.
- Background GC lets Gen 2 run concurrently.
- ArrayPool<T>, RecyclableMemoryStream, object pooling for big buffers.
? What is the POH? :: Pinned Object Heap (.NET 5+) for objects that must not move, reducing fragmentation.
? Should you call GC.Collect? :: Almost never; it usually hurts performance.

@p4-49
