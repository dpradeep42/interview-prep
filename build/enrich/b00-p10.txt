T: What is middleware in ASP.NET Core?
A: A component in the request pipeline that receives HttpContext, can act before and after the next component, or end the request.|The pipeline is a chain of RequestDelegate functions built in Program.cs with app.Use..., in registration order.|Built-in examples: exception handler, HTTPS redirection, static files, routing, CORS, authentication, authorization, rate limiting, endpoints.
H: Russian dolls: each layer wraps the next, in on the way in, out on the way back.
V: mwpipe
L: 131,132
Q: Middleware is a piece of code in the ASP.NET Core request pipeline that handles an HttpContext: it can do work before the next component runs, call the next one, do work after it returns, or stop the request (short-circuit). The pipeline is just a chain of these components, executed in the exact order they are registered in Program.cs.
- How it works: each middleware is a `RequestDelegate` (`Task Invoke(HttpContext)`). At startup the `IApplicationBuilder` composes them in reverse into one delegate, so at runtime a request flows in through every layer and the response flows back out in reverse order.
- Four verbs: `Use` adds a component that can call `next`; `Run` adds a terminal one that never calls next; `Map` branches by path prefix; `MapWhen`/`UseWhen` branch on a predicate (UseWhen rejoins the main pipeline, MapWhen does not).
- Order is behaviour: exception handler first so it catches everything; `UseRouting` before CORS, authentication and authorization; `UseAuthentication` before `UseAuthorization`; endpoints last. WebApplication adds UseRouting and UseEndpoints for you if you do not call them.
- Short-circuiting: static files, CORS preflight, auth failures (401/403) and rate limiting (429) end the request early, so later middleware and your controller never run. That is also a performance win.
- Middleware vs filters: middleware sees every request and knows nothing about MVC actions or model binding; filters run only around controller actions and see ActionArguments and results. Cross-cutting HTTP concerns go in middleware.
- In IRT: our pipeline has [a correlation-id middleware] at the top that reads or creates `X-Correlation-ID`, pushes it into the logging scope and echoes it in the response, plus global exception handling returning ProblemDetails, so every log line in CloudWatch can be traced across services.
- Pitfall: you cannot change status code or headers once the response has started streaming (`Response.HasStarted`); set headers before calling next or use `Response.OnStarting`.
```csharp
var app = builder.Build();
app.UseExceptionHandler();        // 1. catch everything below
app.UseHttpsRedirection();
app.UseMiddleware<CorrelationIdMiddleware>();
app.UseRouting();
app.UseCors("ui");
app.UseAuthentication();          // who are you?
app.UseAuthorization();           // are you allowed?
app.UseRateLimiter();
app.MapControllers();             // terminal: endpoints
app.Run();
```
? What is a RequestDelegate? :: A delegate `Task (HttpContext context)`; the whole pipeline compiles down to one of them.
? What happens if UseAuthorization comes before UseAuthentication? :: HttpContext.User is still anonymous when policies are checked, so protected endpoints return 401 even with a valid token.
? Is middleware a singleton? :: Convention-based middleware is created once at startup (effectively singleton); IMiddleware is resolved per request from DI.

T: How do you write custom middleware?
A: Convention-based: a class with a constructor taking RequestDelegate next and a public InvokeAsync(HttpContext ...) method, registered with app.UseMiddleware<T>().|Factory-based: implement IMiddleware, register it in DI, then UseMiddleware<T>().|Inline: app.Use(async (ctx, next) => { ...; await next(ctx); }).|Wrap it in an extension method such as app.UseCorrelationId() for a clean Program.cs.
H: Before, next, after.
V: mwcustom
Q: There are three ways: an inline lambda with `app.Use`, a convention-based class (constructor takes `RequestDelegate next`, public `InvokeAsync(HttpContext)` method), or a class implementing `IMiddleware` that DI creates per request. Each one does its work before `await next(context)`, after it, or both, and is registered in Program.cs at the right place in the order.
- Convention rules: the class needs a public constructor with `RequestDelegate` and a public method named `Invoke` or `InvokeAsync` returning Task whose first parameter is HttpContext. No interface is required; ASP.NET Core finds the method by reflection once at startup.
- Extra InvokeAsync parameters are resolved from DI per request. That is the correct place for scoped services such as DbContext or an audit service.
- Package it as an extension method (`public static IApplicationBuilder UseCorrelationId(this IApplicationBuilder app) => app.UseMiddleware<CorrelationIdMiddleware>();`) so Program.cs reads like a story.
- Always `await next(context)`; never fire-and-forget it, and do not call it twice. To short-circuit, set the status code, write the response and simply return without calling next.
- Pass CancellationToken from `context.RequestAborted` to downstream calls, and use `ILogger` scopes rather than static state; the class is shared by all requests, so it must be thread-safe.
- In IRT: [the correlation-id middleware and a request-audit middleware] that records user, route, status code and duration for regulated endpoints, writing through a scoped audit service injected into InvokeAsync.
- Testing: unit-test by constructing it with a fake `next` delegate and a `DefaultHttpContext`; integration-test through WebApplicationFactory.
```csharp
public sealed class CorrelationIdMiddleware(RequestDelegate next, ILogger<CorrelationIdMiddleware> logger)
{
    private const string Header = "X-Correlation-ID";

    public async Task InvokeAsync(HttpContext context)
    {
        var id = context.Request.Headers.TryGetValue(Header, out var v) && !string.IsNullOrWhiteSpace(v)
            ? v.ToString() : Guid.NewGuid().ToString("N");
        context.TraceIdentifier = id;
        context.Response.OnStarting(() => { context.Response.Headers[Header] = id; return Task.CompletedTask; });

        using (logger.BeginScope(new Dictionary<string, object> { ["CorrelationId"] = id }))
        {
            await next(context);   // the rest of the pipeline runs inside the scope
        }
    }
}
// Program.cs
app.UseMiddleware<CorrelationIdMiddleware>();
```
? Why use Response.OnStarting for the header? :: Headers must be set before the body starts streaming; OnStarting runs at exactly that moment, even if a later component writes the response.
? How do you unit-test middleware? :: new DefaultHttpContext(), a next delegate that records it was called, then assert headers, status and logs.
? Inline lambda or class? :: Lambda for two lines; a class for anything with dependencies, logic or tests.

T: Convention-based vs factory-based (IMiddleware) middleware, and the scoped-service pitfall?

Q: Convention-based middleware is created once at startup, so anything in its constructor lives as long as the app; scoped services must be taken as `InvokeAsync` parameters instead.
```csharp
public sealed class AuditMiddleware(IAuditWriter audit, ICurrentUser user) : IMiddleware
{
    public async Task InvokeAsync(HttpContext ctx, RequestDelegate next)
    {
        var sw = Stopwatch.StartNew();
        await next(ctx);
        await audit.WriteAsync(user.Id, ctx.Request.Path, ctx.Response.StatusCode, sw.ElapsedMilliseconds, ctx.RequestAborted);
    }
}

```

T: What are the MVC filter types and their order, and how do you write a custom action filter?
A: Order: authorization filters, resource filters, model binding, action filters, the action, exception filters (for errors), result filters, the result.|Custom: implement IAsyncActionFilter (or ActionFilterAttribute) and register globally, per controller, or with [ServiceFilter]/[TypeFilter] for DI.|Use filters for MVC-aware concerns: validation, auditing an action's arguments, caching a result.

Q: Filters run inside the MVC action pipeline, after routing has selected a controller action. The order is authorization, resource, (model binding), action, the action method, exception (on errors) and result filters; each can run code before and after the next stage or short-circuit by setting a result.
- Authorization filters run first and can short-circuit with 401/403; resource filters wrap model binding (good for caching or turning off binding); action filters see `ActionArguments` and the `IActionResult`; result filters wrap result execution; exception filters catch exceptions from model binding, action filters and the action, but not from result execution.
- Scope and order: global, controller, then action; within the same scope the `Order` property decides. Before-code runs outside-in, after-code inside-out.
- DI: attributes cannot take constructor services, so use `[ServiceFilter(typeof(AuditFilter))]` (filter registered in DI) or `[TypeFilter]` (activated with DI arguments).

```csharp
public sealed class StudyNotLockedFilter(IStudyService studies) : IAsyncActionFilter
{
    public async Task OnActionExecutionAsync(ActionExecutingContext ctx, ActionExecutionDelegate next)
    {
        if (ctx.ActionArguments.TryGetValue("studyId", out var id) && await studies.IsLockedAsync((Guid)id!))
        {
            ctx.Result = new ConflictObjectResult(new ProblemDetails { Title = "Study is locked" });
            return;                       // short-circuit: action never runs
        }
        await next();
    }
}
// [ServiceFilter(typeof(StudyNotLockedFilter))] on the controller; services.AddScoped<StudyNotLockedFilter>();
```
? Filter or middleware for global exception handling? :: Middleware (UseExceptionHandler / IExceptionHandler), because exception filters miss errors outside MVC, such as in other middleware or result execution.
? ServiceFilter vs TypeFilter? :: ServiceFilter resolves the filter itself from DI (must be registered); TypeFilter creates it with ActivatorUtilities, so it does not need registration and can take extra arguments.

T: What are hosted services and BackgroundService?
A: IHostedService has StartAsync and StopAsync, called by the host at startup and graceful shutdown.|BackgroundService is a base class: override ExecuteAsync for a long-running loop, honouring the stoppingToken.|Register with AddHostedService<T>() (singleton); create a scope with IServiceScopeFactory for scoped services such as DbContext.
H: The host's own employees: start with the app, stop with the app.
Q: A hosted service is a class the .NET Generic Host starts when the application starts and stops on graceful shutdown, by calling `StartAsync` and `StopAsync`. `BackgroundService` is the convenient base class for a long-running loop: you override `ExecuteAsync(CancellationToken stoppingToken)` and keep working until the token is cancelled.
- Lifetime: hosted services are singletons. To use DbContext or other scoped services, inject `IServiceScopeFactory` and create a scope per unit of work (per message or per loop iteration).
- Shutdown: on SIGTERM (ECS task stop, Kubernetes) the host cancels the stoppingToken and waits `HostOptions.ShutdownTimeout` (30 seconds by default in .NET 6+) for StopAsync; finish or checkpoint the current item inside that time.
- Errors: since .NET 6 an unhandled exception in ExecuteAsync stops the whole host by default (`BackgroundServiceExceptionBehavior.StopHost`), so wrap each iteration in try/catch and log.
- Startup: before .NET 10 the synchronous part of ExecuteAsync up to the first await blocked startup; .NET 10 runs the whole of ExecuteAsync on a background task. .NET 8 added `IHostedLifecycleService` (StartingAsync, StartedAsync...) and concurrent start options.
- Timers: use `PeriodicTimer` (`await timer.WaitForNextTickAsync(ct)`) instead of Task.Delay loops or System.Threading.Timer callbacks that can overlap.
- Scaling: with several instances, every instance runs the service; for single-run jobs use a lock (database or Redis) or a queue so work is not duplicated.
- In IRT: [the SFTP polling worker] that checks vendor folders every [5 minutes], and RabbitMQ consumers that run as BackgroundServices in worker containers on ECS.
```csharp
public sealed class VendorFilePoller(IServiceScopeFactory scopes, ILogger<VendorFilePoller> log) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        using var timer = new PeriodicTimer(TimeSpan.FromMinutes(5));
        while (await timer.WaitForNextTickAsync(stoppingToken))
        {
            try
            {
                using var scope = scopes.CreateScope();
                var importer = scope.ServiceProvider.GetRequiredService<IVendorFileImporter>();
                await importer.ImportNewFilesAsync(stoppingToken);
            }
            catch (Exception ex) when (ex is not OperationCanceledException)
            {
                log.LogError(ex, "Vendor file poll failed");   // keep the host alive
            }
        }
    }
}
builder.Services.AddHostedService<VendorFilePoller>();
```
? Hosted service vs Hangfire or Quartz? :: Hosted services suit simple loops and consumers; Hangfire/Quartz add persistence, retries, cron schedules and dashboards for many scheduled jobs.
? Why not do this work inside an API request? :: Requests should be short; background work needs its own lifetime, retries and graceful shutdown.

T: What are Span<T> and Memory<T>?
A: Span<T> is a ref struct that views a contiguous block of memory (array, stackalloc, native) without copying; slicing is free.|Because it is stack-only it cannot be a field of a class, boxed, or held across await; Memory<T> is the heap-friendly version for async code.|Used for zero-allocation parsing and buffers; ReadOnlySpan<char> for strings.
H: A window onto memory, not a copy.
Q: `Span<T>` is a lightweight view (pointer plus length) over a contiguous region of memory, such as part of an array, a stackalloc buffer or native memory, that lets you read, write and slice it without allocating or copying. It is a `ref struct`, so it lives only on the stack; `Memory<T>` is the equivalent that can be stored on the heap and used across `await`.
- Why it matters: parsing and formatting without creating substrings or temporary arrays cuts allocations and GC pressure; much of .NET's performance gains (System.Text.Json, Kestrel, int.Parse(ReadOnlySpan<char>)) is built on spans.
- Rules: cannot be boxed, captured in lambdas, stored in class fields or used as a generic type argument in most places; C# 13 relaxed this so ref structs can be locals in async methods and iterators as long as they are not used across an await or yield.
- `ReadOnlySpan<char>` from `"text".AsSpan()` replaces Substring in hot paths; `stackalloc byte[256]` for small temporary buffers; `ArrayPool<T>.Shared` for larger rented buffers.
- `Memory<T>` / `ReadOnlyMemory<T>`: store in fields, pass to async APIs (Stream.ReadAsync(Memory<byte>)), and call `.Span` when you process synchronously.
- When to use: hot paths you have measured (parsers, protocol handling); not needed in normal business code where readability wins.
- In my work: [parsing fixed-width fields in vendor files] with ReadOnlySpan<char> slices instead of Substring, which reduced allocations in the import loop; measured with BenchmarkDotNet.
```csharp
static bool TryParseKit(ReadOnlySpan<char> line, out int site, out int kit)
{
    // "SITE0042|KIT000913"
    int bar = line.IndexOf('|');
    site = kit = 0;
    return bar > 4
        && int.TryParse(line[4..bar], out site)          // slice, no allocation
        && int.TryParse(line[(bar + 4)..], out kit);
}
```
? Why can't Span<T> be used across await? :: The method's state is moved to the heap at an await, and a span may point to stack memory that no longer exists.
? Span vs ArraySegment? :: ArraySegment works only over arrays and is a normal struct; Span works over any contiguous memory and is faster but stack-only.

T: What is IAsyncEnumerable<T> and async streams?

```csharp
                       .OrderBy(a => a.Timestamp)
```

T: Response caching vs output caching vs IMemoryCache vs HybridCache?
A: Response caching: honours HTTP Cache-Control headers so browsers and proxies (and the middleware) can reuse responses.|Output caching (.NET 7): server-side cache of whole responses with policies, vary-by and tag-based eviction.|IMemoryCache / IDistributedCache (Redis) cache data in code; HybridCache (.NET 9) combines both with stampede protection.
H: Headers for clients, outputs for endpoints, data for code.
V: cacheTbl
Q: They cache at different levels. Response caching is HTTP-header driven (Cache-Control, Vary) and mostly benefits browsers and proxies; output caching stores the generated response on the server under policies you control; IMemoryCache, IDistributedCache and HybridCache cache data objects inside your code.
- Response caching middleware obeys client headers, so a client sending `Cache-Control: no-cache` bypasses it; it only caches GET/HEAD 200 responses without Authorization headers.
- Output caching: `AddOutputCache` + `[OutputCache(Duration = 60, Tags = ["studies"])]` or `.CacheOutput()`; evict with `IOutputCacheStore.EvictByTagAsync("studies")` when data changes; storage can be Redis (.NET 8) for multiple instances.
- IMemoryCache: per instance, fast, lost on restart, set size limits and expirations; IDistributedCache (Redis/ElastiCache) shares across instances but needs serialisation.
- HybridCache (.NET 9): L1 memory + L2 distributed, stampede protection (one caller computes, others wait), tags; API `GetOrCreateAsync(key, factory)`.
- Pitfalls: caching user-specific or authorised data under a shared key, no invalidation strategy, cache stampede at expiry; add jitter and invalidate on write events.
- In IRT: [reference data such as countries, depots and study configuration] in IMemoryCache with ElastiCache behind it; never randomisation or kit allocation data.
```csharp

    await _cache.GetOrCreateAsync($"study-config:{studyId}",
        async token => await _repo.LoadConfigAsync(studyId, token),
        new HybridCacheEntryOptions { Expiration = TimeSpan.FromMinutes(10) },
        tags: ["study-config"], cancellationToken: ct);
```
? What is a cache stampede? :: Many requests miss an expired key together and all hit the database; prevent with locking (HybridCache does this), early refresh or jittered expirations.
? What should never be cached? :: Security-sensitive or highly consistent data, such as permissions mid-change or kit allocation.

T: How do you add resilience with Polly and .NET 8 resilience handlers?
A: Polly v8 builds ResiliencePipelines of strategies: retry, circuit breaker, timeout, rate limiter, fallback, hedging.|.NET 8 Microsoft.Extensions.Http.Resilience adds AddStandardResilienceHandler to HttpClients with sensible defaults.|Retry only transient errors, with exponential backoff and jitter, and make calls idempotent.
H: Retry, break, time out, fall back.
V: resil
Q: Polly is the standard .NET resilience library; version 8 composes strategies (retry, circuit breaker, timeout, rate limiter, fallback, hedging) into a `ResiliencePipeline`. In .NET 8, `Microsoft.Extensions.Http.Resilience` wires Polly into IHttpClientFactory, and `AddStandardResilienceHandler()` gives a recommended stack in one line.
- Standard handler order (outer to inner): rate limiter, total request timeout (30 seconds), retry (3 attempts, exponential backoff with jitter), circuit breaker, per-attempt timeout (10 seconds). All values are configurable.
- Retry only transient failures (timeouts, 5xx, 408, 429) and idempotent operations; respect `Retry-After`; never retry 400/401/403.
- Circuit breaker: after a failure ratio within a sampling window it opens and fails fast, giving the dependency time to recover, then half-opens to test.
- Hedging (`AddStandardHedgingHandler`) sends a parallel request after a delay to cut tail latency, only for safe reads.
- Polly also works outside HTTP: `ResiliencePipelineBuilder` around SFTP, database or SDK calls; inject `TimeProvider` to test delays.
- Telemetry: Polly v8 emits metrics and logs for retries and circuit state; alert when the breaker opens.
- In IRT: the SFTP base class retries [3 times with backoff and jitter] on timeouts and connection resets, and typed HttpClients to vendor APIs use the standard handler.
```csharp
var pipeline = new ResiliencePipelineBuilder()
    .AddRetry(new RetryStrategyOptions
    {
        MaxRetryAttempts = 3, BackoffType = DelayBackoffType.Exponential, UseJitter = true,
        ShouldHandle = new PredicateBuilder().Handle<TimeoutException>().Handle<SocketException>()
    })
    .AddTimeout(TimeSpan.FromSeconds(60))
    .Build();

await pipeline.ExecuteAsync(async ct => await sftp.UploadAsync(file, ct), cancellationToken);
```
? Why jitter? :: Without randomness all clients retry at the same moment and create synchronised spikes (thundering herd).
? Circuit breaker vs retry? :: Retry handles short blips; the breaker stops calling a dependency that is clearly down, protecting both sides.
