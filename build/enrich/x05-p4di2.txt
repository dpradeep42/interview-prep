X: Choosing lifetimes is a trade-off, and both extremes cause problems.
X: Not everything can be a singleton, because one instance is shared by every thread and every request. So it must be thread-safe, and it must never hold per-request data, or one user could see another user's data. A singleton also can't safely hold scoped things like DbContext, which leads to captive dependency bugs, stale data and concurrency exceptions.
X: Not everything should be transient either. Creating new objects for every injection wastes allocations, expensive objects get rebuilt constantly, and you lose per-request sharing. X: So my rule: singleton for stateless or thread-safe shared things, like configuration, caches, HttpClient factories and the RabbitMQ connection. Scoped for per-request state, like DbContext and the current user. Transient for light, stateless helpers, like validators. I can go through the lifetime dependency rules too.

X: When a request finishes, several things happen in a clean order.
X: First, the endpoint returns, and the response flows back out through the middleware pipeline in reverse order, so middleware can add headers or log the result. X: Use, Run and Map are the three basic ways to build the middleware pipeline.
X: Use adds middleware that receives the context and a next delegate. It can do work before calling next, call next to pass the request on, and then do more work as the response comes back.
