X: Spring Boot is a framework built on top of the Spring framework, for building Java applications and services quickly, with very little setup. It's the Java world's equivalent of ASP.NET Core.
X: The Spring framework itself provides the core features, like dependency injection, web support with Spring MVC, data access and security. But on its own, it needed a lot of configuration. Spring Boot removes most of that with a few key ideas.
X: First, auto-configuration. Spring Boot looks at the libraries on the classpath and configures sensible defaults automatically. For example, if a database driver and Spring Data JPA are present, it sets up a data source and repositories. You only configure what's different.
X: Second, starters. These are dependency bundles, like spring-boot-starter-web, which bring in everything needed for a feature with compatible versions.
X: Third, an embedded web server, like Tomcat, so the application runs as a single executable JAR, with java -jar, which is ideal for containers.
X: Fourth, production-ready features with Actuator: health checks, metrics and other operational endpoints.
X: And externalised configuration, with application.yml files, environment variables and profiles for each environment.
X: My main platform is .NET, but the concepts map almost one to one: auto-configuration and starters are like ASP.NET Core's defaults and NuGet packages, the embedded server is like Kestrel, and Actuator is like health checks and metrics. So I can work comfortably in a Spring Boot codebase.

X: Dependency injection in Spring works the same way as in .NET. Instead of a class creating its own dependencies, they're provided from outside, which makes the code loosely coupled and easy to test.
X: Spring's IoC container, Inversion of Control, is called the ApplicationContext. It creates and manages objects called beans, and wires their dependencies together. Classes become beans in two main ways: through component scanning, where classes marked with annotations like Component, Service, Repository or Controller are discovered automatically, or through Bean methods in a Configuration class, which is useful for third-party classes. Beans have scopes: singleton by default, which means one instance for the whole application, prototype, which means a new instance each time, and web scopes like request.
X: Autowired is the annotation that tells Spring where to inject a dependency. It can be used on constructors, setters or fields. The recommended approach is constructor injection, with final fields, because the dependencies are explicit, required, and easy to provide in tests. And if a class has only one constructor, Autowired isn't even needed; Spring uses it automatically. Field injection, with Autowired on a private field, is discouraged, because it hides dependencies and makes testing harder.
X: When there are several implementations of an interface, Qualifier or Primary chooses one.
X: Coming from .NET, the ApplicationContext is like the service provider, and constructor injection works exactly as I use it every day.

X: Component, Service and Repository are Spring annotations that all register a class as a Spring bean, through component scanning. Technically, Service and Repository are specialisations of Component. The difference is mostly about meaning, with one important extra feature for Repository.
X: Component is the generic annotation. It means "this class is a Spring-managed component". I use it for classes that don't fit a specific layer, like a helper or a mapper.
X: Service marks a class in the business logic layer, like a ShipmentService that applies business rules. It doesn't add special behaviour today, but it makes the code's structure clear, and tools or aspects can target it, for example applying transactions or logging to all services.
X: Repository marks a data access class. It has one real extra feature: exception translation. Spring automatically converts database-specific exceptions, like those from JDBC or Hibernate, into Spring's own consistent DataAccessException hierarchy, so the rest of the application doesn't depend on a particular database technology. With Spring Data JPA, you often just declare a repository interface, and Spring creates the implementation.
X: There's also Controller and RestController, for the web layer.
X: So the reason to use the specific ones is clarity and layering: anyone reading the code knows each class's role straight away. It's similar to how I organise .NET code into controllers, services and repositories.

X: To build a REST controller in Spring Boot, I create a class with the RestController annotation. That combines Controller with ResponseBody, so the return values are written straight into the response as JSON, using Jackson. A RequestMapping annotation on the class sets the base path, like api slash shipments.
X: Each endpoint is a method with an annotation for the HTTP method and path: GetMapping, PostMapping, PutMapping, PatchMapping or DeleteMapping. Parameters are bound from the request with annotations: PathVariable for parts of the URL, like the shipment id, RequestParam for query string values, like page and size, RequestBody for the JSON body, and RequestHeader for headers. Adding Valid to the request body triggers Bean Validation, with annotations like NotNull and Size on the request class, and invalid input returns a 400 error.
X: The controller stays thin. The service is injected through the constructor, and each method just calls the service. For the response, I return ResponseEntity to control the status code and headers, for example 201 Created with a Location header for a new shipment, or 404 when it doesn't exist. Request and response DTOs, often Java records, keep the API separate from the database entities.
X: Errors are handled centrally with a RestControllerAdvice class.
X: It's the same structure as an ASP.NET Core controller, with attributes like HttpGet, FromRoute and FromBody, and returning results like Ok or CreatedAtAction.

X: Spring Boot reads configuration from several sources, in a defined order of priority, so the same application can run in every environment without code changes.
X: The main source is application.properties or application.yml in the project. Values can be overridden by environment variables, command-line arguments, and external configuration services, with higher-priority sources winning. Environment variables are mapped automatically, for example SPRING_DATASOURCE_URL overrides spring.datasource.url, which is ideal for containers.
X: In code, configuration can be read with the Value annotation for single values, but the better approach is a ConfigurationProperties class: a typed class, or record, bound to a section of the configuration, with validation. That's very similar to the options pattern in .NET.
X: Profiles let you have different configuration for different environments. You create files like application-dev.yml, application-uat.yml and application-prod.yml, and activate a profile with the spring.profiles.active setting, usually from an environment variable. Spring loads the common file first, then the profile's file on top. Profiles can also turn beans on or off, using the Profile annotation, for example a fake email sender in dev.
X: Secrets don't go in these files. They come from environment variables or a secrets manager, like AWS Secrets Manager, through Spring Cloud integrations.
X: It's the same idea as ASP.NET Core's appsettings files with environment-specific overrides, like appsettings.Production.json, plus environment variables.

X: JPA, Hibernate and Spring Data JPA are three layers that together handle database access in Java.
X: JPA, now called Jakarta Persistence, is the standard specification. It defines how Java classes are mapped to database tables, using annotations like Entity, Id, Column, and relationships like OneToMany, plus the EntityManager API and the JPQL query language. It's just a specification, not an implementation.
X: Hibernate is the most popular implementation of JPA. It does the actual work: generating SQL, tracking changes to entities, caching, and loading related data, lazily or eagerly.
X: Spring Data JPA sits on top. You declare a repository interface, like ShipmentRepository extends JpaRepository, and Spring creates the implementation at runtime, with methods for saving, finding and deleting. You can even declare methods like findByStatusAndSiteId, and Spring generates the query from the method name. For complex queries, you use the Query annotation with JPQL or native SQL.
X: Compared with EF Core, the concepts are very similar: entities, a unit of work, change tracking, lazy loading, and the N plus one problem to watch out for. The main differences are: EF Core uses LINQ, which is type-checked and composable in C#, while JPA uses JPQL strings or the more verbose Criteria API. EF Core has migrations built in, while Java projects usually use Flyway or Liquibase. And EF Core's DbContext plays the role of the EntityManager.
X: My experience is mainly EF Core, and those concepts transfer directly.

X: For exception handling in Spring Boot, I use a central handler, so every error returns a consistent response, and controllers stay clean.
X: I create a class annotated with RestControllerAdvice, containing methods annotated with ExceptionHandler for specific exception types. For example, a ShipmentNotFoundException returns 404, a validation exception, like MethodArgumentNotValidException, returns 400 with the field errors, and a general handler for unexpected exceptions logs the full error and returns 500 without exposing internal details. Spring supports the standard ProblemDetail format, RFC 9457, the same format ASP.NET Core uses, so responses are consistent across services. That's very similar to exception-handling middleware with problem details in .NET.
X: For security, I use Spring Security. Every request passes through a security filter chain, which is configured as a SecurityFilterChain bean. For an API, I configure it as an OAuth2 resource server: it validates JWT access tokens from our identity provider, checking the signature, issuer, audience and expiry, and the API stays stateless. Then I set authorisation rules for URL patterns, like requiring a role for admin endpoints, and use method security, with the PreAuthorize annotation, for fine-grained checks on service methods. CORS and security headers are configured there too.
X: This maps directly to ASP.NET Core's JWT bearer authentication and authorisation policies, which I use every day.

X: Java and C# are very similar languages. Both are statically typed, object-oriented, run on a managed runtime with garbage collection, the JVM and the .NET runtime, and have large ecosystems. Someone who knows one well can learn the other quickly.
X: The main differences are these. C# often added language features earlier: properties, LINQ, async and await, which arrived in 2012, records, pattern matching, nullable reference types, and extension methods. Java has caught up in many areas, with lambdas, streams, records and pattern matching, but often later. Generics work differently: C# keeps generic type information at runtime, called reified generics, and supports generics over value types, like List of int, without boxing. Java uses type erasure, so generic types disappear at runtime. C# also has custom value types, structs, and features like Span for high-performance code. For concurrency, C# uses async and await, while Java introduced virtual threads in Java 21, which make blocking code scale well, with a different approach. For ecosystems, Java has many JVM vendors and other JVM languages, like Kotlin, and a huge open-source ecosystem, while .NET is led by Microsoft, with a very consistent set of official libraries and tooling.
X: In practice, both are excellent for backend systems. My strength is C# and .NET, and the concepts I use daily transfer directly to Java.
