X: Node.js runs JavaScript on a single main thread, using an event loop. Understanding synchronous versus asynchronous code is critical because of that.
X: Synchronous code runs line by line and blocks the thread until it finishes. In Node, that's dangerous, because while the main thread is busy, nothing else can happen: no other request is handled, no timer fires, and no response is sent. For example, using readFileSync on a large file inside a request handler, or doing a heavy calculation like hashing a big file, freezes the whole server for every user.
X: Asynchronous code starts an operation, like reading a file, querying a database or calling an API, and lets the main thread continue with other work. Node hands the I/O to the operating system, or to its internal thread pool from libuv, and when the result is ready, a callback is queued, and the event loop runs it. With Promises and async and await, the code still reads top to bottom, but the thread is free while waiting. That's why Node can handle thousands of concurrent connections with one thread, as long as the work is mostly I/O.
X: So my rules in Node are: always use the asynchronous versions of I/O functions, never synchronous ones in request handling. For CPU-heavy work, use worker threads, or move it to a separate service or queue. And monitor event loop delay, because it shows when something is blocking.
X: It's the same principle as async and await in ASP.NET Core: don't block threads while waiting for I/O.

X: Express is the most popular web framework for Node.js. It's minimal and flexible: it gives you routing, middleware and helpers for requests and responses, and you add whatever else you need through packages.
X: Middleware is the core concept of Express. A middleware is a function that receives three things: the request, the response, and a next function. Middleware functions run in the order they're registered, forming a pipeline that every request passes through. Each one can do something with the request, like reading headers or adding data, modify the response, end the request by sending a response, or call next to pass control to the next middleware. If it neither responds nor calls next, the request just hangs.
X: Typical middleware includes parsing JSON bodies with express.json, logging, CORS, security headers with Helmet, authentication that validates a token and attaches the user to the request, and rate limiting. Middleware can be applied globally with app.use, to a path, or to a single route, and routers group related routes with their own middleware.
X: Error-handling middleware is special: it has four parameters, starting with the error. When any middleware or route calls next with an error, or, in Express 5, an async handler throws, Express skips to the error middleware, which can log it and send a consistent error response.
X: It's the same idea as the middleware pipeline in ASP.NET Core, which I use every day.

X: In Node.js, I handle errors at three levels: where they happen, in one central place, and as a last safety net for the whole process.
X: Where they happen: for asynchronous code with async and await, I use try and catch around operations that can fail and that I can do something about, like retrying a call or returning a specific message. For Promises without await, every chain needs a catch. I never leave a Promise rejection unhandled.
X: Central handling: in Express, I add error-handling middleware with four parameters at the end of the pipeline. All errors are passed there, either by calling next with the error, or automatically in Express 5 when an async handler throws. It logs the error with the request details and correlation id, and sends a consistent response, like a problem details JSON with the right status code, without exposing stack traces in production. I use custom error classes, like a NotFoundError or ValidationError, with a status code, so the handler can map them correctly.
X: The safety net: process-level handlers for unhandledRejection and uncaughtException. They log the error and then shut down gracefully, letting the container or process manager restart the service, because after an uncaught exception, the process may be in a broken state.
X: And I validate input early with a schema library like Zod, which turns bad input into clear 400 errors instead of crashes later.

X: I secure Node.js APIs in the same layers as any API, using the tools from the Node ecosystem.
X: First, authentication and authorisation. Every protected route validates a JWT from our identity provider, checking the signature, issuer, audience and expiry, with a library like jose or passport, and then checks the user's roles or permissions, including whether they own the resource they're asking for. X: SFTP is the SSH File Transfer Protocol. It transfers files over an SSH connection, usually on port 22, so both the login and the data are encrypted. It's widely used for exchanging files between companies, like the order and status files we exchange with depot vendors.
X: FTP is the original File Transfer Protocol. It sends everything, including the username and password, in plain text, so anyone on the network could read it. It also uses two connections, a control channel and a separate data channel, which makes firewalls harder to configure. It shouldn't be used for anything sensitive.
X: FTPS is FTP with TLS encryption added, the same encryption used by HTTPS. It's secure, but it's still FTP underneath, with separate control and data connections and ranges of ports, so it's more difficult with firewalls and proxies. It also uses certificates, like HTTPS.
X: SFTP, despite the similar name, isn't FTP at all; it's a completely different protocol built on SSH. It uses a single connection and a single port, which is simple for firewalls, and it supports authentication with SSH keys as well as passwords, plus host key verification.
X: That's why SFTP is the standard choice for secure business file transfers, and it's what our IRT system uses with external vendors. I own the SFTP integration component, which works with three different SFTP libraries behind one interface.
+@p7-35
X: SFTP authentication happens in two directions: first the client checks the server, then the server checks the client.
X: First, host key verification. When the client connects, the server presents its host key. The client compares the key's fingerprint with the one it expects. If they don't match, it could be a man-in-the-middle attack, so the connection must be refused. That's why we pin the expected fingerprint for each vendor in configuration, instead of accepting any key.
X: Then the client authenticates, usually with a password or a private key.
X: With password authentication, the client sends a username and password over the encrypted SSH connection. It's simple, but passwords can be guessed, reused or leaked, and they have to be shared with the other party.
X: With private key authentication, the client has a key pair. The public key is given to the vendor and added to their server, and the private key never leaves our side. When connecting, the server sends a challenge, and the client proves it has the private key by signing it. Nothing secret is sent over the network, it can't be brute-forced in practice, and keys can be revoked individually.
X: So private keys are much more secure, and they're what we prefer with vendors. Some vendors still require passwords, so our component supports both. In either case, the keys and passwords are stored in [an encrypted secrets store], never in code or configuration files.

X: Our SFTP integration supports three libraries, ComponentPro, SSH.NET and Rebex, because different vendors' servers work best with different ones. The key to switching between them was one abstraction.
X: I defined an ISftpClient interface with the operations we need: connect, upload, download, list and delete. Each library has its own implementation of that interface, an adapter that translates our calls into that library's API and its errors into our own exception types. The rest of the code, like the jobs that send order files or collect status files, only uses the interface, and has no idea which library is underneath.
X: A factory decides which implementation to use for each vendor, based on configuration. For example, the configuration for DepotA says Rebex, and another vendor says SSH.NET. When a job runs for a vendor, it asks the factory for a client, and gets the right one. So moving a vendor to a different library is just a configuration change, which still goes through our change control, but needs no code change or deployment.
X: Every implementation passes the same set of contract tests, for things like overwriting files, timeouts and errors, so they really are interchangeable.
X: This design made it safe to introduce Rebex in [2024]: we moved vendors over one at a time, starting with [one low-volume vendor] for [two weeks], and could switch back instantly.
+@p7-37
X: SFTP connections to external vendors fail for many reasons, like network problems, vendor server restarts, or timeouts on slow links, so I built retries and failure handling into the shared base of our SFTP component, so every vendor and library gets the same behaviour.
X: Every operation, like connect, upload or download, is wrapped in a Polly policy, with [3] retries, exponential backoff and jitter. So it waits a little longer before each attempt, with some randomness, to avoid hammering the vendor's server. Each retry uses a fresh connection, because a broken SSH session can't be trusted.
X: Importantly, not every error is retried. Temporary errors, like timeouts, dropped connections or "server busy", are retried. Permanent errors, like a failed login, or a host key that doesn't match, are not retried, because they won't fix themselves, and repeated failed logins could even get our account locked by the vendor. Those fail immediately with a clear message.
X: There are also sensible timeouts on connecting and on each operation, so nothing hangs forever.
X: If all retries fail, the job is marked as failed, the error is logged with the vendor, the file and a correlation id, and an alert goes to our support team. The next scheduled run tries again automatically, and because processing is idempotent, a retried upload or download never causes duplicates.
X: This turned what used to be manual follow-ups into mostly self-healing transfers.
+@p7-38
X: File integrity matters a lot for us, because these files contain shipment orders and status updates for clinical trial medication. I protect against corrupted and partial files on both upload and download.
X: For uploads, the biggest risk is the vendor picking up a file while we're still writing it. So I upload with a temporary name, like a .tmp extension, and only rename it to the final name when the upload is complete. The rename is a quick, atomic operation on the server, so the vendor only ever sees complete files. After uploading, I compare the remote file size with the local size, and where the vendor supports it, we also exchange a SHA-256 checksum, so we can confirm the content is identical.
X: For downloads, I only pick up files that are complete, following the vendor's convention, for example a final name, a matching checksum file, or a marker file. After downloading, I check the size and checksum, and validate the content, like the header, the expected format and the record count in the trailer, before processing anything. If a file fails validation, it's moved to an error folder and an alert is raised, instead of importing bad data.
X: For large files on slow connections, I use longer timeouts and resumable transfers where the library supports it.
X: These checks mean a network problem can delay a file, but never silently corrupt our data.
+@p7-39
X: Duplicate files happen for normal reasons: a vendor resends a file, a retry after a timeout uploads it again, or a file stays on the server and gets picked up twice. Processing the same shipment update twice could cause wrong data, so I made the processing idempotent.
X: First, predictable names. Files follow a naming convention with the vendor, the file type, a timestamp and a sequence number, so each file has a unique, meaningful name.
X: Second, a processed-files table in the database. Before processing a file, we check whether we've already seen it, using the file name and a SHA-256 hash of its content. The hash matters, because the same content might arrive with a different name, or a corrected file might come with the same name. If it's already been processed, we skip it, log it, and move it aside, without importing it again. The record is saved in the same transaction as the import, so a crash can't leave the file half-recorded.
X: Third, after successful processing, the file is moved to an archive folder on the server, so it isn't picked up again in the next run.
X: And finally, the records inside the files are handled idempotently too, using business keys like the shipment id and status, so even if two different files contain the same update, it's only applied once.
X: Together, these mean that resends and retries are completely safe.

X: SFTP credentials give access to our vendors' systems, so I treat them like any other production secret.
X: First, storage. Private keys and passwords are stored [encrypted in a secrets store]. They're never in the code, the repository, configuration files or build pipelines. The service reads them at runtime, under a service account that only has permission to read the specific secrets it needs.
