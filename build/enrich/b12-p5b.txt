@p5-18
Q: A primary key uniquely identifies each row, can't be null, and there's one per table (clustered by default in SQL Server). A foreign key is a column referencing another table's primary or unique key, enforcing referential integrity so you can't have orphan rows.
- Surrogate keys (identity, sequence, GUID) vs natural keys (kit number).
- GUID PKs: use sequential GUIDs (NEWSEQUENTIALID, or Guid.CreateVersion7 in .NET 9) to avoid fragmentation.
- Index foreign key columns; SQL Server doesn't do it automatically.
? Should every FK be indexed? :: Usually, for joins and to avoid locking scans on deletes of the parent.
? What is Guid.CreateVersion7? :: A .NET 9 API creating time-ordered UUIDv7 values, better for index locality.

@p5-19
Q: A unique constraint forbids duplicate values and is backed by a unique index. A table has one primary key but can have many unique keys; the PK can't be null, while a unique key in SQL Server allows one NULL (use a filtered unique index to allow many).
- Unique constraints enforce business rules regardless of app bugs or races.
- Composite unique keys (StudyId, KitNumber).
```sql
CREATE UNIQUE INDEX UX_Users_Email ON dbo.Users(Email) WHERE Email IS NOT NULL;
```
? Why enforce uniqueness in the database too? :: Concurrent requests can both pass an app check.
? Can a FK reference a unique key? :: Yes, not only primary keys.

@p5-20
Q: A composite index covers several columns, such as (StudyId, Status, ShipmentDate). Column order matters: it supports seeks on the leading column(s), so put equality-filtered columns first and range or sort columns after. It can serve queries on StudyId alone or StudyId plus Status, but not Status alone.
- Leftmost prefix rule.
- INCLUDE columns make it covering without widening the key.
- Our shipment fix used exactly (StudyId, Status, ShipmentDate) INCLUDE, cutting reads from [400,000 to 2,000].
? Why equality before range? :: After a range column, later key columns can't be used for seeking.
? Can SQL Server use a skip scan? :: Not generally; it would scan instead.

@p5-21
Q: A filtered index is a non-clustered index with a WHERE clause (e.g. only Pending shipments): smaller, cheaper to maintain and faster for queries on a hot subset. The query predicate must match the filter, and parameterised queries may not use it unless the optimizer can prove the match.
- Great for status columns where few rows are "active".
- Filtered unique indexes allow uniqueness only among non-null or active rows.
- Requires specific SET options (QUOTED_IDENTIFIER, ANSI_NULLS).
? Why might a parameterised query ignore it? :: The plan must be valid for any parameter value, so it can't rely on the filter.
? Fix? :: Use a literal for the filtered value or OPTION (RECOMPILE).

@p5-22
Q: Indexes help because the B-tree lets SQL Server seek rows in logarithmic time instead of scanning, cover queries without lookups, and avoid sorts. They hurt when there are too many: every insert, update and delete must maintain them, they use storage and memory, and unused or duplicate indexes add cost without benefit.
- Check sys.dm_db_index_usage_stats for unused indexes.
- Key lookups on many rows can make a seek slower than a scan.
- Fragmentation matters less on SSDs; statistics freshness matters more.
? How many indexes are too many? :: There's no fixed number; judge by write workload and usage stats.
? What is a key lookup? :: Fetching extra columns from the clustered index for each row found in a non-clustered index.

@p5-23
Q: An execution plan is the optimizer's recipe for a query: operators (seeks, scans, join types, sorts), estimated vs actual row counts and costs. I read the actual plan to find scans, key lookups, bad estimates, spills and implicit conversions, and use Query Store to see plan history and regressions.
- Read right to left, top to bottom; thick arrows mean many rows.
- Warnings: implicit conversion, missing index, tempdb spills.
- Join types: nested loops (small inputs), hash (large unsorted), merge (sorted inputs).
- Query Store can force a known good plan.
? Estimated vs actual plan? :: Estimated shows the plan without running; actual adds real row counts.
? What does a big estimate vs actual gap mean? :: Stale statistics or parameter sniffing; investigate cardinality.

@p5-24
Q: A table scan reads every row of a heap; an index scan reads all or a large range of an index (clustered index scan reads the whole table); an index seek navigates the B-tree directly to matching rows. Seeks are best for selective queries; scans can be fine for large portions of data.
- Non-SARGable predicates (functions on columns, leading wildcards, implicit conversions) force scans.
- Range scans are seeks with a range predicate.
```sql
-- Non-SARGable: WHERE YEAR(ShipmentDate) = 2025
-- SARGable:    WHERE ShipmentDate >= '2025-01-01' AND ShipmentDate < '2026-01-01'
```
? Is a scan always bad? :: No, reading most of a small table is cheaper by scan.
? What is SARGable? :: A predicate that can use an index seek (Search ARGument able).

@p5-25
Q: A cardinality estimate is how many rows the optimizer expects at each plan step; statistics are histograms of column value distributions (up to 200 steps) used to make those estimates. Bad estimates from stale or missing statistics lead to bad plans, like nested loops over millions of rows.
- Auto update statistics triggers after a threshold of changes (dynamic threshold since SQL Server 2016).
- UPDATE STATISTICS ... WITH FULLSCAN for skewed data.
- Table variables historically estimated 1 row (improved with deferred compilation in SQL 2019).
? Why did a plan change overnight in your incident? :: A statistics update caused recompilation with an unrepresentative parameter value.
? What is the cardinality estimator version? :: The model tied to compatibility level; changes can shift plans after upgrades.

@p5-26
Q: UNION removes duplicates, which costs a sort or hash; UNION ALL keeps every row and is faster. Use UNION ALL unless you truly need de-duplication.
- Column count and types must match; names come from the first query.
- ORDER BY applies to the whole result, at the end.
? When is UNION needed? :: When overlapping sources may return the same row and duplicates are wrong.
? UNION vs JOIN? :: UNION stacks rows vertically; JOIN combines columns horizontally.

@p5-27
Q: EXISTS stops at the first match; IN compares against a list or subquery. Modern optimizers often produce the same semi-join plan for both, but NOT IN with NULLs in the subquery returns no rows, so I prefer NOT EXISTS for anti-joins.
- Large IN lists from apps create plan cache bloat; use table-valued parameters or JSON (OPENJSON).
- EF Core 8+ translates Contains on lists using OPENJSON parameters.
```sql
SELECT s.* FROM Sites s WHERE NOT EXISTS (SELECT 1 FROM Shipments sh WHERE sh.SiteId = s.Id);
```
? Why does NOT IN fail with NULL? :: Comparison with NULL is unknown, so the whole predicate isn't true.
? How did EF Core 8 change Contains? :: It sends the list as a JSON parameter, keeping one cached plan.

@p5-28
Q: A CTE is a named query for one statement: not materialised, readable, and supports recursion. A temp table (#t) is materialised in tempdb, can be indexed, has statistics and can be reused across statements in the session. Use CTEs for readability, temp tables for large intermediate results reused or needing indexes.
- Table variables (@t) have limited statistics; good for small sets.
- CTE referenced twice is evaluated twice.
- Recursive CTEs for hierarchies (MAXRECURSION default 100).
? Is a CTE faster than a subquery? :: No, it's the same; it's about readability.
? Temp table vs table variable? :: Temp tables have statistics and are better for larger data.

@p5-29
Q: ROW_NUMBER gives a unique sequence even for ties; RANK gives ties the same rank and leaves gaps (1,1,3); DENSE_RANK gives ties the same rank without gaps (1,1,2). All need OVER (ORDER BY ...), optionally PARTITION BY.
- Deterministic ROW_NUMBER needs a unique ORDER BY (add a tie-breaker).
- NTILE splits into buckets; LAG/LEAD access neighbouring rows.
```sql
SELECT SiteId, KitCount,
  ROW_NUMBER() OVER (ORDER BY KitCount DESC) rn,
  RANK()       OVER (ORDER BY KitCount DESC) rnk,
  DENSE_RANK() OVER (ORDER BY KitCount DESC) drnk
FROM SiteStock;
```
? Which for nth-highest distinct value? :: DENSE_RANK.
? Can you filter on a window function in WHERE? :: No, wrap it in a CTE or subquery first.

@p5-30
Q: Group and count: SELECT KitNumber, COUNT(*) FROM Kits GROUP BY KitNumber HAVING COUNT(*) > 1. To see or delete the duplicate rows themselves, use ROW_NUMBER() OVER (PARTITION BY KitNumber ORDER BY Id) and keep rn = 1.
- Delete duplicates via a CTE where rn > 1, then add a unique constraint to prevent recurrence.
```sql
WITH d AS (SELECT *, ROW_NUMBER() OVER (PARTITION BY StudyId, KitNumber ORDER BY Id) rn FROM Kits)
DELETE FROM d WHERE rn > 1;
```
? Why can you delete from a CTE? :: SQL Server allows DML through a CTE over a single base table.
? What prevents new duplicates? :: A unique constraint or index.

@p5-31
Q: SELECT DISTINCT Salary FROM Emp ORDER BY Salary DESC OFFSET N-1 ROWS FETCH NEXT 1 ROWS ONLY; or DENSE_RANK() OVER (ORDER BY Salary DESC) in a CTE and filter on rank = N, which handles ties correctly.
- The classic MAX with subquery works for second highest only.
- Return NULL when there's no nth value if required.
```sql
WITH r AS (SELECT Salary, DENSE_RANK() OVER (ORDER BY Salary DESC) dr FROM Emp)
SELECT DISTINCT Salary FROM r WHERE dr = @N;
```
? Why DENSE_RANK not ROW_NUMBER? :: Ties would otherwise count as separate positions.
? Per department? :: Add PARTITION BY DepartmentId.

@p5-32
Q: Use ROW_NUMBER with PARTITION BY: WITH r AS (SELECT *, ROW_NUMBER() OVER (PARTITION BY SiteId ORDER BY ShipDate DESC) rn FROM Shipments) SELECT * FROM r WHERE rn <= 3. CROSS APPLY with TOP is an alternative that can be faster with a good index.
- Index (SiteId, ShipDate DESC) supports both.
```sql
SELECT s.Id, x.* FROM Sites s
CROSS APPLY (SELECT TOP (3) Id, ShipDate FROM Shipments sh WHERE sh.SiteId = s.Id ORDER BY ShipDate DESC) x;
```
? When is CROSS APPLY better? :: When there are few groups and an index allows a seek per group.
? Ties? :: Use RANK or DENSE_RANK if ties should all be included.

@p5-33
Q: A dirty read reads uncommitted data that may be rolled back; a non-repeatable read gets different values for the same row within a transaction because another transaction updated it; a phantom read finds new rows on re-running a range query because another transaction inserted them.
- Read Uncommitted (NOLOCK) allows dirty reads; Read Committed prevents them; Repeatable Read prevents non-repeatable reads; Serializable prevents phantoms; Snapshot gives a consistent versioned view.
- NOLOCK can also skip or double-read rows, not just read dirty data.
? Why avoid NOLOCK? :: It can return wrong results, including missing or duplicated rows.
? Which isolation does RCSI give? :: Read Committed using row versions, so readers don't block writers.

@p5-34
Q: ACID: Atomicity (all or nothing), Consistency (rules and constraints hold after each transaction), Isolation (concurrent transactions don't interfere beyond the isolation level) and Durability (committed data survives crashes, via the transaction log).
- Write-ahead logging gives durability and rollback.
- Distributed systems trade some ACID across services (sagas, eventual consistency).
? How does SQL Server guarantee durability? :: Log records are hardened to disk before commit returns.
? ACID vs BASE? :: BASE (Basically Available, Soft state, Eventually consistent) describes many NoSQL systems.

@p5-35
Q: Optimistic locking takes no locks; it detects conflicts at write time with a rowversion and fails the second writer, best for low contention (EF Core concurrency tokens). Pessimistic locking locks the row while working (SELECT ... WITH (UPDLOCK)), best for high contention like allocating the next randomization slot.
- EF Core throws DbUpdateConcurrencyException; reload and retry or show a conflict.
- APIs expose the version as an ETag with If-Match.
```csharp
public class Shipment { public int Id { get; set; } [Timestamp] public byte[] RowVersion { get; set; } = []; }
```
? What does EF do with [Timestamp]? :: Adds the version to the UPDATE WHERE clause and checks rows affected.
? Risk of pessimistic locking? :: Blocking and deadlocks if transactions are long.

@p5-36
Q: Measure first (Query Store, wait stats, slow query logs), then fix the top queries (indexes, SARGable predicates, less data fetched, better joins), keep statistics fresh, shorten transactions, consider RCSI, cache hot reads, and scale hardware only after.
- Wait stats tell where time goes (PAGEIOLATCH = I/O, LCK = blocking, CXPACKET = parallelism).
- Batch and set-based operations instead of row by row.
- Archive old data, partition very large tables.
? What do you check first? :: Top queries by total CPU and duration in Query Store.
? When would you partition? :: Very large tables where sliding windows or maintenance per partition help.

@p5-37
Q: Start from real query patterns. The clustered key should be narrow, unique, static and ever-increasing; add non-clustered indexes on foreign keys and frequent filters with equality columns first, INCLUDE columns to cover hot queries, filtered indexes for hot subsets, and remove unused or duplicate indexes. Verify with execution plans.
- Avoid wide clustered keys: they're copied into every non-clustered index.
- Consider write cost on busy tables.
- Review missing index DMVs critically; they often over-suggest.
? Why ever-increasing clustered keys? :: Inserts go to the end, reducing page splits and fragmentation.
? Are missing index suggestions reliable? :: They're hints; combine and validate them.

@p5-38

@p5-42
