### sqlx | Stored procedure vs function in SQL Server: what is the difference? | stored procedure vs function, sql function vs procedure, udf vs stored procedure, table valued function
Both are reusable database code, but they have different rules and uses.

Stored procedures are executed with EXEC. They can contain almost any T-SQL: INSERT, UPDATE and DELETE, transactions, TRY/CATCH, temp tables, dynamic SQL, and calls to other procedures. They can return multiple result sets, output parameters and a return code. They can't be used inside a SELECT statement. They're used for business operations, data changes and batch processes.

Functions return a value and can be used inside queries, like in SELECT, WHERE or JOIN. They're not allowed to change database state: no INSERT, UPDATE or DELETE on real tables, no transactions, no dynamic SQL, and limited error handling.

Types of functions: scalar functions return a single value; inline table-valued functions are a single SELECT statement and behave like a parameterised view, which the optimiser expands into the main query, so they perform well; multi-statement table-valued functions build a table variable in several steps, and historically had poor cardinality estimates, so they often performed badly.

Performance notes: scalar functions used per row in large queries were notoriously slow, though SQL Server 2019 can inline many of them automatically. Inline table-valued functions are usually the best choice when you need reusable query logic.

My rule of thumb: procedures for operations and data changes; inline table-valued functions for reusable filters or calculations inside queries; avoid scalar and multi-statement functions in hot queries. From .NET, procedures are easy to call with EF Core or Dapper, and functions can be mapped too.

### sqlx | How do PIVOT and UNPIVOT work in SQL Server? | pivot sql server, unpivot, rows to columns sql, crosstab query, conditional aggregation
PIVOT turns rows into columns. For example, a table has rows of site, month and shipment count, and the report wants one row per site with a column for each month. PIVOT aggregates the value, like SUM(ShipmentCount), for each listed column value, like Jan, Feb and Mar.

The syntax: select from a source subquery of site, month and count, then PIVOT with SUM of ShipmentCount FOR Month IN the list of month columns, each written as a quoted identifier.

The limitation: the column list must be known when writing the query. If columns depend on data, like a variable list of studies or visit types, you need dynamic SQL to build the column list, and that must be done safely, with QUOTENAME for column names.

Conditional aggregation is an alternative I often prefer: SELECT Site, SUM(CASE WHEN Month = 'Jan' THEN ShipmentCount END) AS Jan, ... GROUP BY Site. It's more flexible, works across databases, can mix different aggregations, and is easier to read for many developers.

UNPIVOT does the opposite: columns into rows, like turning Jan, Feb and Mar columns into rows of month and value. CROSS APPLY with a VALUES list is a more flexible alternative, and it handles NULLs the way you choose, while UNPIVOT drops them.

In practice, I'm careful about doing pivoting in SQL for reports at all: often it's simpler to return normalised rows and let the reporting tool or front end pivot them, which keeps queries stable when new columns appear.

### sqlx | What are CROSS APPLY and OUTER APPLY, and when do you use them? | cross apply, outer apply, apply operator sql server, lateral join, top n per row
APPLY lets you run a table expression for each row of the outer table, where the inner expression can reference columns from the outer row. It's similar to a lateral join in other databases.

CROSS APPLY returns only outer rows for which the inner expression returns rows, like an inner join. OUTER APPLY returns all outer rows, with NULLs when the inner expression returns nothing, like a left join.

Common uses.

Top N per row: for each site, get its latest 3 shipments: SELECT s.Name, x.* FROM Sites s CROSS APPLY (SELECT TOP 3 * FROM Shipments sh WHERE sh.SiteId = s.Id ORDER BY ShippedAt DESC) x. With a good index on SiteId and ShippedAt, this is very efficient.

Calling table-valued functions per row, passing columns from the outer row as parameters.

Splitting or parsing values: CROSS APPLY STRING_SPLIT(row.Tags, ',') to expand a delimited column into rows, or OPENJSON to shred JSON stored in a column.

Computing reusable expressions: CROSS APPLY (SELECT Total = Qty * Price) calc, then using calc.Total in SELECT, WHERE and ORDER BY without repeating the expression.

Unpivoting columns into rows with CROSS APPLY (VALUES ...).

Performance: APPLY with a correlated subquery runs effectively per row, so it's great when the outer set is small and the inner query uses an index seek; for large outer sets, a window function approach, like ROW_NUMBER partitioned by site, may be better. I check the execution plan to decide.

### sqlx | How do LAG and LEAD work, and how do you calculate running totals in SQL? | lag lead sql, running total sql, cumulative sum, window function over, previous row value sql
LAG and LEAD are window functions that read a value from a previous or following row in a defined order, without a self-join.

LAG(Quantity, 1, 0) OVER (PARTITION BY SiteId ORDER BY ShippedAt) gives the previous shipment's quantity for the same site, or 0 if there's none. LEAD does the same for the next row. Uses: comparing each value to the previous one, like stock change since last count; finding time between events, like days between visits; and detecting status changes.

Running totals use an aggregate with an OVER clause: SUM(Quantity) OVER (PARTITION BY SiteId ORDER BY ShippedAt ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) gives a cumulative quantity per site over time.

Important detail: always specify ROWS for running totals. Without a frame, the default with ORDER BY is RANGE UNBOUNDED PRECEDING, which treats rows with the same order value as peers, giving surprising totals when there are ties, and it's slower because it may use an on-disk worktable. ROWS is precise and faster.

Moving averages work the same way with a limited frame, like ROWS BETWEEN 6 PRECEDING AND CURRENT ROW for a 7-day average.

Other useful window functions: FIRST_VALUE and LAST_VALUE, NTILE for buckets, and PERCENT_RANK.

Performance: an index matching the PARTITION BY and ORDER BY columns lets SQL Server compute these without sorting. These functions replaced many old cursor-based or self-join solutions for reports, and they're usually much faster.

### sqlx | How do you query a hierarchy with a recursive CTE? | recursive cte, hierarchical query sql, parent child query, org chart sql, tree query sql server
Hierarchical data, like an organisation chart, a folder tree, a bill of materials, or regions containing countries containing sites, is often stored as a parent-child table, where each row has a ParentId.

A recursive CTE walks the tree. It has two parts joined with UNION ALL: the anchor member selects the starting rows, like the root node, or a specific node; the recursive member joins the table to the CTE itself, to find children of the rows found so far. SQL Server repeats the recursive part until no new rows are found.

Example: WITH Tree AS (SELECT Id, ParentId, Name, 0 AS Level FROM Locations WHERE Id = @rootId UNION ALL SELECT l.Id, l.ParentId, l.Name, t.Level + 1 FROM Locations l JOIN Tree t ON l.ParentId = t.Id) SELECT * FROM Tree.

You can also build a path string to sort and display the tree, and walk upwards from a node to find all its ancestors.

Safety: MAXRECURSION defaults to 100 levels; if the data has a cycle by mistake, the query errors out rather than looping forever. Adjust with OPTION (MAXRECURSION n) if needed, and detect cycles by checking whether an id already appears in the path.

Performance: index ParentId. For large, frequently queried trees, alternatives include the hierarchyid data type, closure tables that store all ancestor-descendant pairs, or a materialised path column, which make subtree queries fast at the cost of more work on updates.

In EF Core, recursive CTEs are written as raw SQL or a view, since LINQ doesn't express recursion directly.

### sqlx | What is the gaps and islands problem in SQL? | gaps and islands, consecutive rows sql, find gaps in sequence, group consecutive dates, streaks sql
Gaps and islands is a classic SQL pattern. Islands are runs of consecutive values, like consecutive days a temperature sensor was out of range, or continuous periods a site was active. Gaps are the missing ranges, like missing ids in a sequence or days with no data.

Finding gaps: use LEAD to compare each value with the next one. SELECT Id + 1 AS GapStart, NextId - 1 AS GapEnd FROM (SELECT Id, LEAD(Id) OVER (ORDER BY Id) AS NextId FROM T) x WHERE NextId - Id > 1.

Finding islands: the trick is the difference between the value and a row number. For dates, compute DATEADD(day, -ROW_NUMBER() OVER (PARTITION BY SensorId ORDER BY ReadingDate), ReadingDate). For consecutive dates, this difference stays the same; when there's a gap, it changes. Then GROUP BY sensor and that group key, and take MIN and MAX dates to get each island's start and end, and COUNT for its length.

For status changes, like periods when a depot was in each state, compare each row's status with the previous one using LAG, mark a change with 1, take a running SUM of those flags to create a group number, and aggregate by group.

Real uses: temperature excursion periods for shipments, continuous enrolment periods, consecutive missed visits, finding missing sequence numbers in imported files, and outage windows from monitoring data.

These set-based solutions replace cursor loops and are much faster on large data, especially with an index on the partition and order columns.

### sqlx | What regular database maintenance should be set up for SQL Server? | sql server maintenance, maintenance plan, dbcc checkdb, update statistics job, backup and index maintenance
On-premise SQL Server doesn't look after itself; a few regular jobs keep it healthy, usually scheduled with SQL Server Agent, often using a well-known maintenance script solution rather than basic maintenance plans.

Backups: full backups, for example weekly or daily; differential backups in between; and transaction log backups every few minutes in the full recovery model, which also keep the log from growing endlessly. Backups go to separate storage, are checked with RESTORE VERIFYONLY or CHECKSUM, and, most importantly, restores are tested regularly.

Integrity checks: DBCC CHECKDB regularly, to detect corruption early, while good backups still exist. For large databases, run it on a restored copy or split it across days.

Monitoring: alerts for failed jobs, low disk space, long-running jobs, blocking, and high severity errors.

With many databases, like one per study, the jobs must loop through all databases, scale well, and be staggered so they don't all run at the same time and overload storage.

### sqlx | How do you implement a reliable queue table in SQL Server? | queue table sql server, readpast updlock, database as queue, dequeue sql, outbox processing locking
Sometimes a table is used as a work queue, like an outbox table or a list of jobs, with several workers taking items. The challenge is letting multiple workers dequeue concurrently without processing the same item twice and without blocking each other.

The standard pattern uses locking hints: WITH (ROWLOCK, UPDLOCK, READPAST). UPDLOCK takes an update lock on rows being read, so two workers can't grab the same row; READPAST skips rows already locked by other workers, instead of waiting for them; ROWLOCK keeps locks fine-grained.

A dequeue in one statement: WITH next AS (SELECT TOP (10) * FROM WorkQueue WITH (ROWLOCK, UPDLOCK, READPAST) WHERE Status = 'Pending' ORDER BY Id) UPDATE next SET Status = 'Processing', LockedBy = @worker, LockedAt = SYSUTCDATETIME() OUTPUT inserted.*. Or delete the rows with OUTPUT if processing is idempotent and failures are handled elsewhere.

Other essentials: an index on Status and Id, or a filtered index for pending rows, so the query doesn't scan; a timeout for stuck items, where items in Processing for too long are reset to Pending, because a worker might crash; an attempt counter, moving items to a failed state after several attempts, like a dead-letter queue; and handlers that are idempotent, because an item may be processed again after a timeout.

When not to use it: very high throughput or many consumers, where a real message broker like RabbitMQ is better. But for outbox tables and moderate job volumes, a queue table keeps work transactional with business data, which is a big advantage.

### sqlx | What is the logical processing order of a SQL query? | logical query processing order, sql order of execution, why can't use alias in where, select execution order
SQL is written in one order but logically processed in another, and knowing that order explains many common errors.

The logical order is: FROM, including JOINs and APPLY; then WHERE; then GROUP BY; then HAVING; then SELECT, where expressions and aliases are computed, along with window functions; then DISTINCT; then ORDER BY; then TOP, or OFFSET and FETCH.

What this explains.

You can't use a column alias from SELECT in WHERE, because WHERE is processed before SELECT. You can use it in ORDER BY, which comes after SELECT.

You can't use aggregates in WHERE; filtering on aggregates belongs in HAVING, after grouping.

Window functions like ROW_NUMBER can't appear in WHERE, because they're computed in the SELECT phase; you wrap the query in a CTE or subquery and filter outside.

With an outer join, a filter in the ON clause behaves differently from the same filter in WHERE: in ON, it decides which rows match, keeping unmatched outer rows; in WHERE, it removes rows after the join, which can effectively turn a left join into an inner join.

TOP without ORDER BY gives arbitrary rows, since ordering is only guaranteed by ORDER BY.

This is the logical order, not the physical execution order. The optimiser can reorder operations, like pushing filters down or choosing join orders, as long as the result is the same. But for reasoning about what a query means, the logical order is the right model.

### sqlx | Which SQL Server date column type should you use: datetime, datetime2 or datetimeoffset? | datetime vs datetime2, datetimeoffset sql, sql server date types, store dates utc sql, date column type
SQL Server has several date and time types, and the choice affects precision, storage and time zone handling.

datetime: the old type, range from 1753, precision about 3 milliseconds, rounded to .000, .003 or .007, using 8 bytes. Its rounding can cause surprising comparisons. I don't use it for new columns.

datetime2: range from year 1, configurable precision up to 100 nanoseconds, and 6 to 8 bytes. It's the recommended type for date and time without an offset. EF Core maps DateTime to datetime2 by default.

datetimeoffset: datetime2 plus a time zone offset, like +05:30, using 10 bytes. It records the moment and the offset it was captured in. It maps to DateTimeOffset in .NET.

date: just the date, 3 bytes, for things like date of birth or a visit date with no time. Maps to DateOnly in newer .NET.

time: just the time of day.

How I choose.

Timestamps for events, like created, updated or shipped times: either datetime2 holding UTC, with a clear naming convention like CreatedAtUtc, or datetimeoffset if the original local offset matters, like when and where a user performed an action.

Business dates without time: date, to avoid off-by-one-day issues caused by time zone conversions.

Comparisons: be consistent, because mixing types causes implicit conversions that can prevent index use.

Also avoid GETDATE(), which returns server local time; use SYSUTCDATETIME() or SYSDATETIMEOFFSET() so values don't depend on the server's time zone setting.

### sqlx | What are computed columns, and when should they be persisted or indexed? | computed column sql server, persisted computed column, index computed column, derived column sql
A computed column is defined by an expression based on other columns in the same row, like FullName AS FirstName + ' ' + LastName, or LineTotal AS Quantity * UnitPrice, or extracting a value from JSON, like JSON_VALUE(Payload, '$.status').

By default, it's virtual: not stored, calculated whenever it's read. That keeps storage small but costs CPU on each read.

PERSISTED stores the computed value physically, updated automatically when the source columns change. Reads are faster, writes slightly slower. The expression must be deterministic, meaning it always returns the same result for the same inputs; functions like GETDATE() aren't allowed.

Indexing: you can create an index on a computed column, persisted or not, if it's deterministic and precise. This is very useful for making queries SARGable: if queries filter on an expression, like WHERE YEAR(ShippedAt) = 2025, or a JSON property, a computed column with an index lets the optimiser seek instead of scanning. SQL Server can even match the expression in the query to the indexed computed column automatically.

Uses I find practical: indexing JSON properties stored in a JSON column; normalised search keys, like upper-cased or trimmed codes; derived values used in filters or sorting; and keeping calculated values consistent without application code.

Cautions: certain SET options must be correct for indexes on computed columns, which can affect older applications or connections; and complex expressions with scalar user-defined functions can hurt performance and prevent parallelism.

In EF Core, HasComputedColumnSql maps them, and the values are read back after saves.

### sqlx | How do you enforce data integrity with constraints in SQL Server? | check constraint, default constraint, data integrity constraints, not null unique foreign key, database constraints vs application validation
Constraints make the database itself reject invalid data, no matter which application, script or person writes it. Application validation is important, but it can be bypassed by bugs, other services or manual fixes.

NOT NULL: required columns. Simple and very effective.

### sqlx | What are the high availability and disaster recovery options for on-premise SQL Server? | always on availability groups, failover cluster instance, log shipping, sql server high availability, sql server disaster recovery
For on-premise SQL Server, there are a few main options, often combined.

Always On availability groups: a group of databases is replicated from a primary replica to secondary replicas on other servers. Synchronous commit replicas, usually in the same data centre, give zero data loss and automatic failover; asynchronous replicas, often in another data centre, give disaster recovery with a small potential data loss. Secondaries can be readable, used for reports and backups. Applications connect through a listener name, so failover is transparent apart from a brief interruption. Note that only databases are replicated; logins, jobs and linked servers must be synchronised separately.

Failover cluster instances: the whole SQL Server instance fails over to another node, using shared storage. Protects against server failure, including instance-level objects, but the shared storage is a single point of failure, so it's often combined with something else for DR.

Log shipping: transaction log backups are copied and restored on a standby server on a schedule. Simple and reliable for DR, with data loss equal to the shipping interval and manual failover.

Backups to offsite storage: always needed, because replication also replicates mistakes, like accidental deletes.

Choosing depends on RPO and RTO targets, budget and licensing.

Application side: use the listener, set MultiSubnetFailover=True in connection strings, add retry logic for transient errors during failover, and practise failovers regularly. With many databases, like one per study, availability groups need planning for the number of databases per group and the synchronisation load.

### sqlx | How does EF Core map inheritance: TPH, TPT and TPC? | ef core inheritance, tph vs tpt vs tpc, table per hierarchy, table per type, discriminator column
When you have a class hierarchy, like a base Notification with EmailNotification and SmsNotification, EF Core can map it to tables in three ways.

TPH, table per hierarchy, is the default: one table holds all types, with a discriminator column saying which type each row is, and columns for all properties of all types, which are nullable for types that don't use them. Queries are fast, with no joins, and polymorphic queries are simple. Downsides: many nullable columns, you can't enforce NOT NULL for subtype-specific columns at database level, and a wide table if there are many subtypes.

TPT, table per type: a table for the base type, and a table for each derived type with its specific columns, linked by the primary key. The schema is clean and normalised, but every query for derived types needs joins, and polymorphic queries join all tables, which gets slow with many types.

Queries for one specific type are fast with no joins; polymorphic queries use UNION ALL across tables. Keys must be unique across all tables, so you need sequences or GUIDs instead of identity columns per table.

My default is TPH for small hierarchies with few differing properties, because it performs best. TPC fits when you mostly query specific types. I'd avoid TPT for performance-sensitive paths.

Often, the best option is to avoid inheritance in the data model and use composition or a type column with a JSON column for type-specific details.

### sqlx | What is a heap table, and why is a table without a clustered key usually a problem? | heap table sql server, table without clustered index, forwarded records, rid lookup, when to use heap
A heap is a table without a clustered index. Rows are stored in no particular order, on whatever pages have space, and nonclustered indexes point to rows using a physical row identifier, the RID, made of file, page and slot.

Problems with heaps.

Forwarded records: when a row is updated and grows, like a varchar column getting longer, and no longer fits on its page, SQL Server moves it to another page and leaves a forwarding pointer behind. Reads then follow extra pointers, causing more I/O. Over time, heavy updates make heaps slower.

Space isn't reclaimed well after deletes, unless the table is rebuilt or deletes take table locks, so heaps can grow with empty pages.

Lookups from nonclustered indexes use RID lookups, and range queries on any order require sorts or scans.

Why clustered indexes are the default: rows are stored in key order, range scans on the key are efficient, there are no forwarded records, and space management is better. A narrow, unique, ever-increasing key, like an identity or sequential value, makes a good clustered key.

When a heap can be fine: staging tables used for fast bulk loads that are read once and truncated, where insert speed matters and data is read fully anyway; or temporary tables.

How I find heaps: query sys.indexes for index_id 0, and check sys.dm_db_index_physical_stats for forwarded record counts. In older databases, finding large, frequently updated heaps and adding a clustered index can give a noticeable performance improvement.

### sqlx | What are the risks of cross-database queries and linked servers? | cross database query, linked server sql server, three part names, four part names, distributed query risks
In SQL Server, you can query another database on the same instance with three-part names, like OtherDb.dbo.Table, and another server with linked servers and four-part names, or OPENQUERY. Schema changes on large, busy tables can lock the table for a long time, blocking users. The trick is knowing which operations are cheap and splitting risky ones into safe steps.

Adding a nullable column: metadata-only in SQL Server, instant regardless of table size.

Adding a NOT NULL column with a default: since SQL Server 2012 Enterprise Edition, this is also metadata-only for runtime constant defaults; older or lower editions may rewrite every row, which is slow and locks the table.

Changing a column's type, or making a column NOT NULL: may scan or rewrite the table. Safer approach: add a new column, backfill it in small batches during quiet times, switch the application to use it, then drop the old column later.

Creating indexes: use ONLINE = ON where the edition allows, and RESUMABLE in newer versions, so it can be paused and continued; otherwise schedule during maintenance windows.

Adding foreign keys or check constraints: WITH NOCHECK first to avoid a long validation, then validate later at a quiet time, so they become trusted.

Use a low lock timeout, like SET LOCK_TIMEOUT, or WAIT_AT_LOW_PRIORITY for online operations, so a schema change waiting for a lock doesn't block everyone queued behind it.

Expand and contract: deploy the schema change first in a backward-compatible way, release code that works with both shapes, then remove the old structure in a later release.

Test on a production-sized copy, measuring duration and lock behaviour, because something instant on a small test database can take an hour in production.
