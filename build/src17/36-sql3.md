### sqlx | Stored procedure vs function in SQL Server: what is the difference? | stored procedure vs function, sql function vs procedure, udf vs stored procedure, table valued function
Okay, both are reusable database code, but the rules and the uses are different.

Stored procedures run with EXEC. They can hold almost any T-SQL, inserts, updates, deletes, transactions, try-catch, temp tables, dynamic SQL, calls to other procedures. They can return multiple result sets, output parameters and a return code. But you can't use them inside a SELECT. So they're for business operations, data changes and batch processes.

Functions return a value and you can use them inside queries, in the SELECT, the WHERE, a JOIN. But they're not allowed to change database state. No inserts, updates or deletes on real tables, no transactions, no dynamic SQL, limited error handling.

Functions come in three flavours. Scalar functions return one value. Inline table-valued functions are a single SELECT and behave like a parameterised view, the optimiser expands them into the main query, so they perform well. Multi-statement table-valued functions build a table variable in several steps, and historically they had bad cardinality estimates, so they often performed badly.

On performance, scalar functions called per row in big queries were famously slow, though SQL Server 2019 can inline a lot of them automatically now. Inline table-valued functions are usually the best choice when you need reusable query logic.

My rule of thumb is procedures for operations and data changes, inline table-valued functions for reusable filters or calculations inside queries, and keep scalar and multi-statement functions out of hot queries. From .NET, procedures are easy to call with EF Core or Dapper, and functions can be mapped too.

### sqlx | How do PIVOT and UNPIVOT work in SQL Server? | pivot sql server, unpivot, rows to columns sql, crosstab query, conditional aggregation
So PIVOT turns rows into columns. Say a table has rows of site, month and shipment count, and the report wants one row per site with a column per month. PIVOT aggregates the value, like the sum of shipment count, for each listed column value, January, February, March.

The syntax is you select from a source subquery of site, month and count, then PIVOT with the sum of shipment count, for month, in the list of month columns, each written as a quoted identifier.

In practice I'm a bit careful about pivoting in SQL for reports at all. It's often simpler to return normalised rows and let the reporting tool or the front end pivot them. The queries stay stable when new columns show up.

### sqlx | How do LAG and LEAD work, and how do you calculate running totals in SQL? | lag lead sql, running total sql, cumulative sum, window function over, previous row value sql
Actually these are window functions that read a value from a previous or next row in a defined order, without needing a self-join.

LAG of quantity, one row back, default zero, over a partition by site ordered by shipped date, gives you the previous shipment's quantity for the same site, or zero if there isn't one. LEAD does the same for the next row. ### sqlx | How do you query a hierarchy with a recursive CTE? | recursive cte, hierarchical query sql, parent child query, org chart sql, tree query sql server
Honestly recursive CTEs look scary but they're quite logical. Hierarchical data, an org chart, a folder tree, a bill of materials, regions containing countries containing sites, is often stored as a parent-child table where each row has a ParentId.

A recursive CTE walks the tree. It has two parts joined with UNION ALL. The anchor part selects the starting rows, the root, or a specific node. In EF Core, recursive CTEs go in raw SQL or a view, since LINQ can't express recursion directly.

### sqlx | What is the gaps and islands problem in SQL? | gaps and islands, consecutive rows sql, find gaps in sequence, group consecutive dates, streaks sql
Yeah, gaps and islands is a classic SQL pattern. Islands are runs of consecutive values, like consecutive days a temperature sensor was out of range, or continuous periods a site was active. Gaps are the missing ranges, missing ids in a sequence, days with no data.

To find gaps, use LEAD to compare each value with the next one. In a subquery you get each id and the next id, and then you keep rows where the next id minus the current one is more than one. The gap starts at id plus one and ends at next id minus one.

Finding islands is the clever bit. The trick is the difference between the value and a row number. For dates, you subtract the row number, partitioned by sensor and ordered by date, as days from the reading date. For consecutive dates that difference stays the same, and when there's a gap it changes. Then group by sensor and that group key, and take the min and max dates for each island's start and end, and the count for its length.

For status changes, like periods a depot was in each state, compare each row's status with the previous one using LAG, mark a change with a one, take a running sum of those flags to get a group number, and aggregate by group.

Real uses I've seen, temperature excursion periods for shipments, continuous enrolment periods, consecutive missed visits, finding missing sequence numbers in imported files, and outage windows from monitoring data.

These set-based solutions replace cursor loops and they're much faster on big data, especially with an index on the partition and order columns.

### sqlx | How do you implement a reliable queue table in SQL Server? | queue table sql server, readpast updlock, database as queue, dequeue sql, outbox processing locking
Okay, sometimes a table is used as a work queue, like an outbox table or a list of jobs, with several workers taking items. The challenge is letting multiple workers dequeue at the same time without processing the same item twice and without blocking each other.

The standard pattern uses three locking hints, ROWLOCK, UPDLOCK and READPAST. UPDLOCK takes an update lock on the rows being read, so two workers can't grab the same row. READPAST skips rows another worker has already locked instead of waiting. ROWLOCK keeps the locks fine-grained.

You can dequeue in one statement. A CTE selects the top ten pending rows with those hints, ordered by id, and then you update that CTE, setting status to Processing, locked-by to the worker and locked-at to the current UTC time, and use OUTPUT to return the claimed rows. Or you delete them with OUTPUT if processing is idempotent and failures are handled somewhere else.

The other essentials. An index on status and id, or a filtered index on pending rows, so the query doesn't scan. A timeout for stuck items, so anything in Processing too long goes back to Pending, because a worker might crash. An attempt counter that moves items to a failed state after a few tries, basically a dead-letter queue. And idempotent handlers, since an item can get processed again after a timeout.

When not to use it, very high throughput or lots of consumers, where a real broker like RabbitMQ is better. But for outbox tables and moderate job volumes, I'd say a queue table is great because the work stays transactional with the business data.

### sqlx | What is the logical processing order of a SQL query? | logical query processing order, sql order of execution, why can't use alias in where, select execution order
Right, SQL is written in one order but processed logically in another, and knowing that order explains a lot of common errors.

The logical order is FROM, including joins and APPLY, then WHERE, then GROUP BY, then HAVING, then SELECT, where expressions, aliases and window functions get computed, then DISTINCT, then ORDER BY, then TOP, or OFFSET and FETCH.

What that explains. You can't use a column alias from the SELECT in the WHERE, because WHERE runs before SELECT. But you can use it in ORDER BY, which comes after.

You can't use aggregates in WHERE. Filtering on aggregates goes in HAVING, after grouping.

Window functions like ROW_NUMBER can't go in WHERE either, because they're computed in the SELECT phase. So you wrap the query in a CTE or subquery and filter outside. I've seen that question come up a lot.

With an outer join, a filter in the ON clause behaves differently from the same filter in WHERE. In ON, it decides which rows match, and unmatched outer rows are kept. In WHERE, it removes rows after the join, which can quietly turn a left join into an inner join. That one bites people in reports.

TOP without ORDER BY gives you arbitrary rows, because order is only guaranteed by ORDER BY.

And this is the logical order, not the physical execution order. The optimiser can reorder things, push filters down, choose join orders, as long as the result is the same. But for reasoning about what a query means, the logical order is the right mental model.

### sqlx | Which SQL Server date column type should you use: datetime, datetime2 or datetimeoffset? | datetime vs datetime2, datetimeoffset sql, sql server date types, store dates utc sql, date column type
So SQL Server has several date and time types, and the choice affects precision, storage and time zone handling.

datetime is the old one. Range from 1753, precision about three milliseconds, it rounds to point zero zero zero, zero zero three or zero zero seven, and uses 8 bytes. That rounding can cause surprising comparisons, so I don't use it for new columns.

datetime2 has a range from year 1, configurable precision down to 100 nanoseconds, and 6 to 8 bytes. It's the recommended type for date and time without an offset, and EF Core maps DateTime to it by default.

Business dates without a time, use date. That avoids the off-by-one-day issues you get from time zone conversions.

Be consistent in comparisons, because mixing types causes implicit conversions that can stop index use.

And avoid GETDATE, which returns server local time. Use SYSUTCDATETIME or SYSDATETIMEOFFSET so values don't depend on the server's time zone. I've seen that cause real bugs between servers in different regions.

### sqlx | What are the high availability and disaster recovery options for on-premise SQL Server? | always on availability groups, failover cluster instance, log shipping, sql server high availability, sql server disaster recovery
For on-premise SQL Server, there are a few main options, often combined.

Always On availability groups: a group of databases is replicated from a primary replica to secondary replicas on other servers. Synchronous commit replicas, usually in the same data centre, give zero data loss and automatic failover; asynchronous replicas, often in another data centre, give disaster recovery with a small potential data loss. Secondaries can be readable, used for reports and backups. Applications connect through a listener name, so failover is transparent apart from a brief interruption. Note that only databases are replicated; logins, jobs and linked servers must be synchronised separately.

Failover cluster instances: the whole SQL Server instance fails over to another node, using shared storage. Protects against server failure, including instance-level objects, but the shared storage is a single point of failure, so it's often combined with something else for DR.

Log shipping: transaction log backups are copied and restored on a standby server on a schedule. Simple and reliable for DR, with data loss equal to the shipping interval and manual failover.

Backups to offsite storage: always needed, because replication also replicates mistakes, like accidental deletes.

Choosing depends on RPO and RTO targets, budget and licensing.

Application side: use the listener, set MultiSubnetFailover=True in connection strings, add retry logic for transient errors during failover, and practise failovers regularly. ### sqlx | What is a heap table, and why is a table without a clustered key usually a problem? | heap table sql server, table without clustered index, forwarded records, rid lookup, when to use heap
A heap is a table without a clustered index. Rows are stored in no particular order, on whatever pages have space, and nonclustered indexes point to rows using a physical row identifier, the RID, made of file, page and slot.

Problems with heaps.

Forwarded records: when a row is updated and grows, like a varchar column getting longer, and no longer fits on its page, SQL Server moves it to another page and leaves a forwarding pointer behind. Reads then follow extra pointers, causing more I/O. Over time, heavy updates make heaps slower.

Space isn't reclaimed well after deletes, unless the table is rebuilt or deletes take table locks, so heaps can grow with empty pages.

Lookups from nonclustered indexes use RID lookups, and range queries on any order require sorts or scans.

Why clustered indexes are the default: rows are stored in key order, range scans on the key are efficient, there are no forwarded records, and space management is better. A narrow, unique, ever-increasing key, like an identity or sequential value, makes a good clustered key.

When a heap can be fine: staging tables used for fast bulk loads that are read once and truncated, where insert speed matters and data is read fully anyway; or temporary tables.

How I find heaps: query sys.indexes for index_id 0, and check sys.dm_db_index_physical_stats for forwarded record counts. In older databases, finding large, frequently updated heaps and adding a clustered index can give a noticeable performance improvement.

Adding a nullable column: metadata-only in SQL Server, instant regardless of table size.

Adding a NOT NULL column with a default: since SQL Server 2012 Enterprise Edition, this is also metadata-only for runtime constant defaults; older or lower editions may rewrite every row, which is slow and locks the table.

Changing a column's type, or making a column NOT NULL: may scan or rewrite the table. Safer approach: add a new column, backfill it in small batches during quiet times, switch the application to use it, then drop the old column later.

Creating indexes: use ONLINE = ON where the edition allows, and RESUMABLE in newer versions, so it can be paused and continued; otherwise schedule during maintenance windows.

Adding foreign keys or check constraints: WITH NOCHECK first to avoid a long validation, then validate later at a quiet time, so they become trusted.

Use a low lock timeout, like SET LOCK_TIMEOUT, or WAIT_AT_LOW_PRIORITY for online operations, so a schema change waiting for a lock doesn't block everyone queued behind it.

Expand and contract: deploy the schema change first in a backward-compatible way, release code that works with both shapes, then remove the old structure in a later release.

Test on a production-sized copy, measuring duration and lock behaviour, because something instant on a small test database can take an hour in production.
