### tx | What is consumer-driven contract testing with Pact? | pact contract testing, consumer driven contracts, contract test microservices, pact broker, provider verification
In microservices, an API change can break a consumer without anyone noticing until integration or production. End-to-end tests catch this, but they're slow and fragile. Contract testing catches it earlier and cheaper.

### tx | What is mutation testing, and what does it tell you that coverage doesn't? | mutation testing, stryker dotnet, stryker mutator, test quality, mutation score, coverage is not enough
Code coverage tells you which lines ran during tests, not whether the tests would notice if those lines were wrong. A test that calls a method and asserts nothing gives full coverage and catches nothing.

Mutation testing measures test quality directly. A tool makes small changes to the code, called mutants: changing greater than to greater than or equal, flipping a boolean, replacing a plus with a minus, removing a method call, or returning a default value. Then it runs the tests against each mutant. If a test fails, the mutant is killed, which is good. If all tests still pass, the mutant survived, meaning nothing in the test suite would notice that bug. The mutation score is the percentage killed.

For .NET, Stryker.NET does this, and Stryker exists for JavaScript and TypeScript too. It produces an HTML report showing each surviving mutant in the code, which points directly to missing assertions or untested edge cases, like boundary conditions in a date or quantity check.

It's slow, because it runs the tests many times, so I don't run it on every build. I run it on critical modules, like calculation, validation or allocation logic, periodically or in a nightly pipeline, and use the --since option to mutate only changed code in pull requests.

I don't chase 100 percent; some mutants are equivalent and can't be killed. The value is finding important gaps that coverage hides.

### tx | What is property-based testing, and when is it useful? | property based testing, fscheck, cscheck, hypothesis python, generative testing, invariants testing
Normal example-based tests check specific inputs: given 10 kits and 3 requested, 7 remain. Property-based testing instead states a rule that must hold for all valid inputs, and the framework generates hundreds of random inputs trying to break it.

Examples of properties: serialising and then deserialising any object gives back the same object; sorting is idempotent and preserves the items; for any sequence of reservations and releases, available stock never goes negative and reserved plus available always equals the total; or a parsing function never throws for any string, it either succeeds or returns a validation error.

When a property fails, the framework shrinks the input to the smallest failing example, like an empty list or a value of exactly zero, which makes the bug easy to understand.

Tools: FsCheck and CsCheck for .NET, which integrate with xUnit; Hypothesis for Python; fast-check for TypeScript.

Where it pays off: algorithms with clear invariants, like allocation, scheduling, calculations, encoders and parsers; code with many edge cases; and stateful systems, where the framework generates random sequences of operations and compares the system against a simple model.

It doesn't replace example tests, which document specific business cases clearly. And properties need some thought to write well; a property that just reimplements the code proves nothing. I use it for the most logic-heavy parts, where it often finds bugs no one thought of.

### tx | What is snapshot or approval testing with Verify? | snapshot testing, approval testing, verify dotnet, verify tests, snapshot test api response, received approved files
Snapshot or approval testing checks a complex output against a previously approved version stored in a file, instead of writing many individual assertions.

With the Verify library in .NET, a test ends with await Verify(result). The first time, Verify serialises the result, like an object graph, an API response, a generated document, or even HTTP calls made, into a received file, and the test fails. A developer reviews it, and if it's correct, accepts it as the verified file, which is committed to the repository. On later runs, the new output is compared with the verified file; any difference fails the test and shows a diff.

It's great for: API response shapes, so an accidental field rename or format change is caught; generated output like reports, emails, CSV or XML exports, PDFs and images; complex mapping results; and characterising legacy code before refactoring, capturing its current behaviour.

Jest has the same idea for JavaScript, with toMatchSnapshot, often used for serialisable outputs rather than whole component trees.

### tx | What are the different types of performance tests? | load test vs stress test, soak test, spike test, endurance test, capacity test, performance testing types
Different performance tests answer different questions, so I pick based on the risk.

A load test runs the expected normal and peak traffic, like the busiest hour of a typical day, for a period. It checks that response times and error rates meet the targets under the load we actually expect.

A stress test increases load beyond expectations until the system breaks, to find the breaking point and, importantly, how it fails. Does it slow down gracefully, shed load with 429 or 503 responses, and recover when load drops? Or does it fall over and stay down?

A spike test applies a sudden jump, like ten times normal traffic within seconds, which tests autoscaling speed, connection pools, caches warming and queues absorbing bursts. Think of a study going live at many sites at once, or a batch import triggering many events.

A soak or endurance test runs a moderate load for many hours or days. It finds problems that only appear over time: memory leaks, connection leaks, growing queues, log disks filling up, slow degradation from fragmentation, and scheduled jobs interfering with traffic.

A capacity test finds how much load a given configuration can handle while meeting targets, which feeds sizing and cost decisions.

Breakpoint and scalability tests check whether adding instances actually increases throughput, or whether a shared resource, like the database, caps it.

All of them need clear targets defined beforehand, and monitoring on the server side to explain the results.

### tx | How do you keep integration tests isolated when they share a database? | test database isolation, respawn, reset database between tests, transaction rollback tests, parallel integration tests

### tx | How do you test for race conditions and concurrency bugs? | test concurrency, race condition test, concurrent requests test, double booking test, optimistic concurrency test
Concurrency bugs, like two requests reserving the same last kit, or a duplicate message being processed twice at the same time, rarely show up in normal tests because tests run one call at a time.

I test them deliberately.

Fire concurrent requests in integration tests: start, say, 20 tasks that call the same endpoint at once, released together with a barrier or a SemaphoreSlim, against a real database. Then assert the invariant: exactly one reservation succeeded, the others got a conflict, and the stock count is correct. Run it multiple times, because a race may not show every run.

Load tests at higher concurrency also surface deadlocks and lock contention.

The key mindset: identify the invariant that must hold, then try hard to break it.

### tx | Do you practise test-driven development? | tdd, test driven development, red green refactor, do you write tests first, tdd benefits drawbacks
I use test-driven development selectively, where it gives the most value, rather than dogmatically everywhere.

The cycle is red, green, refactor: write a small failing test describing the next bit of behaviour, write the simplest code that passes it, then clean up the code and tests while keeping them green, and repeat in small steps.

Where it works really well for me: business rules with clear inputs and outputs, like validation, calculations and allocation logic. Where I'm more flexible: exploratory work, where I don't yet know the shape of the solution, so I spike first, then write tests and often rewrite the code properly; UI layout; and thin glue code, where integration tests give better value.

The benefits I've seen are better designed, more decoupled code, because testable code tends to have clear dependencies, and high confidence when refactoring.

Whether written first or right after, the important thing is that tests describe behaviour, not implementation, and that no logic change goes in without a test.

### tx | How do you add tests to legacy code that has none? | testing legacy code, characterization tests, seams, working effectively with legacy code, refactor without tests
Legacy code without tests is risky to change, but you can't stop and write tests for everything. I follow the approach from Working Effectively with Legacy Code: add tests where you're about to change things.

Characterisation tests first. Before changing a piece of code, I write tests that capture what it currently does, not what it should do. Call it with representative inputs and assert whatever it currently returns. Snapshot tools like Verify make this quick for complex outputs. These tests protect existing behaviour, including odd behaviour that other parts of the system may rely on.

Find or create seams. Legacy code often creates its dependencies directly: new SqlConnection, static calls, DateTime.Now, HttpContext.Current. A seam is a place where behaviour can be replaced for testing without editing the logic. Techniques: extract an interface and inject it; extract the hard-to-test call into a virtual method and override it in a test subclass; wrap static calls behind a small adapter; or pass values in as parameters. I make these changes in small, safe, often tool-assisted refactoring steps.

Sprout and wrap. For new functionality, I write it as a new, tested class or method, and call it from the legacy code, rather than adding more untested lines into a huge method.

Integration tests around the edges, like running the real API or stored procedure against a test database, often give the most protection quickly for very tangled code.

In our .NET Framework core, this is how we change risky areas safely.

### tx | How would you test a randomisation algorithm in a clinical trial system? | test randomization algorithm, randomisation testing, statistical testing allocation, test treatment allocation, irt randomization validation
Randomisation decides which treatment arm a patient gets, so mistakes affect the scientific validity of a trial. Testing it needs both normal tests and statistical checks.

Deterministic unit tests. The algorithm should take its random source as a dependency, so tests can supply a seeded generator or a predefined sequence. Then I assert exact outcomes for specific scenarios: with block size four and a 1:1 ratio, each block contains two of each arm; stratification puts patients into the right stratum based on their factors; when a site or stratum is capped, the right behaviour follows; and with a pre-generated randomisation list, patients receive the next entry in their stratum in order, and no list entry is used twice.

Edge cases: the last slot in a block, a list running out, invalid strata, concurrent randomisations at two sites at the same moment, which must not take the same entry, and re-randomisation rules.

Statistical simulation. Run the algorithm many thousands of times, [like 100,000 simulated patients], and check that the allocation ratios match the design within expected tolerance, that balance holds within strata and sites for dynamic methods like minimisation, and that there's no predictable pattern. These simulations run as part of study configuration testing, not every build.

Validation evidence. In a regulated system, the tests, the simulation reports and the configuration they ran against are kept as validation evidence, and the study's configuration is tested in UAT before it goes live.

### tx | How do you test both states of a feature flag? | test feature flags, feature toggle testing, flag combinations testing, feature flag test strategy
Feature flags double the paths through the code, so the risk is that one state, usually the one not active in the test environment, is never tested and breaks when someone flips the flag.

My approach.

Unit tests for both states of each flag that changes logic. The flag check is injected, through IFeatureManager or a small interface, so tests set it on or off directly. Each flagged behaviour gets a test with the flag on and with it off.

Integration and end-to-end tests run against the configuration production will actually use at release. If production will have the flag off at first, the main test run uses off, plus a second run, or a subset of tests, with it on. Test environments shouldn't just have every flag on, because then the off path, which is what production is running, isn't tested.

Avoid testing every combination. With several flags, combinations explode. Flags should be independent where possible, and I test combinations only for flags that interact.

Test the flip itself for important flags: switching a flag at runtime shouldn't break in-flight requests or leave inconsistent state, like jobs started under the old behaviour.

Test the failure default: if the flag service is unreachable, the code should fall back to the safe value.

And when a flag is removed after full rollout, the tests for the dead path are removed too, which keeps the test suite honest about what the code actually does.

### tx | How do you test Azure Functions or AWS Lambda handlers? | test azure functions, test lambda function, unit test lambda dotnet, local testing serverless, lambda test tool
Serverless functions are easiest to test when the handler is thin.

Structure first. The function method or Lambda handler only translates the trigger into a call: parse the HTTP request, queue message or S3 event, call a service class, and map the result back. The business logic lives in that service class, injected through dependency injection, which both Azure Functions isolated worker and Lambda support. Then most tests are plain unit tests of the service.

Unit testing the handler itself: construct the input object, like an SQSEvent with sample records, an APIGatewayHttpApiV2ProxyRequest, or for Azure Functions, a ServiceBusReceivedMessage or a fake HttpRequestData, plus a test context, like TestLambdaContext from Amazon.Lambda.TestUtilities, and call the method. Assert the response and that the service was called correctly. For SQS batch handlers, test that partial failures are reported correctly. Sample events from AWS documentation or captured from real environments make realistic inputs.

Local runs: Azure Functions Core Tools runs functions locally with Azurite emulating storage queues and blobs; for Lambda, the Lambda Test Tool, SAM CLI's local invoke, or LocalStack emulate the environment.

Integration tests in a real cloud test environment, deployed by the pipeline, then triggered with a real message or HTTP call, verify permissions, triggers and configuration, which emulators can't fully check. Those catch the classic serverless problems, like a missing IAM permission or a wrong queue binding.
