### apix | How do you design pagination in an API response? | api pagination design, paged response, page size limit, next page link, continuation token, cursor pagination api
I always paginate list endpoints, because returning everything works in testing and fails in production when a table grows.

The request takes either a page number and page size, or a cursor. Page size has a sensible default, like 25, and a hard maximum, like 100, enforced on the server, so nobody can request a million rows.

The response wraps the items with metadata: for page-based paging, the page number, page size and total count; for cursor-based paging, a next cursor or continuation token, and whether there are more items. Some APIs also return links to the next and previous pages, or use the Link header, so clients don't build URLs themselves.

Which style I choose depends on the data. Offset paging, with skip and take, is simple and lets users jump to page 10, which suits admin screens. But it gets slow on deep pages, because the database still reads all the skipped rows, and results shift if rows are added while paging. Cursor or keyset paging uses the last item's sort key, like "created after this date and id", which is fast at any depth and stable, so it's better for large tables, infinite scrolling and API consumers syncing data.

Ordering must be deterministic, so I always add a unique tie-breaker, like the id, to the sort.

Total counts can be expensive on big tables, so I make them optional.

### apix | What are ETags, and how do you use them for caching and concurrency? | etag, if none match, if match, conditional request, 304 not modified, 412 precondition failed, optimistic concurrency http
An ETag is a version identifier for a resource, returned in a response header. It can be a hash of the content, or a version number like SQL Server's rowversion. Clients use it in conditional requests, for two purposes.

Caching: the client sends If-None-Match with the ETag it has. If the resource hasn't changed, the server returns 304 Not Modified with no body. That saves bandwidth and processing, which helps for large resources that are fetched often, like study configuration.

Concurrency control: when updating, the client sends If-Match with the ETag it got when it read the resource. The server checks it against the current version. If someone else changed the resource in the meantime, the versions don't match, and the server returns 412 Precondition Failed instead of silently overwriting the other person's change, which is the lost update problem. The client then reloads and lets the user merge or retry. Some APIs also return 428 Precondition Required if If-Match is missing on updates, to force clients to use it.

In ASP.NET Core, I implement this myself: map the entity's row version to the ETag header, read If-Match in the update endpoint, and pass the version into EF Core's concurrency token check, so the database enforces it.

It's the HTTP version of optimistic concurrency.

### apix | How do you use HTTP caching headers for APIs? | cache control header, http caching api, no store, max age, private public cache, vary header
HTTP caching headers tell browsers, CDNs and proxies whether and how long they can reuse a response, which can massively reduce load.

Cache-Control is the main header. max-age equals 300 means the response can be reused for 300 seconds. public allows shared caches, like a CDN, to store it, while private means only the user's own browser may cache it, which is right for user-specific data. no-cache means the client may store it but must revalidate with the server before using it, often with an ETag. no-store means don't store it anywhere, which I use for sensitive data, like patient information or tokens.

Vary tells caches which request headers change the response, like Accept-Language or Authorization, so different versions are cached separately.

For APIs, my defaults are: sensitive or user-specific data gets no-store or private, no-cache; truly public, rarely changing data, like a list of countries or static reference data, gets public with a max-age, maybe through a CDN; and responses with ETags support cheap revalidation.

In ASP.NET Core, I set headers directly, use the ResponseCache attribute, or use output caching middleware for server-side caching of whole responses, which is different: it's the server reusing its own response, regardless of what clients do.

Getting caching wrong with user data can leak information between users, so I'm conservative.

In practice, most modern APIs are JSON only, and that's fine. I've used negotiation mainly for exports, where the same report endpoint returns JSON for the UI and CSV for download, based on the Accept header or a format parameter.

### apix | What is HATEOAS, and do you use it? | hateoas, hypermedia, rest maturity model, richardson maturity model, links in api response
HATEOAS stands for Hypermedia as the Engine of Application State. It's the highest level of the Richardson maturity model for REST. The idea is that responses include links telling the client what it can do next, like a shipment response containing links to "cancel" or "track", only when those actions are allowed. The benefits in theory: clients are less coupled to URL structures, and the server controls which actions are available based on the current state and the user's permissions.

In practice, I rarely see full HATEOAS in real projects, including ours. Most front ends are built together with the API, so they know the URLs. And flags in responses indicating allowed actions, like canCancel or canReturn, computed on the server from the state and the user's permissions, so the UI shows the right buttons without duplicating business rules. That gives most of the benefit with less complexity.

### apix | What are route constraints in ASP.NET Core? | route constraints, int route constraint, guid route constraint, custom route constraint, route parameter constraint
Route constraints restrict which values a route parameter accepts, so the route only matches when the value fits. They're written inside the route template after a colon, like api/shipments/{id:int}, {id:guid}, {code:alpha}, {name:minlength(3)}, {page:range(1,1000)}, or {date:datetime}. Several can be combined, and there's regex for patterns.

They're mainly for disambiguating routes. For example, I might have shipments/{id:int} and shipments/{reference} for lookups by a text reference. The int constraint ensures a numeric value goes to the first, and anything else goes to the second. Without constraints, they'd conflict.

An important point is that constraints aren't validation. If a constraint fails, the route simply doesn't match, so the client gets a 404 Not Found, not a 400 Bad Request explaining the problem. That's confusing for an API consumer who passed an invalid value. So I use constraints for routing decisions, and do input validation separately, returning proper 400 errors with clear messages.

I can also write custom constraints by implementing IRouteConstraint, and register them with a name, for example a constraint that only matches valid study codes.

Also, the datetime and decimal constraints use the invariant culture, which is good, because routes shouldn't depend on the server's culture.

### apix | What are endpoint filters in minimal APIs? | endpoint filters, minimal api filters, iendpointfilter, addendpointfilter, validation filter minimal api
Endpoint filters are the minimal API version of MVC action filters. They run before and after the endpoint handler, can inspect and change the arguments, short-circuit with a different result, or modify the result after the handler runs.

I add one with AddEndpointFilter on an endpoint or on a route group, either as a lambda or a class implementing IEndpointFilter. The filter receives an EndpointFilterInvocationContext, which gives access to the HttpContext and the handler's arguments, and a next delegate to call the rest of the pipeline.

Common uses: validation, where a generic filter finds the argument of a type, runs its FluentValidation validator, and returns a 400 validation problem if it fails, so the handler only runs with valid input; logging or timing for specific endpoints; checking a tenant or feature flag; and wrapping or transforming results consistently.

Filters on a route group apply to every endpoint in that group, which keeps cross-cutting logic in one place. Multiple filters run in the order they're added, like middleware, first in, first to run.

Compared with middleware, endpoint filters run after routing, so they know which endpoint is executing and can access its typed arguments. Middleware runs for every request and only sees the raw HttpContext. So I use middleware for global concerns and endpoint filters for endpoint-specific ones.

### apix | What are TypedResults, and why use them in minimal APIs? | typedresults, results union type, minimal api return types, openapi minimal api responses, results vs typedresults
In minimal APIs, a handler can return results from the Results class, like Results.Ok or Results.NotFound, which return the IResult interface, or from TypedResults, which return concrete types, like Ok of ShipmentDto or NotFound.

TypedResults have two advantages.

First, OpenAPI documentation. Because the return type is concrete, the framework knows exactly what the endpoint returns, and generates the response schema and status codes automatically, without needing Produces attributes or metadata calls.

Second, testing. In a unit test, I can call the handler directly and check that the result is of type Ok of ShipmentDto and inspect its Value, without casting or running an HTTP server.

When a handler can return different results, like Ok or NotFound or ValidationProblem, I declare the return type as a union: Results of Ok of ShipmentDto, NotFound, ValidationProblem. The compiler then checks that the handler only returns those types, and OpenAPI documents all three responses. This is clearer than returning IResult, where anything can come back.

There's no big performance difference; it's mainly about correctness, documentation and testability.

So in new minimal APIs, I use TypedResults with union return types by default, and Results only for quick prototypes.

### apix | How does response compression work in ASP.NET Core? | response compression, gzip brotli, compress api responses, usresponsecompression, breach attack compression
Response compression reduces the size of responses sent to the client, using algorithms like Brotli or Gzip, which can shrink JSON and HTML by 70 to 90 percent. That reduces bandwidth and speeds up responses over slower networks.

The client says what it supports in the Accept-Encoding header, and the server compresses the response and sets the Content-Encoding header.

In ASP.NET Core, I add AddResponseCompression and UseResponseCompression, configure Brotli and Gzip providers, choose the compression level, and the MIME types to compress. For HTTPS, I have to opt in with EnableForHttps, because of security concerns.

But the first question is where compression should happen. If the app runs behind IIS, NGINX, a load balancer or a CDN that already compresses responses, I let them do it, because they're usually more efficient, and the app shouldn't compress twice. The middleware is useful when the app is exposed directly through Kestrel or the proxy can't compress.

Compression costs CPU, so the "fastest" level is often a better trade-off for dynamic responses. It's not useful for already compressed content, like images or zip files, or for very small responses.

The security issue is attacks like BREACH, which can extract secrets from compressed HTTPS responses that mix secrets with attacker-controlled input. So I avoid compressing responses that contain tokens alongside user input.

### apix | How do you add request timeouts in ASP.NET Core? | request timeout middleware, addrequesttimeouts, request timeout .net 8, cancel slow requests, timeout policy endpoint
Since .NET 8, ASP.NET Core has request timeout middleware. I register it with AddRequestTimeouts, add UseRequestTimeouts to the pipeline, and set a default timeout, plus named policies for specific endpoints, using the RequestTimeout attribute or WithRequestTimeout on minimal API endpoints. A long export endpoint might get two minutes, while normal endpoints get ten seconds.

The important thing to understand is how it works. When the timeout expires, it doesn't kill the request. It triggers HttpContext.RequestAborted, the request's cancellation token. So it only helps if my code passes that cancellation token all the way down, to EF Core queries, HttpClient calls and other async operations, so they stop when the token is cancelled. If the code ignores the token, the work continues anyway.

When the timeout fires and the response hasn't started, the middleware returns 504 Gateway Timeout by default, which I can customise.

Timeouts are also disabled while debugging, so they don't interfere.

Why bother? Without timeouts, slow requests keep holding resources, like database connections and threads, long after the client has given up, because the load balancer usually times out first. Under load, that makes everything slower. A server-side timeout, slightly shorter than the load balancer's, frees those resources and keeps the service healthy.

### apix | How does ASP.NET Core run on IIS: in-process vs out-of-process hosting? | iis hosting asp.net core, in process vs out of process, aspnetcore module, ancm, host asp.net core on iis, web.config asp.net core

### apix | What is the forwarded headers middleware, and why is it needed behind a proxy? | forwarded headers, x forwarded for, x forwarded proto, behind load balancer asp.net core, client ip behind proxy, useforwardedheaders
When an ASP.NET Core app runs behind a reverse proxy or load balancer, like NGINX, an AWS ALB or Azure Front Door, the app sees the proxy as the client. So HttpContext.Connection.RemoteIpAddress shows the proxy's IP, and Request.Scheme shows http if the proxy terminated TLS, even though the user connected with https.

That breaks several things: redirect URLs and generated links use http instead of https, the OpenID Connect redirect URI is wrong, so login fails, HTTPS redirection loops, rate limiting by IP limits everyone together, and logs show the wrong client IP.

The proxy adds headers with the original values: X-Forwarded-For for the client IP, X-Forwarded-Proto for the original scheme, and X-Forwarded-Host. The forwarded headers middleware, UseForwardedHeaders, reads them and updates the request, so the rest of the app sees the real values. It should run early in the pipeline.

Security matters here, because clients can send fake X-Forwarded-For headers. So I configure KnownProxies or KnownNetworks, so the middleware only trusts headers from our real proxies, and ForwardLimit for chains of proxies.

On IIS with in-process hosting, and in some container setups, this is handled automatically, but behind a cloud load balancer, I configure it explicitly.

### apix | How do you design a bulk or batch endpoint? | bulk api, batch endpoint, bulk create api, partial success response, 207 multi status, batch operations api
Sometimes clients need to create or update many items at once, like 500 kit status changes, and calling a single-item endpoint 500 times is slow and chatty. So I design a bulk endpoint, carefully.

First, limits: a maximum number of items per request, like 1,000, to protect the server, and for larger volumes, an asynchronous job with a file upload instead.

Second, the transaction semantics, which must be explicit. All-or-nothing: if any item fails validation, nothing is saved, and the response lists all the errors. That's simpler for clients and right when items depend on each other. Or partial success: valid items are saved, and the response contains a result per item, with its index or client-provided reference, status and any error. For partial success, I return 200 with a detailed body, or 207 Multi-Status, and never just a 201, which would hide failures.

Third, idempotency: an idempotency key for the whole request, or a client reference per item, so a retried request doesn't create duplicates.

Fourth, efficient processing: validate everything first, load needed data in a few queries, not one per item, and write in batches.

And for long-running bulk work, return 202 Accepted with a status URL.

I document clearly which mode the endpoint uses, because clients handle them very differently.

### apix | How do you design error responses and error codes for API clients? | api error design, error codes api, problem details errors, error response format, machine readable errors
A good error response helps two audiences: the developer debugging the integration, and the program that needs to react automatically.

### apix | How do you stream a large file download efficiently from an API? | stream file download, filestreamresult, large file download api, range requests, download without loading memory
The key is never loading the whole file into memory. If I read a 2 GB file into a byte array and return it, the server needs 2 GB of memory per concurrent download, it lands on the Large Object Heap, and the server can run out of memory quickly.

### apix | What is IHttpContextAccessor, and what are its pitfalls? | ihttpcontextaccessor, httpcontext in service, access httpcontext outside controller, httpcontext null background thread
IHttpContextAccessor gives access to the current HttpContext from places that don't receive it directly, like a service class. I register it with AddHttpContextAccessor, inject it, and read HttpContext from it. A common use is a CurrentUser service that reads the user's claims, or getting the correlation id for logging.

It works using AsyncLocal, so the context flows with the async execution of the request.

There are several pitfalls. Outside a request, like in a background service, a hosted service or a message consumer, HttpContext is null, so code that depends on it fails there. If code captures the HttpContext and uses it after the request ends, for example in fire-and-forget work, it may be reading a recycled or disposed context, which causes strange bugs. HttpContext isn't thread-safe, so it mustn't be used from parallel tasks. And it couples business logic to the web layer, making it harder to test and reuse.

So my approach: in the business layer, I depend on a small abstraction, like ICurrentUser with UserId and Permissions. The web implementation reads from IHttpContextAccessor; a background job or message consumer provides its own implementation, using the user from the message. Tests just use a fake.

And I copy the values I need while the request is active, never the HttpContext itself.

### apix | How would you migrate an ASP.NET MVC 4.8 application to ASP.NET Core? | migrate asp.net mvc to core, .net framework to .net core migration, system.web adapters, yarp incremental migration, upgrade assistant
For a large MVC application, I'd avoid a big-bang rewrite and migrate incrementally.

Microsoft's recommended approach is the strangler fig with YARP. I create a new ASP.NET Core app that sits in front of the old one as a reverse proxy. Requests for migrated routes are handled by the new app, and everything else is forwarded to the legacy app. I then move controllers and views one area at a time. The System.Web adapters help share code, and can share session and authentication between the two apps, so users don't notice which app served the page.

Before moving code, I prepare it: move business logic into class libraries targeting .NET Standard 2.0, so both old and new apps can use them; remove System.Web dependencies like HttpContext.Current from business code; and update packages to versions that support modern .NET. The .NET Upgrade Assistant helps analyse and convert projects.

The main differences to handle: Global.asax and web.config become Program.cs, middleware and appsettings.json; HTTP modules and handlers become middleware; built-in DI replaces third-party containers; authentication changes; and bundling, Razor and some HTML helpers differ.

Our approach is similar in spirit: rather than converting the legacy MVC portal, we're moving modules to the React shell with new .NET APIs, while shared Keycloak SSO keeps the experience seamless.
