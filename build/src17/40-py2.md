### pyx | list vs tuple vs set vs dict in Python: when do you use each? | python list vs tuple, list tuple set dict, python data structures, when to use tuple, python collections basics
These are Python's four core built-in collections, and choosing well affects correctness and performance.

A list is ordered and mutable, allows duplicates, and is indexed by position. Appending is fast, and membership checks with in are O(n), because Python scans the list. Use it for ordered sequences you'll change, like rows read from a file.

A tuple is ordered and immutable. Because it can't change, it's hashable if its contents are, so it can be a dictionary key or a set member, like a key of site id and date. Tuples signal "this is a fixed record", like coordinates or a function returning several values, and they're slightly lighter than lists.

A set is an unordered collection of unique, hashable items, with O(1) average membership checks, and operations like union, intersection and difference. Use it for de-duplication, or checking membership in large collections, like "have I already processed this id?". frozenset is the immutable version.

A dict maps unique, hashable keys to values with O(1) average lookups, and since Python 3.7, it preserves insertion order. Use it for lookups by key, counting, grouping, and JSON-like data.

A common performance bug I've seen in scripts is checking if item in some_list inside a loop over thousands of items, which makes the work quadratic; converting the list to a set first fixes it.

The collections module adds specialised versions: defaultdict for grouping, Counter for counting, deque for fast appends and pops at both ends, and namedtuple for readable records.

### pyx | What are *args and **kwargs in Python? | args kwargs python, star args, double star kwargs, variable arguments python, keyword only arguments
They let a function accept a variable number of arguments.

*args collects extra positional arguments into a tuple. def log(message, *args) can be called as log("x", 1, 2, 3), and args is the tuple 1, 2, 3.

**kwargs collects extra keyword arguments into a dictionary. def create(**kwargs) called as create(name="kit", qty=5) gives kwargs as a dict with name and qty.

The names args and kwargs are just conventions; the star and double star are what matter.

The same symbols unpack at call time: func(*my_list) passes list items as separate positional arguments, and func(**my_dict) passes dict items as keyword arguments. They also merge dicts, like combined = {**defaults, **overrides}, and unpack lists inside list literals.

Related parameter features.

Keyword-only parameters: anything after a bare star, like def send(to, *, retries=3), must be passed by name, which makes calls clearer and safer.

Positional-only parameters: anything before a slash must be passed by position.

Where they're useful: decorators and wrappers that pass any arguments through to the wrapped function, like def wrapper(*args, **kwargs): return func(*args, **kwargs); functions that forward options to another library; and flexible logging or formatting helpers.

The downside: overusing kwargs hides what a function actually accepts, hurting readability, type checking and autocomplete. For business code, I prefer explicit parameters, and for typed wrappers, ParamSpec in type hints preserves the wrapped function's signature.

### pyx | List comprehensions vs generator expressions vs loops: which do you use? | list comprehension, generator expression, python comprehension, dict comprehension, comprehension vs for loop
A list comprehension builds a list in one expression: squares equals x times x for x in numbers if x is positive, written inside square brackets. It's concise, readable for simple transformations, and usually faster than an equivalent loop with append, because the loop runs in optimised C code. Python also has dict comprehensions, like {s.id: s for s in sites}, and set comprehensions.

A generator expression looks the same but with parentheses: total = sum(x * x for x in numbers). It doesn't build a list; it produces items one at a time, lazily. That uses almost no memory, which matters for large data, like processing millions of lines from a file, and it can stop early, for example with any() or next().

How I choose.

If I need the result as a collection to reuse, index or iterate more than once, a list or dict comprehension.

If I'm feeding the values into a function that consumes them once, like sum, max, any, join or writing to a file, a generator expression.

If the logic has multiple steps, side effects, nested conditions or error handling, a normal for loop. Comprehensions with several nested loops and conditions become hard to read, and readability matters more than saving lines.

Watch out: a generator can only be consumed once; iterating it again gives nothing, which surprises people. And comprehensions shouldn't be used just for side effects, like calling print, because they build a useless list.

These map nicely to C#: list comprehensions are like LINQ with ToList, and generator expressions are like deferred LINQ queries.

### pyx | What are dunder methods in Python, and what is __init__ vs __new__? | dunder methods python, magic methods, __init__ vs __new__, __repr__ vs __str__, python special methods
Dunder, or double-underscore, methods are special methods Python calls to implement built-in behaviour. Defining them lets your classes work naturally with the language.

Common ones: __init__ initialises a new object; __repr__ gives an unambiguous developer representation, used in debugging and logs, while __str__ gives a user-friendly string for print; __eq__ and __hash__ define equality and hashing, which must be consistent, like Equals and GetHashCode in C#; __lt__ and friends define ordering; __len__, __getitem__ and __iter__ make objects behave like collections; __enter__ and __exit__ make context managers; __call__ makes an instance callable like a function; and arithmetic methods like __add__ allow operator overloading.

__new__ vs __init__: __new__ is a static-like method that actually creates and returns the new instance; __init__ then initialises that instance, setting attributes. You rarely override __new__. It's needed for immutable types, like subclassing tuple or str, where values must be set at creation, or for patterns like singletons or caching instances.

Practical advice: always define __repr__ for domain classes, because good logs and debugging output save time; if you define __eq__, Python sets __hash__ to None unless you define it, making objects unhashable, which surprises people.

Dataclasses generate __init__, __repr__ and __eq__ for you, and with order=True or frozen=True, comparison and hashing too, which is why I usually use dataclasses or Pydantic models for data-holding classes instead of writing dunder methods by hand.

### pyx | @property vs @classmethod vs @staticmethod in Python: what is the difference? | python property decorator, classmethod vs staticmethod, python getter setter, alternative constructor python, python class methods
These decorators change how methods in a class behave.

@property turns a method into an attribute-like accessor. order.total looks like an attribute, but runs a method computing it. You can add a setter with @total.setter for validation when assigning. This lets you start with a plain attribute and later add logic without changing callers, so Python doesn't need Java-style getters and setters. For expensive computed values that don't change, functools.cached_property computes once and caches it.

@classmethod receives the class itself, cls, as its first argument instead of an instance. The main use is alternative constructors, like Shipment.from_dict(data) or Config.from_env(), which return cls(...), so they also work correctly for subclasses. They can also access class-level state.

Regular methods receive the instance as self, and are used for behaviour that depends on an object's state.

How I decide: if it needs instance data, a regular method or property; if it creates instances or needs the class, a classmethod; if it needs neither, I ask whether it should just be a module-level function, which is often more Pythonic than a staticmethod.

Comparing to C#: properties are like C# properties, classmethods used as factories are like static factory methods, and staticmethods are like static helper methods.

### pyx | What are abstract base classes in Python, and how do you use them? | abc python, abstract base class, abstractmethod, python interface, abc module
Python's abc module lets you define abstract base classes: a class inheriting from ABC with methods marked @abstractmethod. You can't create an instance of the base class, or of any subclass that hasn't implemented all abstract methods; Python raises a TypeError at instantiation.

Example: a Notifier base class with an abstract send method, and EmailNotifier and SmsNotifier subclasses implementing it. Code depends on Notifier, and the implementation is chosen through configuration or dependency injection, like in FastAPI with Depends.

Why use them: they document and enforce a contract, so forgetting to implement a method is caught early when objects are created, rather than later when the method is called. They can also provide shared implementation in non-abstract methods, like a template method pattern.

Alternatives.

Protocols, from typing, define interfaces structurally: any class with matching methods satisfies the protocol, without inheriting from it. Checked by type checkers like mypy, not at runtime unless marked runtime_checkable. Good for decoupling, especially from third-party classes you can't change.

Duck typing: Python's traditional approach, just call the method and trust the object has it.

How I choose: ABCs when I own the hierarchy and want runtime enforcement and shared code; Protocols when I want lightweight interfaces for type checking and testing, which fits a dependency-injection style; duck typing for small scripts.

Coming from C#, ABCs feel like abstract classes, and Protocols are the closest thing to interfaces, with the difference that implementing them is implicit.

### pyx | How does memory management and garbage collection work in Python? | python memory management, reference counting python, python garbage collector, gc module, python memory leak
CPython, the standard Python implementation, manages memory mainly with reference counting. Every object keeps a count of references to it. When a variable is reassigned, goes out of scope, or a container drops the object, the count decreases, and when it hits zero, the object is freed immediately. That makes memory release predictable, unlike .NET's generational GC, where objects are collected later.

Reference counting can't handle cycles, like two objects referring to each other, or an object referring to itself. So Python also has a cyclic garbage collector, in the gc module, which periodically looks for groups of objects only reachable from each other and frees them. It uses generations, like .NET, checking young objects more often.

Memory allocation: small objects use pymalloc, a specialised allocator with pools, so freed memory is often reused by Python rather than returned to the operating system. That's why a Python process's memory may not shrink after a big job, even when objects are freed.

Common memory problems: holding references longer than needed, like global caches, lists that keep growing, or closures capturing large objects; loading whole files or query results into memory instead of streaming them; and C extensions that leak.

Tools: tracemalloc to see where memory is allocated and compare snapshots, memory profilers like memray, and objgraph to find what's keeping objects alive.

For long-running workers with memory growth, I fix the cause where possible, and as a safety net use worker recycling, like Gunicorn's max_requests or Celery's max tasks per child.

### pyx | asyncio.gather vs TaskGroup: how do you run async tasks concurrently in Python? | asyncio gather, taskgroup python, asyncio concurrency, asyncio timeout, structured concurrency python
To run several async operations at the same time, like calling three APIs in parallel, Python offers a few tools.

asyncio.gather(a(), b(), c()) runs the coroutines concurrently and returns their results in order. By default, if one raises an exception, gather raises it, but the other tasks keep running in the background, which can leave work orphaned. With return_exceptions=True, exceptions are returned as results instead, so you can inspect each.

TaskGroup, since Python 3.11, is structured concurrency: async with asyncio.TaskGroup() as tg: t1 = tg.create_task(a()); t2 = tg.create_task(b()). When the block exits, all tasks have finished. Limiting concurrency: when processing hundreds of items, don't start them all at once; use an asyncio.Semaphore inside each task, or process in batches, to protect downstream services and connection pools.

asyncio.as_completed processes results as they finish, useful for showing progress.

Common mistakes: calling a coroutine without awaiting it, which never runs it; creating tasks with create_task and not keeping a reference, so they may be garbage collected; and mixing blocking calls into async code, which serialises everything.

### pyx | How do you write and package Python Lambda functions? | python lambda, aws lambda python, lambda powertools python, package python lambda dependencies, lambda layers python
Python is a natural fit for Lambda, with fast cold starts and a simple handler model: def handler(event, context), returning a response.

Structure: initialise clients, like boto3 clients and configuration, at module level so they're reused across warm invocations. Keep the handler thin: parse the event, call business logic in separate functions or modules, and return the result. That keeps logic testable without Lambda.

Packaging dependencies: for pure-Python packages, a zip file with dependencies installed into the package folder is enough. For packages with compiled parts, like pydantic-core, cryptography or numpy, they must be built for Amazon Linux and the right architecture, x86 or arm64, so build in a matching container or use the right platform flags with pip. Large dependencies can go in layers, shared across functions, or use a container image, up to 10 GB, when packages are big, like data or ML libraries.

Tools: AWS SAM or CDK to define and deploy functions, with sam build handling dependency packaging; Powertools for AWS Lambda for structured logging, metrics, tracing, event parsing with Pydantic, idempotency, and batch processing helpers for partial SQS failures.

Performance: increase memory to get more CPU; choose arm64 Graviton for better price-performance; avoid importing heavy libraries you don't need; and use SnapStart for Python if cold starts matter.

Testing: unit-test business logic directly, test handlers with sample events, and use moto to mock AWS services, or LocalStack for integration-style tests.

Security: least-privilege execution roles, secrets from Secrets Manager or Parameter Store, not environment variables in plain text.

### pyx | How do you handle dates, time zones and naive vs aware datetimes in Python? | python timezone, naive vs aware datetime, zoneinfo python, utc python datetime, datetime pitfalls python
Python's datetime objects are either naive, with no time zone information, or aware, with a tzinfo attached. Mixing them causes errors, like being unable to compare naive and aware datetimes, and naive values cause silent bugs when code assumes a time zone that isn't there.

My rules.

Use aware datetimes in UTC internally: datetime.now(timezone.utc), not datetime.utcnow(), which returns a naive value and is deprecated, and not datetime.now(), which returns local server time.

Store UTC in databases, in timestamp with time zone columns in Postgres, or as UTC with a clear naming convention in SQL Server.

Convert to the user's or site's local time only for display or for business rules that depend on local time, using zoneinfo with IANA names, like ZoneInfo("Asia/Kolkata"), which handles daylight saving correctly. Never use fixed offsets for regions that change for daylight saving.

Use date, not datetime, for business dates without a time, like a visit date or date of birth, to avoid off-by-one-day bugs when converting between zones.

Parse and format with ISO 8601: datetime.fromisoformat handles most ISO strings since 3.11, and APIs should exchange ISO strings with offsets or a trailing Z. Pydantic parses these automatically.

Arithmetic across daylight saving changes: adding 24 hours isn't always "the same time tomorrow" in local time, so for schedules, compute in local time and convert.

Testing: use freezegun or time-machine to control the current time in tests, and test around midnight and daylight saving changes.

These are the same principles I follow in .NET with DateTimeOffset and DateOnly.
