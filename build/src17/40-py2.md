### pyx | list vs tuple vs set vs dict in Python: when do you use each? | python list vs tuple, list tuple set dict, python data structures, when to use tuple, python collections basics
Yeah, these are Python's four core collections, and picking the right one affects both correctness and performance.

A list is ordered and mutable, allows duplicates, and is indexed by position. Appending is fast, but checking membership with "in" is linear, because Python scans the whole list. Use it for ordered sequences you'll change, like rows read from a file.

A tuple is ordered and immutable. Since it can't change, it's hashable if its contents are, so it can be a dict key or a set member, like a key made of site id and date. Tuples say "this is a fixed record", like coordinates or a function returning several values, and they're a bit lighter than lists.

A set is an unordered collection of unique, hashable items, with constant-time membership checks on average, plus union, intersection and difference. Use it for de-duplication, or checking membership in big collections, like "have I already processed this id?". frozenset is the immutable version.

A dict maps unique, hashable keys to values with constant-time average lookups, and since Python 3.7 it keeps insertion order. Use it for lookups by key, counting, grouping, and JSON-like data.

A common performance bug I've seen in scripts is checking whether an item's in some list inside a loop over thousands of items, which makes the whole thing quadratic. Converting the list to a set first fixes it, and it's like a one-line change.

The collections module adds specialised versions too, defaultdict for grouping, Counter for counting, deque for fast appends and pops at both ends, and namedtuple for readable records.

### pyx | How does memory management and garbage collection work in Python? | python memory management, reference counting python, python garbage collector, gc module, python memory leak
Right, so CPython, the standard implementation, manages memory mainly with reference counting. Every object keeps a count of references to it. When a variable's reassigned, goes out of scope, or a container drops the object, the count goes down, and when it hits zero the object is freed immediately. So memory release is predictable, unlike .NET's generational GC where objects get collected later.

Reference counting can't handle cycles though, two objects pointing at each other, or an object pointing at itself. So Python also has a cyclic garbage collector, in the gc module, which periodically looks for groups of objects only reachable from each other and frees them. It uses generations too, like .NET, checking young objects more often.

Allocation, small objects use pymalloc, a specialised allocator with pools, so freed memory is often reused by Python instead of going back to the OS. That's why a Python process's memory might not shrink after a big job, even though the objects are freed. People think it's a leak, but it's not always.

Real memory problems I've seen, holding references too long, like global caches, lists that keep growing, closures capturing big objects. Loading whole files or query results into memory instead of streaming. And C extensions that leak.

Tools, tracemalloc to see where memory's allocated and compare snapshots, memory profilers like memray, and objgraph to find what's keeping objects alive.

For long-running workers with memory growth, I fix the cause where I can, and as a safety net use worker recycling, like Gunicorn's max requests or Celery's max tasks per child.

### pyx | How do you write and package Python Lambda functions? | python lambda, aws lambda python, lambda powertools python, package python lambda dependencies, lambda layers python
Python is a natural fit for Lambda, with fast cold starts and a simple handler model: def handler(event, context), returning a response.

Structure: initialise clients, like boto3 clients and configuration, at module level so they're reused across warm invocations. Keep the handler thin: parse the event, call business logic in separate functions or modules, and return the result. That keeps logic testable without Lambda.

Packaging dependencies: for pure-Python packages, a zip file with dependencies installed into the package folder is enough. ### pyx | How do you handle dates, time zones and naive vs aware datetimes in Python? | python timezone, naive vs aware datetime, zoneinfo python, utc python datetime, datetime pitfalls python
Python's datetime objects are either naive, with no time zone information, or aware, with a tzinfo attached. Mixing them causes errors, like being unable to compare naive and aware datetimes, and naive values cause silent bugs when code assumes a time zone that isn't there.

My rules.

Use aware datetimes in UTC internally: datetime.now(timezone.utc), not datetime.utcnow(), which returns a naive value and is deprecated, and not datetime.now(), which returns local server time.

Store UTC in databases, in timestamp with time zone columns in Postgres, or as UTC with a clear naming convention in SQL Server.

Convert to the user's or site's local time only for display or for business rules that depend on local time, using zoneinfo with IANA names, like ZoneInfo("Asia/Kolkata"), which handles daylight saving correctly. Never use fixed offsets for regions that change for daylight saving.

Use date, not datetime, for business dates without a time, like a visit date or date of birth, to avoid off-by-one-day bugs when converting between zones.

Parse and format with ISO 8601: datetime.fromisoformat handles most ISO strings since 3.11, and APIs should exchange ISO strings with offsets or a trailing Z. Pydantic parses these automatically.

Arithmetic across daylight saving changes: adding 24 hours isn't always "the same time tomorrow" in local time, so for schedules, compute in local time and convert.

Testing: use freezegun or time-machine to control the current time in tests, and test around midnight and daylight saving changes.

These are the same principles I follow in .NET with DateTimeOffset and DateOnly.
