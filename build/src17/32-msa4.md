### msa | GUIDs vs sequential ids vs Snowflake-style ids: how do you choose? | guid vs int id, sequential guid, snowflake id, distributed id generation, uuid v7, primary key choice
Let me go through them, because the id choice affects database performance, security, and how distributed systems create records.

Auto-increment integers are small, fast, naturally ordered, great for clustered indexes. But the database generates them, so you only know the id after the insert, merging data from several databases causes collisions, and putting them in URLs reveals counts and makes guessing other records easy.

Random GUIDs, version 4, can be generated anywhere without coordination, they're globally unique and unguessable. But they're 16 bytes, and the randomness fragments clustered indexes in SQL Server, because inserts land all over the index, page splits, slower writes.

Sequential GUIDs, NEWSEQUENTIALID in SQL Server, or UUID version 7, which .NET 9 supports with Guid dot CreateVersion7. They put a timestamp at the start, so values are roughly ordered and inserts go at the end of the index like integers, but they're still globally unique and generated in the app. I'd say that's a good default for distributed systems now.

Snowflake-style ids are 64-bit integers combining a timestamp, a machine id and a sequence. Ordered, compact, no coordination, but you need to hand out machine ids uniquely.

My approach, internal clustered keys can be integers or UUID v7. Public identifiers in URLs shouldn't be guessable, so UUIDs or a separate public id. And authorisation never relies on ids being secret.

Business identifiers like kit numbers or subject numbers follow their own business formats, separate from the technical keys.

### msa | What is two-phase commit, and why do microservices avoid it? | two phase commit, 2pc, distributed transaction, xa transaction, msdtc, why not distributed transactions
Right, two-phase commit is a protocol for making one transaction atomic across several resources, like two databases, or a database and a message broker. A coordinator first asks every participant to prepare, basically promise they can commit. If everyone says yes, it tells them all to commit. If anyone says no, everyone rolls back. In the .NET Framework world, MSDTC did this, often transparently with TransactionScope across connections.

Why microservices stay away from it. Availability, every participant has to be up and responsive for it to complete. If one service or database is slow or down, the whole thing waits or fails. Locks are held during prepare, so a stuck coordinator can leave stuff locked.

Coupling, services would have to share transaction infrastructure, which kills independent deployment and technology choice. And a lot of modern components, HTTP APIs, Kafka, cloud services, don't support it at all.

Scalability, the coordination round trips and held locks limit throughput.

So microservices accept eventual consistency, with patterns that give reliability without global locks. The outbox pattern, so a local database change and an event are recorded atomically. Idempotent consumers. And sagas, a sequence of local transactions with compensating actions if a later step fails.

Where you truly need strong consistency, the better answer is often to keep that data in one service and one database, and then a normal local transaction does the job. I think people sometimes split services too early and then fight this problem.
