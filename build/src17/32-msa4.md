### msa | GUIDs vs sequential ids vs Snowflake-style ids: how do you choose? | guid vs int id, sequential guid, snowflake id, distributed id generation, uuid v7, primary key choice
Id choice affects database performance, security and how distributed systems create records.

Auto-increment integers: small, fast, naturally ordered, great for clustered indexes. But the database generates them, so you only know the id after insert, merging data from several databases causes collisions, and exposing them in URLs reveals counts and makes guessing other records easy.

Random GUIDs, version 4: generated anywhere without coordination, globally unique, unguessable. But they're 16 bytes, and their randomness fragments clustered indexes in SQL Server, because inserts land all over the index, causing page splits and slower writes.

Sequential GUIDs: NEWSEQUENTIALID in SQL Server, or UUID version 7, which .NET 9 supports with Guid.CreateVersion7(). They embed a timestamp at the start, so values are roughly ordered, which keeps index inserts at the end like integers, while remaining globally unique and generated in the application. That's a good default for distributed systems now.

Snowflake-style ids: 64-bit integers combining a timestamp, a machine id and a sequence. Ordered, compact and generated without coordination, but they need machine ids assigned uniquely.

My approach: internal clustered keys can be integers or UUID v7; public identifiers in URLs should not be guessable, so either UUIDs or a separate public id; and authorisation checks never rely on ids being secret.

For business identifiers, like kit numbers or subject numbers, those follow their own business formats separately from technical keys.

### msa | What is two-phase commit, and why do microservices avoid it? | two phase commit, 2pc, distributed transaction, xa transaction, msdtc, why not distributed transactions
Two-phase commit is a protocol for making a transaction atomic across several resources, like two databases, or a database and a message broker. A coordinator first asks every participant to prepare, meaning to promise they can commit; if all say yes, it tells everyone to commit; if anyone says no, everyone rolls back. In the .NET Framework world, MSDTC did this, often transparently with TransactionScope across connections.

Why microservices avoid it.

Availability: all participants must be up and responsive for the transaction to complete. If one service or database is slow or down, the whole operation waits or fails. Locks are held during the prepare phase, so a stuck coordinator can leave resources locked.

Coupling: services would need to share transaction infrastructure, which defeats independent deployment and technology choices. Many modern components, like HTTP APIs, Kafka or cloud services, don't support it at all.

Scalability: coordination round trips and held locks limit throughput.

Instead, microservices accept eventual consistency with patterns that give reliability without global locks: the outbox pattern, so a local database change and an event are recorded atomically; idempotent consumers; and sagas, a sequence of local transactions with compensating actions if a later step fails.

Where strong consistency really is required, the better answer is often to keep that data in one service and one database, so a normal local transaction does the job.

### msa | What are leader election and consistent hashing used for? | leader election, consistent hashing, distributed coordination, single leader pattern, partition assignment, hash ring
Both solve coordination problems when several instances of a service run at once.

Leader election: sometimes exactly one instance must do a task, like run a scheduler, process a singleton queue, or coordinate others. Instances compete for a leadership lease; one wins and does the work, renewing the lease periodically; if it dies or stops renewing, another takes over after the lease expires. Implementations: a Kubernetes Lease object, which client libraries support; a distributed lock with expiry in Redis, a database row with an expiry timestamp, or sp_getapplock in SQL Server; or coordination services like ZooKeeper and etcd. Watch-outs: a paused leader, like during a long GC pause, may think it's still leader after its lease expired, so work should carry a fencing token, an increasing number that downstream systems check, to reject stale leaders.

Consistent hashing: distributes keys across a changing set of nodes. Nodes are placed on a hash ring, and each key goes to the next node clockwise. When a node is added or removed, only the keys near it move, instead of almost all keys, as happens with simple hash modulo N. Virtual nodes smooth the distribution. It's used in distributed caches, like Redis Cluster's slot model, which is a related idea, partitioned databases like Cassandra and DynamoDB, and load balancers with session affinity.

In application design, I usually use these through infrastructure rather than building them, but understanding them helps reason about failover and rebalancing.

### msa | What is hexagonal architecture, or ports and adapters? | hexagonal architecture, ports and adapters, onion architecture, clean architecture vs hexagonal, domain isolation
Hexagonal architecture, also called ports and adapters, puts the application's core logic in the middle, with no dependencies on technology, and connects everything else through ports and adapters.

Ports are interfaces defined by the core: incoming ports describe what the application can do, like an IAllocateKit use case; outgoing ports describe what it needs from the outside, like IKitRepository, IClock, or INotificationSender.

Onion architecture and clean architecture are close relatives with the same core idea, differing mostly in how they name layers.

The risk is over-engineering: lots of interfaces and mapping for simple CRUD services. I apply it where there's meaningful business logic, and keep simple services simple.

Batch processing handles data in large chunks at intervals, like a nightly job processing all of yesterday's transactions. Stream processing handles each event continuously as it arrives, within seconds.

### msa | How do you handle write conflicts in an active-active multi-region setup? | active active conflicts, multi region writes, last writer wins, conflict resolution, crdt, multi master replication

### msa | What is load shedding, and how do you implement it? | load shedding, admission control, shed load under overload, priority requests, graceful degradation overload
Load shedding means deliberately rejecting some requests when the system is overloaded, so it can keep serving the rest well. Without it, an overloaded service tries to handle everything, queues grow, every request becomes slow, timeouts cause client retries, and the system collapses for everyone.

How to implement it.

Concurrency limits: cap the number of requests processed at once, with a short queue; beyond that, return 503 or 429 immediately with Retry-After. ASP.NET Core's rate limiting middleware has a concurrency limiter for this, and Kestrel and IIS have connection and queue limits.

Queue time limits: if a request has waited too long to start, drop it, because the client has probably given up already. Processing it wastes capacity.

Prioritisation: not all requests are equal. Keep capacity for critical operations, like a patient randomisation or dispensing, and shed lower-priority work first, like reports, exports, bulk syncs and background refreshes. This can be done with separate limiters per endpoint class, or separate deployments for critical and non-critical traffic.

Adaptive limits: adjust the concurrency limit based on observed latency, growing when the system is healthy and shrinking when latency rises.

Client cooperation: clients should back off on 429 and 503, with exponential backoff and jitter, and not retry immediately.

Degradation: serve cached or simplified responses instead of full ones.

Load tests should show the system shedding load gracefully, not falling over.

### msa | What are hedged requests, and how do they reduce tail latency? | hedged requests, tail latency, p99 latency reduction, speculative retry, backup requests
In distributed systems, a request often fans out to several backends, and the slowest one decides the total latency. Even if each backend is usually fast, occasional slow responses, from GC pauses, noisy neighbours or network hiccups, make the p99 latency much worse than the median. That's tail latency.

A hedged request sends the same request to a second replica if the first hasn't responded within a short delay, like the p95 latency of that call, and uses whichever response arrives first, cancelling the other. Because the delay is set at a high percentile, only a few percent of requests get hedged, so extra load is small, but the slow outliers are cut off.

Polly v8 has a hedging strategy, and the .NET resilience packages provide AddStandardHedgingHandler for HttpClient, which can also route the hedged request to a different endpoint.

When it's appropriate: read operations, or idempotent ones, because the request may execute twice. Never for non-idempotent writes without idempotency keys. And when the backend has multiple independent replicas, so the second attempt is likely to land somewhere healthier.

Risks: under overload, hedging adds load exactly when the system is struggling, so limit the number of hedged attempts and combine it with circuit breakers.

Other tail latency techniques: timeouts with fast fallbacks, reducing fan-out, caching, and fixing the cause of slow outliers, like GC pauses.
