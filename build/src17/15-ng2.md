### ngx | How do NgRx store, actions, reducers, selectors and effects fit together? | ngrx, ngrx store, ngrx effects, ngrx selectors, redux in angular, ngrx actions reducers
So NgRx is basically a Redux-style state management library for Angular, built on RxJS.

The store holds the application state as one immutable object tree. Components never change it directly. Instead they dispatch actions, which are plain objects describing events, like "Shipments Page Opened" or "Shipment Cancelled", created with createAction or grouped with createActionGroup.

Reducers are pure functions. They take the current state and an action and return a new state, built with createReducer and on handlers. No side effects in there, so state changes are predictable and easy to test.

Selectors read and derive data from the store, created with createSelector. They're memoised, so derived values, like pending shipments for the selected site, only get recalculated when their inputs change. Components use store.select, or selectSignal to get a signal.

Effects handle side effects, like API calls. An effect listens for specific actions, calls a service, and dispatches a success or failure action with the result, usually with switchMap or exhaustMap and catchError. Then the reducers update state from those actions.

Redux DevTools shows every action and state change, with time-travel debugging, which honestly helps a lot when debugging.

The downside is boilerplate and indirection. For simple apps or local component state, it's overkill, and services with signals are enough. It pays off in big apps with lots of shared state and complex async flows, with several developers who need consistent patterns.

### ngx | How is the new SignalStore different from the classic NgRx store with reducers and effects? | ngrx signalstore, signal store, signalstate, withstate withmethods, ngrx signals, lightweight state angular
Okay, NgRx SignalStore is a newer, lighter state management approach from the NgRx team, built on Angular signals instead of RxJS and the Redux pattern.

You create a store with signalStore and compose it from features. withState defines the initial state, which becomes signals for each property. withComputed adds derived signals. withMethods adds methods that update state with patchState, or do async work, using rxMethod for RxJS-based flows or plain async functions. And withHooks runs logic on init and destroy. There are reusable features too, like withEntities for collections with ids, and community features for devtools and request status.

The store is an injectable service, so you can provide it at root for global state, or at component level for local, feature-specific state. I like that flexibility.

Compared with the classic NgRx store, there are no separate actions, reducers and effects files, so way less boilerplate. Components just call methods directly. It's signal-based, so it works naturally with OnPush, zoneless change detection and signal inputs. And it's more modular, stores per feature rather than one big global tree. What you lose is some of the strict event-driven traceability that actions give you, though NgRx has added an events plugin for people who want that back.

For new Angular apps, I'd start with SignalStore or simple signal-based services, and only use the classic store where the Redux pattern clearly adds value.

### ngx | How do you handle errors in RxJS streams? | rxjs error handling, catcherror, retry rxjs, error kills observable, retry with delay, finalize rxjs
In RxJS, when an Observable errors, the stream terminates. No more values come through. So in a long-lived stream, like a search box or a polling feed, one single error stops it working until the page is reloaded. That's honestly the most common RxJS bug I see.

catchError intercepts the error and returns a replacement Observable. A fallback value, like an empty array, with of. Or EMPTY to complete quietly. Or rethrow a friendlier error with throwError. The key trick for long-lived streams is putting catchError inside the inner Observable, inside switchMap, not at the end of the outer stream. Then only that one request fails, and the outer stream keeps listening for the next search term.

retry resubscribes to the source after an error, a number of times. Since RxJS 7, retry takes a config with count and a delay function, which allows exponential backoff, like retry with count 3 and a delay based on a timer and the retry count. I only retry for transient errors, network failures or 503, not 400 or 404.

finalize runs when the stream completes, errors or gets unsubscribed, which is useful for turning off a loading spinner.

In Angular, HTTP errors can also be handled centrally in an interceptor, for logging, notifications or redirects on 401, while components handle the errors specific to their screens. That split works well for us.

### ngx | combineLatest vs forkJoin vs withLatestFrom vs zip: what is the difference? | combinelatest vs forkjoin, withlatestfrom, zip rxjs, combine observables, parallel http calls rxjs
So these all combine multiple Observables, but they emit at different times, and honestly that's the whole difference.

forkJoin waits until all the sources complete, then emits once with the last value from each. It's like Promise.all. The right choice for running several HTTP calls in parallel and using all the results together, like loading a site, its inventory and its users before showing a page. If any source errors, the whole thing errors. And if any source never completes, forkJoin never emits, so it's not for long-lived streams.

combineLatest emits whenever any source emits, once each source has emitted at least once, giving the latest value from each. It's for combining ongoing streams, like filters. When the status filter, the date range or the search term changes, recalculate with the latest of all three. A common surprise is nothing emits until every source has emitted once, so startWith helps there.

withLatestFrom is driven by one primary stream. When the primary emits, it combines that value with the latest of the others, but the others emitting doesn't trigger anything. Perfect for "when the user clicks save, take the current form value and the selected site".

zip pairs values by index, first with first, second with second, and so on. I rarely need it, mostly when values correspond one to one.

And with signals, computed covers a lot of combineLatest's use cases more simply.

### ngx | How do you build a search typeahead with RxJS? | typeahead rxjs, debouncetime distinctuntilchanged, search as you type, autocomplete angular, switchmap search, cancel previous request
Let me walk through it. A typeahead calls an API as the user types, so it has to avoid flooding the server and deal with responses arriving out of order.

I start with a stream of the input's values, from a reactive form control's valueChanges, or a signal converted with toObservable. Then a pipeline of operators.

### ngx | What are hot and cold observables, and what does shareReplay do? | hot vs cold observable, shareReplay, share rxjs, multicast, duplicate http calls angular, cache http observable
Okay, a cold Observable starts producing values separately for each subscriber. Angular's HttpClient calls are cold, so each subscription sends a new HTTP request. If a template has two async pipes on the same HTTP Observable, or two components subscribe to the same service method's result, the request goes out twice.

A hot Observable produces values regardless of subscribers, and all subscribers share the same source. Like DOM events, a WebSocket stream, or a Subject. Late subscribers miss earlier values, unless the stream replays them.

share and shareReplay turn a cold Observable into a shared hot one. share multicasts to all current subscribers through one subscription to the source. shareReplay also replays the last N values to new subscribers. So shareReplay with bufferSize 1 is the common way to cache an HTTP result. The first subscriber triggers the request, and everyone after gets the cached value with no new call.

There are pitfalls though. With the old shareReplay of 1 signature, the source subscription stays alive even when all subscribers leave, which can leak for long-lived sources. Using the config with refCount true unsubscribes when nobody's left. A cached error or stale value stays cached, so you need a way to refresh, like a Subject that triggers reloading. And caching in a root service means the data sticks around for the whole session.

For simple shared state, honestly, a signal or BehaviorSubject in a service is often clearer.

### ngx | How does internationalization work in Angular? | angular i18n, localize angular, translation angular, ngx-translate, transloco, multiple languages angular
Angular has a built-in i18n system. I mark text in templates with the i18n attribute, and in code with the $localize tagged template. The CLI extracts all marked text into a translation file, XLIFF or JSON, which translators fill in for each language. Then the build produces a separate compiled version of the app per locale, with translations baked in. Locale data also drives the built-in date, number, currency and percent pipes, and plural and select expressions handle grammar rules.

The advantage of the built-in approach is performance: translations are compiled in, so there's no runtime lookup cost. The disadvantages: a separate build and deployment per language, usually served under a path like /fr/, and switching language means loading a different version of the app, a full page reload.

Runtime libraries, like Transloco or the older ngx-translate, load translation files at runtime and translate with a pipe or directive. One build serves all languages, and users can switch language instantly. The cost is a small runtime overhead and less compile-time checking. Many business apps choose this for its flexibility.

Either way, I keep dates and numbers in neutral formats in the data, format them in the UI with the user's locale, think about right-to-left languages for layouts if needed, and avoid concatenating translated fragments, because word order differs between languages.

### ngx | How do you read route parameters, and what is component input binding? | activatedroute, route params angular, query params angular, withcomponentinputbinding, parammap, route data
Angular's router gives a component access to the current route's information through ActivatedRoute: route parameters, like the id in /shipments/:id; query parameters, like ?status=pending; the fragment; resolved data; and static data defined on the route.

There are two ways to read them. The snapshot, like route.snapshot.paramMap.get of id, gives the value at the moment the component was created. That's fine if the component is always recreated when the parameter changes. But Angular reuses the component when navigating from /shipments/1 to /shipments/2 within the same route, so the snapshot becomes stale. The Observables, paramMap and queryParamMap, emit every time the parameters change, so I combine them with switchMap to load the right data, which also cancels the previous request.

Since Angular 16, there's a simpler option: withComponentInputBinding in the router configuration. Route parameters, query parameters and resolver data are then bound directly to component inputs with the same name. So the component just declares an id input, or a signal input, and reacts to its changes. That removes the ActivatedRoute dependency, makes the component easier to test and reuse, and works nicely with computed signals and resource for loading data.

To update query parameters, like when the user changes a filter, I navigate with queryParams and queryParamsHandling set to merge, which keeps the URL shareable and supports the back button.

### ngx | What are preloading strategies in the Angular router? | preloading strategy, preloadallmodules, custom preloading strategy, lazy loading preloading, quicklink angular
With lazy-loaded routes, each feature's code is downloaded only when the user navigates to it. That keeps the initial bundle small, but the first navigation to a feature waits for its chunk to download, which feels slow on poor networks.

Preloading downloads lazy-loaded route chunks in the background after the app has loaded and become interactive, so later navigation is instant, while initial load stays fast.

Angular has built-in strategies. NoPreloading, the default, only loads on demand. PreloadAllModules preloads every lazy route once the app is stable. That's simple and works for small to medium apps, but in large apps it downloads a lot of code that many users never need, wasting bandwidth.

A custom preloading strategy gives more control. I implement PreloadingStrategy, and decide per route, for example preloading only routes marked with data preload true, the ones most users visit, or only routes the current user's role can access, or skipping preloading on slow connections using the Network Information API. Libraries like ngx-quicklink preload routes whose links are currently visible on the screen, which is a smart middle ground.

It's configured with withPreloading in provideRouter for standalone apps.

Route-level @defer and canMatch guards complement this: canMatch prevents users from downloading features they're not allowed to use.

### ngx | What causes ExpressionChangedAfterItHasBeenCheckedError, and how do you fix it? | expressionchangedafterithasbeencheckederror, ng0100, change detection error, value changed after checked, angular dev mode error
This error appears in development mode when a value bound in a template changes after Angular has already checked it during the same change detection cycle. In dev mode, Angular runs an extra verification pass to make sure the view is stable; if a binding's value differs on the second pass, it throws, because the view would show inconsistent data.

Typical causes. A child component, or a lifecycle hook like ngAfterViewInit, changes a property on the parent that the parent's template already rendered. For example, a child emits an event in ngOnInit that sets the parent's title. A getter or method in the template that returns a new value each time, like new Date or a new object or array, so the second check sees a different value. Or a service shared between parent and child that's updated during rendering.

The fix is to correct the data flow rather than hide the error. Move the logic earlier, like into ngOnInit or the constructor, so the value is set before the view is checked. Avoid updating parent state from a child's lifecycle hooks; instead let the parent compute it, or restructure into a shared service or signal that's set before rendering. Make template expressions stable, using computed signals or pure pipes instead of methods that create new objects.

Workarounds like setTimeout or calling detectChanges again make the error go away, but they hide a design problem and cause an extra render, so I use them only as a last resort.

### ngx | What is the difference between markForCheck and detectChanges? | markforcheck vs detectchanges, changedetectorref, onpush manual update, detach change detection, view not updating onpush
Both are methods on ChangeDetectorRef, used when Angular doesn't automatically notice a change, typically with OnPush components.

markForCheck marks the current component and all its ancestors up to the root as dirty, so they'll be checked in the next change detection cycle. It doesn't run change detection immediately. It's the right tool when an OnPush component's state changed because of something Angular didn't see, like a value pushed from a service subscription, or a callback from a third-party library. The async pipe calls markForCheck internally, which is why it works with OnPush.

detectChanges runs change detection immediately and synchronously, but only for this component and its children. It's useful when I need the view updated right now, for example before measuring the DOM, or for a component that I've detached from the change detection tree with detach, which I then update manually for performance, like a component that redraws only on a timer. Calling it at the wrong time, like during another change detection cycle, can cause errors.

There's also checkNoChanges, used in dev mode for verification.

In modern Angular with signals, these are needed much less: when a signal read in a template changes, Angular marks the component for check automatically. When I find myself calling them often, it usually means state should be in signals or Observables used with the async pipe.

### ngx | Smart vs presentational components: how do you structure an Angular feature? | smart vs dumb components, container presentational, angular component design, feature structure angular, reusable components angular
I split components into two kinds, which makes features easier to test, reuse and change.

Smart components, or containers, know about the application. They inject services or stores, load data, handle routing parameters, call APIs and decide what happens on user actions. They usually correspond to a page or a major section, like ShipmentListPage. Their templates mostly compose presentational components and pass data down.

Presentational components, or dumb components, only know about their inputs and outputs. They receive data through inputs, render it, and emit events through outputs when the user does something, like ShipmentTable emitting a cancelClicked event with the shipment id. No services, no HTTP, no store access. That makes them easy to reuse in different contexts, easy to test with simple inputs, and ideal for OnPush change detection, since they only change when inputs change.

A feature folder typically contains the routes, the page-level smart components, the presentational components, the feature's data service or store, and its models. Shared, generic UI components, like buttons, dialogs and form fields, live in a shared library or the design system.

I don't follow it dogmatically: a small component with one simple service call doesn't need splitting. But for anything substantial, keeping data logic separate from display pays off, especially when the same table or form appears in several places.

### ngx | What is a route reuse strategy in Angular? | route reuse strategy, routereusestrategy, keep component state on navigation, cache route component, tabs keep state angular
By default, when the user navigates away from a route, Angular destroys its component, and when they come back, it creates a new one. Any state in the component, like the scroll position, filters, an expanded row, or data already loaded, is lost, and data is fetched again.

A RouteReuseStrategy lets me customise this. It's a class with methods that the router calls during navigation: shouldDetach decides whether to keep a route's component when leaving it; store saves the detached component tree; shouldAttach and retrieve decide whether to restore a stored component when navigating back; and shouldReuseRoute decides whether to reuse the current component when navigating between two URLs that match the same route config.

A common use is a list-detail flow: the user filters a long list, opens a detail page, and comes back, expecting the list exactly as it was. By detaching and storing the list route, it reappears instantly with its state. Another is a tabbed interface where each tab is a route.

There are pitfalls. Stored components stay in memory, with their subscriptions active, so I need to limit what's stored and clear it, for example on logout. Lifecycle hooks like ngOnInit don't run again on reattach, so components may need to refresh data explicitly.

Often a simpler solution is keeping filter state in the URL's query parameters, or in a service or store, so a new component can restore it.
