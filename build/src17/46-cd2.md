### cdx | What are matrix builds, and when do you use them? | matrix build, matrix strategy github actions, azure pipelines matrix, test multiple versions, parallel jobs
Okay so, a matrix build runs the same job several times with different parameter combinations, in parallel. In GitHub Actions you define a strategy matrix, and in Azure Pipelines a strategy with a matrix of named configurations. Each combination becomes its own job with its own result.

Typical uses are testing a library against several runtime versions, like Node 18, 20 and 22, or Python 3.10 to 3.12, building on Windows and Linux, or testing against different database versions. It's also handy for building lots of similar services or packages from one pipeline, where each matrix entry is one service.

Couple of things from practice. Be careful with fail-fast. Turning it off lets you see all the failing combinations instead of stopping at the first one. Use include and exclude to skip pointless combinations, so you don't end up with an exploding number of jobs. Cache dependencies per combination, keyed by the version, or caches will clash. And keep the matrix small for pull requests, with the full matrix running nightly or on main, because every entry costs agent minutes.

In practice, I used a matrix for our shared front-end npm packages, building and testing against two React versions while the shell migration was going on, because some sub-apps were still on the older one. It caught a breaking peer dependency issue before it reached any app. For services though, I prefer one pipeline per service triggered by path filters, rather than one big matrix that rebuilds everything.

### cdx | Microsoft-hosted vs self-hosted build agents: how do you choose? | self hosted agent, hosted agent, self hosted runner, build agent choice, private network build agent
Hosted agents, Microsoft-hosted agents in Azure Pipelines or GitHub-hosted runners, are fresh virtual machines created per job and thrown away afterwards. Self-hosted agents are machines you run and maintain yourself.

Hosted agents are clean every time, so no leftover state between builds, no patching, and they scale without effort. The downsides are limited control over installed tools, no access to private networks unless you add extra setup, caches that have to be restored every time, and cost or time limits at scale.

Self-hosted agents make sense when builds need to reach private resources, like an on-prem database or an internal package feed, when you need special hardware or licensed tools, when on-disk caches make builds much faster, or when the whole server's on-premises anyway. The cost is operational. You patch them, secure them, and deal with disks filling up and state leaking between builds.

Security really matters with self-hosted agents. Never run untrusted pull requests from forks on them, because a malicious build can attack the network. Run the agent as a low-privilege account, isolate pools per environment so a test build can't deploy to production, and ideally use ephemeral agents, container-based or autoscaled VMs that get recreated after each job.

In our case, the on-prem Azure DevOps Server uses self-hosted agents, since deployments go to servers inside the network. We keep separate pools for build and for production deployment, and the production pool can only be used by approved release pipelines.

### cdx | How do you sign container images and verify them before deployment? | image signing, cosign, sigstore, notation, verify image signature, admission policy signed images, sbom attestation
Signing proves an image was built by your pipeline and hasn't been changed since. Without it, anyone with push access to a registry could swap an image, and the cluster would happily run it.

The common tools are Cosign from the Sigstore project and Notation from the Notary project, which Azure Container Registry supports. The pipeline builds the image, pushes it, and signs it by its digest, not its tag, because tags can move. Signing can use a key held in a key vault, or keyless signing, where a short-lived certificate is tied to the pipeline's identity through OIDC.

Alongside the signature you can attach attestations, an SBOM listing every package in the image, and provenance saying which commit and pipeline built it. Those help a lot when a new vulnerability shows up and you need to know which images contain the affected package.

Verification happens at deploy time. In Kubernetes, an admission controller like Kyverno, Gatekeeper or the Ratify project checks every pod's image and rejects anything unsigned or signed by the wrong identity. Deployments should also reference images by digest, so what was verified is exactly what runs.

I'd roll it out gradually. Sign everything to begin with, then turn on verification in audit mode to find unsigned images, like third-party ones, and only then enforce. Base images from trusted publishers can be allowed by their own signatures. And it gives you a solid answer when security reviewers ask how you know production runs only what CI built.

### cdx | How do conventional commits help generate changelogs and release notes automatically? | conventional commits, automated changelog, release notes generation, semantic release, commit message convention
Conventional commits is basically a simple format for commit messages, a type, an optional scope, and a description. For example, feat for a new feature, fix for a bug fix, docs, refactor, test or chore, plus a breaking-change marker when something isn't backward compatible.

Because the messages are structured, tools can read them. semantic-release or release-please can work out the next version automatically. A fix bumps the patch, a feat bumps the minor, and a breaking change bumps the major. They also generate a changelog grouped by features and fixes, create a tag, and publish the package.

To make it reliable, you enforce the format. commitlint in a Git hook catches mistakes locally, and a pull request check validates the PR title if you squash merge, since that title becomes the commit on main. Linking each commit or PR to a work item lets the release notes include the ticket ids.

And honestly it pays off. Release notes stop being a manual job at the end of a sprint, versions are consistent, and consumers of shared packages can see breaking changes clearly.

We used this pattern for our shared front-end npm packages published to the Azure DevOps feed. The version and changelog came from the commits, so teams consuming a package knew whether an upgrade was safe. For the main application, though, release notes still need business language for the validation team, so the generated list is a starting point someone edits, not the final document.

### cdx | Merge commit vs squash merge vs rebase: which do you use for pull requests? | merge vs rebase, squash merge, git rebase, linear history, git merge strategies, pull request merge type
All three bring a branch's changes into main, but they give you different history.

A merge commit keeps every commit from the branch and adds a merge commit joining the two lines. It preserves exactly what happened, but history gets noisy with lots of small commits like "fix typo", and the graph gets hard to read.

Squash merge combines the whole branch into one commit on main. History becomes one commit per pull request, which is clean and easy to revert, since reverting a feature is just reverting one commit. You lose the individual commits, though they still exist in the pull request.

Rebase replays the branch's commits on top of main, so history stays linear without a merge commit. It keeps individual commits, which is nice if they're meaningful, but because it rewrites history you should never rebase a branch others are working on, and it means force-pushing your own branch.

For me, the default for short-lived feature branches is squash merge, with the pull request title written as a good commit message, since that also works with conventional commits and changelogs. For long-lived release branches, I use real merges so the relationship between branches stays visible. Locally I use rebase to update my feature branch from main before opening a pull request, because it gives reviewers a cleaner diff.

Whatever the team picks, it should be set in branch policies so it's consistent, not left to each person.

### cdx | What are deployment rings, and how do they reduce release risk? | deployment rings, ring based deployment, staged rollout, progressive exposure, early adopters ring
Deployment rings release a change to progressively bigger groups of users, with a pause and a health check between each group. It's how large products avoid exposing everyone to a bad release at once.

A typical setup has ring zero for the internal team, ring one for a small set of friendly customers or one region, ring two for a larger share, and then everyone. Each ring has a bake time, and the pipeline only moves forward if error rates, latency and business metrics stay normal. If something goes wrong, only that ring's affected, and you stop or roll back.

Rings differ from canary releases mainly in what you divide. A canary usually splits traffic randomly by percentage, while rings divide by meaningful groups like tenants, regions or customer types. In multi-tenant systems rings fit really naturally, because you can upgrade tenants or databases in batches.

To do it well, automate the gates, so promotion depends on metrics and not on someone remembering to check. Keep ring membership in configuration, make the code work with mixed versions, and keep database changes backward compatible.

In our platform, each study has its own database, so schema and data changes naturally roll out in batches. We start with internal and test studies, then low-risk studies, then the rest, with checks after each batch. A problem caught in the first batch affects a handful of non-critical databases instead of every live study.

### cdx | What are dark launches and shadow traffic? | dark launch, shadow traffic, traffic mirroring, test in production safely, mirror requests
A dark launch, you know, deploys new code to production and runs it with real traffic, but users don't see its results. Shadow traffic, or traffic mirroring, is a common way to do it. Each real request goes to the current version as normal, and a copy goes to the new version, whose response just gets thrown away.

The point is testing with real production load and real data shapes, which test environments never fully reproduce. You can compare the new version's results with the old one's, watch its latency and errors, and find performance problems before switching anyone over.

You can do it at different levels. A service mesh or proxy like Istio or Envoy can mirror a percentage of requests. In code, you can call both implementations, return the old result, and log the differences, which is the approach libraries like Scientist take.

The big risk is side effects. A shadow request must not write to the real database, charge a card or send an email twice. So shadowing works best for read paths, or the new version writes to a separate store, or calls go out with a dry-run flag.

I'd use it when replacing a critical read path, like a new search or a new calculation engine. For example, when moving a data transfer from the old integration layer to a new .NET API, running both and comparing outputs for a while gives confidence the new one produces identical results before it becomes the real path.

### cdx | How do you keep dev, test and production environments consistent? | environment parity, dev prod parity, environment drift, consistent environments, it works on my machine
Inconsistent environments cause the classic problem: it works in test but fails in production. The goal is that environments differ only in size and configuration, not in how they're built.

The first tool is infrastructure as code. If every environment is created from the same Terraform or Bicep modules with different variables, they can't quietly drift apart, and drift detection in the pipeline catches manual changes.

The second is building once and promoting the same artifact, so test and production run identical binaries or images. Configuration comes from the environment through settings and secret stores, never baked into the build.

The third is matching versions of dependencies: the same database engine version, the same runtime, the same message broker version. Containers and Docker Compose help locally, so a developer runs the same Redis and broker versions as production.

Data is the hard part. Test databases are often small and clean, so performance problems and odd data only show in production. Masked copies of production data, or generated data at realistic volume, close that gap.

Finally, the deployment process itself should be the same everywhere. If test is deployed by hand and production by pipeline, you're not testing the deployment.

In our on-prem setup, we keep a server configuration baseline and compare IIS settings, installed runtimes and app pool settings across environments. A mismatch in a runtime version on one production node once caused a failure that test never showed, which is why we added that check.

### cdx | How do you protect CI pipelines from malicious pull requests? | pipeline security fork pull request, pull_request_target, untrusted code ci, poisoned pipeline execution, secrets in pr builds
A pull request build runs code that someone else wrote, including the build scripts themselves. If that build has access to secrets or a privileged agent, a malicious pull request can steal credentials or attack your network. This is called poisoned pipeline execution.

The main defences are about separation. Pull request builds from forks must run without secrets and with a read-only token. In GitHub Actions, the pull_request event does this by default, while pull_request_target runs with secrets in the base repository's context, so it must never check out and run the pull request's code. In Azure Pipelines, settings control whether fork builds get secrets, and that should stay off.

Run untrusted builds on hosted, throwaway agents, not self-hosted agents inside the network. Require approval before running workflows from first-time contributors.

Protect the pipeline definitions too. Changes to workflow files or templates should need review from owners, using a code owners file, and deployment pipelines should come from protected templates that a pull request can't modify.

Keep deployment credentials scoped to protected environments with approvals, so even a compromised build job on a branch can't deploy to production. Pin third-party actions to a commit hash, since a tag can be moved to malicious code.

For internal repos the threat is lower, but the same rules help against a compromised developer account. Secrets live in environments with approvals, not in the pipeline used for pull request validation.

### cdx | How do you promote container images between registries or environments? | image promotion, promote container image, copy image between registries, acr import, ecr replication, registry per environment
Promotion means the exact image tested in one environment is the one that goes to the next, never a rebuild. With containers, that means moving or re-tagging the same digest.

There are two common setups. With one registry, you promote by adding tags or by updating the deployment to the tested digest. It's simple, but production pulls from a registry that test pipelines can also push to.

With a registry per environment or per trust level, like a dev registry and a production registry, you copy the image across after it passes testing. Azure Container Registry has an import command that copies by digest between registries, ECR supports cross-account replication, and tools like crane or skopeo copy images without pulling them locally. Production clusters only have pull access to the production registry, and only the release pipeline can push to it.

Important details. Always copy and deploy by digest, because a tag like the version number could be overwritten. Copy signatures and SBOMs along with the image so verification still works. Run a vulnerability scan at promotion time as well, since new vulnerabilities appear after build. Keep a record of which digest went to which environment for traceability.

I prefer the separate production registry for anything regulated. It gives a clear boundary: if an image is in the production registry, it passed the gates. The extra copy step is a few seconds and adds a lot of confidence.

### cdx | How do you build a deployment pipeline for serverless apps with SAM or CDK? | sam pipeline, cdk pipelines, deploy lambda ci cd, serverless deployment pipeline, cloudformation deploy lambda
For serverless on AWS, the application and its infrastructure usually deploy together, because a Lambda function, its API Gateway route, its queue and its permissions all belong to the same unit. SAM and CDK both produce CloudFormation, which does the actual deployment.

With SAM, the pipeline runs sam build to package the functions, runs unit tests, and then sam deploy with a parameter file per environment. SAM can also set up gradual deployment for Lambda through CodeDeploy, shifting traffic to the new version over minutes and rolling back automatically if CloudWatch alarms fire.

With CDK, you write infrastructure in a programming language like TypeScript or C#. The pipeline runs cdk synth to produce templates, which become the artifact, and then deploys those same templates to each environment. CDK Pipelines can model the stages and approvals itself, and cdk diff shows what will change, which is useful in a pull request.

Run integration tests against the deployed stack in a test stage before promotion. Watch for changes that replace resources, like renaming a table, which CloudFormation does by deleting and recreating.

For a small team, SAM is quicker to learn. For larger systems with shared constructs, CDK gives better reuse and type checking.

### cdx | What does a good CI pipeline for a Python service look like? | python ci pipeline, python lint test pipeline, ruff mypy pytest ci, python build pipeline, python docker pipeline
A Python pipeline should check quality quickly and produce one reproducible artifact, usually a container image or a wheel.

The steps I use start with setting up the exact Python version and installing dependencies from a lock file, using uv or pip with hashes, with the package cache saved between runs. Then linting and formatting checks with Ruff, which replaces flake8, isort and black and is very fast. Then type checking with mypy or pyright, which matters in a dynamic language. Then tests with pytest, including coverage reporting and integration tests that use Testcontainers or service containers for Postgres or Redis.

Security checks come next: pip-audit for vulnerable packages, a secret scan, and bandit for risky code patterns.

Then the build. For a service, I build a Docker image with a multi-stage Dockerfile, installing dependencies in a builder stage and copying only what's needed into a slim runtime image, running as non-root. For a library, I build a wheel and publish it to an internal feed.

Finally, tag the image with the commit and version, scan it, push it, and deploy through the same promotion flow as other services.

For our Python RAG service with FastAPI and pgvector, the integration tests run against a real Postgres container with the pgvector extension, because mocking vector search wouldn't prove the queries actually work. The whole pipeline runs in a few minutes, mostly thanks to caching and Ruff's speed.

### cdx | How do you use pre-commit hooks with Husky or the pre-commit framework? | pre commit hooks, husky, lint-staged, pre-commit framework, git hooks, shift left checks
Git hooks are scripts that run at points like before a commit or before a push. Pre-commit hooks catch simple problems, like formatting, lint errors or committed secrets, before code ever reaches the pull request.

In JavaScript projects, Husky installs the hooks automatically when someone runs npm install, and lint-staged runs tools only on the files being committed, so it stays fast. A typical setup runs Prettier and ESLint on staged files and commitlint on the commit message.

In Python and many other stacks, the pre-commit framework manages hooks from a config file, with hooks for Ruff, trailing whitespace, large files and secret scanning with tools like gitleaks. It works for any language, so it's a good choice for repos mixing Python, YAML and Terraform.

In .NET, dotnet format can run in a hook, or with Husky.Net.

A few rules. Keep hooks fast, a few seconds, or people will skip them with the no-verify flag. Hooks are a convenience, not a control, because anyone can bypass them, so the pipeline must run the same checks. Don't run the full test suite in a pre-commit hook; at most, run quick tests in a pre-push hook.

In our front-end repos, Husky with lint-staged catches most formatting and lint issues locally, so pull request reviews focus on design rather than style comments. Secret scanning in the hook has stopped a few accidental commits of local configuration files before they left a laptop.
