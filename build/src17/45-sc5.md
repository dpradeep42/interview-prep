### scx | A query is fast in SSMS but slow when called from the application. Why? | fast in ssms slow in app, arithabort, slow from application fast in management studio, parameter sniffing app, different execution plans
This is a classic SQL Server puzzle, and the usual answer is that the two are getting different execution plans.

Why plans differ.

SET options: SSMS sets ARITHABORT ON by default, while ADO.NET connections use ARITHABORT OFF. Plans are cached per combination of SET options, so the application and SSMS use separate plans, even for the same query.

Parameter sniffing: the application's cached plan was compiled for parameter values that were unusual, like a site with very few rows, and the plan performs badly for typical values. In SSMS, you might test with literal values or a fresh compile, getting a good plan.

Parameter data types: the application sends nvarchar parameters for varchar columns, causing implicit conversions that prevent index seeks, while the SSMS test uses literals of the right type.

Local variables vs parameters: testing in SSMS with local variables gives estimates based on averages, which differs from how parameters are optimised.

### scx | Retries made an outage worse. What is a retry storm, and how do you prevent it? | retry storm, retries amplify outage, exponential backoff jitter, retry budget, thundering herd retries
A retry storm happens when a service starts failing or slowing down, and its callers respond by retrying, multiplying the traffic hitting the already struggling service. If each layer in a chain retries three times, a single user request can become dozens of calls at the bottom. The service can never recover, because the load keeps rising.

How it typically develops: the database slows down, API calls time out, the API's clients retry immediately, the gateway also retries, and the front end retries too. Load triples or worse at the worst possible time.

Prevention.

Exponential backoff with jitter: wait longer between each retry, with randomness, so retries spread out instead of arriving in synchronised waves.

Limit retries: few attempts, only for transient errors, and only for idempotent operations.

Retry at one layer: decide where retries happen, usually closest to the failing call, and don't stack them at every layer.

Retry budgets: allow retries only up to a percentage of normal traffic, like 10 percent, so retries can't multiply load.

Circuit breakers: after repeated failures, stop calling the failing service for a while and fail fast, giving it room to recover.

Respect Retry-After headers and 429 or 503 responses.

Timeouts that fit together: outer timeouts longer than inner ones, so callers don't give up and retry while the inner call is still running.

Load shedding on the server: reject excess requests quickly when overloaded, rather than queuing everything.

In .NET, Polly and the standard resilience handler in .NET 8 provide backoff with jitter, circuit breakers and timeouts, which I configure deliberately rather than leaving defaults on every client.

In .NET Framework apps on IIS: URL Rewrite rules that redirect to HTTPS must check the X-Forwarded-Proto header rather than the HTTPS server variable.

Other places to check: redirect rules on both the load balancer and the app doing conflicting things, like the load balancer redirecting HTTP to HTTPS and the app redirecting to a different host; authentication redirects using the wrong scheme for callback URLs, causing login loops; and cookies marked Secure not being sent when the app thinks the request is HTTP.

Alternatively, re-encrypt from the load balancer to the app with HTTPS end to end, which also satisfies stricter security requirements.
