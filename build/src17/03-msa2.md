### msa | How do you monitor and replay messages from a dead-letter queue? | dead letter queue, dlq strategy, poison message, failed messages queue, rabbitmq dead letter, sqs dlq
So a dead-letter queue is where messages go when they can't be processed, so one bad message doesn't block the queue or get retried forever.

First thing I do is separate the failure types. Transient failures, like a database timeout, get a few retries with backoff, ideally delayed redelivery so we're not hammering a dependency that's already struggling. Permanent failures, like a message with invalid data, what we call a poison message, go straight to the DLQ, because retrying won't help anyway.

In RabbitMQ, I set a dead-letter exchange on the queue, so rejected or expired messages get routed there. In SQS it's a redrive policy, the message moves to the DLQ after a max receive count, like five.

But see, a DLQ is useless if nobody looks at it. So I put an alarm when its depth goes above zero, and with each message I keep the original headers, the error reason and how many attempts happened. Then there's a clear process. Inspect, fix the bug or the data, and replay the messages back to the main queue with a tool or a script. Since our consumers are idempotent, replaying is safe.

In our CIRT platform, failed vendor messages land in a dead-letter queue with an alert, and the support team replays them once the fix is in. That's how we handle it day to day.

### msa | How do you handle out-of-order events in a consumer? | message ordering, ordered messages, kafka ordering partition key, fifo queue, out of order events, sequence number
Ordering across the whole system is really hard to guarantee, so first I ask, ordering of what? Mostly we only need ordering per entity, like all events for one shipment in order, not every event everywhere.

The standard way is partitioning by key. In Kafka, messages with the same key, say the shipment id, go to the same partition, and one consumer in the group reads that partition in order. In SQS FIFO, the message group id does the same job. In RabbitMQ, order holds within one queue with one consumer, but once you have multiple consumers or redeliveries, things can get reordered.

But ordering can still break, through retries, redeliveries, or producers sending from different instances. So I make consumers tolerant as well. Each event carries a version or sequence number for its entity, and the consumer just ignores anything older than what it already applied. Or the consumer re-reads the current state from the source instead of trusting the payload.

I also avoid designs that need ordering across different entities, because that kills parallelism.

In IQVIA's newer AWS services, shipment events on Kafka are keyed by shipment id, and consumers store the last version they applied. So a late, older event can't overwrite newer data. That one check saved us from some really confusing bugs.

### msa | How do you handle a downstream service that is completely down for an hour? | dependency down for an hour, downstream outage, service unavailable long time, graceful degradation, fallback when service down
For an hour-long outage, retries and circuit breakers alone won't cut it. You need to decide how the system behaves while that dependency is gone.

First thing, fail fast. The circuit breaker opens, so requests aren't sitting on timeouts and threads aren't piling up. Health checks and alerts tell the team quickly which dependency is down.

Then graceful degradation, and that depends on how important the dependency is. If it's just enrichment, like recommendations or some non-critical widget, I hide that part or return cached or default data, and the main feature keeps working. If the work can wait, I make it asynchronous. Accept the request, put it on a queue, show the user "accepted, processing", and process it when the dependency is back. The queue just absorbs the backlog.

If it's truly critical, like a payment or a safety check, I fail clearly with a helpful message. I won't do something unsafe or half-done just to look available.

When it comes back, I control the recovery. The backlog drains at a limited rate, so we don't flatten the service that's just recovering, and I check the DLQ and replay anything that failed.

In our IRT, if a depot's system is down, shipment requests queue up and site users see "pending", and we clear it when the depot recovers. So users aren't blocked, they just know it's in progress.

### msa | What is a sidecar and a service mesh? | sidecar pattern, service mesh, istio linkerd, envoy sidecar, what is service mesh, mtls service mesh
So a sidecar is a helper container that runs next to your main application container, in the same pod, sharing its network and lifecycle. It adds capabilities without touching the app code, like a logging agent, a proxy, or something that fetches secrets.

A service mesh basically takes that idea everywhere. It puts sidecar proxies, usually Envoy, next to every service, plus a control plane, and manages all service-to-service traffic. Tools are Istio, Linkerd, and historically AWS App Mesh. Since every call goes through the proxies, the mesh can give you, in one consistent way, mutual TLS between services, retries, timeouts, circuit breaking, traffic splitting for canary releases, and detailed metrics and tracing for every call. All configured centrally, no code in each service.

The upside is consistency across languages and teams, and strong zero-trust security with mTLS. The downside, honestly, is complexity. Extra latency and memory for every proxy, and a steep learning curve. Newer things like Istio's ambient mode reduce that per-pod sidecar overhead.

When would I go for it? When there are many services in different languages, and strict security or traffic-control needs. For a smaller set of .NET services, Polly, OpenTelemetry and a gateway usually give you enough, with a lot less to operate. I wouldn't add a mesh just because it's cool.

### msa | How do you choose the size of a microservice? | how big should microservice be, microservice size, too small microservices, nano services, granularity microservices
I don't measure size in lines of code. For me a service is the right size when it maps to one business capability, one team can own it, and most of the time it can be changed and deployed on its own.

How do I know it's too big? Several teams keep changing the same service. Deployments feel risky because unrelated features ship together. Or parts of it have very different scaling needs.

Too small, the nano-service problem, looks different. Almost every feature needs changes in several services. Services call each other constantly in long chains. You need sagas for things that should've been simple. And the operational overhead, pipelines, monitoring, on-call, is more than the benefit.

So I start from the domain, domain-driven design and bounded contexts, and I keep together things that change together and need strong consistency. If data has to be updated in one transaction, that's a strong hint it belongs in one service.

And honestly, it's fine to start a bit bigger and split later when there's a real reason, like independent scaling, a different release cadence or a separate team. Merging services back is much harder than splitting a clean module.

In our IRT, for example, inventory and shipments stay together, because kit allocation and the shipment request have to be consistent. Splitting them would just create a saga for no good reason.

### msa | What is an anti-corruption layer? | anti corruption layer, acl ddd, translate legacy model, adapter for legacy system, protect domain model
An anti-corruption layer is basically a translation layer between your domain and some external or legacy system, so their model doesn't leak into your code.

See, legacy systems and third-party APIs usually have confusing names, odd formats, magic codes, different concepts. If your new service uses all that directly, its model gets "corrupted" by it, and every change on their side ripples through your code.

So I put an adapter in between. My domain code only talks to an interface in my own language, like an IShipmentGateway with a CreateShipment method taking my own Shipment type. The implementation behind it calls the external system, maps my types to theirs and back, converts the codes, handles their error formats and retries. If the external system changes or gets replaced, only the adapter changes, nothing else.

It's really useful during a strangler migration, where new services have to live with an old system for a long time.

In our IRT modernisation, that's exactly what we did. The new .NET APIs talk to the legacy transaction engine through a translation layer. So the new code uses clean names and DTOs, and the old procedures and formats stay hidden behind it. And when parts of the legacy side get replaced, the new code doesn't change at all. That's the whole point.

### msa | How do you share code between microservices? | shared library microservices, nuget package shared code, code sharing microservices, common library, shared contracts
I'm quite careful here, because shared libraries can couple services just as badly as a shared database.

What I'm happy to share is technical, cross-cutting code. Logging and OpenTelemetry setup, a messaging wrapper, standard health checks, auth setup, error-handling middleware, maybe a result type. I publish these as versioned NuGet packages on a private feed, like Azure Artifacts or GitHub Packages, with semantic versioning. So each service upgrades when it's ready, nobody's forced to move all at once.

What I don't share is business logic and domain models. If two services share a domain library, a change for one forces a change and redeploy of the other, and you're back to monolith coupling. Honestly, a little duplication is better than the wrong coupling.

For contracts, like message schemas or API clients, I prefer generating them from one source, an OpenAPI spec, a protobuf file, or a schema registry, rather than hand-sharing DTO classes. That keeps each side independent and catches breaking changes early.

And shared libraries should stay small, well tested, backward compatible, with very few dependencies of their own.

In our CIRT platform, common logging and messaging helpers ship as internal NuGet packages from Azure DevOps Artifacts, while domain models stay inside each service. That balance has worked well for us.

### msa | What is the difference between a command and an event in messaging? | command vs event, events vs commands messaging, integration event, domain event, message types
Both are messages, but they mean different things, and that changes how I design them.

A command is a request to do something. It goes to one specific receiver that owns that action. It's named like an instruction, CreateShipment, SendEmail. The sender expects it to be handled, and the receiver can accept it or reject it. Usually it goes to a queue with one consumer.

An event is a statement that something already happened. Past tense, like ShipmentCreated or SubjectRandomised. The publisher doesn't know or care who's listening, could be zero, one or many subscribers. And you can't reject it, it's a fact. Events go to a topic or an exchange.

Why it matters is coupling. With commands, the sender depends on the receiver. With events, the publisher is independent of its subscribers, so you can add new consumers later without touching the publisher.

There's one more split, domain events versus integration events. Domain events are raised inside a service, between parts of its own domain. Integration events go outside to other services, they're part of the public contract, so we version them and keep them stable.

In our IRT, SubjectRandomised is an integration event, and both the notification and the reporting consumers listen to it. The randomisation side doesn't even know they exist.

### msa | What should an event contain: full data or just an id? | event payload design, fat event vs thin event, event carried state transfer, notification event, event schema design
Honestly, both styles are valid. It depends on the consumers.

A thin event, or notification event, has just the id and type, like "Shipment 123 changed". Consumers then call the owning service to get the current data. It's small and the data is always fresh. But every consumer calls back, which adds load and coupling, and if the owner is down, consumers are stuck.

A fat event, what's called event-carried state transfer, has the relevant data inside it, like the shipment's status, site, kit count, timestamps. Consumers have everything without calling back, so they're more independent and resilient, and the owner gets less load. The catch is bigger messages, more care when the schema changes, and the risk of putting sensitive data in there that not every consumer should see.

What I usually do is go somewhere in the middle. Include the data most consumers need, plus the id and a version number so they can ignore stale events. I don't include sensitive personal data unless every subscriber really needs it, especially in clinical systems where patient data has to be kept to a minimum.

And event schemas get versioned, with fields added in a backward-compatible way.

In IQVIA's newer AWS services, shipment events carry status, location and a version, so most consumers never need to call back. That's worked well for us.

### msa | How do you handle a long-running operation in an API? | long running request api, async request reply, 202 accepted, background job api, polling status endpoint, long running task web api
I don't keep the HTTP request open for minutes. It ties up resources, and you'll hit gateway and load balancer timeouts anyway, usually somewhere between 30 and 120 seconds.

What I do instead is the asynchronous request-reply pattern. The client sends the request, the API validates it, saves a job record, puts the work on a queue, and straight away returns 202 Accepted with a Location header pointing to a status endpoint, like jobs slash 123. A background worker picks up the job and keeps updating status and progress. The client polls that status endpoint, and gets pending, running, completed with a link to the result, or failed with the error. If you don't want polling, you can push a notification with SignalR or a webhook when it's done.

The worker has to be idempotent and able to resume, because it might crash halfway. For really big jobs, I split the work into chunks and track progress per chunk.

And I put an idempotency key on the submit request, so a double click doesn't start two jobs. That one bites people a lot.

This is actually how our study data transfer works. A transfer gets submitted, a worker moves the data in steps, and the UI shows the progress. [It took a transfer from around 40 minutes of manual steps to under 10 minutes, with clear status for the user.] So users stopped calling us to ask if it was still running.

### msa | What is backpressure, and how do you handle it? | backpressure, consumer slower than producer, queue growing, flow control, load shedding, bounded queue
Backpressure is basically the situation where a producer sends work faster than the consumer can handle it, and also what you do about it. If nothing controls it, queues grow without limit, memory runs out, latency goes crazy and the system can fall over.

I handle it in a few ways, depends on the system honestly. Buffering, a durable queue absorbs the spikes, which is fine if the consumer catches up later. But you have to monitor that queue, alerts on depth and on the age of the oldest message. Scaling consumers, autoscale the workers on queue depth, like KEDA on Kubernetes or ECS scaling on SQS backlog. Slowing down the producer, with bounded queues or channels, rate limits, or the consumer signalling to slow down. Like a bounded System.Threading.Channels channel just makes the writer wait when it's full. And load shedding, when you're overloaded, reject low-priority work quickly with a 429 or 503 instead of making everything slow.

In RabbitMQ, I set a prefetch count, so each consumer only takes a limited number of unacknowledged messages. That spreads the load and stops one consumer from hoarding work.

The main thing is to decide on purpose what happens under overload, instead of finding out in production.

In our CIRT notification consumers, prefetch limits plus a separate queue for bulk jobs keep the urgent emails flowing even during large imports. Before that, a big import could delay everything.

### msa | What is the difference between horizontal and vertical scaling? | horizontal vs vertical scaling, scale out vs scale up, stateless services scaling, autoscaling, scale microservices
Vertical scaling, or scaling up, is giving one machine more resources, more CPU, more memory, faster disks. It's simple and you don't change any code. But there's a ceiling, it gets expensive fast, resizing often needs downtime, and it's still one machine, so still a single point of failure.

Horizontal scaling, scaling out, means adding more instances of the service behind a load balancer. There's almost no ceiling, you get redundancy, and it fits cloud autoscaling nicely, add instances when load goes up, remove them when it drops, which saves money.

But see, horizontal scaling needs the service to be stateless. No in-memory session or cache that other instances depend on, no local files that need sharing, no assumption that one instance handles all requests for a user. State goes to a shared store like Redis or a database, files go to blob storage, and background jobs need a lock or a queue so they don't run twice.

Databases are the tricky part. Relational databases usually scale up first, then you add read replicas, caching, and sometimes sharding.

In our on-premise CIRT, we actually use both. The web tier scales out across load-balanced IIS servers, with Redis for the shared cache. And each study's SQL Server database scales up. So it depends on the layer.

### msa | How do you make a background job run only once when you have multiple instances? | distributed lock, run job once multiple instances, scheduled job multiple servers, leader election, quartz clustering, hangfire
So when a service runs on several instances, each one runs the same scheduled jobs. A nightly job could easily run three times. Honestly there are different ways to stop that.

One is a distributed lock. Before running, each instance tries to grab a lock in a shared store, like a Redis key with SET NX and an expiry, a SQL Server application lock, or a DynamoDB conditional write. Only whoever gets it runs the job. The expiry is important, otherwise a crashed instance holds the lock forever.

Another is a clustered scheduler. Quartz.NET in clustered mode, or Hangfire, keep the job state in a shared database and make sure each trigger fires on only one node.

Or a separate worker. Take the scheduled jobs out of the web service and put them in one dedicated worker with a single instance. Or use the platform's scheduler, like EventBridge Scheduler or a Kubernetes CronJob, to start exactly one task.

And on top of any of these, I make the job itself idempotent. So even if it somehow runs twice, it doesn't send duplicate emails or process the same data twice, like by recording what it already handled.

In our CIRT platform, AlertWatchDog runs on Quartz, and the jobs are designed to be safe if a run overlaps or repeats. Honestly, the idempotency part is what really saves you.

### msa | How do you handle partial failure when calling several services in parallel? | partial failure, parallel calls failure, task whenall error handling, fan out fan in, aggregate results partial
When I call several services in parallel, like with Task.WhenAll, some will succeed and some might fail. So I decide up front what partial success means for that feature.

First I classify each dependency, is it required or optional? If a required call fails, the whole operation fails with a clear error. If an optional one fails, like recommendations or some secondary widget, I return the rest with that section empty, plus a flag or warning, so the UI can say "some information is unavailable".

On the technical side, each call gets its own timeout and resilience policy, so one slow service doesn't hold up the whole response. One gotcha with Task.WhenAll, if any task throws, awaiting it rethrows only the first exception. I also set an overall deadline for the whole aggregate request, and cancel whatever's still running with a CancellationToken once it's hit.

For writes it's more serious, because partial failure leaves inconsistent data. There I'd rather use a saga or a queue than parallel calls.

On our IRT dashboard, if the shipment summary call fails, the page still loads subject and inventory data and just shows a small warning on that panel. Users can still do their work.

### msa | What is the twelve-factor app methodology? | twelve factor app, 12 factor app, cloud native principles, 12 factor, stateless processes config in environment
So twelve-factor is a set of principles for building cloud-friendly services that are easy to deploy and scale. Let me go through the ones I actually use every day.

One codebase per app, in version control, deployed to many environments. Dependencies declared explicitly, like NuGet or npm packages, never assumed to be on the server. ASP.NET Core on containers fits all this pretty naturally.
