### msa | How do you make sure an API is backward compatible when you add a field? | backward compatibility api, tolerant reader, adding fields to api, breaking change detection, openapi diff
Adding a new optional field to a response is normally safe, but only if the clients are tolerant readers, meaning they ignore fields they don't recognise. Most JSON clients do that by default. But some strict deserialisers or generated clients can fail on unknown properties, so I actually check how the important clients are built.

On the request side, a new field has to be optional with a sensible default, so old clients that don't send it behave exactly as before. If you make a new field required, that's a breaking change, no way around it.

And there are things that look small but break clients. Renaming a field, changing its type like number to string, removing enum values, changing date formats, changing default sorting or pagination, or changing what an existing value means. Even adding a new enum value can break a client that has a strict switch statement, so I document that enums may grow.

To catch this automatically, I generate the OpenAPI spec during the build and compare it with the previous version using a diff tool like oasdiff, and the build fails on breaking changes. Contract tests with Pact add the consumer's point of view on top.

For events it's the same rules. I treat the event schema as a published contract, just like the API. That's my approach.

### msa | What is the difference between stateful and stateless services? | stateful vs stateless, stateless service, sticky sessions, session state microservices, why stateless
A stateless service doesn't keep any client-specific data in its own memory between requests. Every request carries what it needs, like a token, and anything that has to last goes to a shared backing service, a database, Redis, blob storage. So any instance can handle any request, you can add or remove instances freely, and if one crashes nothing important is lost. That's what makes horizontal scaling, rolling deployments and autoscaling easy.

A stateful service keeps state locally. In-memory sessions, a local cache that has to stay consistent, uploaded files on local disk, WebSocket connections. Then a user has to keep hitting the same instance, so you need sticky sessions, and restarting or scaling an instance loses or moves that state. Load balancing also gets harder.

Some things are just naturally stateful, like databases, brokers, SignalR connections. Those need special handling, StatefulSets in Kubernetes, managed services, or a backplane, like Redis for SignalR, so messages reach users on whichever instance they're connected to.

So my rule is, keep application services stateless and push state into managed, purpose-built stores.

In our CIRT web tier, we moved session data and cache into Redis, so the load balancer can send any request to any IIS server without sticky sessions. That made deployments a lot calmer.

### msa | What is chaos engineering? | chaos engineering, chaos monkey, fault injection, resilience testing, aws fault injection service, game day
Chaos engineering is deliberately breaking things in your system, in a controlled way, to find the weak spots before they cause a real outage. The thinking is, systems will fail anyway, so better we learn how they fail on our own schedule, not at 2 AM.

It works like a scientific experiment. You define the steady state, what normal looks like in metrics, like error rate and latency. Then a hypothesis, say "if one instance of the shipment service dies, users won't notice". Then you inject the failure, kill instances, add network latency, make a dependency return errors, fill a disk, take down an availability zone. And you watch whether the steady state holds. Start with a small blast radius, have a clear way to stop the experiment, and grow it gradually.

Tools, there's AWS Fault Injection Service, Azure Chaos Studio, Chaos Mesh for Kubernetes, and in .NET, Polly's chaos strategies, which can inject faults and latency into HttpClient calls in test environments.

Teams also run game days, where everyone practises an incident scenario together. That tests the people and the runbooks too, not only the system.

But honestly, it's only worth it once the basics are there, monitoring, alerts, resilience patterns. Otherwise you're just breaking things without learning much.

### msa | How do you do zero-downtime database changes with microservices? | zero downtime database migration, expand contract pattern, backward compatible schema change, rolling deployment database, parallel change
So during a rolling or blue-green deployment, old and new versions of the service run at the same time against the same database. That means every schema change has to work with both. The way I do it is expand and contract, some people call it parallel change.

Expand first. Add new things without removing old ones. New column as nullable, or a new table. Deploy code that writes to both old and new, but still reads from the old. Backfill existing data in batches, so we don't lock big tables.

Then migrate. Deploy code that reads from the new column, and verify everything's fine in production.

Then contract. Only when no running version uses the old column, stop writing to it, and drop it in a later release.

So a column rename turns into add, copy, switch, remove, across a few deployments, instead of one risky rename.

A few other rules I follow. Never make a column required in the same release that starts filling it. Create indexes online on large tables, where the edition supports it. Keep migrations small and reversible.

With EF Core, I generate SQL migration scripts, review them, and apply them in the pipeline before the new code goes out. In our CIRT platform, the SSDT database projects follow the same idea, since hundreds of study databases have to be updated. So we're quite strict about it.

### msa | What is multi-tenancy, and what are the ways to isolate tenant data? | multi tenancy, multi tenant architecture, tenant isolation, database per tenant, shared schema tenant id, row level security
Multi-tenancy means one application serves many customers, tenants, while keeping each tenant's data separate and secure.

There are three main ways to isolate the data. Database per tenant, each tenant gets its own database. Strongest isolation, easy per-tenant backup, restore and deletion, and you can tune performance per tenant. But it costs more, and schema changes have to roll out to many databases. Schema per tenant, one database with separate schemas, kind of a middle ground. And a shared database with a tenant id column on every table. Cheapest and simplest to run at scale, but every query has to filter by tenant, and one mistake leaks data.

If it's the shared model, I enforce isolation in the platform, I don't just trust every developer to remember. EF Core global query filters on tenant id, SQL Server row-level security as a second layer, and tests that actually try to read across tenants.

The tenant gets resolved from the token or the host name early in the request, and stored in a scoped tenant context that the data layer uses.

Noisy neighbours are the other worry, one big tenant shouldn't slow everyone else, so per-tenant rate limits and monitoring.

Our IRT uses database per study. In clinical trials, sponsor data separation and audit requirements make strong isolation worth the cost. So for us it was an easy decision.

### msa | How do you handle time zones and dates across services? | time zones microservices, utc dates, datetimeoffset, date handling distributed systems, store dates in utc
Time zones cause so many subtle bugs. So I keep one simple rule, store and transfer instants in UTC, and convert to local time only at the edges, for display, or for business rules that really depend on local time.

In .NET, I use DateTimeOffset or UTC DateTime for timestamps, never DateTime.Now in server code. And I inject a TimeProvider, which came in .NET 8, so both code and tests can control the clock. APIs use ISO 8601 with an explicit offset, ending with Z for UTC, so there's no ambiguity at all.

But some values aren't instants, and people miss this. A date of birth or a visit date is a calendar date. So I use DateOnly, not midnight UTC, otherwise it can shift by a day when converted. A recurring local time, like "send at 9 AM site time", needs the IANA time zone id stored, like Asia/Kolkata, and conversion with daylight saving rules. And with daylight saving, some local times happen twice or not at all, so scheduling code has to handle that.

Servers and containers should run in UTC too.

In our IRT, sites in many countries see dates in their own time zone, while everything's stored in UTC. [A visit window bug at US sites came from a midnight conversion, and we fixed it by storing the date as a date.] That's one I won't forget.

### msa | How do you migrate a feature from the monolith to a new service without downtime? | extract service from monolith, migrate feature without downtime, monolith decomposition steps, carve out microservice
I'd do it step by step, so every step is small and I can roll it back.

To begin with, inside the monolith itself, I clean up the feature's boundary. Its code should depend on the rest only through an interface, and only its own code should touch its tables. Honestly, this refactoring alone takes out a lot of risk.

Then I build the new service with the same behaviour, its own API, its own database. Initially it can read data that's replicated or synced from the monolith.

Then I run both in parallel. Usually shadow traffic or parallel runs, requests still go to the old code, the new service gets called in the background, and I compare results and log the differences. Users aren't affected at all, and you catch logic differences safely.

After that I switch traffic gradually, behind a feature flag or at the routing layer. Start with a small group of users or tenants, watch errors, latency, data consistency. Rollback is just flipping the flag back.

Then the data ownership moves. The new service becomes the source of truth, and the monolith reads from it, through its API or events.

And only at the end, I delete the old code and tables.

This is pretty much how we're moving modules from the old MVC and Angular portal to the React shell, one module at a time. Drug accountability is the one in progress right now.

### msa | What is the difference between a domain event and an integration event? | domain event vs integration event, domain events ddd, mediatr notifications, internal vs external events
Both describe something that happened, but the scope and purpose are different.

A domain event is raised inside a service, inside its domain model, so other parts of the same service can react. Let me take an example. A kit's status changes to damaged, the Kit aggregate raises KitDamaged, and a handler in the same service updates the inventory count or writes an audit entry. These are in-process, often dispatched with MediatR notifications, usually in the same transaction or right after saving. And they can use rich internal types, because nobody outside ever sees them.

An integration event goes outside the service, through a broker, so other services can react. So KitDamaged might also become an integration event that reporting or the notification service consumes. Since it's a public contract between services, it uses simple, stable, versioned DTOs, carries only the data others need, and it's published reliably, ideally through the outbox, so it doesn't get lost if the broker is down.

The common flow is like this. Domain event gets raised, a handler converts it to an integration event, writes it to the outbox in the same transaction, and a publisher sends it later.

Why keep them separate? Because then internal refactoring doesn't break other services. You can change your domain model freely, and the contract stays the same.

### msa | How would you design a real-time dashboard that updates live? | real time dashboard design, live updates, signalr dashboard, websockets dashboard, push updates to browser
I'd push updates to the browser, instead of making it poll every few seconds.

The flow would be like this. When something changes, the owning service publishes an event. A dashboard service consumes these events, updates a small read model or some aggregate counters, like shipments by status, in Redis or a database, and pushes a change notification to the connected browsers.

For the push part, in .NET I'd use SignalR. It uses WebSockets and falls back to other transports automatically. Clients join groups, like a study or a site, so they only get relevant updates, and authorisation is checked when they join a group. With several server instances, you need a Redis backplane, or a managed service like Azure SignalR Service, so a message reaches clients on any instance. On AWS, API Gateway WebSocket APIs are an option.

On the client side, when the page loads, it gets the full current state through a normal API call, and then applies live updates on top. If the connection drops, it reconnects and reloads the state, so it never misses anything.

To avoid flooding the browser, I'd batch or throttle updates, maybe at most once a second per widget.

And honestly, if the dashboard is fine with a bit of delay, just polling every 30 seconds is simpler, and that's a perfectly valid choice too. I wouldn't over-engineer it.
