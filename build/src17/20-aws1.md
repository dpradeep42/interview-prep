### awsx | SQS standard vs FIFO queues: what is the difference? | sqs standard vs fifo, fifo queue, message group id, deduplication id, sqs ordering, sqs throughput
SQS has two queue types.

Standard queues offer nearly unlimited throughput, at-least-once delivery, which means a message can occasionally be delivered more than once, and best-effort ordering, so messages can arrive out of order. They're the default choice for most workloads, as long as consumers are idempotent and don't depend on order.

FIFO queues guarantee exactly-once processing within a deduplication window and strict ordering within a message group. Their names must end in .fifo. Each message has a message group id, like a shipment id: messages in the same group are delivered in order, one at a time, while different groups are processed in parallel. A deduplication id, or content-based deduplication, makes SQS drop duplicates sent within five minutes, which protects against producer retries.

The trade-offs of FIFO: lower throughput, 300 messages per second per API action without batching, 3,000 with batching, and much higher with high-throughput mode, which partitions by message group. And if one message in a group fails repeatedly, it blocks that group until it's handled or moves to the dead-letter queue.

So I use FIFO when order per entity really matters, like applying status changes for the same shipment in sequence, and standard queues everywhere else, with idempotent consumers and version checks to handle duplicates and reordering.

When a consumer receives a message from SQS, the message isn't deleted. It becomes invisible to other consumers for the visibility timeout, 30 seconds by default. That's how SQS guarantees messages aren't lost.

On a known transient failure, the consumer can set the visibility to a short value, so the message is retried sooner, or a longer one for backoff.

Combined with maxReceiveCount on a redrive policy, messages that keep failing go to the dead-letter queue instead of looping forever.

They're often confused, but they solve different problems.

The standby doesn't serve any traffic in the classic Multi-AZ instance deployment. In production, I'd always use Multi-AZ for important databases, and add read replicas only if read load or reporting requires them, with the application aware of replica lag.

### awsx | What causes DynamoDB throttling, and how do you fix hot partitions? | dynamodb throttling, hot partition, hot key dynamodb, provisionedthroughputexceeded, write sharding dynamodb, adaptive capacity
DynamoDB throttles requests when they exceed available capacity, returning ProvisionedThroughputExceededException or ThrottlingException. The SDKs retry automatically with backoff, so throttling first shows up as higher latency, then as errors.

There are two kinds of causes. Table-level: total traffic exceeds the provisioned capacity, or exceeds on-demand's instant scaling for a sudden huge spike. Fixes are raising capacity, adjusting auto scaling, or switching to on-demand.

Partition-level, which is more common and subtle: each partition supports roughly 3,000 reads and 1,000 writes per second. If a large share of traffic targets one partition key, like a single popular item, a status value like "PENDING" used as a partition key, or today's date as the key for all writes, that partition is overwhelmed while the rest of the table is idle. That's a hot partition. Adaptive capacity helps by shifting capacity to busy partitions and isolating frequently accessed items, but it can't exceed the per-partition limit.

Fixes for hot keys: choose a partition key with high cardinality and evenly distributed access, like a shipment id rather than a status; write sharding, adding a random or calculated suffix to the key, like date plus a number from 1 to 10, and querying all shards in parallel when reading; caching hot reads with DAX or ElastiCache; and batching or smoothing write bursts through a queue.

CloudWatch Contributor Insights for DynamoDB shows the most accessed keys, which pinpoints the hot partition quickly.

### awsx | What is DynamoDB TTL, and what are its gotchas? | dynamodb ttl, time to live dynamodb, expire items dynamodb, ttl attribute, automatic deletion dynamodb

### awsx | What are S3 versioning and Object Lock? | s3 versioning, s3 object lock, worm storage, s3 compliance mode, protect from deletion s3, mfa delete
S3 versioning keeps every version of an object in a bucket. When an object is overwritten, the old version is kept; when it's deleted, S3 adds a delete marker instead of removing the data, so the previous version can be restored. It protects against accidental overwrites and deletions, application bugs, and some ransomware scenarios. Once enabled, it can only be suspended, not removed. Old versions cost storage, so lifecycle rules expire noncurrent versions after a period. Versioning is also required for replication.

For regulated audit data or validated documents, compliance mode Object Lock provides strong evidence that records weren't altered, which supports data integrity requirements.

MFA Delete is another protection, requiring MFA to permanently delete versions or change versioning.

### awsx | How do you serve a static site or SPA securely with CloudFront and S3? | cloudfront s3, origin access control, cloudfront spa routing, static website aws, cdn caching cloudfront, s3 private bucket cloudfront
CloudFront is AWS's CDN. Serving a React or Angular build from S3 through CloudFront gives fast global delivery, HTTPS with a free ACM certificate, and caching at edge locations.

Security: the S3 bucket stays private, with Block Public Access on, and is not configured as a public website. CloudFront uses Origin Access Control to sign its requests to S3, and the bucket policy only allows the CloudFront distribution to read objects. So users can't bypass CloudFront to access the bucket directly.

SPA routing: deep links, like /shipments/123, don't exist as files in S3, so S3 returns 403 or 404. I configure CloudFront custom error responses to return index.html with a 200 status for those errors, or use a CloudFront Function to rewrite paths without file extensions to index.html, which is cleaner because real API 404s aren't masked.

Caching: hashed asset files, like main.abc123.js, get long cache times, with Cache-Control max-age of a year and immutable, while index.html gets no-cache, so users pick up new releases immediately. After deployment, I invalidate index.html if needed.

Extra protection: response headers policies add security headers like HSTS and a Content Security Policy; AWS WAF can be attached; and API calls can go through the same distribution under /api to an ALB or API Gateway origin, so the app and API share one domain without CORS.

### awsx | What routing policies does Route 53 support? | route 53 routing policies, weighted routing, latency routing, failover routing, geolocation routing, dns aws
Route 53 is AWS's DNS service, and its routing policies decide which answer to return for a DNS query.

Simple routing returns one record, or several values in random order, with no health checks per value.

Weighted routing splits traffic between records by weight, like 90 percent to the current version and 10 percent to a new one. It's useful for gradual migrations, canary releases at the DNS level, or A/B testing.

Latency-based routing sends users to the region with the lowest latency for them, for multi-region applications.

Failover routing has a primary and a secondary record. Route 53 health checks monitor the primary, and if it fails, DNS answers switch to the secondary, like a static maintenance site or a standby region. That's a building block of disaster recovery.

Geolocation routing answers based on the user's country or continent, for data residency, localised content or legal restrictions. Geoproximity routing is based on distance, with a bias to shift traffic between regions.

Multivalue answer routing returns several healthy records, a simple form of client-side load balancing with health checks.

IP-based routing uses the client's IP ranges.

Alias records are a Route 53 extension that point to AWS resources, like a load balancer, CloudFront or S3, at the zone apex, which a CNAME can't do, and they're free to query.

DNS changes are subject to caching by TTL, so for failover I keep TTLs short, like 60 seconds.

### awsx | What are VPC endpoints, and gateway vs interface endpoints? | vpc endpoints, gateway endpoint vs interface endpoint, privatelink, access s3 privately, nat gateway cost reduction
VPC endpoints let resources in private subnets reach AWS services without going over the internet, and without needing a NAT gateway. Traffic stays on the AWS network, which improves security and can significantly reduce NAT data processing costs.

There are two types.

Gateway endpoints are available only for S3 and DynamoDB. They're added as a target in the subnet route tables, so traffic to those services goes through the endpoint. They're free. Endpoint policies can restrict which buckets or tables can be accessed through them, and bucket policies can require access to come through a specific endpoint, which prevents data exfiltration to other accounts' buckets.

Interface endpoints, powered by PrivateLink, are available for most other AWS services, like Secrets Manager, SQS, ECR, CloudWatch Logs, STS, KMS and SSM, and for third-party and your own services. They create elastic network interfaces with private IP addresses in your subnets. With private DNS enabled, the normal service hostname resolves to these private IPs, so applications don't change anything. They're charged per hour per availability zone and per GB processed, and protected by security groups.

For example, ECS tasks in private subnets without internet access need interface endpoints for ECR, CloudWatch Logs and Secrets Manager, plus the S3 gateway endpoint for image layers, to pull images and start.

I always add the free gateway endpoints for S3 and DynamoDB, and interface endpoints where traffic is high or internet access isn't allowed.

### awsx | VPC peering vs Transit Gateway vs PrivateLink: how do you connect networks? | vpc peering vs transit gateway, privatelink, connect vpcs, hub and spoke network aws, cross account networking
These are different ways to connect VPCs and services.

VPC peering creates a direct, private connection between two VPCs, in the same or different accounts and regions. It's simple, has no bandwidth bottleneck, and no hourly charge, only data transfer. But it isn't transitive: if A peers with B and B with C, A can't reach C through B. With many VPCs, the number of peering connections grows quickly, becoming a mesh that's hard to manage. CIDR ranges can't overlap.

Transit Gateway is a regional hub that VPCs, VPN connections and Direct Connect gateways attach to. It routes between them, with route tables for segmentation, like keeping production and development apart while both reach shared services. It scales to thousands of VPCs and simplifies routing in a hub-and-spoke design, and can peer across regions. It costs per attachment per hour and per GB.

PrivateLink is different: instead of connecting whole networks, it exposes a specific service. A provider puts the service behind a Network Load Balancer and creates an endpoint service; consumers create interface endpoints in their VPCs. Traffic flows one way to that service only, and overlapping CIDRs don't matter. It's ideal for exposing a shared internal API to many teams or accounts, or consuming SaaS privately, with minimal network exposure.

In multi-account organisations, Transit Gateway for general connectivity plus PrivateLink for specific shared services is a common combination.

### awsx | Why use multiple AWS accounts, and what are Service Control Policies? | aws organizations, multi account strategy, service control policies, scp, control tower, landing zone
Using several AWS accounts, organised with AWS Organizations, is the recommended way to structure an AWS environment. An account is the strongest isolation boundary in AWS.

The benefits. Security isolation: a compromised credential or misconfiguration in a development account can't affect production. Blast radius: limits and quotas are per account, so one team's runaway process doesn't consume another's. Clear cost tracking per account, team or environment. Simpler permissions: instead of complex IAM conditions to separate environments in one account, each environment is its own account. And compliance: regulated workloads can live in tightly controlled accounts.

A typical structure has organisational units, like Security, with log archive and audit accounts; Infrastructure, with shared networking; Workloads, with separate dev, test and prod accounts per application; and Sandbox for experiments. AWS Control Tower sets up this landing zone with guardrails, account vending and centralised logging, and IAM Identity Center gives people single sign-on into accounts with role-based permission sets, instead of IAM users.

Service Control Policies are organisation-level guardrails. They define the maximum permissions available in an account or OU, applying even to administrators and the account's root user. They don't grant permissions; they limit them. Typical SCPs: deny leaving the organisation, deny disabling CloudTrail or GuardDuty, restrict which regions can be used, and deny creating resources without required tags.

Resource Control Policies, added in 2024, similarly limit permissions on resources.
