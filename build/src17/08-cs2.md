### csx | What are Native AOT and trimming in .NET? | native aot, ahead of time compilation, trimming, publish aot, startup time .net, aot limitations
Native AOT, ahead-of-time compilation, compiles a .NET app straight to native machine code at publish time, instead of shipping IL that the JIT compiles at runtime. What you get is a self-contained executable that doesn't even need the .NET runtime installed.

What you gain is very fast startup, often a few tens of milliseconds, lower memory, smaller deployments. That's honestly really valuable for serverless like AWS Lambda where cold starts matter, for containers that scale quickly, and for command-line tools.

### csx | What is tiered compilation and ReadyToRun in .NET? | tiered compilation, readytorun, jit compilation, dynamic pgo, startup performance .net, r2r
Both are about how .NET turns IL into machine code, basically balancing startup speed against peak performance.

The JIT compiles a method the first time it's called. With tiered compilation, it first compiles quickly with few optimisations, that's tier 0, so the app starts fast. Methods that get called a lot are recompiled in the background with full optimisations, tier 1. And long-running loops can switch to optimised code mid-execution, which is on-stack replacement.

Then there's dynamic PGO, profile-guided optimisation, on by default since .NET 8. While tier 0 code runs, the runtime collects data on how the code is actually used, like which types get passed to an interface call, and the tier 1 compile uses that to optimise. Like devirtualising and inlining the common case. Honestly, a lot of apps got a noticeable speed-up for free from this.

ReadyToRun is a publish option that pre-compiles IL to native code ahead of time, but keeps the IL too. The app starts faster because there's less JIT work at startup, and the JIT can still re-optimise hot methods later. The files are bigger though.

So for a service where startup matters, containers that scale often or Lambdas, I'd turn on ReadyToRun, or look at Native AOT. For long-running services, the defaults with tiered compilation and dynamic PGO work really well. I wouldn't touch them.

### csx | What is thread pool starvation, and how do you detect it? | thread pool starvation, threadpool starvation, sync over async, blocking calls async, slow requests low cpu
So thread pool starvation is when all the thread pool threads are busy, mostly just blocked and waiting, so new work, like incoming requests or async continuations, has to wait for a free thread. And the thread pool adds new threads slowly, roughly one or two a second once you're above the minimum. So under load, response times explode while CPU stays low. That low CPU is the giveaway.

The most common cause, honestly, is sync over async. Calling .Result, .Wait or GetAwaiter().GetResult on async code. The thread blocks waiting for an operation whose continuation also needs a thread pool thread, so under load all the threads end up waiting on each other. Other causes are long synchronous I/O, like a sync database or file call, Thread.Sleep, or long locks in hot paths.

What you see is requests getting very slow or timing out, the thread count climbing and climbing, and CPU not high at all. Health checks can time out too, so you get restarts on top.

To detect it, I use dotnet-counters and watch thread pool queue length and thread count. A growing queue is the signal. A memory dump, or dotnet-stack, shows lots of threads blocked in the same place, like waiting on a Task.

The real fix is making the call chain async all the way, removing blocking calls, and using async APIs for I/O. Raising the minimum threads only buys you time.

A race condition is a bug where the result depends on the timing of two or more operations running at the same time. So it works most of the time and fails once in a while, which makes it really hard to reproduce.

Classic example is check-then-act. Two requests try to reserve the last kit at a site. Both read the stock and see one available. Both pass the check. Both reserve it. Now we've allocated two kits when only one existed. Each request was correct on its own, the problem is just the interleaving.

Another one is a shared counter incremented by many threads without synchronisation, where updates get lost. Or a lazy cache that gets initialised twice.

They happen in memory and in databases. And with multiple server instances, an in-memory lock doesn't help at all, which people sometimes forget.

The fix depends on where the shared state lives. In memory, locks, Interlocked, or concurrent collections. In the database, make the check and the update one atomic operation, like an UPDATE with a WHERE condition on the available quantity and then check rows affected. Or optimistic concurrency with a row version, or a unique constraint so the second insert just fails. Across instances, a distributed lock, or a single queue consumer per key.

In our IRT, kit allocation uses database transactions and concurrency checks for exactly this reason. You really can't afford a double allocation there.
