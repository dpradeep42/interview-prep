### csx | What are expression trees, and where are they used? | expression trees, expression of func, linq expression, iqueryable expression tree, build dynamic query
An expression tree represents code as data. When a lambda is assigned to an Expression of Func type, instead of compiling it to executable code, the compiler builds an object tree describing it: a parameter, a member access, a comparison, a constant, and so on. Other code can then inspect that tree and translate it into something else.

That's exactly how LINQ providers work. When I write a Where clause on an EF Core IQueryable, the lambda becomes an expression tree, and EF Core walks the tree and translates it into SQL. With a plain IEnumerable, the same lambda is a compiled delegate and runs in memory. That's why some C# methods can't be used inside EF queries: the provider doesn't know how to translate them.

Other uses: building dynamic queries at runtime, like combining filters chosen by the user on a search screen, using Expression.AndAlso or a library like LinqKit's PredicateBuilder. Strongly typed property selectors, like in FluentValidation's RuleFor, or Moq's Setup, which read the property name from the expression. And generating fast code at runtime by compiling an expression into a delegate, which was a common way to avoid slow reflection.

Compiling expressions is relatively expensive, so compiled delegates should be cached.

### csx | Static class vs singleton pattern: which and when? | static class vs singleton, singleton pattern c#, thread safe singleton, static vs singleton di, lazy singleton
A static class can't be instantiated; all its members are static. It's fine for stateless helpers, like extension methods, simple calculations or constants.

A singleton is a normal class with exactly one instance. The classic implementation has a private constructor and a static Instance property, made thread-safe with Lazy of T or a static readonly field.

The singleton has real advantages over a static class. It can implement interfaces and be passed around as a dependency, so it can be mocked in tests. It can hold state that's initialised lazily. And it can inherit from a base class.

But in modern .NET, I almost never write the classic singleton pattern. Instead, I register a normal class in the DI container with AddSingleton. The container ensures there's one instance, while my class stays a plain, testable class with constructor injection, and consumers depend on an interface, not on a static Instance property.

Static classes and classic singletons both share a problem: they're global state, hidden dependencies that make testing and reasoning harder.

My rule: static for pure, stateless functions; DI singletons for shared services, like a cache, a configuration provider or an HttpClient wrapper. And any singleton must be thread-safe, because many requests use it at once.

### csx | What is the difference between decimal, double and float, and which do you use for money? | decimal vs double, money in c#, floating point precision, double rounding error, float vs double vs decimal
float and double are binary floating-point types: float is 32-bit with about 7 significant digits, and double is 64-bit with about 15 to 17. They're very fast, because CPUs support them in hardware, and they have a huge range. But they store numbers in base 2, so many decimal fractions, like 0.1, can't be represented exactly. That's why 0.1 plus 0.2 isn't exactly 0.3 in double, and small errors build up in repeated calculations.

decimal is a 128-bit decimal floating-point type, with 28 to 29 significant digits, which stores numbers in base 10. So 0.1 is exact. It's slower and has a smaller range, but it's precise for decimal values.

So for money, prices, quantities with fixed decimal places, and anything where exact decimal results and rounding matter, I use decimal. For scientific calculations, measurements, graphics or statistics, where tiny errors are acceptable and speed matters, double.

A few related points. Never compare doubles with double-equals; use a tolerance. Use Math.Round with an explicit MidpointRounding mode, because the default is banker's rounding. And in SQL Server, use decimal with a fixed precision and scale, not float, for money columns, and make sure EF Core maps the precision explicitly.

They all prevent changes, but in different ways.

A read-only collection, like ReadOnlyCollection or IReadOnlyList, is a read-only view over another collection. My code can't modify it through that view, but whoever owns the underlying List can still change it, and I'll see the changes. ### csx | What are default interface methods, and when are they useful? | default interface methods, default implementation interface, interface with method body, c# 8 interface
Since C# 8, interfaces can provide a default implementation for a member. Classes that implement the interface get that behaviour automatically, unless they provide their own.

The main reason this was added is evolving an interface without breaking existing implementations. Before, adding a new method to a published interface broke every class that implemented it, which is a real problem for libraries with many consumers. Now the library can add the method with a default body, and old implementations keep compiling.

It also allows some trait-like reuse, where small bits of shared behaviour are defined in terms of other interface members. For example, an ILogger-like interface could have a default LogError method that calls the core Log method with an error level.

There are some rules worth knowing. The default member is only accessible through the interface type, not through the class variable, unless the class implements it. Interfaces still can't have instance fields, so they can't hold state. And it can lead to diamond-inheritance ambiguities if two interfaces provide the same default, which must be resolved in the class.

I use them sparingly: mostly for API evolution in shared libraries. For sharing actual behaviour and state, an abstract base class or composition is usually clearer.

### csx | What are Native AOT and trimming in .NET? | native aot, ahead of time compilation, trimming, publish aot, startup time .net, aot limitations
Native AOT, ahead-of-time compilation, compiles a .NET application directly to native machine code at publish time, instead of shipping IL that the JIT compiles at runtime. The result is a self-contained executable that doesn't need the .NET runtime installed.

The benefits are very fast startup, often a few tens of milliseconds, lower memory use, and smaller deployments. That's valuable for serverless functions like AWS Lambda, where cold starts matter, for containers that scale quickly, and for command-line tools.

Trimming is part of it: the publish process analyses the app and removes unused code from the framework and libraries, to reduce size.

The limitations come from the fact that everything must be known at compile time. No runtime code generation, so no Reflection.Emit, and dynamic assembly loading isn't supported. Reflection over types that the trimmer can't see may break, so libraries must be AOT-compatible. Serialisation needs source-generated System.Text.Json contexts. And not everything supports it; for example, EF Core's AOT support is still limited, and some popular libraries rely on reflection.

ASP.NET Core supports AOT for minimal APIs with the slim builder, and the compiler shows warnings for anything incompatible.

I'd use it for Lambdas and small, focused services, and stay on the normal JIT for large apps with heavy reflection-based libraries.

### csx | What is tiered compilation and ReadyToRun in .NET? | tiered compilation, readytorun, jit compilation, dynamic pgo, startup performance .net, r2r
These are about how .NET turns IL into machine code, balancing startup speed and peak performance.

The JIT compiles methods the first time they're called. Tiered compilation means it first compiles quickly with few optimisations, tier 0, so the app starts fast. Methods that are called often get recompiled in the background with full optimisations, tier 1. Long-running loops can switch to optimised code mid-execution, which is on-stack replacement.

Dynamic PGO, profile-guided optimisation, is on by default since .NET 8. While running tier 0 code, the runtime collects data about how the code is actually used, like which types are passed to an interface call, and the tier 1 compile uses that to optimise, for example devirtualising and inlining the common case. This gave many apps a noticeable free speed-up.

ReadyToRun is a publish option that pre-compiles IL to native code ahead of time, while keeping the IL. The app starts faster, because less JIT work is needed at startup, and the JIT can still re-optimise hot methods later. The files are bigger.

So for a service where startup matters, like containers that scale often or Lambdas, I'd enable ReadyToRun, or consider Native AOT. For long-running services, the defaults with tiered compilation and dynamic PGO work very well.

### csx | What is thread pool starvation, and how do you detect it? | thread pool starvation, threadpool starvation, sync over async, blocking calls async, slow requests low cpu
Thread pool starvation happens when all thread pool threads are busy, usually blocked waiting, so new work, like incoming requests or async continuations, has to wait for a free thread. The thread pool adds new threads slowly, roughly one or two per second once it's above the minimum, so under load, response times explode while CPU stays low.

The most common cause is sync over async: calling .Result or .Wait or GetAwaiter().GetResult on async code. The thread blocks waiting for an operation whose continuation also needs a thread pool thread, so under load, threads are all blocked waiting for each other. Other causes are long synchronous I/O, like a synchronous database or file call, Thread.Sleep, or long locks in hot paths.

The symptoms: requests get very slow or time out, the thread count keeps climbing, and CPU isn't high. Health checks may time out too, causing restarts.

To detect it, I use dotnet-counters and watch the thread pool queue length and thread count; a growing queue is the signal. A memory dump or dotnet-stack shows many threads blocked in the same place, like waiting on a Task.

The fix is to make the call chain async all the way, remove blocking calls, and use async APIs for I/O. Raising the minimum threads is only a temporary relief.

### csx | How do you call async code from synchronous code safely? | sync over async, call async from sync, getawaiter getresult, task result deadlock, async in constructor
The best answer is to avoid it, by making the calling code async as well, all the way up. In ASP.NET Core, controllers, middleware, hosted services and even Main can be async, so there's almost always a way.

When I truly can't, for example in a legacy interface that I can't change, or a constructor, there are some options and risks.

Blocking with .Result, .Wait or GetAwaiter().GetResult works, but it blocks a thread. In apps with a synchronisation context, like classic ASP.NET on .NET Framework, WinForms or WPF, it can deadlock: the async method tries to resume on the context that's blocked waiting for it. ASP.NET Core has no synchronisation context, so it doesn't deadlock there, but blocking still wastes threads and can cause thread pool starvation under load. If I must block, GetAwaiter().GetResult is preferable to .Result, because it throws the original exception instead of an AggregateException, and in libraries, ConfigureAwait of false reduces deadlock risk.

For constructors, I avoid async work entirely. Instead I use an async factory method, like CreateAsync, or lazy async initialisation, or do the work in a hosted service at startup.

For event handlers in desktop apps, async void with try-catch is acceptable.

Our legacy .NET Framework code had a few of these deadlocks, so this is a real concern in our migration.

### csx | What is a race condition? Give an example. | race condition, race condition example, check then act, thread safety bug, concurrency bug
A race condition is a bug where the result depends on the timing of two or more operations that run concurrently, so it works most of the time and fails occasionally, which makes it hard to reproduce.

A classic example is check-then-act. Two requests try to reserve the last kit at a site. Both read the stock and see one available. Both pass the check. Both reserve it. Now we've allocated two kits when only one existed. Each request was correct on its own; the problem is the interleaving.

Another example is a shared counter incremented by many threads without synchronisation, where updates are lost, or a lazy cache initialised twice.

Race conditions happen both in memory and in databases, and with multiple server instances, an in-memory lock doesn't help at all.

Fixes depend on where the shared state lives. In memory: locks, Interlocked, or concurrent collections. In the database: make the check and update one atomic operation, like UPDATE with a WHERE condition on the available quantity and checking the rows affected, use optimistic concurrency with a row version, or a unique constraint so the second insert fails. Across instances: a distributed lock, or a single queue consumer per key.

In our IRT, kit allocation uses database transactions and concurrency checks for exactly this reason.

### csx | What is Lazy<T>, and how does it work? | lazy of t, lazy initialization, lazy thread safety mode, lazy loading object c#, deferred initialization
Lazy of T defers creating an object until it's first needed, and then caches it. I give it a factory function, and the first time I read its Value property, it runs the factory and stores the result. Later reads return the same instance without running the factory again.

It's useful when an object is expensive to create, like loading a large lookup table or building a complex client, and it may not be needed in every code path, so I don't pay the cost at startup or at all if unused.

It's also thread-safe by default. With the default mode, ExecutionAndPublication, if many threads read Value at the same time, only one runs the factory, and the others wait and get the same result. That makes it a simple way to implement a thread-safe singleton or a one-time initialisation, and it's the standard trick to make ConcurrentDictionary's GetOrAdd run the factory only once.

One gotcha: if the factory throws, Lazy caches the exception by default, and every later access rethrows it. That's bad for transient failures, like a network error at startup. In that case, I use the PublicationOnly mode, or a custom approach that retries.

For async initialisation, Lazy of Task of T works, though libraries like AsyncLazy handle retry and cancellation better.

### csx | throw vs throw ex: what is the difference? | throw vs throw ex, rethrow exception, preserve stack trace, exceptiondispatchinfo, wrap exception
Both rethrow an exception from a catch block, but they treat the stack trace differently.

throw, on its own, rethrows the current exception and preserves its original stack trace, so I can still see where the error really happened, deep in the call chain.

throw ex resets the stack trace to the current location, the catch block. All information about where the exception actually originated is lost, which makes debugging production issues much harder. Code analysis tools flag it as a warning.

So inside a catch block, if I want to log something and let the exception continue, I use plain throw.

If I want to add context, I wrap it: throw new ShipmentProcessingException with a useful message and the original exception as the inner exception. Then both the new context and the original stack trace are preserved.

If I need to rethrow an exception later, outside the catch block, for example after capturing it in one thread and rethrowing on another, ExceptionDispatchInfo.Capture and Throw preserve the original stack trace. That's what await does internally.

And often the best choice is not to catch at all. I only catch when I can handle the exception, add useful context, or translate it, and let global exception handling deal with the rest.

### csx | What are exception filters in C#? | exception filters, catch when, when keyword catch, filter exceptions c#, catch specific condition
Exception filters let me add a condition to a catch block using the when keyword, like catch HttpRequestException when ex.StatusCode equals NotFound. The catch block only runs if the condition is true; otherwise the exception keeps propagating as if that catch block didn't exist.

There are a few advantages over catching and then rethrowing inside an if statement.

The stack isn't unwound when the filter is evaluated. If the filter returns false, the exception continues with its original state intact, which makes debugging and crash dumps more useful.

The code is cleaner, especially with several catch blocks for the same exception type but different conditions, like handling a SqlException differently for a deadlock, error number 1205, versus a unique constraint violation, 2627 or 2601.

A neat trick is logging in a filter: catch Exception when LogAndReturnFalse of ex. The filter logs the exception at the point where it happened, with the full stack, and returns false, so the exception isn't actually caught and continues upwards.

Polly-style transient error checks also benefit, for example catching only specific HTTP status codes for a retry.

Filters should be quick and must not throw, because an exception inside a filter is swallowed and treated as false.
