### apix | What is SignalR, and how does it scale across multiple servers? | signalr, signalr scale out, redis backplane, azure signalr service, websockets asp.net core, real time asp.net core
SignalR is ASP.NET Core's library for real-time communication between server and clients. It lets the server push messages to browsers instantly, like notifications, live dashboards or progress updates, without the client polling.

It uses WebSockets when available, and falls back automatically to Server-Sent Events or long polling. I define a Hub class on the server with methods clients can call, and the server can call methods on clients: all clients, a specific user, or a group, like everyone viewing a particular study. The JavaScript and .NET clients handle connection and automatic reconnection.

Authentication works with the same JWT or cookie, though for WebSockets in browsers, the token is passed as a query string parameter, so I make sure it's not logged.

Scaling out is the tricky part. Each connection lives on one server. If server A wants to send a message to a user connected to server B, it can't, by itself. Solutions: a Redis backplane, where every server publishes messages through Redis pub-sub so all servers receive them; or a managed service, like Azure SignalR Service, which holds all the connections itself, so app servers don't. Sticky sessions are also needed for the fallback transports, unless WebSockets-only mode is used.

For AWS, API Gateway WebSocket APIs are an alternative, especially for serverless.

### apix | What are Server-Sent Events, and when would you use them instead of WebSockets? | server sent events, sse, sse vs websockets, eventsource, streaming updates http, typedresults serversentevents
Server-Sent Events is a simple standard for the server to push a stream of text events to the browser over a normal HTTP connection. The browser uses the EventSource API, which reconnects automatically and can resume from the last event id. The response has the text/event-stream content type, and the server writes events as they happen.

Compared with WebSockets: SSE is one-way, server to client only, while WebSockets are two-way. SSE runs over plain HTTP, so it works through most proxies, load balancers and firewalls without special configuration, and benefits from HTTP/2 multiplexing. It's text-only, and reconnection is built in.

So SSE fits well when the client mostly listens: live notifications, progress of a long-running job, a dashboard feed, or streaming an AI model's response token by token, which is exactly how many LLM APIs stream output. WebSockets are better for genuinely interactive two-way communication, like chat or collaborative editing, or binary data.

In ASP.NET Core, I can write SSE manually by setting the content type and flushing writes to the response, and .NET 10 adds TypedResults.ServerSentEvents, which takes an IAsyncEnumerable and streams it as events. SignalR can also use SSE as one of its transports.

One caution: the browser's EventSource can't set an Authorization header, so I use cookies or a fetch-based client.

### apix | What do HTTP/2 and HTTP/3 bring, and does Kestrel support them? | http2, http3, quic, kestrel http2, multiplexing, head of line blocking
HTTP/1.1 sends one request at a time per connection, so browsers open several connections and requests queue behind each other.

HTTP/2 multiplexes many requests and responses over a single TCP connection at the same time, as independent streams. It also compresses headers with HPACK, which saves a lot for APIs with large headers like tokens, and supports stream prioritisation. Fewer connections means less TLS handshaking. gRPC requires HTTP/2.

But HTTP/2 still runs over TCP, so if one packet is lost, all streams on that connection wait for the retransmission. That's TCP head-of-line blocking, and it hurts on unreliable networks, like mobile.

HTTP/3 runs over QUIC, which is built on UDP. Each stream is independent, so a lost packet only delays its own stream. QUIC also has faster connection setup, combining the transport and TLS 1.3 handshakes, and connection migration, so a phone switching from Wi-Fi to mobile data keeps its connection.

Kestrel supports both. HTTP/2 is enabled by default with TLS. HTTP/3 is supported since .NET 7, requiring TLS and the platform's QUIC library, and I configure the endpoint with HttpProtocols.Http1AndHttp2AndHttp3, and clients discover it through the Alt-Svc header.

In practice, the load balancer or CDN in front often handles HTTP/2 and HTTP/3 with clients, and talks to the app over HTTP/1.1 or HTTP/2.

### apix | How does session state work in ASP.NET Core, and should you use it? | session state asp.net core, addsession, distributed session, session vs cookie, isession
ASP.NET Core supports session state as an opt-in feature. I call AddSession with a distributed cache, and UseSession. The browser gets a cookie with a session id, and on the server, ISession stores small values, like strings or byte arrays, keyed by that id. Unlike classic ASP.NET, it doesn't store objects directly; I serialise them, often as JSON.

The storage is an IDistributedCache. The in-memory one only works on a single server. With multiple instances, I use Redis or SQL Server, so any instance can read the session.

Some important behaviours. The session is loaded on first access, and since session access in ASP.NET Core can be synchronous, I call LoadAsync first to avoid blocking. Session data isn't locked, so concurrent requests from the same user can overwrite each other's changes, which differs from the old ASP.NET behaviour. Sessions expire after an idle timeout. And the session cookie is marked essential, or it won't be set when the user hasn't consented to non-essential cookies under privacy settings.

Should I use it? For APIs, no; APIs should be stateless, with state in the client or the database. For server-rendered web apps, it's fine for small, temporary data, like a multi-step wizard, but not for authentication or anything important.

Our legacy MVC portal uses session state, which is one reason Redis was introduced for the load-balanced IIS servers.

### apix | How do you read the request body twice in ASP.NET Core? | read request body twice, enablebuffering, request body stream, body already read, middleware read body
By default, the request body is a forward-only stream. Once something reads it, like model binding or a middleware, it's consumed, and anything after that sees an empty body. That's a common problem when a middleware wants to log the body, or verify a webhook signature, and the controller also needs to bind it.

The solution is Request.EnableBuffering(). It makes the body seekable by buffering it, in memory for small bodies and in a temporary file for larger ones. After reading it, I reset the position to zero with Request.Body.Position equals 0, so the next reader starts from the beginning.

The typical middleware code is: call EnableBuffering, read the body asynchronously with a StreamReader with leaveOpen set to true, do what I need, like computing the HMAC signature, then reset the position, and call the next middleware.

A few cautions. Buffering large bodies uses memory or disk, so I only do it where needed, like specific webhook routes, and with a size limit. I read asynchronously, because synchronous I/O is disabled by default in Kestrel. And for very high throughput, the newer System.IO.Pipelines-based Request.BodyReader is more efficient.

For webhook signature checks, an alternative is binding the body as a raw string or byte array in the endpoint itself, verifying it, then deserialising manually.

### apix | Generic Host vs WebApplication: what is the difference? | generic host, webapplication builder, host createdefaultbuilder, hostapplicationbuilder, worker service host
The Generic Host is the .NET foundation for running any long-lived app: it provides dependency injection, configuration, logging, and the lifetime management for hosted services, with graceful startup and shutdown. It's used for console apps, worker services, and as the base of web apps. Historically, you created it with Host.CreateDefaultBuilder and a chain of callbacks, like ConfigureServices and ConfigureWebHostDefaults.

WebApplication, introduced in .NET 6 with minimal hosting, is a simpler, more direct API built on top of the Generic Host, specifically for web apps. WebApplication.CreateBuilder gives a builder with Services, Configuration, Logging and Environment as properties; I register services, call Build, then configure middleware and endpoints on the app, and Run. No Startup class, no nested callbacks. It still uses the Generic Host under the hood, so hosted services and everything else work.

For non-web apps, .NET 7 introduced Host.CreateApplicationBuilder, which gives the same simple linear style as WebApplication, but without the web server. The Worker Service template uses it.

So today: WebApplication.CreateBuilder for APIs and web apps, Host.CreateApplicationBuilder for workers and consumers, and the older callback style only in existing code. The concepts, like DI, configuration and hosted services, are identical across all of them.

### apix | What are good REST naming conventions for endpoints? | rest naming conventions, api url design, plural nouns api, nested resources url, resource naming, api endpoint naming
I follow a few simple conventions so the API is predictable.

Use nouns for resources, not verbs, because the HTTP method is the verb. So GET /shipments, POST /shipments, GET /shipments/{id}, not /getShipments or /createShipment.

Use plural nouns for collections, consistently: /sites, /kits, /subjects.

Use nesting for clear parent-child relationships, but only one level deep, like /sites/{siteId}/subjects. Deep nesting, like /studies/1/sites/2/subjects/3/visits/4, gets fragile; once a resource has its own id, it can be addressed directly, like /visits/4.

Use lowercase with hyphens for multi-word names, like /return-shipments, and keep JSON property names in camelCase.

Use query parameters for filtering, sorting and paging: /shipments?status=pending&sort=-createdAt&page=2.

For actions that don't map neatly to CRUD, like cancel or dispatch, there are two reasonable choices: model it as a state change, PATCH the status, or a sub-resource action, like POST /shipments/{id}/cancel. I prefer the second when the action has its own rules and side effects, because it's clearer and easier to authorise.

Version at the start of the path if using URL versioning, like /api/v1.

And above all, be consistent across the whole API, documented in the team's API guidelines.

### apix | How do you implement PATCH with JSON Patch or JSON Merge Patch? | json patch, json merge patch, patch partial update, jsonpatchdocument, partial update api
PATCH applies a partial update, changing only some fields of a resource. There are two common formats.

JSON Merge Patch, RFC 7396, sends a JSON object with just the fields to change, like status equals Cancelled. Fields that aren't included stay the same, and a field set to null is removed or cleared. It's simple and intuitive for clients. The limitation is that you can't distinguish "set to null" from some other intentions, and you can't update individual array elements; arrays are replaced entirely.

JSON Patch, RFC 6902, sends a list of operations: add, remove, replace, move, copy and test, each with a path, like op replace, path /status, value Cancelled. It's more powerful, it can modify array items and include test operations that act like preconditions, but it's more complex for clients.

In ASP.NET Core, JsonPatchDocument of T supports JSON Patch. Historically it needed Newtonsoft.Json, and .NET 10 added a System.Text.Json-based implementation. I apply the patch to a DTO, not directly to the EF entity, then validate the DTO, and map the allowed fields to the entity, to prevent over-posting through patch paths.

For merge patch, I deserialise into a DTO with nullable or optional wrapper properties, so I know which fields were actually sent.

In practice, for simple partial updates, I often prefer specific endpoints, like PUT status, which are easier to validate and authorise.

### apix | HttpContext.Items vs a scoped service: how do you share data within a request? | httpcontext items, share data per request, scoped service per request, request context data, per request state
Both let me share data between different parts of the pipeline during a single request, like a tenant id resolved in middleware and used in a controller and repository.

HttpContext.Items is a dictionary on the HttpContext, with object keys and object values, that lives only for the current request. It's built in and quick to use. But it's untyped, so values need casting, keys can clash between components unless I use private object keys, and it ties consumers to HttpContext, which isn't available in background work or easy to set up in unit tests.

A scoped service is a class registered with AddScoped, so DI creates one instance per request. A middleware gets it injected, through InvokeAsync parameters, and sets properties, like TenantContext.TenantId. Controllers, handlers and repositories inject the same instance and read it. It's strongly typed, discoverable, easy to fake in tests, and doesn't depend on HTTP, so the same TenantContext can be filled by a message consumer for background processing.

So I use a scoped service for anything important that business code depends on, like the current user, tenant or study context, and correlation data. HttpContext.Items is fine for small, internal, web-layer-only details, like passing something between two middlewares.

One reminder: scoped services must not be captured by singletons, or they'll leak across requests.

### apix | A POST request reaches the controller with a null body. How do you debug it? | null request body, model binding null, frombody null, 415 unsupported media type, json not binding asp.net core
This is a very common issue, and I check things in a fixed order.

First, the Content-Type header. If the client doesn't send application/json, ASP.NET Core can't use the JSON input formatter. With ApiController, that usually gives a 415 Unsupported Media Type, but in some setups, the parameter is just null.

Second, the JSON shape versus the DTO. If the JSON doesn't match, like a wrapping object the DTO doesn't expect, a string where a number is expected, or an invalid date format, deserialisation fails. With ApiController, that returns a 400 with details in the problem details response, so I look at that response body carefully. Third, property naming and casing. ASP.NET Core uses camelCase and case-insensitive matching by default, but custom JsonSerializerOptions may have changed that. Properties also need public setters or a matching constructor, and fields aren't bound by default.

Fourth, the binding source. A complex type in a controller with ApiController is inferred as FromBody, but without it, or for simple types, I may need FromBody explicitly. And only one parameter can be bound from the body.

Fifth, something read the body earlier, like a logging middleware without EnableBuffering.

To see what's happening, I log ModelState errors, test with a known-good request in an HTTP file or Postman, and enable debug logging for model binding.

### apix | How do you configure Kestrel limits for production? | kestrel limits, max request body size, kestrel configuration, connection limits, request header limits
Kestrel has sensible defaults, but for production I review a few limits, depending on whether Kestrel faces the internet directly or sits behind a reverse proxy.

MaxRequestBodySize defaults to about 30 MB. I lower it for normal APIs, so nobody can send huge bodies, and raise it only for specific upload endpoints with the RequestSizeLimit attribute, or DisableRequestSizeLimit for streaming uploads to storage. Form and multipart limits are separate, in FormOptions.

Request header limits, like MaxRequestHeadersTotalSize and MaxRequestLineSize, protect against oversized headers. Sometimes I need to raise them, for example when SSO cookies or large tokens make headers bigger, which is a known cause of 400 or 431 errors.

Timeouts: KeepAliveTimeout and RequestHeadersTimeout limit slow clients holding connections open, which helps against slowloris-style attacks. MinRequestBodyDataRate and MinResponseDataRate drop connections that send or read data too slowly.

Connection limits: MaxConcurrentConnections and MaxConcurrentUpgradedConnections, for WebSockets, can cap resource use per instance.

HTTP/2 settings, like max streams per connection, exist too.

I configure these in appsettings under the Kestrel section, or in code with ConfigureKestrel, and keep them consistent with the limits on the proxy or load balancer in front, otherwise the first one to reject a request gives a confusing error.
