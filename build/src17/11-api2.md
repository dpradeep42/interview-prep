So Server-Sent Events is a simple standard where the server pushes a stream of text events to the browser over a normal HTTP connection. ### apix | What do HTTP/2 and HTTP/3 bring, and does Kestrel support them? | http2, http3, quic, kestrel http2, multiplexing, head of line blocking
Let me start with HTTP/1.1. It sends one request at a time per connection, so browsers open several connections, and requests queue up behind each other.

HTTP/2 multiplexes lots of requests and responses over a single TCP connection at the same time, as independent streams. It also compresses headers with HPACK, which saves a lot for APIs with big headers like tokens, and supports stream prioritisation. Fewer connections means less TLS handshaking too. And gRPC needs HTTP/2.

But HTTP/2 still runs over TCP. So if one packet gets lost, all the streams on that connection wait for the retransmission. That's TCP head-of-line blocking, and it hurts on flaky networks, like mobile.

HTTP/3 runs over QUIC, which is built on UDP. Each stream is independent, so a lost packet only delays its own stream. QUIC also sets up connections faster, by combining the transport and TLS 1.3 handshakes, and has connection migration, so a phone switching from Wi-Fi to mobile data keeps its connection.

Kestrel supports both. HTTP/2 is on by default with TLS. HTTP/3 is supported since .NET 7, needs TLS and the platform's QUIC library, and you configure the endpoint with Http1AndHttp2AndHttp3. Clients discover it through the Alt-Svc header.

In practice though, the load balancer or CDN in front usually handles HTTP/2 and HTTP/3 with clients, and talks to the app over HTTP/1.1 or HTTP/2.

Well, by default the request body is a forward-only stream. Once something reads it, like model binding or some middleware, it's consumed, and anything after that just sees an empty body. You hit this when a middleware wants to log the body, or verify a webhook signature, and the controller also needs to bind it.

I always read async, because synchronous I/O is disabled by default in Kestrel anyway. And for really high throughput, the newer Pipelines-based Request.BodyReader is more efficient.

For webhook signature checks, another option is to bind the body as a raw string or byte array right in the endpoint, verify it, and then deserialise it yourself. Honestly, that's often simpler than the middleware route.

### apix | How do you implement PATCH with JSON Patch or JSON Merge Patch? | json patch, json merge patch, patch partial update, jsonpatchdocument, partial update api
Okay, so PATCH is for partial updates, changing just some fields of a resource. And there are two common formats.

JSON Merge Patch, RFC 7396, sends a JSON object with only the fields to change, like status Cancelled. Fields you don't include stay the same, and a field set to null gets removed or cleared. Simple and intuitive for clients. The limitation is you can't really tell "set to null" apart from other intentions, and you can't update individual array elements. Arrays get replaced entirely.

JSON Patch, RFC 6902, sends a list of operations, add, remove, replace, move, copy and test, each with a path. Like op replace, path slash status, value Cancelled. It's more powerful. It can change array items and include test operations that act like preconditions. But it's more complex for clients.

In ASP.NET Core, JsonPatchDocument of T supports JSON Patch. It used to need Newtonsoft.Json, and .NET 10 added a System.Text.Json-based version. What I do is apply the patch to a DTO, not directly to the EF entity, then validate the DTO, and map only the allowed fields onto the entity. That prevents over-posting through patch paths.

For merge patch, I deserialise into a DTO with nullable or optional wrapper properties, so I know which fields were actually sent.

Honestly though, for simple partial updates I often prefer specific endpoints, like PUT status, which are easier to validate and authorise.
