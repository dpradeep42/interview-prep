### obx | How do you set up OpenTelemetry in a .NET service? | opentelemetry dotnet setup, otel dotnet, addopentelemetry, otlp exporter, instrument aspnet core opentelemetry
OpenTelemetry is the vendor-neutral standard for traces, metrics and logs. In .NET, the runtime already produces the raw signals: Activity for traces, System.Diagnostics.Metrics for metrics, and ILogger for logs. OpenTelemetry collects and exports them.

Setup in Program.cs: builder.Services.AddOpenTelemetry(), then ConfigureResource to set the service name, version and environment, which every signal carries. WithTracing adds instrumentation for ASP.NET Core, HttpClient, SQL client or EF Core, plus any custom ActivitySource the app defines. Our newest services use OpenTelemetry with Datadog, while older parts log to Splunk with Serilog. Standardising on OpenTelemetry means changing the backend later is configuration, not code.

### obx | What does the OpenTelemetry Collector do, and why use one? | opentelemetry collector, otel collector, collector pipeline receivers processors exporters, agent vs gateway collector
The OpenTelemetry Collector is a separate process that receives telemetry, processes it, and exports it to one or more backends. Applications send to the collector over OTLP instead of talking to vendors directly.

Its configuration has pipelines for traces, metrics and logs, each built from receivers, processors and exporters. Receivers accept data: OTLP from apps, Prometheus scraping, host metrics, log files, Kafka and more. Processors transform it: batching for efficiency, memory limiting, adding resource attributes like cluster and region, filtering out noisy spans like health checks, redacting sensitive attributes, and tail-based sampling. Exporters send it on: to Datadog, Grafana, Jaeger, Prometheus, Azure Monitor, CloudWatch or several at once.

Why it's worth having. Applications stay simple and vendor-neutral; switching or adding a backend is a collector config change, not a redeploy of every service. Exports are offloaded: retries and buffering happen in the collector, so a backend outage doesn't slow the app. Central control: redaction, sampling and enrichment rules are applied consistently for all services. And credentials for the backend live in one place, not in every app.

Deployment patterns: an agent collector per host or as a sidecar or DaemonSet, close to apps, plus optionally a gateway collector cluster for central processing like tail sampling.

The collector itself must be monitored, since it's now part of the pipeline, and sized properly so it doesn't drop data under load.

### obx | Counter vs gauge vs histogram: which metric type do you use when? | metric types, counter gauge histogram, updowncounter, percentile metrics, system diagnostics metrics
Choosing the right metric type decides what questions you can answer later.

A counter only goes up: requests handled, orders created, errors, bytes sent. You never look at its raw value; you look at its rate, like requests per second, or increase over a window. Counters survive restarts in Prometheus-style systems because rate functions handle resets.

An up-down counter or gauge represents a current value that goes up and down. An up-down counter is for things you increment and decrement, like active connections or items in an in-memory queue. A gauge is observed at a point in time, like memory used, queue depth read from the broker, or temperature of a storage unit. For gauges, averages and maximums over time make sense; rates don't.

A histogram records the distribution of values, like request duration or payload size, into buckets. From it you can compute percentiles, like p95 and p99 latency, which matter much more than averages, because averages hide the slow requests real users notice. Histograms can also be aggregated across instances correctly, which pre-computed percentiles can't.

In .NET's System.Diagnostics.Metrics, these are Counter, UpDownCounter, ObservableGauge and Histogram. For example, an allocation service might have a counter for allocations by outcome, a histogram for allocation duration, and an observable gauge for available kits per depot.

Bucket boundaries for histograms should cover the expected range, or exponential histograms can be used to avoid choosing them by hand.

### obx | How do you add custom business metrics to a .NET service? | custom metrics dotnet, meter dotnet, business metrics, system.diagnostics.metrics, imeterfactory, instrument business events
Technical metrics, like CPU and request latency, tell you whether the system is running. Business metrics tell you whether it's doing its job: orders placed, patients randomised, shipments delivered, allocations failed due to no stock. Often a business metric drops before any technical alarm fires, like an integration silently sending nothing.

In .NET, I use System.Diagnostics.Metrics. Get a Meter from IMeterFactory through dependency injection, which makes it testable, and create instruments once: a Counter for randomisations, a Histogram for end-to-end shipment processing time, an ObservableGauge for kits available per depot computed from a cached query. ### obx | What are SLIs, SLOs and error budgets? | sli slo sla, error budget, service level objective, service level indicator, reliability targets
These come from site reliability engineering and give a precise way to talk about reliability.

An SLI, service level indicator, is a measurement of user experience, usually a ratio of good events to total events. For example: the percentage of API requests that succeed, the percentage served within 300 milliseconds, or the percentage of shipment events processed within five minutes.

An SLO, service level objective, is the target for an SLI over a window: 99.9 percent of requests succeed over 28 days, or 95 percent of requests complete within 300 milliseconds.

An SLA is a contract with customers, with consequences, like credits, if it's missed. SLOs should be stricter than SLAs, so you get warning before breaching a contract.

The error budget is what the SLO allows to fail: with 99.9 percent, that's 0.1 percent, roughly 43 minutes of full downtime in 30 days. It turns reliability into a shared, measurable resource. If the budget is healthy, the team can ship faster and take more risk. If it's being burned quickly, the team slows down releases and prioritises reliability work.

Alerting on SLOs uses burn rates: alert when the budget is being consumed much faster than sustainable, like 14 times the normal rate over an hour, which catches real user-facing problems while ignoring blips.

Choosing SLOs: base them on what users actually need, not 100 percent, which is impossible and makes every change risky.

### obx | What are the RED and USE methods for monitoring? | red method, use method, rate errors duration, utilization saturation errors, golden signals, what to monitor
They're two simple checklists for what to monitor, from different angles.

The RED method is for services, from the user's point of view. For every service or endpoint, track Rate, the number of requests per second; Errors, the number or percentage of failed requests; and Duration, the distribution of response times, as percentiles. If you have these three for every service, you can quickly see which service is unhappy and how. They map well to dashboards: one row per service with three panels.

The USE method is for resources, from the infrastructure's point of view. For every resource, like CPU, memory, disk, network, connection pools, thread pools and queues, track Utilisation, how busy it is as a percentage of time or capacity; Saturation, how much extra work is waiting, like the run queue, queue length or thread pool queue; and Errors, like disk errors or dropped packets. Saturation is the one people forget, and it's often the most telling: 70 percent CPU might be fine, but a growing thread pool queue is a real problem.

Google's four golden signals are similar: latency, traffic, errors and saturation.

How I use them together: RED tells me there's a problem, like the allocation API's p95 latency has tripled. USE on the resources behind it tells me why, like the database connection pool is saturated with requests waiting for connections.

### obx | What is high cardinality, and why does it blow up metrics cost? | high cardinality metrics, metric labels cardinality, time series explosion, metrics cost, label best practices
Every unique combination of a metric name and its label values is a separate time series. A request counter with labels for method, route and status code might produce a few hundred series, which is fine. Add a label for user id, and it becomes hundreds of thousands. That's high cardinality.

Why it's a problem. Metrics backends store and index each series separately, so memory, storage and query time grow with the number of series. Prometheus can run out of memory; commercial tools, like Datadog, bill per custom metric series, so a single careless label can create a huge bill overnight. Queries and dashboards slow down too.

Common culprits: user ids, email addresses, request ids, raw URLs with ids in the path instead of route templates, timestamps, exception messages, kit or order numbers, and pod names in very dynamic environments.

How I avoid it. Use bounded values for labels: route templates like /shipments/{id}, status code classes, region, outcome. Put high-cardinality detail in traces and logs instead, which are designed for per-request data and searchable by id. Set up review of new metrics and limits in the pipeline or collector, which can drop or rewrite labels. Monitor the number of series per metric to catch growth.

If you need per-entity analysis, like latency per customer, that's often better answered by querying logs or traces, or with an analytics store designed for high cardinality.

### obx | How do you choose log levels, and what belongs at each level? | log levels, when to log error vs warning, log level guidelines, information vs debug logging, too many logs
Consistent log levels make logs useful and keep costs down. My guidelines:

Critical or Fatal: the application or a key component can't continue, like failing to start because configuration is invalid, or losing the database entirely. Someone should be woken up.

Error: an operation failed and needs attention, like an unhandled exception in a request, a message moved to the dead-letter queue, or an integration call that failed after all retries. Each error log should be actionable; if nobody should do anything about it, it isn't an error.

Warning: something unexpected happened, but the system handled it, like a retry succeeded after a transient failure, a fallback was used, a slow query crossed a threshold, or a deprecated API was called. Warnings help spot trends before they become errors.

Information: significant business and lifecycle events: service started, shipment created, randomisation completed, a job processed 230 records. They tell the story of what the system did, without detail of every step.

Debug and Trace: detailed diagnostic data for developers, like intermediate values and branching decisions. Off in production by default, but switchable per category at runtime, so we can turn it on for one component during an investigation.

Other rules: log an exception once, at the place where it's handled, not at every layer; use structured properties, not string concatenation; never log secrets or personal data; and set per-namespace minimum levels to silence noisy libraries.

### obx | Head-based vs tail-based sampling: how do you sample traces? | trace sampling, head based sampling, tail based sampling, sampling rate opentelemetry, keep error traces
At high traffic, recording every trace is expensive in network, storage and money, and most successful traces look the same. Sampling keeps a representative subset.

Head-based sampling decides at the start of a trace, in the first service, usually as a percentage, like keep 10 percent. The decision is propagated in the trace context, so all downstream services keep or drop the same trace, and traces stay complete. It's simple, cheap and done in the SDK, with ParentBased and TraceIdRatioBased samplers in OpenTelemetry. The downside: the decision is made before you know whether the request will fail or be slow, so you drop 90 percent of your interesting error traces too.

Tail-based sampling decides after the trace has completed, typically in an OpenTelemetry Collector or the backend, which buffers all spans of a trace for a short time. Then rules decide: keep every trace with an error, keep every trace slower than one second, keep traces for specific important endpoints, and keep a small percentage of the rest. You get all the interesting traces and few boring ones. The cost: the collector must receive all spans and hold them in memory, and all spans of a trace must reach the same collector instance, which needs load balancing by trace id.

A common combination: no or light head sampling at the SDK, tail sampling in a collector gateway.

Metrics should be computed before sampling, so rates and error percentages stay accurate.

### obx | How does trace context propagate across HTTP calls and message queues? | trace context propagation, traceparent header, w3c trace context, propagate trace through rabbitmq, distributed tracing messages
Distributed tracing only works if every hop passes the trace context along, so each service's spans join the same trace.

The standard is W3C Trace Context. The traceparent header carries the trace id, the parent span id and sampling flags, and tracestate carries vendor-specific data. Baggage, a separate header, carries application key-value pairs, like tenant id, that should travel with the request, used carefully because it's sent everywhere.

For HTTP, .NET does it automatically: HttpClient instrumentation adds traceparent to outgoing requests, and ASP.NET Core reads it on incoming requests, creating a child Activity. Most other languages' OpenTelemetry instrumentations do the same, which is what makes mixed .NET and Java systems traceable end to end.

For messaging, it's more manual and more often broken. The producer must inject the trace context into message headers or application properties, and the consumer must extract it and start its processing span with a link or as a child. Some client libraries have instrumentation that does this, like for Kafka, Azure Service Bus, MassTransit and NServiceBus; for raw RabbitMQ clients, I add small helpers using OpenTelemetry's propagator API to inject and extract. For batch consumers, span links connect one processing span to the many producer spans.

Where context is lost, like a legacy system in the middle or a file transfer, I carry a correlation id in the payload and log it, so the pieces can still be joined.

### obx | How do you reduce alert fatigue? | alert fatigue, too many alerts, noisy alerts, actionable alerts, on call burnout, alert tuning
Alert fatigue happens when people receive so many alerts, mostly unimportant or false, that they start ignoring them, and then miss the real one. It's a reliability risk and a morale problem.

How I reduce it.

Every page must be actionable and urgent. If the response is "wait and see" or "nothing to do", it shouldn't wake anyone. Those become tickets, dashboard items or daily digests.

### obx | What are exemplars, and how do they connect metrics to traces? | exemplars, metrics to traces, exemplar prometheus, link metric spike to trace, grafana exemplars

### obx | What is Prometheus, and how do you write basic PromQL queries? | prometheus, promql, prometheus scraping, rate function promql, histogram_quantile, prometheus basics
Prometheus is an open-source monitoring system and time-series database. It pulls metrics by scraping HTTP endpoints, usually /metrics, on each target at an interval, like every 15 seconds. In Kubernetes, it discovers targets automatically through service discovery and annotations or ServiceMonitor resources. .NET apps expose metrics through the OpenTelemetry Prometheus exporter, or push via OTLP to Prometheus versions that accept it.

Data is time series identified by a metric name and labels, like http_server_request_duration_seconds with method, route and status code.

Basic PromQL patterns I use often.

Request rate: sum by (route) of rate of http_server_request_duration_seconds_count over a 5-minute range. rate computes per-second increase of a counter over the window.

Error percentage: the rate of requests with status code 5xx divided by the rate of all requests, times 100.

Latency percentile: histogram_quantile(0.95, sum by (le, route) (rate of http_server_request_duration_seconds_bucket over 5 minutes)). The le label holds histogram bucket boundaries.

Saturation, like memory used versus limit per pod, with division between two metrics matched on labels.

Alerting rules use the same expressions with a for duration, evaluated by Prometheus and routed through Alertmanager, which groups, silences and routes notifications.

For long-term storage and multiple clusters, Prometheus is often combined with Thanos, Mimir or a managed service, like Amazon Managed Service for Prometheus or Azure Monitor managed Prometheus, with Grafana on top.

### obx | How do you control the cost of logging and observability? | logging cost, observability cost, reduce log volume, log retention, datadog bill, log sampling

### obx | How do you monitor message queues and consumers? | monitor message queue, consumer lag, queue depth alert, age of oldest message, rabbitmq monitoring, kafka lag monitoring

In our platform, RabbitMQ queues and their retry and dead-letter exchanges are monitored this way, and Grafana dashboards show depth and age per queue next to the consumers' error rates.

### obx | How do you run a blameless post-incident review? | postmortem, blameless postmortem, post incident review, root cause analysis, incident retrospective, five whys
A post-incident review turns an outage into improvements. Blameless means we assume everyone acted reasonably with the information they had, and focus on how the system, processes and tools allowed the problem, not on who made a mistake. If people fear blame, they hide details, and you learn nothing.

How I run one.

Gather facts first: a timeline built from alerts, logs, chat messages and deployment records, covering when it started, when it was detected, by whom, the actions taken, and when it was resolved. Include the impact: which users, how long, and any data affected.

Analyse contributing factors, not a single root cause. Usually several things combined: a code change with an edge case, a missing test, an alert that didn't fire, a runbook that was outdated, a manual step under pressure. Techniques like the five whys help, applied to each factor. Ask what went well too, like fast rollback.

Look at detection and response, not just the trigger: why did it take 40 minutes to notice? Why did diagnosis take long?

Agree on action items, each with an owner and a date, prioritised by impact: a test, an alert, an automated safety check, a design change. Few, well-chosen actions that actually get done beat a long wish list.

Share the write-up widely, because other teams learn from it, and track action items to completion.

In our regulated context, the review also feeds the formal deviation or CAPA process when an incident affects validated functionality.

### obx | How do you instrument a new feature before releasing it? | observability driven development, instrument new feature, telemetry for new feature, release monitoring plan, measure feature health
I treat observability as part of the feature's definition of done, not an afterthought added after the first incident.

Before writing code, I ask: how will we know this feature works in production, and how will we know when it doesn't? That gives a short list of signals.

Logs: information-level logs for key business events in the feature, with structured fields like study, site and outcome, and clear error logs with context when it fails. No personal data.

Metrics: a counter for the feature's main operations by outcome, a histogram for its duration, and a business metric if it has one, like the number of returns processed in the new DARM flow.

Traces: custom spans around important internal steps, like calculating an allocation or calling an external system, with useful attributes, so slow requests show where time goes.

Dashboards and alerts: a panel or a small dashboard for the feature, and alerts if failure rates exceed a threshold or the expected events stop happening.

Release plan: if the feature is behind a flag, I compare the signals for flag on and flag off, and check them right after rollout to each environment and each batch of users. If the numbers look wrong, the flag goes off.

Testing the telemetry: in integration tests or with FakeLogger and metric collectors, I check that important metrics and logs are actually emitted, because silently missing telemetry is discovered at the worst moment.

### obx | What is continuous profiling, and when does it help? | continuous profiling, production profiler, cpu profiling production, pyroscope, datadog profiler, flame graph cpu
Traces tell you which request and which span was slow, but not which line of code inside a service burned the CPU or allocated all the memory. Continuous profiling fills that gap.

A profiler runs inside the application in production, all the time, with low overhead, typically a few percent, by sampling stack traces many times per second. It records where CPU time goes, which methods allocate memory, where threads wait on locks, and exceptions thrown. Data is aggregated over time and shown as flame graphs, filterable by service, version, endpoint and host.

Tools: Datadog Continuous Profiler, which supports .NET, Grafana Pyroscope, Azure's Application Insights Profiler, Amazon CodeGuru Profiler for some runtimes, and the OpenTelemetry profiling signal, which is maturing.

When it helps most. CPU is high but no endpoint looks especially slow: the profile shows the hot method, like JSON serialisation of a huge object, a regex compiled per call, or a LINQ query re-evaluated in a loop. Memory and GC pressure: allocation profiles show what's allocating, like large strings or lists built per request. Comparing versions: diffing profiles before and after a deployment shows exactly what got more expensive. Cost optimisation: shaving the top hot spots reduces instance counts.

Compared with taking a one-off trace with dotnet-trace, continuous profiling already has the data from when the problem happened, which matters for issues that are intermittent or can't be reproduced.

Profiles can contain method names and arguments' types but should never contain data values.
