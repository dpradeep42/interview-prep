### obx | What does the OpenTelemetry Collector do, and why use one? | opentelemetry collector, otel collector, collector pipeline receivers processors exporters, agent vs gateway collector
So the Collector is a separate process. It receives telemetry, processes it, and exports it to one or more backends. The apps just send to the collector over OTLP instead of talking to each vendor directly.

The config is pipelines for traces, metrics and logs, and each pipeline has receivers, processors and exporters. Receivers take data in, OTLP from apps, Prometheus scraping, host metrics, log files, Kafka and so on. Processors change it, so batching, memory limits, adding attributes like cluster and region, dropping noisy spans like health checks, redacting sensitive attributes, tail-based sampling. Exporters send it out to Datadog, Grafana, Jaeger, Prometheus, Azure Monitor, CloudWatch, or several of them at once.

And the backend credentials live in one place instead of in every app.

For deployment, you usually have an agent collector close to the apps, per host, as a sidecar or a DaemonSet, and optionally a gateway collector cluster for central stuff like tail sampling.

One catch, the collector is now part of your pipeline, so you have to monitor it and size it properly, otherwise it drops data right when load is highest.

### obx | Counter vs gauge vs histogram: which metric type do you use when? | metric types, counter gauge histogram, updowncounter, percentile metrics, system diagnostics metrics
Picking the right type actually matters, because it decides what questions you can answer later.

A counter only goes up. Requests handled, orders created, errors, bytes sent. You never really look at the raw number, you look at the rate, like requests per second, or the increase over a window. And in Prometheus-style systems restarts are fine, because the rate functions handle resets.

Then a gauge or up-down counter is a current value that goes up and down. Up-down counter is for things you increment and decrement yourself, like active connections or items in an in-memory queue. A gauge is something you observe at a point in time, like memory used, queue depth read from the broker, or the temperature of a storage unit. For gauges you look at averages and max over time. Rates don't make sense there.

A histogram records the distribution, like request duration or payload size, into buckets. From that you get percentiles, p95, p99 latency, which matter way more than averages, because the average hides the slow requests users actually notice. Histograms also aggregate across instances correctly, which pre-computed percentiles can't do.

In .NET's System.Diagnostics.Metrics these are Counter, UpDownCounter, ObservableGauge and Histogram. So say an allocation service, I'd have a counter for allocations by outcome, a histogram for allocation duration, and an observable gauge for available kits per depot.

Just make sure the histogram buckets cover the expected range, or use exponential histograms so you don't have to pick them by hand.

### obx | What are SLIs, SLOs and error budgets? | sli slo sla, error budget, service level objective, service level indicator, reliability targets
Okay, these come from site reliability engineering, and they basically give you a precise way to talk about reliability instead of just saying "it should be up".

An SLI, service level indicator, is a measurement of what users experience, usually good events divided by total events. Like the percentage of API calls that succeed, or the percentage served within 300 milliseconds, or the percentage of shipment events processed within five minutes.

An SLO is the target for that SLI over a window. So 99.9 percent of requests succeed over 28 days, or 95 percent finish within 300 milliseconds.

An SLA is the contract with the customer, with consequences like credits if you miss it. Your SLOs should be stricter than the SLA, so you get a warning before you breach the contract.

The error budget is what the SLO allows to fail. With 99.9 percent that's 0.1 percent, roughly 43 minutes of full downtime in 30 days. What I like is it turns reliability into a shared thing you can measure. If there's plenty of budget left, the team can ship faster and take more risk. If it's burning fast, you slow down releases and do reliability work.

For alerting you use burn rates. You alert when the budget's being used much faster than it should, say 14 times the normal rate over an hour. That catches real user-facing problems and ignores small blips.

And pick SLOs based on what users actually need. Not 100 percent, that's impossible and makes every change scary.

### obx | What are the RED and USE methods for monitoring? | red method, use method, rate errors duration, utilization saturation errors, golden signals, what to monitor
See, they're two simple checklists for what to monitor, just from different angles.

RED is for services, from the user's point of view. For every service or endpoint you track Rate, requests per second, Errors, the count or percentage of failed requests, and Duration, the response times as percentiles. If you have those for every service, you can see very quickly which one is unhappy and how. It maps nicely to dashboards too, one row per service with three panels.

USE is for resources, from the infrastructure side. For every resource, CPU, memory, disk, network, connection pools, thread pools, queues, you track Utilisation, how busy it is, Saturation, how much work is waiting, like the run queue or the thread pool queue, and Errors, like disk errors or dropped packets. Saturation is the one people forget, and honestly it's often the most telling. 70 percent CPU might be totally fine, but a growing thread pool queue is a real problem.

Google's four golden signals are pretty similar, latency, traffic, errors and saturation.

How I use them together is RED tells me there's a problem, like the allocation API's p95 latency has tripled. Then USE on the resources behind it tells me why, like the database connection pool is saturated and requests are sitting there waiting for a connection. So one finds the symptom and the other one finds the cause.

### obx | What is high cardinality, and why does it blow up metrics cost? | high cardinality metrics, metric labels cardinality, time series explosion, metrics cost, label best practices
Actually it's simple once you know that every unique combination of metric name and label values is its own time series. A request counter with method, route and status code labels might give you a few hundred series, that's fine. Add a user id label and suddenly it's hundreds of thousands. That's high cardinality.

Why it hurts: the backend stores and indexes each series separately, so memory, storage and query time all grow with the series count. Prometheus can just run out of memory. Commercial tools like Datadog charge per custom metric series, so one careless label can create a huge bill overnight. And dashboards get slow.

The usual culprits are user ids, emails, request ids, raw URLs with ids in the path instead of the route template, timestamps, exception messages, kit or order numbers, and pod names in very dynamic setups.

What I do is keep labels to bounded values. Route templates like shipments slash id in braces, status code classes, region, outcome. The high-cardinality detail goes into traces and logs, which are built for per-request data and you can search them by id. New metrics get reviewed, and the pipeline or collector can drop or rewrite labels. I also watch the number of series per metric so growth gets caught early.

And if someone really needs per-entity analysis, like latency per customer, that's usually better answered from logs or traces, or an analytics store that's designed for high cardinality.

### obx | How do you choose log levels, and what belongs at each level? | log levels, when to log error vs warning, log level guidelines, information vs debug logging, too many logs
Honestly, if levels aren't consistent, logs become noise and cost a lot. So here's roughly how I use them.

Critical or Fatal is when the app or a key component can't continue. Like it fails to start because config is invalid, or the database is completely gone. Someone should get woken up.

Error is an operation failed and needs attention. An unhandled exception in a request, a message going to the dead-letter queue, an integration call that failed after all the retries. My rule is every error log should be actionable. If nobody needs to do anything, it's not an error.

Warning is something unexpected but handled. A retry worked after a transient failure, a fallback kicked in, a slow query crossed a threshold, a deprecated API got called. Warnings help you spot trends before they turn into errors.

Information is the important business and lifecycle events. Service started, shipment created, randomisation completed, a job processed 230 records. They tell the story of what happened without every little step.

And a few other things. Log an exception once, where it's handled, not at every layer. Use structured properties, not string concatenation. Never log secrets or personal data. And set minimum levels per namespace to quiet the noisy libraries.

### obx | Head-based vs tail-based sampling: how do you sample traces? | trace sampling, head based sampling, tail based sampling, sampling rate opentelemetry, keep error traces
So at high traffic, recording every single trace costs a lot in network, storage and money, and most successful traces look exactly the same anyway. Sampling keeps a representative subset.

Head-based sampling decides at the start of the trace, in the first service, usually as a percentage, like keep 10 percent. That decision travels in the trace context, so every downstream service keeps or drops the same trace and traces stay complete. It's simple and cheap and done in the SDK, with the ParentBased and TraceIdRatioBased samplers in OpenTelemetry. The problem is it decides before you know whether the request will fail or be slow, so you also throw away 90 percent of your interesting error traces.

Tail-based sampling decides after the trace is complete, usually in an OpenTelemetry Collector or in the backend, which buffers all the spans for a short time. Then rules decide. Keep every trace with an error, keep everything slower than a second, keep traces for important endpoints, and a small percentage of the rest. You get all the interesting ones and only a few boring ones. What you pay for it is the collector has to receive every span and hold them in memory, and all spans of one trace must land on the same collector instance, so you need load balancing by trace id.

What I'd go with usually is little or no head sampling in the SDK and tail sampling in a collector gateway. One thing, compute metrics before sampling, so your rates and error percentages stay accurate.

What not to do, like never purge a queue that has unprocessed clinical events. And when and how to escalate. Keep it short and specific, next to the code or in a wiki the team actually updates after incidents.

Over time the steps people repeat become automation, a button or script that does the safe mitigation and logs it. So humans decide and tools execute.

For the rotation, usually weekly, with a primary and a secondary, clear escalation to subject matter experts and managers, and a handover at the end of each shift covering open issues. And there's a limit on load. If someone's getting paged every night, the system needs fixing, not a tougher engineer. Severity routing makes sure only urgent, user-impacting stuff pages.

After incidents we do a blameless review, and the action items often improve the alerts and runbooks. And in a regulated environment, anything you do on production during on-call is a controlled change too, recorded with who did what and why.

### obx | How do you run a blameless post-incident review? | postmortem, blameless postmortem, post incident review, root cause analysis, incident retrospective, five whys
Honestly, the whole point is to turn an outage into improvements. Blameless means we assume everyone acted reasonably with what they knew at the time, and we look at how the system, process and tools let it happen, not who messed up. If people are scared of blame, they hide details and you learn nothing.

How I run one. Facts first. I build a timeline from alerts, logs, chat messages and deployment records. When it started, when it was detected and by whom, what actions were taken, when it got resolved. Plus the impact, which users, how long, and whether any data was affected.

Then the contributing factors, not one single root cause. It's usually a few things together, a code change with an edge case, a missing test, an alert that didn't fire, an outdated runbook, a manual step done under pressure. Five whys helps, applied to each factor. And I ask what went well too, like a fast rollback.

I also look at detection and response, not just the trigger. Why did it take 40 minutes to notice? Why was diagnosis slow?

Then action items, each with an owner and a date, ordered by impact. A test, an alert, an automated safety check, maybe a design change. A few good actions that actually get done beat a long wish list.

The write-up gets shared widely, other teams learn from it, and we track the actions until they're closed. In our regulated context it also feeds the formal deviation or CAPA process when validated functionality was affected.

### obx | How do you instrument a new feature before releasing it? | observability driven development, instrument new feature, telemetry for new feature, release monitoring plan, measure feature health
So I treat observability as part of the feature's definition of done. Not something you bolt on after the first incident.

Before I write code I ask two questions. How will we know this works in production, and how will we know when it doesn't? That gives me a short list of signals.

Logs, information level for the key business events in the feature, with structured fields like study, site and outcome, and clear error logs with context when it fails. No personal data, obviously.

Metrics, a counter for the main operations by outcome, a histogram for duration, and a business metric if there is one, like the number of returns processed in the new DARM flow.

Traces, custom spans around the important internal steps, like calculating an allocation or calling an external system, with useful attributes, so a slow request shows you where the time went.

Then a panel or small dashboard for the feature, and alerts if the failure rate crosses a threshold or the expected events just stop.

For the release, if it's behind a flag, I compare the signals with flag on and flag off, and check them right after rollout to each environment and each batch of users. If the numbers look wrong, the flag goes off.

And I test the telemetry itself. In integration tests, or with FakeLogger and metric collectors, I check the important logs and metrics actually get emitted. I learned that the hard way, missing telemetry always gets discovered at the worst possible moment.

### obx | What is continuous profiling, and when does it help? | continuous profiling, production profiler, cpu profiling production, pyroscope, datadog profiler, flame graph cpu
Let me explain where it fits. Traces tell you which request and which span was slow, but not which line of code inside the service burned the CPU or allocated all that memory. Continuous profiling covers that.

A profiler runs inside the app in production, all the time, with low overhead, usually a few percent, by sampling stack traces many times a second. It records where CPU time goes, which methods allocate, where threads wait on locks, which exceptions get thrown. It's aggregated over time and shown as flame graphs you can filter by service, version, endpoint and host.

Tools would be Datadog Continuous Profiler, which supports .NET, Grafana Pyroscope, the Application Insights Profiler on Azure, Amazon CodeGuru Profiler for some runtimes, and the OpenTelemetry profiling signal, which is still maturing.

Where it helps most is when CPU is high but no endpoint looks especially slow. The profile shows the hot method, like JSON serialising a huge object, a regex getting compiled on every call, or a LINQ query re-evaluated inside a loop. Memory and GC pressure, the allocation profile tells you what's allocating, large strings or lists built per request. Comparing versions, you diff profiles before and after a deployment and see exactly what got more expensive. And cost, fixing the top hot spots can reduce instance counts.

Compared with a one-off dotnet-trace, the big thing is the data's already there from when the problem happened, which matters a lot for intermittent issues you can't reproduce. Profiles can have method names and types, but never actual data values.
