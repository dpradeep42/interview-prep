### msa | What is the inbox pattern for processing each message only once? | inbox pattern, inbox table, processed messages table, duplicate message handling, at least once delivery consumer
Most brokers, RabbitMQ, SQS, Service Bus, deliver messages at least once. A consumer might get the same message twice after a timeout, a lost acknowledgement or a redelivery. And if processing has side effects, like reserving stock or sending an email, duplicates do real damage.

The inbox pattern makes the consumer idempotent. Every message carries a unique message id. The consumer has an inbox table, or processed messages table, keyed by that id. When a message arrives, in one database transaction the consumer inserts the message id into the inbox and does its business changes. If the insert fails because the id already exists, the message was already processed, so the consumer just acknowledges it and does nothing else. Because both happen in one transaction, you can't end up with the change done but not recorded, or recorded but not done.

It pairs naturally with the outbox pattern on the producer side. The outbox guarantees the message gets published, and the inbox guarantees it's processed once.

Details to handle, clean old inbox rows after a retention period longer than any possible redelivery. And for side effects outside the database, like calling an external API, pass an idempotency key so the other system can deduplicate too.

Libraries like MassTransit and NServiceBus include inbox and outbox support. In our RabbitMQ consumers, a processed message table per database made retries from the dead-letter flow safe, because replaying a message twice simply has no effect the second time. That's pretty much the whole point.

### msa | How do you implement a distributed lock, and when should you avoid one? | distributed lock, redis lock, redlock, sql application lock, sp_getapplock, lease lock, fencing token
A distributed lock makes sure only one instance across many servers does something at a time, like running a scheduled job, refreshing a shared token or processing one customer's batch.

Common ways to do it. Redis with SET using NX and an expiry, where the value's a unique token so only the owner can release it. SQL Server's sp_getapplock, which is simple if you already have a database and is released automatically with the session or transaction. Blob leases in Azure Storage. DynamoDB conditional writes. Or ZooKeeper and etcd for stronger guarantees. Libraries like DistributedLock for .NET wrap several of these.

The hard part is that locks expire. If the holder pauses, say a long garbage collection or a network delay, its lock can expire while it still thinks it owns it, and a second instance starts the same work. The fix is a fencing token, an increasing number issued with each lock, which the protected resource checks, rejecting writes with an older token. Redis-based locks can't fully guarantee safety without that.

So honestly, I avoid distributed locks where I can. Often a better design exists. A database unique constraint, optimistic concurrency with a row version, partitioning work so each key always goes to one consumer, a single active consumer queue, or a scheduler with built-in clustering, like Quartz.NET with a clustered job store.

When I do use one, I treat it as an efficiency mechanism, preventing duplicate work, and make the work itself idempotent, so a rare double run is still safe.

### msa | Should microservices share common libraries, and what should go in them? | shared libraries microservices, common nuget package, shared code between services, chassis library, coupling through shared library
Sharing code across services saves duplication, but a shared library is also a kind of coupling. If every service has to upgrade together whenever it changes, you've basically built a distributed monolith through a NuGet or npm package.

What's good to share is technical, cross-cutting plumbing that rarely changes. Logging and OpenTelemetry setup, standard health checks, authentication configuration, a resilient HTTP client setup, error response formats, and messaging conventions. People often call this a service chassis, and it makes services consistent.

What shouldn't be shared is domain logic and domain models. If two services share a customer entity class, a change for one forces a change in the other, and the service boundaries stop meaning anything. Each service should own its models. For contracts between services, share schemas or generated clients, versioned carefully, not internal classes.

Practices that keep sharing healthy. Version libraries with semantic versioning and keep breaking changes rare. Don't force simultaneous upgrades, services should be able to lag behind for a while. Keep packages small and focused, rather than one giant common package. Avoid heavy transitive dependencies that dictate framework versions. And have a clear owner who reviews changes.

In our front-end work, shared npm packages on the Azure DevOps feed hold the design system, API client and auth helpers for the React shell and sub-apps. They're versioned independently, and a sub-app can stay on an older version until its team's ready, which avoids coordinated big-bang upgrades.

### msa | How does request-reply over a message broker work? | request reply messaging, rpc over rabbitmq, reply queue, correlation id messaging, async request response
Sometimes you want the decoupling of a broker but you still need an answer, like asking a pricing service to calculate a quote. Request-reply over messaging does that.

The requester sends a message to the service's request queue with two extra properties. A reply-to address, which is a queue where it listens for answers, and a correlation id that's unique to the request. The responder processes the message and sends the result to the reply-to queue with the same correlation id. The requester matches the reply to the waiting request by that correlation id.

The reply queue can be one temporary exclusive queue per requester instance, or RabbitMQ's direct reply-to feature, which avoids creating queues. In Azure Service Bus, sessions are often used, with the session id matching the request.

Important points. Always set a timeout, because a reply might never arrive. Messages can be delivered twice, so the responder should be idempotent. If the requesting instance restarts, pending replies are lost, so this suits short, interactive requests, not long processes.

And honestly, I'd always ask whether you really need it. If the caller blocks waiting for the reply, you get the latency of the broker and most of the coupling of a direct call. For real-time answers, a direct HTTP or gRPC call is usually simpler. Request-reply over a broker makes sense when the responder has to sit behind the broker, for load levelling or network reasons, or when the reply can be processed asynchronously, like an event updating status later.

### msa | What is the competing consumers pattern? | competing consumers, multiple consumers one queue, scale message processing, work queue pattern, prefetch count
Competing consumers means several instances of a consumer read from the same queue, and each message goes to only one of them. It's the standard way to scale background processing: if the queue is growing, add more consumers.

The broker handles distribution. RabbitMQ delivers messages round-robin to consumers on the same queue, limited by each consumer's prefetch count. SQS hands messages to whichever poller asks, hiding them for the visibility timeout. Service Bus uses peek-lock with similar behaviour, and in Kubernetes, KEDA can scale consumer pods based on queue length.

It brings a few consequences. Order isn't guaranteed, because two consumers process messages in parallel, so if order matters per entity, you need partitioning, like Service Bus sessions, SQS FIFO message groups or a consistent hash exchange, so all messages for one key go to one consumer. Messages can be redelivered if a consumer crashes, so processing must be idempotent. Poison messages that always fail need a retry limit and a dead-letter queue, or they block a consumer forever.

Prefetch needs tuning. A high prefetch is efficient for fast, small messages but can leave one busy consumer holding many messages while others sit idle; for slow messages, a prefetch of one or a few spreads work fairly.

Our notification and data processing workers use this pattern on RabbitMQ, with multiple worker instances per queue, a low prefetch for heavy messages, and retry with a dead-letter exchange, so scaling is just adding instances.

### msa | What is the claim check pattern for large messages? | claim check pattern, large message payload, store payload in blob, message size limit, reference message
Message brokers have size limits, like 256 kilobytes for SQS and Service Bus standard, and even where they allow larger messages, big payloads slow down the broker and use expensive memory. The claim check pattern avoids putting large data in the message.

The producer stores the large payload in external storage, such as S3, Azure Blob Storage or a database table, and sends a small message containing a reference, the claim check, like the object key, plus useful metadata such as type, size and a hash. The consumer reads the message, fetches the payload using the reference and processes it.

Things to get right. Write the payload before sending the message, so the consumer never gets a reference to something missing. Decide who deletes the payload: a lifecycle rule that expires objects after a few days is simpler than tracking when every consumer has finished. Secure the storage, since the payload may contain sensitive data, using encryption and access limited to the producer and consumers, or short-lived presigned URLs. Include a checksum so the consumer can verify the content.

The Amazon SQS extended client library does this automatically for Java and Python, and similar helpers exist for other SDKs.

A natural example is file processing: an uploaded file lands in storage, and a message with its location triggers the import job. In our data transfer flows, large extracts are written to storage and only the reference and metadata travel through the queue, which keeps the broker fast and messages easy to inspect.

### msa | How do you propagate timeouts and deadlines across a chain of service calls? | deadline propagation, timeout budget, cascading timeouts, grpc deadline, request timeout across services
When service A calls B, which calls C, each with its own timeout, the timeouts often don't add up. If A gives up after two seconds but B waits five seconds for C, B and C keep working on a request nobody is waiting for, wasting capacity exactly when the system is under stress.

Deadline propagation fixes this by passing the remaining time budget down the chain. The edge sets a deadline for the whole request, and each service uses whatever is left, minus a small margin, as the timeout for its own downstream calls. If little time remains, it fails fast instead of starting work that can't finish.

gRPC has this built in: the client sets a deadline, it travels in the request metadata, and the server's cancellation token fires when it expires. With HTTP, you can pass a custom header with the deadline or remaining milliseconds and convert it into a cancellation token.

In .NET, the important part is honouring cancellation: pass the request's cancellation token through to database queries and HTTP calls, so work actually stops. Combining it with a timeout using a linked cancellation token source keeps the code simple.

Some general rules: timeouts should get shorter as you go deeper in the chain; retries must fit inside the remaining budget, or they make things worse; and queued messages should carry an expiry, so a consumer doesn't process a request that's already stale.

This is one of those details that turns a small slowdown into a full outage if ignored, because abandoned work keeps piling up.

### msa | How do you invalidate caches across services when data changes? | distributed cache invalidation, cache invalidation events, redis pub sub invalidation, stale cache microservices, cache across instances
When several instances or services cache the same data, a change in one place must reach all the caches, or users see stale data. There are a few approaches, each with trade-offs.

The simplest is short expiry times. Data is allowed to be stale for a known period, like sixty seconds, and no invalidation is needed. For a lot of reference data, that's good enough.

Event-based invalidation is the next level. The service that owns the data publishes an event when it changes, like product updated, and every service that caches it removes or refreshes that entry. With a message broker, each instance needs its own subscription, not a shared queue, or only one instance hears the event. Redis pub/sub or keyspace notifications work well for in-memory caches across instances.

A shared distributed cache like Redis avoids the problem for instance-local copies, because all instances read the same entry, and the owner updates or deletes it on change. A two-level cache, with memory in front of Redis, still needs invalidation messages for the memory level. HybridCache in .NET 9 supports this layering with tag-based invalidation.

Version stamps are another option: include a version in the cache key, and bump the version when data changes, so old entries are simply never read again.

Always keep expiry as a safety net, since invalidation messages can be lost. In our IIS web farm, configuration data is cached in memory per node, with Redis pub/sub invalidation messages and a short expiry as a backup, which keeps all nodes consistent within seconds.

### msa | What is the tolerant reader pattern? | tolerant reader, robustness principle, ignore unknown fields, backward compatible consumer, postel law api
The tolerant reader pattern says a consumer of an API or message should be strict only about what it actually needs and ignore everything else. It's an application of the robustness principle: be conservative in what you send and liberal in what you accept.

In practice, a tolerant reader ignores unknown fields instead of failing, so the producer can add fields without breaking anyone. It reads only the fields it uses, rather than mapping the whole payload into a strict model. It handles missing optional fields with sensible defaults. And for enums, it has a fallback for unknown values, because a new status value from the producer shouldn't crash the consumer.

Most serializers support this. System.Text.Json ignores unknown properties by default, though .NET 8 added an option to disallow them, which you should leave off for external contracts. In TypeScript, a runtime validator like Zod should be configured to strip unknown keys rather than reject them.

The pattern makes independent deployment possible. A producer can add a field, deploy, and consumers update later when they want to use it. Combined with additive-only changes from producers, versioning becomes rare.

There's a balance though. Being tolerant doesn't mean accepting invalid data silently: required fields and business rules must still be validated, and unknown enum values should be logged so you notice them.

Our front-end sub-apps consume the same APIs at different release cadences. Tolerant parsing with safe defaults means a backend can release a new field without forcing every sub-app to release at the same time.

### msa | What is AsyncAPI, and how do you document event-driven APIs? | asyncapi, document events, event catalog, message contract documentation, openapi for events
OpenAPI documents request-response HTTP APIs, but it doesn't describe events and message queues well. AsyncAPI is the equivalent specification for event-driven systems.

An AsyncAPI document describes the servers, like a RabbitMQ or Kafka broker; the channels, such as queues, topics or exchanges and routing keys; the operations, saying whether the application sends or receives on each channel; and the message payloads with JSON Schema or Avro, plus headers like correlation id and message type. It can also describe security and bindings specific to each protocol.

From that, tools generate human-readable documentation, code models and even boilerplate for producers and consumers. Specifications can be checked into each service's repo and validated in CI like OpenAPI files.

The practical value is discoverability. In an event-driven system, it's surprisingly hard to answer which events exist, who publishes them, who consumes them and what fields they contain. Without documentation, people read code or guess from messages in queues. An event catalog, like EventCatalog or a developer portal such as Backstage, can collect the AsyncAPI files from all services into one browsable place, showing producers and consumers for each event.

Combined with schema compatibility checks, it also supports safe evolution: a change to a message schema shows up in review, and breaking changes can fail the build.

For a team with many RabbitMQ queues built up over years, I'd start small: document the most widely consumed events first, with their payload schemas and owners, because that's where unclear contracts cause the most incidents.

### msa | Event notification vs event-carried state transfer: what is the difference? | event notification vs event carried state transfer, thin events vs fat events, event payload design, domain event payload
These are two ways to design the content of events, sometimes called thin and fat events.

An event notification is thin: it says that something happened and gives an id, like order 123 was updated. Consumers that care call back to the owning service's API to get the current details. Events stay small and stable, and consumers always see the latest data. The downsides are extra calls, load on the owner, and runtime coupling: if the owner is down, consumers can't process the event.

Event-carried state transfer is fat: the event contains the relevant data, like the order's status, items and totals. Consumers can update their own local copy without calling back, so they keep working when the owner is down, and queries become local and fast. The downsides are larger messages, more fields that become part of the contract, harder schema evolution, and data duplicated across services that is eventually consistent.

There's also a middle path: include the fields most consumers need, plus the id for anyone who needs more.

Ordering matters with fat events. If a consumer processes an older event after a newer one, it might overwrite fresh data with stale data, so include a version or timestamp and ignore older ones.

I choose based on the consumers. When many services need to keep their own view of reference data, like site or product details, event-carried state transfer reduces chatter and coupling. For sensitive data, a thin notification is safer, since the details stay behind the owner's API with its access controls.

### msa | What is a cell-based architecture? | cell based architecture, cells, blast radius reduction, shuffle sharding, bulkhead at infrastructure level, partitioned deployment
A cell-based architecture splits a system into several independent, complete copies, called cells, each serving a subset of customers or tenants. Each cell has its own application instances, databases, queues and caches. A thin routing layer sends each request to the right cell based on, say, the tenant id.

The main reason is to limit blast radius. A bad deployment, a noisy tenant, a poison message or a database problem affects one cell, not everyone. It's the bulkhead pattern applied to the whole infrastructure. AWS uses this extensively for its own services.

It also helps scaling and operations. Cells have a known maximum size, so you test that size and add new cells as you grow, instead of discovering new limits in one giant deployment. Deployments roll out cell by cell, which works naturally with deployment rings.

The costs are real. More infrastructure to run and pay for. The routing layer must be very simple and highly available, since it's shared. Moving a tenant between cells needs a data migration process. And cross-cell features, like global reporting or search, need separate aggregation.

It fits systems with natural partitioning, like multi-tenant SaaS, where each customer's data is mostly independent.

A per-study database model is a small step in this direction. Each study's data is isolated, so a problem with one study's data or a migration rarely affects others. A full cell design would go further by also splitting the application tier, so a group of studies runs on its own infrastructure.

### msa | How do you share reference data across microservices? | reference data microservices, shared lookup data, master data across services, country codes services, replicate reference data
Reference data is data that many services need but that rarely changes, like countries, currencies, product catalogues, site details or configuration lists. The question is how services get it without coupling to one central database.

Option one is a reference data service with an API. Every service calls it, usually with caching. It keeps one source of truth, but adds a runtime dependency; if the service is slow or down, callers suffer unless their caches are good.

Option two is replication through events. The owning service publishes changes, and each consumer keeps its own local copy, in its own database or cache. Reads are local and fast, and consumers keep working during outages. The cost is eventual consistency and some storage duplication, which for reference data is usually fine.

Option three is shipping static data with the code, as a package or configuration file. For truly static standards, like ISO country codes, this is simplest. It needs a release to change, though.

Avoid a shared database that every service reads directly, because then no one can change the schema safely.

Whatever the approach, be clear about the owner, use stable identifiers that don't change when display names do, and version changes. For data that affects business rules, like a site being closed, decide how quickly consumers must see it, because that drives the choice between caching, events and direct calls.

In our platform, slowly changing configuration is cached per node with invalidation messages, while truly static lists ship with the application.
