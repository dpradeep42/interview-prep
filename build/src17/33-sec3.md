### secx | What is the OAuth token exchange or on-behalf-of flow? | on behalf of flow, token exchange, obo flow, downstream api user context, delegated token microservices
When a user calls API A, and API A must call API B as that user, so B can apply the user's own permissions, simply forwarding the user's token is a problem: the token's audience is API A, so B should reject it, and forwarding broad tokens everywhere increases the damage if one service is compromised.

The on-behalf-of flow, in Entra ID, and the standard OAuth 2.0 token exchange, RFC 8693, supported by Keycloak and others, solve this. API A sends the incoming user token to the identity provider's token endpoint, authenticating as itself, and asks for a new token for API B. The identity provider checks that A is allowed to call B on behalf of users and issues a token with audience B, containing the user's identity, and often A's identity as the actor. A calls B with that token, and B validates it normally.

Benefits: each token is scoped to exactly one audience, so tokens can't be replayed against other services; downstream services see the real user and enforce their own authorisation; and the identity provider controls which services may delegate to which.

Alternatives: if B doesn't need the user's identity for authorisation, A can call B with its own client credentials token and pass the user id as context, with B trusting A. That's simpler but means B trusts A to have checked permissions.

I'd use token exchange when downstream authorisation depends on the user, and client credentials otherwise.

### secx | How does mutual TLS work, and when would you use client certificates? | mutual tls, mtls, client certificate authentication, certificate based auth api, two way ssl
In normal TLS, only the server presents a certificate, so the client knows it's talking to the real server. In mutual TLS, the client also presents a certificate, so the server knows exactly which client is connecting, at the transport level, before any HTTP request is processed.

How it works: the server is configured to request client certificates and trusts a specific certificate authority. During the handshake, the client proves it holds the private key for its certificate. The server validates the certificate chain, expiry and revocation status, then maps the certificate, by thumbprint or subject, to a client identity. In ASP.NET Core, Kestrel's ClientCertificateMode and the certificate authentication handler do this; behind a load balancer or gateway that terminates TLS, the gateway validates the certificate and forwards details in a header, which the app must only trust from that gateway.

When I'd use it.

Service-to-service communication in a zero trust network, often automated through a service mesh, which issues and rotates certificates.

Partner and B2B integrations, where a partner system connects to our API: certificates are harder to steal and replay than API keys, and some industries require them.

Device authentication, like IoT devices or machines.

OAuth can also bind tokens to the client certificate, so a stolen token is useless without the private key.

The operational cost is certificate management: issuing, distributing, rotating before expiry, and revoking, so automation is essential.

### secx | API keys vs OAuth client credentials for partner integrations: which do you choose? | api keys vs oauth, partner api authentication, client credentials flow, api key security, machine to machine auth
Both authenticate a system rather than a user, but they differ a lot in security properties.

API keys are simple static secrets sent with each request, usually in a header. They're easy for partners to use, which is why they're popular. But they're long-lived, sent on every call, so any leak, in logs, proxies or code, gives access until someone notices and rotates them; they carry no scopes or expiry by themselves, unless the server implements that; and rotation needs coordination.

OAuth 2.0 client credentials: the partner authenticates to the token endpoint with its client id and a secret, or better, a private key JWT or certificate, and receives a short-lived access token with specific scopes, which it sends to the API. The long-lived credential is only sent to the identity provider, not to every API; access tokens expire in minutes; scopes limit what the partner can do; and the identity provider centralises management, rotation and revocation.

My choice: for anything sensitive, like clinical or personal data, or write operations, OAuth client credentials, ideally with private key JWT or mTLS for client authentication. API keys are acceptable for low-risk, read-only or public-ish APIs, or as an additional identifier for rate limiting and analytics alongside OAuth.

If API keys are used, I store only hashes, support multiple active keys for rotation, scope them, log usage per key, and allow fast revocation.

### secx | How do you prevent open redirect vulnerabilities? | open redirect, returnurl validation, unvalidated redirect, redirect after login security, localredirect aspnet core
An open redirect happens when an application takes a URL from user input, like a returnUrl parameter after login, and redirects to it without checking. Attackers send phishing links using our trusted domain: our-site.com/login?returnUrl=https://evil-site.com. The user sees our domain, logs in, and is sent to a fake page that might ask them to "log in again" and steal their credentials. In OAuth flows, open redirects can even leak authorisation codes or tokens.

Prevention.

Only allow local redirects: in ASP.NET Core, Url.IsLocalUrl(returnUrl) checks that a URL is relative to our site, and LocalRedirect() throws if it isn't, which is what the default login templates use. Allowlists: if redirects to other domains are needed, like between our own applications, compare against an explicit list of allowed hosts, not a substring match.

Indirect references: instead of passing a URL, pass an identifier, like a page key, that the server maps to a URL.

For OAuth and OpenID Connect: register exact redirect URIs in the identity provider, with no wildcards, so codes can only go to our own applications.

Front-end code too: SPAs that read a redirect parameter from the URL and assign window.location need the same validation.

It's a small fix with big phishing protection value.

Scanning tools and analyzers flag dangerous serialiser use, which helps find it in large legacy codebases.

### secx | How do you prevent path traversal when handling file names? | path traversal, directory traversal, dot dot slash attack, file download vulnerability, safe file paths
Path traversal happens when user input is used to build a file path, and the attacker includes sequences like ../ to escape the intended folder. A download endpoint like /files?name=report.pdf becomes /files?name=../../web.config, and the server returns its own configuration, with connection strings. On upload, attackers might write files into executable locations.

Prevention.

Don't use user input as a path at all, where possible: store files with server-generated names, like a GUID, and keep the original name only as metadata in the database. The user requests a file by id, the server checks authorisation and looks up the stored path.

Least privilege: the application's identity should only have access to the folders it needs, read-only where possible, so a traversal can't reach sensitive files.

Better still, store files in object storage, like S3 or Blob Storage, with keys generated by the server, which removes the file system from the equation.

Archives need care too: extracting zip files with entries named ../something, called Zip Slip, is the same bug.

### secx | How do you prevent command injection? | command injection, os command injection, process start security, shell injection, run external process safely
Command injection happens when user input is included in an operating system command, and the input contains shell syntax, like ; rm -rf or && net user, which the shell executes. In .NET, it typically appears when code builds a command string for Process.Start with cmd.exe or bash, for example to run a conversion tool or a script with a file name from the user.

Prevention, in order of preference.

Avoid shelling out: use a library or API to do the job in-process, like an image library instead of calling a command-line tool.

If an external program is needed, don't use a shell. Start the executable directly with ProcessStartInfo, UseShellExecute false, and pass arguments through the ArgumentList collection, which passes each argument separately and handles quoting, so input can't break out into new commands. Watch for argument injection: even without a shell, input starting with a dash can be interpreted as an option by the target program; use -- to end options where supported, or validate.

The same thinking applies to PowerShell scripts run from pipelines or automation: parameters, not string-built commands.

### secx | What is an XXE attack, and is .NET vulnerable to it? | xxe, xml external entity, xml parsing security, dtd processing, xmlreader secure settings, xml bomb
XML External Entity attacks exploit XML parsers that process DTDs, document type definitions. ### secx | How do you encrypt sensitive data in SQL Server: TDE, Always Encrypted or column encryption? | tde vs always encrypted, sql server encryption at rest, column level encryption, always encrypted, encrypt pii database
SQL Server has several encryption options that protect against different threats.

Transparent Data Encryption, TDE, encrypts the database files, logs and backups at rest. It's transparent to applications and protects against someone stealing the disks or backup files. But anyone who can query the database, including DBAs and the application, sees plain data. It's a baseline, and usually on by default in cloud databases.

Always Encrypted encrypts specific columns in the client driver, so data is encrypted before it leaves the application and stays encrypted in the database, in memory on the server and in backups. The keys are held by the client, in Key Vault or a certificate store, not by SQL Server. So DBAs and anyone with database access can't read those columns. The trade-off is that the server can't operate on encrypted data: deterministic encryption allows equality lookups, randomised encryption allows nothing. Secure enclaves extend this to some range comparisons and pattern matching. It needs driver support and careful key management.

Cell-level encryption with ENCRYPTBYKEY uses keys inside SQL Server, which gives control but means the server and its administrators can decrypt.

Application-level encryption: the app encrypts fields itself, with envelope encryption using a key management service. Flexible and database-independent.

My choice: TDE everywhere, plus TLS in transit; Always Encrypted or application-level encryption for a few highly sensitive columns, like personal identifiers, where restricting access even from administrators is required.

### secx | What do you check in a security-focused code review? | security code review, secure code review checklist, review for vulnerabilities, security review pull request
Automated tools catch common patterns, but many real vulnerabilities are logic flaws that only a human reviewer sees. In a security-focused review, I go through a mental checklist.

### secx | What does zero trust mean for application design? | zero trust, zero trust architecture, never trust always verify, zero trust network, beyondcorp
Zero trust means no implicit trust based on network location. The old model assumed everything inside the corporate network or VPN was trusted; once an attacker got in, they could move freely. Zero trust says: verify explicitly every time, use least privilege, and assume a breach has already happened.

What it means in practice for applications.

Every request is authenticated and authorised, including internal service-to-service calls. Services verify tokens or mutual TLS identities, rather than trusting calls because they come from the internal network.

Strong identity for users and workloads: MFA and conditional access for users, managed or workload identities for services, and short-lived credentials everywhere.

Least privilege and just-in-time access: services get only the permissions they need; administrators get elevated access temporarily, with approval.

Micro-segmentation: network policies and security groups restrict which services can talk to which, so a compromised service can't reach everything, even though network controls are no longer the main defence.

Encryption in transit everywhere, including internal traffic.

Device and context awareness: access decisions consider device health, location and risk.

Continuous monitoring: log and analyse access, and detect anomalies.

For legacy systems that rely on network trust, like intranet apps with Windows authentication, zero trust is applied gradually: putting them behind an identity-aware proxy, adding MFA, and tightening network paths.

### secx | What is ReDoS, and how do you prevent regex denial of service? | redos, regex denial of service, catastrophic backtracking, regex timeout dotnet, nonbacktracking regex
ReDoS is a denial of service caused by a regular expression that takes exponential time on certain inputs. Patterns with nested quantifiers or overlapping alternatives, like (a+)+$ or (\w+\s?)*$, can make the regex engine backtrack through an enormous number of combinations when the input almost matches but fails at the end. A short malicious string, a few dozen characters, can keep a CPU core busy for seconds or minutes. A handful of such requests can take down an API.

Where it appears: validation of emails, URLs or names with home-made patterns, parsing log lines, and search features that accept user patterns.

Prevention in .NET.

Set timeouts: pass a TimeSpan to the Regex constructor, or set a default with the REGEX_DEFAULT_MATCH_TIMEOUT AppContext setting, so a pathological match throws RegexMatchTimeoutException instead of running forever.

Use RegexOptions.NonBacktracking, available since .NET 7, which uses an automata-based engine with linear-time guarantees, for patterns that don't need backtracking features like lookarounds and backreferences.

Write safer patterns: avoid nested quantifiers on overlapping groups, anchor patterns, and limit input length before matching.

Never run user-supplied patterns without these protections.

Use the source-generated regexes with GeneratedRegex for performance, combined with the above.

Static analysis tools and analyzers can flag risky patterns, and fuzz tests with long near-matching inputs catch them in testing.

### secx | How do you build a secure password reset flow? | password reset security, forgot password flow, reset token security, account recovery, password reset best practices
Password reset is a favourite attack path because it bypasses the password entirely. A secure flow looks like this.

Request: the user enters their email. The response is always the same, like "if an account exists, we've sent a link", whether or not the account exists, so attackers can't use it to discover registered emails. Rate-limit requests per account and per IP.

Token: generate a long, random, single-use token from a cryptographically secure generator, store only its hash, linked to the user, with a short expiry, like 15 to 60 minutes. ASP.NET Core Identity's token providers handle this, and tokens become invalid if the user's security stamp changes.

Logging and monitoring: record reset requests and completions, and alert on unusual volumes.

In enterprise setups with SSO, like Keycloak or Entra ID, the identity provider owns this flow, and the application just links to it, which is better than building our own.

### secx | How do you prevent username or account enumeration? | username enumeration, account enumeration, user enumeration login, login error messages security, registration enumeration
Account enumeration means an attacker can find out which usernames or emails are registered, by watching how the application responds. With a list of valid accounts, credential stuffing and targeted phishing become much more effective.

Where it leaks.

Login: "user not found" versus "wrong password" messages. Fix: one generic message, like "invalid username or password".

Password reset: "no account with that email" versus "email sent". Fix: always respond the same way.

Registration: "this email is already registered". Harder to avoid; options include sending an email to the address instead, saying "you already have an account", while the screen shows a neutral confirmation.

Other signals: different HTTP status codes, response sizes, or account lockout messages that only appear for real accounts.

APIs: endpoints like /users/{email}/exists, or profile lookups, that confirm existence to unauthenticated callers.

Complementary defences: rate limiting and bot detection on these endpoints, CAPTCHA after repeated attempts, and monitoring for enumeration patterns, like many different usernames from one source.

There's a usability trade-off, so for internal enterprise apps using SSO, the identity provider handles most of this; for public-facing apps, I follow these practices fully.

### secx | How does Windows authentication work for intranet apps, and what are its limits? | windows authentication, kerberos vs ntlm, intranet authentication iis, negotiate authentication, integrated windows auth
Windows authentication lets users on domain-joined machines sign in to intranet apps automatically with their Windows login, no password prompt. IIS, or ASP.NET Core with the Negotiate handler, supports it.

It uses two protocols. Kerberos is the preferred one: the browser gets a service ticket from the domain controller for the web application's service principal name, and presents it to the server, which validates it without contacting the domain controller each time. It supports delegation, so the app can call another service, like SQL Server, as the user, if constrained delegation is configured. It requires correct SPNs registered for the service account, and the client must reach the domain controller.

NTLM is the fallback, used when Kerberos isn't possible, like when accessing by IP address or when SPNs are missing. It's a challenge-response protocol, weaker, doesn't support delegation, and is being deprecated by Microsoft.

Limits: it only works well for domain-joined devices inside the corporate network; external users, mobile devices and other platforms struggle. It doesn't fit cloud and SaaS scenarios, it ties the app to Active Directory, and it's hard to combine with modern MFA and conditional access. Proxies and load balancers can break NTLM because it's connection-based.

For modern applications, I'd use OpenID Connect against an identity provider, like Entra ID or Keycloak, which can itself use Kerberos for seamless sign-in on the corporate network, while supporting MFA, external access and token-based APIs.
