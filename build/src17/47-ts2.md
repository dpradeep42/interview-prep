Design matters more than tooling, though. If a test needs five patches, the code probably has hidden dependencies. ### tx | How do xUnit fixtures and parallel test execution work? | xunit fixtures, IClassFixture, ICollectionFixture, xunit parallel, test collections, shared context xunit
xUnit creates a new instance of the test class for every test method, so the constructor is your per-test setup and Dispose is the teardown. That isolation's good, but expensive setup, like starting a database container, shouldn't run for every single test.

Fixtures solve that. A class fixture creates one shared object for all tests in a class, passed into the constructor. A collection fixture shares one object across several classes that belong to the same named collection. For async setup, the fixture implements IAsyncLifetime, with an async initialise and an async dispose. A typical example is a WebApplicationFactory or a Testcontainers database shared by all integration test classes in one collection.

Parallelism follows collections. By default each test class is its own collection, and collections run in parallel, while tests inside one collection run one after another. Things to watch. Shared fixtures mustn't hold state that tests change, or test order starts to matter. Static state breaks parallel runs. And you can tune parallelism with a runner config file, or turn it off for a specific collection.

In our integration tests, one collection fixture starts a SQL Server container and applies the schema once. Each test then runs inside a transaction that gets rolled back, so tests stay independent and the whole suite runs in a couple of minutes.

So fuzz testing sends huge numbers of unexpected, random or malformed inputs to a system to find crashes and unhandled cases. Normal tests check the inputs you thought of, fuzzing finds the ones you didn't.

For APIs, schema-based fuzzers are the practical option. Test impact analysis means working out which tests a change could affect and running only those, instead of the whole suite. It matters when the full suite takes too long for every pull request.

### tx | userEvent vs fireEvent in React Testing Library: which should you use? | userEvent vs fireEvent, user-event library, react testing library events, simulate typing click test
Both trigger events in React Testing Library tests, but they work at different levels.

fireEvent dispatches a single DOM event. fireEvent change sets a value and fires one change event, fireEvent click fires one click. It's low level and doesn't do what a browser does around that event.

userEvent, from the user-event package, simulates what a real user actually does. My default is userEvent for anything a user does, typing, clicking, selecting, tabbing through a form. I keep fireEvent for events users can't easily trigger, like scroll or a custom event, or where userEvent doesn't support something.

Combined with queries by role and label, this keeps tests close to real usage. In our React shell's forms built with MUI, switching from fireEvent to userEvent exposed a validation message that only appeared on blur, which the old tests never triggered.

### tx | Test pyramid vs testing trophy: which shape should your test suite have? | testing trophy, test pyramid vs trophy, testing honeycomb, how many unit vs integration tests, kent c dodds trophy
The test pyramid says most tests should be fast unit tests, fewer integration tests, and very few end-to-end. The testing trophy, which got popular in the front-end world, puts most weight on integration tests, with static analysis like TypeScript and linting as the base, fewer unit tests and a few end-to-end. The pyramid still fits code with heavy logic, calculations, rules engines, parsers, algorithms. Those deserve lots of small unit tests covering edge cases.

For a business API that mostly moves data through validation into a database, I write mainly integration tests at the API level, plus unit tests for the complex rules. For a calculation-heavy module, like randomisation or dosing logic, I write extensive unit tests. Static checks come first everywhere, because the type checker catches a whole class of bugs for free.

The shape matters less than the outcome, tests that are fast, trusted, catch real bugs and don't break on every refactor.

### tx | How do you test an ETL job or data pipeline? | test etl, data pipeline testing, data quality tests, test data transformation, great expectations, reconciliation tests
Data pipelines fail more quietly than APIs, you know. They run successfully but produce wrong or incomplete data. So testing covers both the code and the data.

Unit tests cover transformation logic with small, hand-written inputs, including the awkward cases, nulls, duplicates, dates across time zones, unexpected codes and really long strings. If transformations are pure functions, this is straightforward.

Integration tests run the job end to end against real database containers with a realistic sample dataset, checking the output tables. They catch mapping mistakes, type conversion issues and performance problems with set-based SQL.

Data quality checks run in production too, as part of the pipeline. Tools like Great Expectations or dbt tests, or simple SQL assertions, check row counts against the source, no unexpected nulls in required columns, valid ranges, unique keys and referential integrity. A failed check stops the load or flags it, instead of quietly publishing bad data.

Reconciliation is the last safety net. Compare totals between source and target, like counts per day or sums of key amounts, and alert on differences.

Idempotency testing matters as well. Running the job twice mustn't duplicate data, and a run that fails halfway has to be safe to rerun.

For data transfers between systems, like moving integration flows from a middleware platform to .NET APIs, we ran old and new paths in parallel and compared the outputs record by record before switching, which was the strongest test of all.
