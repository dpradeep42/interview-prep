### rx | How does cache invalidation work in RTK Query with tags? | rtk query tags, providestags invalidatestags, rtk query cache invalidation, refetch after mutation rtk query
RTK Query caches responses from query endpoints, keyed by endpoint and arguments. After a mutation, like creating or updating a shipment, the cached lists and details become stale. Tags tell RTK Query which cached data to refetch automatically.

How it works: in createApi, declare tagTypes, like Shipment. Query endpoints say what data they provide: getShipments provides a Shipment tag with id LIST plus one Shipment tag per returned id, and getShipment provides the Shipment tag for its id. Mutation endpoints say what they invalidate: addShipment invalidates the Shipment LIST tag, so lists refetch; updateShipment invalidates the Shipment tag for that id, so that shipment's detail and any list containing it refetch.

When a mutation succeeds, RTK Query finds active queries with matching tags and refetches them. Components subscribed through hooks re-render with fresh data, with no manual dispatching.

Fine-tuning.

Optimistic updates with onQueryStarted and updateQueryData, to update the cache immediately and undo it if the mutation fails.

Pessimistic updates: write the mutation's response directly into the cache instead of refetching, to save a request.

keepUnusedDataFor controls how long unused cache entries stay; refetchOnFocus and refetchOnReconnect refresh data when users return.

Common mistakes: providing only a generic tag, so every mutation refetches everything; or forgetting the LIST tag, so new items don't appear in lists.

In the React shell with Redux Toolkit, RTK Query keeps API state consistent without hand-written loading flags and thunks, which removes a lot of boilerplate compared to our older patterns.

### rx | staleTime vs gcTime in TanStack Query: what is the difference? | stale time vs gc time, react query cachetime, tanstack query staletime, query keys react query, refetch on window focus
These two settings confuse many people because both relate to caching, but they control different things.

staleTime: how long fetched data is considered fresh. While fresh, TanStack Query serves it from cache without refetching, even when a new component mounts with the same query key. The default is 0, meaning data is stale immediately, so it refetches in the background on events like mount, window focus or reconnect. Setting staleTime to, say, 5 minutes for reference data, like a list of countries or sites, avoids unnecessary requests.

gcTime, called cacheTime before version 5: how long unused data stays in the cache after no component is using it. The default is 5 minutes. After that, it's garbage collected. If a component mounts again before then, cached data shows instantly, possibly with a background refetch if stale.

So: staleTime decides when to refetch; gcTime decides when to forget.

Query keys matter as much: a key array of 'shipments' plus an object with siteId and page includes all parameters, so different filters are cached separately, and invalidateQueries with just the 'shipments' prefix after a mutation refetches all shipment queries.

Typical settings I use: frequently changing data, like statuses, keep staleTime low; reference data gets a long staleTime; refetchOnWindowFocus can be turned off for heavy queries if it causes too many requests.

Showing data: isPending for the first load, isFetching for background refreshes, so the UI can show a subtle indicator instead of a full spinner when refreshing cached data.

Local component state for UI-only state.

Lift to the nearest common parent when siblings share it.

Use a server-state library, like TanStack Query or RTK Query, for data from APIs, rather than copying it into global state.

Use Context for rarely changing app-wide values, like theme, current user or locale.

Use a global store, like Redux Toolkit or Zustand, for complex client state shared widely, like a multi-step workflow or cross-feature selections.

A common anti-pattern I've cleaned up is putting everything into Redux, including form inputs and modal flags, which made simple components depend on the global store and re-render unnecessarily.

The non-null assertion operator, a postfix exclamation mark, like user!.name or document.getElementById('root')!, tells the compiler: trust me, this isn't null or undefined. The problem: if you're wrong, you get a runtime error, like "cannot read properties of undefined", exactly the error that strict null checks were meant to prevent. It silences the compiler instead of handling the case. Over time, code with many exclamation marks gives a false sense of safety.

Definite assignment for class fields initialised outside the constructor, like in Angular with ViewChild, uses a similar exclamation mark, field!: Type, with the same risks; signal-based queries reduce the need for it.

Where it's acceptable: places where the guarantee is obvious and local, like the root element in main.tsx that always exists, or in tests.

I enable the ESLint rule no-non-null-assertion as a warning, so each use is a conscious decision visible in code review.

### rx | What are the Rules of Hooks, and why do they exist? | rules of hooks, hooks rules react, conditional hooks, eslint plugin react hooks, why hooks order matters
React has two main rules for hooks.

First, only call hooks at the top level of a component or custom hook: not inside conditions, loops, nested functions, or after an early return.

Second, only call hooks from React function components or custom hooks, not from regular JavaScript functions or class components.

Why: React doesn't identify hooks by name. It tracks them by the order they're called during each render. The first useState call gets the first state slot, the second gets the second, and so on. If a hook is inside a condition, it may run in one render and not the next, so the order shifts, and React gives one hook's state to another. That causes confusing bugs, and React throws errors like "Rendered fewer hooks than expected".

How to handle conditional logic: put the condition inside the hook, not around it. For example, an effect that returns early when enabled is false, with enabled in its dependency array, or for data fetching, TanStack Query's enabled option. If a component needs very different hooks in different cases, split it into separate components and render one or the other.

Custom hooks must start with "use", so React and linting tools know to apply the rules.

The eslint-plugin-react-hooks package enforces both rules, and its exhaustive-deps rule checks dependency arrays. I keep both as errors in CI, because they catch real bugs.

React 19's use function is an exception: it can be called conditionally, because it doesn't rely on call order in the same way.

### rx | What is the useEffect cleanup function, and when does it run? | useeffect cleanup, cleanup function react, unsubscribe in useeffect, clear interval react, effect cleanup timing
The function you return from a useEffect callback is the cleanup function. React runs it to undo whatever the effect set up.

When it runs: before the effect runs again because its dependencies changed, with the old values, and when the component unmounts. In development with StrictMode, React also runs an extra setup, cleanup, setup cycle on mount, to reveal effects that don't clean up properly.

What needs cleanup.

Subscriptions: event listeners on window or document, WebSocket or SignalR handlers, observable subscriptions, store subscriptions. Remove them in cleanup.

Timers: clearInterval or clearTimeout.

Network requests: abort with an AbortController, so a slow response for old parameters doesn't update state after the parameters changed or the component unmounted.

Third-party widgets: destroy chart or map instances created in the effect.

Example: an effect that calls setInterval(refresh, 5000) and returns a cleanup that calls clearInterval with that id, with refresh as its dependency.

Common bugs without cleanup: memory leaks, duplicated event handlers firing several times, intervals multiplying each time dependencies change, and race conditions where old responses overwrite newer data.

Good practice: every effect that starts something should stop it, so a quick mental check during code review is "what does this effect start, and where is it stopped?"

Many effects can be avoided altogether: data fetching through TanStack Query or RTK Query handles cancellation and caching, and derived values can be computed during render, so fewer effects means fewer cleanup bugs.
