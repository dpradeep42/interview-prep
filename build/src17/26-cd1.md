### cdx | What are stages, jobs, steps and deployment jobs in Azure Pipelines? | azure pipelines stages jobs steps, deployment job, environments azure devops, pipeline structure, run once rolling canary strategy
An Azure Pipelines YAML pipeline has a clear hierarchy.

Stages are the big phases, like Build, Deploy to Dev, Deploy to QA and Deploy to Production. They run sequentially by default, can depend on each other with dependsOn, and can have conditions, like only deploying from main. Approvals and checks are attached at the environment level, so a stage waits until they pass.

Jobs run inside stages. Each job runs on one agent, from a pool, and jobs in a stage can run in parallel. A job can be a normal job or a deployment job.

Steps are the individual tasks or scripts inside a job, like checking out code, running dotnet build, publishing artifacts, or running a PowerShell script.

Artifacts are published in the build stage and downloaded automatically in deployment jobs, so the exact same build output moves through every stage.

On our on-premise Azure DevOps Server, the older classic release pipelines are still used for some apps, but YAML pipelines with environments give us code review and history for pipeline changes.

### cdx | Why should you build once and promote the same artifact through environments? | build once deploy many, artifact promotion, immutable artifact, rebuild per environment problem, environment specific config
Build once, deploy many means the pipeline compiles and packages the application one time, and that exact artifact, the same zip, package or container image, is deployed to dev, test, UAT and production. Only configuration differs per environment.

Why it matters. If you rebuild for each environment, you're not deploying what you tested. A different build agent, an updated base image, a newer dependency resolved by a floating version, or a different commit can sneak in. Then a bug appears in production that never existed in test, and you can't easily tell why.

With a single artifact, testing in each environment adds confidence to the same binary. It's faster, because builds happen once. And it's traceable: the artifact has a version and a hash, linked to a commit and a build, and each deployment records which artifact went where.

To make it work, configuration must be outside the artifact: environment variables, appsettings per environment loaded at runtime, a configuration service, or secrets managers, not build-time constants or per-environment build flags. Front ends need the same idea, loading a runtime config file rather than baking API URLs into the bundle.

In a validated GxP environment, this is close to mandatory, because the validated package must be provably identical to what goes into production. We keep the build artifact, its version and its approvals linked in Azure DevOps for that reason.

### cdx | What are ephemeral preview environments, and how do you set them up? | preview environments, ephemeral environments, pull request environment, review apps, environment per branch
An ephemeral preview environment is a short-lived copy of the application created automatically for a pull request, with its own URL, and destroyed when the pull request is merged or closed. Reviewers, testers and product owners can try the change for real before it merges, instead of reading code or waiting for a shared test environment.

How it's typically built. For front ends, it's easy: services like Azure Static Web Apps, Vercel or Netlify, or a pipeline that uploads to a bucket under a pull-request path, create a preview site per pull request automatically.

For back-end services on Kubernetes, the pipeline deploys the pull request's image into a new namespace named after the pull request, using the same Helm chart with a small values override, and a dynamic host name like pr-123.dev.example.com. Dependencies are either shared, like a common dev database with test data, or created per environment, like a small database container seeded with test data, depending on cost and isolation needs. A cleanup job deletes the namespace when the pull request closes, plus a nightly sweep for anything left behind.

On Azure Container Apps or AWS, infrastructure as code can create and destroy a small stack per pull request.

Watch-outs: cost, so environments are small and auto-expire; secrets, which shouldn't be exposed to pull requests from forks; and data, which must be synthetic, never copies of production data.

### cdx | How do you write reusable GitHub Actions workflows and composite actions? | reusable workflows, composite actions, github actions reuse, workflow_call, github actions templates
GitHub Actions has two main ways to reuse logic, at different levels.

Composite actions bundle several steps into one action, defined in an action.yml with inputs and outputs. For example, a setup-dotnet-build action that installs the SDK, restores with caching, builds and runs tests with coverage. Any job can use it as a single step. They're good for sharing step sequences, and they run inside the caller's job, on the caller's runner.

Reusable workflows are whole workflows triggered with workflow_call, with defined inputs, secrets and outputs. A caller job uses them with uses: org/repo/.github/workflows/deploy.yml@v2. They can contain multiple jobs, use their own runners, environments and protection rules, and are good for standardising entire processes, like build-and-push-image or deploy-to-environment with approvals.

Good practices: keep shared workflows in a central repository, version them with tags, and have consumers pin a tag or, for third-party actions, a full commit SHA, so an upstream change can't silently alter pipelines. Pass secrets explicitly rather than using secrets: inherit everywhere. Set minimal permissions for the GITHUB_TOKEN at the workflow level. Document inputs clearly.

Organisation-level rulesets can require certain workflows to run on all repositories, like a security scan, which gives similar governance to required templates in Azure Pipelines.

Changes to shared workflows are tested on a sample repository before a new version is tagged.

### cdx | How do you get end-to-end traceability from requirement to deployment? | traceability requirement to deployment, work item linking, audit trail release, gxp traceability, commit to production
Traceability means for any change running in production, I can answer: which requirement or bug it came from, who wrote and reviewed it, which tests verified it, which build produced it, and when and by whom it was deployed and approved. In a GxP environment, auditors expect exactly this.

How the tooling provides it in Azure DevOps.

Work items: every requirement, user story and bug is a work item. Branch policies require pull requests to link work items, and commits mention them too.

Pull requests: record the reviewers, approvals, comments and the validation build.

Builds: link to the commits and work items included since the last build, and publish test results and coverage, which attach to the build. The build number carries the version.

Releases and environments: the deployment records which build artifact went to which environment, with timestamps, approvals and who approved. Release notes can be generated from the linked work items.

Test management: test cases link to requirements, and test runs, manual or automated, link to builds, so validation evidence connects requirement to verification.

Going the other way, from a requirement I can find all the code and every release that included it.

What makes it actually work is enforcement through policies rather than discipline alone, and keeping retention settings long enough, because pipeline runs and artifacts are deleted by default after some time, which would break the audit trail. We set retention to match our records requirements.
