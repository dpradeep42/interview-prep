### dkx | How does pod termination work, and how do you make shutdown graceful in Kubernetes? | pod termination kubernetes, prestop hook, terminationgraceperiodseconds, graceful shutdown kubernetes, sigterm kubernetes

The pod's marked Terminating. In parallel two things start. The pod's removed from Service endpoints, so load balancers and kube-proxy stop sending new traffic. And the kubelet runs any preStop hook, then sends SIGTERM to the container's main process. If the process hasn't exited after the termination grace period, 30 seconds by default, it gets SIGKILL.

Make sure the app is PID 1 or uses an init process, so it actually gets the signal.

Set the termination grace period longer than preStop plus the drain time, especially for message consumers with long tasks.

For load balancers outside the cluster, line up the deregistration delay with these timings.

With all that in place, rolling deployments become genuinely zero-downtime.

### dkx | What actually is a container: namespaces and cgroups explained | how containers work, linux namespaces, cgroups, container vs virtual machine, container isolation
Right, a container isn't a small virtual machine. It's a normal Linux process, or a group of processes, that the kernel isolates and limits using two main features.

Namespaces control what a process can see. The PID namespace gives the container its own process tree, so its main process sees itself as PID 1. Control groups, cgroups, control what a process can use. CPU shares and quotas, memory limits, I/O and the number of processes. When a container goes over its memory limit, the kernel's OOM killer stops it. When it goes over its CPU quota, it gets throttled.

Image layers are stacked with a union file system like overlayfs, with a thin writable layer on top. That's why containers start quickly and images share common layers.

Compared to virtual machines, a VM runs a full guest OS on a hypervisor with its own kernel, so stronger isolation but more overhead and slower starts. Containers share the host kernel, so they're lighter and faster, but a kernel vulnerability can affect every container on the host. That's why sandboxed runtimes like gVisor or Kata Containers, and Firecracker micro-VMs used by Lambda and Fargate, add stronger isolation where it's needed.

Knowing this explains things like CPU throttling, OOM kills, and why Windows containers need a Windows host. I think it's one of those fundamentals that pays off every time you debug something.
