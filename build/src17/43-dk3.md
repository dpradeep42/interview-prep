### dkx | What are Kubernetes operators and custom resource definitions? | kubernetes operator, crd, custom resource definition, operator pattern, controller reconcile loop
Kubernetes is extensible. A custom resource definition, CRD, adds a new resource type to the Kubernetes API, like PostgresCluster or Certificate, which you can create with YAML and kubectl just like a Deployment.

An operator is a controller that watches those custom resources and makes reality match them. It encodes operational knowledge, what a human operator would do, into software.

Examples: database operators, like CloudNativePG or the operators for Redis and RabbitMQ, which create clusters, handle failover, backups and upgrades from a simple resource definition; cert-manager, which issues and renews TLS certificates from Certificate resources; Prometheus Operator, which manages monitoring configuration through ServiceMonitor resources; and Argo CD, whose Application resource describes what to deploy.

Why they're useful: complex stateful software becomes manageable declaratively, with GitOps, and day-two operations, like scaling, backups and upgrades, are automated consistently.

Cautions: an operator is powerful software running with broad permissions in your cluster, so choose mature, well-maintained ones and review their RBAC; understand what it does, because when it misbehaves you need to debug both the application and the operator; and keep operators upgraded along with the cluster, since CRD versions change.

Writing your own operator, with tools like Kubebuilder, Operator SDK or KubeOps for .NET, makes sense only for platform teams automating something repeated many times. For most application teams, Helm charts or Kustomize with existing operators are enough.

### dkx | How does pod termination work, and how do you make shutdown graceful in Kubernetes? | pod termination kubernetes, prestop hook, terminationgraceperiodseconds, graceful shutdown kubernetes, sigterm kubernetes
When Kubernetes stops a pod, during a deployment, scale-down or node drain, a sequence happens, and understanding it avoids errors during releases.

The pod is marked Terminating. In parallel, two things start: the pod is removed from Service endpoints, so load balancers and kube-proxy stop sending new traffic, and the kubelet runs any preStop hook, then sends SIGTERM to the container's main process. If the process hasn't exited after terminationGracePeriodSeconds, 30 seconds by default, it gets SIGKILL.

The problem: removing the pod from endpoints takes a moment to propagate to every node, ingress controller and cloud load balancer. If the app exits immediately on SIGTERM, some requests still arrive and fail, causing 502 errors during every deployment.

The fixes.

A short preStop delay, like sleeping 5 to 10 seconds, so the pod keeps serving while endpoint removal propagates. Newer Kubernetes versions support a native sleep action for preStop, which works even in images without a shell.

Handle SIGTERM in the app: stop accepting new work, finish in-flight requests and messages, close connections and flush logs and telemetry. ASP.NET Core does this with its host shutdown timeout, which should be configured to fit within the grace period; Node and Python apps need signal handlers.

Make sure the app is PID 1 or uses an init process, so it actually receives the signal.

Set terminationGracePeriodSeconds longer than preStop plus the time needed to drain, especially for message consumers processing long tasks.

For load balancers outside the cluster, align deregistration delay with these timings.

With this in place, rolling deployments become truly zero-downtime.

Licensing: Docker Desktop requires a paid subscription for larger companies, which led some organisations to adopt Podman Desktop or other alternatives for developer machines.

In practice, the choice matters little for production on Kubernetes, which uses containerd or CRI-O anyway. It matters for developer machines, security-sensitive Linux servers, and CI builds that shouldn't need a privileged daemon.

### dkx | How do maxSurge and maxUnavailable control a Kubernetes rolling update? | maxsurge maxunavailable, kubernetes rolling update strategy, kubectl rollout undo, rollout status, deployment strategy kubernetes
A Deployment's default strategy is RollingUpdate, which replaces old pods with new ones gradually. Two settings control the pace.

maxSurge: how many extra pods above the desired replica count can be created during the update. With 4 replicas and maxSurge 1, Kubernetes can run 5 pods temporarily.

maxUnavailable: how many pods below the desired count can be unavailable during the update. With maxUnavailable 0, Kubernetes never reduces capacity: it adds a new pod, waits until it's ready, then removes an old one.

Both accept numbers or percentages, and the defaults are 25 percent each.

Choosing values: for user-facing services where capacity matters, maxSurge 1 or 25 percent with maxUnavailable 0 keeps full capacity, at the cost of temporarily needing extra resources. For large deployments where speed matters, higher surge speeds up rollouts. If the cluster has no spare capacity, maxUnavailable 1 with maxSurge 0 avoids needing extra nodes, but reduces capacity briefly.

What makes rolling updates safe: readiness probes that reflect real readiness, so traffic only goes to pods that can serve; minReadySeconds, so a pod must stay ready for a while before counting as available, catching quick crashes; and progressDeadlineSeconds, which marks the rollout as failed if it doesn't progress.

Operations: kubectl rollout status watches progress, kubectl rollout history shows revisions, kubectl rollout undo returns to the previous revision, and kubectl rollout pause and resume control a rollout in steps.

For canary or blue-green with automated analysis, tools like Argo Rollouts extend this further.

### dkx | What actually is a container: namespaces and cgroups explained | how containers work, linux namespaces, cgroups, container vs virtual machine, container isolation
A container isn't a small virtual machine. It's a normal Linux process, or group of processes, that the kernel isolates and limits using two main features.

Namespaces control what a process can see. The PID namespace gives the container its own process tree, so its main process sees itself as PID 1. The network namespace gives it its own network interfaces, IP address and ports. The mount namespace gives it its own file system view, built from the image layers. There are also namespaces for hostnames, inter-process communication and user ids, so root inside a container can map to an unprivileged user outside.

Control groups, cgroups, control what a process can use: CPU shares and quotas, memory limits, I/O and the number of processes. When a container exceeds its memory limit, the kernel's OOM killer stops it; when it exceeds its CPU quota, it's throttled.

Image layers are stacked with a union file system, like overlayfs, with a thin writable layer on top, which is why containers start quickly and images share common layers.

Compared to virtual machines: a VM runs a full guest operating system on a hypervisor with its own kernel, giving stronger isolation but more overhead and slower start. Containers share the host kernel, so they're lighter and faster, but a kernel vulnerability can affect all containers on a host. That's why sandboxed runtimes, like gVisor or Kata Containers, and Firecracker micro-VMs used by Lambda and Fargate, add stronger isolation where needed.

Understanding this explains things like CPU throttling, OOM kills and why Windows containers need a Windows host.

### dkx | What are PriorityClasses and preemption in Kubernetes? | priorityclass kubernetes, pod preemption, pod priority, system critical pods, scheduling priority kubernetes
When a cluster runs out of capacity, Kubernetes has to decide which pods get scheduled. PriorityClasses tell it what matters most.

A PriorityClass is a cluster-level object with a name and an integer value; higher means more important. Pods reference it with priorityClassName. Built-in classes, system-cluster-critical and system-node-critical, protect components like CoreDNS and networking agents.

Effects.

Scheduling order: pending pods with higher priority are scheduled before lower-priority ones.

Preemption: if a high-priority pod can't be scheduled because there's no room, the scheduler can evict lower-priority pods from a node to make space. Evicted pods get a graceful termination and go back to pending, to be rescheduled when capacity frees up.

Eviction under node pressure also considers priority, along with resource usage against requests.

How I'd use it: a few clear tiers, like critical for core customer-facing services, default for normal services, and low for batch jobs, CI runners or experiments, so when capacity is short, batch work yields to production traffic. Low-priority classes can set preemptionPolicy Never, so those pods wait in the queue without preempting others.

Placeholder pods: some teams run low-priority "balloon" pods to reserve headroom; real workloads preempt them instantly, and the autoscaler adds nodes for the evicted placeholders, giving faster scaling.

Cautions: too many classes or giving everything high priority makes it meaningless; preemption can cause cascading disruption, so pair it with PodDisruptionBudgets, which preemption respects on a best-effort basis; and ResourceQuotas can limit who may use high-priority classes.
