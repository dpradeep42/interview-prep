### sqlx | What is EF Core's execution strategy, and how does it work with transactions? | execution strategy ef core, enableretryonfailure, retry transient sql errors, user initiated transactions not supported, sql azure transient
EnableRetryOnFailure turns on EF Core's retrying execution strategy for SQL Server. When a command fails with a transient error, like a brief network drop, a failover, or Azure SQL throttling, EF Core waits and retries automatically, with an increasing delay, up to a maximum number of attempts. That makes the app much more resilient in cloud environments, where short blips are normal.

The catch is transactions. If I start a transaction myself, with BeginTransaction, and a command fails in the middle, EF can't just retry that one command, because the earlier work in the transaction was rolled back. So EF Core throws an error saying user-initiated transactions aren't supported with the retrying strategy.

The fix is to wrap the whole unit of work in the strategy: get it with context.Database.CreateExecutionStrategy, and call ExecuteAsync with a delegate that begins the transaction, does all the work, saves and commits. If a transient failure happens, the strategy re-runs the entire delegate from the start, including beginning a new transaction.

That means the delegate must be safe to repeat. It should reload any data it depends on, rather than reusing state from the failed attempt, and avoid side effects outside the database, like sending an email, inside the retried block.

There's also a subtle case where the commit succeeded but the connection failed before confirming it. Making operations idempotent, or using verifySucceeded, protects against applying it twice.

### sqlx | char vs varchar vs nvarchar: how do you choose? | char vs varchar, varchar vs nvarchar, unicode columns, utf8 collation, column data type choice, nvarchar max
char is fixed-length: char(10) always uses 10 bytes, padding shorter values with spaces. It's good for values that are always the same length, like a two-letter country code or a fixed-format code.

varchar is variable-length, using only the bytes needed plus two bytes of overhead, so it's better for values of varying length, like names or descriptions.

nvarchar and nchar store Unicode, traditionally UTF-16, using two bytes per character for most text. They can store any language: Japanese, Arabic, Hindi, accented names. varchar uses a code page, so characters outside it get lost or become question marks, unless the column uses a UTF-8 collation, available since SQL Server 2019, which lets varchar store Unicode as UTF-8.

So for any text that users type, like names, addresses or comments, especially in a global system, I use nvarchar, or varchar with a UTF-8 collation. For internal codes and identifiers that are guaranteed ASCII, varchar saves space.

Other practices. Size columns realistically, not nvarchar(max) everywhere. Max types are stored differently, can't be index keys, and the declared size affects the memory grants the optimiser requests. And match the parameter types from the application to the column types, because a mismatch, like nvarchar parameters against a varchar column, can cause implicit conversions and index scans.

### sqlx | How do NULLs behave in SQL, and what is COUNT(*) vs COUNT(column)? | null in sql, count star vs count column, null comparison, is null, ansi nulls, coalesce isnull
NULL means unknown or missing, not zero and not empty string, and it follows three-valued logic: comparisons with NULL return unknown, not true or false.

That leads to classic surprises. WHERE Column equals NULL returns nothing; I must use IS NULL. WHERE Status not equals 'Shipped' excludes rows where Status is NULL, because NULL not equals 'Shipped' is unknown. NOT IN with a subquery that returns any NULL returns no rows at all, which is a nasty bug; NOT EXISTS doesn't have that problem.

COUNT of star counts all rows. COUNT of a column counts only rows where that column isn't NULL. COUNT DISTINCT also ignores NULLs. Aggregates like SUM and AVG ignore NULLs, so AVG of a column with NULLs isn't the same as SUM divided by COUNT star. And SUM of all NULLs returns NULL, not zero, so I wrap it in COALESCE.

For defaults, COALESCE is standard SQL and accepts many arguments, while ISNULL is SQL Server-specific, takes two, and uses the first argument's data type, which can truncate values.

NULLs in unique constraints: SQL Server allows only one NULL in a unique column, unlike some databases, so a filtered unique index is used to allow many.

In design, I make columns NOT NULL unless missing values are genuinely meaningful.

### sqlx | What is the difference between WHERE and HAVING? | where vs having, having clause, filter aggregates, group by having, logical query processing order
WHERE filters individual rows before they're grouped. HAVING filters groups after GROUP BY and aggregation. So conditions on raw columns go in WHERE, and conditions on aggregates, like COUNT, SUM or AVG, go in HAVING.

For example, to find sites with more than 50 dispensed kits this year: WHERE DispenseDate is in this year and Status equals Dispensed limits the rows first, then GROUP BY SiteId, then HAVING COUNT of star greater than 50 keeps only the groups with enough kits.

This follows the logical processing order of a query: FROM and JOINs, then WHERE, then GROUP BY, then HAVING, then SELECT, then ORDER BY, and finally TOP or OFFSET. That order also explains why you can't use a SELECT alias in WHERE, because SELECT hasn't happened yet, but you can use it in ORDER BY.

For performance, I put row conditions in WHERE whenever possible, not in HAVING, so fewer rows are grouped. The optimiser can often move simple HAVING conditions on grouping columns into WHERE, but writing it correctly makes intent clear and doesn't depend on that.

It's a basic question, but I've seen real bugs where a condition was put in HAVING on a non-aggregated column, or a filter on an outer-joined table in WHERE turned a LEFT JOIN into an inner join.

### sqlx | How do you write an upsert, and what are the risks of MERGE? | upsert sql server, merge statement, insert or update, merge race condition, update then insert pattern
An upsert updates a row if it exists, or inserts it if it doesn't. It's very common when syncing data from external systems, like vendor shipment statuses.

SQL Server's MERGE statement can do it in one statement: MERGE into the target, USING the source, ON the key, WHEN MATCHED THEN UPDATE, WHEN NOT MATCHED THEN INSERT, and optionally WHEN NOT MATCHED BY SOURCE THEN DELETE. It's powerful for syncing a whole set of rows from a staging table.

But MERGE has a reputation for problems. It isn't safe under concurrency by default: two sessions can both see that a row doesn't exist and both try to insert, causing primary key violations, unless I add a HOLDLOCK or SERIALIZABLE hint. It has had a number of bugs over the years, especially with filtered indexes, triggers and certain features. And it's easy to write in a way that does something unexpected.

For single-row upserts, many SQL Server developers prefer an explicit pattern inside a transaction: UPDATE with UPDLOCK and SERIALIZABLE hints, and if no rows were affected, INSERT. The lock hints prevent the race. For sets of rows, an UPDATE joined to the staging table followed by an INSERT of rows that don't exist, in one transaction.

In EF Core, there's no built-in upsert yet, so for high volumes I use SQL directly or a library.

### sqlx | Cursors vs set-based queries: why avoid cursors? | cursor vs set based, sql cursor performance, row by row processing, rbar, while loop sql
SQL Server is designed for set-based operations: describing what result you want for a whole set of rows in one statement, and letting the optimiser decide how to do it efficiently, using indexes, joins, parallelism and batching.

A cursor processes rows one at a time, like a loop in procedural code. Each iteration fetches a row and runs separate statements for it. People call this RBAR, "row by agonising row". For a large table, it's typically orders of magnitude slower than an equivalent set-based UPDATE or INSERT ... SELECT, because each row has its own overhead, locks are held longer, and the optimiser can't optimise the whole operation. WHILE loops that process one row at a time have the same problem.

So when I see a cursor, I try to rewrite it as one or a few set-based statements, using joins, CASE expressions, window functions like ROW_NUMBER or running totals with SUM OVER, and CTEs.

There are legitimate uses for cursors or loops. Administrative tasks that must run something per database or per object, like maintenance across many study databases. Calling a stored procedure that only works one row at a time and can't be changed. And deliberately processing in batches, which is a loop over chunks of thousands of rows, not single rows, to control locking and log growth.

If I must use a cursor, I declare it LOCAL FAST_FORWARD for lower overhead.

### sqlx | How do you write dynamic SQL safely? | dynamic sql, sp_executesql, exec vs sp_executesql, dynamic search query, quotename, dynamic sql injection
Dynamic SQL is building a SQL statement as a string and executing it, which is sometimes necessary, like search screens with many optional filters, dynamic sorting, or administrative scripts that work across tables or databases.

The rules I follow. Use sp_executesql, not EXEC of a concatenated string. sp_executesql takes parameters separately, so user values are never part of the SQL text, which prevents SQL injection. It also allows plan reuse, because the SQL text is the same for different parameter values.

Never concatenate user input as values. Only the structure of the query is built dynamically, like adding "AND SiteId equals @SiteId" when that filter is present, and the values are always passed as parameters.

For identifiers, like table names, column names or sort direction, which can't be parameters, I validate them against a whitelist of allowed names, and wrap them with QUOTENAME to handle special characters safely.

For catch-all search queries with optional filters, building the WHERE clause dynamically with only the filters actually used often gives much better plans than one static query with "OR @Param IS NULL" conditions, which tends to produce poor, generic plans. OPTION RECOMPILE is the other alternative for those.

Dynamic SQL runs with the caller's permissions, and it's harder to read and review, so I keep it small, well commented, and print it in debug mode.

### sqlx | How do you handle errors and transactions in T-SQL with TRY/CATCH and XACT_ABORT? | try catch sql server, xact_abort, t sql error handling, rollback in catch, throw vs raiserror, xact_state
In stored procedures that change data, I use a standard pattern so errors never leave a transaction half-done or open.

At the top, SET XACT_ABORT ON, and SET NOCOUNT ON. With XACT_ABORT on, most runtime errors automatically roll back the whole transaction and abort the batch. Without it, some errors only fail the current statement, and the transaction continues, which can leave partial changes. It also matters when the client times out: the transaction is rolled back instead of staying open, holding locks.

Then BEGIN TRY, BEGIN TRANSACTION, the statements, COMMIT TRANSACTION, END TRY. And BEGIN CATCH: if there's an open transaction, checked with @@TRANCOUNT greater than zero or XACT_STATE, ROLLBACK TRANSACTION; then log the error if needed, and rethrow it with THROW, so the application knows it failed. THROW, available since SQL Server 2012, preserves the original error number and message, and is simpler than RAISERROR.

Logging inside the CATCH should happen after the rollback, otherwise the log row is rolled back too.

Nested transactions in SQL Server aren't real nested transactions: an inner COMMIT only decrements the counter, and any ROLLBACK rolls back everything. So procedures called from other procedures should be careful about starting their own transactions, or use save points.

On the .NET side, I still handle SqlException and use transactions consistently.

### sqlx | What are wait statistics, and how do you use them to tune SQL Server? | wait stats, sys.dm_os_wait_stats, pageiolatch, cxpacket, lck_m waits, sql server waits tuning
Whenever a SQL Server task can't proceed, it waits, and SQL Server records why and for how long. Wait statistics answer the question "what is the server spending its time waiting for?", which points you to the type of bottleneck before you tune anything.

I look at sys.dm_os_wait_stats for the server overall, filtered to exclude benign background waits, and sys.dm_exec_session_wait_stats or Query Store's wait categories for specific sessions or queries.

The common ones and what they suggest. PAGEIOLATCH: waiting to read data pages from disk, which suggests not enough memory for the working set, or queries reading too much data due to missing indexes. WRITELOG: waiting for transaction log writes, so slow log storage or too many tiny commits. LCK_M waits: blocking, waiting on locks held by others. CXPACKET and CXCONSUMER: parallelism, often normal, but heavy amounts may mean large scans or a cost threshold for parallelism that's too low. SOS_SCHEDULER_YIELD: CPU pressure. RESOURCE_SEMAPHORE: queries waiting for memory grants, often due to big sorts or hashes from poor estimates. ASYNC_NETWORK_IO: the client isn't consuming results fast enough, often the application reading row by row or fetching huge result sets.

Wait stats are cumulative since restart, so I compare snapshots over a time window, during the problem period, rather than reading the totals.

### sqlx | What is tempdb contention, and how do you reduce it? | tempdb contention, tempdb allocation contention, pagelatch tempdb, tempdb files, tempdb spills
tempdb is a shared system database used by every database on the instance for temporary tables, table variables, sorts and hashes that spill out of memory, the row version store for snapshot isolation, and some internal work. Because everything shares it, it can become a bottleneck.

Allocation contention is the classic problem. When many sessions create and drop temporary objects at a high rate, they all compete for the same allocation pages, which show up as PAGELATCH waits on tempdb pages. Mitigations: multiple tempdb data files of equal size, usually one per CPU core up to eight, which modern SQL Server setup does by default; newer versions also reduced this contention a lot, and SQL Server 2019 added memory-optimised tempdb metadata.

Other tempdb problems. Spills: a sort or hash join that doesn't get enough memory writes to tempdb, which is slow, and shows as a warning in the execution plan. Fixing estimates, indexes, or the query usually helps. Version store growth: with RCSI or snapshot isolation, a long-running transaction prevents old row versions from being cleaned up, so tempdb grows. And running out of space, which can affect every database on the server.

So I monitor tempdb size and usage, keep it on fast storage, size it properly up front so it doesn't keep auto-growing, and look for queries with spills or excessive temporary object use.

SQL Server records missing index suggestions when the optimiser thinks an index would have helped a query. They appear in execution plans as a green hint, and in the missing index DMVs, along with an estimated improvement. They're a useful starting point, but I never create them blindly.

The limitations. Suggestions are made per query, without considering other indexes, so you often get several overlapping suggestions that should be combined into one. They don't consider the cost of maintaining the index on inserts and updates. The key column order isn't always ideal; equality columns are listed before inequality columns, but not ordered by selectivity. ### sqlx | How do you delete or archive millions of old rows safely? | delete millions of rows, purge old data, archive data sql, batch delete, data retention job

SELECT star returns every column of a table, and in application code, it causes several problems.

### sqlx | What problems do long-running transactions cause? | long running transaction, open transaction problems, transaction log growth, blocking long transaction, keep transactions short
A transaction holds its locks until it commits or rolls back. The longer it runs, the more damage it can do.

Blocking: other sessions that need the locked rows, pages or tables wait, so the application slows down for many users, and deadlocks become more likely.

Transaction log growth: the log can't be truncated past the oldest active transaction, so a transaction left open for hours makes the log grow until the disk fills, even with regular log backups.

Version store growth: with snapshot isolation or RCSI, old row versions in tempdb can't be cleaned up while an old transaction might need them, so tempdb grows.

Recovery and rollback time: if it fails or the server restarts, rolling it back takes a long time, and the database may take longer to recover.

Replication and availability group lag can also increase.

Common causes in applications: doing slow work inside a transaction, like calling an external API, sending an email or waiting for user input; processing a huge batch in one transaction; or a bug where an exception skips the commit and the connection stays open with the transaction.

So I keep transactions as short as possible: prepare and validate data before starting, only include the database writes that must be atomic, do external calls outside, process large changes in batches, and monitor for old open transactions with DBCC OPENTRAN or DMVs.

### sqlx | What is a columnstore index, and when would you use one? | columnstore index, clustered columnstore, analytics sql server, batch mode, reporting performance, olap vs oltp
A normal, rowstore index stores data row by row. A columnstore index stores data column by column, in compressed segments of around a million rows.

That's ideal for analytics: queries that scan many rows but only a few columns, like summing quantities by site and month over millions of shipments. The query reads only the needed columns, the data is highly compressed, often 10 times smaller, and SQL Server processes it in batch mode, handling many rows per operation, which makes aggregations dramatically faster. Segment elimination also skips segments that can't match the filter.

There are two main uses. A clustered columnstore index makes the whole table columnar, which is right for data warehouse fact tables and large history or log tables that are mostly appended and aggregated. A non-clustered columnstore index on a transactional table enables real-time operational analytics: the OLTP workload uses the normal rowstore indexes, while reports use the columnstore, without a separate warehouse.

The trade-offs: they're poor for single-row lookups and frequent small updates, because updates are handled through a delta store and deleted bitmaps, and need maintenance to stay efficient.

So I'd consider a non-clustered columnstore for heavy reporting on a big transactional table, and clustered columnstore for warehouse or history tables. For example, aggregating supply and dispensing history for forecasting reports is a typical fit.

### sqlx | What is Change Data Capture, and how is it different from Change Tracking? | change data capture, cdc sql server, change tracking, debezium, stream database changes, sync data changes
Both are SQL Server features for finding out what changed in tables, so other systems can sync or react, without adding timestamp columns or triggers everywhere.

Change Tracking is lightweight. It records that a row changed, the primary key and the type of change, plus a version number, but not the old or new values. A consumer asks "what changed since version X?", then reads the current values from the table. It's synchronous with the transaction, has low overhead, and is great for syncing caches, mobile clients or search indexes, where only the latest state matters.

Change Data Capture is richer. It reads the transaction log asynchronously and records the full history of changes in change tables: inserts, deletes, and the before and after values of updates, with the order of operations. It's suited to auditing, data warehouse loading, and streaming changes to other systems. Tools like Debezium read CDC and publish each change as an event to Kafka, which is a common way to implement the outbox pattern or feed other services without changing application code.

The trade-offs: CDC uses more storage, needs SQL Server Agent jobs for capture and cleanup on-premise, and adds some latency and operational work. Change Tracking is simpler but loses intermediate values.

So: Change Tracking for "give me what's changed so I can sync", CDC for "give me every change, with history".

### sqlx | What is row-level security in SQL Server? | row level security, rls sql server, security policy predicate, tenant isolation database, session_context
Row-level security lets the database itself filter which rows a user can see or change, based on who is running the query, without changing the queries.

I create an inline table-valued function, the predicate, that returns a row when access is allowed, like when the row's TenantId equals the tenant id stored in the session context. For applications that connect with one shared database login, the user or tenant identity is set per connection with sp_set_session_context, for example through an EF Core connection interceptor right after the connection opens, and the predicate reads it with SESSION_CONTEXT.

It's a strong defence in depth for multi-tenant databases: even if a developer forgets a WHERE clause, or a reporting tool queries the table directly, data from other tenants isn't exposed.
