### sqlx | What is the difference between WHERE and HAVING? | where vs having, having clause, filter aggregates, group by having, logical query processing order
WHERE filters individual rows before they're grouped. HAVING filters groups after GROUP BY and aggregation. So conditions on raw columns go in WHERE, and conditions on aggregates, COUNT, SUM, AVG, go in HAVING.

Let me take an example. Find sites with more than 50 dispensed kits this year. WHERE dispense date is this year and status is Dispensed limits the rows first, then GROUP BY SiteId, then HAVING COUNT star greater than 50 keeps only the groups with enough kits.

This follows the logical processing order of a query. FROM and JOINs, then WHERE, then GROUP BY, then HAVING, then SELECT, then ORDER BY, and last TOP or OFFSET. That order also explains why you can't use a SELECT alias in WHERE, because SELECT hasn't happened yet, but you can use it in ORDER BY.

For performance, I put row conditions in WHERE whenever possible, not HAVING, so fewer rows get grouped. The optimiser can often move simple HAVING conditions on grouping columns into WHERE, but writing it properly makes the intent clear and doesn't depend on that.

It sounds basic, but I've seen real bugs from it. Like a condition put in HAVING on a non-aggregated column. Or a filter on an outer-joined table sitting in WHERE, which quietly turned a LEFT JOIN into an inner join. That second one took a while to spot.

### sqlx | Cursors vs set-based queries: why avoid cursors? | cursor vs set based, sql cursor performance, row by row processing, rbar, while loop sql
See, SQL Server is built for set-based operations. You describe the result you want for a whole set of rows in one statement, and let the optimiser figure out how to do it efficiently, with indexes, joins, parallelism and batching.

A cursor processes rows one at a time, like a loop in procedural code. Each iteration fetches a row and runs separate statements for it. People call it RBAR, row by agonising row. On a big table, it's usually orders of magnitude slower than the equivalent set-based UPDATE or INSERT SELECT, because every row has its own overhead, locks are held longer, and the optimiser can't optimise the operation as a whole. There are legit uses though. Admin tasks that have to run something per database or per object, like maintenance across many study databases. Calling a stored procedure that only works one row at a time and that you can't change. And deliberately processing in batches, which is a loop over chunks of thousands of rows, not single rows, to control locking and log growth.

If I really must use a cursor, I declare it LOCAL FAST_FORWARD, so the overhead is lower. But that's rare for me.

### sqlx | What problems do long-running transactions cause? | long running transaction, open transaction problems, transaction log growth, blocking long transaction, keep transactions short
See, a transaction holds its locks until it commits or rolls back. So the longer it runs, the more damage it can do.

Blocking is the obvious one. Other sessions that need the locked rows, pages or tables just wait, so the app slows down for lots of users, and deadlocks get more likely.
