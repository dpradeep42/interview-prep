### obx | How do you connect logs to traces using trace ids and span ids? | logs and traces correlation, trace id in logs, span id logging, log trace correlation, jump from log to trace
Logs tell you what happened, traces tell you where the time went across services. Linking them means every log line written during a request carries that request's trace id and span id, so from one error log you can open the whole distributed trace, and from a slow span you can see its logs.

In .NET this mostly comes for free. In older services, we already had a correlation id passed through middleware and message headers. In the newer OpenTelemetry-based services, the W3C trace id replaces that, and Datadog connects logs, traces and metrics for one request automatically.

### obx | What is OpenTelemetry baggage, and how is it different from span attributes? | otel baggage, opentelemetry baggage, context propagation baggage, baggage vs attributes, propagate tenant id
Span attributes are key-value pairs recorded on one span, like the HTTP route or the order id. They stay on that span and don't travel to other services.

Baggage is key-value data that travels with the request context across process boundaries. It goes in the baggage HTTP header, next to the traceparent header, and every downstream service can read it. A typical example is a tenant id or customer tier set at the edge, so services several hops away know it without every API passing it as a parameter.

Baggage isn't automatically recorded on spans or logs, though. If you want the tenant id on downstream spans, you add a span processor that copies chosen baggage entries into attributes, which also makes them searchable in the tracing backend.

A few cautions I'd really stress, and people miss these. Baggage goes out on every outgoing call, including calls to third parties unless you strip it, so never put sensitive data like user emails, patient details or tokens in it. Keep it small, since it adds bytes to every request. And treat incoming baggage from outside as untrusted. Anyone can send the header, so it must not drive authorization decisions.

In .NET, the Baggage API in OpenTelemetry, or Activity baggage, sets values, and the propagators handle the header. I'd use it for low-sensitivity routing and diagnostic context, like a tenant or region label, which makes it easy to filter traces by tenant during an incident.

### obx | What are OpenTelemetry semantic conventions, and how should you name spans and attributes? | semantic conventions, span naming, otel attribute names, http.route, low cardinality span names
Semantic conventions are basically OpenTelemetry's standard names for common telemetry. Attributes like http dot request dot method, http dot route, the response status code, db dot system and the messaging destination name, plus standard metric names like the HTTP server request duration. When every service and library uses the same names, dashboards and queries work across languages without any mapping.

The automatic instrumentation for ASP.NET Core, HttpClient, Express or FastAPI already follows them. So the question's mostly about custom spans and attributes you add yourself.

For span names, keep them low cardinality and describing the operation, not the data. GET plus the route template, like orders by id, is good. The full URL with an actual id is bad, because every request becomes a unique name, which breaks aggregation and pushes up cost. For a custom operation, something like process shipment or allocate kit is clear.

For custom attributes, follow the conventions first, then use your own namespace for business attributes, like app dot study dot phase or app dot order dot type, so they don't clash with future standard names. Put high-cardinality identifiers, like an order id, on spans as attributes, where they're useful for search, but never as metric labels.

Record errors with the span status set to error and the exception recorded as an event, so backends show them consistently.

Agreeing a short naming guide across teams was one of the most useful things we did when moving newer services to OpenTelemetry. Without it, the same field showed up under four different names, and cross-service queries were painful.

### obx | What are burn-rate alerts, and why are they better than simple error thresholds? | burn rate alert, multi window burn rate, slo alerting, error budget alert, alert on slo
A simple threshold alert, like error rate above two percent for five minutes, has two problems. It fires on short blips that don't matter, and it misses slow, steady problems that sit just under the threshold but burn through the error budget over days.

Burn rate measures how fast you're using the error budget compared with the allowed pace. If your SLO is 99.9 percent success over thirty days, a burn rate of one uses exactly the budget in thirty days. A burn rate of fourteen point four would use two percent of the monthly budget in one hour, which is serious.

Multi-window, multi-burn-rate alerting, from Google's SRE workbook, combines a fast alert and a slow one. A page fires when the burn rate is high over both a long window, like one hour, and a short window, like five minutes. The long window proves it's significant, the short window proves it's still happening, so the alert clears quickly after recovery. A ticket-level alert fires for a lower burn rate over six hours or a day, catching slow leaks.

What you get is alerts that map to user impact and the SLO the business agreed. People get woken up for things that threaten the budget, not for every spike, and I think that's what keeps on-call sane.

You need an SLI defined as good events over total events, like successful requests under a latency target. Datadog, Grafana and most monitoring tools have built-in SLO and burn-rate alerting, so the hard work is choosing good SLIs, not the maths.

### obx | What is eBPF, and why is it used for observability? | ebpf, ebpf observability, kernel tracing, cilium hubble, pixie, zero instrumentation monitoring
eBPF lets small, verified programs run safely inside the Linux kernel, attached to events like system calls, network packets or function calls, without changing kernel code or restarting anything. For observability, that means you can see what processes are doing from the outside, without adding code to the application.

What it can show you. Network flows between pods, including latency and dropped connections. HTTP and gRPC requests parsed at the kernel level. DNS lookups. File and disk activity. CPU profiles across all processes. And security events like unexpected process launches.

Tools built on it include Cilium with Hubble for Kubernetes network visibility, Pixie and Grafana Beyla for automatic request metrics and traces, Parca and other continuous profilers, Falco for runtime security, and Datadog and other vendor agents, which use it for network monitoring.

The upside is no code changes, really low overhead, and visibility into things applications don't report, like a connection the network dropped or a slow DNS lookup.

The limits are real too, though. It's Linux only and needs a recent kernel and privileges. It sees bytes and calls, not business context, so it can't tell you which study or order a request belonged to. And encrypted traffic is harder to inspect, it needs hooks into TLS libraries.

So for me, eBPF is a complement to OpenTelemetry, not a replacement. It gives a baseline for every workload in a cluster, including ones nobody instrumented, while application instrumentation adds the business meaning.

### obx | What does 99.9 percent availability mean in downtime, and how do dependencies affect it? | availability nines, 99.9 uptime downtime per month, sla calculation, composite availability, dependency availability maths
Each extra nine cuts allowed downtime by ten. Ninety-nine percent allows about seven hours of downtime a month. 99.9 percent, three nines, allows about forty-three minutes a month, or under nine hours a year. 99.95 is about twenty-two minutes a month, and 99.99, four nines, only about four minutes a month, which is less than one manual deployment going wrong.

Dependencies multiply, and this is where people forget the maths. If a request needs three services in series, each 99.9 percent available, the combined availability is roughly 99.9 times 99.9 times 99.9, which is about 99.7 percent. So you can't promise a higher SLA than your critical dependencies allow, unless you take the dependency off the critical path.

Redundancy works the other way. Two independent instances, each 99 percent available, behind a load balancer give about 99.99 percent in theory, because both have to fail together. In practice, shared failure causes, the same bad deployment, the same database, the same region, reduce that benefit a lot.

So to improve availability, make fewer things critical. Cache data, use queues so a downstream outage delays work instead of failing requests, degrade gracefully when an optional service is down, and run across zones.

Also be precise about what availability measures. Is it uptime of a health endpoint, or successful user requests? Request-based SLIs are more honest. And scheduled maintenance windows often aren't counted in contractual SLAs, but users still feel them, which is one more reason I'd aim for zero-downtime releases.

### obx | How do you read a trace waterfall to find where the time is spent? | trace waterfall, read distributed trace, critical path trace, find slow span, span timeline analysis
A trace waterfall shows every span of a request on a timeline. The root span at the top, child spans indented, and each bar's length showing its duration. Reading it well is a quick way to find the real cause of slowness.

I start with the root span's duration and compare it with what's typical, so I know I'm looking at a representative slow trace. Exemplars from a latency chart, or a filter for slow traces, help find one.

Then follow the critical path, the chain of spans that actually decided the end time. A long span running in parallel with others might not matter, while a short span repeated many times in sequence often does.

Common patterns kind of jump out visually. A staircase of many small database or HTTP spans one after another is an N plus one problem. A big gap with no child span means time spent in the service itself, CPU work, lock waits, garbage collection, thread pool starvation, or an uninstrumented call. Spans that could run in parallel but run one after another suggest missing concurrency. A span that waits a long time before starting, like a message sitting in a queue, shows backlog.

Then check span attributes and events, the SQL statement, retry counts, cache hit or miss, response size.

And compare it with a fast trace for the same endpoint. The difference between the two usually points straight at the cause. In our services, the gap pattern once led us to thread pool starvation from a synchronous call inside async code.

### obx | How do audit logs differ from application logs, and how long should you keep each? | audit log vs application log, log retention policy, how long keep logs, compliance logging, immutable audit trail
Application logs are for engineers. Diagnosing errors, understanding behaviour and performance. They're high volume, can be sampled or dropped, and usually only need keeping for days or weeks, because nobody investigates a debug log from last year.

Audit logs are for accountability. Who did what, to which record, when, and sometimes why. They're a business and compliance record, so they have to be complete, accurate and tamper-evident, and kept as long as regulations or contracts require, which can be many years in regulated industries.

That difference drives the design. Audit records shouldn't depend on the logging pipeline, which might drop messages under load. They're usually written in the same database transaction as the change, or through an outbox, so a change can't happen without its audit record. They're append-only, with permissions that stop even administrators from editing them, and ideally protected with hashing or write-once storage. They hold old and new values and the user identity, and they're designed to be queried by business users and auditors.

Application logs go to tools like Splunk, Datadog or CloudWatch, with retention set by cost and need, often thirty to ninety days hot, with older data archived cheaply if required.

Both need data protection. Personal data in application logs should be minimised or masked, while audit logs, which might need personal data, need strict access control.

In a GxP system, I'd say the audit trail is a validated feature of the product, not a side effect of logging, and treating it that way avoids a lot of findings.
