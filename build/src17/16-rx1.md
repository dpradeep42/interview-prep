### rx | How do you avoid race conditions when fetching data in useEffect? | useeffect race condition, abortcontroller react, useeffect cleanup fetch, stale response react, ignore flag useeffect
A classic bug: a component fetches data in useEffect based on a prop, like the selected site id. The user switches from site A to site B quickly. Both requests are in flight, and if A's response arrives after B's, the component shows site A's data while site B is selected.

The fix is the effect's cleanup function. React runs the cleanup before running the effect again, and when the component unmounts. There are two common patterns.

An ignore flag: inside the effect, declare let ignore equals false, and in the cleanup, set ignore to true. When the response arrives, only update state if ignore is still false. The stale response is simply discarded.

AbortController, which is better: create a controller in the effect, pass controller.signal to fetch, or to axios through its signal option, and call controller.abort in the cleanup. The outdated request is actually cancelled, saving bandwidth, and the aborted promise rejects with an AbortError, which I ignore rather than showing as an error.

The cleanup also prevents setting state after unmount.

Honestly, though, in real apps I avoid hand-written fetching in effects. Libraries like TanStack Query or RTK Query handle caching, deduplication, race conditions, retries and loading states for me, keyed by the query parameters. Effects are better kept for synchronising with external systems.

### rx | Why do effects run twice in development with React StrictMode? | strictmode double render, useeffect runs twice, react 18 strict mode effects, double api call development, strict mode react
In React 18 and later, when a component is wrapped in StrictMode, React deliberately mounts it, unmounts it, and mounts it again in development. So every effect runs, its cleanup runs, and it runs again. Render functions are also called twice. This only happens in development; production builds run effects once.

The purpose is to surface bugs early. React is moving towards features, like preserving state when components are hidden and shown again, where components may be mounted and unmounted multiple times. If an effect doesn't clean up properly, like a subscription that isn't removed, a timer that isn't cleared, or an event listener that's added twice, the double invocation exposes it as duplicate behaviour. Double rendering exposes impure render functions that have side effects.

So the right response is not to disable StrictMode, but to make effects resilient: every effect that sets something up should return a cleanup that tears it down, and the effect should work correctly when run twice. For data fetching, the abort or ignore pattern handles it, and the second request is the one that counts. For things that truly must happen once per app, like initialising analytics, I do them outside components, at module level, or guard with a ref.

The duplicate API call in development looks alarming in the network tab, but it's expected, and libraries like TanStack Query deduplicate it anyway.

### rx | useEffect vs useLayoutEffect: what is the difference? | uselayouteffect vs useeffect, layout effect, measure dom react, flicker react, useinsertioneffect
Both run after React has updated the DOM, but at different moments.

### rx | When does React.memo not help? | react memo not working, react.memo pitfalls, memo with object props, unnecessary memo, when to use react memo
React.memo makes a component skip re-rendering when its props are shallowly equal to the previous props. It's useful for expensive components that re-render often with the same props, like rows in a large list or a heavy chart.

But it often doesn't help, for a few reasons.

New object, array or function props on every render. If the parent passes style equals an object literal, items equals data.filter of something, or onClick equals an arrow function, those are new references every time, so the shallow comparison always fails, and memo does nothing except add comparison cost. The fix is useMemo for derived objects and arrays, and useCallback for functions, or moving constants outside the component.

Children as props. JSX children are new elements on every render, so a memoised component that receives children re-renders anyway.

Context. If the component uses a context that changes, it re-renders regardless of memo.

Its own state or hooks changing triggers re-renders too; memo only affects re-renders caused by the parent.

And sometimes it's simply not needed: if the component is cheap, re-rendering costs less than the memo bookkeeping. React's rendering is fast, and re-rendering isn't the same as DOM updates.

So I measure first with the React DevTools Profiler, and memoise where it shows a real cost. The React Compiler, now stable, does much of this memoisation automatically.

### rx | What is automatic batching in React 18? | automatic batching, react 18 batching, setstate batching, multiple setstate one render, flushsync
Batching means React groups several state updates into a single re-render, instead of re-rendering after each one. If a click handler calls setLoading, setData and setError, React renders once with all three changes, which is faster and avoids showing intermediate, inconsistent states.

Apps get fewer renders without any code change. Note that apps still using the old ReactDOM.render, like React 17 apps upgraded without switching to createRoot, keep the old behaviour.

In rare cases, I need an update to be applied immediately, for example to read the updated DOM right after setting state, like scrolling to a newly added item. flushSync forces React to apply the updates inside it synchronously. It hurts performance, so it's used sparingly.

A related point: because of batching, state isn't updated immediately after calling the setter; the new value is available on the next render. For updates based on the previous value, I use the functional form, setCount of c such that c plus one.

### rx | How does Suspense work, and how is it used for data fetching? | react suspense, suspense data fetching, suspense fallback, suspense boundaries, use hook react 19, suspense query

### rx | What are React Server Components? | react server components, rsc, server components vs client components, use client directive, next.js app router
React Server Components are components that run only on the server. They render to a special serialised format that's streamed to the browser, and their own code is never sent to the client. For a single-page app like our React shell, built with Vite and served as static files with .NET APIs, Server Components don't apply directly. They make most sense for content-heavy, public-facing apps.

### rx | What are the performance pitfalls of React Context, and how do you avoid them? | context performance, context re render, split context, usememo context value, context selector, context vs redux performance
When a context's value changes, every component that consumes that context re-renders, even if it only uses a small part of the value. React.memo doesn't stop it.

Common pitfalls. Passing an object literal as the value, like value equals user and setUser in braces. That's a new object on every render of the provider, so all consumers re-render whenever the provider re-renders, even if nothing changed. The fix is to memoise the value with useMemo.

Using context for high-frequency updates, like form input values or real-time data. Context isn't designed for that.

If a part of the app needs fine-grained subscriptions, a store library like Redux Toolkit or Zustand is better, because components subscribe through selectors and only re-render when their selected value changes. There's also use-context-selector as a library.

So I use context for low-frequency, app-wide values, and a store or a server-state library for the rest.

### rx | Why do Redux selectors need memoization, and how does createSelector work? | reselect, createselector, memoized selectors, selector re render, derived data redux
A selector is a function that reads data from the Redux store, like state.shipments.items. With useSelector, a component re-renders whenever the selector's result changes, compared by reference.

The problem comes with derived data.
