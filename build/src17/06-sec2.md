### secx | What is the difference between session cookies and token-based authentication? | cookies vs tokens, session vs jwt, cookie authentication vs jwt, stateful vs stateless auth, which is better cookie or token
With session cookies, the server creates a session after login, stores the session data on the server or in a shared store, and gives the browser a cookie with a session id. The browser sends the cookie automatically on each request. It's simple and secure for traditional web apps, especially with HttpOnly, Secure and SameSite flags, and sessions can be revoked instantly by deleting them. But it needs shared session storage when scaling out, it's tied to one domain, and needs CSRF protection.

With token-based authentication, the client gets a signed token, usually a JWT, and sends it in the Authorization header. The server validates it without storing anything, so it scales easily and works across domains, for mobile apps and service-to-service calls. The downsides are that revocation is harder, and in browsers, storing the token safely is tricky, because JavaScript-readable storage is exposed to XSS.

Modern best practice for browser apps often combines them: a BFF does the OAuth login on the server, keeps tokens server-side, and uses a secure cookie with the browser. APIs called by other services or mobile apps use bearer tokens.

So it's not that one is always better; it depends on the client type.

### secx | What security checks do you apply to uploaded files? | secure file upload, file upload security, validate uploaded files, malware scan upload, upload vulnerabilities
File uploads are a common attack route, so I apply several checks.

Size limits: set a maximum request size and file size, so nobody can fill the disk or memory. In ASP.NET Core, through RequestSizeLimit and Kestrel or form options.

Type validation: allow only the types the feature needs, with an allow-list. Don't trust the file extension or the Content-Type header, because both are set by the client. Check the file's actual signature, its magic bytes, and for documents, parse them safely.

Names: never use the user's file name for storage, because of path traversal tricks like dot-dot-slash. Generate a random name, and keep the original name only as metadata, sanitised.

Storage: store outside the web root, ideally in object storage like S3 or blob storage, in a private bucket, so uploaded files can never be executed by the web server. Serve downloads through the API with authorization checks, or short-lived signed URLs, and with Content-Disposition: attachment.

Scanning: run antivirus or malware scanning before marking the file as available.

Content risks: CSV files can contain formula injection, so exports escape leading equals signs, and images can carry metadata with personal data, so strip it.

And log uploads for audit.

### secx | What is the difference between symmetric and asymmetric JWT signing? | hs256 vs rs256, symmetric vs asymmetric signing, jwt signing algorithm, rs256 jwks, which jwt algorithm
JWTs can be signed in two ways.

Symmetric signing, like HS256, uses one shared secret key both to sign and to verify. It's simple and fast. The problem is that every service that verifies tokens must have the same secret, and anyone with the secret can also create valid tokens. So if any one service leaks it, an attacker can forge tokens for the whole system. It's only reasonable when the issuer and the verifier are the same application.

Asymmetric signing, like RS256 with RSA or ES256 with elliptic curves, uses a private key to sign and a public key to verify. Only the identity provider holds the private key. APIs just need the public key, which isn't secret, so a compromised API can't create tokens. Public keys are published at the JWKS endpoint, with a key id, which makes key rotation easy: the provider adds a new key, starts signing with it, and APIs pick it up automatically.

So for distributed systems and microservices, asymmetric signing is the right choice.

One classic attack is algorithm confusion, where an attacker changes the header's algorithm to "none" or to HS256 using the public key as a secret. Validation must only accept the expected algorithms; ASP.NET Core's JWT handler does this properly when configured with the authority.

### secx | What is a threat model, and how do you do one for a new feature? | threat modeling, stride, threat model feature, security design review, attack surface
A threat model is a structured way to think about what could go wrong with a feature's security before building it, so security is designed in, not patched on later.

I keep it lightweight, often a one-hour session with the team. First, draw a simple data-flow diagram: users, services, data stores, external systems, and the trust boundaries between them, like the internet to our API, or our service to a vendor.

Then go through each element with STRIDE as a checklist. Spoofing: can someone pretend to be another user or service? Tampering: can data be changed in transit or at rest? Repudiation: can someone deny an action because there's no audit trail? Information disclosure: can data leak through APIs, logs or errors? Denial of service: can someone overload it? Elevation of privilege: can a user do more than they should?

For each real threat, we agree a mitigation, like adding resource-level authorization, signing a webhook, or rate limiting, and track it as a work item with an owner. Risks we accept are written down.

The model is revisited when the design changes.

[When we threat-modelled the drug accountability return screens, it showed that the return quantity API needed a site ownership check, which we added before release.]

### secx | How do you secure webhooks you send and receive? | webhook security, verify webhook signature, hmac webhook, secure webhook endpoint, webhook replay attack
Webhooks are HTTP calls between systems, so both sides need to trust each other.

When receiving webhooks, the biggest risk is someone calling the endpoint pretending to be the provider. So I verify a signature: the provider signs the request body with a shared secret using HMAC-SHA256 and sends it in a header. I recompute the HMAC over the raw body and compare with a constant-time comparison. I also check a timestamp header and reject old requests, like older than five minutes, to prevent replay attacks, and store the event id to ignore duplicates, since providers retry. The endpoint responds quickly with 2xx and queues the work, so the provider doesn't time out and resend.

When sending webhooks, I do the same in reverse: sign each payload, include a timestamp and a unique id, use HTTPS only, retry with backoff on failure, and let customers rotate their secrets. I also protect against SSRF, because customers provide the URLs: block internal addresses, like localhost and private IP ranges, and metadata endpoints.

Payloads contain minimal data, often just an id, so the receiver fetches details through the authenticated API.

[Our vendor status callbacks in the newer data transfer API verify an HMAC signature and timestamp before queuing the message.]

### secx | What is SSRF, and how do you prevent it? | ssrf, server side request forgery, prevent ssrf, metadata endpoint attack, url fetch vulnerability
Server-side request forgery happens when an attacker makes our server send a request to a URL they choose. It's a risk whenever the server fetches a URL provided by a user, like importing an image from a link, previewing a URL, or calling a customer-provided webhook.

The danger is that our server sits inside the network, so the attacker can reach things they normally can't: internal admin APIs, databases with HTTP interfaces, or the cloud metadata endpoint, like 169.254.169.254 on AWS, which can expose temporary credentials. That's how some well-known cloud breaches happened.

To prevent it, I avoid fetching user-supplied URLs where possible. If needed, I validate against an allow-list of domains, and resolve the host name and block private, loopback, link-local and metadata IP ranges. I check again after redirects, or disable redirects, because an allowed URL can redirect to an internal one. DNS rebinding is another trick, so I connect to the IP I validated.

At the infrastructure level, on AWS, I require IMDSv2, which uses session tokens and blocks simple SSRF access to metadata, and restrict outbound traffic with security groups or an egress proxy.

Least-privilege roles limit the damage if something still gets through.

### secx | A critical CVE is reported in a transitive NuGet or npm dependency. What do you do? | vulnerable dependency, nuget vulnerability, npm audit, dependency scanning, cve in package, dependabot
First, I assess it. Is the vulnerable package actually used by us, and is the vulnerable code path reachable? What's the severity, and is there a known exploit? Which applications and environments use it? Transitive dependencies matter too, because often the vulnerable package is pulled in by another one.

Tools help: dotnet list package --vulnerable, NuGet audit warnings during restore, npm audit, and automated scanners like Dependabot, Snyk or GitHub's dependency graph, which open pull requests with the fixed version.

Then I fix it. Normally, upgrade to the patched version, run the full test suite, and deploy through the normal pipeline, quickly for critical issues. If the direct package has no fix yet, I can pin the transitive dependency to a fixed version, with a direct reference or npm overrides. If there's no fix at all, I mitigate: disable the affected feature, add input validation or a WAF rule, and track it.

Afterwards, I check for signs of exploitation in logs if the risk was high, and document it.

To prevent surprises, the pipeline runs dependency scanning on every build and fails on high or critical findings, and we keep dependencies reasonably up to date, so upgrades are small.

In a validated environment, even a security patch goes through change control, but we fast-track critical ones.

### secx | What is the Data Protection API in ASP.NET Core? | data protection api, asp.net core data protection, key ring, data protection keys, protect unprotect, cookie encryption keys
The Data Protection API is ASP.NET Core's built-in system for encrypting and signing data that the app itself needs to read back later. The framework uses it for authentication cookies, anti-forgery tokens and TempData, and I can use it for things like protecting a token in a URL.

I get an IDataProtector from IDataProtectionProvider with a purpose string, then call Protect and Unprotect. The purpose string isolates uses, so data protected for "password reset" can't be unprotected as something else. ToTimeLimitedDataProtector adds expiry.

The important production detail is the key ring. Keys are generated and rotated automatically, every 90 days by default. By default they're stored locally, which is fine on one machine. But with several instances behind a load balancer, or containers that restart, each instance would have different keys, so a cookie issued by one instance can't be read by another, and users get logged out or see anti-forgery errors.

So in production, I persist the keys to a shared location, like Redis, a database, blob storage or S3, set the same application name for all instances, and protect the keys at rest, with Azure Key Vault, a certificate, or AWS KMS.

This is a classic issue when moving an app from one server to a load-balanced or containerised setup.

### secx | What is a Content Security Policy, and how do you roll it out without breaking the site? | content security policy, csp, csp rollout, csp report only, nonce csp, csp angular react
A Content Security Policy is a response header that tells the browser which sources are allowed for scripts, styles, images, fonts, frames and API calls. If an attacker injects a script, the browser refuses to run it because it doesn't match the policy. It's one of the strongest defences against XSS.

A strict policy looks like: default-src 'self'; script-src 'self'; object-src 'none'; frame-ancestors 'none'; connect-src for our API and identity provider. Inline scripts are blocked unless they have a nonce, a random value per response, or a hash.

Rolling it out on an existing site needs care, because it can break things: inline scripts, inline event handlers, third-party analytics, fonts from CDNs, or older libraries that use eval.

So I start with Content-Security-Policy-Report-Only, which doesn't block anything but reports violations to an endpoint. I collect reports for a couple of weeks, fix or allow the legitimate sources, remove inline code where possible, and only then switch to enforcing mode. I keep reporting on, to catch new issues.

Modern React and Angular builds with Vite or the Angular CLI work well with a strict CSP, because scripts are external files; Angular also supports nonces for its inline styles.

### secx | How do you keep an Angular or React app's API keys safe? | api keys in frontend, hide api key react, environment variables frontend secret, secrets in spa, vite env secret
The honest answer is that you can't hide a secret in a browser app. Everything in the JavaScript bundle, including environment variables injected at build time, like Vite's VITE_ variables or Angular's environment files, is visible to anyone who opens the developer tools.

So the rule is: never put real secrets in front-end code. Only public values belong there, like the API base URL, the identity provider's URL, a public client id, or a publishable key that's designed to be public and restricted, like a maps key locked to our domain.

When the front end needs to call a service that requires a secret key, the call goes through our own backend. The browser calls our API with the user's token; our API adds the secret, which it reads from a vault, and calls the third-party service. That's also where rate limits and authorization are applied.

For our own APIs, the front end doesn't use API keys at all. Users log in with OpenID Connect, and the app sends a short-lived access token.

I also check build output and the repo with secret scanning, because developers sometimes put a key in a .env file that ends up in the bundle.

Our React shell's Vite variables contain only URLs and the public Keycloak client id.

### secx | What is the difference between a WAF and a firewall? | waf vs firewall, web application firewall, aws waf, network firewall, what is waf
A traditional network firewall works at the network and transport layers. It allows or blocks traffic based on IP addresses, ports and protocols, like "allow HTTPS on port 443 from anywhere, block everything else", or "only the app servers can reach the database on port 1433". In the cloud, security groups, network ACLs and Azure network security groups play this role.

A web application firewall works at the application layer, layer 7. It understands HTTP and inspects the content of requests: URLs, headers, query strings and bodies. It can block common attack patterns, like SQL injection strings, cross-site scripting payloads, known bad bots, requests from certain countries, or too many requests from one IP. Examples are AWS WAF on CloudFront, an ALB or API Gateway, Azure Web Application Firewall on Front Door or Application Gateway, and Cloudflare.

They complement each other: the network firewall limits who can talk to what, and the WAF filters malicious content in allowed traffic.

But a WAF is a safety net, not a replacement for secure code. It can be bypassed with clever encoding and can produce false positives, so I start rules in count mode, review what would be blocked, then enable blocking. The application must still validate input and use parameterised queries.

### secx | How do you rotate secrets and certificates without downtime? | secret rotation, rotate database password, certificate rotation, zero downtime rotation, key rotation
The trick is to have two valid credentials for an overlap period, so nothing breaks during the switch.

For database passwords or API keys, the common approach is dual credentials. Create a new secret while the old one still works. Update the secret store. Applications pick up the new value, either by reloading configuration periodically, or by fetching a fresh secret when authentication fails, then retrying. After all instances use the new one, revoke the old one. AWS Secrets Manager automates this with rotation Lambdas, using alternating users, so one is always valid.

For signing keys, like JWT keys, the identity provider publishes both the old and new public keys in its JWKS. It starts signing with the new key, and once old tokens have expired, removes the old key.

For TLS certificates, I automate renewal well before expiry, using AWS Certificate Manager, Key Vault auto-renewal, or Let's Encrypt with cert-manager, and alert at 30 days before expiry for anything manual. Expired certificates are a surprisingly common cause of outages.

Better still, remove secrets entirely where possible: IAM roles and managed identities rotate credentials automatically.

The application side matters: don't cache secrets forever, and don't require a restart to pick up a new one.

### secx | How do you implement field-level security so some roles never see certain fields? | field level security, data level authorization, hide fields by role, blinded unblinded access, column level security, mask fields by permission
Sometimes the question isn't whether a user can see a record, but which fields of it they can see. In clinical trials, this is critical: blinded users must never see which treatment a subject received, while unblinded roles, like pharmacists or the safety team, can.

I enforce it on the server, never just by hiding fields in the UI, because anyone can call the API directly or look at the network response.

The approach: the user's permissions, from their role, determine a data access level. The API builds different DTOs, or projections, for different access levels, so sensitive fields are simply not selected from the database for blinded users. A blinded user's response doesn't contain the treatment arm at all, not even as null with a hint. Reports and exports follow the same rules, and so do logs and error messages.

For extra protection, the database can enforce it too, with views or column permissions, so a reporting tool can't bypass the application.

Testing is essential: automated tests call each endpoint as a blinded user and assert that unblinded fields never appear.

In our IRT, role and field-level blinding is a core feature, and things like kit numbers that could reveal the treatment are handled carefully.

### secx | Which identity provider would you choose for a new system: Keycloak, Entra ID or Amazon Cognito? | keycloak vs azure ad vs cognito, identity provider comparison, entra id vs keycloak, which identity provider, cognito user pool
All three are identity providers that support OAuth 2.0 and OpenID Connect, so applications integrate with them in a similar way. The differences are about hosting, features and ecosystem.

Keycloak is open source and self-hosted. You run it yourself, on-premise or in the cloud, which gives full control, deep customisation of login flows and themes, user federation with LDAP and Active Directory, and no per-user licence cost. The trade-off is that you operate it: upgrades, high availability, database backups and security patching.

Microsoft Entra ID, formerly Azure AD, is a managed service, ideal when the organisation already uses Microsoft 365, with corporate single sign-on, conditional access, MFA and B2B guest users built in. Entra External ID handles customer-facing identity.

Amazon Cognito is AWS's managed service, with user pools for app users, integration with API Gateway and ALB, and identity pools for temporary AWS credentials. It's cost-effective for customer apps on AWS, though less flexible for complex enterprise scenarios.

For the .NET API, it barely matters: AddJwtBearer with the authority and audience works with all of them.

We use Keycloak for our on-premise IRT, because it runs inside our network and supports our compliance needs, like password policies and lockout.

### secx | What is the difference between TLS termination at the load balancer and end-to-end TLS? | tls termination, ssl offloading, end to end encryption, https load balancer, tls passthrough, re encryption
With TLS termination, or SSL offloading, the load balancer or gateway handles the HTTPS connection with the client, decrypts the traffic, and forwards it to the backend, often as plain HTTP inside the private network. It's simple and efficient: certificates are managed in one place, like AWS Certificate Manager on an ALB, backends don't spend CPU on encryption, and the load balancer can inspect and route by HTTP content, and apply a WAF.

The risk is that traffic between the load balancer and the backend is unencrypted. Inside a well-isolated private network, many teams accept that. But for sensitive data, compliance requirements, or a zero-trust approach, it's not enough.

End-to-end TLS means traffic is encrypted all the way. There are two styles. Re-encryption: the load balancer terminates TLS, inspects the request, then opens a new TLS connection to the backend. TLS passthrough: the load balancer just forwards the encrypted bytes, using a layer 4 balancer, and the backend terminates TLS, but then the load balancer can't route by path.

In ASP.NET Core behind a terminating proxy, I configure the forwarded headers middleware, so the app knows the original request was HTTPS and uses the right client IP and scheme.

For healthcare data, I prefer re-encryption to the backend.
