### azx | How do you design for high availability and disaster recovery in Azure? | availability zones azure, paired regions, azure disaster recovery, zone redundant, rto rpo azure, sql failover group
Actually HA and DR in Azure work at two levels, zones within a region, and regions.

Availability zones are physically separate data centres within a region, with independent power, cooling and networking. Zone-redundant services spread instances across zones automatically. Zone-redundant App Service plans, Azure SQL zone redundancy, ZRS storage, zone-redundant Service Bus Premium, AKS node pools across zones, and so on. That protects against a data centre failure with very little effort, and it's my default for production.

Regions protect against a whole-region outage. Lots of regions have a paired region, used for geo-redundant storage replication and staggered platform updates, though newer regions may not have pairs, so you pick the secondary region yourself.

DR patterns, roughly by cost and recovery time. Backup and restore to another region, with hours of recovery time. Pilot light or warm standby, with data replicated and minimal compute ready to scale up. And active-active, with traffic in both regions through Front Door, for near-zero downtime.

Data replication is honestly the hard part. Azure SQL failover groups with a listener endpoint that stays the same after failover. Cosmos DB multi-region with automatic failover. GZRS storage. And Service Bus geo-replication.

It all starts from the business's RTO and RPO, how long can the system be down, and how much data can we lose. Infrastructure as code makes rebuilding possible, and DR has to be tested regularly with real failovers, not just on paper.

### azx | How do you secure CI/CD connections from Azure DevOps to Azure without secrets? | workload identity federation, azure devops service connection oidc, federated credentials, service principal secret expiry, github actions azure oidc
Okay, traditionally Azure DevOps service connections to Azure used a service principal with a client secret. Secrets expire, usually every year or two, which breaks pipelines out of nowhere, and they can leak, giving attackers access to deploy or change resources.

Workload identity federation removes the secret completely. It uses OpenID Connect. Azure DevOps issues a short-lived token for each pipeline run, identifying the organisation, project and service connection. GitHub Actions works the same way, with federated credentials trusting tokens for a specific repository, branch or environment.

Extra controls I'd add, separate service connections per environment, with production ones needing approvals and checks, and restricted to specific pipelines and branches.

For on-premise Azure DevOps Server, like our setup, federation depends on the version and network reachability, so we follow the same least-privilege idea with whatever the server supports.

### azx | What is Azure SignalR Service, and when do you need it? | azure signalr service, real time azure, scale signalr, signalr backplane, websockets azure, web pubsub
SignalR is ASP.NET Core's library for real-time communication, pushing messages from server to clients over WebSockets, with fallbacks. Self-hosted SignalR has a scaling problem: each client is connected to one server instance, so to send a message to all users, or a specific user connected to a different instance, the servers need a backplane, like Redis, and load balancers need sticky sessions. Each server also holds many open connections, which consumes resources.

Azure SignalR Service solves this. It's a managed service that holds all client connections. The app servers connect to the service and send messages through it, so the service handles fan-out to the right clients, regardless of which app instance sends the message. No backplane or sticky sessions are needed, and app servers no longer hold thousands of connections. It scales to very large numbers of concurrent connections through units. Integration is mostly configuration: AddSignalR().AddAzureSignalR().

It also has a serverless mode, used with Azure Functions bindings, where functions send messages through the service without any hub server, which suits event-driven notifications, like pushing a status update to a user when a background process completes.

Azure Web PubSub is a related service for plain WebSocket clients, without the SignalR protocol, useful for non-.NET clients and other frameworks.

Use cases: live dashboards, notifications, collaborative editing, chat and progress updates. Authentication uses access tokens, and user ids allow targeting specific users and groups.

### azx | What is Conditional Access and Privileged Identity Management in Entra ID? | conditional access, pim, privileged identity management, mfa policy entra, just in time admin access, zero trust azure
Both are key Entra ID security features, part of a zero trust approach.

Conditional Access is Entra's policy engine for sign-ins. Policies are if-then rules: if a sign-in matches certain conditions, then enforce controls. Conditions include which users or groups, which applications, the sign-in risk and user risk detected by Identity Protection, the device platform, whether the device is compliant or joined, the location, like trusted office networks or countries, and the client app. Controls include requiring MFA, requiring phishing-resistant MFA like passkeys for admins, requiring a compliant device, requiring a password change for risky users, limiting session lifetime, or blocking access. Common policies: MFA for everyone, block legacy authentication, stronger requirements for administrators, and block access from unexpected countries. Report-only mode tests policies before enforcing them.

Privileged Identity Management handles privileged roles, both Entra roles and Azure resource roles. Instead of permanent admin assignments, users are eligible for a role and activate it just in time, for a limited duration, like two hours, with MFA, a justification, a ticket number, and optionally approval from another person. Activations are audited and alerts can be raised. Access reviews regularly ask owners to confirm whether people still need their roles, removing stale access.

Together they reduce the risk of stolen credentials: even a compromised account has no standing admin rights, and risky sign-ins are challenged or blocked.
