Config changes. Any change to web.config or files in the bin folder triggers a recycle. So something writing there, like the app writing logs or temp files into its own folder, or antivirus touching files, can cause it.

Periodic recycling. The default regular interval is 1,740 minutes, which means it recycles at a different time every day, sometimes right in peak hours. Better to set a specific off-peak time.

Crashes. An unhandled exception on a background thread, a stack overflow or an access violation kills the worker process, and after several crashes rapid-fail protection can stop the app pool completely. The Application event log shows the .NET runtime errors and Windows Error Reporting entries.

Idle timeout is a bit different, the pool shuts down after inactivity, and the symptom is a slow first request.

For crashes, what I do is set up ProcDump or DebugDiag to capture a crash dump, analyse it for the exception and stack, fix the bug, and check the recycle events stop.

### scx | The app crashes with no logs at all. How do you find out why? | process crash no logs, stackoverflow crash dotnet, unhandled exception crash, app dies silently, crash dump analysis
Honestly, when a process dies without logging anything, it's usually something the app just couldn't catch. A stack overflow, an out-of-memory kill from outside, a native crash, or an unhandled exception on a background thread before the logs got flushed.

So I look for evidence outside the app first. On Windows, the Application event log usually has a .NET Runtime error with the exception type and stack, or an Application Error entry with the faulting module. On Linux or containers, the exit code tells you a lot. 137 means killed by SIGKILL, often out of memory, 139 is a segfault, 134 is an abort. The orchestrator shows the reason, like OOMKilled, and the kernel log has the OOM killer messages.

Then capture a crash dump for next time. On Windows, ProcDump with the e flag, or Windows Error Reporting local dumps. For .NET on Linux, the DOTNET DbgEnableMiniDump environment variables write a dump on crash. Then analyse it with dotnet-dump analyze, WinDbg or Visual Studio, looking at the exception and the thread stacks.

What I usually find is a stack overflow from infinite recursion, often a property calling itself, or a deep recursive algorithm on unexpected data. That can't be caught in .NET, it kills the process instantly. Or unhandled exceptions in async void methods or background threads. Or a native library crashing through interop.

Sometimes the logs were just lost because they were buffered. So configure sinks to flush on shutdown, log to stdout in containers, and add an AppDomain UnhandledException handler that logs synchronously as a last resort.

### scx | An old ASP.NET app hangs under load with low CPU. What is happening? | aspnet hangs low cpu, sync over async deadlock, result wait deadlock, requests stuck legacy aspnet, thread pool blocked
So high latency with low CPU means threads are waiting, not working. In older ASP.NET apps on .NET Framework, I've seen two causes again and again.

The first is sync over async. Code calls dot Result or dot Wait on a Task, say to call an async HttpClient method from a synchronous controller. Classic ASP.NET has a synchronisation context that allows one thread at a time per request. The async method tries to continue on that context, but the request thread is blocked waiting for it, so it deadlocks and the request hangs forever. And under load, even without full deadlocks, blocking threads drains the thread pool and new requests queue up.

The other is plain thread pool starvation. Lots of requests block threads on slow I/O, synchronous database calls or HTTP calls, and the thread pool only grows slowly, adding threads gradually, so requests sit waiting in queues.

To confirm, I take a memory dump during the hang and look at thread stacks with DebugDiag or WinDbg. Loads of threads waiting in Task Wait, Result, Monitor Enter, or in synchronous network calls, that's the pattern. Performance counters show requests queued going up while CPU stays low.

The fix is making the call chain async all the way, from the controller down, instead of blocking. If that's not possible right now, ConfigureAwait false in library code avoids the context deadlock, but it still blocks threads. Add timeouts to every outbound call. Raising the minimum threads is only temporary relief.

### scx | HttpClient calls start failing with socket exhaustion errors. How do you fix it? | socket exhaustion, httpclient per request, too many sockets time_wait, only one usage of each socket address, httpclientfactory fix
Yeah, errors like "Only one usage of each socket address is normally permitted", or connection failures under load with thousands of connections in TIME_WAIT, almost always mean the app creates a new HttpClient for every request.

Why it happens. Each HttpClient has its own connection pool. Disposing it closes the connections, but the OS keeps each closed socket in TIME_WAIT for a while, up to minutes. Under load you open new sockets faster than old ones get released, and you run out of ephemeral ports. The funny part is the using statement around HttpClient looks like good practice, but that's exactly the cause here.

To confirm, netstat shows tons of connections in TIME_WAIT to the same destination, and the code creates an HttpClient per call.

The fix is reusing connections. In ASP.NET Core, use IHttpClientFactory with typed or named clients, which pools and recycles the underlying handlers properly. Or one long-lived HttpClient, static or singleton, with SocketsHttpHandler and PooledConnectionLifetime set, say two minutes, so connections recycle periodically and DNS changes get picked up. A plain static client would miss those.

On .NET Framework, a shared static HttpClient plus ServicePointManager settings like ConnectionLeaseTimeout gives you similar behaviour.

I'd also check the connection limits per server, and that responses are disposed or fully read. Unread response bodies can keep connections busy, and that one can catch people out.

### scx | Real-time updates over SignalR or WebSockets keep disconnecting. How do you debug it? | signalr disconnects, websocket disconnect, signalr reconnecting, websocket proxy timeout, real time connection drops
Let me start with the pattern, because that tells you most of it. Disconnects usually come from something between client and server closing idle or long-lived connections, or from scaling.

So, do they happen after a fixed idle time, like 60 seconds? That's a proxy or load balancer idle timeout. Do they happen when servers are deployed or scaled? Only for users behind certain corporate networks?

Proxy and load balancer timeouts are the most common. Idle timeouts on the load balancer, IIS, nginx or a corporate proxy. SignalR's keep-alive pings, every 15 seconds by default, should keep things alive, as long as that interval is shorter than every timeout along the path. Some proxies don't handle WebSockets properly, so SignalR falls back to Server-Sent Events or long polling, which behave differently.

WebSockets not enabled. On IIS the WebSocket Protocol feature has to be installed, and load balancers have to allow the upgrade.

Multiple servers without sticky sessions. SignalR's negotiate and connect requests have to hit the same server, unless you use Azure SignalR Service, or WebSockets only with skip negotiation. Without that, connections fail randomly as soon as there are two instances. You also need a backplane like Redis so messages reach users connected to other servers.

Deployments and restarts drop connections, so clients need withAutomaticReconnect, and the app should resync state after reconnecting. And on the client side, browsers throttle background tabs and mobile networks switch.

Logging on both sides, with the transport and close reasons, shows you which case it is pretty fast.

### scx | Your rate limiter is blocking legitimate users from a corporate network. What do you do? | rate limiter blocking users, rate limit by ip problem, corporate nat rate limit, false positive rate limiting, 429 legitimate users
Right, so rate limiting by IP assumes one IP is one user. Big organisations, like a hospital or a sponsor's office, often route everyone through a few NAT or proxy IPs, so hundreds of real users look like one really busy client and they all get 429s.

For immediate relief, I find the affected IP ranges from the logs and raise their limits or temporarily allowlist them. But I look at the rest of that traffic first so we're not opening a hole for attackers.

The better fix is rate limiting by a more meaningful key. For authenticated endpoints, partition by user id or client id from the token, so each user gets their own budget. ASP.NET Core's rate limiting middleware supports partitioned limiters with a custom key. For API clients, partition by API key or client application. Keep IP-based limits only for unauthenticated endpoints like login, set them higher, and combine them with per-account limits, that's where brute-force protection really matters.

Also check the app actually sees the real client IP. Behind a load balancer, without forwarded headers configured, every request looks like it came from the load balancer's IP, so literally everyone shares one bucket. ForwardedHeaders middleware with known proxies fixes that. I've seen that one be the whole problem.

Then tune with real data. Look at the distribution of request rates per user, set limits well above legitimate peaks, send Retry-After headers, and monitor 429 counts per client so false positives show up quickly.

### scx | A partner says your API is slow, but your metrics look fine. How do you investigate? | partner says api slow, client reports slowness, server metrics fine client slow, latency discrepancy, network latency partner
Okay, if the client says slow and our server says fast, the time's going somewhere our server metrics don't measure. So I get specifics first, which endpoints, what times, request ids or timestamps, and what latency they're seeing.

Then I compare what we measure with what they experience. Our server metrics usually measure from when the request reaches the app to when the response leaves. They miss everything before that, TLS handshakes, load balancers, WAF inspection, API gateway processing, and queueing in the web server before the app even sees the request, like IIS queues or Kestrel connection limits. Load balancer and gateway logs record total time, so they help here.

Network. The partner might be far away, behind a slow proxy, or have packet loss. Big response bodies make it worse, so compression and smaller payloads help.

Connection handling. If their client opens a new connection for every request, each call pays for DNS, TCP and TLS setup, which can add hundreds of milliseconds across continents. Keep-alive and connection reuse on their side fixes that.

Their own processing. Their number might include their own retries, serialisation or queueing.

And averages hide tails. Our average could be fine while p99 is bad, and they might be hitting exactly those slow cases. So I check percentiles for their specific client id.

A joint test with timestamps on both sides, or a synthetic check from their region, usually settles where the time actually goes.

### scx | All health checks are green, but users report errors. What's wrong with your monitoring? | health checks green users errors, monitoring blind spot, false healthy, health check misleading, users report errors dashboards green
