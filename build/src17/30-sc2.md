### scx | The app crashes with no logs at all. How do you find out why? | process crash no logs, stackoverflow crash dotnet, unhandled exception crash, app dies silently, crash dump analysis
When a process dies without logging anything, it's usually a crash the app couldn't catch: a stack overflow, an out-of-memory kill from outside, a native crash, or an unhandled exception on a background thread before logs were flushed.

Find external evidence first. On Windows, the Application event log usually has a .NET Runtime error with the exception type and stack, or an Application Error entry with the faulting module. On Linux or containers, the exit code tells a lot: 137 means killed by SIGKILL, often out-of-memory; 139 is a segmentation fault; 134 is an abort. The orchestrator shows the reason, like OOMKilled, and the kernel log shows OOM killer messages.

Capture a crash dump next time: on Windows, ProcDump with the -e flag or Windows Error Reporting LocalDumps; for .NET on Linux, the DOTNET_DbgEnableMiniDump environment variables to write a dump on crash. Then analyse with dotnet-dump analyze, WinDbg or Visual Studio, looking at the exception and the thread stacks.

Common findings.

Stack overflow: infinite recursion, often from a property calling itself, or a deep recursive algorithm on unexpected data. It can't be caught in .NET, and kills the process instantly.

Unhandled exceptions in async void methods or background threads.

Native library crashes, from interop with unmanaged code.

Logs lost because they were buffered: configure logging sinks to flush on shutdown, and log to stdout for containers.

Add an AppDomain UnhandledException handler that logs synchronously, as a last resort.

### scx | An old ASP.NET app hangs under load with low CPU. What is happening? | aspnet hangs low cpu, sync over async deadlock, result wait deadlock, requests stuck legacy aspnet, thread pool blocked
High latency with low CPU means threads are waiting, not working. In older ASP.NET apps on .NET Framework, two causes are very common.

Sync over async: code calls .Result or .Wait() on a Task, for example to call an async HttpClient method from a synchronous controller. In classic ASP.NET, there's a synchronisation context that allows only one thread at a time per request; the async method tries to continue on that context while the request thread is blocked waiting for it, so it deadlocks, and the request hangs forever. Under load, even without full deadlocks, blocking threads drains the thread pool, and new requests queue up.

Thread pool starvation: many requests block threads on slow I/O, like synchronous database calls or HTTP calls, and the thread pool grows slowly, adding threads gradually, so requests wait in queues.

How to confirm: take a memory dump during the hang and look at thread stacks with DebugDiag or WinDbg. Many threads waiting in Task.Wait, Result, or Monitor.Enter, or in synchronous network calls, show the pattern. Performance counters show requests queued rising while CPU stays low.

Fixes: make the call chain async all the way, from the controller down, instead of blocking. If that's not immediately possible, ConfigureAwait(false) in library code avoids the context deadlock, but still blocks threads. Add timeouts to every outbound call. Raising minimum threads is a temporary relief only.

### scx | HttpClient calls start failing with socket exhaustion errors. How do you fix it? | socket exhaustion, httpclient per request, too many sockets time_wait, only one usage of each socket address, httpclientfactory fix
Errors like "Only one usage of each socket address is normally permitted" or connection failures under load, with thousands of connections in TIME_WAIT state, typically mean the app is creating a new HttpClient for every request.

Why it happens: each HttpClient instance has its own connection pool. Disposing it closes its connections, but the operating system keeps each closed socket in TIME_WAIT for a while, up to minutes. Under load, the app opens new sockets faster than old ones are released, and runs out of ephemeral ports. The using statement around HttpClient looks like good practice, but it's the cause here.

How to confirm: netstat shows many connections in TIME_WAIT to the same destination, and the code creates HttpClient per call.

Fixes: reuse connections. In ASP.NET Core, use IHttpClientFactory with typed or named clients, which pools and recycles the underlying handlers properly. Or use a single long-lived HttpClient, a static or singleton instance, with SocketsHttpHandler and PooledConnectionLifetime set, like two minutes, so connections are recycled periodically and DNS changes are picked up, which a plain static client would miss.

For .NET Framework, a shared static HttpClient plus ServicePointManager settings, like ConnectionLeaseTimeout, give similar behaviour.

Also check connection limits per server, and that responses are disposed or fully read, because unread response bodies can keep connections busy.

### scx | Real-time updates over SignalR or WebSockets keep disconnecting. How do you debug it? | signalr disconnects, websocket disconnect, signalr reconnecting, websocket proxy timeout, real time connection drops
Disconnections usually come from something between the client and the server closing idle or long-lived connections, or from scaling issues.

Check the pattern: do disconnects happen after a fixed idle time, like 60 seconds? That points to a proxy or load balancer idle timeout. Do they happen when servers are deployed or scaled? Do they affect only users behind certain corporate networks?

Common causes.

Proxy and load balancer timeouts: idle connection timeouts on the load balancer, IIS, nginx or a corporate proxy. SignalR's keep-alive pings, every 15 seconds by default, should keep connections alive, as long as the keep-alive interval is shorter than every timeout along the path. Some proxies don't support WebSockets properly, so SignalR falls back to Server-Sent Events or long polling, which may behave differently.

WebSockets not enabled: on IIS, the WebSocket Protocol feature must be installed; on load balancers, WebSocket upgrade must be allowed.

Multiple servers without sticky sessions: SignalR's negotiation and connection requests must reach the same server unless using Azure SignalR Service or WebSockets only with skip negotiation. Without that, connections fail randomly once there are two instances. A backplane, like Redis, is also needed so messages reach users connected to other servers.

Deployments and restarts: connections drop when the server restarts; clients must reconnect with withAutomaticReconnect, and the app should resync state after reconnecting.

Client-side: browsers throttle background tabs, and mobile networks switch.

Logging on both client and server, with transport and close reasons, quickly shows which case it is.

### scx | Your rate limiter is blocking legitimate users from a corporate network. What do you do? | rate limiter blocking users, rate limit by ip problem, corporate nat rate limit, false positive rate limiting, 429 legitimate users
Rate limiting by IP address assumes one IP is one user. Large organisations, like a hospital or a sponsor's office, often route everyone through a few NAT or proxy IPs, so hundreds of real users look like one very busy client, and they all get 429s.

Immediate relief: identify the affected IP ranges from logs and raise their limits or temporarily allowlist them, while understanding the rest of the traffic so we don't open a hole for attackers.

Better fix: rate limit by a more meaningful key.

For authenticated endpoints, partition by user id or client id from the token, so each user gets their own budget. ASP.NET Core's rate limiting middleware supports partitioned limiters with a custom key.

For API clients, partition by API key or client application.

Keep IP-based limits only for unauthenticated endpoints, like login, and set them higher, combined with per-account limits, which is where brute-force protection matters.

Also check that the app sees the real client IP: behind a load balancer, without forwarded headers configured, every request appears to come from the load balancer's IP, so everyone shares one bucket. ForwardedHeaders middleware with known proxies fixes that.

Tune limits with real data: look at the distribution of request rates per user, set limits well above legitimate peaks, return Retry-After headers, and monitor 429 counts per client so false positives show up quickly.

### scx | A partner says your API is slow, but your metrics look fine. How do you investigate? | partner says api slow, client reports slowness, server metrics fine client slow, latency discrepancy, network latency partner
When the client says slow and our server says fast, the time is being spent somewhere our server metrics don't measure. I get specifics first: which endpoints, what times, request ids or timestamps, and the latency they measure.

Then compare what we measure with what they experience.

Our server metrics usually measure from when the request reaches the app to when the response leaves it. They miss time spent before: TLS handshakes, load balancers, WAF inspection, API gateway processing, and queueing in the web server before the app sees the request, like IIS queues or Kestrel connection limits. Load balancer and gateway logs, which record total time, help here.

Network: the partner may be far away, behind a slow proxy, or have packet loss. Large response bodies make this worse. Compression and smaller payloads help.

Connection handling: if their client opens a new connection for every request, each call pays DNS, TCP and TLS setup, which can add hundreds of milliseconds across continents. Keep-alive and connection reuse on their side fix this.

Their own processing: their latency measurement may include their own retries, serialisation or queueing.

Averages hide tails: our average might be fine while the p99 is bad, and they may be hitting those slow cases. I check percentiles for their specific client id.

A joint test with timestamps on both sides, or a synthetic check from their region, usually settles where the time goes.

### scx | All health checks are green, but users report errors. What's wrong with your monitoring? | health checks green users errors, monitoring blind spot, false healthy, health check misleading, users report errors dashboards green
When dashboards say healthy and users say broken, the monitoring is checking the wrong things. First I help the users, then fix the blind spot.

Find the user problem directly: get specific examples, like the screen, the action, the time and the user, and trace those requests in logs. Often the errors are in a specific flow, a specific browser, or a specific tenant.

Typical blind spots.

Health checks that only test that the process responds, not that it can do real work. The app returns 200 on /health while the database, a queue or an external dependency is failing for actual requests.

Errors that aren't errors to the server: the API returns 200 with an error message in the body, or business failures, like "no kits available", that are logged as information. Front-end failures, like JavaScript errors, failed chunk loads or CORS failures, never reach server metrics.

Averages hiding problems: overall error rate at 0.5 percent looks fine, but it's 100 percent for one feature or one site.

Asynchronous failures: the API accepted the request, but the background processing failed later.

Fixes: synthetic monitoring of real user journeys; real-user monitoring and front-end error tracking; SLIs per important flow, not just overall; business metrics, like successful randomisations per hour; consistent use of correct HTTP status codes; and alerts on dead-letter queues and async processing failures. Each incident like this should add the missing signal.
