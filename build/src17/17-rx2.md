For React 18, update react and react-dom, and replace ReactDOM.render with createRoot. That turns on concurrent features and automatic batching. Code that depended on synchronous, unbatched updates in async callbacks might behave differently, so I'd test flows with timeouts and promises. In StrictMode, effects run twice in development, which exposes missing cleanups that need fixing. Types changed too. React.FC doesn't include children implicitly anymore, so components that take children have to declare them.

Honestly, the bigger effort is often the libraries. MUI, Redux, React Router, testing libraries, any design system packages all need to support the new version. In a shell with separate feature packages, every package's peerDependencies range has to allow the new version, and they all need testing together, because everything must share one React instance.

For React 19, run the official codemods, which handle a lot. Removed APIs include propTypes and defaultProps on function components, string refs, legacy context and ReactDOM.render. ref becomes a normal prop, so forwardRef can go over time. Error handling changed slightly.

Testing is critical. Unit tests, the end-to-end suite, and manual checks of key screens. In a regulated product, the upgrade is a validated change with regression testing.

Our shell is on React 17, so for us this is a real roadmap item.

### rx | What is useSyncExternalStore, and when do you need it? | usesyncexternalstore, external store react, subscribe to store react, tearing concurrent rendering, browser api hook
So useSyncExternalStore is a React 18 hook for subscribing to data that lives outside React. Like a state library's store, browser APIs, or any custom event source, in a way that's safe with concurrent rendering.

You give it a subscribe function, which registers a callback and returns an unsubscribe function, a getSnapshot function that returns the current value, and optionally getServerSnapshot for server rendering. React re-renders the component when the snapshot changes.

Why does it exist? Tearing. With concurrent rendering, React can pause rendering in the middle and continue later. If an external store changes during that pause, different components in the same render could read different versions of the data, and you'd show an inconsistent UI. useSyncExternalStore guarantees a consistent snapshot for the whole render.

Library authors are the main users. Redux's useSelector, Zustand and others use it internally. In app code, I use it for browser state. Like a useOnlineStatus hook that subscribes to the online and offline events and reads navigator.onLine. Or a hook that reads from localStorage and listens for storage events from other tabs. Or media queries.

One important rule, getSnapshot has to return the same value, by reference, if nothing changed. Returning a new object every time causes an infinite re-render loop. I learned that one the hard way, so now I return primitives or cached objects.

### rx | How do you update nested state immutably, and how does Immer help? | immutable state update react, nested state update, spread operator nested, immer, produce immer, mutating state react bug
Okay, React and Redux detect changes by comparing references. If you mutate an object or array in place, like pushing to an array in state, or setting user.address.city directly, the reference doesn't change. So React may not re-render, memoised components and selectors miss the change, and you get bugs that are hard to trace.

So updates have to create new objects for every level that changes. For nested state, that means spreading at each level. A new state object, with a new user object, with a new address object, with the new city. For arrays, use map to replace an item, filter to remove, and spread or concat to add, instead of push, splice or assigning by index. Newer array methods like toSorted and with return copies too.

Honestly, deep nesting gets verbose and error-prone, and that's a hint you should flatten or normalise the state.

Immer fixes the verbosity. Its produce function gives you a draft copy you can "mutate" with normal assignment and push, and Immer records the changes and produces a new immutable object, structurally sharing the unchanged parts. Redux Toolkit uses Immer inside createSlice reducers, which is why reducers there can be written in mutating style. use-immer gives a useImmer hook for component state.

The one rule to remember with Immer in Redux Toolkit is either mutate the draft or return a new value. Not both.
