### rx | What are discriminated unions, and how do you use them for UI state? | discriminated unions typescript, tagged union, loading success error state, exhaustive switch never, union types state
A discriminated union is a union of object types that share a common literal property, the discriminant, which TypeScript uses to narrow the type.

The classic UI use is request state. Instead of separate isLoading, error and data fields, which allow impossible combinations, like loading true with data and an error at the same time, I define one type: either status 'idle', or status 'loading', or status 'success' with data of type Shipment array, or status 'error' with an error message. For exhaustiveness, in a switch over the status, the default case assigns the value to a variable of type never. If someone adds a new status, like 'cancelled', without handling it, the compiler errors in every switch that misses it.

The same pattern fits many domain concepts: Redux actions with a type property, form steps, permission results, or events like KitDispensed versus KitReturned, each with different fields.

It's one of the most valuable TypeScript features for making front-end code correct, because it moves bugs from runtime to compile time.

They combine nicely: as const satisfies some type gives an immutable, precisely typed object that's also validated against a contract, like a route table, a permission map or a configuration object.

I use satisfies a lot for configuration objects, and as const for lists of literal values and lookup tables.

### rx | What are keyof, typeof, mapped types and conditional types in TypeScript? | keyof typeof, mapped types, conditional types, infer keyword, advanced typescript types, indexed access types
These are the building blocks of TypeScript's type-level programming, and the built-in utility types are made from them.

keyof T gives a union of T's property names. For Shipment, keyof Shipment is 'id' or 'status' or 'site'. It's useful for type-safe functions, like a sortBy function whose key parameter must be a real property of the item type.

Conditional types choose a type based on a condition: T extends string ? A : B. With infer, they can extract parts of types, like the element type of an array, or the resolved type of a promise, which is how Awaited and ReturnType work.

In everyday application code, I mostly use keyof, typeof and indexed access. Mapped and conditional types matter more when writing shared libraries, generic hooks, or typed API clients, where they let one generic definition give precise types for many cases.

### rx | TypeScript enums vs union of string literals: which do you prefer? | enums vs union types typescript, string literal union, const enum, typescript enum pitfalls, enum alternative
TypeScript enums, like enum ShipmentStatus with Pending and Shipped, look familiar to C# developers, but they have some quirks.

Numeric enums allow any number to be assigned, and have reverse mappings, so they're less type-safe than they look. Regular enums generate runtime JavaScript objects, adding code. const enums are inlined, but they cause problems with isolated module compilation, which tools like Vite, esbuild and Babel use. And enums are a TypeScript-only construct: Node's native TypeScript type stripping, and the erasableSyntaxOnly option, don't support them, because they aren't just types.

A union of string literals, like type ShipmentStatus equals 'Pending' or 'Shipped' or 'Delivered', has no runtime cost, works directly with JSON from APIs, which are plain strings, gives autocomplete and exhaustiveness checks, and is just JavaScript with types erased.

When I also need the values at runtime, for a dropdown list or validation, I define a const array or object with as const, and derive the union type from it, so one definition serves both purposes.

So for new code, I prefer string literal unions, or as const objects. Enums are fine where a codebase already uses them consistently, and string enums are much safer than numeric ones.

For API contracts generated from a .NET backend, I configure the generator to produce string unions, matching enums serialised as strings.

### rx | What is useSyncExternalStore, and when do you need it? | usesyncexternalstore, external store react, subscribe to store react, tearing concurrent rendering, browser api hook
useSyncExternalStore is a React 18 hook for subscribing to data that lives outside React, like a state management library's store, browser APIs, or any custom event source, in a way that's safe with concurrent rendering.

I give it a subscribe function, which registers a callback and returns an unsubscribe function, a getSnapshot function that returns the current value, and optionally a getServerSnapshot for server rendering. React re-renders the component when the snapshot changes.

The reason it exists is tearing. With concurrent rendering, React can pause rendering in the middle and continue later. If an external store changes during that pause, different components in the same render could read different versions of the data, showing an inconsistent UI. useSyncExternalStore guarantees a consistent snapshot for the whole render.

Library authors are the main users: Redux's useSelector, Zustand and others use it internally. In application code, I use it for browser state, like a useOnlineStatus hook that subscribes to the online and offline events and reads navigator.onLine, or a hook that reads from localStorage and listens for storage events from other tabs, or media queries.

One important rule: getSnapshot must return the same value, by reference, if nothing changed. Returning a new object each time causes an infinite re-render loop, so I return primitives or cached objects.

### rx | How do you update nested state immutably, and how does Immer help? | immutable state update react, nested state update, spread operator nested, immer, produce immer, mutating state react bug
React and Redux detect changes by comparing references. If I mutate an object or array in place, like pushing to an array in state, or setting user.address.city directly, the reference doesn't change, so React may not re-render, memoised components and selectors don't see the change, and bugs appear that are hard to trace.

So updates must create new objects for every level that changes. For nested state, that means spreading at each level: a new state object with a new user object with a new address object with the new city. For arrays, I use map to replace an item, filter to remove, and spread or concat to add, instead of push, splice or direct index assignment. Newer array methods, like toSorted and with, return copies.

Deep nesting gets verbose and error-prone, which is a hint to flatten or normalise state.

Immer solves the verbosity. Its produce function gives me a draft copy that I can "mutate" with normal assignment and push, and Immer records the changes and produces a new immutable object, structurally sharing unchanged parts. Redux Toolkit uses Immer inside createSlice reducers, which is why reducers there can be written in mutating style. use-immer provides a useImmer hook for component state.

The rule to remember with Immer in Redux Toolkit: either mutate the draft or return a new value, not both.
