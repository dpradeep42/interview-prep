### scx | Celery tasks are running twice or getting lost. How do you fix it? | celery duplicate tasks, celery task lost, celery acks late, celery visibility timeout, celery reliability
Both problems come from how Celery acknowledges tasks and how the broker redelivers them.

Tasks running twice.

Redis broker visibility timeout: with Redis, if a task isn't acknowledged within the visibility timeout, default one hour, it's redelivered to another worker. Long-running or ETA and countdown tasks scheduled further than the timeout get executed again. Fix: increase the visibility timeout above the longest task duration or delay, or use RabbitMQ.

acks_late with crashes: with acks_late enabled, a task is acknowledged only after it finishes, so if a worker dies midway, it runs again. That's intended, but means tasks must be idempotent.

Multiple beat schedulers: running celery beat on more than one instance schedules periodic tasks twice. Run exactly one beat, or use a scheduler with locking.

Retries after partial success: a task that did some work, then failed and retried, repeats the first part.

Tasks getting lost.

Default early acknowledgement: tasks are acknowledged when received, so if the worker crashes or is killed during deployment, the task is gone. Fix: acks_late with reject_on_worker_lost for important tasks.

Prefetch: workers reserve several tasks; if killed, prefetched tasks may be lost or delayed. Lower worker_prefetch_multiplier to one for long tasks.

Results expiring or the result backend misconfigured, so it looks lost.

The real safety net is idempotency: tasks take ids, check whether work was already done, and use database constraints or upserts. Plus monitoring with Flower or metrics for queue length, failures and retries, and graceful worker shutdown during deployments.
