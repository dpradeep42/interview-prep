### sqlx | What is a covering index, and what are INCLUDE columns? | covering index, include columns, index include, avoid key lookup, nonclustered index include
So a covering index is basically a non-clustered index that has every column a query needs, so SQL Server can answer the query from the index alone, without going back to the table.

Normally a non-clustered index stores the key columns plus a pointer to the row. If the query needs other columns, SQL Server does a key lookup for each matching row, jumping to the clustered index to fetch them. For a few rows that's fine. For thousands of rows, those lookups get really expensive, and the optimiser may just give up on the index and scan the whole table.

INCLUDE columns solve this. You create the index with key columns for filtering and sorting, and add the other columns with INCLUDE. Like an index on SiteId and Status, including ShipmentDate and KitCount. Included columns are stored only at the leaf level, not in the key, so they don't affect sorting and the key stays small, but the query is fully covered.

It's not free though. Every included column makes the index bigger and makes inserts and updates slower, because the index has to be maintained. So I don't include everything. I cover the important, frequent queries, and check the execution plan to confirm the key lookup is actually gone.

[Adding one covering index to the shipment search query removed a key lookup on about 40,000 rows and cut its time from several seconds to under 200 milliseconds.]

### sqlx | What is a key lookup in an execution plan, and how do you fix it? | key lookup, rid lookup, bookmark lookup, execution plan key lookup, fix key lookup
Okay, so a key lookup shows up in a plan when SQL Server uses a non-clustered index to find the matching rows, but the index doesn't have all the columns the query needs. For each row found, it goes back to the clustered index, using the clustering key, to fetch the missing columns. On a heap, a table without a clustered index, the same thing is called a RID lookup.

In the plan, you see an Index Seek joined with Nested Loops to a Key Lookup. The cost is per row, one extra random read for every row. If the seek returns 10 rows, who cares. If it returns 50,000 rows, it can dominate the whole query.

To fix it, I look at the key lookup operator's Output List, which shows exactly which columns it fetched. Then a few options. Add those columns to the index as INCLUDE columns, making it covering. Or drop columns from the query that aren't really needed, like a SELECT star where the screen only uses four columns. In EF Core that means projecting to a DTO with Select instead of loading whole entities. Or, if the predicate also uses columns that aren't in the key, rethink the index key order.

I also watch for the opposite problem. When the estimate is wrong, SQL Server may choose a seek plus lookup for way more rows than it expected. That's usually a statistics or parameter sniffing issue, not an index issue.

### sqlx | What is index fragmentation, and should you rebuild or reorganize? | index fragmentation, rebuild vs reorganize, index maintenance, fill factor, page splits
See, fragmentation happens as data gets inserted, updated and deleted. When a page is full and a new row has to go in the middle, SQL Server splits the page and moves half the rows to a new page somewhere else. Over time, the logical order of pages stops matching their physical order, that's external fragmentation. And pages get left partly empty, which is internal fragmentation, or low page density.

On spinning disks, logical order really mattered for range scans. On modern SSDs and SANs, external fragmentation matters much less. Low page density matters more, because more pages means more I/O and more memory used in the buffer pool.

You've got two maintenance options. Reorganize is lightweight and always online. It reorders the leaf pages and compacts them, good for moderate fragmentation. Rebuild drops and recreates the index, fully defragmenting it and updating its statistics with a full scan. It can be online in Enterprise edition and Azure SQL, but it's heavier.

The old rule of thumb was reorganize between 5 and 30 percent fragmentation, rebuild above 30. These days, honestly, a lot of experts say focus on updating statistics regularly, which often gives most of the benefit, and maintain indexes less often, based on measured impact. Ola Hallengren's maintenance scripts handle all this nicely.

And a suitable fill factor can reduce page splits on indexes with random inserts, like GUID keys.

### sqlx | What are snapshot isolation and read committed snapshot? | snapshot isolation, read committed snapshot, rcsi, row versioning, readers block writers, tempdb version store
Okay, so by default SQL Server uses read committed with locking. Readers take shared locks, so a reader can get blocked by a writer holding an exclusive lock, and a writer can get blocked by readers. Under heavy mixed load, you get blocking and sometimes deadlocks.

Row versioning is the alternative. When it's on, SQL Server keeps previous versions of modified rows in the version store, in tempdb, or in the database itself with Accelerated Database Recovery. Readers read the last committed version instead of waiting on locks.

Read committed snapshot isolation, RCSI, is a database setting that makes the default read committed level use versioning. Each statement sees data as it was when the statement started. Readers don't block writers, writers don't block readers. It's usually a big drop in blocking with zero code changes, and it's actually the default in Azure SQL Database.

Snapshot isolation is a separate level that a transaction has to ask for explicitly. The whole transaction sees a consistent snapshot as of its start. If it tries to update a row that another transaction changed after that snapshot, it gets an update conflict error, so the code has to handle it and retry.

What it costs you, more tempdb usage and a bit more overhead on updates. And code that relied on blocking behaviour, like a read-then-update pattern, may need explicit locking hints or a different approach. So I'd test that before switching it on.

### sqlx | Why is NOLOCK dangerous? | nolock, with nolock, read uncommitted, dirty reads, nolock problems, nolock hint
WITH NOLOCK is the same as the READ UNCOMMITTED isolation level. It tells SQL Server to read without taking shared locks and to ignore other transactions' locks. People add it to stop queries getting blocked, and yeah, the blocking goes away, but it can return wrong data.

The obvious problem is dirty reads. You read changes from a transaction that hasn't committed and might roll back, so you see data that never officially existed.

The less obvious problems are actually worse. Since the scan isn't protected while pages split and rows move around, a NOLOCK query can miss rows entirely, or read the same row twice. So a count or a sum can just be wrong, even for data that wasn't logically being changed. Queries can even fail with an error about data movement.

For approximate reports, like a dashboard estimate, maybe that's acceptable. But anywhere correctness matters, stock levels, financial data, clinical supply quantities, it's not acceptable at all.

The better fix for blocking is read committed snapshot isolation, which gives readers a consistent, committed version of the data without blocking. Plus good indexes and short transactions, so locks are held only briefly.

When I see NOLOCK sprinkled all over old stored procedures, I take it as a sign there was a blocking problem in the past, and I go looking for the real cause.

### sqlx | What is lock escalation in SQL Server? | lock escalation, row lock to table lock, escalation threshold, lock_escalation, large update blocking
Actually SQL Server normally takes fine-grained locks, row or page locks, so different transactions can work on different rows of the same table at once. But every lock uses memory. When a single statement grabs a lot of locks on one table, around 5,000, or when lock memory gets high, SQL Server converts them into a single table lock. That's lock escalation.

It saves memory, sure. But a table-level exclusive lock blocks everyone else on that table until the transaction ends. So a big update or delete, like updating 100,000 rows in one statement, can suddenly block every other user, even people working on completely unrelated rows.

What I do to avoid it is process large changes in batches. Like 2,000 to 4,000 rows per transaction in a loop, so each batch stays below the escalation threshold and locks get released frequently. That's my standard approach for purges, backfills and big data fixes. Good indexes help too, because without them a statement might scan and lock far more rows than it actually changes.

For partitioned tables, you can set the LOCK_ESCALATION table option to AUTO, so escalation goes to the partition level instead of the whole table. You can also disable it for a table, but that risks high lock memory, so I rarely do that.

Monitoring tools and extended events can show you when escalation is happening.

If data changes between them, results can be inconsistent, unless you use a transaction with snapshot or serialisable isolation. And ordering with Skip and Take needs a unique, stable sort.

So I use single queries for one collection or small data, split queries for multiple large collections. And honestly, often the best option is projecting with Select into exactly the DTO shape the screen needs.

### sqlx | What are EF Core interceptors, and what have you used them for? | ef core interceptors, savechangesinterceptor, dbcommandinterceptor, audit with interceptor, connection interceptor
So interceptors basically let you hook into EF Core's operations and inspect, change or suppress them. You register them with AddInterceptors when configuring the DbContext, and they can use dependency injection.

You've got a few kinds. SaveChanges interceptors run before and after SaveChanges, with access to the ChangeTracker. Command interceptors wrap every SQL command, so they see the command text and parameters and can modify them or the results. Connection interceptors run when connections open and close, transaction interceptors around transactions, and materialisation interceptors when entities get created from query results.

In my project, what we used them for, audit fields first of all. A SaveChanges interceptor sets CreatedBy, CreatedAt, ModifiedBy and ModifiedAt on any entity implementing IAuditable, using the current user service, so no developer has to remember. Audit trail too, capturing old and new values of changed properties into audit records in the same SaveChanges. Soft delete, turning deletes into updates of an IsDeleted flag. Outbox, converting domain events raised by entities into outbox rows in the same transaction. Slow query logging, a command interceptor that logs commands above a threshold with their duration. And connection setup, like setting session context with the tenant id through sp_set_session_context, for row-level security.

The nice part is all these cross-cutting things live in one place, not scattered through business code.

### sqlx | What are value converters in EF Core? | value converters, ef core hasconversion, store enum as string, strongly typed id ef core, encrypt column ef core
Okay, value converters transform a property's value when it's written to the database and when it's read back. You configure them with HasConversion in the model configuration.

Where I use them, enums as strings is the most common. HasConversion of string stores Delivered instead of 3, which is readable in the database and safe if enum members get reordered. Strongly typed ids, like a ShipmentId record struct wrapping a Guid or int, converted to the primitive for storage, so the domain model can't mix up a ShipmentId with a SiteId. Value objects, like a Money or EmailAddress type stored as a simple column. Collections or small objects stored as a delimited string or JSON, though JSON columns are better for that now. Date handling, like always storing DateTime as UTC and restoring the Kind on read. And encryption, encrypting a sensitive column on write and decrypting on read, though database features like Always Encrypted are usually stronger.

EF Core has lots of built-in converters, and since EF Core 6, pre-convention model configuration can apply a converter to every property of a type in one go.

The main catch is querying. EF translates queries using the stored values, so some operations on converted properties just can't be translated to SQL, like calling methods on a value object. Equality comparisons usually work fine, but anything fancier might fail or force client evaluation. So I always test the queries I actually need.

### sqlx | How do JSON columns work in EF Core and SQL Server? | json columns ef core, tojson, store json in sql server, openjson, json_value, owned types json
Actually from EF Core 7, you can map an owned type, or a collection of owned types, to a single JSON column, using ToJson in the configuration. Like a Study entity storing its flexible settings, or a shipment its list of temperature readings, as JSON, while the rest of the entity stays in normal columns.

The nice part is queries still work in LINQ. EF translates filters on JSON properties into SQL Server's JSON functions, like JSON_VALUE and OPENJSON. So you can write a Where on Settings.MaxKits greater than 10, and it becomes SQL. Updates can modify just part of the JSON. EF Core 8 added primitive collections, like a List of int stored as JSON. And SQL Server 2025 and Azure SQL now have a native json data type, which is more efficient than nvarchar.

When does it fit? Data that's naturally a document, owned by one entity and usually read together with it. Flexible attributes that vary by study or customer, configuration blobs, small nested lists. It saves you lots of tiny tables and joins.

When doesn't it fit? Data that needs relational integrity, foreign keys, frequent filtering and sorting, or joins with other tables. Filtering on JSON properties can't use normal indexes unless you add computed columns with indexes on the extracted values.

So I use it selectively. Honestly, it shouldn't become a way to avoid designing a schema.

### sqlx | What is DbContext pooling, and when does it help? | dbcontext pooling, adddbcontextpool, context pooling performance, pooled dbcontext factory
See, normally ASP.NET Core creates a new DbContext for each request and disposes it at the end. Creating one is fairly cheap, but in very high-throughput services, the setup work, initialising internal services and the change tracker, does add up.

With AddDbContextPool instead of AddDbContext, EF Core keeps a pool of DbContext instances. A request takes one from the pool, and at the end the context gets reset, tracked entities and state cleared, and goes back for the next request. That cuts allocation and setup overhead. AddPooledDbContextFactory does the same for code that creates contexts through a factory, like background services or Blazor.

Benchmarks show real gains only at very high request rates with simple queries, so for a lot of apps it's a minor optimisation. I'd turn it on when profiling shows context creation in the hot path.

Now the important limitation. Since instances are reused, the DbContext must not hold per-request state in its own fields, like a tenant id or current user injected through the constructor. A pooled instance could carry one request's state into another one, which is scary in a multi-tenant system. Constructor injection of scoped services into a pooled DbContext doesn't work the usual way. For multi-tenant cases, I set the per-request state after getting the context from the pool, with a factory or some custom approach that resets it.

And just to be clear, this is different from database connection pooling, which ADO.NET does anyway.

### sqlx | What is connection pool exhaustion, and how do you fix it? | connection pool exhaustion, timeout expired max pool size, connection leak, sqlconnection pool, max pool size reached
Okay so ADO.NET keeps a pool of open database connections per connection string, 100 by default. When code opens a connection, it gets one from the pool, and closing or disposing it gives it back. If all connections are in use, the next request waits, and after the timeout it fails with that famous error, "Timeout expired, the timeout period elapsed prior to obtaining a connection from the pool", which says max pool size was reached.

What usually causes it? Connection leaks, number one. Code opening connections or data readers without disposing them, especially when an exception skips the close, so they never go back. Then long-running queries or transactions hogging connections. Sync-over-async or thread pool starvation, where connections are held while threads wait. A traffic spike with slow database responses, so more requests hold connections at once. And slightly different connection strings creating separate pools, which people don't expect.

To diagnose, I check how many connections the app's host has in sys.dm_exec_sessions, look at what those sessions are doing, and review the code for missing using statements or DbContexts that aren't disposed. EF Core with DI handles disposal correctly if contexts are scoped properly.

The fix is disposing connections with using, shorter transactions, faster queries, and async all the way. Bumping Max Pool Size just hides the problem, honestly, and it can overload the database.

### sqlx | Dapper vs EF Core: when do you use each? | dapper vs ef core, micro orm, dapper performance, use both dapper and ef, raw sql vs orm
So Dapper is a micro-ORM. You write the SQL yourself, and Dapper maps results to objects and handles parameters. It's very fast, almost no overhead over raw ADO.NET, and you have full control over the SQL.

EF Core is a full ORM. LINQ queries translated to SQL, change tracking, relationships, migrations, concurrency handling, interceptors, a lot more. Developers are productive, and the code is strongly typed and easy to refactor.

The performance gap has narrowed a lot in recent versions. EF Core with AsNoTracking and projections to DTOs is close to Dapper for most queries, so performance alone rarely decides it anymore.

I use EF Core for most application code, especially writes. Change tracking, relationship handling, concurrency tokens and transactions save a lot of code and a lot of mistakes. And for typical queries too.

I reach for Dapper, or EF Core's raw SQL features like SqlQuery, when I need hand-tuned SQL. Complex reporting queries with window functions or CTEs, calls to legacy stored procedures, bulk reads where every millisecond counts, or databases EF doesn't model well.

And using both in the same service is completely fine, they can even share the same connection and transaction.

In our CIRT platform, the newer APIs use EF Core, while the legacy parts lean heavily on stored procedures with ADO.NET-style data access. So I work with both every week.
