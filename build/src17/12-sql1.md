### sqlx | What is a covering index, and what are INCLUDE columns? | covering index, include columns, index include, avoid key lookup, nonclustered index include
A covering index is a non-clustered index that contains every column a query needs, so SQL Server can answer the query from the index alone, without going back to the table.

Normally, a non-clustered index stores the indexed key columns plus a pointer to the row. If the query needs other columns, SQL Server does a key lookup for each matching row, jumping to the clustered index to fetch them. For a few rows that's fine, but for thousands of rows, those lookups get very expensive, and the optimiser may give up on the index and scan the whole table instead.

INCLUDE columns solve this. I create an index with key columns for filtering and sorting, and add other columns with INCLUDE. For example, an index on SiteId and Status, including ShipmentDate and KitCount. The included columns are stored only at the leaf level, not in the key, so they don't affect sorting and keep the index key small, but the query is fully covered.

There are trade-offs. Every included column makes the index bigger and makes inserts and updates slower, because the index must be maintained. So I don't include everything; I cover the important, frequent queries, and check the execution plan to confirm the key lookup is gone.

[Adding one covering index to the shipment search query removed a key lookup on about 40,000 rows and cut its time from several seconds to under 200 milliseconds.]

### sqlx | What is a key lookup in an execution plan, and how do you fix it? | key lookup, rid lookup, bookmark lookup, execution plan key lookup, fix key lookup
A key lookup appears in an execution plan when SQL Server uses a non-clustered index to find the matching rows, but the index doesn't contain all the columns the query needs. For each row found, it goes back to the clustered index, using the clustering key, to fetch the missing columns. On a heap, a table without a clustered index, the same thing is called a RID lookup.

In the plan, it shows as an Index Seek joined with a Nested Loops to a Key Lookup. The cost is per row: one extra random read for every row. If the seek returns 10 rows, it doesn't matter. If it returns 50,000 rows, it can dominate the query's cost.

To fix it, I look at the key lookup operator's Output List, which shows exactly which columns it fetched. Then I have a few options. Add those columns to the index as INCLUDE columns, making it covering. Remove columns from the query that aren't really needed, like a SELECT star where the screen only uses four columns; in EF Core, that means projecting to a DTO with Select instead of loading whole entities. Or, if the predicate also uses columns that aren't in the key, rethink the index key order.

I also watch for the opposite problem: when the estimate is wrong, SQL Server may pick a seek plus lookup for many more rows than expected, which is often a statistics or parameter sniffing issue.

### sqlx | What is index fragmentation, and should you rebuild or reorganize? | index fragmentation, rebuild vs reorganize, index maintenance, fill factor, page splits
Fragmentation happens as data is inserted, updated and deleted. When a page is full and a new row must go in the middle, SQL Server splits the page, moving half the rows to a new page somewhere else. Over time, the logical order of pages doesn't match their physical order, which is external fragmentation, and pages are left partly empty, which is internal fragmentation, or low page density.

On spinning disks, logical order really mattered for range scans. On modern SSDs and SANs, external fragmentation matters much less; low page density matters more, because more pages means more I/O and more memory used in the buffer pool.

There are two maintenance options. Reorganize is a lightweight, always-online operation that reorders leaf pages and compacts them, suitable for moderate fragmentation. Rebuild drops and recreates the index, fully defragmenting it and updating its statistics with a full scan; it can be online in Enterprise edition and Azure SQL, but it's heavier.

The old rule of thumb was reorganize between 5 and 30 percent fragmentation, and rebuild above 30. Today, many experts recommend focusing on updating statistics regularly, which often gives most of the benefit, and maintaining indexes less often, based on measured impact. Tools like Ola Hallengren's maintenance scripts handle this well.

A suitable fill factor can reduce page splits on indexes with random inserts, like GUID keys.

### sqlx | What are snapshot isolation and read committed snapshot? | snapshot isolation, read committed snapshot, rcsi, row versioning, readers block writers, tempdb version store
By default, SQL Server uses read committed with locking: readers take shared locks, so a reader can be blocked by a writer holding an exclusive lock, and a writer can be blocked by readers. Under heavy mixed load, that causes blocking and sometimes deadlocks.

Row versioning offers an alternative. When it's on, SQL Server keeps previous versions of modified rows in the version store, in tempdb, or in the database itself with Accelerated Database Recovery. Readers read the last committed version instead of waiting for locks.

Read committed snapshot isolation, RCSI, is a database setting that makes the default read committed level use versioning. Each statement sees data as it was when the statement started. Readers don't block writers, and writers don't block readers. It's usually a big reduction in blocking with no code changes, and it's the default in Azure SQL Database.

Snapshot isolation is a separate level that a transaction must request explicitly. The whole transaction sees a consistent snapshot as of its start. If it tries to update a row that another transaction changed after the snapshot, it gets an update conflict error, so the code must handle and retry it.

The costs: more tempdb usage and a bit more overhead for updates, and some code that relied on blocking behaviour, like a read-then-update pattern, may need explicit locking hints or a different approach.

### sqlx | Why is NOLOCK dangerous? | nolock, with nolock, read uncommitted, dirty reads, nolock problems, nolock hint
WITH NOLOCK, which is the same as the READ UNCOMMITTED isolation level, tells SQL Server to read without taking shared locks and to ignore other transactions' locks. People add it to stop queries being blocked, and it does make blocking go away, but it can return wrong data.

The obvious problem is dirty reads: reading changes from a transaction that hasn't committed and might roll back, so you see data that never officially existed.

The less obvious problems are worse. Because the scan isn't protected while pages split and rows move, a NOLOCK query can miss rows entirely, or read the same row twice. So a count or a sum can simply be wrong, even for data that wasn't being changed logically. Queries can even fail with an error about data movement.

For reports that are just approximate, like a dashboard estimate, this may be acceptable. But for anything where correctness matters, like stock levels, financial data, or clinical supply quantities, it's not acceptable.

The better fix for blocking is read committed snapshot isolation, which gives readers a consistent, committed version of the data without blocking, plus good indexes and short transactions, so locks are held briefly.

When I see NOLOCK sprinkled across old stored procedures, I treat it as a sign of a past blocking problem, and look for the real cause.

### sqlx | What is lock escalation in SQL Server? | lock escalation, row lock to table lock, escalation threshold, lock_escalation, large update blocking
SQL Server normally takes fine-grained locks, like row or page locks, so different transactions can work on different rows of the same table at the same time. But each lock uses memory. When a single statement acquires a lot of locks on one table, around 5,000, or when lock memory gets high, SQL Server converts them into a single table lock. That's lock escalation.

It saves memory, but a table-level exclusive lock blocks everyone else using that table until the transaction ends. So a large update or delete, like updating 100,000 rows in one statement, can suddenly block all other users, even those working on unrelated rows.

To avoid problems, I process large changes in batches, like 2,000 to 4,000 rows per transaction in a loop, so each batch stays below the escalation threshold and locks are released frequently. That's my standard approach for purges, backfills and large data fixes. Good indexes also help, because without them, a statement may scan and lock far more rows than it changes.

For partitioned tables, the LOCK_ESCALATION table option can be set to AUTO, so escalation goes to the partition level instead of the whole table. It can also be disabled for a table, but that risks high lock memory, so I rarely do that.

Monitoring tools and extended events can show when escalation happens.

### sqlx | How do you find what is blocking a query in SQL Server? | find blocking sql server, sp_whoisactive, blocking chain, head blocker, sys.dm_exec_requests, blocked process report
When users say the system is hanging, blocking is one of the first things I check.

For a live problem, I query sys.dm_exec_requests, which shows each running request, its wait type, how long it's been waiting, and the blocking_session_id. Following the blocking session ids leads to the head blocker, the session at the top of the chain, which is blocking others but isn't blocked itself. Then I look at what it's doing with sys.dm_exec_sql_text, and its open transactions.

The community procedure sp_WhoIsActive makes this much easier: it shows all active sessions with their SQL text, waits, blocking info, and optionally the plans and locks, in one result. Older tools like sp_who2 work too, with less detail.

Common findings: a transaction left open by application code, for example a transaction started and an exception swallowed without rollback, or a session that's "sleeping" with an open transaction; a long-running update or report without good indexes; or a query waiting for user input inside a transaction.

For recurring or past blocking, I enable the blocked process report with a threshold, like 10 seconds, and capture it with Extended Events, or use a monitoring tool.

Killing the head blocker is a last resort, because its transaction rolls back, which can take time. The real fix is shorter transactions, better indexes, or RCSI.

### sqlx | What is Query Store, and how have you used it? | query store, sql server query store, force plan, regressed queries, plan regression, query performance history
Query Store is a SQL Server feature, on by default for new databases since SQL Server 2022 and in Azure SQL, that records the history of queries, their execution plans, and their runtime statistics, like duration, CPU, reads and executions, over time. It's like a flight recorder for query performance.

It's very useful in a few situations. Plan regression: when a query suddenly becomes slow, Query Store shows whether its plan changed, and lets me compare the old good plan with the new bad one. I can then force the good plan as an immediate fix, while working on the root cause. Finding top resource consumers: which queries use the most CPU or I/O over a period. Comparing before and after a release or an index change. And on SQL Server 2022, automatic features like parameter-sensitive plan optimisation and query store hints build on it.

To use it, I look at the Regressed Queries and Top Resource Consuming Queries reports in SSMS, or query the catalog views directly.

### sqlx | Temporary table vs table variable: what is the difference? | temp table vs table variable, #temp vs @table, table variable performance, temp table statistics, tempdb objects
Both store intermediate results in tempdb, but they behave differently.

A temporary table, with a hash prefix like #Kits, is a real table in tempdb. It has statistics, so the optimiser can estimate row counts accurately. It can have indexes added after creation. It's visible to nested stored procedures called from the creating session. It's affected by transactions and rollbacks. And it can cause statement recompilations when its data changes significantly.

A table variable, like @Kits, is declared like a variable, scoped to the batch or procedure. It historically had no statistics, and the optimiser assumed it held one row, which led to terrible plans when it actually held thousands. Since SQL Server 2019, deferred compilation improves this by using the actual row count at first execution, but there are still no column statistics. Its data isn't rolled back by a transaction rollback, which is occasionally useful for logging. And it causes fewer recompilations.

My rule: table variables for small sets, a few hundred rows or fewer, and for passing data around simply. Temporary tables for larger intermediate results, especially when they're joined or filtered further, because good statistics matter there.

Also, table-valued parameters, which pass a set of rows from .NET to a procedure, are table variables, so the same considerations apply.

### sqlx | What are table-valued parameters, and how do you use them from .NET? | table valued parameters, tvp, pass list to stored procedure, sql where in list, user defined table type
A table-valued parameter lets me pass a whole set of rows from the application to a stored procedure or query in one parameter, instead of sending many separate calls or building a long IN list.

First, I create a user-defined table type in SQL Server, like dbo.KitIdList with a KitId column, and a primary key if useful. The procedure declares a parameter of that type, which must be READONLY. Inside, I can join to it like any table.

From .NET with ADO.NET or Dapper, I build a DataTable, or a list of SqlDataRecord, or use Dapper's AsTableValuedParameter, and pass it as a SqlParameter with SqlDbType.Structured and the type name. EF Core can use it through raw SQL with a SqlParameter too.

The benefits are big. One round trip instead of thousands. Set-based processing in SQL, like inserting or updating many rows in one statement. Fully parameterised, so no SQL injection, and the query plan can be reused, unlike dynamic IN lists of varying lengths, which create a new plan for every different count.

For very large data, like hundreds of thousands of rows, SqlBulkCopy into a staging table is faster.

Since EF Core 8, a list Contains in LINQ is translated using OPENJSON with a single JSON parameter, which solves the varying plan problem for simple cases.

### sqlx | Why are scalar user-defined functions slow in SQL Server? | scalar udf performance, scalar function slow, inline table valued function, udf inlining, function in where clause
A scalar user-defined function returns a single value, and is often used in a SELECT list or a WHERE clause, like dbo.GetKitStatus of KitId. It looks clean, but traditionally it has serious performance problems.

The function is executed once per row, like a hidden loop, with its own overhead for each call. If the function itself queries tables, it runs a query for every row, which is an N+1 problem inside the database. The optimiser couldn't see inside the function, so it estimated its cost poorly. And queries that use scalar functions couldn't run in parallel; the whole query was forced into a serial plan.

SQL Server 2019 introduced scalar UDF inlining, which automatically converts many simple scalar functions into inline expressions, removing much of the cost. But not every function qualifies, for example ones with certain constructs or that depend on the time, so I don't rely on it blindly.

Better alternatives: an inline table-valued function, which is a single SELECT statement returning a table. The optimiser expands it into the calling query like a view with parameters, so it's set-based and fully optimised, used with CROSS APPLY. Or put the logic directly in the query with a join or a CASE expression. Or a computed column, persisted and indexed if needed.

Multi-statement table-valued functions have similar problems to scalar ones, so I avoid them in hot paths too.

### sqlx | What are views and indexed views? | sql views, indexed view, materialized view sql server, view vs table, schemabinding view
A view is a stored SELECT query that acts like a virtual table. It doesn't store data itself; when I query it, SQL Server expands its definition into my query. Views are useful to simplify complex joins, to provide a stable interface to consumers, like a reporting tool, while the underlying tables change, and for security, giving users access to a view with selected columns and rows instead of the base tables.

Performance-wise, a normal view is just a query; it's as fast as the query it expands to. Views stacked on views can get hard for the optimiser, and can hide expensive joins, so I avoid deep nesting.

An indexed view, which other databases call a materialised view, has a unique clustered index, so its result is actually stored and kept up to date automatically when the base tables change. It's great for expensive aggregations that are read often, like totals of kits by site and status: the query reads pre-computed results instead of aggregating millions of rows.

But it has requirements and costs. The view must be created WITH SCHEMABINDING, use two-part names, and follow many restrictions, like no outer joins or certain aggregates. Every insert, update and delete on the base tables must also update the indexed view, so it slows writes, and can increase blocking.

So I use indexed views for read-heavy aggregates on tables that aren't written heavily.

### sqlx | What are the pros and cons of database triggers? | triggers sql server, after trigger, instead of trigger, trigger pros cons, audit trigger, inserted deleted tables
A trigger is code that runs automatically in the database when data changes, like AFTER INSERT, UPDATE or DELETE on a table, or INSTEAD OF a change, often used on views. Inside, the special inserted and deleted tables contain the new and old versions of the affected rows.

The advantages: a trigger runs no matter how the data is changed, whether by the application, a script, a data fix or another system. That makes triggers useful for audit trails and history tables, enforcing complex integrity rules that constraints can't express, and keeping denormalised data in sync.

The disadvantages are significant. Triggers are hidden: developers reading the application code don't see them, so behaviour seems magical and debugging is harder. They run inside the same transaction, so they make every write slower and hold locks longer. A common bug is writing triggers that assume one row, when a statement can affect many rows at once, so they must be set-based. Triggers can call other triggers, creating chains that are hard to follow. And business logic in triggers is hard to test and version.

So I use triggers sparingly, mainly for audit or history capture where guaranteed coverage matters, and keep them simple and set-based. For business rules, I prefer the application layer.

For history, temporal tables are now often a cleaner alternative.

### sqlx | What are temporal tables in SQL Server? | temporal tables, system versioned tables, history table, for system_time, point in time query, audit history sql
System-versioned temporal tables keep a full history of every change to a table automatically. When I enable them, SQL Server adds two period columns, valid from and valid to, and creates a linked history table. Whenever a row is updated or deleted, the old version is moved to the history table with the time range it was valid for. The application doesn't need any code for this.

I can then query the data as it was at any point in time using FOR SYSTEM_TIME, like AS OF a specific date and time, or BETWEEN two times, or ALL, to see every version of a row. That's great for audits, investigating "who changed this and what was it before", recovering from accidental updates, and reports that must show data as of a past date.

EF Core supports temporal tables too: I configure IsTemporal in the model, and LINQ has TemporalAsOf, TemporalAll and similar methods.

Some limitations. The period times are in UTC, based on when the transaction started. It records what changed and when, but not who changed it or why, so for a regulated audit trail, I still need the user and the reason, usually stored in columns on the row itself. History tables can grow large, so a retention policy is needed. And schema changes need care.

In regulated systems, I see temporal tables as a solid foundation for history, combined with application-level audit information.

### sqlx | What is table partitioning, and when does it help? | table partitioning, partition function, partition scheme, partition switching, partition elimination, large table management
Partitioning splits one large table into multiple partitions based on a column, usually a date, like one partition per month. To queries, it's still one table. Underneath, each partition is stored separately and can be on different filegroups.

It's mainly a data management feature, rather than a magic performance feature. The big wins are these. Partition switching: I can move a whole partition in or out of the table almost instantly, as a metadata operation. So archiving or deleting a month of old data becomes switching that partition out to an archive table, instead of a huge, slow, log-heavy DELETE. Loading data can work the same way. Maintenance per partition: index rebuilds and statistics updates can target only the recent, active partitions. And lock escalation can be set to the partition level.

For queries, partition elimination helps when the query filters on the partition column, because SQL Server only reads the relevant partitions. But if queries don't filter on it, partitioning can even make them slower, because they must check every partition. Good indexes usually matter more for query speed.

So I'd consider partitioning for very large tables, hundreds of millions of rows, with a natural time-based access pattern and data lifecycle needs, like logs, events or audit records. For normal-sized tables, it adds complexity without benefit.

### sqlx | What is database sharding, and what are its challenges? | sharding, database sharding, shard key, horizontal partitioning across servers, resharding, tenant sharding
Sharding splits data across multiple separate databases, often on separate servers, where each shard holds a subset of the rows, based on a shard key, like tenant id or customer id. It's horizontal scaling for the database, when one server can't handle the data volume or the write load, even after scaling up, indexing and adding read replicas.

Choosing the shard key is the most important decision. A good key spreads data and load evenly, and keeps related data together, so most queries hit only one shard. Tenant id is a natural choice for multi-tenant systems. A bad key creates hotspots, where one shard gets most of the traffic.

The challenges are significant. Queries across shards, like global reports, must fan out to every shard and combine results, which is slow and complex. Transactions across shards aren't available, so you need sagas or careful design. Unique constraints and joins only work within a shard. Resharding, when a shard gets too big, means moving data while the system is live. And operations, like backups, schema changes and monitoring, multiply with the number of shards.

So sharding is a last resort. Before it, I'd use caching, read replicas, archiving old data, and splitting data by service.

Database per tenant, like our database per study in IRT, is a simple form of sharding by tenant, with each study fully isolated.

### sqlx | What are read replicas, and what are their pitfalls? | read replicas, read scale out, always on availability groups readable secondary, replica lag, read write splitting
A read replica is a copy of the primary database that's kept up to date by replication and accepts read-only queries. Sending reporting and read-heavy queries to replicas takes load off the primary, which handles all the writes. In SQL Server, this is done with Always On availability groups and readable secondaries; in AWS, RDS and Aurora read replicas; and in Azure SQL, read scale-out.

In the application, I use separate connection strings: one for the primary, and one with ApplicationIntent equals ReadOnly for the replica, and route queries accordingly, for example a separate read-only DbContext for reports and search.

The main pitfall is replication lag. Asynchronous replicas can be seconds behind, or more under heavy load. So if a user saves something and the next screen reads from a replica, they might not see their change, which looks like a bug. For that, I read from the primary right after a write, or route all of that user's reads to the primary for a short time.

Other pitfalls: long-running queries on a replica can be affected by or interfere with replication, depending on the database. Replicas need the same indexes, and possibly extra ones for reporting. And failover changes which server is primary, so the connection should use the listener or cluster endpoint, not a server name.

So replicas suit reports, exports and search, where slight staleness is fine.

### sqlx | What are SQL Server recovery models and point-in-time restore? | recovery model, full recovery model, simple recovery, transaction log backup, point in time restore, rpo rto database
The recovery model controls how the transaction log is managed, and therefore which restore options you have.

In the simple recovery model, the log is truncated automatically after checkpoints, so it doesn't grow much, but there are no log backups. You can only restore to the time of your last full or differential backup. Anything after that is lost. It's fine for development databases or data that can be easily rebuilt.

In the full recovery model, every change is kept in the log until a log backup is taken. With a chain of full, differential and regular log backups, say every 15 minutes, I can restore the database to any point in time, like just before someone ran a bad update at 10:42. That's essential for production databases with important data. The log must be backed up regularly, otherwise it grows until the disk fills, which is a classic production incident.

Bulk-logged is a variation that minimally logs bulk operations, used temporarily during large loads.

These choices connect to RPO, how much data we can afford to lose, which drives the log backup frequency, and RTO, how fast we must recover, which depends on database size and restore speed.

And backups are only real if restores are tested. I'd regularly restore to a test server to prove the backups work and measure the time it takes. In managed services like RDS or Azure SQL, point-in-time restore is built in.

### sqlx | What is an implicit conversion, and how can it kill index usage? | implicit conversion, convert_implicit, nvarchar vs varchar index, data type mismatch query, ef core varchar parameter
An implicit conversion happens when SQL Server compares two values of different data types, and silently converts one to match the other, following data type precedence rules.

The problem is when the conversion is applied to the column instead of the parameter. A classic example: a column is varchar, but the application sends the parameter as nvarchar, which is .NET's default for strings. nvarchar has higher precedence, so SQL Server converts every value in the varchar column to nvarchar to compare. Depending on the collation, that can turn an index seek into an index scan of the entire table, because the index is on the original varchar values. The query still returns the right result, just much slower, and CPU goes up.

In the execution plan, it shows as CONVERT_IMPLICIT, and a warning icon on the SELECT operator mentions that the conversion may affect the cardinality estimate or seek plan.

The fix is to make the types match. In EF Core, I configure the column as non-Unicode, with IsUnicode false or the column type varchar, so EF sends varchar parameters. In Dapper or ADO.NET, I specify DbType.AnsiString for varchar columns. In stored procedures, parameters should be declared with the same type and length as the columns.

Other common mismatches are numbers stored in string columns, and dates compared to strings.

### sqlx | Why can a GUID primary key be a problem, and what are the alternatives? | guid primary key, uniqueidentifier clustered index, newsequentialid, guid fragmentation, uuid v7, int vs guid key
GUIDs are attractive as keys: they're globally unique, can be generated by the application before saving, don't reveal record counts, and make merging data from different databases easy.

The problem is using a random GUID, from NEWID or Guid.NewGuid, as the clustered index key in SQL Server. The clustered index orders the table by its key. Random values mean each new row goes to a random place in the index, not at the end. That causes constant page splits, heavy fragmentation, lower page density, more I/O, and more memory needed to keep the active part of the index cached. It's also 16 bytes, four times an int, and the clustered key is copied into every non-clustered index, so all indexes get bigger.

Alternatives. Sequential GUIDs: NEWSEQUENTIALID in SQL Server, or sequential GUID generation in the app, like EF Core's default value generator for SQL Server, or the new UUID version 7 with Guid.CreateVersion7 in .NET 9, which is time-ordered. Inserts then go to the end, like an identity.

Or use an int or bigint identity as the clustered primary key, and add a GUID as a separate public identifier with a unique non-clustered index, so external APIs don't expose sequential ids.

For DynamoDB or distributed stores, random keys are actually good, because they spread load, so the right choice depends on the database.

### sqlx | Identity vs sequence in SQL Server, and what is HiLo in EF Core? | identity vs sequence, sql sequence, hilo ef core, key generation, identity gaps, sequence cache
An identity column generates incrementing values automatically for one table when a row is inserted. It's simple and the most common choice. The application only knows the new id after the insert, which EF Core retrieves with OUTPUT. Identity values can have gaps, after rollbacks or server restarts, so they shouldn't be used where gaps matter, like invoice numbers that must be continuous.

A sequence is an independent database object that generates numbers on request with NEXT VALUE FOR. It isn't tied to a table, so one sequence can provide ids for several tables, or for a business number like a shipment reference. I can get a value before inserting, control start, increment, cycling and caching. It also has gaps after restarts when caching is used.

The trade-off is larger gaps and ids that aren't strictly in insert order.

For business-facing numbers, like a kit or shipment number with a format and no gaps allowed, I use a separate, dedicated mechanism with proper locking, rather than relying on identity values.

### sqlx | How do you implement soft delete with EF Core? | soft delete ef core, isdeleted flag, global query filter soft delete, hasqueryfilter, logical delete
Soft delete means marking a record as deleted, with an IsDeleted flag and usually DeletedAt and DeletedBy columns, instead of physically removing it. It's common when data must be kept for audit, regulatory reasons or undo, which is the norm in clinical systems.

In EF Core, I implement it in two parts.

### sqlx | What is the cartesian explosion problem, and when do you use split queries? | cartesian explosion, assplitquery, split query ef core, multiple include performance, single query vs split query
When I load an entity with several collection navigations using Include, like a Shipment with its Kits and its StatusHistory, EF Core by default generates one SQL query with JOINs. The problem is that joining two independent collections multiplies the rows: a shipment with 100 kits and 20 history entries returns 100 times 20, which is 2,000 rows, each repeating all the shipment's columns. With more collections or more parent rows, the data transferred grows enormously. That's the cartesian explosion, and EF Core logs a warning about it.

AsSplitQuery tells EF Core to load each collection with a separate SQL query: one for the shipments, one for the kits, one for the history, joined in memory. Total rows are 1 plus 100 plus 20, instead of 2,000. It can be enabled per query, or as the default with UseQuerySplittingBehavior.

But split queries have trade-offs. More round trips to the database. And consistency: the separate queries aren't run as one snapshot, so if data changes between them, the results can be inconsistent, unless I use a transaction with snapshot or serialisable isolation. Ordering with Skip and Take needs a unique, stable sort.

So I use single queries for one collection or small data, split queries for multiple large collections, and often the best option is projecting with Select into exactly the DTO shape the screen needs.

Audit fields: a SaveChanges interceptor sets CreatedBy, CreatedAt, ModifiedBy and ModifiedAt on any entity implementing IAuditable, using the current user service, so no developer has to remember. Audit trail: capturing old and new values of changed properties into audit records in the same SaveChanges. Soft delete: converting deletes into updates of an IsDeleted flag. Outbox: converting domain events raised by entities into outbox rows in the same transaction. Slow query logging: a command interceptor that logs commands taking longer than a threshold, with their duration. And connection setup: setting session context, like the tenant id, with sp_set_session_context, for row-level security.

They keep these cross-cutting concerns in one place, out of business code.

### sqlx | What are value converters in EF Core? | value converters, ef core hasconversion, store enum as string, strongly typed id ef core, encrypt column ef core
Value converters transform a property's value when it's written to the database and when it's read back. I configure them with HasConversion in the model configuration.

Common uses. Enums as strings: HasConversion of string stores "Delivered" instead of 3, which is readable in the database and safe if enum members are reordered. Strongly typed ids: a ShipmentId record struct wrapping a Guid or int, converted to the primitive for storage, so the domain model can't mix up a ShipmentId with a SiteId. Value objects: like a Money or EmailAddress type stored as a simple column. Collections or simple objects stored as a delimited string or JSON, though JSON columns are now better for that. Date handling, like storing DateTime always as UTC with the Kind restored on read. And encryption: encrypting a sensitive column on write and decrypting on read, though database-level features like Always Encrypted are often stronger.

EF Core has many built-in converters, and since EF Core 6, pre-convention model configuration can apply a converter to all properties of a type at once.

The main caveat is querying. EF translates queries using the stored values, so some operations on converted properties can't be translated to SQL, like calling methods on a value object. Comparisons for equality usually work fine, but anything more complex may fail or force client evaluation, so I test the queries I need.

### sqlx | How do JSON columns work in EF Core and SQL Server? | json columns ef core, tojson, store json in sql server, openjson, json_value, owned types json
EF Core 7 and later can map an owned type, or a collection of owned types, to a single JSON column, using ToJson in the configuration. For example, a Study entity could store its flexible settings, or a shipment its list of temperature readings, as JSON, while the rest of the entity stays in normal columns.

The nice part is that queries still work in LINQ. EF translates filters on JSON properties into SQL Server's JSON functions, like JSON_VALUE and OPENJSON, so I can write Where s.Settings.MaxKits greater than 10, and it becomes SQL. Updates can modify just part of the JSON. EF Core 8 added primitive collections, like a List of int stored as JSON, and SQL Server 2025 and Azure SQL now have a native json data type, which is more efficient than nvarchar.

When is it a good fit? For data that's naturally a document, owned by one entity and usually read together with it: flexible attributes that vary by study or customer, configuration blobs, or small nested lists. It avoids lots of small tables and joins.

When is it a bad fit? For data that needs relational integrity, foreign keys, frequent filtering and sorting, or joins with other tables. Filtering on JSON properties can't use normal indexes unless I add computed columns with indexes on the extracted values.

So I use it selectively, not as a way to avoid designing a schema.

### sqlx | What is DbContext pooling, and when does it help? | dbcontext pooling, adddbcontextpool, context pooling performance, pooled dbcontext factory
Normally, ASP.NET Core creates a new DbContext instance for each request and disposes it at the end. Creating a DbContext is fairly cheap, but in very high-throughput services, the setup work, like initialising internal services and the change tracker, adds up.

With AddDbContextPool instead of AddDbContext, EF Core keeps a pool of DbContext instances. When a request needs one, it takes one from the pool; at the end, the context is reset, clearing tracked entities and state, and returned to the pool for the next request. That reduces allocation and setup overhead. AddPooledDbContextFactory does the same for code that creates contexts through a factory, like background services or Blazor.

Benchmarks show measurable gains only for very high request rates with simple queries, so for many apps it's a minor optimisation. It's worth turning on when profiling shows context creation in the hot path.

The important limitation: because instances are reused, the DbContext must not hold per-request state in its own fields, like a tenant id or current user injected through the constructor, since a pooled instance could carry one request's state into another. Constructor injection of scoped services into a pooled DbContext doesn't work as usual. For multi-tenant scenarios, I set the per-request state after getting the context from the pool, using a factory or a custom approach that resets it.

Note this is different from database connection pooling, which ADO.NET does anyway.

### sqlx | What is connection pool exhaustion, and how do you fix it? | connection pool exhaustion, timeout expired max pool size, connection leak, sqlconnection pool, max pool size reached
ADO.NET keeps a pool of open database connections per connection string, 100 by default. When code opens a connection, it gets one from the pool, and closing or disposing it returns it to the pool. If all connections are in use, the next request waits, and after the timeout, it fails with an error like "Timeout expired. The timeout period elapsed prior to obtaining a connection from the pool. This may have occurred because all pooled connections were in use and max pool size was reached."

The common causes. Connection leaks: code that opens connections or data readers without disposing them, especially when an exception skips the close, so connections are never returned. Long-running queries or transactions holding connections for a long time. Sync-over-async or thread pool starvation, where connections are held while threads wait. A traffic spike with slow database responses, so more requests hold connections at once. And slightly different connection strings creating separate pools.

To diagnose, I check the number of connections from the app's host in sys.dm_exec_sessions, look at what those sessions are doing, and review code for missing using statements or DbContexts not disposed. EF Core and DI handle disposal correctly if contexts are scoped properly.

The fixes are disposing connections with using, shorter transactions, faster queries, and async code all the way. Increasing Max Pool Size only hides the problem, and can overload the database.

### sqlx | Dapper vs EF Core: when do you use each? | dapper vs ef core, micro orm, dapper performance, use both dapper and ef, raw sql vs orm
Dapper is a micro-ORM: I write the SQL myself, and Dapper maps results to objects and handles parameters. It's very fast, with almost no overhead over raw ADO.NET, and gives complete control over the SQL.

EF Core is a full ORM: LINQ queries translated to SQL, change tracking, relationships, migrations, concurrency handling, interceptors and much more. Developers are productive, and the code is strongly typed and refactor-friendly.

The performance gap has narrowed a lot in recent versions. EF Core with AsNoTracking and projections to DTOs is close to Dapper for most queries, so performance alone rarely decides it.

I use EF Core for most application code, especially writes, where change tracking, validation of relationships, concurrency tokens and transactions save a lot of code and mistakes, and for typical queries.

I use Dapper, or EF Core's raw SQL features like SqlQuery, when I need hand-tuned SQL: complex reporting queries with window functions or CTEs, queries against legacy stored procedures, bulk reads where every millisecond counts, or databases that EF doesn't model well.

Using both in the same service is completely fine, even sharing the same connection and transaction.

In our CIRT platform, the newer APIs use EF Core, while the legacy parts rely heavily on stored procedures with ADO.NET-style data access.
