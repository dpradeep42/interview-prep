### ngx | What is zone.js, and what does zoneless Angular mean? | zone.js, zoneless angular, ngzone, provideZonelessChangeDetection, run outside angular, change detection trigger
zone.js is a library that patches browser async APIs, like setTimeout, promises, DOM events and XHR, so Angular knows whenever some async work finishes. After any of these, Angular runs change detection to update the view. That's why, in classic Angular, changing a component property inside a click handler or an HTTP callback just works, without calling anything.

The downsides: it's a fairly heavy library, it triggers change detection very often, even when nothing relevant changed, async stack traces get harder to read, and native async/await can't be patched, so Angular had to downgrade it during builds.

The NgZone service lets you control it, for example runOutsideAngular for frequent events, like mousemove or a polling timer, so they don't trigger change detection on every tick.

Zoneless Angular removes zone.js entirely. Change detection is triggered explicitly by things Angular knows about: signals changing, the async pipe, event handlers bound in templates, and markForCheck. It was experimental in Angular 18, stable in 20, and it's the default for new apps since Angular 21, configured with provideZonelessChangeDetection in older versions.

The benefits are smaller bundles, better performance and cleaner debugging. Migrating requires components to work well with OnPush and signals, because code that changes state outside those triggers won't update the view anymore.

### ngx | What are @defer blocks in Angular? | defer blocks, @defer angular, deferrable views, lazy load component template, on viewport, on idle
@defer, introduced in Angular 17, lazily loads part of a template and its dependencies. Components, directives and pipes used only inside the @defer block are split into a separate JavaScript chunk, which is downloaded and rendered only when a trigger condition happens.

### ngx | What are computed and effect in Angular signals, and what are the pitfalls of effect? | computed signal, effect angular, signal effect pitfalls, untracked, derived state signals, allowsignalwrites
A computed signal derives its value from other signals: total equals computed of items() reduced to a sum. It's lazy and memoised: it only recalculates when one of the signals it read has changed, and only when someone reads it. It's read-only and should be a pure function. It's the right tool for derived state, like filtered lists, totals or flags.

An effect runs a side-effect function whenever the signals it reads change. It tracks dependencies automatically, runs at least once, and is cleaned up when its component is destroyed. Effects are meant for syncing with things outside Angular's signal world: writing to local storage, logging, calling a third-party chart library, or manual DOM work.

The pitfalls. Using effects to derive state, like an effect that sets another signal whenever a signal changes. That's what computed is for, and the effect version causes extra change detection cycles, timing issues, and possibly loops. Angular originally blocked signal writes inside effects by default for this reason. Unintended dependencies: every signal read inside the effect becomes a dependency, so reading something incidental re-runs the effect; untracked lets me read a signal without tracking it. Async work inside effects can race, so I use the cleanup function, onCleanup, to cancel previous work.

For data loading driven by signals, the newer resource and httpResource APIs are usually better than effects.

### ngx | inject() function vs constructor injection in Angular: what is the difference? | inject function angular, constructor injection angular, injection context, functional injection, inject vs constructor
Angular has two ways to get dependencies. Constructor injection declares them as constructor parameters, like constructor(private http: HttpClient). The inject function, available since Angular 14, gets them from inside the class body or a function: private http equals inject of HttpClient.

Both use the same injector hierarchy, so the dependency is the same. The differences are practical.

inject works in functions, not just classes. That enabled functional route guards, resolvers and HTTP interceptors, which are much shorter than class-based ones. It also allows reusable helper functions that inject things, like an injectStudyId function that reads the route.

Inheritance is easier: with constructor injection, a subclass must repeat all the base class's dependencies and pass them to super. With inject, the base class gets its own dependencies.

It works better with modern TypeScript and the useDefineForClassFields setting, where constructor parameter properties had ordering issues with field initialisers.

The Angular team now recommends inject, and there's a migration schematic to convert constructor injection. For unit tests, both work the same way with TestBed.

### ngx | How does Angular's hierarchical dependency injection work? | hierarchical injectors angular, providedin root, component providers, environment injector, element injector, service instance per component
Angular has a tree of injectors, and where a service is provided decides how many instances exist and who shares them.

At the top is the environment injector hierarchy. providedIn root in the Injectable decorator registers a singleton for the whole app, and it's tree-shakable: if nothing injects it, it's removed from the bundle. Services provided in an application's providers, or in a lazy-loaded route's providers, live in environment injectors. A lazy route with its own providers gets its own child injector, so a service provided there is a separate instance for that feature.

Then there's the element injector hierarchy, following the component tree. If a component lists a service in its providers array, each instance of that component gets its own instance of the service, shared with its children, and destroyed with the component. That's useful for state that belongs to one part of the screen, like a form wizard's state service or one editor instance per tab. viewProviders limits visibility to the component's own view, not projected content.

When a component injects something, Angular searches up the element injectors first, then the environment injectors, until it finds a provider. Modifiers change the search: Optional, Self, SkipSelf and Host, which are options on the inject function.

A common bug is accidentally providing a "global" service in a component's providers, creating separate instances and making shared state look broken.

### ngx | How do you handle token refresh on 401 in an Angular interceptor? | token refresh interceptor, 401 retry angular, refresh token interceptor, queue requests during refresh, httpinterceptorfn auth
An auth interceptor adds the access token to outgoing requests, and handles expired tokens transparently.

The flow: the interceptor attaches the bearer token to requests going to our API, and only to our API's URLs, never to third-party domains. If a response comes back 401, it tries to refresh the token, and on success, retries the original request with the new token. If the refresh fails, it logs the user out and redirects to the login page.

The tricky part is concurrency. A screen often fires several requests at once, and they might all get 401 at the same time. Without care, each one triggers its own refresh, and with refresh token rotation, the second refresh uses an already-used refresh token and fails, logging the user out. So the interceptor keeps a single in-flight refresh: a flag plus a BehaviorSubject, or a shared Observable with shareReplay. The first 401 starts the refresh; other requests wait for it with filter and take of one, then retry with the new token.

Other details: don't intercept the refresh call itself, to avoid loops; retry each request only once; and refresh proactively before expiry when possible, which avoids most 401s. Libraries like angular-auth-oidc-client or keycloak-angular handle much of this.

In our apps, the Keycloak adapter refreshes tokens before expiry, and the interceptor attaches the current token.

### ngx | What is server-side rendering and hydration in Angular? | angular ssr, hydration angular, angular universal, prerendering, incremental hydration, ssr benefits

Angular officially supports upgrading one major version at a time, so going from 8 to 17 is nine steps, not one jump. I'd plan it as a project.

First, preparation. Make sure there's a good test suite and an end-to-end smoke test, because each step needs verifying. Check the third-party libraries, since they're usually the real blocker: each library needs a version compatible with each Angular version, and some are abandoned, so they must be replaced. Also check the Node.js and TypeScript versions each Angular version needs.

Then, step by step, using the Angular Update Guide at angular.dev/update, which lists the changes for each version pair. For each version, run ng update for @angular/core and @angular/cli, which applies automatic migrations to the code, then update other Angular packages like Material, fix compile errors, run tests, and commit. Keeping each step in its own commit or branch makes problems easy to isolate.

The big milestones along the way: Ivy becoming the only engine in version 12 and 13, which removed View Engine and broke old libraries; the removal of IE11 support; strict typed forms in 14; standalone components in 14 and 15; and the builder change to esbuild and the new control flow in 17. Those later features are optional migrations, which I'd do after the upgrade itself.

Our older sub-apps are on Angular 8 and 12, and the plan has been to move modules to React rather than upgrade them all.

### ngx | How can you embed an Angular app inside a server-rendered ASP.NET MVC page? | angular in mvc, embed angular in razor page, angular sub app, angular hybrid mvc, angular inside legacy app
This is a common pattern in modernisation: the legacy MVC application keeps its layout, menu and authentication, while specific pages host a modern Angular sub-application.

The Angular app is built separately with the Angular CLI, producing JavaScript and CSS bundles. The MVC view for that page includes the bundles with script and link tags, and contains the root element, like a custom app-root tag, where Angular bootstraps. Settings that the Angular app needs, like the API URL, the current study, the user's culture or an anti-forgery token, can be passed from the server into the page, for example as a JSON block or data attributes that the app reads at startup.

Routing needs care. Either the Angular app uses hash-based routing, so it doesn't conflict with MVC routes, or MVC routes all sub-paths of that page to the same view, and Angular's base href is set to that page's path.

Authentication is shared: if the MVC site uses cookies, the Angular app calls the same site's APIs and the cookie is sent automatically, with anti-forgery protection; or both use SSO and tokens.

Styles must not clash with the MVC site's global CSS, so encapsulation and prefixed classes help.

Deploying means copying the Angular build output into the MVC site, ideally with hashed file names for cache busting.

Our legacy portal hosts Angular 8 and 12 sub-apps in this way, for screens like the advanced subject view and the material forecasting dashboard.
