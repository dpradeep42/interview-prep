### csx | What is clean architecture, and what is the dependency rule? | clean architecture, onion architecture, dependency rule, domain application infrastructure layers, hexagonal architecture
Okay, so clean architecture organises code in layers, with the business rules in the centre and the technical details on the outside. The core idea is the dependency rule, source code dependencies only point inward. Inner layers know nothing about the outer ones.

In a typical .NET solution, you'd have four projects. Domain is at the centre, entities, value objects, domain events and business rules, with no dependency on frameworks or databases. ### csx | What is vertical slice architecture, and how does it compare with clean architecture? | vertical slice architecture, feature folders, vertical slices vs layers, organize by feature, minimal api vertical slice

For CRUD-heavy services with lots of independent features, I like slices. For complex domains, I add a richer domain layer on top. That's how I'd balance it.

### csx | What do DRY, KISS and YAGNI mean, and when can DRY go wrong? | dry kiss yagni, dont repeat yourself, keep it simple, you aint gonna need it, wrong abstraction, design principles
DRY, Don't Repeat Yourself, means each piece of knowledge should have one authoritative place in the code, so a change doesn't need to happen in ten places. KISS, Keep It Simple, means picking the simplest solution that works, because simple code is easier to understand, test and change. ### csx | What is the Big-O complexity of common .NET collections? | big o collections, collection complexity, list vs dictionary vs linkedlist, sorteddictionary complexity, choose collection c#
Knowing this actually helps me pick the right collection, so let me go through the common ones.

List of T is a dynamic array. Index access is O(1). Adding at the end is O(1) on average, with the occasional resize. Inserting or removing in the middle is O(n), because elements shift. Contains or IndexOf is O(n), since it scans. Sort is O(n log n).

Dictionary and HashSet are hash tables, so O(1) average for add, remove and lookup by key, and no ordering.

SortedDictionary is a balanced tree, O(log n) for add, remove and lookup, and it keeps keys sorted. SortedList is an array-backed sorted collection, O(log n) lookup with binary search, but O(n) inserts. It uses less memory though.

LinkedList has O(1) insert and remove when you already have the node, but O(n) to find anything, and poor cache locality. So honestly it's rarely the best choice in practice.

Queue and Stack are O(1) for enqueue, dequeue, push and pop.

PriorityQueue, which came in .NET 6, is a heap. O(log n) to enqueue and to dequeue the smallest priority item, and O(1) to peek.

In real projects, the biggest win I've seen is replacing repeated List.Contains or First lookups inside loops with a Dictionary or HashSet built once. That turns O(n squared) into O(n), and it's usually a five-minute fix.

### csx | What is the difference between Task.Run and an async method? | task.run vs async, when to use task.run, task.run in asp.net core, cpu bound vs io bound, offload work thread pool
See, an async method that awaits I/O, like a database query or an HTTP call, doesn't hold a thread while it waits. The thread goes back to the pool, and when the I/O finishes, some thread picks up the continuation. That's what makes servers scale.

Task.Run is different. It queues a delegate to run on a thread pool thread, so it's for CPU-bound work, it moves the work off the current thread. In a desktop app, that's useful to keep the UI thread responsive while doing some heavy calculation.

Extra overhead, zero benefit. And wrapping a synchronous I/O call in Task.Run, what people call fake async, still blocks a thread, it just hides it somewhere else. The real fix there is a truly async API.

Task.Run in ASP.NET Core makes sense only in specific cases. Running several CPU-bound pieces of work in parallel, or kicking off fire-and-forget background work. Even for that, honestly, I prefer a hosted service with a queue, because it handles errors, scopes and shutdown properly.

So my rule is simple. async and await for I/O, and Task.Run only for CPU-bound work that really benefits from running somewhere else.

### csx | What are local functions, and how are they different from lambdas? | local functions, local function vs lambda, static local function, nested method c#
Okay, so a local function is just a method declared inside another method. It's only visible inside that method, so you keep helper logic close to where it's used without cluttering up the class.

How it's different from a lambda, a few things. Local functions can be declared after they're used, they're named, and recursion is easy. A lambda that captures variables allocates a closure object and a delegate on the heap. If you mark a local function static, it can't capture any variables of the enclosing method. That makes dependencies explicit and avoids accidental captures.

Two places I use them a lot. One is argument validation for iterators and async methods. An iterator's body runs lazily, so I validate arguments in the outer method, which runs immediately, and put the yield return logic in a local function. Same for async methods, when I want validation exceptions thrown right away and not inside the task. The other is breaking a long method into readable steps that don't really make sense as class-level methods.

And I use lambdas when I need a delegate to pass somewhere, like into LINQ or an event.
