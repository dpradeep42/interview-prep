### csx | Explain the Strategy pattern with a real example. | strategy pattern, strategy design pattern c#, replace switch with strategy, pluggable algorithm, strategy with dependency injection
The Strategy pattern defines a family of interchangeable algorithms behind one interface, so the calling code can pick one at runtime without knowing the details. It replaces big if-else or switch blocks that choose behaviour based on a type or setting.

For example, imagine calculating resupply quantities for sites, where studies use different methods: a simple min and max level, or a predictive method based on upcoming visits. Instead of one method with a growing switch statement, I define an interface, IResupplyStrategy, with a method like CalculateQuantity. Then I write MinMaxResupplyStrategy and PredictiveResupplyStrategy, each with its own logic and its own unit tests. The calling service gets the right strategy, based on the study's configuration, and just calls CalculateQuantity.

With dependency injection, I register all strategies, inject an IEnumerable of them, and pick by a key property, or use .NET 8 keyed services, resolving by the strategy name.

The benefits: each algorithm is isolated and testable, adding a new one doesn't touch existing code, which is the open-closed principle, and the choice can come from configuration.

The pluggable SFTP providers I built are also a Strategy: one interface, three provider implementations, selected by configuration.

I don't use it for two simple cases; an if statement is fine there.

### csx | Explain the Decorator pattern and how you use it with dependency injection. | decorator pattern, decorator design pattern c#, scrutor decorate, add caching with decorator, cross cutting decorator
The Decorator pattern wraps an object with another object that implements the same interface, adding behaviour before or after delegating to the wrapped one. The caller doesn't know it's talking to a decorator. Decorators can be stacked.

It's perfect for cross-cutting concerns that I don't want inside the business class: caching, logging, retries, timing metrics or authorization checks.

For example, I have an IStudyConfigProvider that reads study configuration from the database. I write a CachedStudyConfigProvider that also implements IStudyConfigProvider, takes the real provider in its constructor, and checks the cache first, only calling the inner provider on a miss. The database class stays simple, and caching can be added, removed or tested separately.

In ASP.NET Core's built-in DI, registering decorators is a bit manual: I register the inner class, then register the interface with a factory that creates the decorator around it. The Scrutor library makes it one line with services.Decorate.

The framework uses the pattern a lot too: DelegatingHandler for HttpClient is a decorator chain, where each handler adds behaviour like logging or auth headers. MediatR pipeline behaviours work the same way around handlers. And Stream wrappers, like BufferedStream or GZipStream, are decorators.

### csx | Explain the Factory pattern, and when you need a factory with DI. | factory pattern, factory method, abstract factory, factory with dependency injection, func factory c#
A factory is an object or method whose job is creating other objects, so the calling code doesn't need to know which concrete class to create or how to build it.

The Factory Method lets a method decide which class to instantiate, often based on input, like a NotificationSenderFactory that returns an EmailSender or SmsSender based on the channel. The Abstract Factory creates families of related objects that belong together.

With dependency injection, most object creation is handled by the container, so I need fewer factories. But I still use them when: the concrete type depends on runtime data, like the study's configuration or a user's choice, which the container can't know at startup; the object needs both injected services and runtime parameters, like a file processor that needs a logger and a file path; or creation is complex and needs validation.

In .NET, the factory itself is registered in DI and gets its dependencies injected. It can use IServiceProvider internally, carefully, or ActivatorUtilities.CreateInstance, which builds an object using DI for services plus the runtime parameters I pass. Keyed services in .NET 8 often replace simple factories that choose by name. IHttpClientFactory and IDbContextFactory are framework examples.

I avoid factories that just wrap new for no reason.

### csx | Explain the Builder pattern with an example. | builder pattern, builder design pattern c#, fluent builder, test data builder, step by step object creation
The Builder pattern constructs a complex object step by step, usually with a fluent interface, and produces the final object at the end with a Build method. It's useful when an object has many optional parts, or when the construction steps need validation, so a constructor with ten parameters would be confusing and error-prone.

ASP.NET Core itself is full of builders: WebApplication.CreateBuilder configures services, configuration and logging, and then Build gives the app. The configuration builder, the host builder, and EF Core's ModelBuilder are builders too. StringBuilder is a simple builder for strings.

In my own code, I use builders a lot for test data. A ShipmentBuilder has sensible defaults for every field, and methods like WithStatus, WithSite or WithKits. So a test only states what matters to it: new ShipmentBuilder().WithStatus(Delivered).Build(). Tests become shorter and clearer, and when the Shipment class gets a new required field, I only update the builder, not hundreds of tests.

Another use is building complex queries or requests, like a report filter or an email message with optional attachments and recipients, where Build validates that required parts are present.

For simple objects, object initialisers with required and init properties are enough, and I don't add a builder.

### csx | Explain the Observer pattern and how C# events relate to it. | observer pattern, observer design pattern c#, events c#, publish subscribe in process, iobservable
The Observer pattern lets one object, the subject, notify many other objects, the observers, when something changes, without knowing who they are. Observers subscribe and unsubscribe, and the subject just raises a notification. It keeps them loosely coupled.

In C#, events are the built-in implementation. A class declares an event, like ShipmentStatusChanged; other objects subscribe with plus-equals and a handler; and the class raises the event, which calls every subscriber. IObservable and IObserver are the more formal interfaces, and Rx.NET builds a powerful reactive library on them, and RxJS in Angular follows the same idea.

A big gotcha with events is memory leaks: the subject holds references to the subscribers' handlers, so a long-lived subject, like a singleton, keeps short-lived subscribers alive if they never unsubscribe. So I always unsubscribe, typically in Dispose.

Exceptions are another issue: if one handler throws, the following handlers aren't called.

In modern web back ends, I rarely use C# events for business logic. Inside a service, I use domain events with MediatR notifications, which work well with DI and scoped services. Across services, the same idea becomes publish-subscribe messaging through RabbitMQ or Kafka.

### csx | Explain the Adapter pattern with an example. | adapter pattern, adapter design pattern, wrapper class, wrap third party library, interface adapter c#
The Adapter pattern makes a class with an incompatible interface usable where a different interface is expected, by wrapping it in an adapter that translates the calls. It's like a travel plug adapter.

I use it mostly to isolate third-party libraries and external systems. For example, our SFTP integration needed to support three different SFTP libraries, and each has its own classes, method names, exceptions and connection handling. I defined our own simple interface, ISftpClient, with the operations we need, like Connect, Upload, Download and List. Then I wrote one adapter per library, each implementing ISftpClient and translating calls and exceptions to our own types. The rest of the code only knows ISftpClient.

The benefits: business code is independent of the library, so switching or upgrading the library touches only the adapter; it's easy to mock our own small interface in unit tests; and library-specific exceptions are translated into our own, so callers handle errors consistently.

The same idea applies to the anti-corruption layer for legacy systems, which is basically an adapter at the service boundary.

The Adapter differs from the Decorator, which keeps the same interface and adds behaviour, and from the Facade, which simplifies a complex subsystem behind one easier interface.

### csx | Explain the Chain of Responsibility pattern. | chain of responsibility, chain of responsibility pattern, pipeline pattern, middleware chain, handler chain c#
In the Chain of Responsibility pattern, a request passes through a chain of handlers. Each handler decides whether to process it, pass it on to the next, or stop the chain. The sender doesn't know which handler will deal with it.

ASP.NET Core's middleware pipeline is the best-known example. Each middleware gets the HttpContext and a next delegate; it can do work before calling next, after it, or short-circuit, like the authentication middleware returning 401 without calling the rest. HttpClient's DelegatingHandlers and MediatR pipeline behaviours are the same idea.

I've used it for validation and rule checks. For example, before allowing a subject to be randomised, a series of checks must pass: is the site active, is consent recorded, is the subject eligible, is there drug stock. Each check is a small class implementing a common interface. The chain runs them in order, and stops with a clear message at the first failure. Adding a new rule means adding a class and registering it, without touching the others, and each rule is unit-tested alone.

The risks are that the order of handlers matters and must be explicit, and that it can be hard to see which handler did what, so I log the outcome of each step.

### csx | What is the Specification pattern? | specification pattern, specification pattern ef core, reusable query filters, ardalis specification, business rule objects
The Specification pattern puts a business rule or query criteria into its own small, named, reusable object. Instead of repeating the same Where conditions in many places, I create a class like ActiveSitesInCountrySpecification, which encapsulates the condition, and use it wherever I need that filter.

A specification usually exposes an expression, like Expression of Func of Site, bool, so it can be used both with EF Core, which translates it to SQL, and in memory, to check a single object. Specifications can be combined with And, Or and Not, building complex rules from simple named ones.

With repositories, it keeps the repository small. Instead of a method for every query combination, like GetActiveSitesByCountryWithDepots, the repository has one method that takes a specification. The Ardalis.Specification library also lets specifications include related data, ordering and paging.

The benefits: business rules have names that the business understands, the logic lives in one place, and each specification is easy to unit test.

The downside is more classes and abstraction. With EF Core, many teams simply use extension methods on IQueryable, like query.ActiveOnly().InCountry(code), which give most of the benefit with less ceremony. That's often what I do, and I use full specifications when the rules are complex and reused heavily.

### csx | What is the Template Method pattern? | template method pattern, template method design pattern, abstract base class steps, hook methods, skeleton algorithm
The Template Method pattern defines the skeleton of an algorithm in a base class, with a fixed sequence of steps, and lets subclasses override specific steps without changing the overall flow.

For example, every file import follows the same process: open the file, validate the header, read each row, validate the row, transform it, save in batches, and write a summary. A base class, ImportJobBase, implements the Run method with that sequence, and declares abstract or virtual methods for the parts that differ, like ValidateRow and MapRow. A KitImportJob and a SiteImportJob only implement those parts. The common logic, like batching, error collection, logging and progress reporting, is written once, so every import behaves consistently.

Hook methods are optional steps with a default empty implementation, like OnCompleted, which subclasses can override if they need to.

The downside is that it relies on inheritance, which creates tight coupling between the base and derived classes, and deep hierarchies get hard to follow. So in modern code, I often prefer composition: one ImportRunner class that takes an IRowHandler strategy for the varying parts. It gives the same consistent flow, but the parts are swappable and easier to test.

BackgroundService in .NET is a small template method example: StartAsync is fixed, and you override ExecuteAsync.

### csx | What is clean architecture, and what is the dependency rule? | clean architecture, onion architecture, dependency rule, domain application infrastructure layers, hexagonal architecture
Clean architecture organises code in layers, with the business rules at the centre and technical details on the outside. The core idea is the dependency rule: source code dependencies only point inward. The inner layers know nothing about the outer ones.

In a typical .NET solution there are four projects. Domain is at the centre: entities, value objects, domain events and business rules, with no dependencies on frameworks or databases. Application contains use cases, like commands and queries with their handlers, and defines interfaces it needs, like IShipmentRepository or IEmailSender. It depends only on Domain. Infrastructure implements those interfaces with real technology: EF Core, SQL Server, RabbitMQ, SMTP, external APIs. And the API layer, the presentation, contains controllers or minimal API endpoints, and wires everything together with dependency injection.

Because Application defines the interfaces and Infrastructure implements them, the business logic doesn't depend on the database or frameworks. That's dependency inversion. So business rules are easy to unit test, and technical details can be changed with less impact.

The costs are more projects, more mapping and some ceremony, which is overkill for simple CRUD services.

Our newer IRT APIs follow this structure, with MediatR handlers in the Application layer and EF Core in Infrastructure.

### csx | What is vertical slice architecture, and how does it compare with clean architecture? | vertical slice architecture, feature folders, vertical slices vs layers, organize by feature, minimal api vertical slice
Vertical slice architecture organises code by feature instead of by technical layer. Each feature, or use case, like CreateShipment or GetSiteInventory, gets its own folder or file containing everything it needs: the request, the validation, the handler with its data access, and the response. Slices are independent of each other.

In a layered structure, adding one feature means touching a controller, a service, a repository, DTOs and mappings across several projects. With vertical slices, a change is usually contained in one place, so it's easier to find, understand and delete code. Each slice can also choose the simplest approach it needs: one might use EF Core with projections, another raw SQL with Dapper, without forcing every feature through the same abstraction layers.

Compared with clean architecture, which focuses on the direction of dependencies between layers, vertical slices focus on cohesion around features. They aren't really opposites: many teams combine them, keeping a shared domain model and infrastructure, but organising the application layer by feature, often with MediatR handlers.

The risk with vertical slices is duplication between slices, and shared logic leaking in random ways, so I extract shared domain rules into the domain model when I notice repetition.

For CRUD-heavy services with many independent features, I like slices. For complex domains, I add a richer domain layer.

### csx | What do DRY, KISS and YAGNI mean, and when can DRY go wrong? | dry kiss yagni, dont repeat yourself, keep it simple, you aint gonna need it, wrong abstraction, design principles
DRY, Don't Repeat Yourself, means each piece of knowledge should have one authoritative place in the code, so a change doesn't need to be made in many places. KISS, Keep It Simple, means choosing the simplest solution that works, because simple code is easier to understand, test and change. YAGNI, You Aren't Gonna Need It, means not building features or abstractions for imagined future needs.

DRY can go wrong when it's applied to code that only looks similar, but represents different business concepts. If I merge them into one shared method or base class, they're now coupled. When one changes for its own reasons, the shared code gets parameters and flags for each caller, and becomes harder to understand than the duplication was. That's the wrong abstraction. A common rule of thumb is the rule of three: tolerate duplication twice, and abstract when the third case shows the real pattern.

Across microservices, DRY is even riskier: sharing business code between services couples their deployments, so a little duplication is often better.

YAGNI and KISS work together: no generic plugin framework for one use case, no repository over a repository. I'd rather keep code simple and refactor when a real need appears, supported by good tests.

### csx | How do you benchmark C# code properly? | benchmarkdotnet, benchmark c#, micro benchmark, measure performance c#, memorydiagnoser
I use BenchmarkDotNet, because accurate micro-benchmarking is surprisingly hard to do by hand with a Stopwatch. The JIT needs warm-up, tiered compilation changes the code over time, the GC can pause in the middle, and the compiler can optimise away code whose result isn't used. BenchmarkDotNet handles all of that: it runs warm-up iterations, many measured iterations, separate processes, and gives statistics like the mean, error and standard deviation.

I write a class with methods marked Benchmark, for example comparing two ways of parsing a file line, set one as the Baseline, add MemoryDiagnoser to see allocations per operation, and use Params to test different input sizes. Then I run it in Release mode, never Debug, with BenchmarkRunner.

The results show time and allocated bytes per operation, and the ratio to the baseline. Allocations matter as much as time in a server app, because they drive GC pressure.

Some good practices: benchmark realistic data, return or consume results so code isn't eliminated, and remember that a micro-benchmark only tells you about that small piece. Before optimising, I first profile the real application, with dotnet-trace or a profiler, to find the actual hot spot, then use benchmarks to compare fixes.

I also keep important benchmarks in the repo to catch regressions.

### csx | Which .NET diagnostic tools do you use in production: dotnet-counters, dotnet-trace, dotnet-dump? | dotnet counters, dotnet trace, dotnet dump, dotnet gcdump, diagnose production dotnet, diagnostic tools

### csx | How do you load plugins dynamically in .NET? | plugin architecture, assemblyloadcontext, load assembly dynamically, plugin loading .net, isolated plugin dependencies
In modern .NET, AssemblyLoadContext is the way to load plugin assemblies at runtime, replacing AppDomains from .NET Framework.

The structure is: a shared contracts assembly defines the plugin interface, like IDataTransferJob, referenced by both the host and the plugins. Each plugin is built as a separate assembly with its own dependencies. At startup, the host scans a plugins folder, creates a custom AssemblyLoadContext for each plugin, loads its main assembly, finds types that implement the interface, and creates them, often with ActivatorUtilities so they get DI services.

The custom load context uses AssemblyDependencyResolver, which reads the plugin's deps.json, so each plugin can use its own versions of dependencies without conflicting with the host or other plugins. The shared contracts assembly must be loaded from the host's context, otherwise the types won't match and casting to the interface fails, which is the most common plugin bug.

Load contexts can be collectible, so a plugin can be unloaded, but only if no references to it remain.

A simpler alternative, when plugins are known at build time, is to reference them as packages and register them with DI, selected by configuration. That's often enough.

Our newer data transfer APIs run integration jobs as plugins, so new vendor integrations can be added without changing the host.

### csx | What is the Big-O complexity of common .NET collections? | big o collections, collection complexity, list vs dictionary vs linkedlist, sorteddictionary complexity, choose collection c#
Knowing this helps me pick the right collection.

List of T is a dynamic array. Index access is O(1). Add at the end is O(1) on average, with occasional resizing. Insert or remove in the middle is O(n), because elements shift. Contains or IndexOf is O(n), because it scans. Sort is O(n log n).

Dictionary and HashSet are hash tables, with O(1) average for add, remove and lookup by key, and no ordering.

SortedDictionary is a balanced tree, with O(log n) for add, remove and lookup, keeping keys sorted. SortedList is an array-backed sorted collection with O(log n) lookup by binary search, but O(n) inserts; it uses less memory.

LinkedList has O(1) insert and remove when you already have the node, but O(n) to find anything, and poor cache locality, so it's rarely the best choice in practice.

Queue and Stack are O(1) for enqueue, dequeue, push and pop.

PriorityQueue, added in .NET 6, is a heap: O(log n) to enqueue and dequeue the item with the smallest priority, and O(1) to peek.

In practice, the biggest real-world win is usually replacing repeated List.Contains or First lookups inside loops with a Dictionary or HashSet built once, turning O(n squared) into O(n).

### csx | What is the difference between Task.Run and an async method? | task.run vs async, when to use task.run, task.run in asp.net core, cpu bound vs io bound, offload work thread pool
An async method that awaits I/O, like a database query or an HTTP call, doesn't use a thread while waiting. The thread goes back to the pool, and when the I/O completes, a thread picks up the continuation. That's what makes servers scalable.

Task.Run queues a delegate to run on a thread pool thread. It's for CPU-bound work: it moves the work off the current thread. In a desktop app, that's useful to keep the UI thread responsive while doing a heavy calculation.

In ASP.NET Core, the request is already running on a thread pool thread. So wrapping work in Task.Run and immediately awaiting it just swaps one pool thread for another, adding overhead and no benefit. And wrapping a synchronous I/O call in Task.Run, called fake async, still blocks a thread; it just hides it. The right fix there is a truly async API.

Task.Run in ASP.NET Core is useful only in specific cases: running several CPU-bound pieces of work in parallel, or starting fire-and-forget background work, though for that I prefer a hosted service with a queue, because it handles errors, scopes and shutdown properly.

So: async and await for I/O; Task.Run only for CPU-bound work that genuinely benefits from running elsewhere.

### csx | What are tuples and deconstruction in C#? | tuples c#, value tuple, deconstruction, return multiple values, named tuple, tuple vs class
Tuples group a few values together without defining a class. Modern C# uses ValueTuple, which is a struct, with nice syntax: a method can return (int Count, decimal Total), and the caller reads result.Count and result.Total. The element names are a compile-time feature, so they make the code readable without creating a type.

Deconstruction splits a tuple, or any type with a Deconstruct method, into separate variables: var (count, total) equals GetSummary(). Records support it automatically through their positional parameters, and I can use underscore as a discard for values I don't need. Deconstruction also enables neat tricks, like swapping two variables with (a, b) equals (b, a).

Tuples also work well in pattern matching, like switching on a tuple of two values, for example (status, isUrgent) switch, which is much clearer than nested if statements.

I use tuples for private and internal helper methods that return two or three related values, and for local grouping in LINQ. I avoid them in public APIs, DTOs and anything serialised, because element names don't survive serialisation and they don't carry meaning or validation. If a tuple is passed around a lot, it's a sign it should become a record.

The older System.Tuple class, with Item1 and Item2, is a reference type, and I don't use it in new code.

### csx | What are local functions, and how are they different from lambdas? | local functions, local function vs lambda, static local function, nested method c#
A local function is a method declared inside another method. It's only visible inside that method, so it keeps helper logic close to where it's used without cluttering the class.

They differ from lambdas in a few useful ways. Local functions can be declared after they're used, are named, and can be recursive easily. They support generics, ref and out parameters, params and iterators with yield return. And performance: a lambda that captures variables allocates a closure object and a delegate on the heap. A local function that's only called directly can capture variables into a struct on the stack, so no allocation, which matters in hot paths.

Marking a local function as static prevents it from capturing any variables of the enclosing method, which makes dependencies explicit and avoids accidental captures.

Two common uses. First, argument validation for iterators and async methods. Because an iterator's body runs lazily, I validate arguments in the outer method, which runs immediately, and put the yield return logic in a local function. Same for async methods, when I want validation exceptions thrown immediately rather than inside the task. Second, splitting a long method into readable steps that don't make sense as class-level methods.

I use lambdas when I need a delegate to pass somewhere, like to LINQ or an event.
