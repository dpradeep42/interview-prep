In-process, the function code ran inside the Functions host process, sharing its .NET version and assemblies. ### azx | Azure Storage queues vs Service Bus queues: how do you choose? | storage queue vs service bus, azure storage queues, azure queue options, simple queue azure, service bus features
Both give you queues on Azure, but they're aimed at pretty different needs.

Azure Storage queues are part of a storage account. Simple and cheap, they can hold a huge number of messages, up to the storage account's capacity, and you access them over HTTP. Service Bus queues are an enterprise message broker. Service Bus for business messaging between services, where losing, duplicating or misordering messages actually matters, like order processing or integration events, and whenever you need publish-subscribe, dead-lettering, sessions or transactions.

Event Grid and Event Hubs are different again, event notification and high-throughput streaming rather than command queues.

For business integration flows like the ones we run on RabbitMQ with retries and dead-letter handling, I'd go with Service Bus as the natural Azure equivalent.

### azx | Cosmos DB vs Azure SQL: how do you choose? | cosmos db vs azure sql, nosql vs sql azure, when to use cosmos db, document database vs relational, azure database choice
Both are excellent, honestly, but they're built for different access patterns.

Azure SQL is a relational database. Strong schema, joins, complex queries and reporting, foreign keys, multi-row ACID transactions across any tables, and mature tooling. Cost works differently too. Cosmos DB charges by request units, so inefficient queries or a poor partition key get expensive fast. Azure SQL charges by compute and storage.

### azx | How do you build a reliable Service Bus consumer in .NET with ServiceBusProcessor? | servicebusprocessor, service bus consumer dotnet, azure service bus dotnet, peek lock dotnet, service bus retry
