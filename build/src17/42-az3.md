### azx | Azure Functions isolated worker vs in-process model: what is the difference? | azure functions isolated worker, in process vs isolated, dotnet isolated functions, functions worker model, migrate to isolated worker
Azure Functions for .NET historically had two hosting models.

In-process: the function code ran inside the Functions host process, sharing its .NET version and assemblies. It was fast to start and supported some bindings directly, but your app was tied to the host's .NET version, and dependency conflicts with the host's assemblies were common. Microsoft has ended support for the in-process model with .NET 8 as its last version, with support ending in November 2026.

Isolated worker: the function app runs in its own .NET process, separate from the host, communicating over gRPC. Benefits: you choose the .NET version, including newer ones as soon as they're supported; no assembly conflicts; full control over startup with the normal Program.cs, dependency injection and configuration, just like any .NET app; and middleware support, so cross-cutting concerns like logging, correlation and exception handling work like in ASP.NET Core. It's now the only supported model going forward.

Migration steps: change the project to the isolated worker packages, Microsoft.Azure.Functions.Worker and extension packages instead of WebJobs extensions; add a Program.cs with the host builder; update function signatures, since bindings and types differ, like HttpRequestData or ASP.NET Core integration for HTTP functions; replace ILogger injection patterns; update settings, like FUNCTIONS_WORKER_RUNTIME to dotnet-isolated; and test each trigger carefully, especially Durable Functions, which have their own isolated package.

If I were moving our AlertWatchDog-style scheduled checks to Azure Functions, I'd write them on the isolated model from the start, with timer triggers and dependency injection shared with our other .NET code.

### azx | How would you move from RabbitMQ to Azure Service Bus? | rabbitmq to service bus, migrate rabbitmq azure, service bus vs rabbitmq, exchanges to topics, messaging migration azure
The concepts map reasonably well, but not one to one, so I'd plan the mapping first.

Mapping: a RabbitMQ queue with a single consumer group maps to a Service Bus queue. A fanout or topic exchange with several queues bound to it maps to a Service Bus topic with subscriptions; routing keys and binding patterns map to subscription filters, SQL or correlation filters. Dead-letter exchanges map to the built-in dead-letter sub-queue on every queue and subscription. Retry queues with TTLs, which we build manually in RabbitMQ, can be replaced with Service Bus's delivery count and max delivery count, plus scheduled messages for delayed retries. Consumer acks map to peek-lock with Complete, Abandon or DeadLetter. Message ordering per key maps to sessions.

Differences to handle: Service Bus has message size limits per tier, 256 KB on Standard and up to 100 MB on Premium; lock durations need renewing for long processing; and duplicate detection is built in, based on message id.

Migration approach.

Abstract messaging behind an interface, or use a library like MassTransit, which supports both brokers, so switching transport is mostly configuration.

Run both in parallel: bridge messages from RabbitMQ to Service Bus for a period, or move one flow at a time, starting with low-risk ones.

Make consumers idempotent, since a migration increases the chance of duplicates.

Monitor dead-letter counts and queue lengths on both sides during cutover.

Connectivity matters for on-premise apps: they need reliable outbound access to Azure, ideally through private endpoints over ExpressRoute or VPN, and managed identity is only available to Azure-hosted workloads.

### azx | What is Dapr, and how does it help microservices on Azure Container Apps or Kubernetes? | dapr, distributed application runtime, dapr sidecar, dapr pub sub, dapr building blocks
Dapr, the Distributed Application Runtime, is an open-source project that runs as a sidecar next to each service and provides common microservice capabilities through simple HTTP or gRPC APIs, so application code doesn't depend on specific infrastructure SDKs.

Building blocks.

Service invocation: call another service by its app id, with service discovery, retries, mTLS and tracing handled by the sidecars.

Pub/sub: publish and subscribe to events, with the broker, like Service Bus, RabbitMQ, Kafka or Redis, chosen through configuration components.

State management: key-value state with pluggable stores, like Redis or Cosmos DB, with concurrency control.

Bindings: input and output connectors to external systems, like queues, storage or cron schedules.

Secrets and configuration: read from Key Vault or other stores through one API.

Workflows and actors for stateful patterns.

Resiliency policies: timeouts, retries and circuit breakers defined in configuration.

Why teams use it: services in different languages, like .NET, Node and Python, get the same capabilities consistently; switching infrastructure, like from RabbitMQ in one environment to Service Bus in another, is a configuration change; and observability is built in.

Azure Container Apps has Dapr integration built in, enabled per app with a setting, which makes it easy to try. On Kubernetes, it's installed in the cluster.

Trade-offs: an extra sidecar per service adds latency, resource use and another moving part to operate and upgrade; abstractions hide broker-specific features; and teams must learn its concepts. For a small number of .NET-only services, native SDKs with a library like MassTransit may be simpler.

### azx | What is Azure Bastion, and how do you access private VMs securely? | azure bastion, rdp ssh without public ip, secure vm access azure, jump box azure, just in time vm access
Exposing RDP or SSH ports to the internet is one of the most common causes of compromised VMs, because attackers scan constantly for them. Azure Bastion provides secure access without public IPs on the VMs.

How it works: Bastion is a managed service deployed into a dedicated subnet, AzureBastionSubnet, in the virtual network. Users connect through the Azure portal over HTTPS, or with the native RDP or SSH client using the Azure CLI on the Standard tier, and Bastion opens the RDP or SSH session to the private IP of the VM. The VMs need no public IP, and their network security groups can allow RDP and SSH only from the Bastion subnet.

Benefits: no exposed management ports; authentication through Entra ID for portal access, so MFA and Conditional Access apply; session recording on the Premium tier for audit; and with peering, one Bastion can serve VMs across peered networks.

Complementary controls.

Just-in-time VM access in Defender for Cloud opens management ports only when requested, for a limited time and specific source IP.

Entra ID login for VMs, so users sign in with their corporate identity rather than local accounts.

Run commands and automation, instead of interactive logins, for routine tasks.

Compared to AWS: the equivalent is Systems Manager Session Manager, which needs no network entry point at all, since it uses an agent connecting outbound.

My principle is the same in any environment: interactive server access should be rare, audited and time-limited, and routine work should go through automation and pipelines.

### azx | Azure Storage queues vs Service Bus queues: how do you choose? | storage queue vs service bus, azure storage queues, azure queue options, simple queue azure, service bus features
Both provide queues on Azure, but they're aimed at different needs.

Azure Storage queues are part of a storage account. They're simple and cheap, can hold very large numbers of messages, up to the storage account's capacity, and are accessed over HTTP. Messages are up to 64 KB. Features are basic: at-least-once delivery with a visibility timeout, a dequeue count, and that's mostly it. No ordering guarantee, no topics, no built-in dead-lettering; you implement poison message handling yourself, though Azure Functions moves messages to a poison queue after several failures.

Service Bus queues are an enterprise message broker: larger messages, up to 256 KB on Standard or 100 MB on Premium; FIFO ordering with sessions; built-in dead-letter queues; duplicate detection; scheduled and deferred messages; transactions across operations; topics and subscriptions with filters for publish-subscribe; and AMQP protocol support.

How I choose.

Storage queues: simple background work distribution, like resizing images or sending notifications, where order doesn't matter, high volume is expected and cost should be minimal, or when the app already uses a storage account.

Service Bus: business messaging between services, where losing, duplicating or misordering messages matters, like order processing or integration events; when you need publish-subscribe, dead-lettering, sessions or transactions.

Event Grid and Event Hubs are different again: event notification and high-throughput streaming, rather than command queues.

For business integration flows, like the ones we run on RabbitMQ with retries and dead-letter handling, Service Bus is the natural Azure equivalent.

### azx | How do you protect Key Vault with soft delete, purge protection and RBAC? | key vault soft delete, purge protection, key vault rbac vs access policies, key vault security, key vault firewall
Key Vault holds the most sensitive items: secrets, keys and certificates. Protecting the vault itself matters as much as using it.

Soft delete: deleted vaults and objects are kept for a retention period, 7 to 90 days, and can be recovered. It's now enabled on all vaults by default and can't be turned off.

Purge protection: prevents anyone, even administrators, from permanently purging deleted items or vaults until the retention period ends. This protects against malicious or accidental permanent deletion, especially important for encryption keys, because losing a key means losing the data it encrypts. Once enabled, it can't be disabled. I enable it for production vaults, especially those holding keys used for encryption at rest.

Access control: Azure RBAC is now the recommended permission model, instead of vault access policies. RBAC gives fine-grained roles, like Key Vault Secrets User for reading secrets, can be scoped down to individual secrets, is managed in the same way as other Azure permissions, and works with Privileged Identity Management for just-in-time admin access. Access policies were vault-wide and harder to audit.

Network: disable public network access and use private endpoints, or at least the vault firewall with allowed networks.

Separate vaults per application and environment, so access and blast radius are limited.

Monitoring: diagnostic logs to Log Analytics, with alerts on unusual access patterns, failed access attempts, and deletions.

Rotation: set expiry dates on secrets and certificates, with Event Grid notifications before expiry, and automate rotation where possible.

### azx | How do Azure SQL elastic pools help when you have many databases? | azure sql elastic pool, elastic pool many databases, database per tenant azure, edtu vcore pool, saas database pool
An elastic pool lets many Azure SQL databases share a set amount of resources, compute and storage, instead of each database having its own fixed size. Databases use what they need from the pool, within per-database minimum and maximum limits.

Why it helps: in a database-per-tenant or database-per-customer model, most databases are idle or lightly used most of the time, and their peaks happen at different times. Sizing each database for its own peak wastes money. In a pool, the combined capacity can be much smaller than the sum of individual peaks, so costs drop significantly while each database still gets resources when busy.

This pattern is very similar to a system with one database per study plus a master database. Studies have different activity levels: a few are in busy enrolment phases while others are in maintenance or closing, which fits pooling well.

Considerations.

Sizing: monitor combined usage and set the pool size to handle the busiest concurrent load, with per-database caps so one busy database can't starve others, the noisy neighbour problem.

Very large or consistently busy databases may be better as single databases outside the pool.

Operations across many databases: Elastic Jobs run T-SQL across all databases in a pool for maintenance or schema changes, and deployment pipelines need to update all databases consistently.

Limits: there's a maximum number of databases per pool, so very large estates need several pools.

High availability and backups work per database, as usual, and failover groups can include pooled databases.

On-premise, the equivalent is consolidating databases on shared instances, but elastic pools add per-database limits and easier scaling.

### azx | Cosmos DB vs Azure SQL: how do you choose? | cosmos db vs azure sql, nosql vs sql azure, when to use cosmos db, document database vs relational, azure database choice
Both are excellent, but they're built for different access patterns.

Azure SQL is a relational database: strong schema, joins, complex queries and reporting, foreign keys, multi-row ACID transactions across any tables, and mature tooling. It fits most business systems, especially with complex relationships and reporting needs, like clinical supply data with studies, sites, kits and shipments all linked together.

Cosmos DB is a globally distributed NoSQL database, with document, key-value and other APIs. It offers single-digit millisecond reads and writes at any scale, automatic horizontal scaling through partitioning, multi-region writes, tunable consistency levels, and a change feed. Transactions are limited to items within one logical partition, and queries across partitions are more expensive. You design the data model around access patterns, often denormalised, with the partition key as the most important decision.

When I'd choose Cosmos DB: very high scale with predictable access by key, like user profiles, device telemetry, session state, product catalogues or event data; globally distributed apps needing low latency in many regions; flexible schemas that change often; and event-driven architectures using the change feed.

When I'd choose Azure SQL: complex relationships and queries, ad hoc reporting, strong consistency across many entities, and teams with strong SQL skills. Most line-of-business systems fall here.

Cost: Cosmos DB charges by request units, so inefficient queries or poor partition keys get expensive quickly; Azure SQL charges by compute and storage.

Often the best architecture uses both: SQL for the core transactional system, and Cosmos DB for specific high-scale features.

### azx | How do you build a reliable Service Bus consumer in .NET with ServiceBusProcessor? | servicebusprocessor, service bus consumer dotnet, azure service bus dotnet, peek lock dotnet, service bus retry
The Azure.Messaging.ServiceBus SDK provides ServiceBusProcessor, which handles receiving, concurrency and lock management, so I don't write receive loops by hand.

Setup: create one ServiceBusClient per application, registered as a singleton, using DefaultAzureCredential with managed identity rather than connection strings. Create a processor for a queue or topic subscription with options: MaxConcurrentCalls to control parallelism, PrefetchCount for throughput, AutoCompleteMessages set to false so I complete messages explicitly, and MaxAutoLockRenewalDuration so locks are renewed for long-running processing.

Handlers: ProcessMessageAsync receives each message. I deserialise and validate the body, process it idempotently, checking the message id against a processed-messages store or using upserts, then call CompleteMessageAsync. For invalid messages that will never succeed, DeadLetterMessageAsync with a reason and description. For transient failures, let the exception propagate or abandon the message, so it's retried, and after MaxDeliveryCount attempts, Service Bus dead-letters it automatically. ProcessErrorAsync logs errors from the processor itself, like connection issues.

Hosting: run the processor inside a BackgroundService, starting it in StartAsync and stopping it gracefully in StopAsync, so in-flight messages finish during deployments.

Ordering: for per-entity ordering, use sessions with ServiceBusSessionProcessor.

Delayed retries: schedule a copy of the message for later with an attempt count, and complete the original, for backoff beyond immediate redelivery.

Observability: the SDK supports distributed tracing, so traces connect producer and consumer; monitor active and dead-letter message counts with alerts.

These are the same reliability habits as our RabbitMQ consumers, translated to Service Bus.
