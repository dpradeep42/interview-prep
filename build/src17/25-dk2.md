### dkx | A Kubernetes Service returns 503 or has no endpoints. How do you troubleshoot it? | service no endpoints, 503 ingress kubernetes, selector mismatch, service not routing, endpointslice empty, targetport wrong
When traffic through a Service or Ingress fails with 503 or connection refused, I follow the path from the outside in, checking each hop.

First, does the Service have endpoints? kubectl get endpointslices for that service, or kubectl describe service. If the endpoints list is empty, the Service isn't selecting any ready pods. The two usual reasons: the Service selector doesn't match the pod labels, maybe a typo, or a label changed in the Deployment but not in the Service; or the pods exist but aren't ready, because their readiness probe is failing, and Kubernetes removes unready pods from endpoints on purpose.

Second, ports. The Service's targetPort must match the port the container actually listens on. A classic .NET example: since .NET 8, the container images listen on 8080 by default, but the Service still points to 80, so everything is refused.

Third, the app itself. I port-forward directly to a pod, kubectl port-forward pod/name 8080, and call it. If that works, the problem is in the Service or Ingress; if not, it's the app.

Fourth, the Ingress or Gateway: the backend service name and port in the rule, the host and path matching, TLS secrets, and the ingress controller's logs, which usually say clearly that there's no healthy upstream.

Finally, NetworkPolicies that block traffic from the ingress controller's namespace to the app's namespace.

### dkx | A node shows NotReady. What do you do? | node notready, kubelet not ready, node pressure, node troubleshooting kubernetes, disk pressure memory pressure
NotReady means the control plane hasn't received healthy status from the node's kubelet for a while, about 40 seconds by default. After a few minutes, pods on that node are marked for eviction and rescheduled elsewhere, provided there's capacity and the workloads have more than one replica.

My first step is kubectl describe node, looking at Conditions and recent events. The conditions say a lot: MemoryPressure, DiskPressure or PIDPressure being true points to resource exhaustion; NetworkUnavailable points to the network plugin; and if the kubelet has simply stopped posting status, the Ready condition shows Unknown.

Common causes. The kubelet or container runtime crashed or is stuck, often visible in the node's system logs with journalctl. The disk filled up with images, logs or emptyDir data, which triggers disk pressure and image garbage collection. Memory exhaustion where system processes got OOM-killed because pods had no limits. Network problems between the node and the control plane, like security group or firewall changes, or expired node certificates. On cloud providers, the underlying VM may be impaired or being retired.

For immediate impact, I cordon the node so nothing new lands there, and drain it if it's partly working, so pods move cleanly.

On managed node groups, often the quickest fix is to replace the node, letting the autoscaler or node group create a fresh one, and then investigate the root cause from logs rather than nursing the broken node.

### dkx | Pods are being evicted. Why, and how do you stop it? | pod evicted, eviction kubernetes, ephemeral storage eviction, node pressure eviction, priority class, evicted pods cleanup
An evicted pod was stopped by the kubelet or the API, not because the app crashed. kubectl describe pod shows the reason, and it's usually one of these.

Node pressure eviction. When a node runs low on memory, disk or process ids, the kubelet evicts pods to protect the node. It chooses by quality of service and usage: BestEffort pods first, then Burstable pods using more than their requests, and Guaranteed pods last. Fix: set realistic requests, so heavy pods count properly at scheduling time, set memory limits, and right-size nodes.

Ephemeral storage. A container writing too much to its writable layer or an emptyDir volume, like large temp files or logs written to files instead of stdout, exceeds its ephemeral storage limit or fills the node's disk. Fix: set ephemeral-storage requests and limits, write logs to stdout, clean up temp files, and use a persistent volume for big data.

Preemption. A higher-priority pod needed room, so the scheduler evicted lower-priority pods. That's by design if PriorityClasses are used; critical services should have higher priority than batch jobs.

API-initiated eviction, during node drains for upgrades or autoscaler scale-down, which PodDisruptionBudgets control.

Evicted pods stay listed with status Failed until garbage collected, which is just noise, but a steady stream of evictions is a signal that capacity or limits need attention.

### dkx | How do you debug a running container that has no shell? | kubectl debug, ephemeral container, debug distroless, kubectl exec no shell, node debugging kubernetes
With distroless or chiseled images, kubectl exec with bash fails, because there's no shell. That's good for security, but I still need ways to debug.

Of course, the first tools are still logs, metrics and traces; interactive debugging in production is a last resort, and access to it should be restricted and audited.

### dkx | How do taints, tolerations and node affinity work? | taints and tolerations, node affinity, node selector, dedicated node pool, gpu nodes kubernetes, schedule on specific nodes
These features control which pods run on which nodes, from two directions.

Taints are on nodes and repel pods. A taint like dedicated=batch:NoSchedule means no pod is scheduled there unless it tolerates that taint. NoExecute also evicts running pods that don't tolerate it, and PreferNoSchedule is a soft version. Kubernetes uses taints itself, for example on nodes that are not ready or under pressure.

Tolerations are on pods and allow them onto tainted nodes. But a toleration only permits; it doesn't attract the pod to that node.

Node affinity is on pods and attracts them to nodes with certain labels, like a particular instance type, zone, or a GPU label. requiredDuringSchedulingIgnoredDuringExecution is a hard rule; preferredDuringScheduling is a weighted preference. nodeSelector is the simple, older form of a hard rule.

So, to dedicate nodes to a workload, you combine both: taint the node pool so other pods stay away, and give the workload a toleration plus node affinity so it goes there and only there.

Typical uses: GPU nodes for machine learning jobs, nodes with lots of memory for a cache, spot nodes for interruptible batch work with a toleration, separate system node pools for cluster add-ons, and Windows nodes for Windows containers, where Windows pods need a nodeSelector for the OS.

### dkx | How do you spread pods across nodes and zones for high availability? | topology spread constraints, pod anti affinity, spread across zones, high availability kubernetes, zone failure
Running three replicas doesn't help much if all three land on the same node or in the same availability zone. One node failure or zone outage takes the service down. So I tell the scheduler to spread them.

Pod anti-affinity is the older way. A rule says don't schedule this pod on a node, or in a zone, that already runs a pod with the same label. The required form is strict, which can leave pods Pending if there are more replicas than nodes; the preferred form is a soft preference. It also gets expensive to compute in large clusters.

Topology spread constraints are the better, more flexible tool. A constraint says spread pods matching a label across a topology key, like topology.kubernetes.io/zone or kubernetes.io/hostname, with a maxSkew, the maximum allowed difference in pod count between domains. whenUnsatisfiable set to DoNotSchedule makes it strict; ScheduleAnyway makes it best-effort. I usually add two constraints: across zones, and across nodes.

Some details matter. Spread only applies at scheduling time, so after a zone recovers, pods don't automatically rebalance; the descheduler can help with that. The autoscaler must be able to create nodes in each zone. And PodDisruptionBudgets keep the spread safe during maintenance.

Zone spreading can add cross-zone data transfer costs, which is usually worth it for production APIs.

### dkx | How do applications pick up ConfigMap and Secret changes? | configmap change not reflected, reload config kubernetes, configmap hot reload, reloader, rollout restart config
A frequent surprise: you update a ConfigMap, and the application keeps using old values. It depends on how the configuration is consumed.

Environment variables are read only when the container starts. Changing the ConfigMap does nothing to running pods; they need a restart.

Mounted volumes are updated by the kubelet eventually, typically within a minute or so, because files are refreshed through a symlink swap. An application that watches the file can reload. In .NET, adding a JSON file with reloadOnChange and reading settings through IOptionsMonitor works, though file watching on these symlinked volumes can be unreliable, so polling may be needed. Volumes mounted with subPath are never updated.

Common approaches. Rollout restart: kubectl rollout restart deployment after the change, which recreates pods gradually. A checksum annotation in the Helm chart: the pod template includes a hash of the ConfigMap contents, so any config change changes the pod template, which triggers a normal rolling update automatically. That's my preferred method, because the change goes through the same safe rollout as a code change. A controller like Stakater Reloader watches ConfigMaps and Secrets and restarts deployments that reference them.

Immutable ConfigMaps with versioned names, like app-config-v12, are another pattern: each change creates a new ConfigMap, and the deployment references the new name, which also makes rollback clean.

Real feature flags that must change instantly are better served by a feature flag service than by ConfigMaps.

### dkx | How do you manage secrets in Kubernetes properly? | kubernetes secrets base64, external secrets operator, sealed secrets, secrets store csi driver, encrypt secrets etcd
Kubernetes Secrets are only base64-encoded, not encrypted, by default. Anyone who can read them through the API, or read etcd backups, can see the values. So I treat native Secrets carefully and usually source them from a real secrets manager.

Baseline protections: enable encryption at rest for secrets in etcd, which managed clusters support with a KMS key; restrict RBAC so few people and service accounts can get or list secrets; and never commit secret manifests to Git in plain form.

Then choose how secrets get into the cluster.

External Secrets Operator: an ExternalSecret resource says which keys to fetch from AWS Secrets Manager, Parameter Store, Azure Key Vault, HashiCorp Vault or others, and the operator creates and refreshes a normal Kubernetes Secret. Apps stay unchanged, and rotation in the source flows through.

Secrets Store CSI Driver: mounts secrets from the external store directly as files in the pod, optionally syncing to a Kubernetes Secret.

Sealed Secrets: encrypt secrets with the cluster's public key so the encrypted version can be safely committed to Git, which suits GitOps; only the controller in the cluster can decrypt them.

Even better, avoid secrets where possible: use workload identity, like IRSA or Pod Identity on EKS and Workload ID on AKS, so pods authenticate to cloud databases and services without any stored credentials.

### dkx | How do you upgrade a Kubernetes cluster safely? | kubernetes upgrade, eks upgrade, aks upgrade, deprecated api removal, node pool upgrade, version skew
Kubernetes releases a minor version roughly every four months, and each is supported for about a year upstream, longer on some managed services with paid extended support. So upgrades are routine, and I treat them as a process, not an event.

Before upgrading: read the release notes for removed or deprecated APIs. Tools like Pluto or kubent scan manifests and Helm releases for API versions that will stop working. Check that add-ons, like the ingress controller, CNI, CSI drivers, cert-manager and monitoring agents, support the new version, and upgrade them first if needed. Upgrade one minor version at a time; you can't skip versions on the control plane.

The order: upgrade a non-production cluster first and run the test suites. Then the control plane, which managed services do for you without downtime. Then the node pools, which must stay within the supported version skew of the control plane. For nodes, I prefer creating a new node pool on the new version and draining the old one, or using surge upgrades that add new nodes before removing old ones. PodDisruptionBudgets, multiple replicas, and graceful shutdown keep services up as pods move.

After: watch error rates and events, then upgrade remaining add-ons.

Teams that keep clusters disposable and fully defined in code sometimes do blue-green clusters instead: build a new cluster on the new version, shift traffic, and retire the old one.

### dkx | What are Pod Security Standards and admission policies? | pod security standards, pod security admission, restricted baseline privileged, kyverno, opa gatekeeper, validating admission policy
Admission control is the step where the Kubernetes API checks or modifies objects before saving them. It's where you enforce security rules on every workload, rather than trusting each manifest.

Pod Security Standards define three profiles. Privileged has no restrictions, for system components. Baseline blocks known privilege escalations, like privileged containers, host networking and host paths. Restricted enforces hardening best practices: non-root users, no privilege escalation, dropped capabilities, and a seccomp profile.

Pod Security Admission is built into Kubernetes and applies these profiles per namespace, using labels. Each profile can be set to enforce, which rejects violating pods; audit, which logs them; or warn, which returns a warning to the user. I usually start with warn and audit on restricted, fix the workloads, then enforce.

For rules beyond pod security, policy engines help. Kyverno writes policies as Kubernetes YAML: require labels like owner and cost centre, require resource limits, allow images only from our registry, require signed images, or add default settings automatically. OPA Gatekeeper uses the Rego language for the same purposes. Kubernetes also now has built-in ValidatingAdmissionPolicy using CEL expressions, which covers many simple rules without installing anything.

I keep policies in Git, test them in CI against our manifests, and roll them out in audit mode first, so nobody's deployment breaks without warning.

### dkx | What happens when you run kubectl apply? Walk through the control plane. | kubectl apply flow, kubernetes control plane components, api server etcd scheduler, controller manager, kubelet, how kubernetes works
Walking through it shows how the pieces fit together.

kubectl reads the manifest and sends it to the API server over HTTPS, authenticating with my credentials. kubectl apply uses server-side or client-side apply to work out what changed compared to the last applied configuration.

The API server authenticates me, checks RBAC authorisation, then runs admission controllers: mutating ones, which may add defaults or sidecars, then validating ones, like Pod Security or policy engines. If everything passes, it stores the Deployment object in etcd, the cluster's key-value database. Nothing has run yet; we've only recorded desired state.

Controllers watch the API server for changes. The Deployment controller, in the controller manager, sees the new Deployment and creates a ReplicaSet. The ReplicaSet controller sees that it needs three pods and creates three Pod objects, with no node assigned.

The scheduler watches for unassigned pods. For each, it filters nodes that fit the requests, taints, affinity and spread rules, scores them, and binds the pod to the best node.

The kubelet on that node sees a pod assigned to it, asks the container runtime, like containerd, to pull the image and start the containers, sets up networking through the CNI plugin and volumes through CSI, runs probes, and reports status back.

Meanwhile, the EndpointSlice controller adds ready pods to the Service, and kube-proxy or the CNI updates routing so traffic can reach them.

### dkx | How do PersistentVolumes, PersistentVolumeClaims and StorageClasses work? | persistent volume, persistent volume claim, storage class, dynamic provisioning, access modes rwo rwx, reclaim policy
Containers are ephemeral, so anything written inside them disappears on restart. Persistent storage in Kubernetes has three layers.

A PersistentVolume is a piece of storage in the cluster, like an EBS volume, an Azure Disk, or a network file share, with a size, access modes and a reclaim policy.

A PersistentVolumeClaim is a request for storage by a workload: I need 20 GiB, ReadWriteOnce, of this class. The pod mounts the claim, not the volume directly, so application manifests don't depend on the storage details.

A StorageClass describes a type of storage and its provisioner, like gp3 EBS volumes, premium Azure disks, or EFS. With dynamic provisioning, creating a claim makes the provisioner create a matching volume automatically. volumeBindingMode WaitForFirstConsumer delays creation until the pod is scheduled, so the volume is created in the same availability zone as the pod.

Access modes matter. ReadWriteOnce means one node can mount it, typical for block disks. ReadWriteMany means many nodes, which needs a network file system, like EFS or Azure Files. ReadWriteOncePod restricts it to a single pod.

The reclaim policy decides what happens when the claim is deleted: Delete removes the underlying disk, Retain keeps it for manual recovery. For important data, I use Retain plus regular snapshots with the CSI snapshot feature.

For most stateless services, I avoid volumes entirely and use object storage or managed databases.

### dkx | containerd vs Docker: what changed when Kubernetes removed dockershim? | containerd vs docker, dockershim removal, container runtime interface, cri-o, oci image, docker images still work kubernetes
Kubernetes talks to container runtimes through the Container Runtime Interface. Docker Engine never implemented CRI, so Kubernetes had an adapter called dockershim to talk to it. That adapter was removed in Kubernetes 1.24.

What that meant in practice: clusters switched to CRI-compatible runtimes, mainly containerd, which was actually the component Docker itself used under the hood, or CRI-O. Managed services like EKS, AKS and GKE moved to containerd.

What didn't change: images built with Docker still work everywhere, because they follow the OCI image standard, and containerd runs OCI images. Developers keep using Docker Desktop or Docker Engine to build and run containers locally; only the runtime on cluster nodes changed.

Things that did break: anything that relied on the Docker socket on nodes, like CI jobs building images inside pods by mounting /var/run/docker.sock, or monitoring agents reading Docker's API. Those moved to alternatives, like BuildKit, Kaniko or buildah for in-cluster builds, and runtime-agnostic agents. Debugging on nodes uses crictl instead of the docker command.

So in an interview, the key points are: Docker is a developer tool and image format ecosystem; containerd is the runtime; OCI standards make images portable between them; and Kubernetes only needs a CRI runtime on nodes.

### dkx | How do you run database migrations when deploying to Kubernetes? | database migration kubernetes, ef core migrations kubernetes, migration job helm hook, init container migration, schema change deployment
Running migrations from the application at startup, like calling Database.Migrate in Program.cs, is risky in Kubernetes. With several replicas starting at once, they race to apply the same migration, startup gets slow, and the app needs DDL permissions it shouldn't have at runtime.

Better options.

A Kubernetes Job before the rollout. The pipeline runs a migration Job, using the same image or a dedicated migrator image, waits for it to complete successfully, and only then updates the Deployment. In Helm, this is often a pre-upgrade hook, so the release fails if the migration fails. The Job uses a separate database identity with schema-change rights.

A migration step in the pipeline itself, outside the cluster, applying an idempotent script or an EF Core migration bundle generated at build time. This makes the migration a visible, auditable release step.

Init containers can work for simple cases, but every pod would try to run them, so they need locking, and I don't usually prefer them.

Whatever the mechanism, the schema changes themselves must be backward compatible, because during a rolling update old and new versions run side by side. I use the expand and contract pattern: add new columns or tables first, deploy code that writes both, backfill, switch reads, and only drop old columns in a later release. That also keeps rollback of the application safe without rolling back the database.

### dkx | How do you do progressive delivery on Kubernetes with Argo Rollouts or Flagger? | argo rollouts, flagger, progressive delivery, canary analysis kubernetes, automated rollback metrics, analysis template
A plain Deployment does a rolling update: it replaces pods gradually, but it only checks readiness, not whether the new version is actually healthy for users. Progressive delivery tools add real canary and blue-green releases with automated analysis.

Argo Rollouts replaces the Deployment with a Rollout resource. A canary strategy lists steps, like send 10 percent of traffic, pause five minutes, run analysis, go to 30 percent, analyse again, then 100 percent. Traffic splitting can be by replica count, or precise using an ingress controller, the Gateway API, or a service mesh. Analysis templates query a metrics provider, like Prometheus, Datadog or CloudWatch, with success conditions, like error rate below one percent and p95 latency below 400 milliseconds. If analysis fails, the rollout aborts and traffic returns to the stable version automatically. Blue-green is also supported, with preview services and promotion.

Flagger does the same with a different model: you keep your Deployment, and Flagger creates the canary and primary objects and drives traffic shifting with a mesh or ingress, using metric checks and webhooks for load tests or approvals.

What makes this work in practice: good metrics per version, labelled so you can compare canary with stable; enough traffic for statistics to mean something; and backward-compatible database changes, since both versions run together.

It's essentially the automatic rollback answer for Kubernetes: health is judged by real user signals, not by humans watching dashboards.
