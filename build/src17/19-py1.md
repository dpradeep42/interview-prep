### pyx | What is the GIL in Python, and how does it affect performance? | gil, global interpreter lock, python threading cpu, free threaded python, python 3.13 no gil, python multicore
Okay, the Global Interpreter Lock is a lock in CPython, the standard Python interpreter, that allows only one thread to execute Python bytecode at a time. It simplifies memory management, since reference counting doesn't need fine-grained locks, and makes C extensions easier to write.

The effect is Python threads can't run CPU-bound Python code in parallel on multiple cores. Ten threads doing heavy calculations take about as long as one thread, or even longer.

But for I/O-bound work, HTTP calls, database queries, file reads, the GIL is released while waiting on I/O, so threads, or asyncio, work well for concurrency. And many C-based libraries, like NumPy, release the GIL during heavy computations, so they can use multiple cores.

For CPU-bound Python code, the usual options are multiprocessing or ProcessPoolExecutor from concurrent.futures, which use separate processes, each with its own interpreter and GIL. Or moving the hot code into a compiled library. Or running multiple worker processes, which web servers like Gunicorn do anyway.

Things are changing though. Python 3.13 introduced an experimental free-threaded build without the GIL, and in 3.14 the free-threaded build became officially supported, though not the default. Many libraries are still catching up, and single-threaded code can be slightly slower in that build.

For our RAG service, the work is mostly I/O, calling embedding APIs and the database, so async FastAPI fits well, and honestly the GIL just isn't a bottleneck there.

### pyx | What are generators in Python, and why use yield? | python generators, yield python, generator expression, lazy evaluation python, iterator protocol python, yield from

Async generators, with async def and yield, work with async for, for streaming data from APIs or databases.

### pyx | What is the mutable default argument pitfall in Python? | mutable default argument, default list argument python, python function default bug, none default python
So in Python, default argument values are evaluated once, when the function is defined, not every time it's called. So if the default is a mutable object, like a list or dictionary, the same object gets shared across all calls that use the default.

Let me take an example. def add_item of item, and items equals an empty list, appends the item and returns items. First call returns a list with one item. The second call, which you'd expect to return a new list with one item, returns a list with two, because it's the same list object as before. Data leaks between calls, which causes really confusing bugs, especially in long-running services where state builds up across requests.

The standard fix is to use None as the default and create a new object inside the function. items equals None, then if items is None, items equals an empty list.

Same idea shows up in other places. Class attributes defined with mutable values are shared by all instances, so per-instance lists should be created in the init. Dataclasses protect you here, they raise an error for a mutable default, and I use field with default_factory equals list instead. Pydantic models handle mutable defaults safely by copying them.

Linters like Ruff flag mutable default arguments automatically, which is honestly one reason I always run a linter.

Create a small hierarchy of custom exceptions for the application, like a base AppError with NotFoundError and ValidationError, which FastAPI exception handlers map to HTTP responses. Use finally or context managers for cleanup.

Python 3.11 added exception groups and except star for handling multiple errors from concurrent tasks, like those in a TaskGroup.

### pyx | How do you call external REST APIs robustly from Python? | httpx, requests python, retry python tenacity, python http client timeout, connection pooling python, call api python
For HTTP calls in Python, I use httpx, which supports both sync and async with the same API, or requests for simple synchronous scripts.

Several things make it robust.

Reuse the client. Creating a new client per request loses connection pooling and keep-alive, so I create one httpx.AsyncClient at application startup, in the FastAPI lifespan, with a base URL, default headers and limits, and close it on shutdown. It's the same lesson as HttpClient in .NET.

Timeouts. requests has no default timeout at all, so a hung server blocks forever; httpx has a default of five seconds. I set explicit connect and read timeouts suited to the API.

Check status codes. Call raise_for_status, or check the status explicitly and handle errors.

Retries with backoff. The tenacity library provides a retry decorator with stop_after_attempt, wait_exponential with jitter, and retry_if_exception_type, so I retry only transient failures, like connection errors, timeouts, 429 and 503, and respect Retry-After. For non-idempotent POST requests, I retry only with an idempotency key.

Concurrency limits. When making many calls with asyncio.gather, I use an asyncio.Semaphore to limit concurrent requests, respecting the API's rate limits.

And logging with the request id, plus OpenTelemetry instrumentation for httpx, so external calls appear in traces.

For the embedding API calls in our RAG service, batching and rate-limit-aware retries were essential.

### pyx | What Python security issues should you watch for? | python security, pickle security, eval exec security, bandit, yaml safe load, subprocess shell injection
Python has a few specific risks on top of the usual web security issues.

pickle: unpickling data can execute arbitrary code, so I never unpickle data from untrusted sources, like uploads, network messages or shared caches. JSON is the safe choice for data exchange. The same applies to tools built on pickle, like some model file formats; for ML models, safer formats like safetensors exist.

eval and exec: running strings as code is dangerous with any user input. For parsing simple literals, ast.literal_eval is safe.

YAML: yaml.load with the default or full loader can create arbitrary Python objects; I always use yaml.safe_load.

subprocess: passing a command string with shell equals True and user input allows shell injection. I pass arguments as a list without the shell.

SQL: always parameterised queries, through SQLAlchemy or the driver's parameters, never f-strings in SQL.

Path traversal: building file paths from user input needs resolving the path and checking it stays inside the allowed directory.

Insecure randomness: random is predictable; for tokens and passwords, I use the secrets module.

Dependencies: typosquatted packages on PyPI exist, so I pin dependencies with a lockfile, scan them with pip-audit, and review new packages.

Tools help: Bandit, or Ruff's security rules, flag many of these patterns automatically in the pipeline.

### pyx | How do you process a large CSV file efficiently in Python? | large csv python, pandas chunksize, csv module python, polars, process big file python, memory efficient python
The key is not loading the whole file into memory at once, unless it comfortably fits.

For row-by-row processing, the built-in csv module with DictReader reads one row at a time from a file object, which is a generator-like stream. Memory stays flat regardless of file size. I combine it with batching: collect rows into batches of, say, 5,000, validate them, and write each batch to the database with a bulk insert, like executemany or PostgreSQL's COPY, which is far faster than inserting rows one by one.

For analysis and transformation, pandas is convenient, but it loads data into memory, which can be several times the file size. read_csv with chunksize returns an iterator of DataFrames, so I can process a large file in chunks. Specifying dtypes and usecols, reading only the needed columns with the right types, reduces memory and speeds up parsing a lot. The pyarrow engine is also faster.

Polars is a newer DataFrame library written in Rust. It's much faster than pandas, uses all CPU cores, and its lazy API with scan_csv builds a query plan and processes data in a streaming way, even for files larger than memory. For heavy data work, it's my preferred choice now. DuckDB is another excellent option that can query CSV files with SQL directly.

Whatever the tool, I collect invalid rows with their line numbers into an error report instead of failing the whole file.

### pyx | What is structural pattern matching in Python? | python match case, structural pattern matching, match statement python 3.10, pattern matching python, case guard python
Python 3.10 added the match statement, which compares a value against a series of patterns, and runs the first case that matches. It's much more than a switch statement on values; it can match on the structure of data.

Patterns include: literal values, like case "pending"; the wildcard underscore as a default; OR patterns, like case "shipped" or "delivered"; capture patterns, which bind parts of the value to names; sequence patterns, like case first, then star rest, for lists; mapping patterns, like case with a "type" key equal to "kit_dispensed" and a "kit_id" key captured into a variable, which is great for handling JSON events or messages; and class patterns, like case Shipment with status equal to "cancelled", which match on type and attributes, using dataclass fields. Guards add extra conditions with if after the pattern.

It's very useful for routing messages or events by type and shape, parsing command-line style inputs, and handling different variants of a result object, similar to discriminated unions in TypeScript or pattern matching with switch expressions in C#.

A gotcha: a bare name in a case is a capture pattern, not a comparison with a variable. case STATUS captures anything into a new variable named STATUS. To compare with constants, they must be dotted names, like Status.PENDING from an Enum, or literals.

### pyx | What are Python Protocols, and how do they compare with interfaces? | python protocol, structural typing python, typing protocol, duck typing, abc abstract base class python, interface in python
Python has two ways to describe an interface-like contract.

Abstract base classes, from the abc module, are nominal: a class must explicitly inherit from the ABC and implement its abstract methods, otherwise it can't be instantiated. That's close to an abstract class or interface in C#, enforced at runtime.

Protocols, from typing, are structural, which is formalised duck typing. A Protocol defines the methods and attributes something must have, like an Embedder protocol with an embed method that takes a list of strings and returns a list of vectors. Any class that has a matching method is considered an Embedder by the type checker, without inheriting from it or even knowing the Protocol exists. That's like interfaces in TypeScript or Go.

Protocols are great for dependency injection and testing. My RAG code depends on the Embedder protocol, not on the Azure OpenAI client. Production passes the real client wrapper; tests pass a simple fake class with an embed method, and mypy verifies both fit the protocol. Third-party classes that I can't modify can also satisfy a protocol.

By default, protocols are only checked statically by mypy or Pyright. With the runtime_checkable decorator, isinstance checks work too, but they only check that the methods exist, not their signatures.

I use Protocols for boundaries between components, and ABCs when I want to share implementation in a base class.

### pyx | What is the LEGB rule, and how do closures work in Python? | legb rule, python scope, closures python, nonlocal keyword, global keyword, late binding closures
LEGB describes the order Python uses to look up a name: Local, the current function's scope; Enclosing, the scopes of any outer functions; Global, the module's scope; and Built-in, names like len and print. The first match wins.

A closure is an inner function that remembers variables from its enclosing function's scope, even after the outer function has returned. For example, make_multiplier of n returns an inner function that multiplies its argument by n; each returned function keeps its own n. Decorators rely on closures: the wrapper remembers the original function.

Assigning to a name inside a function makes it local by default. So if an inner function tries to increment a counter from the outer function, Python raises an UnboundLocalError, because the assignment makes it local and it's read before being assigned. The nonlocal keyword says the name refers to the enclosing function's variable, and global refers to the module-level variable. I use nonlocal occasionally, but global almost never, because module-level mutable state is hard to reason about and test.

A classic gotcha is late binding: closures capture variables, not values. Creating lambdas in a loop, like functions that return i, gives functions that all return the last value of i, because they look up i when called. The fix is binding the current value as a default argument, or using functools.partial.

It's similar to the classic C# closure-in-a-loop problem from older versions.
