### apix | Why do async controller actions improve scalability in ASP.NET Core? | async controller actions, async await scalability, why async in web api, thread pool web requests, async io scalability
In ASP.NET Core, each request runs on a thread pool thread. If an action calls a database or another API synchronously, that thread sits blocked, doing nothing, until the response comes back. Under load, all threads can end up blocked waiting on I/O. The thread pool then grows slowly, requests queue up, and latency spikes, even though the CPU is mostly idle. That's thread pool starvation.

With async actions, when the code awaits an I/O operation, like await db.Shipments.ToListAsync() or await httpClient.GetAsync(), the thread is released back to the pool while the operating system waits for the I/O. When the result arrives, a pool thread continues the method. So a small number of threads can serve many concurrent requests that are mostly waiting.

Important points.

Async improves scalability and throughput under concurrency, not the speed of a single request; a single request may even be slightly slower due to overhead.

It only helps for I/O-bound work. CPU-bound work still needs a thread; wrapping it in Task.Run inside a request just moves it to another pool thread and adds overhead.

It must be async all the way: calling .Result or .Wait() on async methods blocks a thread again and can cause starvation.

Pass the request's CancellationToken to async calls, so work stops when the client disconnects.

In our legacy ASP.NET MVC applications, moving data access to async was one of the changes that helped the application handle peak usage better without more servers.

Measure: track the latency of the first requests after deployments, and the startup duration, so regressions are visible.

For serverless, like Lambda or Azure Functions, the same idea applies as cold starts, with provisioned concurrency or premium plans as additional options.
