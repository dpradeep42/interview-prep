### apix | Why do async controller actions improve scalability in ASP.NET Core? | async controller actions, async await scalability, why async in web api, thread pool web requests, async io scalability
Right, so in ASP.NET Core each request runs on a thread pool thread. If an action calls a database or another API synchronously, that thread just sits there blocked, doing nothing, until the response comes back. Under load, all the threads can end up blocked waiting on I/O. The thread pool grows slowly, requests queue up, latency spikes, while the CPU's mostly idle. That's thread pool starvation.

With async actions, when the code awaits an I/O operation, like awaiting ToListAsync on a DbSet, or an HttpClient GetAsync, the thread goes back to the pool while the OS waits for the I/O. When the result comes in, a pool thread continues the method. So a small number of threads can serve lots of concurrent requests that are mostly waiting.

A few important points. Async improves scalability and throughput under concurrency, not the speed of one request. A single request might even be a tiny bit slower because of the overhead.

It only helps I/O-bound work. CPU-bound work still needs a thread, and wrapping it in Task Run inside a request just moves it to another pool thread and adds overhead.

It has to be async all the way. Calling dot Result or dot Wait on async methods blocks a thread again and can bring the starvation right back.

And pass the request's CancellationToken into async calls, so work stops when the client disconnects.

In our legacy ASP.NET MVC applications, moving data access to async was one of the changes that helped handle peak usage better without adding servers.

How I reduce it. Warm up before taking traffic. In rolling or slot deployments, call key endpoints or run a warm-up routine before the instance is marked ready. An IHostedService can do warm-up work at startup, touching the DbContext, loading reference data into cache, opening connections, and a readiness health check only passes once warm-up's done.

IIS specifics, enable the Application Initialization module with preload enabled and start mode AlwaysRunning, and configure initialisation pages, so IIS starts the app and calls warm-up URLs after a recycle, before users arrive. Also avoid unnecessary recycles, like the default idle timeout that shuts down quiet apps. That idle timeout catches people out a lot on internal apps that only get used in the morning.

Reduce the startup cost itself. ReadyToRun compilation to pre-compile code, EF Core compiled models for big models, which matters when you've got hundreds of tables, avoiding heavy reflection scanning at startup, and lazy initialisation only for rarely used parts.

Measure it. Track the latency of the first requests after deployments and the startup duration, so regressions are visible.

For serverless, like Lambda or Azure Functions, it's the same idea as cold starts, with provisioned concurrency or premium plans as extra options.
