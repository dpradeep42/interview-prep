### awsx | What is SQS long polling, and how do you handle large messages? | sqs long polling, receive message wait time, sqs short polling, sqs message size limit, sqs extended client
When a consumer calls ReceiveMessage, SQS can respond two ways.

Short polling returns immediately and only checks a subset of SQS servers, so it can return nothing even when messages exist. And an idle consumer makes constant empty calls, which costs money, because SQS bills per request.

Long polling waits up to 20 seconds for messages to arrive before responding, and checks all the servers. You set the wait time seconds on the receive call, or the receive message wait time on the queue, to 20. It cuts empty responses, cost, and pickup latency. I use it by default for every consumer, and Lambda's SQS integration already uses it.

Message size. SQS messages are limited to 256 KB, recently raised to 1 MB. For bigger payloads, it's the claim-check pattern. Store the payload in S3 and send a message with a reference to it. Even under the limit, I keep messages small, ids and essential data, because smaller messages are cheaper and faster, and you don't put sensitive data into queues for no reason.

Other settings that go with it, a visibility timeout longer than your processing time, a dead-letter queue with a sensible max receive count, and monitoring the age of the oldest message to catch consumers falling behind. That metric's saved us a few times, I think.

### awsx | How do CloudFront cache policies and invalidations work? | cloudfront cache policy, cloudfront invalidation, cache key cloudfront, cloudfront ttl, cdn caching aws
CloudFront caches responses at edge locations, and cache behaviours and policies control what's cached, for how long and under which key.

Cache behaviours match path patterns, like slash assets slash star or slash api slash star, each with its own origin and policies, so static files and API calls get treated differently.

The cache policy defines the cache key, which headers, cookies and query strings make a response unique, plus minimum, default and maximum TTLs. A smaller cache key means more cache hits. Include only what actually changes the response, so for static assets don't include all the cookies.

The origin request policy defines what gets forwarded to the origin without being part of the cache key, like a header the origin needs that doesn't change the response.

TTLs, the origin's Cache-Control headers set the time, bounded by the policy's min and max.

Invalidation removes objects from edge caches before they expire, using paths like slash index dot html or slash star. The first 1,000 paths a month are free, then they cost, and they take a little while to finish.

My approach for SPAs avoids frequent invalidation. Hashed file names for JavaScript and CSS, like main dot some-hash dot js, cached for a year, because every new build produces new names. And index dot html with no-cache or a very short TTL, so users get the new version right after a deployment. Then one small invalidation of index dot html, or none at all, is enough.

For APIs, I'd say caching's usually disabled with the managed caching-disabled policy, or there's short caching only for public, non-personalised GET responses.

### awsx | What are the disaster recovery strategies on AWS: backup and restore, pilot light, warm standby, multi-site? | aws disaster recovery strategies, pilot light, warm standby, multi site active active, rto rpo aws
AWS describes four disaster recovery strategies, trading cost against recovery time, RTO, and data loss, RPO.

Backup and restore: regularly back up data, with AWS Backup, snapshots and S3 cross-region replication, and keep infrastructure as code. In a disaster, recreate infrastructure in another region and restore data. Cheapest, but RTO is hours and RPO depends on backup frequency.

Pilot light: core data is continuously replicated to the recovery region, like an Aurora global database or cross-region read replica, while compute is off or minimal. In a disaster, scale up compute from templates and switch traffic. RTO in tens of minutes.

Warm standby: a scaled-down but fully working copy runs in the recovery region, with data replicated. It can serve traffic immediately after scaling up. RTO in minutes, higher cost.

Multi-site active-active: full capacity in two or more regions, both serving traffic, with Route 53 or Global Accelerator routing users. Near-zero RTO, but the highest cost and complexity, especially for data conflicts between regions.

How to choose: start from business requirements: how long can the system be down, and how much data can be lost? Clinical systems that sites use to randomise patients need short RTO and near-zero RPO for transactional data, while reporting systems may tolerate more.

What makes any strategy work: everything as code, so environments can be rebuilt; automated, tested runbooks; regular DR drills, including failing back; monitoring of replication lag; and remembering dependencies like DNS, certificates, secrets and third-party allow-lists in the recovery region.
