### scx | The cache expired and the database got overloaded. How do you prevent a cache stampede? | cache stampede, thundering herd, dog piling, cache expiry overload, hybridcache stampede protection, cache warmup
See, a stampede is when a popular cached item expires, or a restart empties the cache, and lots of concurrent requests all miss at the same time and run the same expensive query together. The database suddenly gets hundreds of identical queries, slows down, and that makes even more requests pile up. It's a classic outage right after a cache restart or a deployment.

How I prevent it. Request coalescing, so only one request recomputes a given key and the others wait for that result. In .NET 9, HybridCache does this automatically for concurrent callers in the same process. Otherwise a per-key SemaphoreSlim or a Lazy task does it, and across servers a short distributed lock in Redis.

Jittered expiration. Add a random bit to each item's TTL so they don't all expire at the same moment.

Refresh ahead. Popular items get refreshed in the background before they expire, so users never see a miss. Stale-while-revalidate is similar, you serve the slightly old value while one request refreshes it.

Warm up the known hot keys after deployments or cache restarts, before taking full traffic.

And protect the database anyway. Limit concurrency on expensive queries with a bulkhead and put a circuit breaker in, so even if the cache fails badly, the database survives and recovers.

I'd also monitor the cache hit ratio, so a sudden drop alerts us before the database falls over. That's usually the earliest sign something's off.

Concurrency. Test has one or two users, production has hundreds at once. Lock contention, connection pool limits, thread pool starvation, cache stampedes, those only show up under real load.

Config differences. Debug logging on, different cache settings, some feature flag on, smaller instances, or database settings like compatibility level or read committed snapshot being different.

Network and integrations. Production calls real external services with real latency, through proxies, firewalls and gateways, while test might use stubs sitting in the same network.

Background workload. In production, scheduled jobs, reports and integrations are running at the same time and competing for the database.

And the front end, users have more data on the page, older devices, slower networks, browser extensions.

My approach is measure in production first, with traces showing where the time actually goes, instead of guessing from test. Then reproduce that specific condition in a perf environment, fix it, and make that environment closer to production in data size so it catches the next one.

### scx | A scheduled job ran twice and processed data twice. How do you prevent it? | job ran twice, duplicate job execution, scheduled job multiple servers, distributed lock job, quartz clustering
Right, jobs run twice for a few different reasons, and each one has its own fix.

The most common is multiple instances. The app got scaled from one server to two, or deployed to several nodes, and every instance has the same scheduler, so each one runs the job. Fixes are a clustered scheduler, like Quartz with a shared database job store and clustering on, so only one node fires each trigger. Or a distributed lock at the start of the job, like a Redis lock or a SQL app lock with sp_getapplock. Or move scheduling to one external trigger, a Kubernetes CronJob, EventBridge Scheduler or an Azure Functions timer, which behaves like a singleton.

Overlapping runs, where the previous run hadn't finished when the next started. Quartz has the DisallowConcurrentExecution attribute, or use a lock, and Kubernetes CronJobs have concurrencyPolicy Forbid.

Misfire handling. After downtime, the scheduler fires the missed runs on startup. Configure the misfire instructions on purpose.

And manual reruns or retries after a partial failure.

But because some duplication is always possible, my rule is the job itself has to be idempotent. Track what's been processed with a run id or a per-record processed flag, put unique constraints on outputs like invoices or notifications, and design the steps so rerunning them doesn't double the effect.

Then clean up the data from the double run carefully, using the job's own records to work out what got duplicated.

### scx | A poison message keeps crashing the consumer. What do you do? | poison message, consumer crash loop, message causes exception, bad message queue, dead letter poison message
Actually let me explain what it is first. A poison message is one that can never succeed, malformed data, an unexpected null, a reference to something that doesn't exist. If the consumer crashes or rejects it with requeue, the broker delivers it again, it fails again, and the consumer's stuck in a loop blocking everything behind it.

The immediate fix is getting it out of the way without losing it. With a proper setup it goes to the dead-letter queue by itself after a few attempts. If not, I move it manually with the broker tooling to a parking queue so everything else starts flowing again. Never just purge the queue, especially with business events.

Then investigate. Look at the message, its headers and the consumer's error logs. Is it actually invalid, sent by a buggy producer, or is our consumer failing on a valid edge case?

Fix the cause, either the producer or the consumer, then replay the parked message, or correct it if it really is invalid.

For prevention, every consumer gets retry limits with backoff and a dead-letter queue, with retry counts tracked in headers. I separate error types, so transient ones like timeouts get retried, and permanent ones like validation failures go straight to the DLQ with no retries. Exceptions are caught per message, so one bad message never takes down the whole consumer process. Messages get validated at the start of processing. And we alert when anything lands in the DLQ, with tooling to inspect and replay.

### scx | SQL Server's transaction log is full and writes are failing. What do you do? | transaction log full, log file full sql server, error 9002, log_reuse_wait_desc, log backup, database log growth

First I find out why the log can't be reused. I query sys dot databases for log reuse wait desc on that database, and the value tells me the cause.

If it's LOG_BACKUP, the database is in full recovery but log backups haven't been running, maybe the backup job failed. So I take a log backup right away, which lets the space be reused, then fix the job and alert on its failures.

If it's REPLICATION or AVAILABILITY_REPLICA, a replica or replication isn't keeping up, so the log has to be kept for it. Or it's one huge operation, like an index rebuild or deleting millions of rows in a single transaction.

Prevention is working, monitored log backups, alerts on log usage percentage, and batching big data operations into smaller transactions.

### scx | tempdb is filling up on SQL Server. How do you find the cause? | tempdb full, tempdb growth, tempdb contention, version store growth, sort spill tempdb, tempdb space usage
So tempdb is shared by everything on the server, which means when it fills up, queries in every database start failing. I figure out which kind of usage is growing.

The file space usage DMV for tempdb splits the space into user objects, internal objects and the version store.

User objects are temp tables and table variables created by queries or procedures. The session and task space usage DMVs show which sessions use the most, and that leads me to the query or job. Typical ones are a procedure loading millions of rows into a temp table, or temp tables never dropped on long-lived connections.

Internal objects are work tables and spills from sorts, hashes and spools, when a query's memory grant is too small, or it sorts or hashes a huge result. Execution plans with spill warnings show it. The fix is better indexes to avoid big sorts, fixing bad cardinality estimates, or rewriting the query.

Version store. With read committed snapshot or snapshot isolation on, row versions live in tempdb as long as the oldest open transaction needs them. One long-running transaction, even an idle open one, blocks cleanup, and the version store just keeps growing. So find the oldest active snapshot transaction and deal with it. I've seen this one catch people out more than the others.

For immediate relief, kill the offending session if that's okay after checking the impact, or add space. Restarting SQL Server resets tempdb, but that's a last resort, it's full downtime.

And prevent it, size tempdb properly with multiple equal data files, monitor usage, and alert on long-running transactions.
