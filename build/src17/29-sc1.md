### scx | A query was fast yesterday and is slow today, with no code change. What happened? | query suddenly slow, parameter sniffing, statistics out of date, plan regression, same query slow today

### scx | The cache expired and the database got overloaded. How do you prevent a cache stampede? | cache stampede, thundering herd, dog piling, cache expiry overload, hybridcache stampede protection, cache warmup
A cache stampede happens when a popular cached item expires, or the cache is emptied by a restart, and many concurrent requests all miss at once and run the same expensive database query at the same time. The database is suddenly hit with hundreds of identical queries, slows down, which makes more requests pile up. It's a classic cause of outages right after a cache restart or deployment.

Prevention techniques.

Request coalescing: only one request recomputes a given key; the others wait for that result. In .NET 9, HybridCache does this automatically for concurrent callers in the same process. Otherwise, a per-key SemaphoreSlim or Lazy task achieves it, and across servers, a short distributed lock in Redis.

Jittered expiration: add a random amount to each item's TTL, so items don't all expire at the same moment.

Refresh ahead: refresh popular items in the background before they expire, so users never see a miss. Stale-while-revalidate is a similar idea: serve the slightly old value while one request refreshes it.

Warm up after deployments or cache restarts, for the known hot keys, before taking full traffic.

Protect the database anyway: limit concurrency to expensive queries with a bulkhead, and add a circuit breaker, so even if the cache fails badly, the database survives and recovers.

And monitor cache hit ratio, so a sudden drop alerts us before the database falls over.

### scx | Redis goes down in production. What happens, and what do you do? | redis down, cache unavailable, redis outage, redis failover, cache server down, graceful degradation cache
What happens depends on how we use Redis and how the app handles its failure, which is why I design for this before it happens.

If Redis is purely a cache, the right behaviour is graceful degradation: cache calls fail fast with a short timeout, are caught, logged and counted, and the app goes to the database instead. Users see slower responses, but everything works. The risks are that every request now waits for a long Redis timeout before falling back, so timeouts must be short and a circuit breaker should skip Redis entirely while it's down; and that the database suddenly receives the full load, so it needs headroom, or we limit concurrency on expensive queries.

If Redis holds state, like sessions, distributed locks, rate-limit counters or data protection keys, the impact is bigger: users logged out, locks unavailable, or rate limiting failing open or closed. Each needs a deliberate choice, like failing open for rate limits but failing safe for locks.

Afterwards: replicas with automatic failover, alerts on memory and connections, and stampede protection for when the cache comes back empty.

On our platform, Redis caches configuration and reference data, so the fallback is the database, with short timeouts.

My approach is to measure in production first, using traces to see where time is actually spent, rather than guessing from test. Then reproduce the specific condition in a performance environment, fix it, and make that environment closer to production in data size so it catches the next one.

### scx | Traffic suddenly jumps tenfold. How do you keep the system up? | sudden traffic spike, 10x traffic, traffic surge, handle load spike, scale under sudden load, load shedding
First, figure out whether it's legitimate, like a study going live at many sites, a batch import, or a partner integration resending data, or something bad, like a bot, a misbehaving client in a retry loop, or an attack. The response differs.

For abusive or accidental traffic: identify the source from logs, like IP, API key, client id or user agent, and block or rate-limit it at the gateway or WAF. A client stuck in a retry loop can be throttled while we contact its owner.

For legitimate traffic, keep the system up in order of speed.

### scx | A nightly batch job is now running into business hours. What do you do? | batch job running long, nightly job overrun, job takes too long, batch window exceeded, long running job business hours
A job that overruns its window starts competing with users for the database, causing locks and slowness, so it needs attention before it becomes an outage.

Short term: if it's affecting users right now, decide whether it's safe to pause or stop it, which depends on whether it's restartable and what happens if it doesn't finish. Communicate the impact.

Then find out why it's slower.

Data growth: the job processes everything every night, and the data has grown. Jobs that scale with total data instead of changed data eventually break. Fix: process incrementally, only records changed since the last run, using a watermark like a last-modified timestamp or change tracking.

Inefficient processing: row-by-row work with a query per row, which can often be replaced with set-based SQL or batched operations. Missing indexes for the job's queries.

Contention: something new runs at the same time, like a backup, index maintenance or another job, and they block each other. Check the job schedule and wait stats.

External dependency: a slow partner API or file transfer.

Improvements: break the job into chunks with commits per batch, so it doesn't hold long locks and can resume after failure; parallelise independent parts carefully; run heavy reads on a readable replica if available; and spread jobs across the night.

Monitoring: record duration and records processed per run, and alert when duration trends upward, so we see it long before it hits business hours.

### scx | A scheduled job ran twice and processed data twice. How do you prevent it? | job ran twice, duplicate job execution, scheduled job multiple servers, distributed lock job, quartz clustering
Jobs run twice for a few reasons, and each has its own fix.

Multiple instances: the most common. The app was scaled from one server to two, or deployed to several nodes, and every instance has the same scheduler, so each runs the job. Fixes: use a clustered scheduler, like Quartz with a shared database job store and clustering enabled, which ensures only one node fires each trigger; or a distributed lock, like a Redis lock or a SQL application lock with sp_getapplock, acquired at the start of the job; or move scheduling to a single external trigger, like a cron job in Kubernetes, EventBridge Scheduler or an Azure Functions timer, which has singleton behaviour.

Overlapping runs: the previous run hadn't finished when the next one started. Quartz's DisallowConcurrentExecution attribute, or a lock, prevents this; Kubernetes CronJobs have concurrencyPolicy Forbid.

Misfire handling: after downtime, the scheduler fires missed runs on startup. Configure misfire instructions deliberately.

Manual reruns or retries after a partial failure.

Because some duplication is always possible, the job itself must be idempotent. Track what's been processed, with a run id or per-record processed flag, use unique constraints for outputs, like invoices or notifications, and design steps so rerunning them doesn't double the effect.

Then fix the data from the double run carefully, using the job's own records to identify what was duplicated.

### scx | A poison message keeps crashing the consumer. What do you do? | poison message, consumer crash loop, message causes exception, bad message queue, dead letter poison message
A poison message is one that can never be processed successfully, like malformed data, an unexpected null, or a reference to something that doesn't exist. If the consumer crashes or rejects it with requeue, the broker delivers it again, it fails again, and the consumer is stuck in a loop, blocking everything behind it.

Immediate fix: get the message out of the way without losing it. With a proper setup, after a few failed attempts it goes to the dead-letter queue automatically. If not, I move it manually with the broker's tooling to a parking queue, so processing of other messages resumes. Never just purge the queue, especially with business events.

Then investigate: inspect the message, its headers and the consumer's error logs. Is the message invalid, sent by a buggy producer, or is our consumer failing to handle a valid edge case?

Fix the cause: either fix the producer, or fix the consumer to handle the case, and then replay the parked message, or correct it if it's truly invalid.

Prevention.

Retry limits with backoff and a dead-letter queue for every consumer, with retry counts tracked in headers.

Distinguish error types: transient errors, like timeouts, get retried; permanent errors, like validation failures, go straight to the dead-letter queue without retries.

Catch exceptions per message, so one bad message never crashes the whole consumer process.

Validate messages at the start of processing.

Alert on dead-letter queue arrivals, with tooling to inspect and replay.

### scx | Log volume suddenly increased tenfold. What do you do? | log volume spike, logs increased suddenly, logging flood, log cost spike, disk filling with logs, noisy logs
A sudden jump in log volume is both a symptom and a problem: it may signal something broken, and it can fill disks, slow the application and create a huge bill.

Find the source: group log counts by service, logger category, level and message template in the logging tool. Usually one or two messages account for most of the increase.

Then understand why.

An error loop: something is failing repeatedly, like a consumer retrying a poison message, a client in a retry loop, or a background job failing every second. The logs are the symptom; fix the failing thing.

A config change: debug or trace logging turned on in production and forgotten, or a library's log level lowered.

A code change: a new log statement inside a hot loop, or logging full request bodies.

A traffic change: legitimate traffic increased, so logs grew proportionally, which may need sampling.

Mitigate quickly: raise the log level for the noisy category through runtime configuration, if supported, or filter it in the collector, without a redeploy. If disks are at risk, ensure rotation is working.

Prevent: alerts on log volume per service, rate-limited or deduplicated logging for repetitive errors, like logging one summary per minute instead of every occurrence, code review attention to logging in loops, and budgets per team so the cost is visible.

### scx | Errors are coming from only one instance out of several. What do you do? | one instance errors, bad node, single server failing, one pod failing, instance specific errors
If one instance fails while others are fine, the code is probably fine, and something about that instance is different.

Version: did a deployment only partially succeed, so it runs an old or mixed version?

### scx | Users get intermittent 502 or 504 errors from the load balancer. How do you troubleshoot? | intermittent 502, 504 gateway timeout, load balancer 502, bad gateway intermittent, alb 502 troubleshooting
These come from the load balancer or proxy, not directly from the app, so the app's logs may show nothing. A 502 means the proxy got an invalid response or the connection failed; a 504 means it waited too long.

For 504s: some requests take longer than the proxy's timeout. Find which endpoints, from the load balancer access logs, which record target response time. Fix the slow operations, or make long operations asynchronous; raise timeouts only if the long duration is legitimate.

For 502s, the common causes.

Keep-alive mismatch: the app server closes idle connections before the load balancer does. The load balancer reuses a connection the server just closed, and the request fails. The rule: the app's keep-alive timeout must be longer than the load balancer's idle timeout. For Kestrel, KeepAliveTimeout; for Node, server.keepAliveTimeout; for IIS, connection timeout settings.

Deployments: instances shutting down while still receiving requests, without connection draining or graceful shutdown. If 502s cluster around deployment times, that's the cause.

App crashes or restarts: the process dies mid-request, from out-of-memory kills or unhandled exceptions.

Response problems: invalid headers, oversized headers, or the app resetting connections.

Health and capacity: all targets unhealthy briefly, or the app's connection or thread limits reached, so new connections are refused.

The investigation is mostly correlation: load balancer logs with timestamps and target, against app logs, restarts and deployments. The pattern, random versus clustered, quickly narrows it down.

### scx | New instances fail health checks after deployment because they start slowly. What do you do? | slow startup health check failure, startup probe, warmup dotnet, deployment fails slow start, health check grace period
If an app takes longer to become ready than the health check allows, the orchestrator kills or replaces it before it's ready, the deployment fails or loops, and old instances may be removed too early.

First, find out why startup is slow. Measure the startup phases with logs or a trace: loading configuration from remote stores, running database migrations at startup, warming caches by loading large reference data, connecting to many dependencies, JIT compiling a large application, or waiting on a slow dependency that's timing out.

Then fix both sides.

Make startup faster: move migrations out of startup into a pipeline step; load caches lazily or in the background, with the app serving requests from the database while the cache warms; parallelise independent initialisation; use ReadyToRun compilation to reduce JIT time in .NET; and set timeouts on dependencies so a missing one doesn't hang startup.

Readiness should become true only once the app can actually serve requests.

Deployment strategy: ensure the rollout waits for new instances to be ready before removing old ones, so a slow start doesn't reduce capacity.

And keep a startup duration metric, so regressions are noticed when a change adds seconds to startup.

### scx | SQL Server's transaction log is full and writes are failing. What do you do? | transaction log full, log file full sql server, error 9002, log_reuse_wait_desc, log backup, database log growth
Error 9002 means the transaction log is full and SQL Server can't write new transactions, so all writes to that database fail. It's urgent.

First, find out why the log can't be reused: query sys.databases for log_reuse_wait_desc for that database. The value tells me the cause.

LOG_BACKUP: the database is in full recovery model, but log backups haven't run, maybe the backup job failed. Fix: take a log backup immediately, which allows the log space to be reused, then fix the backup job and alert on its failures.

ACTIVE_TRANSACTION: a long-running or forgotten open transaction is holding the log. Find it with DBCC OPENTRAN or sys.dm_tran_active_transactions, and decide with the owner whether to wait or kill it, remembering that killing triggers a rollback that also takes time.

REPLICATION or AVAILABILITY_REPLICA: a replica or replication process isn't keeping up, so the log must be kept for it.

Other causes: a huge single operation, like an index rebuild or a delete of millions of rows in one transaction.

To get running quickly, if the disk has space, I can grow the log file or add a log file on another drive. What I don't do is switch to simple recovery and shrink everything in a panic, because that breaks the backup chain and point-in-time recovery, which matters a lot for regulated data.

Prevention: monitored, working log backups, alerts on log usage percentage, and batching large data operations into smaller transactions.

### scx | tempdb is filling up on SQL Server. How do you find the cause? | tempdb full, tempdb growth, tempdb contention, version store growth, sort spill tempdb, tempdb space usage
tempdb is shared by everything on the server, so when it fills up, queries across all databases start failing. I find out which kind of usage is growing.

sys.dm_db_file_space_usage shows tempdb space split into user objects, internal objects and the version store.

User objects: temporary tables and table variables created by queries or procedures. sys.dm_db_session_space_usage and sys.dm_db_task_space_usage identify the sessions using the most, which leads to the query or job. A procedure loading millions of rows into a temp table, or temp tables not dropped in long-lived connections, are typical.

Internal objects: work tables and spills from sorts, hashes and spools, when a query's memory grant is too small, or a query sorts or hashes a huge result. Execution plans with spill warnings show this. Fix: better indexes to avoid big sorts, fixing bad cardinality estimates, or rewriting the query.

Version store: with read committed snapshot or snapshot isolation enabled, row versions are kept in tempdb as long as the oldest open transaction needs them. One long-running transaction, even an idle open one, prevents cleanup, so the version store grows and grows. Find the oldest active snapshot transaction and deal with it.

Immediate relief: kill the offending session if appropriate, after checking impact, or add space. Restarting SQL Server resets tempdb, but that's a last resort with full downtime.

Prevention: size tempdb properly with multiple equal data files, monitor its usage, and alert on long-running transactions.
