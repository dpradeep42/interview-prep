### azx | How do App Service deployment slots and slot swaps work? | deployment slots, slot swap, staging slot app service, zero downtime app service, sticky settings, swap with preview
Deployment slots are live copies of an App Service app, like a staging slot alongside production, each with its own hostname, running on the same App Service plan. They're available on Standard tier and above.

The flow: I deploy the new version to the staging slot, warm it up and test it at its own URL, then swap staging with production. Settings matter. App settings and connection strings can be marked as deployment slot settings, or sticky, so they stay with the slot instead of moving with the code. For example, the staging slot keeps pointing to a staging database or has a flag disabling background jobs. Non-sticky settings move with the app during the swap.

Swap with preview does the swap in two phases, applying production settings to staging first, so I can validate before completing. Auto swap swaps automatically after a deployment to a slot, which suits continuous deployment.

Traffic routing can also send a percentage of production traffic to a slot, for simple testing in production.

One caution: database schema changes must be compatible with both versions, since the swap is instant but the database is shared.

### azx | Azure RBAC vs Entra ID roles: what is the difference? | azure rbac vs entra roles, azure role assignment, owner contributor reader, azure ad roles, scope management group subscription
They're two separate role systems that people often mix up.

Entra ID roles, formerly Azure AD roles, control administration of the directory itself: managing users, groups, app registrations, licences and identity settings. Examples are Global Administrator, User Administrator, Application Administrator and Security Reader. They apply to the tenant, or to administrative units.

Azure RBAC roles control access to Azure resources: subscriptions, resource groups, and resources like VMs, storage accounts and databases. Built-in roles include Owner, with full access including granting access to others; Contributor, which can manage resources but not grant access; Reader; and many service-specific roles, like Storage Blob Data Reader or Key Vault Secrets User, which control data-plane access, reading the actual data rather than managing the resource.

A role assignment has three parts: a security principal, like a user, group, service principal or managed identity; a role definition, which is a set of allowed actions; and a scope: management group, subscription, resource group or resource. Permissions inherit downward, so a role at the subscription applies to all resources in it. Deny assignments and Azure Policy can restrict further.

Best practices: assign roles to groups, not individuals; use the narrowest scope and the least powerful role; use data-plane roles instead of keys; use Privileged Identity Management for just-in-time, time-limited elevation to powerful roles, with approval; and review assignments regularly.

A Global Administrator can elevate themselves to manage all subscriptions, so that role is tightly controlled.

### azx | What are the Cosmos DB consistency levels? | cosmos db consistency levels, session consistency, bounded staleness, eventual consistency cosmos, strong consistency cosmos
Cosmos DB offers five consistency levels, which trade off consistency against latency, availability and throughput, especially with multiple regions.

Strong: reads always return the latest committed write, linearisability. Writes must be acknowledged across regions, so latency is higher, and it isn't available with multiple write regions.

Bounded staleness: reads may lag behind writes, but by no more than a configured number of versions or time interval. Within that bound, order is guaranteed. It suits globally distributed apps that need near-strong guarantees.

Session: the default and most popular. Within a client session, identified by a session token, you read your own writes, and reads are monotonic, never going backwards. Other clients may see slightly older data. That fits most applications: a user always sees their own changes immediately.

Consistent prefix: reads never see out-of-order writes; you might see older data, but never a gap, like seeing update three without update two.

Eventual: no ordering guarantee; replicas converge eventually. It's the lowest latency and highest throughput, fine for things like counts of likes or non-critical data.

The level is set on the account, and requests can relax it, but not strengthen it beyond the account default. Weaker levels also cost fewer request units for reads.

For a web app, session consistency is usually right, as long as the session token is passed consistently, which the SDK does within one client instance. Across instances behind a load balancer, I'd pass the token explicitly when read-your-writes matters.

### azx | How do you choose a Cosmos DB partition key, and what are request units? | cosmos db partition key, request units, ru cosmos, hot partition cosmos, cross partition query, hierarchical partition key
Cosmos DB measures cost and throughput in request units. Every operation costs RUs, based on CPU, memory and I/O: a point read of a 1 KB item by id and partition key costs one RU, writes cost more, and queries cost more depending on how much data they scan. Throughput is provisioned in RU per second, manual or autoscale, or you use serverless, paying per RU consumed. Exceeding throughput returns 429 errors, which the SDK retries.

The partition key is the most important design decision, because it determines how data and throughput are distributed. Items with the same partition key value live in the same logical partition, limited to 20 GB, and logical partitions are spread across physical partitions, each limited to 10,000 RU per second.

A good partition key: has high cardinality, many distinct values; spreads reads and writes evenly, avoiding hot keys; and matches the most frequent queries, so they hit a single partition. A query filtering on the partition key is efficient; one that doesn't becomes a cross-partition query, fanning out to every partition, which costs more RUs and latency.

For example, in a multi-tenant app, tenantId seems natural, but a huge tenant can exceed 20 GB or become hot. Hierarchical partition keys solve this, using tenantId then userId or shipmentId as sub-keys, so a big tenant spreads across partitions while queries by tenant stay targeted.

The partition key can't be changed easily later, so I design it from access patterns first.

### azx | What are the Azure Storage redundancy options? | lrs zrs grs gzrs, storage redundancy azure, geo redundant storage, read access geo redundant, storage failover
Azure Storage always keeps multiple copies of data, and the redundancy option decides where those copies are.

Locally redundant storage, LRS, keeps three copies within a single data centre in one region. It's the cheapest and protects against disk and server failures, but not against a data centre or zone outage.

Zone-redundant storage, ZRS, keeps three copies across three availability zones in the region. It protects against a whole zone going down, with data still readable and writable, so it's the recommended option for high availability within a region.

Geo-redundant storage, GRS, keeps three copies with LRS in the primary region and asynchronously replicates to a paired secondary region, which also keeps three copies with LRS. It protects against a regional disaster, but replication is asynchronous, so recent writes may be lost, measured by the last sync time.

Geo-zone-redundant storage, GZRS, combines ZRS in the primary region with geo-replication to the secondary, giving the best durability and availability.

Read-access variants, RA-GRS and RA-GZRS, let applications read from the secondary region at any time, even when the primary is healthy, which helps for read availability during an outage.

If the primary region fails, Microsoft may initiate failover, or customers can trigger a customer-managed failover, which promotes the secondary.

My choice: ZRS for most production data, and GZRS or RA-GZRS for critical data needing regional disaster recovery.

### azx | How do Service Bus sessions and duplicate detection work? | service bus sessions, ordered messages service bus, session id, duplicate detection service bus, message id dedup, fifo azure
Service Bus sessions provide ordered, first-in first-out processing of related messages. Each message has a SessionId, like a shipment id or order id. Messages with the same SessionId are delivered in order, and a session can be locked by only one receiver at a time, so all messages for that shipment are processed sequentially by one consumer, while different sessions are processed in parallel by different consumers. That gives ordering per entity with horizontal scale, similar to Kafka partition keys or SQS FIFO message groups.

Sessions also have session state, a small storage area per session that the receiver can read and update, useful for tracking workflow progress across messages. The queue or subscription must be created with sessions enabled, and every message must then have a SessionId. Receivers use a session processor in the SDK, with settings for the maximum concurrent sessions.

Duplicate detection protects against producers sending the same message twice, for example when a send times out and is retried, though the first send succeeded. When enabled on a queue or topic, Service Bus remembers the MessageId of messages received within a time window, which can be up to seven days, and silently discards any new message with the same MessageId. The producer must set a meaningful, deterministic MessageId, like an event id, not a random one per send.

Duplicate detection doesn't protect against duplicates on the consumer side, from lock expiry and redelivery, so consumers still need to be idempotent.

### azx | How do Service Bus topics, subscriptions, filters and dead-lettering work? | service bus topic subscription, subscription filters, sql filter service bus, dead letter queue service bus, max delivery count, auto forwarding
A Service Bus topic is for publish-subscribe. Publishers send messages to the topic, and each subscription gets its own copy of every message that matches its filter. Each subscription acts like a separate queue, with its own consumers, so services process events independently.

Filters decide which messages a subscription receives. A SQL filter uses a SQL-like expression on message properties, like eventType = 'Delivered' AND region = 'EU'. A correlation filter matches on properties exactly, and is more efficient. A subscription can also have actions that modify properties. Without filters, a subscription receives everything. Filtering at the broker means consumers don't receive and discard irrelevant messages.

Dead-lettering: each queue and subscription has a dead-letter sub-queue. Messages go there when they exceed the maximum delivery count, for example after ten failed attempts; when they expire, if dead-lettering on expiration is enabled; when filter evaluation fails; or when the consumer explicitly dead-letters a message it knows can't be processed, like invalid data, with a reason and description. Messages in the dead-letter queue stay until someone reads them, so I monitor the dead-letter count with alerts, investigate, fix the cause, and resubmit or discard messages, through Service Bus Explorer in the portal or a tool.

Auto-forwarding chains a subscription or queue to another queue or topic, which helps build routing topologies.

Our on-premise RabbitMQ setup uses the same ideas: exchanges, bound queues, retry and dead-letter exchanges.

Parameter files, in the .bicepparam format, hold environment-specific values, like dev, test and prod, with the same template for all environments. Secrets are referenced from Key Vault, not stored in files.

What-if is a preview of a deployment: az deployment group what-if shows what will be created, modified and deleted, and property-level differences, without making changes. I run it in pull request pipelines and before production deployments, similar to Terraform plan. It can be noisy for some resource properties, so reviewers learn to read it.

Deployment stacks manage a group of resources as a unit, so resources removed from the template can be deleted or detached automatically, and deny settings protect managed resources from changes outside the stack.

### azx | How do you use Key Vault references and App Configuration in .NET apps? | key vault references app service, azure app configuration, feature flags azure, configuration refresh dotnet, sentinel key
Two services work together for configuration in Azure.

Key Vault references let App Service and Functions app settings point to secrets instead of containing them. An app setting value like @Microsoft.KeyVault(SecretUri=...) is resolved by the platform using the app's managed identity, and the app just reads a normal setting. Without a version in the URI, it picks up the latest version of the secret, refreshed periodically. So the code doesn't change, and secrets never appear in configuration or pipelines.

Azure App Configuration is a central store for application settings and feature flags, shared across services and environments. Keys can have labels, like dev or prod, and the .NET configuration provider loads them into IConfiguration, alongside appsettings.json, so options classes work as normal. App Configuration can also hold Key Vault references, which the provider resolves with the app's identity.

Dynamic refresh: the provider can watch settings and reload them without restarting the app. The common pattern is a sentinel key: the app checks just one key periodically, and when it changes, all settings reload, so a set of related changes is applied together. IOptionsSnapshot or IOptionsMonitor then gives code the new values.

Feature flags: the Microsoft.FeatureManagement library reads flags from App Configuration, with filters for percentage rollouts, targeting specific users or groups, and time windows, so features are enabled without deployments and can be switched off quickly.

Access uses managed identities with data reader roles, not connection strings.

### azx | How do you query logs with KQL in Log Analytics? | kql query, kusto query language, log analytics workspace, application insights query, kql summarize, find exceptions kql
Log Analytics workspaces collect logs from Azure Monitor, Application Insights, VMs, containers and more, and KQL, the Kusto Query Language, is how I query them. It reads like a pipeline: start with a table and pipe through operators.

For a spike in failures in a web API, using Application Insights tables in a workspace:

AppRequests, then where TimeGenerated > ago(1h) and Success == false, then summarize count() by bin(TimeGenerated, 5m), ResultCode, then render timechart. That shows when failures started and which status codes.

Then the top failing operations: AppRequests, where Success == false, summarize failures = count() by OperationName, then top 10 by failures.

Then exceptions: AppExceptions, summarize count() by ProblemId, OuterMessage, which groups identical exceptions.

To trace one request across components: union AppRequests, AppDependencies, AppExceptions, AppTraces, then where OperationId == "the-id", then order by TimeGenerated. Everything sharing the operation id is one end-to-end transaction.

For latency: summarize percentiles(DurationMs, 50, 95, 99) by OperationName.

Useful operators: extend to compute columns, project to select columns, join to combine tables, parse and extract for text, and mv-expand for arrays. Custom dimensions from structured logging are in a dynamic Properties column, accessed like tostring(Properties.TenantId).

Queries can become alert rules, and pinned to workbooks and dashboards.

The same KQL works in Azure Data Explorer, Microsoft Sentinel and Fabric.
