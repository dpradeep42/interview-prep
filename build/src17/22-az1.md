### azx | What are the Cosmos DB consistency levels? | cosmos db consistency levels, session consistency, bounded staleness, eventual consistency cosmos, strong consistency cosmos
See, Cosmos DB gives you five consistency levels, trading consistency against latency, availability and throughput, especially with multiple regions.

Strong means reads always return the latest committed write, linearisability. Writes have to be acknowledged across regions, so latency is higher, and it's not available with multiple write regions.

Bounded staleness means reads can lag behind writes, but by no more than a configured number of versions or a time interval. Within that bound, order is guaranteed. It suits globally distributed apps that need near-strong guarantees.

Session is the default and the most popular. Within a client session, identified by a session token, you read your own writes, and reads are monotonic, they never go backwards. Other clients might see slightly older data. That fits most apps, since a user always sees their own changes immediately.

Consistent prefix means reads never see out-of-order writes. You might see older data, but never a gap, like seeing update three without update two.

Eventual has no ordering guarantee, replicas just converge eventually. Lowest latency, highest throughput, fine for things like like-counts or non-critical data.

The level is set on the account, and requests can relax it, but not make it stronger than the account default. Weaker levels also cost fewer request units for reads.

For a web app, session is usually right, as long as the session token is passed consistently, which the SDK does inside one client instance. Across instances behind a load balancer, I'd pass the token explicitly when read-your-writes matters. That's an easy one to miss.

### azx | How do you choose a Cosmos DB partition key, and what are request units? | cosmos db partition key, request units, ru cosmos, hot partition cosmos, cross partition query, hierarchical partition key
Actually Cosmos DB measures cost and throughput in request units. Every operation costs RUs, based on CPU, memory and I/O. A point read of a 1 KB item by id and partition key costs one RU, writes cost more, and queries cost more depending on how much data they scan. The partition key is the most important design decision, because it decides how data and throughput get distributed. A good partition key has high cardinality, lots of distinct values. It spreads reads and writes evenly, so no hot keys. And it matches the most frequent queries, so they hit a single partition. Let me take an example. In a multi-tenant app, tenantId feels natural, but a huge tenant can go past 20 GB or become hot. Hierarchical partition keys fix that, using tenantId then userId or shipmentId as sub-keys, so a big tenant spreads across partitions while queries by tenant stay targeted.

And the partition key can't be changed easily later, so I design it from access patterns first.

### azx | What are the Azure Storage redundancy options? | lrs zrs grs gzrs, storage redundancy azure, geo redundant storage, read access geo redundant, storage failover
So Azure Storage always keeps multiple copies of data, and the redundancy option decides where those copies live.

Locally redundant storage, LRS, keeps three copies within a single data centre in one region. Cheapest, protects against disk and server failures, but not a data centre or zone outage.

Zone-redundant storage, ZRS, keeps three copies across three availability zones in the region. It survives a whole zone going down, with data still readable and writable, so it's the recommended option for high availability within a region.

Geo-redundant storage, GRS, keeps three copies with LRS in the primary region and replicates asynchronously to a paired secondary region, which also keeps three copies with LRS. If the primary region fails, Microsoft may start a failover, or customers can trigger a customer-managed failover, which promotes the secondary.

I'd go with ZRS for most production data, and GZRS or RA-GZRS for critical data that needs regional disaster recovery. That's usually the conversation I'd have with the team, cost versus how bad losing a region would be.

### azx | How do Service Bus sessions and duplicate detection work? | service bus sessions, ordered messages service bus, session id, duplicate detection service bus, message id dedup, fifo azure

Messages with the same SessionId are delivered in order, and a session can be locked by only one receiver at a time. So all messages for that shipment get processed sequentially by one consumer, while different sessions are processed in parallel by different consumers. Ordering per entity with horizontal scale, similar to Kafka partition keys or SQS FIFO message groups.

And duplicate detection doesn't help with duplicates on the consumer side, from lock expiry and redelivery, so consumers still need to be idempotent.

### azx | How do you use Key Vault references and App Configuration in .NET apps? | key vault references app service, azure app configuration, feature flags azure, configuration refresh dotnet, sentinel key
So two services work together for configuration in Azure.

Key Vault references let App Service and Functions app settings point to secrets instead of holding them. An app setting value that starts with at-Microsoft-dot-KeyVault and gives the secret URI is resolved by the platform using the app's managed identity, and the app just reads a normal setting. Without a version in the URI, it picks up the latest version of the secret, refreshed periodically. So the code doesn't change, and secrets never show up in configuration or pipelines.

Azure App Configuration is a central store for app settings and feature flags, shared across services and environments. Keys can have labels, like dev or prod, and the .NET configuration provider loads them into IConfiguration, alongside appsettings.json, so options classes just work. App Configuration can also hold Key Vault references, which the provider resolves with the app's identity.

Dynamic refresh, the provider can watch settings and reload them without restarting the app. The usual pattern is a sentinel key. The app checks just one key periodically, and when it changes, all settings reload, so a set of related changes lands together. IOptionsSnapshot or IOptionsMonitor then gives the code the new values.

Feature flags, the Microsoft.FeatureManagement library reads flags from App Configuration, with filters for percentage rollouts, targeting specific users or groups, and time windows. So features get turned on without deployments and can be switched off quickly if something goes wrong.
