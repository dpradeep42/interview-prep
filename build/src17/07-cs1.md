### csx | What is the contract between Equals and GetHashCode? | gethashcode, equals and gethashcode, override gethashcode, hash code contract, dictionary key custom class, hashcode.combine
The rule is, if two objects are equal by Equals, they have to return the same hash code. The other way isn't required, different objects can share a hash code, that's just a collision.

Why it matters, hash-based collections like Dictionary and HashSet first use the hash code to find the bucket, and only then call Equals inside that bucket. Then a dictionary lookup with an equal key just doesn't find the entry, and a HashSet happily stores duplicates. Honestly those bugs are really confusing to debug.

One more rule, the hash code shouldn't change while the object is being used as a key. If I change a field that's part of the hash after adding it to a dictionary, it's basically lost in the wrong bucket. That's why keys should be immutable.

Records and value tuples generate correct Equals and GetHashCode automatically. So for value-like keys, like a composite key of study id and site id, I just use a record struct. Saves a lot of trouble.

### csx | How does Dictionary work internally, and what is its lookup complexity? | dictionary internals, hash table c#, dictionary lookup o(1), dictionary vs list lookup, hash collision, dictionary capacity
A Dictionary is basically a hash table. When you add a key, it calls GetHashCode on the key, maps that hash to a bucket index, and stores the entry there. If two entries land in the same bucket, that's a collision, and they get chained together.

On lookup, it computes the hash, goes straight to the bucket, and then compares keys inside that bucket using Equals. With a decent hash function, buckets have very few entries, so lookup, insert and remove are O(1) on average. Compare that to searching a List, which is O(n), since it might check every element.

When the dictionary grows past its capacity, it resizes. It allocates a bigger array, roughly double, and re-inserts every entry, which is an O(n) operation. So if I roughly know the size, I pass the capacity to the constructor and avoid all that resizing.

Performance really depends on the key's hash. A bad GetHashCode, say one that returns the same value for everything, turns the dictionary into a slow linked list, O(n) per lookup.

A couple more points. Dictionary isn't thread-safe for writes, so for concurrent use I'd go with ConcurrentDictionary. Insertion order isn't guaranteed. And for string keys, I often pass StringComparer.OrdinalIgnoreCase so lookups are case-insensitive. That one saves a lot of small bugs.

### csx | What is a finalizer, and how is it different from Dispose? | finalizer, destructor c#, dispose pattern, gc.suppressfinalize, safehandle, unmanaged resources
A finalizer, the one written with the tilde like a destructor, is a method the garbage collector calls before reclaiming an object's memory. Dispose is a method my code calls explicitly, usually through using, to release resources at a known time.

The main difference is timing and reliability. Dispose runs immediately, deterministically. A finalizer runs at some unknown later time, on the finalizer thread, after the GC notices the object is unreachable. And it might not run at all if the process exits abruptly.

Finalizers are also expensive. Objects with finalizers survive at least one extra GC, because they go to the finalization queue first. That promotes them to an older generation and increases memory pressure.

Honestly, in modern .NET, I almost never write a finalizer.
