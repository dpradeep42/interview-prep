### csx | What is the difference between == and Equals() in C#? | double equals vs equals, == vs equals, reference equality vs value equality, operator equality c#, referenceequals
For reference types, the == operator by default compares references, meaning whether two variables point to the same object in memory. Equals is a virtual method, and by default it also compares references, but classes can override it to compare values.

The difference shows up when a type overrides them. String is the classic example: both == and Equals are overridden to compare the characters, so two different string objects with the same text are equal either way.

But == is resolved at compile time, based on the variable's declared type, while Equals is resolved at runtime, based on the actual object. So if two strings are stored in variables of type object, == compares references and can return false, while Equals still compares the text and returns true. That's a classic interview trick.

For value types, like int or a struct, Equals compares the values. A struct's default Equals uses reflection, which is slow, so for performance-sensitive structs, I implement IEquatable of T.

Records generate value-based Equals and == for you.

If I override Equals, I must also override GetHashCode, and usually the == and != operators, so they behave consistently. And for a guaranteed reference check, I use ReferenceEquals.

### csx | What is the contract between Equals and GetHashCode? | gethashcode, equals and gethashcode, override gethashcode, hash code contract, dictionary key custom class, hashcode.combine
The rule is: if two objects are equal according to Equals, they must return the same hash code. The reverse isn't required; different objects can share a hash code, which is a collision.

This matters because hash-based collections, like Dictionary and HashSet, first use the hash code to find the bucket, and only then call Equals within that bucket. If I override Equals to compare by value but leave the default GetHashCode, which is based on the object reference, two "equal" objects will usually land in different buckets. Then a dictionary lookup with an equal key fails to find the entry, and a HashSet happily stores duplicates. Those bugs are very confusing.

So whenever I override Equals, I override GetHashCode using the same fields. In modern .NET, HashCode.Combine of the fields does it neatly.

Another important rule: the hash code shouldn't change while the object is used as a key. If I mutate a field that's part of the hash after adding the object to a dictionary, it's effectively lost in the wrong bucket. That's why keys should be immutable.

Records and value tuples generate correct Equals and GetHashCode automatically, so for value-like keys, like a composite key of study id and site id, I use a record struct.

The cost is that repeated concatenation in a loop creates many temporary strings. Building a string from 10,000 pieces with plus-equals copies the growing string every time, which is roughly quadratic, and creates a lot of garbage for the GC.

My rule: for a few concatenations, or one expression, plain concatenation or interpolation is fine and more readable; the compiler optimises it. In loops or when building large text, like a CSV export or an email body, I use StringBuilder, or string.Join for joining collections.

For very hot paths, there's also Span-based formatting and string.Create.

### csx | What does yield return do, and how do iterators work in C#? | yield return, iterator c#, yield break, lazy sequence, custom ienumerable, state machine iterator
yield return lets me write a method that produces a sequence one item at a time, lazily, without building the whole collection in memory.

When a method returns IEnumerable of T and uses yield return, the compiler turns it into a state machine class. Nothing runs when the method is called. Code runs only when someone enumerates the result, for example with foreach. Each time the consumer asks for the next item, the method runs until the next yield return, hands back that value, and pauses, remembering where it was. yield break ends the sequence early.

For asynchronous sources, like paging through an API, I use async iterators: IAsyncEnumerable with yield return and await foreach.

### csx | How does Dictionary work internally, and what is its lookup complexity? | dictionary internals, hash table c#, dictionary lookup o(1), dictionary vs list lookup, hash collision, dictionary capacity
A Dictionary is a hash table. When I add a key, it calls GetHashCode on the key, maps the hash to a bucket index, and stores the entry there. Entries that land in the same bucket, collisions, are chained together.

When I look up a key, it computes the hash, goes straight to the bucket, and then compares the keys in that bucket using Equals. With a good hash function, buckets contain very few entries, so lookup, insert and remove are O(1) on average. Compare that with searching a List, which is O(n), because it may check every element.

As the dictionary grows past its capacity, it resizes: allocates a bigger array, roughly doubling, and re-inserts every entry, which is an O(n) operation. So if I know the approximate size, I pass the capacity to the constructor and avoid repeated resizing.

Performance depends on the key's hash. A bad GetHashCode, like one that returns the same value for everything, turns the dictionary into a slow linked list, O(n) per lookup.

Also, Dictionary isn't thread-safe for writes; for concurrent use I'd use ConcurrentDictionary. It doesn't keep insertion order guaranteed, and for string keys, I often pass StringComparer.OrdinalIgnoreCase to make lookups case-insensitive.

### csx | When would you use a HashSet instead of a List? | hashset vs list, hashset c#, contains performance, unique values collection, set operations c#
I use a HashSet when I need fast membership checks or uniqueness, and I don't care about order or duplicates.

A List keeps items in order and allows duplicates, and Contains has to scan the list, which is O(n). A HashSet stores unique items using hashing, so Contains, Add and Remove are O(1) on average. Add returns false if the item already exists, which is handy for de-duplication.

The difference is huge in loops. If I check, for each of 10,000 incoming records, whether its id is in a list of 10,000 existing ids, that's around 100 million comparisons with a List, but only about 10,000 hash lookups with a HashSet.

HashSet also has efficient set operations: UnionWith, IntersectWith, ExceptWith and IsSubsetOf, which are perfect for things like "which kit ids in the file are not in the database".

The trade-offs: a HashSet uses more memory than a List, there's no index access, and the order isn't guaranteed. And it relies on good Equals and GetHashCode for the element type.

In LINQ, Distinct, Except and Intersect use a set internally, but if I do repeated lookups, I build the HashSet once myself.

In our CSV import, I load the existing kit numbers into a HashSet once, so validating each row is a fast lookup.

### csx | What are the common pitfalls of ConcurrentDictionary? | concurrentdictionary, getoradd pitfall, concurrentdictionary thread safe, lazy getoradd, addorupdate
ConcurrentDictionary is thread-safe for individual operations, but there are a few traps.

The biggest is that the value factory in GetOrAdd and AddOrUpdate isn't guaranteed to run only once. If two threads ask for the same missing key at the same time, both may run the factory, and only one result is stored. If the factory is expensive, like a database call, or has side effects, like creating a connection, that's a problem. The common fix is to store Lazy of T values, so the dictionary only stores the Lazy wrapper, and the expensive work runs once when Value is accessed, with thread-safe Lazy mode.

Second, compound operations aren't atomic. Checking ContainsKey and then adding, or reading a value and then updating it, can race with other threads. I use the atomic methods instead: GetOrAdd, AddOrUpdate, TryUpdate with a comparison value, or TryRemove.

Third, the values themselves aren't protected. If the value is a mutable List, two threads can still modify it at the same time.

Fourth, some operations, like Count, Keys or ToArray, lock all internal locks, so calling them often under load hurts performance.

And finally, a ConcurrentDictionary used as a cache grows forever unless something evicts entries. For caching, I'd usually use IMemoryCache or HybridCache instead, which have expiry and size limits.

### csx | Why is async void dangerous? | async void, async void exception, async void event handler, fire and forget async, avoid async void
An async void method can't be awaited, and that causes two main problems.

First, exceptions. In an async Task method, an exception is captured in the returned Task, and the caller sees it when it awaits. In async void, there's no Task to hold the exception, so it's raised directly on the synchronisation context or the thread pool. Everywhere else, I return Task or ValueTask. If I truly want fire-and-forget, I don't hide it in async void; I put the work on a background queue processed by a hosted service, with proper error handling and logging, and a fresh DI scope.

### csx | What is a finalizer, and how is it different from Dispose? | finalizer, destructor c#, dispose pattern, gc.suppressfinalize, safehandle, unmanaged resources
A finalizer, written with the tilde syntax like a destructor, is a method the garbage collector calls before reclaiming an object's memory. Dispose is a method that my code calls explicitly, usually through using, to release resources at a known time.

The key difference is timing and reliability. Dispose runs immediately and deterministically. A finalizer runs at some unknown later time, on the finalizer thread, after the GC notices the object is unreachable, and may not run at all if the process exits abruptly.

Finalizers are also costly. Objects with finalizers survive at least one extra GC, because they go to the finalization queue first, which promotes them to an older generation and increases memory pressure.

So the classic dispose pattern was: Dispose releases resources and calls GC.SuppressFinalize, so the finalizer doesn't run; the finalizer is only a safety net for unmanaged resources if someone forgot to dispose.

In modern .NET, I almost never write a finalizer. Unmanaged handles should be wrapped in a SafeHandle, which has its own reliable finalization, and my class just implements IDisposable and disposes the SafeHandle. For classes that only hold managed disposables, like a DbContext or HttpClient, I implement Dispose without any finalizer.

### csx | What are readonly struct and ref struct? | readonly struct, ref struct, span ref struct, stackonly struct, defensive copy, struct performance
Both are special kinds of structs aimed at correctness and performance.

A readonly struct declares that all its fields are readonly, so the struct is immutable. Besides making the intent clear, it helps performance. When you call a method on a struct through a readonly reference, like an in parameter or a readonly field, the compiler normally makes a defensive copy, because it can't be sure the method won't modify the struct. With a readonly struct, it knows nothing can change, so it skips those copies. I use readonly structs for small value types, like a Money or Coordinates type.

A ref struct is a struct that must live only on the stack. It can't be boxed, can't be a field of a class or a normal struct, couldn't traditionally be used as a generic type argument, can't be captured in lambdas, and historically couldn't be used across await in async methods. Span of T is the famous example. These rules make it safe for Span to point at stack memory or slices of arrays, because it can never outlive the memory it points to.

C# 13 relaxed some rules: ref structs can implement interfaces and be used as generic arguments with the allows ref struct constraint, and can be used in async methods and iterators, as long as they don't cross an await or yield.

### csx | What are covariance and contravariance in C#? | covariance contravariance, in and out generic, variance c#, ienumerable covariance, func contravariance
Variance describes whether a generic type can be used with more specific or more general type arguments than declared.

Covariance, marked with the out keyword, lets me use a more derived type where a base type is expected, for types that only produce values. IEnumerable of T is covariant, so an IEnumerable of string can be assigned to an IEnumerable of object. That's safe, because I can only read from it, and every string is an object.

Contravariance, marked with the in keyword, goes the other way, for types that only consume values. Func of T result is both: contravariant in its input parameters and covariant in its return type.

Arrays are covariant for historical reasons, which isn't type-safe: putting the wrong type into a covariant array compiles but throws ArrayTypeMismatchException at runtime.

Variance only applies to interfaces and delegates, and only to reference types.
