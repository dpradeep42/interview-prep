### awsx | How does IAM policy evaluation work when allow and deny conflict? | iam policy evaluation, explicit deny, implicit deny, permission boundary, resource policy vs identity policy, iam access denied why
IAM evaluates every request against all policies that apply, and the logic is simple to remember: by default, everything is implicitly denied; an explicit allow grants access; and an explicit deny always wins over any allow.

The policies involved within an account: identity-based policies attached to the user or role; resource-based policies, like an S3 bucket policy or KMS key policy; permission boundaries, which set the maximum permissions an identity can have; session policies, passed when assuming a role; and, from the organisation, Service Control Policies and Resource Control Policies.

The evaluation order, simplified: if any policy has an explicit deny matching the request, it's denied. Then the request must be allowed by SCPs, by the permission boundary if one is set, and by the session policy if there is one, because these are limits. Finally, it must be allowed by either the identity policy or the resource policy. For cross-account access, both sides must allow it: the caller's identity policy and the resource policy in the other account.

When I debug an AccessDenied error, I check, in order: the error message, which now often names the policy type that denied it; CloudTrail for the exact action, resource and principal; any explicit denies, including SCPs and bucket policies with conditions, like requiring encryption or a VPC endpoint; KMS key policies, which are commonly forgotten when accessing encrypted S3 objects or secrets; and the IAM policy simulator.

### awsx | ECS task role vs task execution role: what is the difference? | ecs task role vs execution role, ecs iam role, task execution role permissions, container aws credentials, ecs secrets permission
ECS tasks use two different IAM roles, and confusing them is a common source of errors.

The task execution role is used by the ECS agent and Fargate infrastructure, not by my application code. It grants the permissions needed to start the task: pulling the container image from ECR, sending container logs to CloudWatch Logs, and fetching secrets from Secrets Manager or Parameter Store that are injected as environment variables in the task definition. The managed policy AmazonECSTaskExecutionRolePolicy covers ECR and logs; secrets need extra permissions, including KMS decrypt if a customer key encrypts them.

The task role is used by my application inside the container. When the code uses the AWS SDK, the SDK automatically gets temporary credentials for this role from the container credentials endpoint. It grants whatever the application needs: reading from an S3 bucket, sending messages to SQS, reading and writing a DynamoDB table. Each service should have its own task role with least-privilege permissions.

Symptoms of mixing them up: if a task fails to start with errors pulling the image, or "unable to retrieve secret", the execution role is missing permissions. If the task runs but the application gets AccessDenied when calling S3 or SQS, the task role is missing permissions, or the task has no task role, so the SDK can't find credentials.

So the execution role gets the task running; the task role is what the running code uses.

### awsx | What is KMS envelope encryption? | kms envelope encryption, data key, aws kms, customer managed key, encrypt data aws, generate data key
AWS KMS manages encryption keys, and its keys never leave KMS unencrypted. But KMS can only encrypt up to 4 KB directly, and calling KMS for every piece of data would be slow and costly. Envelope encryption solves this.

The process: the application asks KMS to generate a data key, under a KMS key, often called the master key. KMS returns two copies of the data key: plaintext and encrypted under the KMS key. The application encrypts the data locally with the plaintext data key, using a fast algorithm like AES-GCM, then discards the plaintext key from memory, and stores the encrypted data key alongside the encrypted data. To decrypt, the application sends the encrypted data key to KMS, which decrypts it, if the caller has permission, and returns the plaintext data key, which then decrypts the data locally.

The benefits: large data can be encrypted efficiently; the KMS key itself never leaves KMS; access to data is controlled by KMS key policies and IAM, and every decrypt is logged in CloudTrail; and rotating the KMS key doesn't require re-encrypting all the data.

AWS services, like S3, EBS, RDS and Secrets Manager, use envelope encryption under the hood when you choose a KMS key. For application-level encryption, the AWS Encryption SDK implements it properly, including data key caching.

Customer managed keys give control over key policies, rotation and deletion, and allow cross-account access.

A typical investigation for a spike in errors:

Good queries depend on good logs: consistent structured fields like correlation id, tenant, endpoint and duration.

### awsx | ECS deployments: rolling vs blue/green, and what is the deployment circuit breaker? | ecs rolling deployment, ecs blue green, ecs deployment circuit breaker, minimumhealthypercent, ecs rollback, codedeploy ecs
ECS services support several deployment strategies.

Rolling update is the default. ECS replaces tasks gradually, controlled by minimumHealthyPercent and maximumPercent. For example, 100 and 200 means ECS starts new tasks first, up to double the desired count, waits for them to pass health checks, then stops old tasks, so capacity never drops. 50 and 100 replaces half at a time without extra capacity.

The deployment circuit breaker watches a rolling deployment: if new tasks keep failing to start or fail health checks, it marks the deployment as failed, and with rollback enabled, automatically returns to the last successful deployment. Since 2025, ECS supports blue/green natively, with lifecycle hooks to run tests, a test listener to check green before production traffic, and a bake time before old tasks are removed, allowing instant rollback by switching traffic back. Previously this required CodeDeploy, which also supports canary and linear traffic shifting. ECS now also has native linear and canary strategies.

I'd use rolling with circuit breaker and alarms as the baseline, and blue/green or canary for critical services.

### awsx | How does ECS service auto scaling work? | ecs service auto scaling, target tracking ecs, ecs scale on request count, step scaling, ecs scale on sqs queue depth
ECS service auto scaling adjusts the desired number of tasks in a service, using Application Auto Scaling.

Target tracking is the simplest and usually best. I pick a metric and a target, like average CPU at 60 percent, memory at 70 percent, or ALB request count per target at 500, and auto scaling adds or removes tasks to keep the metric near that target. Request count per target is often better than CPU for web APIs, because it reacts directly to load.

Step scaling uses CloudWatch alarms with steps, like add two tasks when CPU is above 70 percent and four when above 85 percent, which gives more control for unusual patterns.

Scheduled scaling changes the minimum and maximum capacity at specific times, like scaling up before business hours or a known batch window. Predictive scaling, now available for ECS, forecasts load from history and scales ahead of time.

For queue workers, I scale on queue backlog. The best metric is backlog per task: the approximate number of visible messages divided by running tasks, published as a custom metric or computed with metric math, with a target based on how many messages a task can process within acceptable latency.

Things to tune: minimum and maximum tasks, so there's always some capacity and costs are bounded; cooldowns, with scale-out fast and scale-in slower to avoid flapping; and enough cluster capacity, which Fargate handles automatically, while EC2 needs capacity providers.

Capacity providers decide where ECS tasks run and manage the underlying capacity.

For Fargate, there are two built-in capacity providers: FARGATE and FARGATE_SPOT. Fargate Spot runs tasks on spare AWS capacity at up to about 70 percent discount, but tasks can be interrupted with a two-minute warning when AWS needs the capacity back. ### awsx | How do ALB health checks and deregistration delay affect deployments? | alb health check, target group health check, deregistration delay, connection draining, 502 during deployment ecs, alb slow start
Both settings matter a lot for zero-downtime deployments.

Only healthy targets receive traffic. During a deployment, new tasks only get traffic once they pass health checks, and ECS only stops old tasks once new ones are healthy. ### awsx | How does SnapStart improve Lambda cold starts for .NET? | lambda snapstart, snapstart dotnet, lambda cold start dotnet, native aot lambda, reduce cold start lambda
Cold starts happen when Lambda creates a new execution environment: downloading code, starting the runtime, and running initialisation code. For .NET, JIT compilation and loading dependencies, like dependency injection setup and SDK clients, can make cold starts take a second or more.

SnapStart, available for .NET 8 and later managed runtimes since late 2024, as well as Java and Python, addresses this. When I publish a function version, Lambda runs the initialisation phase once, takes a snapshot of the memory and disk state of the initialised environment, encrypts and caches it. New execution environments are resumed from the snapshot, rather than initialising from scratch, which can reduce cold start times dramatically.

Things to be careful about. Uniqueness: anything generated during initialisation, like random seeds, unique ids or cached credentials, is the same in every environment restored from the snapshot. There are runtime hooks, before snapshot and after restore, to refresh such state, and network connections opened during init may need re-establishing after restore. It works with published versions and aliases, not $LATEST. There's a cost for caching and restoring snapshots for .NET. And it can't be combined with provisioned concurrency.

The alternatives: Native AOT compilation, which removes JIT and gives very fast starts, but requires trimming-compatible code and libraries; provisioned concurrency, which keeps environments warm at a cost; and simply reducing initialisation work, lazy loading what isn't always needed, and choosing more memory, which also gives more CPU.

### awsx | How do .NET apps get AWS credentials, and why should you never use access keys in code? | aws credentials dotnet, default credential chain, aws sdk credentials, access keys in code, iam roles anywhere, aws sso credentials
The AWS SDK for .NET resolves credentials through a default credential provider chain, checking several sources in order, so the same code works everywhere without changes.

Roughly, the order is: credentials passed explicitly in code; environment variables, like AWS_ACCESS_KEY_ID; the shared credentials and config files with profiles, including IAM Identity Center SSO profiles for developers; web identity tokens, used by EKS IRSA and OIDC in CI; the ECS container credentials endpoint, which gives tasks their task role credentials; and the EC2 instance metadata service, for the instance role.

So in practice: developers run aws sso login and use a profile with short-lived credentials; CI pipelines assume a role through OIDC federation, with no stored secrets; ECS tasks use their task role; Lambda functions use their execution role; EKS pods use Pod Identity or IRSA. All of these are temporary credentials that rotate automatically.

Long-lived access keys in code, in configuration files, or in environment variables are a serious risk. They get committed to Git, leaked in logs or container images, they never expire unless rotated manually, and they're often over-privileged. Attackers scan public repositories for AWS keys within minutes.

For workloads outside AWS, like on-premise servers that need AWS access, IAM Roles Anywhere issues temporary credentials based on X.509 certificates from a trusted certificate authority, instead of access keys.

If keys are unavoidable, they get least privilege, rotation, and storage in a secrets manager.

### awsx | How do you set up Terraform remote state with locking on AWS? | terraform remote state s3, terraform state locking, use_lockfile, dynamodb lock terraform, terraform backend s3, state file security
Terraform's state file maps configuration to real resources, so for a team it must be stored remotely, shared and locked.

On AWS, the standard backend is S3. I create a dedicated bucket, often in a separate management or tooling account, with versioning enabled, so previous states can be recovered after corruption or a bad apply; encryption with KMS; Block Public Access; and a bucket policy limiting access to the CI roles and a few administrators, because state can contain sensitive values like generated passwords.

Locking prevents two applies running at the same time and corrupting the state. Historically, this used a DynamoDB table referenced in the backend configuration. Since Terraform 1.10, the S3 backend supports native locking with use_lockfile = true, which creates a lock file in the bucket using S3 conditional writes, and DynamoDB locking is deprecated. If a run crashes, a stale lock can be removed with terraform force-unlock, carefully.

Structure: separate state files per environment and per component, like network, data and services, using different keys, so a mistake has a limited blast radius and plans are faster. Teams then read outputs from other states, or better, look up resources with data sources.

Access: CI uses an OIDC role to read and write state; humans normally don't apply from laptops.

Terraform Cloud or HCP Terraform are alternatives that manage state, locking and runs.

### awsx | How do you safely refactor Terraform: import, moved and removed blocks? | terraform import block, terraform moved block, terraform removed block, terraform refactor without destroy, terraform state mv
As Terraform code evolves, I often need to change how resources are tracked without destroying and recreating them. Doing this wrong can delete a production database, so modern Terraform provides declarative blocks that are reviewed in pull requests like any other code.

Import blocks bring existing resources, created manually or by another tool, under Terraform management. I write an import block with the resource address and the real resource id, and run terraform plan with -generate-config-out to generate a starting configuration, then clean it up. The plan shows the import, and apply records it in state, without changing the resource. Import blocks can use for_each for many resources.

Moved blocks handle renames and restructuring: renaming a resource, moving it into a module, or converting from count to for_each. Without a moved block, Terraform would plan to destroy the old address and create a new one. With moved from and to, it simply updates the state. These replace manual terraform state mv commands, which weren't reviewed or repeatable across environments.

Removed blocks, since Terraform 1.7, stop managing a resource without destroying it, with lifecycle destroy = false, for example when handing a resource to another team's configuration.

Throughout, the plan is my safety net: before applying, I check it shows no unexpected destroys or replacements. I also add prevent_destroy to critical resources, like databases and state buckets.

### awsx | How do you add policy checks and security scanning to Terraform pipelines? | terraform policy as code, checkov, tfsec, trivy terraform, opa conftest, sentinel, terraform security scanning
Policy as code catches insecure or non-compliant infrastructure before it's created, which is much cheaper than finding it in production.

Static scanning of Terraform code: tools like Checkov, Trivy, which absorbed tfsec, and KICS scan configurations for misconfigurations, like S3 buckets without encryption or Block Public Access, security groups open to the internet, unencrypted databases, missing logging, or overly broad IAM policies. They run in the pull request pipeline and annotate findings. Teams can suppress specific checks with a documented reason in code.

Policy checks on the plan: since the plan shows exactly what will change, including computed values, I can evaluate the JSON plan output with Open Policy Agent, using Conftest, or Sentinel in HCP Terraform, against custom rules. For example: every resource must have owner and cost-centre tags, only approved instance types and regions, no public IPs on databases, or deletions of certain resource types need a special approval.

Linting and validation: terraform fmt, terraform validate and TFLint catch errors and provider-specific mistakes early.

A typical pipeline: on pull request, run format, validate, lint, security scan and plan, post the plan summary and findings as a comment, and fail on high-severity issues. On merge, apply the reviewed plan with an approval for production.

Runtime controls complement this: AWS Config rules and Service Control Policies catch anything created outside Terraform.
