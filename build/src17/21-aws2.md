### awsx | What is KMS envelope encryption? | kms envelope encryption, data key, aws kms, customer managed key, encrypt data aws, generate data key
Okay, AWS KMS manages encryption keys, and its keys never leave KMS unencrypted. But KMS can only encrypt up to 4 KB directly, and calling KMS for every piece of data would be slow and expensive. Envelope encryption solves that.

How it works. The app asks KMS to generate a data key, under a KMS key, often called the master key. KMS returns two copies of the data key, one plaintext and one encrypted under the KMS key. Access to data is controlled by KMS key policies and IAM, and every decrypt is logged in CloudTrail. And rotating the KMS key doesn't mean re-encrypting all the data.

AWS services like S3, EBS, RDS and Secrets Manager use envelope encryption under the hood when you pick a KMS key. For application-level encryption, the AWS Encryption SDK implements it properly, including data key caching, so I wouldn't hand-roll it.

Customer managed keys give you control over key policies, rotation and deletion, and allow cross-account access.

Actually the AWS SDK for .NET resolves credentials through a default credential provider chain. It checks several sources in order, so the same code works everywhere without changes.

Roughly the order is credentials passed explicitly in code. Then environment variables, like AWS_ACCESS_KEY_ID. Then the shared credentials and config files with profiles, including IAM Identity Center SSO profiles for developers. Then web identity tokens, used by EKS IRSA and OIDC in CI. Then the ECS container credentials endpoint, which gives tasks their task role credentials. And the EC2 instance metadata service, for the instance role.

Lambda functions use their execution role. EKS pods use Pod Identity or IRSA. All temporary credentials that rotate automatically.

Long-lived access keys in code, config files, or environment variables are a serious risk. For workloads outside AWS, like on-premise servers that need AWS access, IAM Roles Anywhere issues temporary credentials based on X.509 certificates from a trusted certificate authority, instead of access keys.

And if keys really can't be avoided, they get least privilege, rotation, and storage in a secrets manager.

### awsx | How do you safely refactor Terraform: import, moved and removed blocks? | terraform import block, terraform moved block, terraform removed block, terraform refactor without destroy, terraform state mv
So as Terraform code evolves, you often need to change how resources are tracked without destroying and recreating them. Get this wrong and you can delete a production database, so modern Terraform gives you declarative blocks that get reviewed in pull requests like any other code.

Import blocks bring existing resources, created manually or by another tool, under Terraform management. You write an import block with the resource address and the real resource id, and run terraform plan with the generate-config-out flag to generate a starting configuration, then clean it up. The plan shows the import, and apply records it in state without changing the resource. Import blocks can use for_each for many resources.

Moved blocks handle renames and restructuring. Renaming a resource, moving it into a module, or converting from count to for_each. Without a moved block, Terraform would plan to destroy the old address and create a new one. With moved from and to, it just updates the state. These replace manual terraform state mv commands, which weren't reviewed or repeatable across environments.

Removed blocks, since Terraform 1.7, stop managing a resource without destroying it, using a lifecycle setting with destroy set to false. Like when you're handing a resource over to another team's configuration.

Through all of it, the plan is my safety net. Before applying, I check it shows no unexpected destroys or replacements. I also add prevent_destroy to critical resources, like databases and state buckets. Trust me, that one's worth it.
