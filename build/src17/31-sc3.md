### scx | A long-running user request ties up the server. How do you redesign it? | long running request, request takes minutes, move to background processing, async request reply, 202 accepted pattern
So if a request takes minutes, generating a big report, running a simulation, importing a large file, keeping the HTTP request open causes timeouts at proxies and browsers, holds server resources, and fails badly when the connection drops.

The redesign is the asynchronous request-reply pattern. The API validates the request quickly, creates a job record with a status like Pending, puts a message on a queue, and returns 202 Accepted with a job id and a status URL.

A background worker, a hosted service, a separate worker or a function, picks up the message and does the work, updating progress and status, and stores the result somewhere like blob storage or a results table.

The client polls the status URL, or gets a push notification through SignalR or email when it's done, and then fetches the result.

What you get is no request timeouts, work that survives server restarts because it's queued, retries on failure, controlled concurrency so ten big jobs don't flatten the database, and a UI that can show progress while users keep working.

The details I'd get right are idempotency, so a retried submission doesn't create duplicate jobs, using an idempotency key. Authorisation on the status and result endpoints, so users only see their own jobs. Cancellation support, cleanup of old results, and clear error states.

For stuff under a minute, just optimising the work might be enough. Anything longer, I'd go with this pattern, it's the reliable answer.

### scx | Production config has a value that nobody can explain. What do you do? | unknown config value, mystery configuration, undocumented setting, config archaeology, configuration ownership

### scx | Your service depends on a legacy system that is very slow. How do you protect your users? | slow legacy dependency, protect from slow dependency, legacy system bottleneck, wrap slow service, cache legacy data
Honestly I can't always fix the legacy system, but I can stop its slowness from becoming my users' problem.

I measure first. Which calls are slow, how slow, and how often my service calls it per user action. Sometimes the biggest issue is actually my side calling it too often.

Then the protections. Timeouts on every call, so a slow response fails fast instead of holding threads and connections. Paired with a circuit breaker, so when the legacy system is struggling, we stop hammering it and fail fast or degrade.

Caching, if the data rarely changes, reference data, configuration, cache it with a sensible TTL so most requests never touch the legacy system at all.

Async integration. For writes or long operations, queue the requests and process them in the background at a pace the legacy system can handle, and give the user an immediate acknowledgement.

A replicated read model. For data that's read a lot, keep a local copy synced through change data capture, events or a scheduled sync, and serve reads from it. Users get fast responses and accept a small delay in freshness.

Bulkheads, isolate calls to the legacy system in their own limited pool, so its slowness can't eat all my service's resources.

Graceful degradation, show what's available and clearly mark what couldn't load, instead of failing the whole page.

And longer term, these protections often end up being the first step of a strangler fig migration, replacing the legacy system piece by piece.

### scx | Error rates rise only during deployments. How do you get to zero-downtime releases? | errors during deployment, downtime during release, zero downtime deployment, deploy causes errors, graceful shutdown deploy
So if errors spike every time we deploy, something in the release process is either interrupting in-flight work or sending traffic to instances that aren't ready yet. I go through it phase by phase.

Instances starting. Are new ones getting traffic before they're ready, before caches warm, JIT finishes, connections are set up? The fix is readiness checks that only pass when the app can really serve, warm-up requests, and Application Initialization on IIS.

Instances stopping. Are old ones getting killed while handling requests? Take them out of the load balancer first, let connections drain with a deregistration delay, and implement graceful shutdown, so on SIGTERM the app stops taking new requests, finishes the in-flight ones and closes consumers cleanly within the timeout.

Capacity during rollout. If half the instances get replaced at once, the rest can get overloaded. Rolling updates with extra surge capacity mean capacity never drops.

Version incompatibility. During a rolling update, old and new run side by side and clients or other services hit both. So API changes have to be backward compatible, schema changes use expand and contract, and message formats need to be readable by both versions. This one can catch people out.

Sessions and state, in-memory sessions vanish when an instance stops, so keep services stateless with external session storage. And background workers, messages in progress at shutdown should be completed or returned to the queue, not lost.

I'd also track errors per deployment as a metric, so you can see things improving and catch regressions.

### scx | A cloud region or data centre has an outage. What do you do? | region outage, data centre outage, cloud outage response, failover to dr, disaster recovery activation
Okay, a full region or data centre outage is exactly what disaster recovery plans exist for. So the response follows the plan, not improvisation.

I confirm and assess first. Check the provider's status page and our own monitoring from outside the affected region. Work out which systems are hit and how long it might last, if the provider has an estimate.

Then decide whether to fail over. Failing over has its own risks and costs, especially with asynchronous replication, where you might lose some recent data, up to the recovery point objective. If the provider expects recovery soon, waiting might be better. Who decides and on what criteria is defined in the DR plan ahead of time, usually based on expected outage duration versus our recovery time objective.

If we fail over, promote the replicated databases in the secondary region, switch DNS or global load balancing over, start or scale up compute there from infrastructure as code, and verify the critical journeys. Keep users and stakeholders informed.

During the outage, track which data might be lost or in an uncertain state, like transactions that were in flight.

Fail back once the primary is healthy, resync data and switch back in a planned window. Honestly that's often harder than the failover itself.

Afterwards, review against the plan, measure the actual recovery time and data loss, and fix the gaps. The biggest thing is regular DR testing, because an untested DR plan usually fails right when you need it.
