### scx | A background job holds locks and blocks users. How do you fix it? | background job blocking users, long running batch locks, batch update blocking, job causes timeouts, chunked batch processing

### scx | An index maintenance job caused an outage. What went wrong and how do you fix it? | index rebuild outage, index maintenance blocking, rebuild index locks, online index rebuild, maintenance window issue
Index maintenance is meant to help performance, but done carelessly it can take locks, fill the transaction log and saturate I/O.

What usually goes wrong.

Offline rebuilds: on editions or settings without online operations, ALTER INDEX REBUILD takes a schema modification lock, blocking all access to the table for the duration. On a large table, that's minutes or hours of outage.

Log growth: rebuilding a big index generates a lot of transaction log, which can fill the log disk, especially if log backups don't run during the job, and in availability groups it can overwhelm replicas.

Running at the wrong time: overlapping with business hours in another region, or with batch jobs and backups.

Doing too much: rebuilding every index every night regardless of need, burning resources for little benefit.

Use online rebuilds, with WAIT_AT_LOW_PRIORITY so the rebuild yields to user queries, and resumable index operations, which can be paused and resumed.

Use a proven maintenance solution, like Ola Hallengren's scripts, with thresholds and time limits.

### scx | Money values are off by a cent in some calculations. How do you fix it? | rounding error money, floating point currency, decimal vs double money, off by one cent, rounding mode, precision loss json
Off-by-a-cent errors almost always come from using floating point types for money, or from inconsistent rounding.

Floating point: double and float in C#, and number in JavaScript, are binary floating point, which can't represent many decimal fractions exactly. 0.1 plus 0.2 isn't exactly 0.3. Summing many values accumulates tiny errors that eventually show up as a cent difference. Fix: use decimal in C#, and DECIMAL or NUMERIC with fixed scale in SQL, never FLOAT or REAL for money.

Rounding rules: .NET's Math.Round uses banker's rounding by default, rounding 2.5 to 2, while business users and other systems may expect away-from-zero rounding, 2.5 to 3. Use MidpointRounding explicitly, and agree on the rule with the business.

When to round: rounding each line and then summing gives a different total than summing and then rounding. The business rules must define which one, like rounding per line item for invoices, and the code must do it consistently everywhere, including reports and exports.

Front end: JavaScript numbers can lose precision on very large values, and calculations in the browser can disagree with the server. Do authoritative calculations on the server, send money as strings or with known scale if precision matters, and only format on the client.

Currency: different currencies have different numbers of decimal places, so the scale comes from the currency.

Then add tests with known tricky values and compare totals across the system.

The redesign is the asynchronous request-reply pattern.

The API validates the request quickly, creates a job record with a status like Pending, puts a message on a queue, and returns 202 Accepted with a job id and a status URL.

A background worker, a hosted service, a separate worker service or a function, picks up the message and does the work, updating the job's progress and status, and storing the result somewhere, like blob storage or a results table.

The client checks the status URL periodically, or receives a push notification through SignalR or email when it's done, then fetches the result.

Benefits: no request timeouts; work survives server restarts because it's queued; retries happen on failure; concurrency is controlled, so ten big jobs don't overload the database; and the UI can show progress and let users keep working.

Details to get right: idempotency, so a retried submission doesn't create duplicate jobs, using an idempotency key; authorisation on the status and result endpoints, so users only see their own jobs; cancellation support; cleanup of old results; and clear error states.

For moderately long operations, under a minute, simply optimising the work may be enough; for anything longer, this pattern is the reliable answer.

### scx | Production config has a value that nobody can explain. What do you do? | unknown config value, mystery configuration, undocumented setting, config archaeology, configuration ownership
A mystery value in production configuration is risky both ways: changing it might break something, and leaving it might be hiding a problem. So I investigate before touching it.

Find its history: source control history for config files and pipeline variables, deployment logs, change tickets, and the configuration store's audit history. Often a commit message or ticket explains why it was set, like a timeout increased during an incident years ago.

Find its usage: search the code for the key, including libraries and scripts, to see what reads it and what effect it has. Sometimes nothing reads it anymore, and it's a leftover.

Ask people: the team, previous owners, operations and the vendor documentation, if it's a framework setting.

Test the effect in a lower environment: change it there and observe, ideally with load or integration tests that exercise the related path.

Then decide: keep it and document why, change it through a normal change with monitoring, or remove it if unused, again through a normal change, not quietly.

Prevent future mysteries: keep all configuration in source control with meaningful commit messages, document non-obvious settings next to the value or in a configuration reference, use strongly typed options classes with validation and comments, and remove unused settings regularly.

In a regulated system, configuration values that affect validated behaviour need to be controlled anyway, so this kind of documentation is part of the expected evidence.

### scx | Your service depends on a legacy system that is very slow. How do you protect your users? | slow legacy dependency, protect from slow dependency, legacy system bottleneck, wrap slow service, cache legacy data
I can't always fix the legacy system, but I can stop its slowness from becoming my users' problem.

Measure first: which calls are slow, how slow, and how often my service calls it per user action. Sometimes the biggest issue is my side calling it too often.

Then apply protections.

Timeouts on every call, so a slow response fails fast instead of holding threads and connections. Paired with a circuit breaker, so when the legacy system is struggling, we stop hammering it and fail fast or degrade.

Caching: if the data changes rarely, like reference data or configuration, cache it with a sensible TTL, so most requests never touch the legacy system.

Asynchronous integration: for writes or long operations, put requests on a queue and process them in the background at a pace the legacy system can handle, giving users an immediate acknowledgement.

Replicated read model: for frequently read data, keep a local copy synchronised through change data capture, events or scheduled sync, and serve reads from it. Users get fast responses, accepting a small delay in freshness.

Bulkheads: isolate calls to the legacy system in their own limited pool, so its slowness doesn't consume all of my service's resources.

Graceful degradation: show what's available, and clearly mark what couldn't be loaded, rather than failing the whole page.

Longer term, these protections often become the first step of a strangler fig migration, replacing the legacy system piece by piece.

### scx | Error rates rise only during deployments. How do you get to zero-downtime releases? | errors during deployment, downtime during release, zero downtime deployment, deploy causes errors, graceful shutdown deploy
If errors spike every time we deploy, something in the release process interrupts in-flight work or sends traffic to instances that aren't ready.

Check each phase.

Instances starting: are new instances receiving traffic before they're ready, before caches warm, JIT completes or connections are established? Fix: readiness checks that only pass when the app can serve, warm-up requests, and Application Initialization on IIS.

Instances stopping: are old instances killed while handling requests? Fix: remove them from the load balancer first, let connections drain with a deregistration delay, and implement graceful shutdown, so the app stops accepting new requests, finishes in-flight ones and closes consumers cleanly on SIGTERM, within the timeout.

Capacity during rollout: if half the instances are replaced at once, the rest may be overloaded. Fix: rolling updates with extra capacity, like surge, so capacity never drops.

Incompatibility between versions: during a rolling update, old and new versions run together, and clients or other services may hit both. API changes must be backward compatible, database schema changes must use expand and contract, and message formats must be readable by both versions.

Sessions and state: in-memory sessions lost when an instance stops. Fix: stateless services with external session storage.

Background workers: messages in progress during shutdown should be completed or returned to the queue, not lost.

I measure errors per deployment as a metric, so improvements are visible and regressions get caught.

### scx | A cloud region or data centre has an outage. What do you do? | region outage, data centre outage, cloud outage response, failover to dr, disaster recovery activation
A full region or data centre outage is what disaster recovery plans are for, and the response follows the plan rather than improvisation.

Confirm and assess: check the provider's status page and our own monitoring from outside the affected region. Determine which systems are affected and the expected duration, if the provider has an estimate.

Decide whether to fail over: failing over has its own risks and costs, especially if data replication is asynchronous, where some recent data may be lost, up to the recovery point objective. If the provider expects recovery soon, waiting may be better. The decision criteria and who makes it are defined in the DR plan in advance, typically based on the expected outage duration versus our recovery time objective.

Fail over, if decided: promote the replicated databases in the secondary region, switch DNS or global load balancing to the secondary, start or scale up compute there, from infrastructure as code, and verify the critical journeys. Communicate to users and stakeholders.

During the outage, track what data may have been lost or is in an uncertain state, like transactions in flight.

Fail back: once the primary is healthy, resynchronise data and switch back in a planned window, which is often harder than the failover itself.

Afterwards: review against the plan, measure actual recovery time and data loss, and fix gaps. The most important preparation is regular DR testing, because an untested DR plan usually fails when it's needed.
