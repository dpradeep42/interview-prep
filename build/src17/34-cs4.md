### csx | What is reflection in .NET, and what does it cost? | reflection c#, system reflection, gettype getproperties, reflection performance, activator createinstance
Reflection lets code inspect and use types at runtime: list a type's properties, methods and attributes, read or set property values by name, call methods dynamically, and create instances with Activator.CreateInstance. A lot of framework magic is built on it: ASP.NET Core model binding and controller discovery, dependency injection containers, serialisers, ORMs like EF Core and Dapper mapping columns to properties, and test frameworks finding test methods.

The costs.

These all run work in parallel, but they suit different kinds of work.

Parallel.For and Parallel.ForEach are for CPU-bound work on in-memory data, like processing thousands of records with calculations. ### csx | How do memory leaks happen in .NET, and how do you find them? | memory leak dotnet, managed memory leak, event handler leak, find memory leak, dotnet-gcdump
.NET has a garbage collector, but leaks still happen whenever objects stay reachable when they shouldn't. The GC can't collect anything that something still references.

Common causes.

Event handlers: subscribing to a long-lived object's event, like a static event or a singleton service, from a short-lived object, and never unsubscribing. The publisher holds a reference to the subscriber forever.

Static collections and caches without limits: a static dictionary that only grows, or an in-memory cache with no size limit or expiration.

Captive dependencies: a singleton holding scoped or transient objects, which then live forever.

Timers and background tasks referencing objects they never release.

Unmanaged resources not disposed, like streams, database connections or native handles, which also leak memory outside the managed heap.

Closures and lambdas capturing large objects unintentionally, and held by long-lived delegates.

HttpClient created per request, leaking sockets rather than memory.

Finding them: watch the trend, with dotnet-counters or metrics showing GC heap size growing after each full GC, rather than levelling off. Take two memory snapshots some time apart, with dotnet-gcdump or a full dump with dotnet-dump, and compare them in Visual Studio, PerfView or another memory profiler: which types increased in count, and what's the retention path, meaning the chain of references keeping them alive. That path usually points straight to the event subscription or static collection responsible.

Fixes follow the cause: unsubscribe or use weak events, bound caches, fix lifetimes, and dispose properly.

### csx | How do you design immutable types in C#? | immutable types c#, immutability c#, immutable class, readonly properties, record with expression
An immutable object can't change after it's created. Any "change" produces a new object. This makes code easier to reason about, because nothing can modify an object behind your back, it's naturally thread-safe, and it's safe to use as a dictionary key or share in caches.

How I build them in C#.

Records are the simplest: positional records, like record Address(string Street, string City), have init-only properties, value equality, and with-expressions to create modified copies, like address with { City = "Pune" }.

For classes: properties with get only or init, set through the constructor or object initialisers, and required members to ensure they're set; fields marked readonly; no methods that modify state; methods that return new instances instead, like Money.Add returning a new Money.

Watch out for shallow immutability: a record with a List<string> property is not truly immutable, because the list can still be changed. Use IReadOnlyList with a copy, ImmutableArray or ImmutableList, or FrozenSet for collection properties, and copy incoming collections in the constructor.

readonly struct for small value types guarantees all fields are read-only.

Where I use immutability: value objects in the domain, like Money, DateRange or strongly typed ids; DTOs and messages, which shouldn't change after creation; configuration snapshots; and state in front-end code, like Redux, where the same idea applies.

The cost is more allocations when changing objects frequently, which is rarely an issue in business code, but matters in tight loops.

### csx | What does the volatile keyword do, and what is the .NET memory model? | volatile keyword c#, memory model dotnet, memory barrier, instruction reordering, volatile read write
Compilers, the JIT and CPUs are allowed to reorder memory reads and writes, and to cache values in registers, as long as single-threaded behaviour is unchanged. In multi-threaded code, this means one thread may not see another thread's writes when expected, or may see them in a different order.

The .NET memory model defines what's guaranteed. volatile on a field makes reads have acquire semantics and writes have release semantics: a volatile read always reads the current value from memory, and operations after it can't be moved before it; a volatile write makes all earlier writes visible before it. A classic use is a stop flag: private volatile bool _stopRequested; one thread sets it, and a worker loop checks it, without the JIT hoisting the read out of the loop and spinning forever.

What volatile doesn't do: it doesn't make compound operations atomic. count++ on a volatile field is still a read-modify-write race; Interlocked.Increment is needed for that. It also doesn't give full ordering between a write followed by a read.

In practice, I rarely use volatile directly. Higher-level tools are clearer and safer: lock, which includes full memory barriers; Interlocked for atomic updates; Volatile.Read and Volatile.Write methods for explicit cases; CancellationToken for stop signals instead of a volatile bool; and concurrent collections, Lazy<T> and Channels for coordination.

Knowing the memory model mainly helps me recognise subtle bugs in lock-free code, and avoid writing it unless really necessary.

TaskCompletionSource<T> lets you create a Task that you complete manually. You give the Task property to callers, who await it, and later your code calls SetResult, SetException or SetCanceled, or the Try versions, to complete it.

### csx | Server GC vs workstation GC: what is the difference? | server gc vs workstation gc, gc modes dotnet, concurrent gc, background gc, dotnet gc settings
The .NET garbage collector has modes tuned for different kinds of applications.

Workstation GC is designed for desktop and client apps. It uses a single heap and collects on the thread that triggered the collection, with lower memory usage, so it's friendly to machines running many processes.

Server GC is designed for high-throughput server apps. It creates a separate heap and a dedicated GC thread per CPU core, so allocations scale across cores and collections run in parallel, finishing faster. It uses more memory, because each heap has its own budget. ASP.NET Core apps use Server GC by default.

Both can run with concurrent, or background, GC enabled, which is the default: full, generation 2 collections mostly run in the background while application threads continue, reducing pauses.

Why it matters in practice.

Containers: with Server GC on a machine with many cores but a small memory limit, heap counts and memory usage can surprise you. .NET respects container CPU and memory limits, and you can tune with settings like GCHeapCount, GCHeapHardLimit, or the newer DATAS mode, dynamic adaptation to application sizes, on by default in .NET 9 for Server GC, which adjusts heap count to load and reduces memory for small apps.

Many small services on one host: Workstation GC, or DATAS, may be better to save memory.

Latency-sensitive work: GC latency modes, like SustainedLowLatency, can reduce blocking collections during critical periods.

I don't change GC settings by guess; I measure with dotnet-counters, looking at GC pause time, heap size and allocation rate, and then adjust.

COM interop, like automating Office, where APIs are loosely typed; dynamic made this much simpler.

Interop with dynamic languages, like IronPython.

Some reflection-heavy scenarios, where dynamic is shorter than reflection code, like calling a generic method with a runtime type, which uses dynamic dispatch to pick the right overload.

In business applications and APIs, I prefer strong types, DTOs and generics. If I see dynamic in a code review outside interop scenarios, I usually ask whether a proper type or JsonNode would be clearer.

### csx | How do you make a deep copy of an object in C#? | deep copy c#, shallow copy c#, clone object c#, memberwiseclone, record with shallow copy
A shallow copy creates a new object, but copies references for reference-type fields, so the copy and the original share nested objects. Changing a nested list in the copy also changes it in the original. A deep copy duplicates the nested objects too, so the copies are fully independent.

MemberwiseClone: a protected method on object that creates a shallow copy. You can call it from a Clone method in your class.

Records with with-expressions: also shallow. order with { Status = "Shipped" } copies the top-level values, but a List property is shared.

Manual copy methods or copy constructors: the most explicit and fastest; each class copies its own nested objects, like new Order(other) creating new item objects. Safe, but must be maintained when properties are added.
