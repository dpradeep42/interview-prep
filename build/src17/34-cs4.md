### csx | What does the volatile keyword do, and what is the .NET memory model? | volatile keyword c#, memory model dotnet, memory barrier, instruction reordering, volatile read write
Let me start with the problem. Compilers, the JIT and CPUs are allowed to reorder memory reads and writes, and cache values in registers, as long as single-threaded behaviour doesn't change. In multi-threaded code, that means one thread might not see another thread's writes when you expect, or sees them in a different order.

The .NET memory model defines what's guaranteed. volatile on a field gives reads acquire semantics and writes release semantics. A volatile read always reads the current value from memory, and operations after it can't move before it. A volatile write makes all earlier writes visible before it. The classic use is a stop flag. In practice I rarely use volatile directly. Higher-level tools are clearer and safer. lock, which includes full memory barriers. Interlocked for atomic updates. For me, knowing the memory model mostly helps me spot subtle bugs in lock-free code, and avoid writing lock-free code unless it's really necessary.

Workstation GC is meant for desktop and client apps. Single heap, collects on the thread that triggered the collection, lower memory usage, so it's friendly to machines running lots of processes.

Lots of small services on one host, Workstation GC or DATAS might be better to save memory. Latency-sensitive work, GC latency modes like SustainedLowLatency can reduce blocking collections during critical periods.

But my rule is, I don't change GC settings on a guess. I measure with dotnet-counters, GC pause time, heap size, allocation rate, and then adjust.
